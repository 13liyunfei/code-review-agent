0. 一页结论（TL;DR）

四句话：

  1. 锚点项目 alibaba/open-code-review 真实、活跃、Apache-2.0、Go、41,646★ / 192 贡献者，差异点是「确定性工程硬约束 + LLM Agent」混合架构与成体系的多语言内置规则集；但它明确不做 AST、不支持 Gitea、没有阻断式门禁。
  2. 本项目 code-review-agent 在两条线上已经领先锚点：① AST 语义分析（JavaParser + tree-sitter，OCR 全篇无 AST）；② Gitea 一等公民 + 多租户 + 成本治理（OCR 无 Gitea、无多租户、无成本口径）。这是可以对外讲的真实差异点，不是自我感觉。
  3. 本项目最大的三处落后：① 确定性规则层只有 3 个 Skill + 1 份 handbook（OCR 是 ~40 类文件/语言规则文档，四层优先级链）；② 完全没有阻断式质量门禁（全库 grep block|gate|failOn 命中 0）；③ 没有 CLI / Coding-Agent 插件 / MCP Server 出口（只有服务端 webhook）。
  4. 落地上分三档：P0 三项（规则层扩容、文件筛选闸门、质量门禁）不改架构即可做，本周就能开工；P1 四项（文件捆绑、定位+反思轮、审查级评测基准、出口层）需要新增模块；P2 两项（Semgrep 第二道闸门、可信度材料）涉外部依赖与法务，必须权衡。

三个「不要做」（下面 §7 有完整理由）：

  • ❌ 不要为了像 OCR 而把服务改成 Go CLI——OCR 的定位是"开发者本地一条命令"，本项目的定位是"平台上的一等服务"，改架构换来的是别人的形状。
  • ❌ 不要引入 AGPL / 非 OSI 的源码（Kodus AGPL-3.0+EE、LiveReview Sustainable Use License、Sweep EE License）——本项目是 MIT，混入会污染许可面。只借鉴设计，不抄代码。
  • ❌ 不要选 CodeQL 做第二道闸门——github/codeql 仓库的 MIT 只覆盖查询库，真正的 CLI/engine 是商业专有许可，没有 GHAS 时按其条款只能用于 GitHub.com 上的开源库，私有库跑 CI 即违约。

1. 业界项目分类地图

1.1 为什么按"它到底在哪一层动手"分类

同一批项目被混在一起时，最常见的误判是拿"审查载体"去比"审查能力"（例如问 Gerrit 和 AI-Jury 哪个强）。正确的分法是问三个问题：

  1. 它持有什么？（diff 与评论的托管权 / 分析能力 / 交付管道）
  2. 它什么时候被触发？（commit 前 / PR 打开 / 人工点一下）
  3. 它的输出是"给人看的"还是"给机器判的"？

1.2 四类地图

类别 它持有 触发点 输出 代表
A. AI 驱动类 LLM 推理 + 评论回写 PR 事件 / 评论 @ / CLI 给人和给机器都有 见 §1.3
B. 传统 / 平台型 diff 与评审流程的托管权（不做分析） 推 patchset / 提交评审请求 门禁判定（submit / Ship It） Gerrit、Phabricator→Phorge、Review Board
C. 静态分析 / Linter 集成类 确定性分析引擎或投递管道 pre-commit / CI / PR SARIF / issue 列表 SonarQube、Semgrep、CodeQL、reviewdog
D. 工具与机器人 编排：把 A/C 的能力塞进某个平台 平台事件 平台侧评论 / 状态检查 reviewdog、Mozilla Code Review Bot、ReviewBot

关键洞察：B 类在"什么算通过"这件事上的成熟度远高于 A 类。Gerrit 的 submit requirements、Review Board 的 Ship It 是可审计的门禁语义；而绝大多数 A 类项目（包括 OCR）只做"发评论"，不做 fail the build。本项目要补的门禁，正确做法是借 B 类的语义，而不是抄 A 类的代码。

2.3 三个"选型场景"里谁赢

  • 想要"最接近 OCR 的体验" → 只有 OCR 自己（它的体验来自 CLI + 规则集 + Session Viewer 的组合，缺一个都不像）。
  • 想要"私有化 + Gitea + 自托管 GitLab 一次齐活" → PR-Agent 与 LiveReview 是仅有的两家。
  • 想要"阻断式门禁" → LiveReview（jq + GET /ci-rulesets/:id/evaluate 按 HTTP 状态阻断）；合规面是 Kodus Enterprise（SSO/RBAC/audit/SOC 2）与 SonarQube Quality Gate。

3. 三类典型方案：适用场景与优缺点

3.1 方案一 · 可自托管 AI Agent 类

代表：Kodus、LiveReview、OCR（自托管 GitLab 形态）、本项目 形态：一个常驻服务 + webhook 接入 + 队列 + 存储（PG/向量库）+ 控制台

内容
适用 代码不能出网；要团队级知识库/规则；要审计与成本口径；要多平台多租户；要接内部系统（工单/IM）
优点 数据可控；能力可堆叠（RAG / 记忆 / 校准 / 成本）；能覆盖"组织级"的横切需求（租户、配额、审计）
缺点 运维成本：PG + 向量库 + Redis + 迁移 + 容量；上线周期长；升级即风险（配置/迁移耦合）
本项目的位置 已经在这条路上，且比 OCR 多做了横切面（多租户 / 成本 / 可观测）。方向没错，缺的是规则层与出口层

3.2 方案二 · GitHub Action 轻量集成类

代表：ChatGPT-CodeReview（4,467★）、shippie（2,505★）、PR-Agent Action、reviewdog 形态：uses: xxx@v0 一行接入，跑在 runner 上，无服务端

内容
适用 个人/小团队快速试用；只想"每条 PR 自动多一双眼睛"；不想运维
优点 5 分钟能用；零基础设施；成本随用量；失败即失败，不污染别的系统
缺点 无状态：没有记忆、没有团队知识、没有跨 PR 的跟踪（Kodus 的 "Kody Issues" 这类能力天然没有）；无多租户；token 出网；细粒度权限受限（pull_request_target 的安全陷阱）
意外结论 这一类不是本项目的竞争对手，而是本项目的"入口"——Action 可以只做"调我们服务的 API"，见 §5 P1-8

3.3 方案三 · 静态分析 + AI 混合类

代表：Semgrep + LLM、SonarQube + LLM、OCR（规则文本 + LLM，注意它做的不是真 AST）、Kodus（tree-sitter AST + LLM） 形态：确定性层先跑（模式/类型/污点），LLM 只看"确定性层标记过的东西"或做解释

内容
适用 有合规/审计要求；要可复现的结论；要可门禁（"新增严重问题数 = 0"这种硬阈值）
优点 结论可复现、可举证（这是 AI 单独给不了的）；成本低（确定性层不烧 token）；天然适合做门禁
缺点 事实上的"两种技术栈"要维护；误报率是这类工具的主要敌人（假警报多了就被关掉）；语言覆盖受规则生态限制
关键判断 "混合"有两种完全不同的混法：
· OCR 式：规则是文本注入 prompt（便宜、覆盖广、但不理解语法树）
· Kodus 式：AST + Code Knowledge Graph 喂给 LLM（贵、语言少、但结构信息真实）
本项目已有第二种的底子（JavaParser + tree-sitter），却还没把它变成"审查输入" → 见 §5 P1-9

# 差距 缺了会出什么事（不是"功能少"，是故障形态） 参照
1 无阻断式门禁 审查结论没有任何下游消费者——被忽略的 P0 问题照样合入；"审查通过"这句话在系统里不存在，无法审计 LiveReview、Gerrit submit requirements、SonarQube Quality Gate
2 确定性规则层过薄（3 个 Skill / 1 份 handbook） 规则覆盖率低 → "没报问题"被读成"没有问题"；且团队规范（唯一那份 handbook）是全局的，无法按团队/按文件模式生效 OCR 四层优先级 + ~40 类规则文档
3 无文件筛选闸门 把 .env / .ssh/** / 二进制 / vendor 目录的 diff 送进 LLM ⇒ 密钥出网 + token 白烧；反过来又可能漏掉重要变更 OCR selection.go 六道闸门 + secret 路径优先于用户规则
4 无文件捆绑（bundling） 相关文件被拆到不同 Agent 的上下文里 ⇒ 跨文件不一致审不出来（如 i18n 两份 properties、DTO 与契约） OCR smart file bundling（message_en/zh.properties 绑成一个单元，每 bundle 一个隔离上下文的 sub-agent）
5 无"定位 + 反思"独立环节 行级评论位置漂移 ⇒ 评论挂在错误的行上，比不评论更伤信任 OCR 的 external positioning + reflection modules；AI-Jury 的 verify 轮
6 无审查级评测基准 改 prompt / 换模型之后无法回答"是不是变好了"；"精度换噪音"这类取舍没有数据支撑，只能靠感觉 OCR 的 Alibaba-Aone/aacr-bench（50 仓库 / 200 PR / 10 语言 / 1,505 条 ground truth / 80+ 人交叉标注）
7 无 CLI / Coding-Agent 插件 / MCP Server 出口 开发者只能在平台上等 webhook；无法"本地先跑一遍"，也就无法在提交前发现问题（审查的价值被推迟到 PR 阶段） OCR：ocr review/scan/session --resume + Claude Code/Codex/Cursor 插件 + MCP Server + Session Viewer
8 平台面窄（仅 Gitea + GitLab） 面向 GitHub 用户时根本无法接入；企业里 Bitbucket / Azure DevOps 场景直接出局 PR-Agent 五平台、LiveReview 五平台
9 AST 结果没有变成"审查输入" 已经有 JavaParser + tree-sitter + 调用图，但审查路径里没有把它作为结构化上下文注入（Kodus 的 CALLS/IMPORTS/EXTENDS/IMPLEMENTS + 影响面 0/1/2/N 分级是现成参照） Kodus、Semgrep generic AST

4.3 反向优势（可以对外讲的真实差异点，3 条）

  1. AST 语义分析：OCR 明确不做 AST，Kodus 的 AST 微服务已归档（kodustech/kodus-service-ast archived: true）。本项目把 JavaParser + tree-sitter + 调用图留在主干里，这是稀缺的。
  2. Gitea 一等公民：OCR 不支持 Gitea，Kodus 只覆盖 Forgejo（Gitea 的 fork，不做等价断言）。同时支持 Gitea + 自托管 GitLab 的，全生态只有 PR-Agent、LiveReview、本项目三家。
  3. 横切面完备：多租户（team 级隔离 + 知识/记忆/历史/反馈/规则全套）、成本治理（独立 token-factory）、全链路轨迹（对应 harness 的 "Model-visible means logged" 不变式）——OCR、PR-Agent、ChatGPT-CodeReview 三家一个都没有。

5. 优化方案：最佳实践 → 拟改进点 → 优先级

每条给：借鉴自谁 / 为什么 / 怎么做 / 验收判据。验收判据一律是可机械检查的，不接受"感觉好了"。

P0 · 不改架构即可落地（三周内可完成，收益最大）

P0-1 · 确定性规则层扩容：从「3 个 Skill」到「文件模式 → 规则文档」四层链

  • 借鉴：OCR 的 system_rules.json + 四层优先级（--rule > 项目 .opencodereview/rule.json > 全局 ~/.opencodereview/rule.json > 内置 system 层），以及它的"文件模式 → 规则文档"映射。
  • 为什么：现在 core/skill/impl/ 只有 3 个 Skill、resources/handbook/ 只有 1 份全局 Java 规范 ⇒ 规则命中率和"按团队/按路径生效"两个能力都不存在。这是最容易见效的一处。
  • 怎么做（4 步）：
    1. 在 resources/ 下新建 rules/ 目录，按文件模式组织（**/*mapper*{mapper,dao}*.xml、pom.xml、application*.yml、**/*.sql、**/*.java 等），每份是一段 markdown 规则文本；
    2. 在 core/skill 里加一层 RuleResolver，四级覆盖链：请求级（API 参数）> 团队级（team 隔离的存储）> 全局 > 内置 rules/；
    3. 结构上保持"永远有规则可解析"——内置层不可被覆盖为空（OCR 的设计要点）；
    4. 把已命中的规则文档写进 ReviewTrajectory（可追溯）。
  • 验收判据：① find src/main/resources/rules -name '*.md' | wc -l ≥ 15；② 对 10 个真实 PR 跑一遍，规则命中率（至少命中一条规则文档的 diff 占比）≥ 90%，且命中清单可从轨迹里读出；③ 故意把团队级规则置空，请求仍能跑通（验证"不可覆盖为空"）。

P0-2 · 文件筛选闸门 + 密钥路径保护（safe-by-default）

  • 借鉴：OCR internal/agent/selection.go 的六道闸门：binary → secret_exclude → user_exclude → user_include → unsupported_ext → default_path；以及"secret 路径优先于用户规则、include 也无法覆盖"这条硬约束。另有"diff 单独超过 max_tokens 80% 即判 too_large"。
  • 为什么：这是唯一一条既省钱又防泄露的改动。当前没有任何筛选 ⇒ .env / 密钥文件 / 二进制 / target/ 构建产物都可能进 prompt。
  • 怎么做（3 步）：
    1. 实现 PathGate 链（六道闸门按固定顺序，短路求值）；
    2. 内置 secret 清单（**/.ssh/**、**/.npmrc、**/.pypirc、**/.dockercfg、除 *.example/*.sample 外的 .env*…），且放在用户 include 之前；
    3. 每个被拦掉的路径记 ${reason}（secret_exclude / binary / too_large…），进轨迹并可在控制台按原因聚合。
  • 验收判据：① 造一个含 .env + *.jar + target/ 的测试 PR，三者全部不出现在送审清单里，且原因可查；② 用户显式 include: .env 时仍被拦（这条最容易做错）；③ 拦掉的路径数进指标端点。

P0-3 · 阻断式质量门禁（fail the build）

  • 借鉴：LiveReview 的 jq 规则 + GET /ci-rulesets/:id/evaluate 按 HTTP 状态阻断合并（README 给了三档团队策略的 jq 示例，安全敏感团队的规则是 (.counts.by_category.security > 0) or (.counts.by_severity.critical > 0) 即阻断）；语义层借 Gerrit 的 submit requirements。
  • 为什么：这是本项目最大的结构性缺口（全库 grep 命中 0）。没有门禁，审查结论就只是"一条没人看的评论"，也就不可能有"审查通过"这个状态可审计。
  • 怎么做（4 步）：
    1. 把 ReviewReport 派生出规范化计数（counts.by_severity.* / counts.by_category.*）——这是门禁规则的判据面；
    2. 新增 RuleSet 实体（按团队隔离，复用现有多租户存储），规则正文是可执行的表达式（Java 侧可用 SpEL / MVEL，或直接存 jq 并 shell 出去）；
    3. 新增端点 POST /api/rulesets/{id}/evaluate，入参是 reportId，返回 HTTP 200/409（冲突即"门禁失败"）；
    4. 平台侧：Gitea/GitLab 的 commit status / pipeline 步骤接入该端点——评论照发，但构建要红。
  • 验收判据：① 造一个含 Critical 安全问题的 PR，门禁端点返回非 2xx 且 Gitea 上该 PR 的检查状态为 failed（在平台 UI 上肉眼可见）；② 同一个 PR 修掉问题后状态转 success；③ 门禁判据（用的哪条规则、读了哪几个计数）能在报告里回读——"为什么红"必须可回答。

P1 · 需要新增模块（一个月量级）

P1-4 · 文件捆绑（bundling）：把「按维度并行」补成「按维度 × 按 bundle」二维

  • 借鉴：OCR 的 smart file bundling——把相关文件打包为一个审查单元，每个 bundle 作为一个隔离上下文的 sub-agent 并发跑（README 举的例子就是 message_en.properties 与 message_zh.properties 必须在一起）。
  • 为什么：本项目现在的并行是星型按维度 fan-out（5 个 Agent 各审全部 diff）。这解决"专业分工"，但没解决"同一改动散落在多个文件"——i18n、DTO+契约、SQL+实体这三类不一致必然审不出来。
  • 怎么做：在 ReviewContext 里引入 Bundle 维度；先做三类静态可判的捆绑规则（同 basename 不同语言后缀 / 同名 .xml mapper 与 @Mapper 接口 / entity 与 migration SQL），再考虑按调用图聚簇（这里正好能复用 core/analysis 的调用图）。
  • 验收判据：① 造一个"改了 message_zh.properties 但没改 message_en.properties"的 PR，审查必须报出这一条（当前基线：报不出，先测出基线再改）；② bundle 数与 sub-agent 并发数在轨迹里可读。

P1-5 · 定位校验 + 反思轮（把"评论挂错行"变成可检出缺陷）

  • 借鉴：OCR 的 external positioning + reflection modules；AI-Jury 的 verify + synthesis 轮（三段式：并行评审 → 自适应辩论 → 验证裁决，且带"去假阳性验证轮"）。
  • 为什么：行级评论位置漂移是最伤信任的一类错误（比漏报更伤）。本项目有行内评论 + Apply 按钮，但没有独立的定位校验环节。
  • 怎么做（3 步）：
    1. 加 PositionVerifier：拿 finding 的 file+line 回到 diff 原文核对，对不上就降级为"文件级评论"或丢弃；
    2. 加一轮反思调用：只把"高严重度 + 低置信度"的 finding 送去复核（成本可控，不要把全部送一轮）；
    3. 反思的输入里显式带上引用原文，输出必须是"保留 / 降级 / 丢弃 + 理由"，理由入轨迹。
  • 验收判据：① 构造 10 条故意错位的 finding，位置校验必须拦下全部；② 反思轮的 token 增量 ≤ 总 token 的 15%（超了就不划算）；③ 保留/丢弃的理由可回读。

P1-6 · 审查级评测基准（回答"改完到底变好没有"）

  • 借鉴：OCR 的 Alibaba-Aone/aacr-bench（50 个热门开源仓库 / 200 个真实 PR / 10 种语言 / 1,505 条 ground-truth issue / 80+ 资深工程师交叉标注），以及它敢把"Recall 低于通用 Agent"写在 README 里这件事本身。
  • 为什么：本项目已有 RagEvaluator + golden 检索指标（hit@k / MRR），但那是检索级的；审查结论级的 precision / recall 完全没有。没有它，任何 prompt 或模型改动都是不可验证的。
  • 怎么做（4 步）：
    1. 选 20 个 PR（自己仓库的历史 PR + 2 个开源仓库的真实 PR），人工标注 ground-truth issue；
    2. 定义三个指标：precision（报出的问题里真问题占比）/ recall（真问题里报出占比）/ 噪音比（每 PR 平均评论数）；
    3. 把 ReviewReplay（确定性回放）接到这套基准上——保证"同输入同输出"，否则指标不可比；
    4. 基准跑分写进 CI，回归即红。
  • 验收判据：① 基准集 ≥ 20 PR / ground-truth issue ≥ 60 条；② 同一次改动前后两次跑分可复现（同输入同输出）；③ 报告里必须显式写出当前是"精度优先"还是"召回优先"以及理由——这是 OCR 教给我们最重要的一条纪律。

P1-7 · 出口层：CLI + MCP Server + Coding-Agent 插件

  • 借鉴：OCR 的 ocr review（workspace / --from/--to merge-base / --commit）、ocr scan（无 git 历史也可全文件扫描）、ocr session list、ocr review --resume <session-id>、Coding-Agent 插件（Claude Code / Codex / Cursor / Kimi Code / OpenCode）、官方 MCP Server、Session Viewer（回放会话、把评论标为 fixed/ignored）。
  • 为什么：本项目已经有 core/resume（断点续跑）与 core/trajectory（事件源轨迹）——能力都在，只是没有出口。没有 CLI/插件，审查只能发生在 PR 阶段；提交前的那一步是空的。
  • 怎么做（按性价比排序）：
    1. MCP Server（最便宜）：把"审查本地 diff / 取某次审查的 finding / 标记已修"暴露为 3–5 个工具，复用现有 REST 层；
    2. CLI（次便宜）：一个薄壳（cr review --staged / --base main），调 REST；
    3. Session Viewer：控制台已有 Skills 市场/知识库，加一个"审查会话回放"页，把 ReviewTrajectory 渲染出来；
    4. Coding-Agent 插件：最后做（它依赖前三个稳定）。
  • 验收判据：① MCP Server 在 Claude Code 里能被发现并成功调用一次真实审查；② CLI 能对未提交的 staged diff 出结论（这条是"提交前闸门"的前提）；③ Session Viewer 能回放出至少一次完整审查的全部阶段耗时。

P1-8 · 平台面补齐（GitHub 优先）

  • 借鉴：PR-Agent / LiveReview 的五平台面；OCR 的 examples/ 组织方式（每个平台一个目录 + 一份 recipe 文件）。
  • 为什么：现在 integration/ 只有 gitea + gitlab ⇒ GitHub 用户接不进来，开源项目的"可试用面"直接砍半。而 Gitea 是本项目的差异点，不该被"平台太少"拖累。
  • 怎么做：抽 GitPlatformClient 接口（现在两个包各自实现），新增 github 实现（webhook 签名 + commit status + inline comment），然后按同样的 recipe 补 Bitbucket / Azure DevOps。这一步和第 P0-3 门禁是同一件事的两面（门禁要靠 commit status）。
  • 验收判据：① 在 GitHub 上提一个 PR，端到端出评论 + 门禁状态；② 平台适配层新增一个平台不修改审核内核（用 diff 里"改动只在 integration/github/"来证明）。

P1-9 · 把 AST 结果变成审查输入（兑现已有优势）

  • 借鉴：Kodus 的 tree-sitter 9 语言 → Code Knowledge Graph（节点 + CALLS / IMPORTS / EXTENDS / IMPLEMENTS 关系）+ 影响面按层级 0/1/2/N 分组；Semgrep 的 generic AST 思路。
  • 为什么：本项目有 core/analysis 18 文件 / 2,709 行（JavaParser + tree-sitter + 调用图 + 影响面），却在审查路径里没用起来 ⇒ 优势只是"存在于仓库里"。这是唯一一条"投入产出比最高"的增强：基础设施已付过账了。
  • 怎么做（3 步）：
    1. 在 ReviewContext 里加 structuralContext：对每个改动点给出调用方清单（含层级）+ 被调方 + 继承/实现关系；
    2. 按影响面分层，只把"层级 0/1 + 跨模块"的部分注入 prompt（全部注入必然爆预算）；
    3. 关系类型对齐 Kodus 的四类命名，便于和业界文档对话。
  • 验收判据：① 造一个"改了被 30 处调用的公共方法"的 PR，审查输出里必须提到影响面（当前基线：不提）；② 结构上下文的 token 占比 ≤ 上下文预算的 25%；③ 影响面数据在报告里可回读。

P2 · 涉外部依赖与法务，必须先权衡

P2-10 · 第二道确定性闸门：选 Semgrep CE，不选 CodeQL / SonarQube

  • 结论与理由（三条硬事实）：
    • ✅ Semgrep CE：引擎 LGPL-2.1，无人数限制、无需登录；官方规则是 Semgrep Rules License v1.0，只在"卖竞争性扫描 SaaS"时受限，内部使用 OK。最易落地，但要接受它的边界：卡单文件模式与密钥类，卡不住跨文件污点。
    • ⚠️ SonarQube：核心 LGPL-3.0 可商用，但内置分析器自 2024-11-29 起改为 SSALv1，SSAL 明文禁止在自带功能之外用 AI 与软件交互 ⇒ 想把它接进自研 LLM 链路必须法务确认。
    • ❌ CodeQL：github/codeql 的 MIT 只覆盖查询库，CLI/engine 是商业专有许可；无 GHAS 时只能用于 GitHub.com 上的开源库，私有库跑 CI 即违约。
  • 怎么做：Semgrep CE 跑在送审之前（正好接在 P0-2 的闸门之后），输出 SARIF，只把命中项交给 LLM 解释（而不是让它重审一遍），并把严重级映射到 P0-3 的计数里。
  • 验收判据：① 一次扫描的 SARIF 条目数与 LLM 调用数都可比对；② LLM 侧对"Semgrep 已标记项"的解释覆盖率 ≥ 90%；③ 许可清单进 NOTICE，写明规则集许可与边界。

P2-11 · 可信度材料（把"能交付"变成"可举证"）

  • 借鉴：OCR 的 ASSURANCE_CASE.md + OpenSSF Best Practices Gold 徽章（它把合规材料当产品的一部分）。
  • 为什么：企业采购问的第一个问题往往不是"准不准"，而是"凭什么信你"。
  • 怎么做：补 SECURITY.md（威胁模型 + 已知边界）、ASSURANCE_CASE.md（每项安全主张对应的实现与证据）、NOTICE（第三方许可）、SBOM；把 P2-10 的 Semgrep 集成写进威胁模型。
  • 验收判据：① 每一条安全主张都指向一个可执行证据（测试名或脚本名），不允许"设计上支持"这种话；② NOTICE 覆盖全部直接依赖。

6. 工具选型建议（四个场景）

场景 首选 备选 不要选 / 注意
① 最接近 open-code-review 体验 alibaba/open-code-review 本身：Apache-2.0、41,646★、CLI ocr、~40 类规则、25 个 provider、Session Viewer。"像 OCR"只有 OCR 自己 The-PR-Agent/pr-agent（要自托管服务 + 五平台时） 注意 OCR 无 Gitea、无门禁；kodustech/kodus-ai 是 AGPL-3.0+EE，用于商业产品前必须过法务
② 私有化本地模型（代码不出网） Nayjest/Gito：README 明确列出 Ollama / vLLM / llama.cpp / SGLang / LM Studio，LLM_API_BASE 指自托管端点，原话 "If you use a local model, your code never leaves your network" OCR + Ollama（官方有逐行配置，但约束：本地模型必须支持 native tool calling）；LiveReview（Ollama + "no code leaves your network"）；AI-Jury（vendor="local" 默认 http://localhost:11434/v1） ❌ diffray（未声明本地模型，FAQ 说代码送给 Claude/Cursor）；❌ shippie（provider 只有 Anthropic/OpenAI/OpenRouter/Cloudflare Workers AI）；❌ Tabby（本地化最彻底但不是审查工具，只能当本地模型基础设施参考）
③ 快速启用（5 分钟） anc95/ChatGPT-CodeReview（ISC，GitHub Action 一行 uses:，4,467★） mattzcarey/shippie（MIT，uses: mattzcarey/shippie@v0，可 /shippie review 按需触发）；PR-Agent Action 注意三者都只有单次/少量 LLM 调用：无记忆、无团队知识、无跨 PR 跟踪。它们适合"先看一眼"，不适合做质量体系
④ 企业级质量门禁 HexmosTech/LiveReview：唯一有完整"阻断式门禁"文档的项目——写 jq 规则 + GET /ci-rulesets/:id/evaluate，用 HTTP 状态阻断合并，README 给了三档团队策略示例 SonarQube（Quality Gate 是行业事实标准：New Code 覆盖率/重复率/严重问题数阈值）；Semgrep CE（pre-commit / CI 阻断，许可最干净）；Gerrit 3.14（AiCodeReviewProvider + submit requirements，评审载体自带门禁） ❌ OCR 没有门禁（它只发评论）；LiveReview 是非 OSI 的 fair-code 许可，不能抄代码，只能借鉴设计；Kodus 的合规面（SOC 2/RBAC/audit）在 Enterprise 版

一句话选型：

要看齐体验 → 直接用 OCR；要私有化 → Gito 最明确；要快 → ChatGPT-CodeReview/shippie；要门禁 → LiveReview 的 jq+HTTP 设计 + SonarQube 的阈值语义（代码自己写，因为它和本项目同源收益最大）。

9.4 全量回归的实况

mvn test：Tests run: 396, Failures: 0, Errors: 0, Skipped: 1（BUILD SUCCESS）。

上一轮记录的 1 个 Errors（TokenFactoryIntegrationTest.factory_provider_reads_usage_and_actual_provider）本轮已修，并顺带把它从「疑似环境问题」钉成了确凿的契约不一致：

  1. 反编译实际生效的 token-factory-client-0.1.0.jar 可见：ChatCompletionResponse 的第 7 个 record 组件是 TfExtension tf，而 provider() / upstreamModel() / costMicros() / traceId() / latencyMs() 五个访问器全部委托给 tf；requireExtension() 在 tf == null 时抛的正是那条「响应缺少 tf 扩展块」——所以这次是客户端对的、测试桩错的；
  2. 修法是只改测试桩（把扩展字段移进 tf 对象），不动生产代码；
  3. tf 内部字段是 snake_case（upstream_model / cost_micros / trace_id / latency_ms）。这一条是实测得到的，不是读注解推出来的：先按「TfExtension 只有 @JsonIgnoreProperties、没有 @JsonNaming」推断为 camelCase，跑出来 upstreamModel() 为 null（回落到别名 default），说明外层的 @JsonNaming(SnakeCaseStrategy) 会作用到嵌套 record 的属性命名上；

⇒ 教训：依赖 jar 的 wire format 要以「实际生效的二进制」为准，不能以 sources jar 或印象为准——本仓拿到的 -sources.jar 还是更早的平铺版本，照它修会继续错。 ⇒ 另：Skipped: 1 是显式跳过的基线刷新入口（只在 -Dbench.updateBaseline=true 时跑），不是漏跑。
