## 0. 一页结论（TL;DR）

**四句话**：

1. **锚点项目 `alibaba/open-code-review` 真实、活跃、Apache-2.0、Go、41,646★ / 192 贡献者**，差异点是「**确定性工程硬约束 + LLM Agent**」混合架构与成体系的多语言内置规则集；但它**明确不做 AST**、**不支持 Gitea**、**没有阻断式门禁**。
2. **本项目 `code-review-agent` 在两条线上已经领先锚点**：① **AST 语义分析**（JavaParser + tree-sitter，OCR 全篇无 AST）；② **Gitea 一等公民 + 多租户 + 成本治理**（OCR 无 Gitea、无多租户、无成本口径）。这是可以对外讲的**真实差异点**，不是自我感觉。
3. **本项目最大的三处落后**：① **确定性规则层只有 3 个 Skill + 1 份 handbook**（OCR 是 ~40 类文件/语言规则文档，四层优先级链）；② **完全没有阻断式质量门禁**（全库 grep `block|gate|failOn` **命中 0**）；③ **没有 CLI / Coding-Agent 插件 / MCP Server 出口**（只有服务端 webhook）。
4. **落地上分三档**：**P0 三项**（规则层扩容、文件筛选闸门、质量门禁）**不改架构即可做**，本周就能开工；**P1 四项**（文件捆绑、定位+反思轮、审查级评测基准、出口层）需要新增模块；**P2 两项**（Semgrep 第二道闸门、可信度材料）涉外部依赖与法务，**必须权衡**。

**三个「不要做」**（下面 §7 有完整理由）：
- ❌ **不要为了像 OCR 而把服务改成 Go CLI**——OCR 的定位是"开发者本地一条命令"，本项目的定位是"平台上的一等服务"，改架构换来的是别人的形状。
- ❌ **不要引入 AGPL / 非 OSI 的源码**（Kodus `AGPL-3.0+EE`、LiveReview `Sustainable Use License`、Sweep `EE License`）——本项目是 MIT，混入会污染许可面。**只借鉴设计，不抄代码。**
- ❌ **不要选 CodeQL 做第二道闸门**——`github/codeql` 仓库的 MIT **只覆盖查询库**，真正的 CLI/engine 是**商业专有许可**，没有 GHAS 时按其条款**只能用于 GitHub.com 上的开源库**，私有库跑 CI 即违约。

## 1. 业界项目分类地图

### 1.1 为什么按"它到底在哪一层动手"分类

同一批项目被混在一起时，最常见的误判是**拿"审查载体"去比"审查能力"**（例如问 Gerrit 和 AI-Jury 哪个强）。正确的分法是问三个问题：

1. **它持有什么？**（diff 与评论的托管权 / 分析能力 / 交付管道）
2. **它什么时候被触发？**（commit 前 / PR 打开 / 人工点一下）
3. **它的输出是"给人看的"还是"给机器判的"？**

### 1.2 四类地图

| 类别 | 它持有 | 触发点 | 输出 | 代表 |
|---|---|---|---|---|
| **A. AI 驱动类** | LLM 推理 + 评论回写 | PR 事件 / 评论 @ / CLI | 给人和给机器都有 | 见 §1.3 |
| **B. 传统 / 平台型** | **diff 与评审流程的托管权**（不做分析） | 推 patchset / 提交评审请求 | 门禁判定（submit / Ship It） | Gerrit、Phabricator→Phorge、Review Board |
| **C. 静态分析 / Linter 集成类** | **确定性分析引擎**或**投递管道** | pre-commit / CI / PR | SARIF / issue 列表 | SonarQube、Semgrep、CodeQL、reviewdog |
| **D. 工具与机器人** | 编排：把 A/C 的能力塞进某个平台 | 平台事件 | 平台侧评论 / 状态检查 | reviewdog、Mozilla Code Review Bot、ReviewBot |

**关键洞察**：**B 类在"什么算通过"这件事上的成熟度远高于 A 类**。Gerrit 的 submit requirements、Review Board 的 Ship It 是**可审计的门禁语义**；而绝大多数 A 类项目（包括 OCR）只做"发评论"，**不做 fail the build**。本项目要补的门禁，正确做法是**借 B 类的语义**，而不是抄 A 类的代码。

### 1.4 C 类（静态分析）的关键：**许可差异比能力差异更要命**

| 项目 | 引擎许可 | 规则/查询许可 | 能不能进商业产品 | 一句话定位 |
|---|---|---|---|---|
| **Semgrep CE** | **LGPL-2.1（最干净）** | Semgrep Rules License v1.0（源码可用、非 OSI） | ✅ 引擎可用可改；**规则在"卖竞争性扫描 SaaS"时受限**，内部用 OK | 单文件模式 + 密钥类，最易落地；**卡不住跨文件污点** |
| **SonarQube** | 核心 LGPL-3.0 | **内置分析器自 2024-11-29 起改为 SSALv1（源码可用、非 OSI）** | ⚠️ **有雷**：SSAL 明文**禁止在自带功能之外用 AI 与软件交互** → 想喂给自研 LLM **必须法务确认** | 复杂度 / 重复率 / 覆盖率等**质量阈值**是行业基准 |
| **CodeQL** | **CLI/engine 商业专有**（`github/codeql` 的 MIT 只覆盖查询库） | 查询库 MIT | ❌ 无 GHAS 时**只能用于 GitHub.com 上的开源库**；私有库跑 CI 即违约 | 跨文件 CWE/注入类最强，**许可最难** |
| reviewdog | MIT | — | ✅ | **自身零分析引擎**，只是 SARIF/errorformat → PR 评论的**投递管道** |
| Mozilla Code Review Bot | MPL-2.0 | — | ✅ | 编排型：调用外部分析器投递到 Phabricator |

**结论（用于 §5 的选型）**：要做"确定性第二道闸门"，**Semgrep CE 是许可最干净的入口**（但要注意：它只卡单文件模式与已知模式，**别指望它做跨文件污点分析**）；**CodeQL 直接排除**（许可）；**SonarQube 的分析器要过法务**。

### 2.3 三个"选型场景"里谁赢

- **想要"最接近 OCR 的体验"** → 只有 OCR 自己（它的体验来自 CLI + 规则集 + Session Viewer 的组合，缺一个都不像）。
- **想要"私有化 + Gitea + 自托管 GitLab 一次齐活"** → **PR-Agent** 与 **LiveReview** 是仅有的两家。
- **想要"阻断式门禁"** → **LiveReview**（jq + `GET /ci-rulesets/:id/evaluate` 按 HTTP 状态阻断）；合规面是 **Kodus Enterprise**（SSO/RBAC/audit/SOC 2）与 **SonarQube Quality Gate**。

## 3. 三类典型方案：适用场景与优缺点

### 3.1 方案一 · 可自托管 AI Agent 类
**代表**：Kodus、LiveReview、OCR（自托管 GitLab 形态）、本项目
**形态**：一个常驻服务 + webhook 接入 + 队列 + 存储（PG/向量库）+ 控制台

| | 内容 |
|---|---|
| **适用** | 代码不能出网；要团队级知识库/规则；要审计与成本口径；要多平台多租户；要接内部系统（工单/IM） |
| **优点** | 数据可控；能力可堆叠（RAG / 记忆 / 校准 / 成本）；能覆盖"组织级"的横切需求（租户、配额、审计） |
| **缺点** | **运维成本**：PG + 向量库 + Redis + 迁移 + 容量；**上线周期长**；**升级即风险**（配置/迁移耦合） |
| **本项目的位置** | **已经在这条路上，且比 OCR 多做了横切面**（多租户 / 成本 / 可观测）。**方向没错，缺的是规则层与出口层** |

### 3.2 方案二 · GitHub Action 轻量集成类
**代表**：ChatGPT-CodeReview（4,467★）、shippie（2,505★）、PR-Agent Action、reviewdog
**形态**：`uses: xxx@v0` 一行接入，跑在 runner 上，无服务端

| | 内容 |
|---|---|
| **适用** | 个人/小团队快速试用；只想"每条 PR 自动多一双眼睛"；不想运维 |
| **优点** | **5 分钟能用**；零基础设施；成本随用量；失败即失败，不污染别的系统 |
| **缺点** | **无状态**：没有记忆、没有团队知识、没有跨 PR 的跟踪（Kodus 的 "Kody Issues" 这类能力天然没有）；无多租户；token 出网；**细粒度权限受限**（`pull_request_target` 的安全陷阱） |
| **意外结论** | 这一类**不是本项目的竞争对手，而是本项目的"入口"**——Action 可以只做"调我们服务的 API"，见 §5 P1-8 |

### 3.3 方案三 · 静态分析 + AI 混合类
**代表**：Semgrep + LLM、SonarQube + LLM、OCR（规则文本 + LLM，**注意它做的不是真 AST**）、Kodus（tree-sitter AST + LLM）
**形态**：确定性层先跑（模式/类型/污点），LLM 只看"确定性层标记过的东西"或做解释

| | 内容 |
|---|---|
| **适用** | 有合规/审计要求；要**可复现**的结论；要**可门禁**（"新增严重问题数 = 0"这种硬阈值） |
| **优点** | **结论可复现、可举证**（这是 AI 单独给不了的）；成本低（确定性层不烧 token）；**天然适合做门禁** |
| **缺点** | 事实上的"两种技术栈"要维护；误报率是这类工具的**主要敌人**（假警报多了就被关掉）；语言覆盖受规则生态限制 |
| **关键判断** | **"混合"有两种完全不同的混法**：<br>· **OCR 式**：规则是**文本**注入 prompt（便宜、覆盖广、但不理解语法树）<br>· **Kodus 式**：AST + Code Knowledge Graph 喂给 LLM（贵、语言少、但结构信息真实）<br>**本项目已有第二种的底子（JavaParser + tree-sitter），却还没把它变成"审查输入"** → 见 §5 P1-9 |

### 3.4 选择矩阵

| 你的约束 | 首选 | 次选 | 避开 |
|---|---|---|---|
| 代码必须出不了网 | Gito（本地模型声明最具体）/ LiveReview / 本项目 | OCR + Ollama | diffray（未声明）、shippie（无本地） |
| 有 Gitea + 自托管 GitLab | PR-Agent / LiveReview / **本项目** | — | OCR（无 Gitea） |
| 必须 5 分钟启用 | ChatGPT-CodeReview / shippie | PR-Agent Action | Kodus（首装 15–30 分钟） |
| 必须有阻断式门禁 | LiveReview / SonarQube | Semgrep CE | **OCR（无门禁）**、ChatGPT-CodeReview |

### 4.3 反向优势（可以对外讲的真实差异点，3 条）

2. **Gitea 一等公民**：OCR **不支持 Gitea**，Kodus 只覆盖 Forgejo（Gitea 的 fork，**不做等价断言**）。同时支持 Gitea + 自托管 GitLab 的，全生态只有 **PR-Agent、LiveReview、本项目**三家。
3. **横切面完备**：多租户（team 级隔离 + 知识/记忆/历史/反馈/规则全套）、成本治理（独立 `token-factory`）、全链路轨迹（对应 harness 的 "Model-visible means logged" 不变式）——**OCR、PR-Agent、ChatGPT-CodeReview 三家一个都没有**。

## 5. 优化方案：最佳实践 → 拟改进点 → 优先级

> 每条给：**借鉴自谁 / 为什么 / 怎么做 / 验收判据**。验收判据一律是**可机械检查的**，不接受"感觉好了"。

### P0 · 不改架构即可落地（三周内可完成，收益最大）

#### P0-1 · 确定性规则层扩容：从「3 个 Skill」到「文件模式 → 规则文档」四层链
- **借鉴**：OCR 的 `system_rules.json` + 四层优先级（`--rule` > 项目 `.opencodereview/rule.json` > 全局 `~/.opencodereview/rule.json` > 内置 system 层），以及它的"文件模式 → 规则文档"映射。
- **为什么**：现在 `core/skill/impl/` 只有 3 个 Skill、`resources/handbook/` 只有 1 份全局 Java 规范 ⇒ 规则命中率和"按团队/按路径生效"两个能力都不存在。这是最容易见效的一处。
- **怎么做**（4 步）：
  1. 在 `resources/` 下新建 `rules/` 目录，**按文件模式组织**（`**/*mapper*{mapper,dao}*.xml`、`pom.xml`、`application*.yml`、`**/*.sql`、`**/*.java` 等），每份是一段 markdown 规则文本；
  2. 在 `core/skill` 里加一层 `RuleResolver`，**四级覆盖链**：请求级（API 参数）> 团队级（team 隔离的存储）> 全局 > 内置 `rules/`；
  3. 结构上保持"**永远有规则可解析**"——内置层不可被覆盖为空（OCR 的设计要点）；
  4. 把已命中的规则文档**写进 ReviewTrajectory**（可追溯）。
- **验收判据**：① `find src/main/resources/rules -name '*.md' | wc -l` ≥ 15；② 对 10 个真实 PR 跑一遍，**规则命中率（至少命中一条规则文档的 diff 占比）≥ 90%**，且命中清单可从轨迹里读出；③ 故意把团队级规则置空，请求仍能跑通（验证"不可覆盖为空"）。

#### P0-2 · 文件筛选闸门 + 密钥路径保护（safe-by-default）
- **借鉴**：OCR `internal/agent/selection.go` 的**六道闸门**：`binary` → `secret_exclude` → `user_exclude` → `user_include` → `unsupported_ext` → `default_path`；以及"**secret 路径优先于用户规则、`include` 也无法覆盖**"这条硬约束。另有"diff 单独超过 max_tokens 80% 即判 `too_large`"。
- **为什么**：这是**唯一一条既省钱又防泄露**的改动。当前没有任何筛选 ⇒ `.env` / 密钥文件 / 二进制 / `target/` 构建产物都可能进 prompt。
- **怎么做**（3 步）：
  1. 实现 `PathGate` 链（六道闸门按固定顺序，短路求值）；
  2. 内置 secret 清单（`**/.ssh/**`、`**/.npmrc`、`**/.pypirc`、`**/.dockercfg`、除 `*.example`/`*.sample` 外的 `.env*`…），**且放在用户 `include` 之前**；
  3. 每个被拦掉的路径记 `${reason}`（`secret_exclude` / `binary` / `too_large`…），进轨迹并可在控制台按原因聚合。
- **验收判据**：① 造一个含 `.env` + `*.jar` + `target/` 的测试 PR，**三者全部不出现在送审清单里**，且原因可查；② 用户显式 `include: .env` 时**仍被拦**（这条最容易做错）；③ 拦掉的路径数进指标端点。

#### P0-3 · 阻断式质量门禁（fail the build）
- **借鉴**：LiveReview 的 **jq 规则 + `GET /ci-rulesets/:id/evaluate` 按 HTTP 状态阻断合并**（README 给了三档团队策略的 jq 示例，安全敏感团队的规则是 `(.counts.by_category.security > 0) or (.counts.by_severity.critical > 0)` 即阻断）；语义层借 Gerrit 的 **submit requirements**。
- **为什么**：**这是本项目最大的结构性缺口**（全库 grep 命中 0）。没有门禁，审查结论就只是"一条没人看的评论"，也就不可能有"审查通过"这个状态可审计。
- **怎么做**（4 步）：
  1. 把 `ReviewReport` 派生出**规范化计数**（`counts.by_severity.*` / `counts.by_category.*`）——这是门禁规则的判据面；
  2. 新增 `RuleSet` 实体（**按团队隔离**，复用现有多租户存储），规则正文是**可执行的表达式**（Java 侧可用 SpEL / MVEL，或直接存 jq 并 shell 出去）；
  3. 新增端点 `POST /api/rulesets/{id}/evaluate`，入参是 `reportId`，**返回 HTTP 200/409**（冲突即"门禁失败"）；
  4. 平台侧：Gitea/GitLab 的 **commit status / pipeline 步骤**接入该端点——评论照发，但**构建要红**。
- **验收判据**：① 造一个含 Critical 安全问题的 PR，门禁端点返回非 2xx 且 **Gitea 上该 PR 的检查状态为 failed**（在平台 UI 上肉眼可见）；② 同一个 PR 修掉问题后状态转 success；③ 门禁判据（用的哪条规则、读了哪几个计数）**能在报告里回读**——"为什么红"必须可回答。

### P1 · 需要新增模块（一个月量级）

#### P1-4 · 文件捆绑（bundling）：把「按维度并行」补成「按维度 × 按 bundle」二维
- **借鉴**：OCR 的 smart file bundling——**把相关文件打包为一个审查单元，每个 bundle 作为一个隔离上下文的 sub-agent 并发跑**（README 举的例子就是 `message_en.properties` 与 `message_zh.properties` 必须在一起）。
- **为什么**：本项目现在的并行是**星型按维度 fan-out**（5 个 Agent 各审全部 diff）。这解决"专业分工"，但**没解决"同一改动散落在多个文件"**——i18n、DTO+契约、SQL+实体这三类不一致**必然审不出来**。
- **怎么做**：在 `ReviewContext` 里引入 `Bundle` 维度；先做三类**静态可判**的捆绑规则（同 basename 不同语言后缀 / 同名 `.xml` mapper 与 `@Mapper` 接口 / entity 与 migration SQL），再考虑按调用图聚簇（这里正好能复用 `core/analysis` 的调用图）。
- **验收判据**：① 造一个"改了 `message_zh.properties` 但没改 `message_en.properties`"的 PR，**审查必须报出这一条**（当前基线：报不出，先测出基线再改）；② bundle 数与 sub-agent 并发数在轨迹里可读。

#### P1-5 · 定位校验 + 反思轮（把"评论挂错行"变成可检出缺陷）
- **借鉴**：OCR 的 **external positioning + reflection modules**；AI-Jury 的 **verify + synthesis 轮**（三段式：并行评审 → 自适应辩论 → 验证裁决，且带"去假阳性验证轮"）。
- **为什么**：行级评论位置漂移是**最伤信任**的一类错误（比漏报更伤）。本项目有行内评论 + Apply 按钮，但**没有独立的定位校验环节**。
- **怎么做**（3 步）：
  1. 加 `PositionVerifier`：拿 finding 的 `file+line` 回到 diff **原文**核对，对不上就降级为"文件级评论"或丢弃；
  2. 加一轮**反思调用**：只把"高严重度 + 低置信度"的 finding 送去复核（成本可控，不要把全部送一轮）；
  3. 反思的输入里显式带上**引用原文**，输出必须是"保留 / 降级 / 丢弃 + 理由"，理由入轨迹。
- **验收判据**：① 构造 10 条故意错位的 finding，**位置校验必须拦下全部**；② 反思轮的 token 增量 **≤ 总 token 的 15%**（超了就不划算）；③ 保留/丢弃的理由可回读。

#### P1-6 · 审查级评测基准（回答"改完到底变好没有"）
- **借鉴**：OCR 的 `Alibaba-Aone/aacr-bench`（**50 个热门开源仓库 / 200 个真实 PR / 10 种语言 / 1,505 条 ground-truth issue / 80+ 资深工程师交叉标注**），以及它**敢把"Recall 低于通用 Agent"写在 README 里**这件事本身。
- **为什么**：本项目已有 `RagEvaluator` + golden 检索指标（hit@k / MRR），但那是**检索级**的；**审查结论级**的 precision / recall 完全没有。没有它，任何 prompt 或模型改动都是**不可验证的**。
- **怎么做**（4 步）：
  1. 选 **20 个 PR**（自己仓库的历史 PR + 2 个开源仓库的真实 PR），人工标注 ground-truth issue；
  2. 定义三个指标：**precision（报出的问题里真问题占比）/ recall（真问题里报出占比）/ 噪音比（每 PR 平均评论数）**；
  3. 把 `ReviewReplay`（确定性回放）接到这套基准上——**保证"同输入同输出"**，否则指标不可比；
  4. 基准跑分写进 CI，**回归即红**。
- **验收判据**：① 基准集 ≥ 20 PR / ground-truth issue ≥ 60 条；② 同一次改动前后两次跑分**可复现**（同输入同输出）；③ 报告里必须显式写出**当前是"精度优先"还是"召回优先"以及理由**——这是 OCR 教给我们最重要的一条纪律。

#### P1-7 · 出口层：CLI + MCP Server + Coding-Agent 插件
- **借鉴**：OCR 的 `ocr review`（workspace / `--from/--to` merge-base / `--commit`）、`ocr scan`（无 git 历史也可全文件扫描）、`ocr session list`、`ocr review --resume <session-id>`、**Coding-Agent 插件（Claude Code / Codex / Cursor / Kimi Code / OpenCode）**、**官方 MCP Server**、**Session Viewer**（回放会话、把评论标为 fixed/ignored）。
- **为什么**：本项目已经有 `core/resume`（断点续跑）与 `core/trajectory`（事件源轨迹）——**能力都在，只是没有出口**。没有 CLI/插件，审查只能发生在 PR 阶段；**提交前的那一步是空的**。
- **怎么做**（按性价比排序）：
  1. **MCP Server**（最便宜）：把"审查本地 diff / 取某次审查的 finding / 标记已修"暴露为 3–5 个工具，**复用现有 REST 层**；
  2. **CLI**（次便宜）：一个薄壳（`cr review --staged` / `--base main`），调 REST；
  3. **Session Viewer**：控制台已有 Skills 市场/知识库，**加一个"审查会话回放"页**，把 `ReviewTrajectory` 渲染出来；
  4. Coding-Agent 插件：最后做（它依赖前三个稳定）。
- **验收判据**：① MCP Server 在 Claude Code 里能被发现并成功调用一次真实审查；② CLI 能对**未提交的 staged diff** 出结论（这条是"提交前闸门"的前提）；③ Session Viewer 能回放出**至少一次完整审查**的全部阶段耗时。

#### P1-8 · 平台面补齐（GitHub 优先）
- **借鉴**：PR-Agent / LiveReview 的五平台面；OCR 的 `examples/` 组织方式（每个平台一个目录 + 一份 recipe 文件）。
- **为什么**：现在 `integration/` 只有 `gitea` + `gitlab` ⇒ **GitHub 用户接不进来**，开源项目的"可试用面"直接砍半。而 Gitea 是本项目的**差异点**，不该被"平台太少"拖累。
- **怎么做**：抽 `GitPlatformClient` 接口（现在两个包各自实现），新增 `github` 实现（webhook 签名 + commit status + inline comment），然后按同样的 recipe 补 Bitbucket / Azure DevOps。**这一步和第 P0-3 门禁是同一件事的两面**（门禁要靠 commit status）。
- **验收判据**：① 在 GitHub 上提一个 PR，端到端出评论 + 门禁状态；② 平台适配层**新增一个平台不修改审核内核**（用 diff 里"改动只在 `integration/github/`"来证明）。

#### P1-9 · 把 AST 结果变成审查输入（兑现已有优势）
- **借鉴**：Kodus 的 **tree-sitter 9 语言 → Code Knowledge Graph**（节点 + `CALLS` / `IMPORTS` / `EXTENDS` / `IMPLEMENTS` 关系）+ **影响面按层级 0/1/2/N 分组**；Semgrep 的 generic AST 思路。
- **为什么**：本项目有 `core/analysis` **18 文件 / 2,709 行**（JavaParser + tree-sitter + 调用图 + 影响面），却在审查路径里没用起来 ⇒ **优势只是"存在于仓库里"**。这是唯一一条"投入产出比最高"的增强：基础设施已付过账了。
- **怎么做**（3 步）：
  1. 在 `ReviewContext` 里加 `structuralContext`：对每个改动点给出**调用方清单（含层级）+ 被调方 + 继承/实现关系**；
  2. 按影响面分层，**只把"层级 0/1 + 跨模块"的部分注入 prompt**（全部注入必然爆预算）；
  3. 关系类型对齐 Kodus 的四类命名，便于和业界文档对话。
- **验收判据**：① 造一个"改了被 30 处调用的公共方法"的 PR，**审查输出里必须提到影响面**（当前基线：不提）；② 结构上下文的 token 占比 ≤ 上下文预算的 25%；③ 影响面数据在报告里可回读。

### P2 · 涉外部依赖与法务，必须先权衡

#### P2-10 · 第二道确定性闸门：**选 Semgrep CE，不选 CodeQL / SonarQube**
- **结论与理由（三条硬事实）**：
  - ✅ **Semgrep CE**：引擎 **LGPL-2.1**，无人数限制、无需登录；官方规则是 **Semgrep Rules License v1.0**，**只在"卖竞争性扫描 SaaS"时受限**，内部使用 OK。**最易落地，但要接受它的边界：卡单文件模式与密钥类，卡不住跨文件污点。**
  - ⚠️ **SonarQube**：核心 LGPL-3.0 可商用，但**内置分析器自 2024-11-29 起改为 SSALv1**，SSAL 明文**禁止在自带功能之外用 AI 与软件交互** ⇒ 想把它接进自研 LLM 链路**必须法务确认**。
  - ❌ **CodeQL**：`github/codeql` 的 MIT **只覆盖查询库**，CLI/engine 是**商业专有许可**；无 GHAS 时**只能用于 GitHub.com 上的开源库**，私有库跑 CI 即违约。
- **怎么做**：Semgrep CE 跑在**送审之前**（正好接在 P0-2 的闸门之后），输出 SARIF，**只把命中项交给 LLM 解释**（而不是让它重审一遍），并把严重级映射到 P0-3 的计数里。
- **验收判据**：① 一次扫描的 SARIF 条目数与 LLM 调用数**都可比对**；② LLM 侧对"Semgrep 已标记项"的解释覆盖率 ≥ 90%；③ 许可清单进 `NOTICE`，写明规则集许可与边界。

#### P2-11 · 可信度材料（把"能交付"变成"可举证"）
- **借鉴**：OCR 的 `ASSURANCE_CASE.md` + **OpenSSF Best Practices Gold 徽章**（它把合规材料当产品的一部分）。
- **为什么**：企业采购问的第一个问题往往不是"准不准"，而是"**凭什么信你**"。
- **怎么做**：补 `SECURITY.md`（威胁模型 + 已知边界）、`ASSURANCE_CASE.md`（每项安全主张对应的实现与证据）、`NOTICE`（第三方许可）、SBOM；把 P2-10 的 Semgrep 集成写进威胁模型。
- **验收判据**：① 每一条安全主张都**指向一个可执行证据**（测试名或脚本名），不允许"设计上支持"这种话；② `NOTICE` 覆盖全部直接依赖。

### 7.2 需权衡取舍（做之前必须先定条件）

| 项 | 取舍点 | 建议的决策规则 |
|---|---|---|
| **P1-4 文件捆绑** | 捆绑会让 **bundle 数 × sub-agent 数**上升 ⇒ 成本与延迟同时涨 | 先只做三类**静态可判**的捆绑（i18n / mapper / entity-migration）；用 P1-6 的基准证明"报出了原本报不出的问题"**再扩** |
| **P1-8 补平台** | 每个平台一套签名/状态/评论语义，**维护面线性增长** | **只补 GitHub**（收益/成本最高），其余等有真实用户再排；抽接口是前提 |
| **P2-10 Semgrep** | 引擎许可干净，但**规则集是独立许可**，且它的"跨文件能力弱"会**改变产品承诺** | 明确写"我们做的是单文件模式 + 密钥闸门"，**不要对外宣称污点分析**；规则集许可进 `NOTICE` |
| **SonarQube 接入** | **SSALv1 明文禁止在自带功能之外用 AI 与软件交互** | **先法务，再动手**；不确定就不要接 |
| **CodeQL** | 无 GHAS 时仅限 GitHub.com 上的开源库 | **不接**（本项目面向私有库场景） |
| **许可纯度** | Kodus `AGPL-3.0+EE`、LiveReview `Sustainable Use License`、Sweep `EE License` 都**不是 OSI 开源** | **只读设计、不抄代码**；需要抄的算法（如影响面分层、jq 门禁表达式）**自己实现** |
| **改造成 Go CLI** | 会丢掉服务端横切能力（多租户/成本/轨迹） | **不做**。要"本地体验"就补 P1-7 的 CLI + MCP，**而不是把服务改成 CLI** |
| **本地模型的现实约束** | OCR 官方明确：**本地模型必须支持 native tool calling**，否则链路跑不通；且慢速模型要把 `timeout_sec` 从 300 调到 900 | 本项目若开本地模型通道，**启动时先做一次 tool-calling 冒烟探测**，不支持就 fail-fast（拒绝启动该 provider），**不要静默降级** |

### 7.3 建议的执行顺序（依赖关系）

```
P0-1 规则层 ─┐
P0-2 闸门  ─┼─→ P0-3 门禁（门禁的判据面来自规则命中的计数）
            │
            └─→ P2-10 Semgrep（接在闸门之后，只把命中项交给 LLM）
P1-6 评测基准 ─→ 之后所有内容改动都以它为验收（没有它任何改动都不可验证）
P1-9 AST 注入 ─→ P1-5 定位/反思（反思要用到结构上下文判断"这条是否真的可达"）
P1-8 补平台   ─→ P1-7 CLI/MCP（CLI 依赖稳定的平台层；门禁也依赖 commit status）
```

**一句话**：**先做 P1-6（基准），再做 P0-1/P0-2/P0-3（规则 / 闸门 / 门禁）**——基准必须先于所有内容改动，否则后面每一次改动都无法判断是变好还是变坏。

**三条设计约束（都是「会静默失效」的那一类，因此写成了结构性保证而不是文档约定）**：

1. **安全类闸门排在策略类之前**——`binary` / `secret_exclude` 先于 `allow` / `include` 求值，用户放宽规则在结构上碰不到机密。上有专项测试 `userIncludeCannotOverrideSecret` / `allowOnlyOpensPolicyGates`。
2. **内置规则层不可被覆盖为空**——上三层只做叠加与同 id 覆写，任何一层缺失 / 为空 / JSON 损坏都只降级该层。上有 `emptiedTeamLayerStillResolvesBuiltin` / `brokenTeamJsonDoesNotKillBuiltinLayer`。
3. **「决定了什么」必须可回读**——闸门决策写进轨迹事件 `files.gated`（含按原因聚合），规则命中写进 `rules.resolved`（含层级:id 清单），并暴露 `GET /api/admin/gate/stats`。理由：闸门是本项目**唯一会减少送审内容**的组件，规则层是唯一会**改变模型判据**的组件，两者的决策若不留痕，等于装了两个看不见的静音开关。

**★ P1-6 的两条诚实边界（比"已落地"更重要）**

1. **`ReviewReplay` 是"重建"不是"接上"**。方案 §P1-6 第 3 步写「把 `ReviewReplay`（确定性回放）接到这套基准上」——**实测该组件在 HEAD 上不存在**：引入于 `681d70e`（P2-⑨），**删除于 `ff2feb5`**（「全仓死代码清理」）。仓库里原先只剩 `RagEvaluator`（153 行，**检索级** hit@k/MRR），审查结论级的 precision/recall 完全没有。⇒ 方案里凡写「复用已有组件」的话都要先回源核实。
2. **回放输入不是真实模型产出**。`replayInput.origin = derived-from-ground-truth+controlled-distractors`：候选发现由 ground-truth 加**受控干扰项**派生（`noise`/`dup`/`conflict`/`feedback` 各对应链上一段可被改坏的逻辑）。因此**本基准测的是确定性后处理链，不是模型质量**；报告里也写死了这一条。真实模型采集（`origin=captured`）接进来后，同一套指标与门禁可直接复用。
   另：**precision 的绝对值不可跨语料比较**（FP 由构造的受控噪音决定），有意义的是**同语料下的前后差**——这正是 CI 门禁比较的对象。
