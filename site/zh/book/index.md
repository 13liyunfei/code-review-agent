# 前言：为什么是 Java，为什么是"工程化"

## 一个真实的面试场景

2026 年春天，我面一家公司的 Agent 应用开发岗。

面试官没有问"什么是 RAG"，也没有问"ReAct 和 Plan-and-Execute 的区别"。他问的是：

> "你们的检索质量怎么保证的？"

我打开笔记本，给他看两张表。第一张是同一条查询在修复前后的命中情况——**修复前，中文词命的命中是 `false`，英文词 `SQL` 的命中也是 `false`**；第二张是修复后的对照，两行都是 `true`。

他沉默了几秒，然后问："这是真库上测的？"

我说是，PostgreSQL 17.11 + pgvector 0.8.6，`psql` 里跑的，一行一列都在。

那次面试的后续我不展开。但我想说的是：**能让你在 Agent 岗上脱颖而出的，不是"我会用 LangChain4j"，而是"我知道它在生产环境里会在哪里骗我，以及我怎么发现的"。**

这本书就是那两张表的完整来历。

**如果你属于下面这类人，这本书就是为你写的**：

> 面试 Agent 岗，需要真实项目可讲。

全书 73 讲分上下两篇，**同一个系统、同一套代码，读法不同**。

**面向读者**：3–8 年 Java 后端/全栈工程师，想转 AI/Agent 方向，或者已经在做但不知道怎么让它稳定跑在生产上。

**读法**：按顺序读，第 02 讲开始就动手敲代码，每讲结束你手上多一个能跑的组件。

**面向读者**：Harness 工程师、系统架构师、模型研究员、技术决策者——你已经建过 Agent 系统，现在想从"知道怎么建"进阶到"**知道每个决定为什么这么做、还有没有别的做法、代价是什么**"。

**目标**：用机制视角重读六大核心机制（模型调用 / 上下文压缩 / 工具 / 权限 / 记忆 / 技能），打开一个**真实开源 harness（DeepSeek Harness，全 TypeScript / Cordis 插件）的内部实现**，再对照一流产品（Claude Code）的实现取舍，补齐大模型底层原理与主流框架生态——让你能独立做架构选型、能评审别人的设计、能向团队解释"为什么我们要这样做"。

**读法**：可直接从 M7 开始读，不需要先读完上篇。每讲都标注了与上篇的对应锚点，需要时再回查。

## 为什么是 Java

AI 应用开发领域，Python 是事实上的默认语言。但你如果是一个 Java 后端，放弃 Java 栈去学 Python 做 Agent，是一件**性价比很低的事**：

- 你的 7 年积累（并发模型、事务边界、类型系统、可观测性、部署运维）几乎全部作废；
- 而 Agent 应用真正的难点，**恰恰不是你调不动模型，而是你怎么让一个不确定的组件在一个确定的生产系统里活着**。

后者是 Java 的主场。

举几个本书会反复出现的例子：

- **超时不是 `orTimeout` 挂上去就完事**。把 `orTimeout` 挂在 `allOf` 上再 `join()`，等于没挂——因为 `join()` 本身没有超时。这个坑我们在第 17 讲用真实的 P0 事故讲。
- **`CompletableFuture` 的异常不会传到 `join()` 之前**。多 Agent 并行时，一个 Agent 挂了，你得知道怎么让其他 Agent 的正常结果不被污染。第 13 讲。
- **成本要用微元整数记**。用 `double` 记钱，调用量上去之后你会看到对不上账。第 32 讲。

这些不是 AI 知识，是**工程知识**。而市面上 90% 的 AI 课不讲这些。

副标题里"生产级"三个字是有成本的。它意味着这本书不会让你在 10 分钟内看到"Hello, Agent"就跑起来了——虽然第 02 讲确实会给你一个 10 分钟能跑通的例子。

## 主线：你将亲手建成的系统

这不是一本"知识点合集"。42 讲只建**一个系统**：

**`code-review-agent` —— 一个 AI 代码审查引擎。**

它接收 Git 平台的 webhook，把 PR 的 diff 拆给 5 个各有所长的 Agent 并行审查，用加权仲裁把 5 份意见合成一份（其中 Security Agent 有一票否决权），再把结果行内评论回写到 PR 上。整个过程跑在 PostgreSQL + pgvector 上，知识库用中文编码规范。

```
Git 平台 webhook
      │
      ▼
┌──────────────────────────────────────────────────────────┐
│                    code-review-agent                      │
│                                                           │
│   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐  │
│   │Security│ │ Logic  │ │ Perf   │ │ Arch   │ │ Style  │  │
│   │ 权重100│ │ 权重90 │ │ 权重70 │ │ 权重60 │ │ 权重10 │  │
│   └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘  │
│       └──────────┴──────────┴──────────┴──────────┘       │
│                          │                                │
│                  ┌───────▼────────┐                       │
│                  │  加权仲裁 + 否决 │ ← BLOCKER 不可抑制     │
```

而 `token-factory`（LLM 网关）和 `agent-kit`（多 Agent 基座）**不是另外两个项目**，是为它造的两件工具——模块一先当**调用方**把 LLM 用对，模块五再当**平台方**把它变成给团队用的基建。

## 如何使用本书

每讲都是**五段式**：

1. **痛点** —— 先讲一个真实的、会让人损失金钱或信誉的问题。不铺垫概念。
2. **原理** —— 为什么会这样。讲机制，不讲 API 签名。
3. **代码** —— 指向真实仓库文件（可对照 `文件:行号` 阅读）。
4. **避坑清单** —— 可以直接搬进你项目的检查项。
5. **动手任务** —— 一个你能亲手复现的实验或修复。

**建议的读法**：

- 如果你是**为面试读**（上篇）：先读第 01、15、17、18、19、26、27、35、41 讲。
- 如果你是**为落地读**（上篇）：按模块顺序读，第 02 讲开始就动手敲。
- 如果你是**为架构选型/机制深度读**（下篇）：直接从第 43 讲开始，按 M7→M8→M9→M10→M11 顺序。
- 如果你是**为踩坑读**：直接翻每讲的"避坑清单"，全书有 762 条。

## 关于代码

四个仓库都是开源的，书里的代码片段全部来自真实文件，不是为写书而临时造的示例。

> 本书所有类名、文件路径、常量值、版本号，都经过逐项核对。
> **写作纪律：落笔前必须核对仓库或逐条数一遍。** 已发生过的教训——写错过版本号（把 Java 17 写成 21）、写错过讲数、甚至写进过一个项目里根本不存在的技术名词。这类错误比内容平淡更致命：**读者照着跑不起来，比读得不过瘾糟得多。**

### 两条读代码的约定

**① 仓库归属。** 全书涉及四个仓库。**没写仓库名的 `Xxx.java:NN-NN`，一律在 `code-review-agent` 里找。** 之所以要专门说这一句：`code-review-agent` 和 `token-factory` **各有一个 `BackoffPolicy.java`、各有一个 `DefaultRetryClassifier.java`**，`agent-kit` 和 `code-review-agent` **各有一个 `InMemoryVectorStore.java`**。书里凡引用同名类，都会在代码块头部写出仓库，例如 `// token-factory / core/resilience/BackoffPolicy.java:58-65`。

**② 图。** 书里的结构图、流程图、状态机、时序图**统一用 Mermaid 画**（终端输出、日志、目录树仍用等宽文本块）。GitHub、Gitee、Typora、Obsidian、VS Code（Markdown Preview Mermaid 插件）都能直接渲染；**如果你用的是不支持 Mermaid 的阅读器，会看到图的源码而不是图**——换个阅读器，或对着源码读，语义是一样的。

> **这两个约定不是形式主义，是能省下你最多时间的两句话**：一个让你不会照着错误的文件翻半天，一个让你不会以为"这书怎么缺图"。
