# 第 58 讲 · 工具机制对照：Claude Code 让模型的"手"伸向哪里

> 🎯 导读问题：**"Claude Code 的工具范围和我们的 Agent 有什么本质差别？"** ——能答出"差别不在『会不会调工具』，而在 **『工具的边界由谁划、伸向什么对象』**：我们让工具伸向 API/库，是**受控的、可审计的**；Claude Code 让工具伸向真终端，是**外放的、但同样不越界**。**工具机制的灵魂是『边界』，不是『能力清单』。"**

## 一、痛点

第 45 讲我们读工具系统时，核心是 `ToolRegistry` 的**声明 + schema + 能力边界**：它决定模型能不能用某个工具、用什么形态调用、行为是否可审计。这套骨架里，"工具的边界"是隐式的——工具都指向**代码、文件、库 API**这类**受控对象**。

现在用 Claude Code 做第二参照物。它不是"在沙箱里调 API",它是**真在终端里跑**——能读真文件、能执行真命令、能访问真网络。这立刻把工具机制推到一个极端问题：

> **当工具的"手"能碰真系统时，什么东西还在替这个 Agent 守边界？**

你很容易掉进两个相反的坑：

**坑一："能力越外放越高级。"** 于是你的工具系统拼命塞能力——能跑命令、能读全盘、能删文件。能力清单越拉越长，边界反而失守。**你以为在学 Claude Code，其实在制造一个权限失控的 Agent。**

**坑二："终端 Agent 有真命令，我们没有，所以学不了。"** 反过来，你觉得只有"碰真系统"才配叫工具机制，自己那些"读文件/调 API"的工具太弱。**于是放松了对自己工具边界的守卫，把工具系统的价值定义成了"能力大小"。**

本讲要破除的，正是"工具=能力清单"这个误会。真相是：

> **工具机制的灵魂不是『会调多少工具』，而是『边界由谁划』。Claude Code 能力外放，但它守边界、守授权的方式，和你 `ToolRegistry` 里那道"声明+能力+审计"的骨架是同一个东西——只是它面对的对象更危险，所以边界更显眼。**

## 二、原理

### 2.1 先对齐骨架：工具永远是"声明 + 调用 + 边界"

无论 `ToolRegistry` 还是 Claude Code，一个工具系统都由同一套骨架构成——这份骨架在 `agent-kit` 里落了真实行号，在 Claude Code 里落了公开命令：

| 骨架 | `ToolRegistry` / `AgentTool`（第 45 讲）| Claude Code 公开形态 |
|---|---|---|
| **声明** | `AgentTool` 四方法：`name()` + `description()` + `parameterSchema()` + `execute()` | 内置工具清单 + MCP 工具，模型按名字+参数调用 |
| **调用** | `ToolCallingLoop` 驱动 LLM 出 `{action,tool,arguments}` → 执行 → 观察回灌 | 模型产出工具调用 → 执行 → 结果回灌上下文 |
| **边界** | `GuardedTool` 装饰器：执行前 `ToolSchemaValidator.validate()` | 权限模式 + 权限规则（allow/ask/deny） |

`AgentTool` 的契约是**四条就够**：工具只负责"**声明自己 + 执行**",决策（何时调、传什么参）交给 `ToolCallingLoop` 驱动的 LLM。这是关键的分工——**工具实现类不感知 LLM**，它只回答"我是什么、我能接什么参数、我跑起来产出什么"。骨架完全同构。

**第 45 讲反复讲的"schema 描述决定模型用不用这个工具"，在两边都成立**：`ToolRegistry.describeForPrompt()` 把每条工具拼成 `- 名字: 描述 参数: schema` 塞进决策上下文，模型就是靠这段文本来判断该调谁。**描述写得含糊，再强的工具模型也想不到用**——这条铁律跨产品成立。

### 2.2 你家的"边界"是怎么被代码守住的：GuardedTool 三层校验

很多人以为工具系统里"边界"是个抽象口号。不，它在 `GuardedTool` 里是**一段真实的前置校验**——工具注册时被包一层，执行前先"验参数"：

```java
// GuardedTool.execute：先校验，后执行
ToolSchemaValidator.Validation v = ToolSchemaValidator.validate(schema, args);
if (!v.valid()) {
    return ToolResult.fail("参数校验未通过: " + v.reason());  // 拒绝，绝不透传
}
return delegate.execute(args);
```

这里藏着一个 Harness 判据的落地：**"越界的判定"从"模型会不会乱填"里独立出来，变成一段可机器验证的 schema**。模型可以任意给参数，但 `validate()` 是确定性闸门——参数类型错、缺必填、越出白名单，直接 `fail` 返回，不进入真实执行。**这是"边界的自动化",不靠人盯。**

再往下，决策循环 `ToolCallingLoop` 提供了**第二道边界——终止条件**：

```java
for (int i = 1; i <= maxIterations; i++) {          // 系统硬上限
    String decision = chatModel.chat(buildPrompt(...)); // 每轮带目标+工具清单+历史观察
    if (action == finish) return answer;            // 模型软终止
    AgentTool tool = registry.get(toolName);
    if (tool == null) observation = "工具不存在...";  // 不存在 = 边界，不空指针
    observation = safeExecute(tool, args);           // 执行异常被 catch，不炸循环
    transcript.add(observation);                     // 结果回灌，下一轮可观察
}
```

三个细节正是第 45 讲"声明 + 调用 + 降级"的源码版：**① `maxIterations` 硬上限**防死循环；**② `safeExecute` 把任何工具异常接成 `ToolResult.fail`**，绝不让一个工具炸掉整个 Agent（实现契约里写明"实现必须自兜底，绝不抛出"）；**③ LLM 输出非法 JSON 时优雅降级为纯文本答案**，不抛异常中断业务。**这些不是"鲁棒性的锦上添花",是工具机制"可判定终止"的承重墙——没有硬上限，Agent 就可能在"调工具→观察→再调"里空转到底。**

### 2.3 真正的分野：边界对象不一样，所以守卫方式不一样

差别不在骨架，在 **"手伸向什么"**：

- **你的工具伸向受控对象**（代码库、文件、库 API）：边界靠**schema 校验 + 能力白名单**就够——你在注册一个 `AgentTool` 时，它的能力就固化了，越界是"根本没声明这个工具"或"参数没过 `validate`"。
- **Claude Code 的工具伸向真终端**（真文件、真命令、真网络）：边界必须靠**显式的授权策略**——因为"执行命令"这个能力本身是**开放的**（任何 shell 命令都可能），真正守边界的是"**这条命令能不能跑、这个目录能不能碰**",而这通常需要**人的确认**。

所以 Claude Code 最显眼的公开行为——**对危险操作先问再动**——不是"它机制弱所以求人",而是它**把『边界判断』这件无法在工具层自动判定的事，显式交回给了人**。它公开出来的权限模式（`/permissions` 里可切换）正是这个机制的**分层可见形态**：

| 权限模式 | 机器自动 vs 人裁决 | 对应你家工具机制的哪一环 |
|---|---|---|
| `default`（默认）| 读放行；改文件/跑命令**逐条问** | `GuardedTool` 的 schema 校验（能自动判的就自动判）|
| `acceptEdits` | 编辑类操作自动放行，危险命令仍问 | 白名单放宽，但"删/网络/越界"仍留人工闸 |
| `plan`（只读规划）| 只读不写，整体不落地 | `paramSchema` 收紧到只读子集 |
| `bypassPermissions`（慎用）| 全放行，无人裁决 | 相当于拆掉 `validate()`，只留给受控沙箱 |

**四种模式不是四条死规则，是把『边界判断该自动化到什么程度』做成了一个可调旋钮。** 你的 `GuardedTool` 其实已经具备这个旋钮的雏形："能自动判的参数越界就用 schema 拦，不能自动判的危险意图就拦下来交回给人"。**边的界不是"全自动"或"全人工"二选一，而是每一类操作都该有它该在的那一格。**

### 2.4 MCP：让"工具"从进程内长到进程外的桥

Claude Code 的工具机制还有一层国内外正在对齐的东西——**MCP（Model Context Protocol）**：把"工具"从进程内的一等公民，变成**跨进程、可插拔的协议端点**。一个 MCP server 起在独立进程里，暴露 `tools/list` / `tools/call` 两个操作，Claude Code 作为 client 连上去，就把它当成自己的工具用。

这跟你 `ToolRegistry` 的差异，**不在"能不能调工具",而在"工具的加载边界"**：

- `ToolRegistry`：工具是 JVM 里的类，进程内注册，`get(name)` 直接拿到实例调 `execute`。
- MCP：工具是**网络端点**，协议层把"声明"（`tools/list` 返回的 schema）和"执行"（`tools/call`）解耦，工具可以跑在别的地方、别的语言、别的进程里。

**但骨架没变**：MCP 的工具声明依旧是"名字 + 描述 + 参数 schema",模型依旧靠描述选工具，执行结果依旧回灌上下文——它只是把 `AgentTool.execute()` 换成了 `tools/call` 的一次 RPC。**结论：协议换得了"工具住在哪",换不了"声明 + 调用 + 边界"这三件套。** 你读到这里，已经能一眼看穿任何新 protocol/framework 的工具层——它无非是在"进程内注册"和"进程外桥接"之间选了个位置，判据不变。

### 2.5 可迁移的判据

**第 45 讲的闭环（工具调用要可审计、结果要回灌）在两边都成立**。把它提炼成可迁移判据：

> **工具的『手』伸多长，由『边界』划定，不由『能力清单』决定。** 清单只回答"它能做什么",边界才回答"它被允许做什么"。清单再长，边界失守就是权限失控；边界清晰，能力再小也是可信的工具系统。

而"边界"要可落地，必须能回答四个问题——这是第 2.2/2.3 节所有细节的收口：

1. **不能调什么**（越界名单在哪）；
2. **为什么不能**（那条拒绝的依据是什么）；
3. **这条"不能"写在哪个闸门上**（schema 校验？白名单？还是交回给人的确认）；
4. **违规/放行有没有被记下来**（审计痕迹在哪）。

**这四条答不出来，你的系统离 Claude Code 的"外放但守界"还有距离——而且差的恰恰不是能力，是边界。** 能力是模型给的，边界是你写的。

### 2.6 前沿深挖：MCP 生态一年长成基础设施，但"工具描述"已被证实是注入通道

MCP 从 2024 年底发布到 2025-11-25 版，一年四版，changelog 里的机制级增量值得逐条读：**OIDC Discovery（身份发现）、增量 scope 授权、sampling 支持 tools/toolChoice（MCP server 可以反向要求宿主模型带着工具继续推理）、experimental tasks（长任务异步化）、JSON Schema 2020-12 默认化（参数校验表达力升级）**。Claude Code 作为 MCP 的头号宿主，这些能力大多第一时间落地——**你在第 2.4 节看到的那座"桥"，桥墩正在一年一变地加粗。**

但同一份规范也打开了新的攻击面，2025 年的安全研究把两类攻击落了锤：

- **Tool poisoning**（[arXiv:2506.01333](https://arxiv.org/abs/2506.01333)）：恶意 MCP server 在 **tool description / 参数 schema 注释 / 返回值文档**里埋指令。模型读工具清单时把这些元数据当成行为指令的一部分——**你以为 description 是给人看的文档，模型眼里它是 prompt 的一部分**。Claude Code 的防线是权限确认弹窗，但弹窗防不住"工具描述本身就带毒"。
- **Rug pull**：server 通过审批后**动态改变**工具行为（返回值里藏指令、能力范围悄悄扩大）。一次授权 ≠ 长期可信。

**可迁移判据**：**MCP 工具接入要过三关——接入时审 schema 与 description（当不可信文本过注入检测）、运行期对返回值过输出护栏、版本变更时强制重新审批（钉死 schema 哈希）。** 你的 GuardedTool 三层校验管"参数对不对"，这三关管"工具本身可不可信"——两层防御，缺一不可。

## 三、避坑清单

- [ ] **别用能力清单的长度衡量工具系统。** 灵魂是边界，不是会多少。
- [ ] **每个工具都要有"能力白名单 + 调用校验"**：能做什么、参数怎么约束，写死在声明里。
- [ ] **手伸向危险对象时，必须加显式授权/确认**，把不可自动判定的边界判断交回给人。
- [ ] **工具调用必须可审计**：谁调了、传了什么参、结果是什么，一条都不能少。
- [ ] **模型用不用工具，取决于工具描述的清晰度**——schema 描述差，再好的工具模型也想不到用。
- [ ] **引用 Claude Code 工具行为时，只引公开命令/授权模式**，不编造内部函数名。

## 四、动手任务

> **目标**：给已有的工具系统补上它最缺的——"边界"。

**步骤 1：给每个工具写"不能做什么"**

打开你的 `ToolRegistry`，给每个工具**补一段"边界"**：什么参数值拒绝、什么对象不许碰、越界时报什么。别只写"能力"。

**步骤 2：标出危险工具**

把有能力伸向真系统（写文件、跑命令、碰网络、删改）的工具标出来，给它们**加一道显式授权/确认**——像 Claude Code 那样"先问再动"。

**步骤 3：给边界留审计**

确保每一条"被边界拦下/被授权放行"的工具调用都被记录下来。能回答"这条为什么放行了/为什么拦了",才是可信的边界。

**步骤 4：对照判断**

对每个工具问第 2.3 节三个问题：**不能调什么、为什么、这条不能字写在哪、违规了会不会被记下来。** 答不出就补。

## 本讲小结

1. **工具机制的灵魂是边界，不是能力清单。** 清单说你"能做什么",边界说你"被允许做什么"。
2. **骨架同构**：声明 + 调用 + 边界，`ToolRegistry` 与 Claude Code 是同一个东西。
3. **边界对象决定守卫方式**：受控对象靠白名单，危险对象靠显式授权/确认。
4. **"先问再动"不是机制弱，是把不可自动判定的边界判断交回给人。**
5. **工具调用必须可审计**——清单再长，边界失守就是权限失控。

下一讲我们对照第四道机制：**权限机制**——Claude Code 的"能力边界谁批准、凭什么"正好放大成第 46 讲 `TeamResolver` 讲过的多租户授权与基线叠加。
