# 第 57 讲 · 上下文压缩对照：Claude Code 的"给模型看什么"

> 🎯 导读问题：**"Claude Code 多轮长会话，上下文怎么处理？"** ——能答出"它不是无限塞，而是**分级收紧 + 分层**：最新的全量、中间的压缩、老的在会话记录里可回查"，就算读懂了。**本讲的判据是：上下文管理的胜负手不在『挤进多少』，而在『选定哪些不重要』——压缩策略必须可判定，不能是碰运气。**

## 一、痛点

第 44 讲我们立下判据：**上下文管理 = 准入 + 分层 + 投放三件事，截断是最后手段不是第一手段。**

这套判据在"检索增强"的场景里很自然：你从知识库召回、精排、注入几条，每一条都是**主动决定**"这一段值得给模型看"。

但当你面对一个**多轮长会话终端 Agent**（Claude Code 这种），疑虑会换成另一种：

**"它一次聊几十轮，塞不进窗口怎么办？总不能每轮都重新检索吧？"**

于是你心里浮现两个错误答案：

**错误答案一：直接把对话历史的旧轮次截掉。** 简单，但会让 Agent"失忆"——前面讲过的重要约束，后面它"忘了"，于是重复问、重复犯错。这正是第 44 讲反复警告的"**截断是最后手段**"。

**错误答案二：把截断包装成"压缩"，反正都是丢。** 你在日志里写"context compressed"，自我安慰这是"高级做法"，但实际上它**根本没管"丢什么"**——只是在新一轮载入时赌运气。这违背第 44 讲的三件事里最核心的"**投放**"。

本讲要破除的，就是把"丢什么"当成省 token 的凑数。真相是：

> **长会话 Agent 的上下文处理，和 RAG 是同一套机制：准入 + 分层 + 投放。只是它的"分层"换了一种形态——按时间分层而不是按相关度分层。而"丢什么"同样是可判定的决定，绝不是截断凑数。**

## 二、原理

### 2.1 Claude Code 的公开分层形态：三层时间分层

Claude Code 作为持久的终端会话工具，其核心机制在公开文档与社区方案中体现为一种**三层形态**：

| 层 | 内容 | 类比第 44 讲的 |
|---|---|---|
| **最新层** | 最近的对话原文，几乎全量进上下文 | 你的"精排后注入"的几条 |
| **中间层** | 较久的历史被摘要/压缩，只保留要点 | 你的召回的候选集 |
| **沉淀层** | 很早的历史与最终产物，进会话记录可回查 | 你的知识库可再召回 |

关键在于**第三层——它没有"真丢"**。Claude Code 的重要设计是：**任何被压出"即时上下文"的老内容，都还躺在会话记录里可回查**（`--continue` / 读历史会话可恢复现场）。这跟第 44 讲"可回查"的底线完全同构：**你压出去的不是"删除了"，是"移出了即时区，进了可召回区"。**

### 2.2 中间层是怎么"压"的：auto-compact 的摘要化，而不是截断

"中间层摘要"这件事，Claude Code 有一个**公开可观察的实现形态**——**auto-compact（自动压缩）**：

> 当会话上下文逼近窗口上限时，Claude Code 会**自动触发一次压缩**：把前面冗长的对话历史，交给模型**总结成一份精简的摘要**，然后用这份摘要替换掉原始的历史，腾出空间继续干。这个阈值和开关在设置里可见（`/config` 的 autoCompact 相关项），`/compact` 命令也可以手动触发。

这个机制和第 44 讲"截断是最后手段"的判据**惊人地一致**，但它揭示了压缩的一个关键区别：

| 做法 | 本质 | 有没有"理解" |
|---|---|---|
| 截断 | 按位置砍掉最早的部分 | 无——机械丢弃 |
| **摘要压缩（auto-compact）** | 让模型把历史"读一遍、提炼要点" | **有**——语义级提炼 |

**摘要压缩贵，但贵得有道理**：它花一次模型调用的钱，换取"被压掉的内容里，真正重要的部分以浓缩形式保留下来"。截断是零成本的、也是零理解的。**"丢什么"的质量，取决于你愿不愿意为"理解被丢内容"付一次成本**——这正是第 44 讲"越靠前越便宜"的反面：**压缩这一环，恰恰是"越认真越贵、也越值"的地方。**

### 2.3 CLAUDE.md：长会话里那条"永远在场"的系统层

第 44 讲的分层模型里，最顶层是"**系统提示——恒定规范、每次都在**"。Claude Code 把这个层落成了一个具体、公开、用户可写的文件：**`CLAUDE.md`**。

它是一份**分层记忆**文件，按作用域分三级，逐级叠加进来：

| 作用域 | 位置 | 类比第 44 讲 |
|---|---|---|
| 用户级 | `~/.claude/CLAUDE.md` | 全局系统提示 |
| 项目级 | 仓库根 `/CLAUDE.md` | 项目规范层 |
| 子目录级 | 子目录下的 `CLAUDE.md` | 局部上下文层 |

**每一次会话启动，这些 CLAUDE.md 被自动、恒定地注入**——这就是第 44 讲"恒定的规范进系统提示"在终端产品里的具体形态。它印证了那条判据：**"每次都在、几乎不变"的内容，要有一个专门的、固定的槽位，而不是每次会话临时拼进去。**

更深一层，这和你 `RagContextBuilder` 末尾的【历史经验参考】是**同一个"分层"思想的两种落点**：

- CLAUDE.md 放的是**人写的、静态的、跨会话的规范**（"你要遵守这些风格/规则"）；
- 【历史经验参考】放的是**系统攒的、动态的、会衰减的经验**（"这个仓库上次出过这种坑，注意点"）。

**一个静态一个动态，一个靠人维护一个靠状态机维护，但它们在上下文里都占据"恒定在场、末尾或开头、独立成层"的位置**——这就是"分层"这个抽象在不同产品里的同构复用。

### 2.4 最隐蔽的一层：子代理 = 上下文隔离，不塞一个窗口，用多个窗口

Claude Code 还有一个**很多人没意识到它属于"上下文管理"** 的机制：**子代理（subagents）**。

当你让它"同时调研 A、B、C 三个模块"时，它会把这些拆给**多个子代理**，每个子代理在**自己独立的上下文窗口**里干活，只把**结论**返回给主上下文。

这件事和第 44 讲的"投放预算"是同一个目的，但手法完全不同：

> **第 44 讲用"准入+分层+投放"在一个窗口内做减法；Claude Code 用子代理做"结构性隔离"**——不把 A/B/C 的中间过程全塞进一个窗口，而是把它们**分到多个独立窗口**里并行，最后只回传结论。

这给我们一个重要的架构启示：**"上下文不够用"有两条完全不同的解法**——一条是"在同一个窗口里压得更狠"（压缩/检索），另一条是"**别把所有东西塞进同一个窗口**"（拆任务、分上下文、只汇结论）。你的第 15 讲"星型拓扑多 Agent"、第 14 讲的 Coordinator，其实早就是这个思路了：**多 Agent 不只是在"并行干活"，更是在"隔离上下文"**。理解这一层，你才真正看懂为什么"多 Agent"和"上下文压缩"是同一张牌的两面。

### 2.5 判据一模一样的"取舍权衡"

第 44 讲的 RAG 三级收窄，每一步都在回答"**这条值不值得给模型**"。Claude Code 的三层形态，每一步也在回答同一个问题，只是**权衡的变量从'相关度'换成'时间'**：

- **相关度的取舍**（RAG）：用 query 去比，相关才注入。第 44 讲：**query 决定一切**。
- **时间的取舍**（长会话）：最近的最可能还有用，老的优先压缩。Claude Code：最新原文、中间摘要、老的可回查。

**这两套取舍都要求一个共同的东西——可判定的策略**：

> **任何被压出即时上下文的片段，都必须是"按一条明确判据选出来的"，而不是"窗口满了随手丢的"。** 相关度版靠向量分数，时间版靠新旧分界；没有判据的取舍和丢硬币没区别——这是上下文压缩的底线。

### 2.6 前沿深挖：Anthropic 自己也在给 CLAUDE.md"减肥"——80% 规则被删掉的启示

一个容易被忽略的事实：**CLAUDE.md 分层机制的发明者，自己也在拼命压缩它。** Anthropic 官方 context engineering 博客披露：为 Claude 5 世代模型，他们**移除了 Claude Code 中 80% 以上的 system prompt 内容，代码评测无可测损失**。

这件事对"分层记忆"信仰者是一记校准：

- **分层不是目的，是手段。** CLAUDE.md 三层（用户级/项目级/子目录级）解决的是"加载时机"，但加载了不等于有用——**每一条常驻规则都在消耗注意力预算，且会和用户当前指令竞争**。
- **context rot 是真实存在的衰减。** 长会话中，早期规则的影响力随轮次衰减（社区称为 context rot）；lost-in-the-middle 研究（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)）进一步证明**中段内容的召回最差**——所以 CLAUDE.md 里最重要的规则要放开头或结尾，且条目数本身就该被预算约束。
- **新范式是"即时检索 > 常驻加载"。** Context Folding（[arXiv:2510.11967](https://arxiv.org/abs/2510.11967)）等方向把已完成子任务整体折叠成摘要，活跃上下文只留未决约束——这与 auto-compact 同族，但粒度从"整个会话"细化到"每个子轨迹"。

**可迁移判据**：**给你的 CLAUDE.md / 系统提示做"条目审计"——每一条都要能回答"删掉它，哪次输出会变差？"答不上来的条目就是预算浪费。** Anthropic 删掉 80% 还不掉点，说明大多数团队的分层记忆里，也躺着 80% 的"心理安慰型规则"。

## 三、避坑清单

- [ ] **别把截断包装成压缩。** 压缩必须管"丢什么"；截断零理解，摘要压缩才是有理解的。
- [ ] **三层形态都要有，第三层是承重墙。** 被压出去的内容必须能回查，否则 Agent 会"失忆"。
- [ ] **取舍必须有判据。** 相关度靠分数，时间靠新旧分界；没有判据就是丢硬币。
- [ ] **"恒定在场"的内容要有专门槽位**——你自己的系统提示/规范，别每次会话临时拼。
- [ ] **"上下文不够"有两条解法**：单窗口压得更狠（压缩/检索）vs 分窗口隔离（子代理/多 Agent）。别只盯第一条。
- [ ] **不可逆的丢弃先确认。** 能不能回退，决定了压缩是改进还是破坏。
- [ ] **压缩是可观测的。** 你要能回答"这一轮为什么看这几段"。
- [ ] **对照第 44 讲，别造两套真理。** RAG 和长会话是同一机制，写成两套逻辑必然漂移。

## 四、动手任务

> **目标**：把你的上下文处理，从"截断凑数"升级成"可判定的分层压缩"。

**步骤 1：给会话分层**

如果你现在多轮会话是"全量塞，塞不下就截"，先改成三层：**最新原文 / 中间摘要 / 史料可回查**。三层各自用一个数据结构，别混在一处。

**步骤 2：给"恒定在场"的内容建槽位**

把你系统里"每次都要有的规范/指令"，抽成一个专门的、自动注入的槽位（对应 CLAUDE.md），而不是每次会话临时拼。标出哪些是"静态规范"、哪些是"动态经验"（后者走第 47 讲的状态机）。

**步骤 3：给取舍写判据**

为新旧分界写一条明确的规则（按轮数或按 token 预算），并记录**每一轮压缩选了哪些、为什么**。

**步骤 4：验证可回退**

把被压出去的中间层存下来，验证"下一轮确需某条旧信息时，能从记录里找回来"。找不回来，说明你的压缩不可回退。

**步骤 5：对照 RagContextBuilder**

让"可回查"的出口露出水面（像第 44 讲末尾的【历史经验参考】那样），确保它是"追加可查"而不是"覆盖即丢"。

## 本讲小结

1. **上下文压缩不是截断，是三层分层**：最新原文、中间摘要、史料可回查。
2. **中间层的压缩靠"摘要化"而非"截断"**——auto-compact 花一次调用买"理解被丢内容"，这才是"可判定的丢"。
3. **CLAUDE.md 是"恒定在场"系统层的落地**——静态规范 vs 动态经验，两种内容在同构的"分层槽位"里各就各位。
4. **"上下文不够"有两条解法**：单窗口压缩 vs 子代理/多 Agent 的上下文隔离。多 Agent 和压缩是同一张牌的两面。
5. **与 RAG 是同一机制**，取舍变量从"相关度"换成"时间"；"丢什么"必须有判据、可回退。
6. **别造两套真理**：RAG 与长会话是同一个 Harness 机制，写成两套必然漂移。
