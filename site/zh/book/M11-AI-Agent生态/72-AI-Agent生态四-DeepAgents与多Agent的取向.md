## 一、痛点

前两讲我们把"循环怎么编"这一层照清了——LangChain 是链、LangGraph 是图。这一讲到 DeepAgents，很多人会在真正开问之前先卡在两个地方：

**痛点一："DeepAgents（多 Agent 框架）和 LangGraph……不是一个东西吗？"** 你可能看到多 Agent 框架也用"编排"，于是把"图编排"和"多 Agent"混成一团。→ **这两个是不同维度**：LangGraph 管的是"一次任务里某几步怎么循环/分叉"，多 Agent 管的是"这个任务要不要拆成多个独立 Agent、谁来协调、结果怎么聚"。**把一个任务拆成 5 个子 Agent，然后用图把每个子 Agent 内部的循环画出来，两者可以同时成立**——它们不是替代关系。

**痛点二："拆多个 Agent 听起来更智能，我是不是也该拆？"** 你以为"多 Agent "=高级，于是总想把系统拆得越来越细。→ 但第 14 讲已经立过判据：**多 Agent 不是默认选项。拆得多 = 协调复杂 × 成本 × 延迟，只有当『单一 Agent 做不了或做不好』时才值得拆。** 你的审查系统拆成 5 个审查 Agent，是被"安全/逻辑/性能/架构/风格五个维度需要专业分工"这一道判据逼出来的，不是拍脑袋。

本讲要建立的，是为你手上的"框架地图"补上最后一块、并收束整个模块：

> **DeepAgents 不是又一个"循环怎么编"的方案，它是『要不要拆多个 Agent、怎么分工、谁来调度、结果怎么聚』的多 Agent 架构取向。** 你用它照自己在 M3 建的星型汇聚：**1 个协调者 + 5 个专业 Agent + 加权仲裁**——这就是一次真实的多 Agent 落地，而且你早在看到任何框架之前就做完了。

## 二、原理

### 2.1 多 Agent 的取向：协调者 + 子 Agent

DeepAgents 这类"多 Agent 取向"框架的典型形状是**星型 / 层级**：

```
                    ┌── 子 Agent.Safety ──┐
协调者(Planner/Executor) ┼── 子 Agent.Logic ─┼→ 聚合 / 仲裁 → 最终输出
                    ├── 子 Agent.Perf  ──┤
                    └── 子 Agent.Arch  ──┘
```

它的骨架是：

- **一个协调者（Coordinator / Planner / Executor）**：决定"这次任务怎么拆、分给谁、什么时候聚"。
- **多个子 Agent（Specialist）**：各司其职，彼此不直接通信，只向协调者回结果。
- **聚合 / 仲裁（Aggregate / Judge）**：把子 Agent 的结果合成最终输出，必要时做冲突裁决与置信度校准。

**关键**：子 Agent 之间通常**不直接对话**，而是**星型向协调者汇聚**——协作通过协调者完成，而不是子 Agent 相互通信。这正是你在第 15 讲选的**星型汇聚**、第 18 讲的**加权仲裁**。

### 2.2 多 Agent 能并行不乱的三个设计支柱

"多调几个模型"谁都会，但**怎么让它们并行而不互相污染、结果还可靠汇总**，才是多 Agent 框架真正的设计含量。DeepAgents 依赖三个支柱，你该把它们和你的实现逐一对上：

**① 上下文隔离（context isolation）**：每个子 Agent **只拿到它该看的那份上下文**，看不到主 Agent 的完整上下文，也看不到别的子 Agent 的中间产物。**为什么这么重要**：一个子 Agent 若被塞进主语境的全量信息，注意力会被无关信息稀释（第 65 讲 O(n²) 的代价、第 44 讲的准入分层）——**隔离是为了让每个 Agent 聚焦**。对应你第 59 讲的 **TeamResolver + X-Team-Id 租户隔离**：每个团队只见自己的基线，正是"上下文隔离"在生产里的版本。

**② 结构化交接（structured handoff）**：协调者给子 Agent 的不只是一段自由文本指令，而是一张**任务卡（task card）**——里面写清**目的、它该看的上下文、它和工具集、以及它要交付结果的 schema**。子 Agent 完成后，**按约定 schema 回传一个结构对象**（而非自由发挥一段话）。**为什么关键**：自由文本交接会让下游"解析"变成灾难（第 06 讲结构化失败的对立面）；结构化交接让聚合器能**确定性消费**每个子结果。对应你第 45 讲的 **`ToolResult` 结构化设计**、第 14 讲 `Verdict`/`Level` 枚举——**你不是让 Agent"自由汇报"，而是让它"按枚举返回可裁决的结论"。**

**③ 共享文件系统当工作内存**：多 Agent 之间若必须共享"中间态"（比如一个子 Agent 产出的草稿，另一个要接着改），DeepAgents 常用**共享文件系统**做协作媒介——每个子 Agent 读写约定好的文件，而不是直接"对话"。**为什么用文件**：文件是**持久、可定位、可基准**的共享态，比"发消息"更容易排错、可回溯（对应你"材料二进制存 MinIO、元数据存 PG"的铁律）。对应你第 15 讲把各 Agent 结果先落库、再由聚合器读库的做法。

**这三根支柱，一句话收束**：**隔离上下文保证聚焦、结构化交接保证可消费、文件共享保证可回溯**——是"多 Agent 能并行还不乱"的最小充分条件。你对照自己的系统，会发现你已经用 `X-Team-Id` / `ToolResult` / PG 分别实现了这三件事，只是之前没给它们起"多 Agent 设计支柱"这个名字。

### 2.3 两种调度模式：handoff（交接）vs supervisor（监督）

多 Agent 框架里，协调者"怎么调用子 Agent"有两条主流路线，值得分清：

- **handoff（交接/委托）**：主 Agent 把一个子任务**整个交给**一个子 Agent，交出去后**自己等结果**，子 Agent 拥有该子任务的**完全自主权**。像"老板把事情包给一个下属，只要成品"。**对应你审查流程里"把一个维度整个交给 Safety Agent，它自己闭环"**。
- **supervisor（监督者）**：协调者**逐轮**给不同的 worker 下指令、看结果、决定下一轮叫谁，像一个**中央调度**反复派活。**对应你第 15 讲协调者"收到结果 → 仲裁 → 决定是否补一轮"的中央控制**。

**你的系统其实是"两者混用"**：把维度**交接**给 5 个 Agent（handoff 式分工），但**聚合与是否重审**由协调者中央裁决（supervisor 式控制）。看清这两条路线，你就能读出"我这个多 Agent 到底是委托型还是监督型、该不该调整"。

### 2.4 它和"图"不是一回事（把维度分开）

这是整个模块最容易混的地方，单独扣一下：

| 框架 | 它解决的层次 | 一句话 |
|---|---|---|
| **LangChain（链）** | 单次任务的**编排原语** | 顺序步骤 |
| **LangGraph（图）** | 单次任务的**编排原语** | 节点 + 边 + 闭环 |
| **DeepAgents（多 Agent）** | 任务的**架构取向** | 要不要拆多人做、怎么聚 |

**关键**：图和多 Agent 是**两个维度**。你可以**用图来实现多 Agent**（协调者是图里一个节点，调度多个子 Agent 的流程在图里画），也可以**只用链跑单 Agent**。**"用多 Agent 框架"不代表"用图"，"用了图"也不代表"就是多 Agent"。**

**对你的启示**：你的 `code-review-agent` 同时用了两者——**多 Agent 维度**上它是 1 协调 + 5 子 Agent（第 15 讲星型），**编排维度**上它用 CompletableFuture + 状态机实现了并行和聚合（第 17 讲）。**你不是"图"或"多 Agent"，你是"多 Agent 架构 + 自写并发编排"的组合。**

### 2.5 什么时候该用多 Agent、什么时候不该

**判据句**：**多 Agent 不是默认选项——只有当『单一 Agent 因为专业性、并行性、判据独立性，做不了或做不好』时才拆；拆了之后必须想清楚『谁来协调、结果怎么聚、冲突谁仲裁』，并落实『上下文隔离、结构化交接、可追溯共享态』三支柱。** 沿用第 14 讲那道四级判据。

拆与不拆的两种典型处境：

- **该拆**：任务被**专业维度**自然切分、每个维度有独立判据（你的五个审查维度恰好如此），或需要**并行**提速。→ 星型汇聚 + 专业分工 + 三支柱。
- **不该拆**：任务是一个强依赖前后文的整体、拆了协调成本大于收益，或"多个 Agent"纯为显得高级。→ 单一 Agent（或"骨架固定 + 局部闭环"）。

**对你的启示**：审查的正解是**该拆**——五维度判据独立、可并行、仲裁可解释。但**不是所有任务都这样**：比如"把一段代码重构"，强依赖上下文，拆多个 Agent 反而更慢更乱。**知道什么时候不拆，是和知道什么时候拆同等重要的能力。**

### 2.6 前沿深挖：多 Agent 的正面证据与反面檄文——15 倍 token 的账单与 Cognition 的反对票

多 Agent 在 2025 年同时拥有最亮的实战数据和最尖锐的反对意见，两边都该读：

**① 正面：Anthropic 的多 Agent 研究系统给了真实的成本-收益比。** Anthropic 官博《How we built our multi-agent research system》披露：其 Research 功能用 **orchestrator-worker 架构**（lead agent 规划并派生多个并行子 agent，各自带独立上下文窗口），在内部评测中**多 Agent 系统比单 Agent 表现领先约 90%**——但账单同样醒目：**多 Agent 消耗约 15 倍于普通 chat 的 token，单个 Agent 任务也已是 4 倍**；且**token 用量解释了约 80% 的性能方差**。**这组数字就是多 Agent 的定价公式：它只适合"答案价值 ≫ 15 倍 token 成本"的深度任务**——深度研究、大规模审查值得；日常问答是拿大炮打蚊子。

**② 反面：Cognition《Don't Build Multi-Agents》的核心指控是"隐式决策冲突"。** Cognition（Devin 团队）的反对不是性能而是**可靠性**：子 Agent 各自在隔离上下文里做了大量**隐式决策**（怎么理解任务、哪些细节重要），主 Agent 拿到的只是浓缩摘要——**摘要丢失了决策依据，多个子 Agent 的结论可能在隐含假设上互相冲突，而聚合者无从发现**。他们的替代方案：**只读/边界清晰的子任务才隔离；写操作保持单线程**；子 Agent 返回的不只是结论，还要带回关键上下文。

**③ DeepAgents 的位置：它是"LangGraph 之上的官方 harness 样板"。** LangChain 官方的 `deepagents` 包（github.com/langchain-ai/deepagents）把四件事打包成开箱即用：**文件系统工具（读/写/编辑/ls 当"外挂记忆"）、子 Agent 派发、上下文管理、 skills 挂载**——底层仍是 LangGraph 运行时。它的意义不在于新原语，而在于**把"一个像样的 Deep Research 式 harness 该有什么"固化成了参考实现**——和你这 73 讲建的东西是同一层。

**可迁移判据**：**多 Agent 的立项检查表三问——任务价值是否 ≫ 15× token 成本？子任务边界是否清晰到"只读隔离"就足够？聚合者能不能拿到"结论 + 决策依据"而不只是摘要？三问有一问答不出，先用单 Agent + 好工具。**

## 三、避坑清单

- [ ] **别把"多 Agent"和"图"混成一回事**——图是编排原语，多 Agent 是架构取向，两维度。
- [ ] **别以为"多 Agent 听起来高级就应该用"**——第 14 讲判据：单一 Agent 做不好才拆，拆了要讲清谁来协调、怎么聚、谁仲裁。
- [ ] **理解多 Agent 的三设计支柱**——上下文隔离、结构化交接、可追溯共享态；少了任何一根，并行就会乱。
- [ ] **理解星型汇聚的取舍**——子 Agent 不直接通信、向协调者汇聚，是减少耦合的关键，也是单点（协调者）风险所在。
- [ ] **分得清 handoff 与 supervisor 两种调度**——委托型 vs 监督型，你的系统常是混用，要知其取舍。
- [ ] **别用多 Agent 掩盖设计不明**——如果说不清"为什么每个子 Agent 独立存在"，那拆了就是加协调成本。
- [ ] **知道"什么时候不该拆"同样重要**——强依赖上下文的任务用单一 Agent 或"骨架固定 + 局部闭环"。

## 四、动手任务

> **目标**：用"多 Agent 架构取向 + 三支柱"，审视你自己的系统，并把它和"图/链"的维度分开。

**步骤 1：画出你的多 Agent 形状**

把 `code-review-agent` 画成"协调者 + 子 Agent + 聚合"的星型图。**标出：谁是协调者、每个子 Agent 的专业边界、结果怎么聚、冲突谁仲裁。**

**步骤 2：回答"为什么拆"**

对每个子 Agent 问一句：**"这个维度为什么不能由别的 Agent（或单一 Agent）顺带做？"** 答得出独立判据 → 拆得对；答不出 → 可能是为了拆而拆。

**步骤 3：用"三支柱"核对你自己的实现**

对照第 2.2 节三支柱，指出你系统里**哪块在实现"上下文隔离"（X-Team-Id）、哪块在实现"结构化交接"（ToolResult/Verdict）、哪块在实现"可追溯共享态"（PG/MinIO）**。缺哪根，就补哪根。

**步骤 4：写一张"维度分开"的对照表**

画一张表：**你的系统在『编排原语』（链/图/自写）和『架构取向』（单/多 Agent）两个维度上分别是什么**。这张表就是你说"我理解 DeepAgents，也理解我的系统"的底稿。

## 本讲小结

1. **DeepAgents = 多 Agent 架构取向**：协调者调度多个子 Agent，星型汇聚 + 聚合/仲裁。
2. **多 Agent 能并行不乱靠三支柱**：上下文隔离、结构化交接、可追溯共享态。
3. **图 vs 多 Agent 是两维度**：图是编排原语，多 Agent 是架构取向，可组合不替代。
4. **你的 code-review-agent 是真实多 Agent 落地**：1 协调 + 5 子 Agent + 加权仲裁（M3），三支柱已按 X-Team-Id / ToolResult / PG 落实。
5. **多 Agent 不是默认选项**：第 14 讲判据——单一 Agent 做不好才拆，拆了要讲清协调/聚合/仲裁。
6. **知道"什么时候不该拆"同样重要**——强依赖上下文的任务用单一 Agent 或"骨架固定 + 局部闭环"。

**模块十一收官**。四个专题（通用知识 / LangChain / LangGraph / DeepAgents）用同一把"六机制四问"尺子照完，你得到的不是"会用四个框架"，而是**一套能读懂任何 Agent 系统的判断力**——这正是你在 M7 建好的 Harness 判断力，在生态层面的反馈闭环。全书至此，从"你能建一个系统"，到"你能读懂任何系统"，闭环合上。
