> 🎯 导读问题：**"Jev 凭什么比大模型快两个数量级——是它更小更弱，还是它压根没干同一件事？"** ——能答出"它砍掉了整整一个**解码环节**：第 62 讲说自回归模型每吐一个 token 都要跑一次完整前向，生成 N 个 token 就是 N 次串行前向；第 65 讲又告诉我们，这 N 次里每一次都要把前面全部的 KV cache 重读一遍（decode 是**显存带宽密集型**，不是算力密集型）。而 Jev 的输出是**你预先写死的选项空间上的概率分布**——它**没有输出序列**，一次前向把所有问题答完。所以快不是"算力省了"，是"**解码这一步根本不存在**"，这也正是它敢把"输出免费"写进价目表的原因"——就把"决策模型"和"更便宜的对话模型"彻底分开了。**本讲判据：凡是"答案空间可以事先写死"的地方，都不该付生成的钱——把"判断"从"生成"里拆出来。**

## 一、痛点

前四讲我们一直在问"别人怎么把 Agent 编起来"。这一讲要问的是一个你在前 72 讲里**从没正眼看过**的问题——而它恰恰是你系统里最贵、最不稳、最难调的那部分。

**痛点一：你一直在用"会写作文的模型"做"填选择题"的活。** 回想你在第 06 讲建的那条链：让模型返回一段 JSON，然后**解析、校验 schema、失败重试**。你在那里立过判据——"**模型说人话和不说错话是两件事**"。可现在回头看，这条判据还留着一个没堵完的口子：**我们从来没有质疑"这件事该不该用生成模型做"**。让模型判断"这段代码是不是 SQL 注入"、"这次请求危不危险"、"这条 PR 该走哪个审查档位"——**这些问题的答案空间，我们事先就知道全部可能取值**（是 / 否；五个档位之一；1 到 5 分）。而我们付出了什么？**prompt 里写一遍格式要求、输出里生成一段解释、程序里把解释切掉、schema 不对再重试一次。** 你为一段你根本不要的"理由"付了 token，还得自己把它摘干净，然后祈祷第一个 token 没有把后面的结构带跑偏。

**痛点二：你的"置信度"只在离线管用，线上没有一个"当场识别"的接口。** 你在第 19 讲建了 `ConfidenceCalibrationService`——**事后算账**：规则准不准，靠人工标记的误报/正报慢慢校准，`calibrated = rawConfidence × historicalAccuracy`（`code-review-agent` / `core/calibration/ConfidenceCalibrationService.java:93`）。它解决的是"**同一规则长期准不准**"，但它回答不了另一个问题：**"就这一段代码、就这一次判断，模型自己有多确定？"** 而你现在拿到的是什么？——`LlmFindingParser` 里模型不给 `confidence` 时，**默认兜底 0.75**（`core/llm/LlmFindingParser.java:74`）。**一个"默认值"混进了本该表达不确定性的字段**：0.75 既不是模型的判断，也不是历史准确率，它只是一个占位符。于是一条"模型其实很含糊"的发现，和一条"模型很确定"的发现，在你系统里长得一模一样。

**痛点三（这一讲新增的视角）：你从没算过"生成"这笔账到底贵在哪一层。** 你在第 32 讲记过 token 成本、在第 44 讲压缩过上下文，但你可能把"生成慢"当成一个**笼统的量**——"模型大所以慢"。而第 62 讲和第 65 讲已经把这件事拆得很细了：**慢的是解码循环，不是那一坨参数**。分不清这一点，你就看不出"不生成"到底省了什么，也就无法判断 Jev 这类东西是"又一个便宜模型"还是"另一件事"。

本讲要建立的，是一条能把这三个痛点一次切开的判据：

> **"判断"和"生成"是两种活，不该用同一种模型干。** 凡是答案空间**可以事先写死**的判断——是不是、选哪个、打几分——都应该走**决策模型**：不生成文本、直接回类型化答案和校准概率、一次请求并行问完。生成模型只留给你真的需要"产出语言"的地方。你系统里那些"用生成模型做选择题 + 解析 + 重试 + 兜底 0.75"的地方，就是这条判据的靶心。

## 二、原理

### 2.1 它是什么：一句接口，把整件事讲完

Jev 的官方定义只有一句：**System One 模型读得懂自然语言，但返回类型化答案和概率，而不是生成的文本**（TypeSafe AI 官方文档 `docs.typesafe.ai/concepts/system-one`）。它的接口形状更短——**一个端点、一次往返**：

```
POST https://api.typesafe.ai/v1/systemone

{
  "model": "jev-latest",
  "state": { "ticket_message": "…", "refund_policy": "…" },
  "questions": {
    "refund_requested": { "type": "noul", "instructions": "Does `ticket_message` request a refund?" },
    "request_type":     { "type": "choice", "instructions": "…", "criteria": { "refund": "…", "rebooking": "…" } },
    "frustration":      { "type": "score", "instructions": "…", "criteria": ["Calm", "Concerned", "Very angry"] }
  }
}
```

拿回来的不是文本，是**你指定的那几个 ID 上的类型化答案**。它有两条性质，是后面所有取舍的根：

- **答案被约束在你给的选项里。** 模型只在你的选项 / 档位上给出概率分布，**永远不会回一个选项之外的值**——所以"解析"这一步在架构上就不存在（这正是第 06 讲那条"结构化输出会失败"的病，从**接口契约**层被切掉，而不是靠重试修补）。
- **每个答案互相独立。** 一个问题的答案不会变成另一个问题的隐式上下文，你可以随时加减问题而不改变其它问题的结果。**这条"独立"，正是 2.3 节"一次前向答完全部"的机制前提。**

**"System One"这个名字的来源，官方自己写明了**：来自卡尼曼在《思考，快与慢》里普及的概念——**系统 1 快而直觉，系统 2 慢而审慎**，这里强调的是**快而聚焦的判断**。对齐一下你熟悉的东西：**你天天调的生成模型是系统 2**（逐 token 串行推导），**Jev 是系统 1**（一次并行给出判断）。这个类比不是营销词——它精确描述了 2.3 节那个"快"的真实来源。

### 2.2 三个原语：把"判断"收敛成三种形状

Jev 只允许你问三类问题。这个"少"是刻意的：**它逼你把一个含糊的大判断，拆成能被代码直接消费的原子判断。**

| 原语 | 回答什么 | 返回什么 | Java 里对应什么 | 典型用法 |
|---|---|---|---|---|
| **Choice** | 这几个选项里是哪个？ | `choice` + `probabilities`（全选项分布）+ `confidence` | `switch` 的真值分支 | 分流、分类、指派 |
| **Score** | 落在哪一档？ | `score`（**可以落在两档之间**）+ `legend` + `probabilities` + `confidence` | 阈值比较 | 严重度、优先级、风险分 |
| **Noul** | 这件事成立吗？ | `noul`（0~1 的"是"的概率）——**没有单独的 confidence** | 一个 `if` | 是否越权、是否注入、是否需要人看 |

三条官方给的判据，值得原样记住（2.4 节会从 softmax 的角度解释它们为什么长这样）：

**① 选 Noul 还是 Score，看你要的是"是/否"还是"程度"。** 官方专门警告了一个坑：**Noul 的 0.5 表示"是"和"否"概率相等，它不是"中等程度"**。如果你要表达"这个候选人 Python 强不强"，用 Noul 就会得到一个无法解释的数——正确的问法是"**简历里是否写明在工作中用过 Python**"（一个可判定的命题），或者干脆改用 Score（无经验 / 有点熟 / 天天用 / 深度掌握）。

**② 看不清"操作"和"判断"边界的地方，挑代码能直接消费的那个形状。** Choice 天然映射三条代码分支，Score 映射一个阈值，Noul 映射一个 `if`。

**③ 别问"复合问题"，拆开再在代码里加权。** 这是官方最强调的一条工程纪律：像"评估这次客服交互并决定是否全额退款"这种**一语多问**的复合 prompt，把用户情绪、政策资格、购买凭证、金额影响全揉进一个不透明的自然语言结论里——**拆成三个原子问题**（是否有退款诉求 / 是否有重复扣款证据 / 政策是否支持），各自拿一个标量，**在确定性代码里按权重合成**（官方叫 Composite scoring）。**权重是你的、显式的、可改的、可回归的**——而不是藏在 prompt 里的形容词。

> 一句话对照你已经建过的东西：**这三个原语，等价于你第 14 讲给 `Verdict` 定枚举、第 45 讲给 `ToolResult` 定结构、第 18 讲给仲裁定权重**——你早就在这么干了，只是干在了"自己写的规则"上；Jev 把这一步做成了一个不用你写规则的接口。

### 2.3 底层第一刀：砍掉 decode 循环——从"N 次前向"和 KV 缓存账说起

前面两节是"它长什么样"。从这一节起，我们换一把尺子——**用 M10 讲过的机制，量它到底在底层动了哪一刀**。因为"快两个数量级"这句话如果只是厂商口径，它就没有工程价值；只有当你能指出**它省掉的是哪一步计算**，你才能判断这个便宜是不是可持续、以及你会不会在别的地方把它省下的钱又花回去。

**先看生成模型这边。第 62 讲 2.4 节把这条账算过了，这里只取两句结论：**

- **① 自回归 = 生成 N 个 token 就要跑 N 次完整前向。** 注意不是"一次前向输出一段"，是**一次前向只输出一个位置**。你要 150 个 token，就是 150 次。
- **④ prefill 与 decode 是两种不同的计算。** prefill（把整段提示词一次性塞进模型）是**计算密集型**，矩阵乘法多、并行度高；decode（一个一个吐 token）是**显存带宽密集型**——每次算的量很小，但要频繁读 KV cache。

**再看第 65 讲 2.4 节那份账。** KV cache 的显存占用是：

```
KV cache ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 每参数字节数
```

以第 65 讲手算过的 **Llama 3 8B**（32 层 / 32 头 / 头维度 128 / FP16）为例，**每一个 token 的 K、V 是 512 KiB**：

```
2 × 32 × 32 × 128 × 2 字节 = 512 KiB / token
```

上下文 4k 时，这份缓存是 **2 GiB**（与第 65 讲的例题一致）。**关键在下一步**——decode 阶段每生成一个新 token，都要把这份缓存**完整读一遍**：它算的量很小、读的量很大。这就是"显存带宽密集型"的物理含义。

**把两个数字乘起来，你就看见钱花在哪了：**

> **一次 150 token 的 JSON 输出**（假设 batch=1、不共享前缀）
> = **150 次 decode 前向**
> × **每次重读约 2 GiB KV 缓存**
> ≈ **300 GiB 量级的显存读取**
>
> 按一张 A100 约 2 TB/s 的显存带宽折算，**光"重读缓存"这一项就是 0.15 秒量级的纯读时间**——还没算权重读取、矩阵计算、调度开销。
>
> **而 Jev 这边：一次 prefill + 一次输出前向。它没有第 2 个 token。**

必须说清这个演算的边界（否则就是拿它当营销材料）：**这不是在拿 Jev 和 Llama 比速度**——Jev 的模型规模、层数、架构**都没有公开**，两者不可直接相减。这个演算只证明一件事——**结构差异在哪一层**：

| | 成本随什么增长 | 输出长度是变量吗 |
|---|---|---|
| **生成模型** | 随**输出 token 数**线性增长（N 次 decode） | 是。写得越长越贵，且贵在带宽 |
| **Jev** | 与**输出长度无关**（没有输出序列） | 否。它产出的是一组标量 |

于是"**加一个问题≈不加延迟**"就有了机制解释：官方说每个问题的答案**互相独立**（2.1 节那条性质），**没有串行依赖就没有串行计算**——它不是"算得快"，而是**这些问题之间本来就不需要排队**。

**现在回头看那条价目表：输入 $0.042 / 百万 token，输出免费。** 把这两件事并排看——**"输出免费"不是一个营销决定，而是"没有输出 token"这个机制事实在账单上的直译**。生成模型最贵的那部分（逐 token 解码）在这个产品里根本不存在，所以它只能按输入计费。**当你能用一个机制事实去解释一条商业条款时，这个便宜才是结构性的，而不是补贴出来的。**

把这两条路径并排画出来，差异一眼可见——**注意右边那条链比左边短了整整一段，而短掉的那一段正是"随输出长度增长"的那一段**：

> **图 73-1**　两条前向链的对比。上排是生成模型：prefill 之后必须进入 **N 次 decode**，每一步都要把前面的 KV 缓存完整重读一遍（第 65 讲），**成本随输出 token 数线性增长，且贵在显存带宽**。下排是 Jev：prefill 之后**只有一次输出前向**，每个问题各得一个分布，**没有输出序列**——所以"多问一个问题"几乎不增加延迟，所以"输出免费"在机制上讲得通。

> **本节的判据**：看到任何一个"比大模型快 N 倍"的叙事，先问**它砍掉的是哪一段计算**。砍掉的是解码循环（结构性的、可持续），还是换了个更小的模型（程度问题、可被对手追上）——这两者的工程含义完全不同。

### 2.4 底层第二刀：softmax 之后的那条岔路——生成模型扔掉的分布，Jev 交还给你

如果说 2.3 节讲的是"**省掉了什么**"，这一节讲的是"**拿回了什么**"。而它会揭示一件更根本的事：**Jev 在数学上并没有发明新东西，它只是站在了同一条前向链的一个更早的位置上。**

第 62 讲 2.3 节把"模型怎么吐出文字"拆成了四层，我们来重看一遍——**重点在第 2 层和第 4 层之间发生的事**：

| 层 | 生成模型做了什么 | Jev 做了什么 |
|---|---|---|
| ① **logits** | 最后一层对词表每个 token 给出未归一化分数 | 同样产生一组分数 |
| ② **softmax** | `p_i = e^{z_i} / Σⱼ e^{z_j}`，压成合法概率分布 | **同样产生一个概率分布** |
| ③ **温度** | 用 T 调节分布的"尖锐 vs 平坦" | **不调节**（T 这个旋钮它不需要） |
| ④ **采样** | top-k / top-p / greedy，**从分布里挑走一个 token** | **不采样** |

**岔路就在第 4 层。** 生成模型辛辛苦苦算出了一个完整的概率分布，然后——**采样策略从里面挑走了一个 token，剩下的分布被丢掉了**。你拿到的是"它选了 `好`"；你**拿不到**"`好` 到底是 0.71 还是 0.99"，除非你额外去要 logprobs。

**Jev 做的事，就是停在第 2 层之后、第 3 层之前：它不进入采样，直接把整个分布交给你。** 所以所谓"决策模型"，在底层上不是一个新架构——**它是把同一条前向链，在 softmax 之后提前结束了。**

这一步立刻解释了三件事，而它们之前看起来像是三个独立的产品设计：

1. **为什么它的答案"永远不会跑出选项"？** 因为你给的是有限选项，分布就定义在这个有限集合上。生成模型的"跑偏"风险来自**在几万到十几万维的词表上采样**（第 62 讲：词表 |V| 通常是几万到十几万），而 Jev 的采样空间是**你写的那 3 个、5 个选项**。**风险不是被"约束"掉的，是这个风险的分母根本不存在。**

2. **为什么三个原语长成那三副样子？** 它们是**同一个分布被读取的三种方式**：`choice` 读"最大值落在哪个选项"、`score` 读"分布的重心落在哪一档"、`noul` 读"某一侧的总概率"。这也顺带解释了 2.2 节那条官方警告——**`noul = 0.5` 为什么不是"中等"**：它是二项分布两半各占 50%，**是分布平坦，不是程度居中**。你要是拿它当"中等程度"用，就是让"不确定"冒充"中等"。

3. **为什么它天生没有"采样随机性"这个病？** 第 62 讲那句结论在这里直接兑现——"**只要 T>0 或用了采样，就没有 100% 确定这回事**"。而 Jev 没有温度、没有采样，**同一个输入给出的是同一个分布**。你系统里那些"同一个 prompt 跑两次结论不一样"的困扰，在这个形态里不存在。

> **本节的判据**：区分"**生成**"和"**判断**"最锋利的那一刀，不切在模型大小上、不切在参数上，**切在 softmax 之后**——**要不要从分布里采样**。采样了，你拿到的是一个 token 序列，你得自己从文本里把答案抠出来；不采样，你拿到的就是答案本身。

### 2.5 `confidence` 是"分布有多尖"的读数——但它只读了最大的那一项

上一节说 Jev 把分布交给你。可工程上"一个分布"没法直接进 `if`——你需要一个标量。这就是 `confidence` 的角色，而它的定义（官方文档 `docs.typesafe.ai/confidence`）恰好把 2.4 节的话接上了：

- **`probabilities` 是分布本身**：Choice 给所有选项上的分布，Score 给所有档位上的分布。
- **`confidence` 是把这个分布"尖不尖"压成的一个 0~1 的数**：**全部压在一个选项上就是 1.0，越摊平越低**。官方给的三选项近似算法是 `(3 × 最大概率 − 1) / 2`。
- **Noul 没有 `confidence`**——因为概率本身就是答案（二项分布一个数就说完了）。

**先看清楚这个公式是什么。** 把 `confidence = c` 反解，得到 `p_max = (2c + 1) / 3`：

| `confidence` | 最大概率 `p_max` | 分布形态 |
|---|---|---|
| 1.00 | 1.00 | 完全押在一项上（最尖） |
| 0.50 | 0.67 | 有明显优势但没压倒 |
| 0.00 | 0.33 | 三选项完全均匀（最平） |

**所以 `confidence` 就是"最大概率"的一次线性变换**——它读的是**分布最高的那一根柱子有多高**。回想第 62 讲 2.3 节讲的那件事：**温度 T 控制的是"分布的尖锐 vs 平坦"**。`confidence` 就是**同一个性质的一个读数**——只不过温度是你调节分布的旋钮，`confidence` 是模型自报的、这个分布当前的尖锐度。

**这里有一个你必须自己知道的盲点**（这一段是本讲的深挖，官方文档没写，但从它给的公式可以直接推出来）：

> **`confidence` 只用了 `p_max` 一项，它看不见"第二名"离得多近。**
>
> 拿两个分布对比（三选项）：
>
> - 分布 A = `[0.60, 0.20, 0.20]` → `confidence = (3×0.6 − 1)/2 = 0.40`
> - 分布 B = `[0.60, 0.40, 0.00]` → `confidence = (3×0.6 − 1)/2 = 0.40`
>
> **两者的 `confidence` 完全相同（都是 0.40），但它们的工程含义截然相反**：A 是"第一项遥遥领先、后面两个都差不多"，B 是"**第二项只差一点就翻盘**"。对"要不要送人工复核"这个决策，**B 才是该警觉的那个**——但你只看 `confidence` 的话，两者长得一模一样。

这正是官方那句"**你并没有被锁死在官方那个 `confidence` 算法上——完整分布也一并给你了**"的具体含义：**`confidence` 是官方给的一个便利读数，不是唯一读数。** 完整分布给到你手上，你就可以自己定义更贴业务的确定性度量——比如把"最大项"和"次大项"的差（margin）也纳进来，或者直接算归一化熵。**这是把"要不要人复核"这条线掌握在自己手里的前提。**

**而阈值怎么定，官方给的是三档，但真正的判据是"分界线随风险走"**：

| 档位 | 行为 | 官方口径 |
|---|---|---|
| 高置信 | 自动执行 | 模型读得清，无需人介入 |
| 中置信 | 谨慎推进 | 让用户确认 / 标记待审 / 补信息 |
| 低置信 | 不执行 | 转人工、要求澄清、回退到别的系统 |

官方示例里 **`confidence < 0.5` 一律转人工**（"模型自己说不确定就不要猜"）；**低风险动作**（比如展示余额，错了可恢复）在中置信就执行；**高风险动作**（比如批准转账）要求 **0.9 以上**才自动放行。**风险容忍度写在你的代码里，是你可以读、可以改、可以回归的数字。**

**这里有一条官方声明，是整段最该抄进你笔记的一句**：

> **校准是"跨预测群体"的度量——它不保证单个答案是对的。**（Calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct.）

对照你的系统，这段的落点非常清楚：**第 19 讲的 `calibrate()` 是"这条规则历史上准不准"（规则级、离线、事后）；Jev 的 `confidence` 是"就这一次判断，模型自己有多确定"（实例级、在线、当场）。** 两者是**同一条轴线上的两端**——而不是两套互相竞争的做法。你过去只有左端，右端靠一个 `0.75` 的默认值硬撑；**这就是"当场识别"缺的那一环。**

顺带说，第 62 讲 2.5 节讲过的两个"当场识别"黑盒方案——**对同一前缀采样多次看 log-prob 方差**、**盯住第一个幻觉 token**——和 Jev 是同一件事的两条路：**黑盒方案要"采样 3~5 次"才能近似摸到的东西，白盒形态一次请求就给全了**。这不是说 Jev 更好，而是说：**当你要的是"不确定性"这个量时，"能直接给分布的模型"和"得靠重复采样去估计的模型"是两代形态。**

### 2.6 训练侧的对标：RLCD 接在"可验证奖励"这条线上

前面三节讲的是**推理**（2.3 省了什么、2.4 拿回什么、2.5 怎么读）。这一节看**训练**——因为"它为什么值得信任"这个问题的答案，最终在训练方法里。

官方只给了一个名字和一句定位：训练方法是 **RLCD（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习）**，**不做微调 / 不加 LoRA、所有账号共用同一套权重**。**它没有公开奖励怎么构造、损失怎么写的细节。** 所以下面这段是**机制层的对照，不是对 RLCD 内部实现的复述**——请按"分析"读，不要按"官方口径"读。

先把第 68 讲那条谱系摆出来。那一讲在 2.7 节给出了一个关键判断：**2025 年对齐的主线已经从"讨好人类"转向"可验证奖励"（RLVR），但 RLVR 只覆盖"能判对错"的域**——数学题对答案、代码跑测试，这类任务有**裁判**，所以奖励信号干净；而"写得好不好""回答得体不得体"没有裁判，只能训练奖励模型（reward model），**而 reward model 会被 hack**（第 68 讲 2.7 节引的那条工作：**奖励不能无界，要限制最大奖励并加强 KL 惩罚**）。

**现在问一个问题：一个"判断概率"的模型，它的奖励可验证吗？**

**答案是可验证的——而且验证方式极其朴素：事后对照真值。** 你说"这件事有 70% 概率成立"，等事情有了结果，就能检验这句话的准确性。一套校准良好的预测系统，长期看它的 0.7 应该真的对应约 70% 的命中率。**这意味着"校准"恰好落在 RLVR 那条线上**：它不需要人类来打分，**它有裁判**（真值），所以奖励信号是干净的、不容易被 hack 的。

把这条对照说成一张表，就是本节的结论：

| | 奖励从哪来 | 有裁判吗 | 会被 hack 吗 |
|---|---|---|---|
| **RLHF**（第 68 讲） | 人类偏好排序 → 奖励模型 | 没有（裁判是人类喜好的代理） | 会。"为讨好而编造"就是它的副作用 |
| **RLVR**（第 68 讲 2.7） | 数学对答案 / 代码跑测试 | **有**，客观可判 | 难（除非测试集本身被过拟合） |
| **RLCD**（Jev） | **校准**：概率与真实频率是否一致 | **有**，事后知道真值就能算 | 机制上难（要作弊就得让概率与真值长期一致） |

**顺着这张表，你还能推出一个有意思的结论：Jev 几乎没有"讨好的空间"。** 第 68 讲 2.6 节讲过 RLHF 的副作用——模型学会"把话说得像正确的、像你想听的"，**而这种倾向恰恰是编造的温床**。但 Jev 不说人话：**它不产出一段能被"讨好"改写的东西，它只输出一组概率**。它没有"把话说漂亮"这条路可走，**它的全部作弊空间被压缩在"概率报得准不准"这一件事上**——而这正是它被训练去优化的目标。**"不给理由"在这里不只是产品选择，它同时删掉了一整类失败模式。**

> **本节的判据（也是本讲最深的一条）**：**在"判断"这类任务上，可验证性比表达能力重要。** 一个能说会道的模型给你的理由，可能本身是"对齐出来的合理话术"（第 68 讲）；而一个只报概率的模型，至少**它的输出是可以被真值检验的**。选工具的时候先问：**这东西的输出，事后能不能判对错？能判——那它适合被训练得很准；不能判——那你只是在信任一段措辞。**

### 2.7 中文为什么弱：分词层与校准层的双重夹击

这一节处理那条最像"备注"、实际最像"前置条件"的限制：**官方文档说英文是主要训练语言、准确率最好；包括 CJK 在内的其它语言"能处理，但不如英文好"，并建议"在依赖它处理非英文负载之前先自己测，并特别关注 confidence"。**

对你这套**输入面全是中文代码评审文本**的系统来说，这句话是能不能用的门槛。而它的原因，M10 讲了两层，**而且两层是叠乘的**：

**第一层在分词（第 64 讲）。** 第 64 讲 2.4 节的词表决策树里写得很直白：**纯 BPE 字节级方案下中文"按字节切，一个字拆 2–3 个 token"，多语言通用词表（10 万级）下"中文仍然偏碎，约 1.5–2× 英文 token 数"**。而 2.3 节讲过 BPE 的一条代价——**低频词一定会被拆碎**。中文在英文为主的语料里就是"低频"的：同样一句意思，中文会被切成更多、更碎的 token。

**这对 Jev 的伤害比对生成模型更大**，原因在于 2.5 节那条——**它的核心能力是"校准"，而校准是在训练分布上学出来的**。一旦输入分布换了语言：

- 语义单元被切得更碎 → 送进模型表示层的"块"更小、更碎；
- 而**校准恰恰是对"分布外"最敏感的那种性质**：模型在英文上学到的"我说 0.7 就有 70% 对"，换到中文负载上**没有理由自动成立**。

**所以官方那句"特别关注 confidence"不是随口提醒的客套话——它在说：这个产品最值钱的那部分输出（校准），恰好是最容易在换语言时失准的那部分。** 这也是为什么第 64 讲 2.4 节那条工程判据——**"接入一个新模型前，先拿你业务的真实语料跑一次 tokenizer，算 fertility"**——在这里从"省钱技巧"升级成了"能不能用"的前置检查。

> **本节的判据**：**语言支持不是一个"覆盖率"问题，是"校准还有没有效"的问题。** 生成模型换个语言，最坏结果是"说得差一点"；而一个校准模型换个语言，最坏结果是——**它依然用同样自信的语气，给出一个已经不成立的置信度。** 后者危险得多，因为你的代码正在拿这个数做自动放行的决定。

### 2.8 为什么"不解释自己"在这里反而是一种诚实

官方最硬的一条限制：**System One 模型不写回复、不产出代码、不解释自己的推理。** 一般读到这里会把它当缺点记账。但把第 66 讲和第 68 讲摆过来看，这条限制有另一面。

第 66 讲 2.3 节给的判断是：**涌现出来的"推理"是"貌似推理"，本质仍是统计产物**——模型没有真正的逻辑推理，它只是把看起来连贯的东西接下去。而第 68 讲 2.6 节补了另一半：**对齐会让模型倾向于"把话说得像正确的、像你想听的"**。把这两条叠起来，你就得到一个不太舒服的结论：

> **当生成模型给你一段解释时，你无法从这段话本身判断它是"真的因果"还是"一段被对齐得很像解释的措辞"。**

而 Jev 选择**不进入这个游戏**：它不给措辞，只给一个数。于是：

- **好处**：你说的每句话都**天然可检验**（对着真值算就行），**没有任何一段"听起来很合理"的话术需要你去拆穿**。你不会被"论证的流畅度"误导。
- **代价**：**可解释性的责任整个移到了你这边**。你拿到一个 0.4，要给人一个说法，就必须**自己挂一层真正的生成模型**去写解释——而这层解释和那个数字之间，是**你自己搭的关系**，不由模型兜着。

这不是"缺点 vs 优点"的选择题，而是一条**架构分工**：**Jev 是链路上的一颗判断件，不是一个可以单独顶上去的系统。** 所以采用它的正确姿势从来不是"替换掉生成模型"，而是"**把判断从生成里拿走，然后把要说话的那部分，明确地交给另一个组件**"。凡是你的流程需要"给个说法"（给用户看的说明、给审计的论证、给下一个 Agent 的上下文），那一环必须另有其人。

### 2.9 四个插点：把它接到你自己的系统上

产品好不好用是一回事，**它在你系统里补的是哪个洞**是另一回事。对着真实代码找，正好四个，而且每个都能指出**现在缺什么**。

**插点①：模型档位路由——你的网关现在是"可用性路由"，不是"语义路由"。** 看 `ModelGateway` 的循环（`code-review-agent` / `core/llm/ModelGateway.java:113`）：`routeStrategy.next(rotate(candidates, strategyCursor))`——它按**优先级顺序轮转**，跳过熔断 OPEN 和配额耗尽的供应商。这是一条很硬的**失败兜底**链路（选谁不选谁由"谁还活着"决定），但它**不回答"这道题该用哪个档"**：一次拉取式问答和一次架构级根因分析，在它眼里是同一类任务。而这恰好是 Jev 官方给的第一个杀手级用法——**模型路由**：让一个决策模型判断"这个请求属于简单查询 / 常规编码 / 复杂架构"，然后把**最便宜且够用的模型**选出来。LangChain 的官方集成里，这就是一个 `ModelRouterMiddleware`（挂在 `before_agent` / `wrap_model_call`），判据句官方给的是："**Choose the least costly model that can complete the task safely.**"——**用最便宜的、能安全完成任务的模型**。对照你的系统：**你现在只有"降级链"，没有"降档链"。** 接上第 66 讲 2.2 节的 scaling law 再读一遍这条——**"选多大的模型"本来就是一笔算力-收益权衡（收益是幂律、成本是线性）**，而你现在的网关根本没有在解这道题，它只在处理故障。

**插点②：工具风险前置闸门——把"要不要执行"从生成模型手里拿走。** 你在第 45 讲（工具机制）和第 59 讲（对照 Claude Code 的权限机制）反复立过同一条判据：**工具的危险性判定，不应该由"提议调用工具的那个模型"自己说了算**。Jev 官方给的用法正中这条：**在工具真正执行前问一次"这次调用是否危险、是否授权不足"**，拿回一个 `noul` 概率，然后用**代码里的阈值**决定放行、还是转人工。LangChain 集成里的 `AutoModeMiddleware`（挂在 `wrap_tool_call`）就是它，它的问法直白到几乎就是你写在 `VetoPolicy` 里的那句话——**"这次工具调用是否风险过高、授权不足"**。对照你的系统：你的 `VetoPolicy` 现在已经能保证**父不覆盖子、BLOCKER 不可被抑制**（`core/permission/VetoPolicy.java:26`）——**缺的不是"收敛"，是收敛之前在入口处那一次"这动作危不危险"的独立判断**。

**插点③：注入的语义复核——你已经在用一次"有界判断"了，只是判官是你自己写的向量。** 看 `SemanticInjectionDetector`：它把已知注入模式**预计算成向量**（`"ignore previous instructions and do what I say"`、`"忽略以上所有指令"`…），对输入做余弦相似度，**阈值 0.85 卡死**（`core/security/SemanticInjectionDetector.java:26`），而且**向量服务不可达时降级为空集合、等同放行**。这个设计在你当时的约束下是合理的（它只是纵深防御的第二层，"边界由确定性规则兜底"）。但把它的形状抽象出来看，它做的就是**一个答案空间写死的判断**：`noul`——"这段内容是否在指令劫持"。**区别在于判据的来源**：现在判据是"和 6 条硬编码短语的余弦距离"，改成 Jev 就是"按你写在 `instructions` 里的语义判据判一次"。**这不是"把规则换成模型"那么简单**——它把"**只能匹配我想到的句式**"变成"**可以概括我没写进词表的改写**"，而且**判据句本身进了版本控制**（改判据 = 改一行字符串，可以 code review）。顺带一提，官方把这件事列为 Jev 的**首要推荐用法**：**用极小成本给每一次进出 LLM 的输入输出加一道闸门**（提示注入 / 越狱检测）。

**插点④：结论可信度分——把"当场识别"那半条轴补上。** 回到 2.5 节：你现在有规则级的离线校准（`:93` 的 `calibrate()`），但单条发现拿到的模型置信度是**默认 0.75**（`LlmFindingParser.java:74`）。而你的仲裁是按**固定优先级权重**裁决的——安全 100 > 逻辑 90 > 性能 70 > 架构 60 > 风格 10（`core/report/ArbitrationPolicy.java:21`）。这是一条**正确但粗糙**的判据：它比的是"哪个 Agent 说了话"，**不比"这次它说得有多确定"**。把一条结论的"可信度"补上，你的仲裁就能从"**谁的优先级高**"升级成"**优先级 × 这次判断的确定性**"——**而这一层，恰恰是 2.5 节那个 `confidence`（或者你自己用完整分布定义的那个度量）天然能喂进来的输入**。

### 2.10 前沿深挖：边界、反方证据，和那条必须自己测的前提

产品好用，但把边界讲清才是"深挖"。以下每一条都来自官方文档或公开复测，**并且按"谁说的"分开放**。

**① 它不解释自己——这是最硬的一条限制（机制面见 2.8 节）。** 你拿到的是一个数，不是一个理由。所以但凡你的流程需要"给个说法"，**你必须再挂一个真正的 LLM**——**架构结论：Jev 是链路上的一颗判断件，不是一个可以单独顶上去的系统。**

**② 答案空间必须"事先有界"，且边界由你负责。** 官方明说：Jev **不会替你写 schema**——你必须在调用前就想清楚所有合法取值。这就带来一个**设计责任在前置**的后果：**问不出好问题的团队，用 Jev 只会得到一个精确的坏答案。** 官方给的两个具体量：Choice 的选项集合超过 **255 个**时，得先做**两段式打分**再显式选择（这会同时改变延迟与实现）；Score 的档位官方支持 **2~10 档**。**"问题设计属于系统容量的一部分"**——这句话就是这条限制的工程翻译。

**③ 它只收文本，且英文最好——机制面见 2.7 节，这一条是你必须自己先测的前提。** 官方文档明确：**输入目前仅文本**（字符串 / JSON 对象 / 文本数组），图像、音频、视频都不支持，非文本输入要**先你自己转成文本或结构化字段**。往回接一句第 67 讲：多模态那条线的做法是**把所有模态编码到同一个向量层**，而 Jev 直接砍掉了这条支路——**它的输入面只剩文本 tokenizer 一条入口**。所以你系统里任何"截图 → 判断"的诉求，都要先自己补一个 OCR / 描述层。

**④ 上下文与版本：两个"会静默影响你阈值"的量。** 官方口径是**每请求 64k token 上限**，构成是 **32k 给 `state` + 最长的那一个问题**（不是每个问题各给 32k）。这个 32k 不是随便定的数字——按第 65 讲的账，**上下文长度就是 KV cache 的显存预算**，"上下文预算"这个词在这里是字面意义的账单。另外**别名会漂移**：`jev-latest` / `jev-preview` 都指向版本化的 `jev-1.13.0`，官方明确提醒——**"别名会随新版本发布而移动，你背后的答案会在你毫无改动的情况下变化"**，所以 **"如果你已经把 confidence 阈值调到某个版本上，就钉死版本号，而不是用别名"**。这条对你这种"阈值写进配置、要能回归"的系统是致命的细节：**2.5 节那些按风险分档的阈值，全部依赖校准是稳定的——而别名漂移会从背后悄悄改掉校准。**

**⑤ 训练方法与评测口径：官方披露到哪里，我们就知道到哪里。** 除了 2.6 节的 RLCD 与"不微调、共用权重"之外，更要紧的是它**没给的**：**没有公开权重、没有公开论文、没有公开排行榜**，性能评测目前**主要来自厂商自己**（有德语媒体 heise 也指出过这一点）。所以正确的读法是：**机制层可以信（并行评估、类型化输出、校准概率是写在接口里的）；数字层要打折，且必须用自己的数据重测。** 名字来源上还有个有意思的解读：有分析认为 **Jev 取自经济学家 William Stanley Jevons**（Jevons 悖论：让一种资源急剧变便宜，总消耗反而上升）——**这是第三方解读，不是官方口径**，但它和这个产品的赌注对得上：**当一次"判断"便宜两个数量级，你会在原来根本不会调模型的地方开始调模型**（比如第 62 讲 2.5 节那些"每个 token 都值得查一次"的幻觉检测）。

**⑥ 工程侧的现实：它是"一天就长出生态"的那种东西，也是"还没长出官方 Java 支持"的那种东西。** 2026-09-15 上线时还要排队，到 **2026-09-21 就取消候补、任何人可注册**（新账号给 $5 额度）。官方 SDK 是 **Python 与 JavaScript**；**Java / Kotlin / Scala 的官方指引是"直接调 HTTP API"**——于是社区补上了第一个 JVM 客户端（`typesafe-ai-java`，MIT，`com.jamilxt:typesafe-ai-java-core:0.1.1`，附 Spring Boot starter 与 Spring AI 桥接）。**那个 SDK 作者做得最对的一个决定，恰好是本讲 2.4 节那条判据的答辩**：他**拒绝**把它建在 Spring AI 的 `ChatModel` 抽象上——理由是架构性的而非风格的：`ChatModel` 假设的是"消息进、生成文本出、支持流式"，**而 Jev 没有消息、没有生成、没有流**；硬塞进去就得**把问题藏进 prompt、再从一段假装的生成里把答案抠出来**，**正好丢掉类型化问题和一等公民的概率**。**"抽象不能吞掉你能 debug 的可见性"**——这是模块十一第 69 讲就立过的规矩，在这里得到了一个具体的案例。

**把 2.3–2.9 和这段合起来，一句话收束**：

> **Jev 的价值不在"更便宜的大模型"，而在"把判断从生成里拆出来"这件事终于有了一个直接的接口。** 用 M10 的尺子量下来，它动的每一刀都落在同一处：**softmax 之后不再采样**（2.4）——由此省掉解码循环（2.3）、由此拿走那个被丢弃的分布（2.5）、由此让"概率报得准"成为一个可验证的训练目标（2.6）。而它的边界同样清晰：**不解释、不写 schema、只吃文本、别名叫不准、中文要自己测、数字要自己测。**

## 三、避坑清单

- [ ] **别把 Jev 当"更便宜的大模型"用**——它不做生成、不做推理链、不解释。判据是那句：**答案空间能不能事先写死**；写不死，就是选错工具。
- [ ] **别只看"快多少倍"，要看"省的是哪一段计算"**——省掉解码循环是结构性优势；如果把它的输出再喂给一个大模型去解释、去推理，你等于把省下的解码开销又买了回来。
- [ ] **别拿 Noul 当"程度"用**——`noul = 0.5` 是"是/否各半"，**不是"中等"**（2.4 节：它是分布平坦，不是程度居中）。要程度就用 Score，并把每一档的含义写成**可观察的环境事实**（"4 = 数据外泄尝试"），而不是主观形容词。
- [ ] **别只用 `confidence` 做决策**——它只读最大概率，**看不见"第二名差一点就翻盘"**（2.5 节：`[0.6, 0.2, 0.2]` 与 `[0.6, 0.4, 0.0]` 的 `confidence` 完全一样）。完整分布官方给了，**该自己算 margin 或熵的地方要自己算**。
- [ ] **别问复合问题**——"评估这次交互并决定是否退款"必须拆成三个原子问题，**在代码里按权重合成**。权重是你的、显式的、可回归的。
- [ ] **别把它的概率当"这次一定对"**——官方明说**校准是跨预测群体的度量，不保证单个答案正确**。要自己定义确定性度量、自己画置信度-准确率曲线。
- [ ] **别把阈值钉在别名上**——`jev-latest` 会随新版本漂移，**答案会在你零改动的情况下变化**；要调阈值就钉 `jev-1.13.0` 这样的版本号。**这条和上一条是一对**：阈值建立在"校准稳定"上，而别名漂移会从背后把它换掉。
- [ ] **别在中文负载上直接上线**——官方明说英文最好、**CJK"能处理但不如英文好"，并建议先自测、特别关注 confidence**。机制上这是"分词更碎 + 校准最怕分布外"的双重夹击（2.7 节）。先用你自己的评审文本跑一批、看置信度分布，再决定它能不能进链路。
- [ ] **别让它"自己决定自己的事"**——判断归判断、动作归代码。**工具执行前的风险判定、权限放行、不可逆操作**这三件事，判断可以交给它，**决定必须留在代码或人手里**。
- [ ] **别把厂商数字当结论**——"193 倍 / 444 倍"是厂商口径；独立复测里它是"略逊于对手的准确率 + 10~20 倍的价格优势"。**买的是形态，不是智力。**
- [ ] **别忽略"谁给的判据"这件事**——把 6 条硬编码短语的余弦匹配换成 Jev，收益不只是"更鲁棒"，更是**判据句进了版本控制、可以 code review**；但代价是**判据的模糊性从 0 变成了一点点**，边界那一层确定性规则**不能撤**。

## 四、动手任务

> **目标**：不动生产链路，只做两件你现在就能做完的事——**在自己系统里找出"本该是选择题"的地方**，并**亲手把那笔解码账算一遍**。

**步骤 1：做一张"生成 / 判断"切分表**

把 `code-review-agent` 的一次完整审查流程摊开，逐环节标注它属于哪种活：

| 环节 | 现在谁干 | 属于 | 该不该交给决策模型 |
|---|---|---|---|
| 代码摘要 / 建议生成 | 生成模型 | 生成 | 否 |
| 这条代码是不是 SQL 注入 | 规则 + 生成模型？ | **判断** | 是 |
| 这段自定义 Agent 描述是否指令劫持 | `SemanticInjectionDetector`（余弦 0.85） | **判断** | 是，见插点③ |
| 这次工具调用危不危险 | ？ | **判断** | 是，见插点② |
| 这次请求该用哪个模型档 | 无（只有降级链） | **判断** | 是，见插点① |
| 多个 Agent 结论冲突听谁的 | `ArbitrationPolicy` 固定权重 | **判断 + 策略** | 判断可交，**策略留在代码** |

**要求：凡标"判断"的行，必须写出这个判断的完整选项空间**（noul 还是 choice 还是 score、选项/档位清单）。**写不出选项空间的，说明这个判断还不够原子，继续拆。**

**步骤 2：亲手算一遍"解码账"，再算一遍"你的账"**

用第 65 讲的公式，算清楚你当前最贵的那次调用到底贵在哪：

1. 取你正在用的主力模型，查出**层数 / 头数 / 头维度 / 精度**，按 `2 × L × h × d_head × bytes × n` 算出**每 token 的 KV cache**与**你典型上下文下的总缓存**；
2. 问：**这次调用把这份缓存重读了多少遍？**（用输出 token 数估）
3. 然后回答一句：**这次调用里，有多少输出 token 是你真正要的？**——如果你要的只是一个分类结果或一个分数，那 2.3 节那笔账就是**你为"不需要的 token"付的钱**。

**步骤 3：给四个插点各写一次请求草稿**

按 2.9 节四个插点，各写一段不超过 20 行的请求草稿（用 2.1 节的接口形状）。**每一步都必须回答两个问题**：① 这个判断的 `instructions` 里，判据句是什么（一句话，能 code review）；② 拿到答案之后，**代码**要根据哪个阈值做什么动作。

**步骤 4：为每个阈值写"度量 + 回退"**

步骤 3 每个插点，写一张表：`动作 | 用哪个度量（confidence / margin / 熵）| 阈值 | 越界动作`。**高风险动作的阈值必须显著高于只读动作**（官方示例的形态是：0.5 以下一律转人工，只读动作中置信放行，不可逆动作要求 0.9 以上）。同时写**回退策略**：Jev 不可用时这个插点退回到什么——你现在 `SemanticInjectionDetector` 的做法是"降级为放行"，**把你系统里每一个这样的"静默放行"都找出来，明确它是不是可接受**。

**步骤 5：写"不采用"的理由**

至少写出一条**你决定不用 Jev** 的判断，并给出理由（例如：需要理由说明、选项空间无法枚举、中文负载信心不足、不可逆操作必须人工）。**这一步的产出和步骤 1–4 同样重要**——它证明你是在做架构判断，不是在追新产品。

## 本讲小结

1. **Jev 是决策模型，不是小号 LLM**：只收 `State + 类型化问题`，只回类型化答案与校准概率，**不生成任何文本**；System One 的命名来自卡尼曼的系统 1。
2. **它砍掉的是解码循环（2.3）**：第 62 讲说自回归生成 N 个 token 要跑 N 次前向，第 65 讲说每次 decode 都要把 KV 缓存重读一遍——**一次 150 token 的输出就是 150 次前向**。Jev **没有输出序列**，所以成本与输出长度无关，所以"**输出免费**"是机制事实的定价翻译，不是营销。
3. **它拿回的是那个被丢掉的分布（2.4）**：第 62 讲把生成拆成 logits → softmax → 温度 → 采样；**生成模型在第 4 层采样走一个 token、把分布丢掉，Jev 停在第 2 层之后直接把分布交给你**。"生成 vs 判断"最锋利的那一刀，切在 softmax 之后。
4. **三个原语是同一个分布的三种读法（2.4 / 2.5）**：Choice 读最大项、Score 读重心、Noul 读单侧总概率——所以 `noul = 0.5` 是"分布平坦"，**不是"中等"**。
5. **`confidence` 是"分布有多尖"的读数，但它只读最大那一项（2.5）**：`(3p_max − 1)/2` 反解就是 `p_max`；`[0.6, 0.2, 0.2]` 和 `[0.6, 0.4, 0.0]` 读数相同、**风险完全不同**。官方把完整分布给了你，就是让你在它不够用的地方自己定义度量。
6. **训练侧它对标的是"可验证奖励"（2.6）**：第 68 讲说 RLVR 只覆盖"有裁判的域"，而**校准恰好有裁判**（事后知道真值就能算）；相比 RLHF 的"为讨好而编造"，**一个只报概率的模型几乎没有讨好的空间**。
7. **中文弱是分词层与校准层的双重夹击（2.7）**：第 64 讲的中文切分更碎（1.5–2× token 数），而**校准最怕分布外**——所以官方那句"特别关注 confidence"是技术提醒，不是客套。
8. **接回你的系统有四个真实插点（2.9）**：模型档位路由（现在只有降级链、没有降档链）、工具风险前置闸门、注入语义复核、结论可信度分——**第四个正是第 19 讲"置信度校准"缺的在线那一半**。
9. **边界同样清楚**：不解释、不写 schema、只吃文本、CJK 需自测、别名叫不准、数字要自己测。**判断归 Jev，动作归代码，不可逆的交给人。**

**模块十一至此五讲**：总纲给了尺子（六机制四问），LangChain / LangGraph / DeepAgents 各照出一种编排取向，这一讲补上**垂直轴**——**一次 Agent 运行里，哪些步骤是生成、哪些是判断、哪些必须交回确定性代码**。而这一讲我们多做了半件事：**用 M10 的底层尺子把这条垂直轴又量了一遍**——量到最后你会发现，所谓"决策层"不是什么新物种，它就是**在同一条前向链上，选择了在 softmax 之后停手**。横向比框架、纵向切职责、**再往下钻一层看机制**，你手上这张图的用法就完整了：**读任何 Agent 系统，先问它把判断放在了哪一层。**
