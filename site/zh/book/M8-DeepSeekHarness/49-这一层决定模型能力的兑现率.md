# 第 49 讲 · 这一层决定模型能力的兑现率

> 🎯 导读问题：**"同一个模型、同一份提示词，换一个 harness，表现为什么差一个档？"** ——能答出"模型给的是**能力上限**，harness 决定这份能力被**兑现多少**；所以'模型不行'是最省事、也最没信息量的归因"——这一句就把你和"把一切归因于模型"的人分开了。**本讲要建立的判据是：换 harness 就是换兑现率，而兑现率是**可设计**的——`Profile` 定组装、`Bundle` 定可被 patch 的边界、插件树定最终装配。**

> **模块八 · 进入方式**：前七讲你把「模型调用 / 上下文压缩 / 工具 / 权限 / 记忆 / 技能」六大机制**在自家 Java 系统里读了一遍**（43–48 讲）。这一模块换一个坐标：一个**真实开源 harness 的内部实现**——**DeepSeek Harness**（`dsh`）。它不教你"怎么调 API"，而是回答一个更值钱的问题：**当"六大机制"被做成一个可组合系统时，它们各自被放在了哪一层、用什么原语表达、替换一处会不会牵动全身。**
>
> **本模块面向算法 / 模型研究员，读法有三处不同（请先接受这三条）**：
> ① **代码是 TypeScript 与 Cordis 插件，不是 Java。** 引用的锚点是**真实文件路径与接口名**，不做逐行 Java 对照——你不必会写 TS，只需要能读"谁声明、谁实现、谁消费"。
> ② **重心在"为什么这样分层"**（可组合、可替换、可回放），不在"怎么调 API"。每一讲的判据句都是**架构判据**，不是用法。

## 一、痛点

你在模型侧做过这样的事：换一个 checkpoint、调一次 temperature、加两轮 SFT。然后你发现——**同一份权重，接进不同的 harness，表现能差出一个档**。同一个模型，在 A 里能稳定完成 12 步的工具调用，在 B 里第 3 步就开始丢掉前面的约束。

这时最省事的句式是"**模型不行**"。它的问题是：**它无法被证伪，也无法被改进。** 你说不出要动模型的哪一部分才能让第 3 步不丢约束——因为丢约束的那段逻辑，很可能根本不在模型里。

这里有一个被普遍低估的分工：

> **模型提供的是"给定上文、输出分布"这一件事的能力上限；而"上文到底是什么"、"工具能不能调"、"调错了谁拦着"、"这一步该不该继续"——全部由 harness 决定。**

所以"换 harness 差一个档"不是玄学，它有一个可测量的解释：**模型的上限没变，兑现率变了。**

如果你只做模型侧的研究，这条结论对你尤其重要：**你的实验里有一个不受控的变量，叫 harness。** 论文里写"我们的方法在 agent 任务上提升 8%"时，如果没交代 harness，那 8% 里有多少来自模型、多少来自"你把工具描述写清楚了"，是说不清的。反过来，**harness 也是你的杠杆**：不改一个权重，只把"模型能看见什么"表达对，就能把那 8% 拿回来一大半。

这一讲要回答的是最上层的一个问题：**一个把六大机制都做成可替换的系统，是怎么被"组装"出来的？**

## 二、原理

### 2.1 `dsh` 是什么：一个把"一切皆插件"当架构原语的 harness

先看它自己的自我定位（`README.zh.md:5-7`）：

> DeepSeek Harness（`dsh`）是由 DeepSeek AI 开发的开源 agent harness（智能体框架）。它构建于**一切皆插件**的架构之上，由 [Cordis](https://github.com/cordiverse/cordis) 驱动，其设计参见论文 [_A Programming Paradigm for Spatiotemporal Composability_](https://arxiv.org/abs/2608.25512)。

三个可直接核对的事实：

| 事实 | 出处 |
|---|---|
| 许可证 **MIT** | `README.zh.md:94-96` |
| 状态是**开发者预览**，官方明说"未来将出现破坏兼容性的变更" | `README.zh.md:11-13` |
| 运行只要一条命令：`npx @deepseek-ai/dsh web`，默认在 `http://127.0.0.1:3080` 起 Web UI | `README.zh.md:21-29` |

最后一条值得注意：**它把"跑起来"压成了一条 npm 命令**。这不是好意，这是架构结论——**"一切皆插件"如果成立，那么换一个交付形态就不该需要换一个仓库**（第 54 讲会把这一点推到"一套内核五种形态"）。

**给研究员的第一个抓手**：拿到一个 harness，先跑 `--dump-config`。`dsh` 的这一条是：

```sh
dsh --profile web --dump-config
```

`docs/architecture.zh.md:33-39` 对它的说明是一句判据：

> 它打印出的任何条目，都可以由你自己的 patch 替换。

**"打印出来的都是可替换的"**——这一句话把"可组合"从一个形容词变成了一个**可验证的断言**。

### 2.2 三层：Profile → Bundle → 插件树

`dsh` 的运行体是一棵**插件树**，由启动时按序叠加的各层组合而成（`docs/architecture.zh.md:15-17`）。三层各自的职责，原文给得很清楚：

| 层 | 是什么（原文） | 出处 |
|---|---|---|
| **Profile** | "存放在 Harness home 中的具名组装。它列出自己叠放的组合包，存放自己安装的树外插件，并保存用户自己的 `cordis.patch.yml`" | `docs/architecture.zh.md:19` |
| **Bundle（组合包）** | "是 Cordis 配置项及其挂载代码的分发格式，因此它插入的内容始终可被其上各层 patch" | `docs/architecture.zh.md:21` |
| **插件树** | 各层叠加后的产物；每条 patch"按 id 定位某个条目并替换其整个 config，或插入新条目" | `docs/architecture.zh.md:27` |

随发行版交付的 profile 模板有**五个**：`web`、`headless`、`sdk`、`sdk-minimal`、`acp`（`docs/architecture.zh.md:19`）。

**层与层的声明方式**是同一条约定（`docs/architecture.zh.md:23`）：

> 两者都在各自的 `package.json` 中通过 `dsh` 字段声明自己：`dsh.profile` 列出一个 profile 的组合包，`dsh.bundle` 指向一个组合包的 patch 文件。

**★ 应用顺序是本讲最该记住的一条**（`docs/architecture.zh.md:27`）：

> 各层按此顺序应用在空条目列表之上：先按 profile 列出的顺序应用每个组合包，然后是 profile 的 `cordis.patch.yml`，然后是 home 级的那份，最后是任意 `--patch` overlay。

翻译成工程语言，这是一条**"覆盖顺序由外到内、由粗到细"**的规则：

```
空条目列表
  ← 各 bundle（按 profile 列出的顺序）
  ← profile 的 patch         （这一份组装自己的偏好）
  ← home 的 patch            （这一台机器的偏好）
  ← --patch overlay          （这一次运行的偏好）
```

**为什么这个顺序重要**：它让"改一次行为"有四级粒度可选，而且**从最外层的临时覆盖到最内层的发行版默认值，越靠后越强**。你调一个参数做实验，用 `--patch`；这台机器上永远要这么配，用 home patch；这个组装形态一直这么配，用 profile patch；改所有人的默认，才去改 bundle。**四级粒度把"实验"和"发布"分开了**——这正是模型侧做实验时最缺的东西：**同一条实验命令可以完整复现，而不必"记得当时改了哪个文件"。**

### 2.3 `dsh-base`：被共享的第一层，和那个刻意的例外

五个 profile 并不是五套东西。它们共享同一层：**`dsh-base`**（`docs/architecture.zh.md:25`）。

> `dsh-base` 是 `web`、`headless`、`sdk` 与 `acp` profile 的共享第一层：模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测。

注意这一层的内容：**模型接入、工具、持久化、沙箱与审批**——恰好就是你在 43–48 讲逐讲读过的那几个机制。`dsh` 把它们打包成"共享第一层"，于是四个形态**共享同一套模型连接、同一套工具集、同一套持久会话历史、同一套安全默认值**（`packages/bundle/base/README.zh.md:12` 原文）。

**但有一个刻意的例外**（`docs/architecture.zh.md:25` 末句）：

> `dsh-sdk-minimal` 是刻意保留的例外：一个组合包拥有完整的显式 SDK 配置树，不应用 `dsh-base`。

它的自我说明（`packages/bundle/sdk-minimal/README.zh.md:12`）说得更绝——它"**刻意排除** `dsh-base`、Web、settings、托管凭据、遥测、压缩（compaction）、文件系统工具、workspace 指令、skill（技能）、jobs 与 subagent"。

**★ 判据句（本讲的第一个架构判据）**：

> **"共享第一层"是默认，但默认不是铁律。** 当某个交付形态的**约束与共享层相反**时（SDK 客户端要的是"小、显式、可控"），正确做法是**为它单独定义一棵树**，而不是往共享层里塞开关，也不是 fork 出一个仓库。**"一个例外"和"一堆开关"的区别是：例外自己就是完整的、可 `--dump-config` 打印出来的树；开关藏起来的分支不是。**

### 2.5 前沿深挖：从"配置即架构"到"可组合性的代价"

这一讲要留下一条**研究员最容易问错方向**的认知。

先看 `dsh` 这棵树**能做什么**：`docs/architecture.zh.md:11-13` 原文——

> 产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop（智能体循环）本身，因此每个都可以从配置替换。不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。

请把这句话里的三个"包括"读慢一点：**模型适配器**（换模型）、**工具注册表**（换工具集）、**`agent loop` 本身**（换那个 while 循环）。第三个是最激进的——**很多系统里 agent loop 是整个架构的"地心"，而这里它是可替换的。**

**但"可组合"不是白拿的。** 代价藏在同两句话的后半段里：**"各项注册都是副作用，会在其插件卸载时撤销"**。

这条约束有两个方向都会咬人：

**方向一：注册不可回收 ⇒ 卸载会留残留。** 如果你绕过框架的注册 API 自己管资源（直接 `addEventListener`、自己开一个全局连接），那么插件卸载时**框架不会替你撤销**——残留就是"看起来卸载了、其实还在"。`dsh` 的教程把这条写成硬规则（`docs/cordis-tutorial/02-lifecycle-and-effects.zh.md:5`）：

> 通过 Cordis API 建立的注册属于 effect，会在所属插件卸载时撤销；**在这些 API 之外管理的资源必须包装在 `ctx.effect()` 中。**

**方向二：依赖不存在 ⇒ 静默等待，不报错。** 这条更隐蔽。插件声明它依赖某个服务（`inject`），如果那个服务**没人提供**，它**不会崩、不会警告**，而是**一直 `PENDING`**（`docs/cordis-tutorial/06-composition-and-hmr.zh.md:42`）：

> 如果插件的 `inject` 指定了无人提供的服务，它就会一直等待，不输出任何内容。这不是错误，因为 PENDING 是合法状态，提供方可能稍后才挂载。

**这是可组合性最典型的失效面：一个"合法状态"和一个"配错了"在观测上长得一模一样。** 而且 `inject` 不是一次性的启动检查——运行期所需服务消失时，依赖它的插件会**整体卸载**；服务恢复后再加载（`docs/cordis-tutorial/03-services.zh.md:76`）。这对"热插拔"是优点，对"我为什么什么都没输出"是灾难。

**★ 判据句（本讲的第二个架构判据，也是模块八的总纲）**：

> **可组合性把"装配期错误"翻译成了"运行期静默状态"。** 装错一个插件的后果，不再是"启动失败"，而是"它不工作，且不告诉你"。因此一个可组合系统**必须额外造出两样东西**：① **能打印出"实际装配了什么"的出口**（`--dump-config` 就是它）；② **把"没输出"和"没配"分开的观测**（否则你永远在 debug 一个根本没错的插件）。
>
> **这两样东西不是可选的附属品，它们是"可组合"这个选择的必要成本。** 看到"某框架什么都能换"，先问它这两件事做没做——**做没做，决定了你能不能在 40 分钟内定位一次装配错误，还是耗掉两天。**

## 三、避坑清单

- [ ] **别把"表现差"自动归因到模型。** 先问：上文里模型实际看到了什么、工具 schema 是谁写的、失败是谁拦的——这三件都不在模型里。
- [ ] **做模型侧实验时，把 harness 当受控变量写进方法。** 没交代 harness 的"提升 X%"，无法排除"其实是把工具描述写清楚了"。
- [ ] **拿到一个可组合系统，第一件事是让它把装配树打印出来**（`dsh --profile <name> --dump-config`）。打印不出来 ⇒ 它的"可组合"不可验证。
- [ ] **改配置按四级粒度选**：一次实验用 `--patch`，一台机器用 home patch，一种形态用 profile patch，所有人默认才改 bundle。别一上来就改 bundle。
- [ ] **别把"要一个小形态"做成"往共享层加开关"。** 与共享层约束相反时，单独定义一棵显式的树（`sdk-minimal` 的做法），而不是加第 N 个布尔开关。
- [ ] **自己管的资源必须包成 effect。** 绕过注册 API 的副作用，卸载时不会有人替你撤销——这就是"假卸载"。
- [ ] **遇到"插件没输出"，先怀疑 `inject` 依赖没人提供**（合法 `PENDING`），而不是先怀疑逻辑写错。
- [ ] **不要用"这一版的事实"当永久契约。** `dsh` 是开发者预览，官方预告破坏性变更；引用路径要带版本（本模块统一用 commit `477b4f4`）。

## 四、动手任务

> **目标**：亲手确认"兑现率可设计"这句话，不是修辞。

**步骤 1：跑起来，然后打印装配树**

先跑起来：

```sh
npx @deepseek-ai/dsh web        # 默认 http://127.0.0.1:3080
```

再打印这棵树：

```sh
npx @deepseek-ai/dsh --profile web --dump-config
```

**任务**：数一数树里有多少条目，并从中**找到"模型适配器"和"agent loop"这两个条目**。找到它们，本讲 2.5 节那句"连 agent loop 本身都是插件"就从传言变成了你亲眼看到的一行。

**步骤 2：找一次"替换"的最短路径**

在打印出的条目里挑一个（比如模型适配器），**不要改 bundle**，用 `--patch` 覆盖它一次。**任务**：验证"四级粒度"里最外层那级真的能生效，且**不需要重新构建**。

**步骤 3：亲手制造一次"静默 PENDING"**

按 `docs/cordis-tutorial/01-first-plugin.zh.md:12-19` 抄一个最小插件（整段只有 7 行）：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

先让它在**没人提供依赖**的情况下声明一个 `inject`，观察它是不是"一直不输出、也不报错"。**任务**：写出你用来区分"静默等待"和"真的挂了"的那条观测手段——**如果你写不出来，说明你还没理解可组合性的代价在哪。**

**步骤 4：把这张坐标搬回你自己的系统**

## 本讲小结

1. **模型给上限，harness 给兑现率。** "模型不行"是不能证伪、也不能改进的归因；换 harness 差一个档，差的是兑现率。
2. **`dsh` 用三层组织兑现率**：`Profile`（具名组装）→ `Bundle`（可被上层 patch 的分发格式）→ 插件树（启动时按序叠加）。
3. **应用顺序由粗到细**：bundle → profile patch → home patch → `--patch`。四级粒度把"实验"与"发布"分开，让一次实验可完整复现。
4. **共享第一层是默认，默认不是铁律。** 与共享层约束相反时，单独定义一棵显式的树（`sdk-minimal`），而不是往共享层堆开关。
5. **"打印出来的都是可替换的"** —— `--dump-config` 把"可组合"从形容词变成可验证的断言。
6. **可组合性的代价是"装配期错误被翻译成运行期静默状态"**：注册不可回收 ⇒ 假卸载；依赖没人提供 ⇒ 合法 `PENDING` 却没输出。所以可组合系统必须自带"打印实际装配"的出口和"区分没输出与没配"的观测。
7. **对研究员最实际的一条**：harness 是你实验里的受控变量，也是你不改权重就能拿回性能的杠杆。
