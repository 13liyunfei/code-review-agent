# 第 55 讲 · 生态与最佳实践：怎么读一个 harness

> 🎯 导读问题：**"给你一个从没见过的 agent 系统，你从哪三个问题开始读？"** ——能答出"**真相源在哪（谁能被重放）、替换点在哪（谁是 seam）、拦截点在哪（事件域与中间件）**"——这三问就把"读源码"从"从 main 开始翻"变成了一次有方向的勘查。**本讲要建立的判据是：一个 harness 值不值得长期投入，看它有没有把"文档不会撒谎"也做成门禁——因为文档与代码的漂移，是比任何一个 bug 都更贵的负债。**

> **模块八 · 收束之讲**：前六讲读完了 `dsh` 的机制。这一讲换一层：**它怎么保证这些机制不腐烂**——决策记录、事故复盘、文档级真源、双语门禁。**对研究员尤其重要**：你未来大概率要在一个 harness 里做长周期实验，那么"这个仓库的文档值不值得信、它的决策史查不查得到"直接决定你的返工量。

> **本讲也是全模块的方法收束**：把六讲的内容压成三个问题。**你能用它们去读 `dsh`，就能用它们去读 codex、读任何你遇到的 agent 系统。**

## 一、痛点

假设你下周要接手一个陌生的 agent 系统，或者要基于它做三个月的实验。你会怎么开始？

最常见的两种开始方式，都很贵：

**方式一：从 `main()` 往下读。** 你会花两天搞清楚启动流程，然后用两周发现"真正的核心在另一个模块里"，最后在某个你从没听过的事件回调里找到关键逻辑。**这条路的成本随代码量线性上升，收益却完全靠运气。**

**方式二：读文档。** 这条路有一个致命前提——**文档是对的。** 而真实经验是：**越是架构复杂、迭代快的系统，文档越不可信**；你按文档改，跑不起来，然后你既不知道是自己理解错了，也不知道是文档过期了。

> **第二种失败比第一种更贵。** 因为第一种你至少知道"我在探索"，第二种你**相信了一个错误的前提**——等你发现时，已经按它做了决定。

所以本讲要回答两件事：**① 有没有一套稳定的问题，能快速定位一个系统的关键结构？② 怎么判断这个仓库的文档值不值得信？**

第一件事前面六讲已经给了答案，这一讲把它命名并收束；第二件事是 `dsh` 提供的一个**很罕见的样本**——它把"文档不会撒谎"做成了**会失败的检查**。

## 二、原理

### 2.1 三个抓手：真相源 / 替换点 / 拦截点

前面六讲其实是沿着同一条线走的。把它抽成三个问题：

| 抓手 | 问题 | 在 `dsh` 里的答案 | 对应讲 |
|---|---|---|---|
| **① 真相源** | **谁的记录能让这次运行被重放？** | 会话日志（`ctx.sessions`）：仅追加、模型历史由它投影；不变式"模型可见即已记录" | 51 |
| **② 替换点** | **换掉哪一处能改变一片行为？** | capability seam：三角色齐全的可替换能力（33 个）；`--dump-config` 打印的都是可替换的 | 53 |
| **③ 拦截点** | **在哪能插进"观察/改写/否决"？** | 三个事件域 + waterfall（`agent/pre-step`、`agent/request`、`llm/stream`、`tools/*`） | 52 |

**★ 判据句（本讲第一个判据，也是本模块的"操作手册"）**：

> **这三个问题的顺序不能换。** 先问真相源——**没有可重放的事实，你后续所有的调试都只能靠猜**；再问替换点——**决定你"改动的影响半径"**；最后问拦截点——**决定你"最小侵入的介入方式"**。
>
> **反过来用也对**：如果一个系统**答不出**第一个问题（"日志在哪儿、能不能重放"），那它后面两个问题答得再好也不值得深入——**因为你无法复现，就永远无法确认自己改对了。**
>
> **对照第 49 讲的三个"抓手"**：第 49 讲给的是"**读一个 harness 的入口**"（跑起来 + 打印装配树），这一讲给的三个是"**读它的骨架**"。两组合起来是一套完整的勘查流程：**先让它自陈（dump-config），再问它三个问题。**

### 2.2 工程纪律一：决策记录不是文档，是"带生命周期的资产"

`dsh` 用一套叫 **Agent Note** 的机制记录决策（`.agents/notes/`）。它的设计有几个点很值得学。

**① 生命周期是目录，且是封闭集合**（`.agents/notes/README.zh.md:11-14`）：`proposed/`（实施前评审的提案）、`implemented/`（决策已交付，与实际交付保持同步）、`rejected/`（被否决）。另有 `archived/` ——**只在 `implemented` 之后的冻结归档树**。

**② 分类（class）是封闭集合，由脚本定义、由门禁强制**（`:25` 原文）：

> 每份 Agent Note 属于 `scripts/agent-note-tree.ts` 中**封闭集合**里的一个路径编码类别；**分类门禁拒绝其他文件夹**。

六个类别是（`:29-34`）：`feature`、`bug-fix`、`simplification`、`architecture`、`process`、`testing`。其中 `architecture` 与 `process` 的界线是"**前者关于交付源码，后者关于围绕源码的工具与工作流**"，且 `refactor` **被有意排除**（`:36`）。

**③ 有一条"不许改写历史"的硬规则**（`:52`）：

> Agent Note **永不被编辑为不同的决策**（用新记录取代并互相链接，除非完全合并）。

**④ 状态行只有三种合法形式**，且**必须与所在生命周期文件夹一致**（`:74-80`）：`Status: proposed` / `Status: implemented` / `Status: rejected — <why, in one line>`。而 **`## Alternatives considered` 是每份记录必需的一节**（`:117`）。

**⑤ 归档规则区分了"删"和"冻"**（`:40`、`:42`）：仅描述小型 UI 调整或纯机械变更的 `implemented` 记录**直接删除**；其他已实施记录**仅在"完整落地、依据不太可能再指导未来工作、但仍具历史决策价值"时**归档；**绝不归档 `proposed`**（应转 `rejected`）。归档后**永久冻结**，禁止编辑 / 翻译 / 移动 / 删除。

**★ 判据句（本讲第二个判据）**：

> **"决策记录"这件事，真正的分水岭是"它可不可以被改写"。** 允许改写的记录，最终一定会变成"事后美化的宣传稿"；**而"永不被编辑为不同的决策，只能被取代"这条规则，保证了历史是可追溯的。**
>
> **第二重要的是"`Alternatives considered` 必需"。** 只写"我们这么做了"的决策记录，价值接近于零；**写清"还有哪几条路、为什么没走"的，才是三个月后真正能省时间的那份。** 因为三个月后你的问题几乎从来不是"当初怎么做的"，而是"**当初为什么没选那条更省事的路**"。

**规模感**（我自己用 `git ls-tree -r HEAD --name-only` 数的树级统计，commit `477b4f4`）：`.agents/notes/` 下共 **3,617 个文件**，其中 `.zh.md` **1,204** 篇。

按 **class** 分组（文件数）：

| class | 文件数 |
|---|---|
| `feature` | 1,062 |
| `architecture` | 1,017 |
| `bug-fix` | 570 |
| `process` | 459 |
| `simplification` | 360 |
| `testing` | 141 |

按 **lifecycle** 分组（文件数）：`archived` 1,922、`implemented` 1,529、`proposed` 120、`rejected` 42。

**这张分布表本身就有信息量**：`archived` 最多（1,922 > `implemented` 1,529），说明这个仓库**真的在按规则归档**（而不是只进不出、堆成垃圾场）；`proposed` 只有 120，说明"提案"这一档被**克制地使用**（不是每条想法都开一份）。

**⑥ 还有一处刻意的"不做"**：**没有集中式 `INDEX.md`**。这不是遗漏——`implemented/process/2026-07-19-remove-generated-agent-note-index.zh.md` 这份记录的名字就写明了"**移除生成的 Agent Note 索引**"。⇒ **他们做过一个索引，然后把它删了。**

**★ 判据句（本讲第三个判据）**：

> **"目录结构 + 脚本门禁"是比"手工维护的索引"更抗腐蚀的形态。** 索引的问题和所有"另存一份"一样（第 51 讲的同一条病）：**它会过期，而它过期时没人知道。** 换成"**路径本身编码语义 + 门禁拒绝非法路径**"，你就得到了一个**不会过期、且无法悄悄违反**的组织方式。
>
> **注意这里的取舍**：删掉索引**牺牲了"一眼看全"的快慢**，换来"**永远是对的**"。对一个三年后还要维护的仓库，这个交换是划算的。

### 2.3 工程纪律二：事故复盘的**收录判据**

`dsh` 有 4 篇事故复盘（`docs/postmortem/`），前面两讲各用过一篇。但更值得学的是**它的收录标准**（`docs/postmortem/README.zh.md:9` 原文）：

> 当一个 bug 满足以下条件时，请撰写事故复盘：**隐蔽**（机制不显而易见，即使是细心的工程师也得费力重新推导）、**系统性**（逃逸的原因是测试、工具、约定的缺口，而非一次性的笔误）、**重新发现的代价高**（它消耗了真实的调试时间，且下次还会如此）。

另外两条边界（`:7`、`:11`）：**事故复盘不是 Agent Note**（两者是两个体系，不混用）；**每篇以一段执行摘要开头**。

**★ 判据句（本讲第四个判据）**：

> **"什么值得写下来"必须比"什么发生过"更窄。** 三条判据里最关键的是第二条——**系统性：逃逸原因是"测试 / 工具 / 约定的缺口"，而不是一次笔误。**
>
> 这条判据的威力在于：**它把"复盘"从"检讨谁写错了"变成了"补哪个缺口"**。一次笔误不需要复盘（写的人知道错了）；**而"我们的测试方式根本覆盖不到这个路径"需要复盘，因为它会在下一个人身上重演。**
>
> **这就是为什么第 50、51 讲那两篇事故（`0001` 默认导出吃掉 `inject`、`0002` 快照把 bug 接受成预期）能写进这本书**：它们**不是因为"有人手滑了"，而是因为"测试方式与交付方式不一致"**——而那是**结构问题**，任何人都会踩。

### 2.4 工程纪律三：文档级真源——让"抄代码"这件事不会漂移

这是 `dsh` 里**最漂亮的一条工程机制**，也是本讲最想推荐你抄的一样东西。

问题很朴素：**子系统文档里需要粘贴类型定义**（否则读者不知道接口长什么样）。而**手抄的类型定义一定会和源码漂移**——这是第 51 讲那条"存两份必然漂移"的又一实例。

`dsh` 的解法（`docs/development.zh.md:187-195` 要点）：

1. 子系统页把"**与源码等价的声明及原始 JSDoc**"一并粘贴，**必须**围栏为 ` ```ts type-equiv `；
2. 每处这样的代码块，**必须在 `scripts/type-equiv.manifest.json` 登记**它镜像的源文件与符号，例如（`:192`）：
   `{ "doc": "docs/subsystems/session.md", "symbol": "SessionEvent", "source": "packages/core/session/src/types.ts" }`
3. `pnpm run verify-type-equiv`（doc-sync 的一环）**经 TypeScript 解析器提取该符号的声明及 JSDoc**，并**断言代码块同时匹配这两者**；
4. 门禁按"文档 / 符号 / 投影"强制主块与 manifest 条目 **1:1**；`doc-typecheck` 对可编译围栏应用同一派生规则，同时**跳过**这两种源码等价围栏的编译。

**★ 判据句（本讲第五个判据——这一条我认为最值得抄）**：

> **"文档里的代码示例"必须变成"可校验的镜像"，否则它一定会过期。** 三要素缺一不可：**① 一个标记（`ts type-equiv`）让门禁知道该管它；② 一份 manifest 说明它镜的是什么；③ 一个用真解析器取源的检查**（不是字符串比对——比对字符串是另一回事，那会禁止格式化差异）。
>
> 注意第 ③ 条的技术含量：**它用 TypeScript 解析器提取声明与 JSDoc，再断言相等。** 这意味着**文档里的东西必须在语法与注释两个层面都与源码一致**——**JSDoc 也被管住了，而 JSDoc 恰恰是"最容易被抄错、又最影响理解"的部分。**
>
> **如果只抄一条到你的项目里，抄这条。** 它的成本极低（写代码块时加个围栏 + 一行 manifest），收益是**整本技术文档永远不会撒谎**。

### 2.5 工程纪律四：双语与生成物——把"配套"也纳入门禁

`dsh` 的文档是**英中双语**维护的，而它的做法同样把问题变成了机械检查。

**i18n 的形态**（`docs/i18n/README.zh.md:5`、`:12`）：**一对文档 = 三个同目录文件**（`foo.md`、`foo.zh.md`、`foo.i18n.yaml`）；**不用语言目录、不用独立翻译仓库**。

**一致性记录**（`:13`、`:24`）：YAML 按标题分节保存两侧 hash；**只有两分支改动同一分节计入 hash 的内容时，记录才冲突**；`pnpm run verify-translation-pairing --write <pair>` 重新记录，**那份 YAML 的 diff 就是"确认一致"这个动作**。门禁 `verify-translation-pairing` 做三条检查：完整配对、产物完整一致、`excluded` 文件不得有 `.zh.md` 与 `.i18n.yaml`（`:32-36`）。

**而这里有一条尤其诚实的话**（`:46`）：门禁通过 **≠** 翻译本身正确可靠。⇒ **它明确承认机械检查的边界。**

**翻译规则里也有几条可核对的硬要求**（`docs/i18n/translation-rules.zh.md:24-33`、`:37`、`:45-52`）：**围栏代码块逐字节一致（包括注释）**、行内代码原样保留、术语以 `terminology.md` 为双向真源、中文排版（中西文间半角空格、全角标点、禁全角数字、第二人称"你"）。

**★ 判据句（本讲第六个判据）**：

> **翻译质量不可机械判定，但"翻译是否配套、代码块是否被改动"可以。** 把可判定的部分变成门禁，把不可判定的部分**明确标注为"不可判定"**——这是工程诚实度的直接体现。
>
> **"围栏代码块逐字节一致（包括注释）"这条尤其值得抄**：它防的是翻译者"顺手把代码也翻译了 / 顺手改了注释里的示例值"这类**看起来很尽责、实际上在制造漂移**的行为。

**生成物同理**：`dsh` 有**一整套由脚本生成、只读不写的文档**（`docs/*.zh.md` 文件头都署名了生成脚本）：

| 生成脚本 | 产物 |
|---|---|
| `scripts/gen-config-catalog.ts` | `docs/config-catalog.*` |
| `scripts/gen-persistence-catalog.ts` | `docs/persistence-catalog.*` |
| `scripts/gen-tool-catalog.ts` | `docs/tool-catalog.*` |
| `scripts/gen-module-graph.ts` | `docs/module-graph.*` |
| `scripts/gen-doc-graphs.ts` | `agent-lifecycle` / `capability-seams` / `event-producer-consumer` / `graph-atlas` / `tool-execution-pipeline` |
| `scripts/gen-cordis-catalog.ts` | `docs/cordis-api/*`，并在各子系统页写入 `BEGIN GENERATED cordis-surface` 区块 |
| `scripts/gen-session-format-catalog.ts` | 会话格式目录（推导 codec 顺序、检查相邻迁移是否到达写入器版本） |

**注意这些产物的性质**：**能力图、事件生产消费矩阵、工具目录、配置目录、模块图、会话格式目录**——全是"人写容易漏、机器算不会漏"的东西。**而它们的入口也都从 `cordis` 声明里被发现**（第 53 讲 2.6 节那条"服务从 Cordis 声明中发现"）。

### 2.6 生态、治理与安全：三条必须如实说的事

最后把"生态"这层讲清楚，**包括不太好看的那部分**。

**① 当前不接受外部 PR**（`CONTRIBUTING.zh.md:9` 原文）：

> 很抱歉，我们目前无法接受外部 PR（Pull Request）。

替代的参与方式是（`:11-17`）：**GitHub Discussions** 报告问题、**给你的插件仓库加 `dsh-plugin` 话题**、写博客、回答问题。`README.zh.md:47-51` 另外给了 Docs 站、`dsh-plugin` topic、企微群三条入口。

⇒ **生态的形态是"插件生态"，不是"贡献者生态"。** 这个区分很重要：**你要做的不是"给它提 PR"，而是"在它旁边写插件"**——这恰好是第 50 讲那三个动作（服务 / 事件 / effect）存在的意义。

**② 安全定位必须原样转述**（`SAFETY.zh.md:7`、`:13`）：它是**实验性开发者预览软件，尚未接受安全审计，不得视为安全或可用于生产环境**；而最关键的一句是：

> 沙箱、审批提示与权限控制可以降低风险，但不保证隔离，也不能保证防止损害。即使限制得到正确执行，也无法保护本项目获准访问的资源。

**③ 最后一条容易忽略但很实用的**：`dsh` 把自己的**框架源码 vendor 进来**（`docs/rescope.zh.md:5`：Cordis 框架及其基础库以源码形式 vendored 在 `vendor/` 下，并以 `@deepseek-ai` scope 发布；该页是**名字映射表**，改名由 `scripts/rescope-vendor.ts` 承载）。

**★ 判据句（本讲第七个判据）**：

> **"我们不接受 PR"不是一个缺陷，它是一种生态定位。** 但它的**前提**是你必须提供**插件级的扩展面**（否则外部什么都做不了）——这就是为什么第 50 讲那三个动作**必须**存在。**"封闭核心 + 开放插件"和"开放贡献"是两种生态，评价它们要看是否自洽，而不是哪个更开放。**
>
> **而安全文档那句"不保证隔离，也不能保证防止损害"，是本书反复倡导的同一个态度**：**把能力的边界写清楚，比把能力说得更强更有价值。** 一份说"我们做到 X，做不到 Y"的文档，比一份说"企业级安全"的文档值得信任得多。

### 2.7 收束：这七讲之后，你手上有什么

把七讲压成一张表——**这是本模块的全部结论**：

| 讲 | 你要带走的判据 |
|---|---|
| 49 | 模型给上限，harness 给**兑现率**；可组合性把"装配期错误"翻译成"运行期静默状态"，所以要自带 `--dump-config` 与"没输出 vs 没配"的观测 |
| 50 | 插件只做三个动作，**共同约束是"注册必须可回收"**；`waterfall` 里不调 `next()` = 否决；"测试通过 ≠ 按交付方式工作" |
| 51 | **只存一份，方向是"日志 → 历史"**；"发生过"与"模型看见过"分表；"能重建"是一条**每次运行都跑的等式**；快照会把稳定的 bug 稳定成"预期" |
| 52 | **顺序能改结论 ⇒ waterfall；顺序改不了 ⇒ serial**，更优的形态是"钩子投递事实、数据决定结论"；工具流水线 13 阶段里"策略在前、实现在中、规范化在后" |
| 53 | **seam = 三角色齐全的能力**，验收标准是"换过 provider 且消费方零改动"；**按共同依赖划分 seam**；多 provider 表达力不同时只允许"做到"或"明确拒绝" |
| 54 | **形态差异走配置与 patch，不走 fork**；"禁用"≠"不包含"；"例外形态"要另立**显式**的树；"只有 N 种形态"必须被 CI 守着 |
| 55 | 读一个 harness 用三问；**决策记录不许被改写、必须写清被否决的方案**；**文档里的代码示例要变成可校验的镜像** |

## 三、避坑清单

- [ ] **读陌生系统先问三个问题，且按顺序**：真相源 → 替换点 → 拦截点。第一个答不出来，后面两个不值得深入。
- [ ] **别把"能 dump 出装配树"当可有可无。** 那是判断"可组合"是否真实可验证的唯一入口。
- [ ] **决策记录一旦允许改写，就会变成宣传稿。** 规则应该是"**只可取代，不可改写**"，且**被否决的方案必须留档**。
- [ ] **事故复盘的收录标准要比"发生过"窄**：只收"隐蔽 + 系统性 + 重新发现代价高"的。**笔误不需要复盘，缺口才需要。**
- [ ] **别手工维护索引。** 用"路径编码语义 + 门禁拒绝非法路径"替代；索引必然过期，而它过期时没人知道。
- [ ] **文档里的代码示例一律加可校验标记 + manifest**，用真解析器取源比对（连 JSDoc 一起）。**这是投入产出比最高的一条工程纪律。**
- [ ] **可机械判定的做门禁，不可判定的明确标注"不可判定"**（例如翻译质量）。假装能判，比承认判不了更糟。
- [ ] **双语 / 多语言时，代码围栏必须逐字节一致（含注释）**，防止"顺手把代码也翻译了"。
- [ ] **"能生成的别手写"**：能力图、事件矩阵、工具目录、配置目录、模块图、格式目录——全是机器算更准的东西。
- [ ] **安全边界要如实写"做不到什么"。** "不保证隔离、不保证防止损害"比"企业级安全"更值得信任。
- [ ] **"不接受 PR"要配"插件扩展面"**，否则生态不成立。

## 四、动手任务

> **目标**：用三个抓手读一个**你没读过的** harness，并给你自己的项目补上一条"防撒谎"的门禁。

**步骤 1：用三问读一个陌生系统**

挑一个你**没用过**的 agent 框架（不要挑 `dsh`）。**任务**：只回答三个问题，每个问题写**证据出处**（文件路径或文档位置）：

1. **真相源在哪？** 它的会话/运行记录存哪、能不能重放？
2. **替换点在哪？** 换掉哪个对象能改变一片行为？
3. **拦截点在哪？** 在哪能插进"观察 / 改写 / 否决"？

**验收标准**：每一问都必须给出**可核对的位置**。给不出位置的，写"未找到"——**"未找到"本身就是一条有价值的结论。**

**步骤 2：给你的项目补一条"文档不撒谎"的门禁**

选一样最容易被手抄走样的东西（类型定义 / 配置示例 / API 响应样例 / SQL schema）。**任务**：按 2.4 节的三要素落一遍——**① 加标记 ② 写 manifest ③ 用真解析器（或真校验工具）比对**。**验收标准**：故意改源码不改文档，检查必须失败；改回后检查必须通过。**两向都要试。**

**步骤 3：审一遍你自己的"决策记录"**

用 2.2 节的五条（生命周期 / 封闭分类 / 不可改写 / 状态行三形式 / `Alternatives considered` 必需），给你项目的决策记录打分。**任务**：写出**最缺的那一条**，并在本周补上它的机制（哪怕只是一个模板 + 一条 review 规则）。

**步骤 4：写下你自己的"三个抓手"**

用三问回答你自己的系统，**每一问都给出具体位置或明确写"没有"**。

**任务**：三问里答"没有"的那一问，就是你系统的下一个架构任务。**这一条也正好接上下一讲**——我们要去看另一个真实产品，用它当第三参照物，检验这套问题是不是真的通用。

## 本讲小结

1. **读一个 harness 用三个抓手，顺序不能换**：**真相源**（谁可被重放）→ **替换点**（谁是 seam）→ **拦截点**（事件域与中间件）。第一问答不出来，后两问不值得深入。
2. **Agent Note 的五条纪律**：生命周期是目录（`proposed` / `implemented` / `rejected` / `archived`）、分类是**封闭集合**且由门禁强制（6 类）、**永不被编辑为不同的决策**、状态行只有三种合法形式、**`Alternatives considered` 必需**。
3. **决策记录的分水岭是"可不可以被改写"**；第二重要的是"**写清被否决的方案**"——三个月后你要的几乎总是"当初为什么没走那条路"。
4. **规模实测量级**：`.agents/notes/` 共 3,617 个文件（`.zh.md` 1,204 篇）；class 文件数 feature 1,062 / architecture 1,017 / bug-fix 570 / process 459 / simplification 360 / testing 141；lifecycle 文件数 archived 1,922 / implemented 1,529 / proposed 120 / rejected 42。**`archived` 多于 `implemented` 说明它真的在归档。**
5. **用"路径编码语义 + 门禁"替代"手工索引"**——他们甚至**删掉过一个生成的索引**。索引必然过期，而它过期时没人知道。
6. **事故复盘的收录判据是"隐蔽 + 系统性 + 重新发现代价高"**，核心是第二条：**逃逸原因必须是"测试/工具/约定的缺口"，而不是一次笔误。** 这让复盘从"检讨人"变成"补缺口"。
7. **文档级真源（`ts type-equiv` + manifest + 解析器比对）是投入产出比最高的一条工程纪律**：它让文档里的类型与 JSDoc **永远不会和源码漂移**。
8. **可判定的做门禁，不可判定的明确标注**（翻译质量、安全边界）。**把边界写清楚，比把能力说得更强更有价值。**

**模块八到此七讲。** 回到结论上一层：模块七（43–48）用你自己的 Java 系统把六大机制读了一遍；**模块八（49–55）打开了一个真实开源 harness 的内部实现**，看到同一套机制如何被做成**可组合、可替换、可回放**的原语；而它的施工纪律（决策不可改写、事故按缺口收录、文档可校验）回答了"**这套东西怎么才能十年不烂**"这个问题。

**下一站**：模块九换一个**产品形态**的参照物——**Claude Code**。它是把六大机制全部做进**一个终端产品**的典型：闭源的内部我们不看，只看它的**公开形态**——它暴露了什么配置、在什么条件下拒绝了什么。而这一回你手上有**两把尺子**了：一把是你自己建的 Java 系统，一把是刚读完的 `dsh`。**用两把尺子量同一个产品，量出来的差异，才真正属于"产品形态"，而不是"我的实现习惯"。**
