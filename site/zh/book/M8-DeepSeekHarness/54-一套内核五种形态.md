# 第 54 讲 · 一套内核，五种形态

> 🎯 导读问题：**"Web 版、命令行版、SDK 版、编辑器插件版——这是四个仓库还是四个分支？"** ——能答出"是**同一棵插件树的四种装配**：形态差异走 **Profile + 有序 patch**，不走 fork；而'有个形态需要完全不同的树'时，答案也不是加开关，而是**给它一棵显式的、独立的树**"——这一句就把"多形态交付"和"复制一份代码改改"分开了。**本讲要建立的判据是：可替换性如果只发生在 provider 层，是不够的——它必须一直贯通到"交付形态"这一层。**

> **模块八 · 第六讲**：上一讲说"换一个 provider 就能改变整个产品"。这一讲把这句话推到极致——**`dsh` 用同一套内核，交付成五种产品形态**（外加一个 Electron 桌面应用）。这是"架构可复用"最强的证据：**如果五种形态能共用一套内核，说明这套内核的抽象是真的通用，而不是为某一种产品量身定做的。**

> **图 54-0**　本讲地图：`dsh-base` 是四个形态的共享第一层；`sdk-minimal` 刻意不套 base（另立一棵显式树）；桌面版是第六个消费者、有保留的 profile 与独立端口。**形态之间的差异全部表达为"配置与 patch"，不表达为"分叉的代码"。**

## 一、痛点

你在 Java 里大概经历过这个场景：**同一套业务逻辑，要出 Web 版、要给命令行用、要被别的系统当 SDK 调、还要塞进某个平台做插件。**

第一反应通常是**分层**：`core` + `web-adapter` + `cli-adapter` + `sdk-adapter`。这个方向是对的。但你很快会遇到三件麻烦：

**麻烦一：共享的东西越改越不敢改。** 四个适配器都依赖 `core`，于是 `core` 里出现越来越多的"**给 Web 用的钩子**"、"**CLI 才需要的一个 flag**"。**共享层变成了所有形态差异的垃圾桶。**

**麻烦二：启动路径开始分叉。** Web 要热重载，CLI 不要；SDK 要长驻，CLI 要一次性；编辑器插件要纯自动化。于是启动逻辑从一份变成四份（或者一份里面套四层 `if`）。**"哪份启动代码在跑"变成一个要靠打日志才能回答的问题。**

**麻烦三：没法解释"为什么这个形态没有那个功能"。** 你只记得"好像 CLI 版不装那个东西"，但**说不出来它到底装了什么**。

> **这三件事的共同根源是：形态差异没有被表达成"数据"。** 只要它表达为代码分支，它就会同时污染共享层、分叉启动路径、并让"实际装配了什么"变得不可回答。

`dsh` 对这三件事的回答，是同一条——**把形态差异做成"一棵可以被打印出来的树"**。下面看具体怎么做的。

## 二、原理

### 2.1 五个 profile：每一个的职责，用它自己的话说

随发行版交付的 profile 模板有五个（`docs/architecture.zh.md:19`）：`web`、`headless`、`sdk`、`sdk-minimal`、`acp`。**每个组合包的 README 第一段就是它的职责定义**，我逐条引原文，不做转述：

| Profile | 职责（原文） | 出处 |
|---|---|---|
| **`dsh-base`**（共享层，不是 profile） | "每个基于 base 的 `dsh --profile` 表层都运行在 `dsh-base` 上，因此这些表层**共享模型连接、完整工具集、持久会话历史和 workspace 安全默认值**" | `packages/bundle/base/README.zh.md:12` |
| **`web`** | "打开提供**聊天、模型与设置管理以及会话历史**的交互式浏览器 GUI。它使用与其他 dsh 表层相同的模型访问、工具与安全默认值" | `packages/bundle/web-app/README.zh.md:12` |
| **`headless`** | "**从命令行运行一个 dsh 任务并打印最终答案，然后退出**——没有 GUI、没有服务器、没有浏览器" | `packages/bundle/headless/README.zh.md:12` |
| **`sdk`** | "以 `dsh-base` 为基础的 SDK stdio 应用……它**继承 base 默认禁用模块 HMR 的策略**；其 patch 设置 coding agent persona、挂载应用自有的**零选项命令提供方**，并且**只在该提供方接受调用后**启动 `dsh-sdk-jsonrpc-server`" | `packages/bundle/sdk-app/README.zh.md:12` |
| **`acp`** | "以 `dsh-base` 为基础的**纯自动化 ACP** stdio 应用……继承 base 禁用模块 HMR 的策略；其 patch 设置 coding agent persona 与默认模型路由、挂载应用自有的零选项命令提供方，并且只在该提供方接受调用后启动 `dsh-acp`" | `packages/bundle/acp-app/README.zh.md:12` |
| **`sdk-minimal`** | "当 SDK 客户端需要**小型、显式**的 coding agent 运行时时使用……**提供完整 Cordis 配置树，并刻意排除** `dsh-base`、Web、settings、托管凭据、遥测、压缩（compaction）、文件系统工具、workspace 指令、skill（技能）、jobs 与 subagent" | `packages/bundle/sdk-minimal/README.zh.md:12` |

**把这张表横着读一遍，你会看到一条很清楚的设计手法**：`sdk` 和 `acp` 的说明**句式完全一样**——"以 base 为基础 + 继承禁用 HMR + patch 设置 persona + 挂载零选项命令提供方 + **只在该提供方接受调用后**启动真正的服务器"。

**★ 判据句（本讲第一个架构判据）**：

> **"只在该提供方接受调用后启动服务器"——这个"只……才"是启动纪律，也是可测试性。** 它保证了一件事：**如果配置错了，进程不会先起来再崩，而是根本不启动。** 形态之间的差异，因此被压缩成"patch 里那几行"，而不是"另一份启动代码"。
>
> **注意 `sdk` 与 `acp` 的差异有多大**：目标读者不同（写代码的 SDK 客户端 vs 编辑器的自动化协议）、传输不同（JSON-RPC vs ACP）、是否设置默认模型路由都不同——**但这些差异的载体，是同一个形状的 patch。** 这是"差异表达为数据"的直接收益：**新增一种形态，是写一份 patch，不是写一个启动器。**

### 2.2 层与 patch：形态差异到底被编码在哪里

上一讲（第 49 讲）给过四级应用顺序，这里把它落到"形态"这个场景上看：

```
空条目列表
  ← 按 profile 列出的顺序应用每个 bundle     ← 形态的"骨架"在这里
  ← profile 的 cordis.patch.yml            ← 这个形态自己的偏好
  ← home 级 cordis.patch.yml               ← 这台机器的偏好
  ← 任意 --patch overlay                   ← 这一次运行的偏好
```

（顺序出自 `docs/architecture.zh.md:27`；"一条 patch 按 id 定位某个条目并**替换其整个 config**，或插入新条目"）

**★ 判据句（本讲第二个架构判据）**：

> **"替换整个 config"而不是"合并字段"——这个选择决定了 patch 是可推理的。** 如果 patch 是"深度合并"，那么"当前这个条目最终长什么样"就必须靠**脑内跑一遍合并算法**；而"整块替换"让你只需要回答"**哪一层最后写了它**"。
>
> **这是一个典型的架构取舍**：深度合并更"省字"，但**结果是不可读的**；整块替换更"啰嗦"，但**每一层的意图都能单独读懂**。对配置系统来说，**可读性应该赢**——因为出问题时你要做的是"定位哪一层写错了"，不是"欣赏它多简洁"。

### 2.3 HMR：形态之间**最该不同**的一处，以及它的表达方式

热重载（HMR）是"形态差异"里最典型的一处：**开发时要，生产形态不要。** `dsh` 的表述极其干净（`docs/architecture.zh.md:29` 原文）：

> YAML 控制 HMR：**base 启用仅监视配置的 `dsh-hmr`**；**Headless、SDK 和 ACP 禁用它**；**`sdk-minimal` 不包含它**。Profile patch 覆盖这些默认值。

请把这三档读慢一点——**它们不是三个同义词**：

| 表述 | 语义 |
|---|---|
| base **启用** HMR | 装了这个插件，开着 |
| Headless / SDK / ACP **禁用它** | 插件**还在**，但被关掉 |
| `sdk-minimal` **不包含它** | 插件**根本不在树里** |

**★ 判据句（本讲第三个架构判据）**：

> **"禁用"和"不包含"必须能分开表达。** 这不只是洁癖：**被禁用但存在的插件仍然在树里**——它可能仍被 `--dump-config` 打印出来、仍参与依赖解析、仍可能在一次 patch 里被重新打开。而"不包含"意味着**它连成为问题的资格都没有**。
>
> **这个区分对安全与体积都成立**：要交付一个"最小攻击面"的运行时（`sdk-minimal` 的定位），你需要的是**不包含**，不是"配了一堆 disabled"。**如果一个配置系统只有"开关"没有"缺席"，你就永远无法表达"这东西不在场"。**

### 2.4 `sdk-minimal`：一个"刻意的例外"该长什么样

这是本讲最值得学的**一处反面设计的正面用法**。

第 49 讲已经引过：`sdk-minimal` 是"**刻意保留的例外**：一个组合包拥有**完整的显式 SDK 配置树，不应用 `dsh-base`**"（`docs/architecture.zh.md:25`）。它的 README 把"排除清单"列得极长（`:12`）：`dsh-base`、Web、settings、托管凭据、遥测、compaction、文件系统工具、workspace 指令、skill、jobs、subagent。

而它的**正面定义**同样精确（同段）：它"**默认只公布按平台选择的持久 shell**，把会话持久化为**未压缩 JSONL**，并从 **SDK 初始化请求**选择模型"。

**注意这三点都是"做了别的选择"，不是"少做了"**：
- 公布的范围：**只公布持久 shell**（不是"工具少一些"，而是"公布集合被重新定义"）；
- 持久化：**未压缩 JSONL**（放弃了压缩这个能力，换来的是可读/可流式处理）；
- 模型选择：**从初始化请求里来**（不是配置文件里来——因为它的调用方是一个 SDK 客户端）。

**而架构文档还补了一条边界条件**（`docs/architecture.zh.md:45`）：`sdk-minimal` "是**位于同一 launcher 后的仓库自有独立组合包**，而**不是由调用方提供的 Cordis 配置树**"。

**★ 判据句（本讲第四个架构判据）**：

> **"例外"的合格形态是：它自己就是一棵完整、显式、可 `--dump-config` 打印的树。** 它**不是**"共享树 + 一堆 `if`"，也**不是**"把组装权交给调用方"。
>
> 前者的问题你已经知道（开关爆炸）；后者的边界条件很有讲究：**如果把"组装一棵树"的权力交给外部调用方，你就失去了"这个形态长什么样"的唯一答案**——每个客户端都能给你一棵不同的树，你就再也没法回答"我的 SDK 版支持什么"。`sdk-minimal` 的选择是：**权力留在仓库里，只是另立一棵树。**
>
> **这是"既要极简、又要可解释"的唯一出路**：**另立一棵显式的树，而不是让树变得可参数化。**

### 2.5 前沿深挖一：第六个消费者——Electron 桌面应用

五种 profile 之外，`dsh` 还有一个**桌面应用**。它的实现是本讲"形态可复用"的**最强证据**——因为它把"同一套内核"搬到了一个**进程模型完全不同**的环境里。

`docs/architecture.zh.md:53` 原文：

> **Electron 桌面应用**在**签名资源中携带精确匹配的 dsh 生产运行时**，并拥有**保留的** `$DSH_HOME/profiles/desktop`。共享 profile helper 初始化其文件、协调已安装 bundle，并解析安装与 bundle 的依赖**而不替换 pnpm 拥有的包**。**CLI 与 Desktop 共享产品数据**，可执行包、启用选择与锁文件**保持独立**。**公开 CLI 不能管理 Desktop profile。**

这几句里有四个可直接复用的判断：

| 设计 | 为什么 |
|---|---|
| 签名资源里携带**精确匹配的**生产运行时 | 桌面应用不能"依赖用户机器上装了什么版本"——**版本必须被钉住** |
| 拥有**保留的** `$DSH_HOME/profiles/desktop` | 它是一个**独立的 profile 身份**（`apps/desktop/README.zh.md:68`、`:79`、`:133` 三处都写了这一点） |
| **CLI 与 Desktop 共享产品数据**，但可执行包 / 启用选择 / 锁文件**保持独立** | "共享数据、独立装载"——**数据可以共享，依赖图不能共享** |
| **公开 CLI 不能管理 Desktop profile** | 边界是**显式**的，不是"不小心"的 |

启动路径同样说明了"同一套内核"（`docs/architecture.zh.md:55`）：Electron 用 **Electron Node 模式**启动一个**私有 Desktop Host**；Host 调用**共享的 CLI profile runner 与完整 Web 应用**；窗口先加载打包好的 Web 资源，等待启动注入后**在同一文档中激活客户端插件**；Node IPC 承载启动注入、就绪、致命错误与关闭。

以及最实在的一条（`apps/desktop/README.zh.md:5`）：

> Desktop 默认使用端口 `19387`，与 Web 的 `3080` **分开**；可通过 `webserver.config.port` patch 覆盖。

**★ 判据句（本讲第五个架构判据）**：

> **"共享数据、独立依赖"是跨形态复用的一条关键切分。** 桌面版和 CLI **共享同一批会话数据**（用户切形态时历史还在），但**各自持有自己的可执行包、启用选择与锁文件**（一边升级不会把另一边弄坏）。
>
> **如果把这四个（数据、可执行包、启用选择、锁文件）当成一坨"共享还是独立"来一起决定，你一定会在某一端做错。** 正确做法是**逐项决定，并把这个决定写进文档**——`dsh` 这里就是逐项写清楚的。

### 2.6 前沿深挖二：Python SDK 与"应用启动器纪律"

两种额外证据说明"五种形态"不是特例、而是**被纪律保证的**。

**证据一：Python SDK 走同一套架构**（`docs/architecture.zh.md:49` 原文）：

> Python SDK 遵循**相同的应用架构**。其运行时 wheel 把普通 `dsh` CLI 打包为 `deepseek-harness-sdk-runtime-<platform>-<arch>`，客户端默认以**显式 Harness home** 启动 `dsh --profile sdk`。极简示例选择随附的 `sdk-minimal` profile。Python 暴露 **profile 选择与有序 patch 文件**，而不是完整 Cordis 树；持久外部插件通过 `dsh plugin` 安装。

注意最后一层的克制：**Python 侧暴露的是"profile 选择 + 有序 patch 文件"，不是整棵树。** ⇒ **不同语言绑定可以有不同粒度的控制面**，但**装配规则是同一套**。

**证据二：有一条会失败的检查，专门守"不许绕过启动器"**（`docs/architecture.zh.md:47` 原文）：

> `verify-application-entrypoints` 将每个包 bin、可执行源码、根 demo 以及根脚本 `start:web` 与 `dev:web` **归入显式类别**，并**拒绝任何绕过 `dsh` 的 Node 应用路径**。

以及同段对"什么不算应用启动"的明确排除：Vendored CLI、仅用于构建和测试的可执行文件、进程内直接挂载插件、私有浏览器 WebWorker 预览——**都不属于 Harness 应用启动器**。

**★ 判据句（本讲第六个架构判据，也是"多形态"能长期成立的前提）**：

> **"多形态"最大的敌人不是设计，是熵**：某天有人为了调试方便，加了一个 `node scripts/run-agent.js`——于是**出现第六条启动路径**，而它不在任何形态的装配规则里。
>
> `dsh` 的解法是**把这件事变成一个会失败的检查**：把所有的入口**归入显式类别**，然后**拒绝**任何绕过 `dsh` 的应用路径。⇒ **"只有五种形态"这句话，是被 CI 守着的，不是被文档呼吁的。**
>
> **迁移建议**：你的多形态交付里，凡是"启动方式"都应该有一个**白名单 checker**。**没有 checker 的"约定"，保质期通常不超过两个季度。**

**顺便把开发命令也核一遍**（`docs/development.zh.md:164`、`:166-171`）：`start:*` 启动**上一次 `pnpm run build` 的产物**；`dev:*` **先执行该构建再启动**；Web 还会在源码修改时持续重建 client bundle。四条命令是 `pnpm run start:web` / `dev:web` / `start:desktop` / `dev:desktop`，其中 `dev:web` 还接受 `--skip-build`（复用现有产物树）与 `--no-serve`（只跑重建 watcher）；Web 命令的参数会透传给 `dsh web`。`Makefile` 只提供 **6 个 target**（`.PHONY: help build web desktop dev-web dev-desktop`，`Makefile:4`），并把它们映射到上面同一批 `pnpm` 命令（`Makefile:10-14`）。⇒ **开发入口也收敛到"同一批命令的两个变体"**，而不是每加一种形态就多一套脚本。

## 三、避坑清单

- [ ] **形态差异要表达成"配置与 patch"，不要表达成"分叉的代码"。** 分叉的启动路径会让"哪份代码在跑"变成一个要打日志才能回答的问题。
- [ ] **共享层里出现"给某形态用的钩子"，就是设计开始腐烂的信号。** 那说明形态差异正在污染共享层。
- [ ] **patch 语义优先选"整块替换"而不是"深度合并"。** 合并算法让"最终长什么样"不可读；整块替换让"哪一层最后写了它"可读。
- [ ] **"禁用"与"不包含"必须能分开表达。** 只有开关、没有缺席，你就无法表达"这东西不在场"——而"最小攻击面"要的正是不在场。
- [ ] **"例外形态"的正确做法是另立一棵显式、可打印的树**，不是"共享树 + 一堆 if"，也不是"把组装权交给调用方"。
- [ ] **新增一种形态时，先问它是否真的需要一棵新树。** 大多数情况（换传输、换 persona、换是否 HMR）都只是 patch。
- [ ] **"数据 / 可执行包 / 启用选择 / 锁文件"逐项决定共享还是独立**，不要当成一坨一起决定。
- [ ] **给"启动方式"配一个白名单检查器**，拒绝绕过统一启动器的路径。否则形态数量会悄悄地长到七种。
- [ ] **别让外部调用方提供整棵配置树。** 那会让你失去"这个形态支持什么"的唯一答案。
- [ ] **发行形态要钉住运行时版本**（桌面版"携带精确匹配的生产运行时"）。"依赖用户机器上装了什么"，就是不可复现。

## 四、动手任务

> **目标**：把你的一套内核，整理成"可打印的形态"。

**步骤 1：列出现有形态，以及它们"事实上装了什么"**

对你交付的每个形态（Web / CLI / SDK / 插件…），写下：**它装了哪些模块、开了哪些开关。** 来源必须是**实际配置**，不能凭印象。

**任务**：写完之后检查——**能不能用一条命令打印出这张表？** 如果不能，你的第一个任务是造这条命令（对照第 49 讲的 `--dump-config`）。

**步骤 2：找出"共享层里的形态钩子"**

在共享层里搜形态相关的分支（`if (isWeb)` / `if (cli)` / `--headless` 之类的条件）。**任务**：每找到一处，判断它属于哪一类——**应该是配置**、**应该是缺席**、还是**真的属于共享逻辑**。前两类移到 patch 里，第三类保留并加注释说明为什么。

**步骤 3：把某一种形态的"权限"显式化**

挑一个"给外部客户端用"的形态（SDK / 插件 / 桌面）。**任务**：把这四项分别写下结论——**数据、可执行包、启用选择、锁文件**，哪些共享、哪些独立。**验收标准**：四项都必须有明确结论，不许写"看情况"。

**步骤 4：写一个"启动方式白名单"检查**

列出你系统里**所有**能启动应用的方式。**任务**：把每一类归入"正式启动器 / 构建测试用 / 不属于启动"三类，然后写一个检查（脚本即可）**拒绝**四类之外的方式。**这一步做完，你才算真的"只有 N 种形态"。**

## 本讲小结

1. **五种 profile 是同一棵树的五种装配**：`web`（浏览器 GUI）、`headless`（跑一次打印答案就退出）、`sdk`（JSON-RPC 服务器）、`acp`（纯自动化 ACP 服务器）、`sdk-minimal`（刻意极简）。**形态差异走 Profile + 有序 patch，不走 fork。**
2. **`dsh-base` 是四形态的共享第一层**（模型连接、完整工具集、持久会话历史、workspace 安全默认值）；**`sdk-minimal` 刻意不套它**，另立一棵**完整、显式**的树。
3. **HMR 的三档表述必须分清**：base **启用**、Headless/SDK/ACP **禁用**、`sdk-minimal` **不包含**。"禁用"≠"不包含"——最小攻击面要的是**不在场**。
4. **"例外"的合格形态是"自己的完整显式树"**，且**组装权留在仓库内**——把组装权交给调用方，你就失去了"这个形态支持什么"的唯一答案。
5. **桌面应用是"同一套内核"最强的证据**：签名资源携带精确匹配的生产运行时、保留独立的 `profiles/desktop`、默认端口 `19387`；**共享数据，但可执行包 / 启用选择 / 锁文件各自独立**。
6. **Python SDK 走同一套装配规则**，只是控制面粒度不同（暴露 profile 选择与有序 patch，不暴露整棵树）。
7. **"只有 N 种形态"必须被 CI 守着**：`verify-application-entrypoints` 把所有入口**归入显式类别**并**拒绝任何绕过 `dsh` 的 Node 应用路径**。没有 checker 的约定，保质期不到两个季度。

下一讲是本模块的收束：**怎么读一个 harness**。前面六讲给的是一套"读任意 agent 系统"的方法——**真相源在哪、替换点在哪、拦截点在哪**；而 `dsh` 的工程纪律（决策记录、事故复盘、文档级真源、双语门禁）恰好是这套方法的**元层**：**它连"怎么保证文档不撒谎"都做成了门禁。**
