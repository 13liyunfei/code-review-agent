## 一、痛点

有个 PR，审查报告显示"🔴 存在 2 个 BLOCKER，已进入强制审批流"。

但它被合了。

不是有人点了"忽略警告"，也不是分支保护没配。是**那句"已进入强制审批流"根本没兑现**——PR 的提交状态实际上没有被置为 `failure`，所以分支保护看到的是一片绿，**机制上没有任何东西在拦**。

我查了一个多小时才找到原因。而最难的地方不是找到它，是**我一开始根本没往那个方向想**：

> 评论里明明白白写着"已进入强制审批流"，我潜意识里就当这件事**已经发生**了。

真相是：**"在评论里说了一句话"和"在平台上改变了状态"，是两件完全独立、各自可能失败的事。** 而我们的代码把它们写成了一段顺序执行的语句，连返回值都没接。

这就是这一讲要讲的东西。Webhook 接入与平台回写，看起来是"收发 HTTP 请求"的集成活，其实它是整个系统里**唯一一处既要对外界负责、又不受自己控制**的边界。而边界上每一个动作都会失败，每一个失败都有不同的可见度。

## 二、原理

### 2.1 回写不是一件事，是三条独立通道

先把这个系统往代码平台上写的所有东西列出来：

| 通道 | 平台对象 | 用什么 API | 谁在读它 |
|---|---|---|---|
| **① 内容** | PR/MR 评论（Markdown 报告） | `POST /issues/:index/comments` | **人**（开发者点开看） |
| **② 裁定** | 提交状态（commit status） | `POST /repos/:o/:r/statuses/:sha` | **机器**（分支保护规则） |
| **③ 追踪** | 工单（Issue） | `POST /repos/:o/:r/issues` | **人**（整改闭环） |
| **①' 内容（行内）** | 代码行旁的 `suggestion` 评论 | `POST /pulls/:index/reviews` + `comments[]` | **人**（一键 Apply） |

**四条通道，四种失败后果，四套可见度**：


<img class="mermaid-svg" src="/zh/book-assets/diag-0091.svg" alt="四条通道，四种失败后果，四套可见度：" />

> **图 38-1**　四条回写通道，四种失败后果。**只有 ② 是完全静默的**——因为它的读者是机器，而机器不会来问"为什么这次没出现"。

**②是这里面最危险的，而且它的危险方向恰恰来自它的"正确"**：commit status 的语义是"这个 commit 通过了/没通过某个检查"。**它必须由机器读，也就意味着它必须由机器写对。** 一旦写错，读它的机器会照错执行——**没有任何人参与，也就没有任何人察觉**。

### 2.2 AI 该不该有权阻断一次合并

这是接入一个代码平台时最需要先想清楚的问题，而且它是**产品/责任问题，不是技术问题**。

这个项目给出的答案，写在两个地方：

```java
// GiteaApiClient.java:203（行内评论的 review 提交）
payload.put("event", "COMMENT");
```

```java
// ReviewWorkflowEngine.java:62-63（BLOCKER 时的提交状态）
giteaClient.createCommitStatus(owner, repo, headSha, "failure",
        "code-review/blocker", "存在 BLOCKER 级问题，禁止合入");
```

**行内评论一律用 `event: COMMENT`，从不用 `REQUEST_CHANGES`。**

这个区别很关键：在 Gitea/GitHub 的模型里，`REQUEST_CHANGES` 是一个**社会性动作**——它把"我不同意"变成一个挂在人的 PR 上的、需要被"回应"的状态。而 `COMMENT` 是"我表达意见，但我不对你的 PR 行使否决权"。

而真正的阻断能力交给 **commit status**（`state: failure` + `context: code-review/blocker`）。为什么这样分？

> **因为 status 是"可配置策略"，comment 是"人的意见"。**
>
> 用 `REQUEST_CHANGES` 阻断，等于**AI 直接代替人做了决定**——而且这个决定会落在人的 PR 上、以 AI 的名义挂着。
> 用 commit status 阻断，等于**AI 只上报事实，是否真的拦住由分支保护规则决定**——团队可以决定"code-review/blocker 是 required check 吗？"、"BLOCKER 要不要真的拦？"。**决定权在配置里的人手里，不在 AI 手里。**

**AI 可以强烈反对，但不该替人做阻断的决定。** 这条边界的工程形态就是：**内容通道与裁定通道分开。**

### 2.3 一个容易被忽略的设计：主动上报 `success`

注意 `ReviewWorkflowEngine:73-74` 这段——**没有 BLOCKER 时，它会主动把状态置为 `success`**：

```java
giteaClient.createCommitStatus(owner, repo, headSha, "success",
        "code-review/blocker", "无 BLOCKER 级问题");
```

很多人会觉得这一步可以省（"没问题就不上报"）。但省掉它会造成一个很具体的后果：

```
分支保护要求："code-review/blocker 必须通过才能合并"
→ 如果 AI 从不主动上报 success，这个 context 在 Gitea 里就是"从未出现"
→ "从未出现的 required check" 在多数平台上的处理是【永远不满足】→ PR 卡死
→ 或者被管理员当成噪声把整个 required check 关掉 → 【阻断能力永久失效】
```

**"不说话"和"说通过"是两回事。** 前者会让规则无法判定；后者给了规则一个明确的输入。**当一个机制要依赖你表态时，沉默不是中立的——沉默会让机制退化。**

### 2.4 降级该报什么状态：`success` / `pending` / `failure` 三选一

既然 status 是机器判据，那么当**审查本身不可信**时该报什么？

先看这个项目实际会报什么。`ReviewWorkflowEngine.handle` 的全部判据只有两行：

```java
// ReviewWorkflowEngine.java:43-45
List<Finding> findings = report.getFindings();
long blockers = findings == null ? 0
        : findings.stream().filter(f -> f.severity().name().equals("BLOCKER")).count();
```

**它只看 `findings` 里有没有 `BLOCKER`。**

而第 16 讲我们已经讲过：模型全挂时，`DeclarativeReviewAgent` 会吞掉异常，那个 Agent 的输出变成 **"0 条发现"**，同时在报告顶部加一个降级告警块。

于是链路变成：

```
模型全挂
  → SecurityAgent 降级（ModelUnavailableException）
  → 报告顶部有降级告警块（第 16 讲已修 ✅）
  → findings 为空 → blockers = 0
  → ReviewWorkflowEngine:73  createCommitStatus(..., "success", "无 BLOCKER 级问题")
  → Gitea 分支保护看到 code-review/blocker = success → 允许合并
```

**降级在报告里是黄色告警，在平台上变成了一盏绿灯。**

而且这两个信号**强度差得远**：

| 信号 | 在哪 | 谁读 | 被忽略的成本 |
|---|---|---|---|
| 报告顶部的降级告警 | 评论正文 | **人，要主动点开看** | 高（多数人只看结论行） |
| `code-review/blocker = success` | 平台状态栏 | **机器，自动读** | 零（没人参与） |

**第 16 讲修好了"报告里不产生假通过"，但平台回写链路上还留着一条把降级翻译成 `success` 的出口。** 这就是为什么"修好一个降级传播"不等于"修好降级传播"——**降级的传播路径有几条，就要修几条。**

那正确该报什么？三个候选：

| 状态 | 语义 | 适不适合"审查降级" | 问题 |
|---|---|---|---|
| `success` | 通过了这个检查 | ❌ **这正是缺陷** | 断言了一个没人验证过的事实 |
| `pending` | 检查还没出结果 | 🤔 语义接近，但**可能永久 pending** | 有些平台/规则会无限期等待，PR 再也不动 |
| `failure` | 检查没通过 | ✅ **推荐（fail-closed）** | 描述写明"降级，需人工" |

**推荐 `failure` 的理由和整个系统的基调一致**：宁可让人来处理一次"其实没问题的 PR"，也不要放行一次"没人看过的 PR"。**代价是可见的、可控的（人会来问）；收益是隐形的（拦住了一个坏提交）。这类取舍永远应该选前者。**

### 2.5 `accepted` 不等于 `reviewed`

Webhook 的返回值得单独说一句，因为它是**平台与你系统之间的第一个契约**。

```java
// GiteaWebhookController.java:143-147
return ResponseEntity.ok(Map.of(
        "status", "accepted",
        "pr", String.valueOf(prNum),
        "repo", repoFullName
));
```

**`accepted` 的准确语义是：「我收到了，并且我会异步处理」，而不是「审完了」。**

为什么必须异步？因为平台侧有超时：

| 平台 | Webhook 超时 | 你的审查耗时 |
|---|---|---|
| GitLab | 10 秒 | 分钟级（5 个 Agent 并行 + LLM） |
| Gitea | 与设置有关，通常 ≤10 秒 | 同上 |

代码注释把这件事写得很直白：

```java
// GitLabWebhookController.java:29
 *   <li>异步调用 {@link GitLabReviewService} 执行审查，立即返回 200（避免 GitLab 10s 超时）。</li>
```

**如果同步处理，平台会认为投递失败并重投**，于是你得到：同一事件被重投 N 次、每次都在做一次分钟级审查、每次审查都产生一条评论。**"为了不重投"而做的异步化，代价是必须自己保证幂等**——这就是为什么两个 `ReviewService` 里都有一段幂等判重（见 3.5）。

**这三件事是一条链**：超时 → 异步 → 可能被重投 → 必须幂等。少想一环，就会在多实例 + 重投的组合下变成一个反复出现的线上问题。

## 三、代码

### 3.1 准入：Gitea 的 HMAC 验签

```java
// GiteaWebhookController.java:24-38（类注释）
/**
 * Gitea Webhook 接收控制器。
 *
 * <p>监听 {@code POST /webhook/gitea}，接收 Gitea Pull Request 事件。
 *
 * <p>处理流程：
 * <ol>
 *   <li>校验 {@code X-Gitea-Signature} 请求头（HMAC-SHA256(body, secret)）与配置密钥是否匹配；</li>
 *   <li>解析 payload，提取 action / PR 序号 / 仓库全名；</li>
 *   <li>仅在 action 为 {@code opened} / {@code reopened} / {@code synchronized} 时触发审查；</li>
 *   <li>异步调用 {@link GiteaReviewService} 执行审查，立即返回 200（避免 Webhook 超时重试）。</li>
 * </ol>
 *
 * <p>仅在 {@code gitea.enabled=true} 时注册此 Controller。
 */
```

`/webhook/gitea` 这个路径是**未鉴权的公网入口**（它不在 `/api/**` 的鉴权拦截器作用域内——第 31 讲讲过 `WebConfig` 只拦 `/v1/**` 与 `/api/admin/**`）。所以**签名校验就是这个端点唯一的防线**：

```java
// GiteaWebhookController.java:87-108
// 1. 校验 Webhook 签名（HMAC-SHA256）
if (webhookSecret != null && !webhookSecret.isBlank()) {
    boolean sigMissing = (signature == null || signature.isBlank());
    if (sigMissing) {
        if (allowUnsigned) {
            // 本地 dev：Gitea webhook 通常未配 secret，放行以便端到端联调。
            log.warn("[Gitea Webhook] 引擎已配置 webhook-secret，但请求未携带 X-Gitea-Signature 头；"
                    + "dev 开关 webhook-allow-unsigned=true，放行（生产环境必须保持 secret 一致）");
        } else {
            log.warn("[Gitea Webhook] 签名校验失败：引擎已配置 webhook-secret，但 Gitea 未携带签名头"
                    + "（Gitea webhook 未配 secret）。请在 Gitea webhook 设置里填入与引擎相同的 secret，"
                    + "或将引擎 GITEA_WEBHOOK_SECRET 清空。bodyLen={}", body.length());
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                    .body(Map.of("error", "Invalid webhook signature"));
        }
    } else if (!signature.equalsIgnoreCase(hmacSha256Hex(body, webhookSecret))) {
        log.warn("[Gitea Webhook] 签名校验失败：secret 不一致。expected={}, received={}, bodyLen={}",
                hmacSha256Hex(body, webhookSecret), signature, body.length());
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                .body(Map.of("error", "Invalid webhook signature"));
    }
}
```

**先表扬 `allowUnsigned` 的精细语义。** 从名字看它像个"跳过校验"的后门，但实现**不是**：

| 请求形态 | `allowUnsigned=false` | `allowUnsigned=true` |
|---|---|---|
| 带签名且正确 | 通过 | 通过 |
| **带签名但不匹配** | **401** | **401**（仍然拒绝） |
| **不带签名头** | **401** | **放行**+WARN |

**它放行的不是"校验"，而是"允许你的 Gitea 没配 secret"这件事。** 一个签名**错误**的请求，即使开了这个开关也照样 401。这是我在这个项目里见到的少数"开关的名字歧义、但行为严格收敛"的例子——**名字应该改成 `gitea-webhook-secret-optional` 之类，但行为本身是对的。**

**然后指出两处问题。**

**★ 问题一：`equalsIgnoreCase` 是非常量时间比较。**

```java
} else if (!signature.equalsIgnoreCase(hmacSha256Hex(body, webhookSecret))) {
```

第 31 讲我们花了一整节讲恒定时间比较，那个项目里是有现成工具的：

```java
// core/security/KeyHasher.java:56-63（第 31 讲已核对）
public static boolean constantTimeEquals(String a, String b) { ... MessageDigest.isEqual(...) ... }
```

**同一个仓库里，API 密钥用 `MessageDigest.isEqual`，Webhook 签名用 `String.equalsIgnoreCase`。** 两种标准。

- **诚实地说**：这个具体场景下时序攻击的可行性很低——攻击者要靠比纳秒级的响应差异去逐字符猜 HMAC，而这个端点还有网络抖动、`body.length()` 日志等噪声；更关键的是，**攻击者如果真的能观测时序，他通常已经在网络路径上了**（那时候他直接读 webhook 请求就行）。
- **但它仍然值得改**，理由不是"这里会被打"，而是**标准不一致的成本**：下一次有人（可能是读者）来给这个文件加一个新的校验，他会照着这个文件里已有的写法写 `equals`。**不安全的示范比不安全本身传播得快。**

**★ 问题二：日志把「期望签名」打了出来。**

```java
log.warn("[Gitea Webhook] 签名校验失败：secret 不一致。expected={}, received={}, bodyLen={}",
        hmacSha256Hex(body, webhookSecret), signature, body.length());
```

`expected` 就是 `HMAC-SHA256(body, secret)`——**用你的密钥对这个 body 算出的正确签名**。而 `body` 本身也在日志上下文里（前面 `:84-85` 打了 `bodyLen`，`DemoRunner`/调试日志还可能打出 body 内容）。

问题在于：**这个签名本身是一份"可用凭据"**。

- HMAC 是单向的，拿到 `HMAC(secret, body)` **不能反推 secret**——所以这不是"密钥泄露"。
- 但**签名校验没有时间戳、没有 nonce、不防重放**：只要 `body` 和 `signature` 都知道，攻击者就能构造出一次**通过校验的投递**。
- 而日志里恰好同时有：`body`（来自请求，或可从平台侧获取同样的 JSON）+ `expected`（正确的签名）。**这等于把一份合法签名写进了日志文件。**

**正确做法**：日志只记录**判断结果**，不记录**用于判断的秘密衍生值**：

```java
// 修法示意（不是仓库现状）
log.warn("[Gitea Webhook] 签名校验失败：请求签名与引擎密钥不匹配（receivedLen={}, bodyLen={}）。"
        + "请核对 Gitea webhook 的 Secret 与 GITEA_WEBHOOK_SECRET 是否一致。",
        signature == null ? 0 : signature.length(), body.length());
```

**通用规则：日志里可以出现"长度、是否为空、比较结果"，不可以出现"期望值"。** 期望值 = 你的系统能算出的正确答案；把它打出来，等于把一次性的挑战-应答变成了一份可以存档重放的凭据。

### 3.2 Gitea 与 GitLab：两套实现，一张漂移表

先把两个 Webhook 控制器的同一条链路并排放：

| 维度 | `GiteaWebhookController` | `GitLabWebhookController` |
|---|---|---|
| 验签方式 | HMAC-SHA256（`X-Gitea-Signature`） | 明文 token 相等（`X-Gitlab-Token`） |
| 比较实现 | `signature.equalsIgnoreCase(...)`（`:102`） | `token.equals(webhookSecret)`（`:74`） |
| **traceId** | **`TraceContext.newTraceId()` + `set`（`:82-83`）** | **无** |
| **异步是否传 trace** | **`TraceContext.wrap(...)`（`:139`）** | **无（`:120-122`）** |
| 解析容错 | 拿不到 PR 字段 → `200 ignored` | 非 mrm 事件 → `200 ignored` |
| 字段缺失 | 与"非 PR 事件"合并判断（`:119`） | 单独 `400` + WARN（`:110-114`） |
| 触发 action（注释） | `opened`/`reopened`/`synchronized` | **"`open` 或 `update`"**（`:28`） |
| 触发 action（实现） | 同注释（`:128-129`） | **`open`/`reopen`/`update` 三个**（`:105`） |
| 测试可注入 | — | — |

**最刺眼的是 traceId 那两行。** 第 36 讲我们讲过：traceId 是"把散落在多线程、多服务里的一条链路串起来"的唯一线索。Gitea 链路有，GitLab 链路**没有**：

```java
// GiteaWebhookController.java:81-85
// 0. 生成全链路追踪号（入口即生成，贯穿后续所有环节，便于线上问题定位）
String traceId = TraceContext.newTraceId();
TraceContext.set(traceId);
log.info("[Gitea Webhook] 收到请求：bodyLen={}, teamHeader={}, traceId={}",
        body.length(), teamHeader, traceId);
```

```java
// GiteaWebhookController.java:139-141
CompletableFuture.runAsync(TraceContext.wrap(() ->
        reviewService.reviewPullRequest(owner, repo, prNum, headSha, teamHeader)
), webhookExecutor);
```

```java
// GitLabWebhookController.java:120-122 —— 注意没有 wrap
CompletableFuture.runAsync(() ->
        reviewService.reviewMergeRequest(pid, path, iid, teamHeader)
, webhookExecutor);
```

**后果**：在 GitLab 这条链路上，
1. 日志里没有 traceId，**按 traceId 检索搜不到任何东西**；
2. `TraceContext` 在 `webhookExecutor` 的线程上是空的 → **即使下游某处打印了 traceId，也是另一个（或空的）值**；
3. 第 36 讲那个"从 traceId 反查某次审查发生了什么"的排查手段，在 GitLab 接入时**完全不可用**。

而且 `GitLabReviewService:89` 的日志印证了这一点：

```java
log.info("[GitLab审查] 开始处理 MR !{}（projectId={}, repo={}，团队={}）", mrIid, projectId, projectPath, teamId);
```

三个必须记住的要点：

```
        但如果还是拿不到 → 幂等键还是 key(main)
      → historyStore.getLatest 返回的是 commit A 那次 → runId 相同
      → 【判重命中，整轮跳过，commit B 一条评论都没有】
```

**不是"行号会偏"，是"新 commit 被当成已审过，静默跳过"。** 这个后果比注释描述的严重一个量级，而且是**完全静默**的（返回 200 + `log.info` 幂等命中）。

**修法方向**：headSha 拿不到时**不要兜底**，而是**拒绝审查并明确告知**——因为"用分支名当版本标识"会让三个键的语义同时失效，这比"这次不审"贵得多。

**这是本讲对全书那句判据的又一次应用：兜底不能改变标识的语义。** 拿不到版本号就不做事，比"用一个近似的版本号做事"安全。

## 四、避坑清单

- [ ] **把回写拆成独立通道并分别观测**：内容（评论）、裁定（commit status）、追踪（工单）、行内。**至少裁定通道的失败必须是 error 级别、且与"结论日志"相邻**——否则诊断信息会散落在不同类里，检索不到。
- [ ] **绝不让"动作失败"在文案里表现为"动作成功"。** 凡是评论/报告里写了"已 X"，都要检查那个 X 的调用返回值是否被接住。本项目现状：工单接了、状态没接。
- [ ] **AI 不代替人做阻断决定**：报告内容用 `COMMENT`（表达意见），阻断能力交给平台侧的 required status check（可配置策略）。**不要让 Agent 去 `REQUEST_CHANGES`**——那是社会性动作，该由人做。
- [ ] **无问题时主动上报 `success`**，不要"没问题就不上报"。required check 依赖你表态，沉默会让规则无法判定、进而被整体关掉。
- [ ] **降级必须上报 `failure`（fail-closed），不能报 `success`。** 检查方法：`handle()`/工作流类里，判定"有没有 BLOCKER"之前，是否先看了报告里的降级标记？没看就是漏。
- [ ] **枚举比较一律用 `==` / `switch`，禁止 `.name().equals("字面量")`。** 字符串拼错编译通过、运行期静默为 false，是"机制整个失效"最短的路径。
- [ ] **返回值有特殊值（0/-1/null/空串）时，先问"这个特殊值有几种原因"。** 多于一种就换成类型/`Optional`/异常。本项目：`postReviewComments` 返回 `0` 有四种含义。
- [ ] **接住每一个外部调用的返回值。** 同一段代码里出现两种处理标准（一个接一个不接）几乎必然是遗漏，而不是有意。
- [ ] **日志只记"长度/是否为空/比较结果"，不记"期望值"。** 对 HMAC/签名类校验尤其重要：`expected` + `body` 一起落盘，等于把一张可重放的凭据存档。
- [ ] **安全比较统一用恒定时间实现**（`MessageDigest.isEqual`）。即使当前场景的时序风险低，也要统一——**不安全的示范会传播**。
- [ ] **多平台接入抽公共骨架**。功能集差异超过 3 项时，"两套实现"必然漂移。核对方法：把两条链路的步骤列成表，**逐项问"这个差异是外部协议决定的，还是我们没抽出来？"** 前者保留、后者收敛。
- [ ] **i18n 覆盖要检查所有对外文案出口**，包括每个平台的 footer。硬编码中文出现在"声称走 i18n"的路径上，会让双语用户以为是渲染 bug。
- [ ] **Webhook 入口必须能生成并贯穿 traceId**（含异步线程的传递 `TraceContext.wrap`）。缺少它 = 这条链路**不可按 traceId 检索**。
- [ ] **headSha / 版本号拿不到时不要兜底。** 用分支名之类的近似值会让断点键、历史键、幂等键同时失效，后果是"新提交被静默跳过"。
- [ ] **测试桩在隔离外部依赖的同时也移除了覆盖**。每写一个"绕开真实实现"的桩，就问一句：**被绕开的那段逻辑，还有别的地方覆盖吗？** 本项目：`ReviewWorkflowEngine.handle` 的两条分支零覆盖。

## 本讲小结

1. **回写是四条独立通道**：内容（评论）、裁定（commit status）、追踪（工单）、行内 suggestion。它们的失败后果与可见度**完全不同**——**裁定通道的失败是唯一"完全静默"的一种**，因为它由机器读、由机器执行。
2. **AI 该不该阻断合并，是责任问题不是技术问题。** 本项目的答案：**内容用 `event: COMMENT`（表达意见），阻断交给平台侧的 required status check（可配置策略）。AI 可以强烈反对，但不替人做决定。** 这条边界的工程形态就是"内容通道与裁定通道分开"。
3. **无问题时必须主动上报 `success`。** "沉默"不是中立——required check 会因"从未出现"而无法判定，最终被管理员整体关掉，**阻断能力永久失效**。
4. **★ 降级被翻译成了绿灯（本讲最重要）**：`ReviewWorkflowEngine:43-45` 只看 `findings` 里的 BLOCKER 数、**不看报告是否降级** → 模型全挂时 0 条发现 → `:73` 上报 `success`。**第 16 讲修好了"报告里不产生假通过"，但假通过还有第二个出口，在平台回写这一侧。** 降级传播有几条路径，就要修几条。
5. **降级该报 `failure`**（fail-closed），不报 `success`（断言了没人验证过的事实），慎报 `pending`（可能永久挂住 PR）。取舍原则：**宁可让人处理一次"其实没问题"，不要放行一次"没人看过"。**
6. **★ `createCommitStatus` 的返回值被忽略**（`ReviewWorkflowEngine:62` / `:73`），而同一段代码里 `createIssue` 的返回值**是被处理的**（`:66`）。后果：**评论写"已进入强制审批流"，而机制可能根本没建立**——本讲开头那个痛点的真实来源。**同一段代码里两种返回值处理标准，几乎必然是遗漏。**
7. **★ 用 `.name().equals("BLOCKER")` 比较枚举**，而唯一提到该类的测试用 `InertWorkflow` **把 `handle` 整个绕过去了**。后果：拼错一个字 → 阻断机制静默失效 → **338 个测试一个都不会红**。**测试桩在隔离外部依赖的同时，也把这段逻辑移出了观测范围。**
8. **★ `postReviewComments` 返回 `0` 有四种含义**（无事可做 / HTTP 4xx / 抛异常 / 本来为空），而调用方只打一行 `info`。于是"发布失败 7 条"和"没有可锚定行"在日志里长得一模一样。**凡是返回值有特殊值语义，先问"这个特殊值有几种原因"。**
9. **Gitea 1.27 的行内评论只有一个入口**：`POST /pulls/:index/reviews` + `comments[]` + `event: COMMENT`。旧接口已移除，所以**行内评论是批量一次性的**——`commit_id` 决定锚定版本，`side: RIGHT` 且行号必须落在新增侧。
10. **★ 日志打印了"期望签名"**（`GiteaWebhookController:103-104`）。HMAC 不能反推密钥（不是密钥泄露），但**签名不防重放**，而 `body` 也在上下文里——**等于把一张合法凭据存档**。规则：日志可记长度/是否为空/比较结果，不可记期望值。
11. **`allowUnsigned` 的语义是精细的**：它只放行"缺签名头"（= 你的 Gitea 没配 secret），**签名不匹配仍然 401**。名字有歧义，行为严格收敛——**这是正确但该改名的开关**。
12. **Gitea 与 GitLab 两条链路的漂移表**：七项增强功能（自动修复、工作流、行内评论、分步耗时、经验反思、LLM 评估、i18n）GitLab 路径**一项都没有**，而它的类注释写的是"串联**完整**审查链路"。其中 i18n 那一项让 `review.lang=en` 变成半真半假：报告正文英文、footer 硬编码中文。
13. **唯一的正当差异**：幂等判重的位置（Gitea 在拉取前、GitLab 在拉取后）——**因为 Gitea 的 payload 带 head SHA、GitLab 的不带**，且注释写清了这个原因。**判据：差异由外部协议决定是对的，由"没抽公共代码"决定是漂移。**
14. **★ headSha 兜底成分支名的注释只说了一半**：注释讲"行号会偏"，实际后果是**断点键/历史键/幂等键同时退化**→ 同分支的新 commit 会被判重命中**整轮静默跳过**。**兜底不能改变标识的语义：拿不到版本号就不做事，比拿近似值做事安全。**
15. **GitLab 链路没有 traceId**（`GitLabWebhookController` 无 `newTraceId`、async 无 `TraceContext.wrap`）。后果：第 36 讲那套"按 traceId 反查一次审查"的排查手段，**在 GitLab 接入时完全不可用**。

**模块六走到这里，你已经把系统"接到了外面的世界"，也看见了边界上所有的坑。** 下一讲换一个完全不同的角度——**把一个跑在开发者机器上的系统，变成一个人能一键装起来的东西**：镜像怎么分层、配置怎么给、沙箱能不能用、以及为什么"本地能跑"和"容器里能跑"经常不是同一件事。
