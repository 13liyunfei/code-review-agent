## 一、痛点

面试邀约来了。技术面 60 分钟，对面是一位后端出身、最近在做 Agent 方向的面试官。

你讲：PR 进来触发 webhook，5 个 Agent 并行审查、去重、仲裁、回写评论。你讲了八分钟，讲得很顺。

面试官听完，问了一句：

> "所以，你这个系统本质上就是——把 diff 拼进 prompt，调了一下模型的 API 对吧？"

**这一句话，能把 300 小时的工作量折成"调 API"。**

它不是恶意。它甚至有一半是对的：这个系统确实在调 API，也确实在拼 prompt。问题在于，**你花力气最多的那部分，恰好是面试场上最不容易被"听见"的部分**：

- 你用 `CompletableFuture` 而不是 MQ，因为结果必须到齐才能仲裁——**这是架构判断，不是 API 调用**。
- 你把置信度校准的接线点收敛在"落库咽喉"，让新增入口零改动就能被学习——**这是扩展点设计，不是 API 调用**。
- 你为了让 `docker build` 在只有 Docker 的机器上跑通，把镜像改成多阶段——**这是交付能力，不是 API 调用**。
- 你把"误报率"从一个只能手算的数，变成一条能被 SQL 查出来的链路——**这是度量能力，不是 API 调用**。

**这些全部在代码里，但没有一句话在"自我介绍"里。**

而这正是本讲要解决的问题：**从"我做了什么"翻译成"我在哪一层做过决定"。**

不过还有一个更麻烦的痛点，它比上面这个更隐蔽。

### 你的手册会腐烂，而你照着手册讲

这个项目里有一份 `docs/interview-walkthrough.md`，615 行，覆盖从端到端主链路到 15 个深挖问答，**每一条结论都带 `文件:行号`**。它存在的原因，正是为了防"讲不出细节"。

但它有一个致命假设：**写它的时候是对的，讲它的时候还是对的。**

在任何长期维护的仓库里，这个假设都不成立。为了让本讲不是空谈，我在动笔前把这份手册**逐条实测**了一遍。结果：

|---|---|---|---|

| 代码规模 **16,150 行 / 199 个 Java 文件** | 手册 `:18` | **221 个文件 / 22,784 物理行** | ❌ 滞后 |
| grep `$SRC/core/feedback/FileFeedbackStore.java` | 手册 `:567` | **该文件已不存在** | ❌ 失效 |

**五条里五条对不上。** 而这五条，都是面试官**当场就能打开仓库验证**的种类。

最坏会发生什么？你正说到"我们测试很全，296 例"，面试官共享屏幕，`mvn test` 跑出 338。你没说错方向，但**你失去了"这个人对自己的系统有精确掌握"这个印象**——而这个印象，是整场面试里最贵的东西。

更讽刺的是：**这份手册里专门有一节叫"附：grep 验证清单"**（手册 `:540-615`），它存在的唯一目的就是防这件事。

**它自己没被跑过。**

这和上一讲那个"闭环断在第 7 跳"是同一种病：**机制有了，执行没有。** 只不过上一讲丢的是误报率，这一讲丢的是可信度。

## 二、原理

### 2.1 面试官听的不是"系统是什么"，而是"你在哪一层做过决定"

同一个系统，可以讲出三种完全不同的水平。区别不在信息量，**在你说的话落在哪一层**：

| 层次 | 你在做的事 | 对应的高水平问句 | 本项目对应模块 |
|---|---|---|---|
| **调用方** | 把 LLM 用对 | "它挂了你会知道吗？" | 模块一（协议 / 流式 / 结构化 / 路由）、模块五（网关 / 成本 / 限流 / 注入） |
| **编排方** | 让多个 Agent 协作 | "它们意见冲突时听谁的？" | 模块二（单 Agent）、模块三（多 Agent） |
| **平台方** | 把 LLM 变成别人能用的基建 | "别人怎么在不改你代码的前提下扩展？" | 模块四（RAG）、模块五、模块六（存储 / 回写 / 部署） |

"调 API"这个评价，**只对应第一层的最低档**。而这三层里最容易被听见的，是**第二、三层**——因为第一层的答案在网上到处都是，第二、三层的答案只存在于你自己的取舍里。

**所以 30 秒的开场，结构必须是"先选型、后功能"。**

选型是一句可被追问的判断（"为什么不用 MQ"），功能是一句可被略过的描述（"能审 Java 代码"）。**先给面试官一个可以追问的钩子，比先给一段他记不住的功能列表有效得多。**

### 2.2 30 秒 / 3 分钟 / 10 分钟：不是"同一段话的详略"

这是最常被搞错的一点。很多人以为长版就是短版加细节——于是 10 分钟版的第 30 秒，和 30 秒版一模一样。

**正确的结构是：每一档换一种信息组织方式。**

| 档位 | 回答的问题 | 内容结构 | 失败形态 |
|---|---|---|---|
| **30 秒** | 这是个什么东西？ | 定位一句话 + **架构选型一句话** | 变成功能罗列，面试官抓不到钩子 |
| **3 分钟** | 它由哪几块构成？ | 30 秒版 + **四块能力**（每块一句"它难在哪"） | 变成 30 秒版的四倍速播放 |
| **10 分钟** | 为什么这么做？ | 3 分钟版 + **三条决策链**（每条：约束 → 备选 → 判据） | 变成模块目录朗读 |

**判据很简单：如果面试官听完 30 秒版就能问出一个好问题，它成功了；如果他只能问"然后呢"，它失败了。**

而 3 分钟版里的"四块能力"，每一块都要自带一句"它难在哪"。比如"三级降级"这个点，光说"有三级降级"没有信息量；说"**关键优化是结构化失败时复用已有的 rawResponse，不重调模型**"——这才是信息量，因为它包含了一个成本判断。

### 2.3 缺陷清单是加分项，但它有三个使用条件

手册开篇第一句就写了这个判断（手册 `:6`）：

> **L3 的缺陷清单是加分项 —— 能主动说出自己系统的毛病，比背八股文有说服力得多。**

这句话对，但它有一个前提被省略了：**主动说缺陷，只有在你能说清"当时为什么这么做、现在会怎么改"时才加分。**

否则它扣分：

| 说法 | 面试官的解读 |
|---|---|
| "这块当时没时间做" | 你在甩锅，且没有技术判断 |
| "我知道有问题，但一直没排上" | 你知道却不做，说明你分不清优先级 |
| "我原来的实现是 X，问题出在 Y，因为当时 Z 约束；如果重做我会改成 W" | **你在做工程判断** |
| "这个缺陷我留下了测试锁定，防止复发" | **你有闭环能力** |

**三个条件**：① 你主动提；② 你说清当时的约束（而不是把它描述成疏忽）；③ 你给出"现在会怎么改"，并且这个改法要具体到能被追问。

**第 ③ 条最关键。** 因为面试官接着一定会问"那你为什么当时不这么做"——**如果你答不出来，说明你现在的方案只是想当然。**

### 2.4 话术地图的保鲜机制：每一条都要能在 30 秒内自证

一份面试手册要长期可用，它的每一条**必须能被一条命令验证**。这就是手册 `附：grep 验证清单`（`:540-615`）的设计意图，也是本讲认为整份手册里**最有价值的一节**——比 15 个 Q&A 更值钱。

理由：**Q&A 是你对系统的理解，grep 清单是你对理解的校验。前者可以自我欺骗，后者不行。**

一条好的自证锚点长这样：

```bash
# P0-3 修复验证：校准闭环已接线（mark 方法现在有真实调用方了）
grep -n "implements FeedbackListener" $SRC/core/calibration/ConfidenceCalibrationService.java
grep -n "onFeedback" $SRC/core/calibration/ConfidenceCalibrationService.java
grep -n "MIN_ACCURACY" $SRC/core/calibration/ConfidenceCalibrationService.java
```

它同时满足三个条件：**命令能跑、输出非空、输出内容与你的说法一一对应**。

对照一下失效的那条（手册 `:567`）：

```bash
grep -n "listener.onFeedback" $SRC/core/feedback/FileFeedbackStore.java
```

**它跑不出任何东西，因为 `FileFeedbackStore` 这个类已经不存在了。**

### 2.5 为什么"手册腐烂"这件事难以被发现

因为它失败时**不报错**：

1. **没人跑它。** grep 清单写在文档里，而文档不在 CI 里。`DeadCodeGuardTest` 会拦住"生产零引用的类型"，但拦不住"文档里引用了一个不存在的类"。
2. **跑的人不会读输出。** grep 一个不存在的文件，shell 报 `No such file or directory`，然后你的眼睛自动略过——**你在找的是"有没有输出"，不是"输出是不是对的"**。
3. **行号漂移尤其阴险。** 类名漂移会让 grep 零输出（可见）；**行号漂移会让 grep 出正确的类、错误的行**——你看到类名对了就放心了，后面显示的代码不是你要讲的那段，你也不会细看。
4. **最重要的原因**：手册的"作者"和"读者"是同一个人。**你不会去质疑一份自己写的、自己看得懂的东西。** 上一讲那本"季度复盘答不出误报率"是同一个结构——**只有第三人称视角才能发现它。**

## 三、代码

### 3.1 一页纸：先选型，后数字

手册第 0 节叫"一页纸速览"（`:10-27`）。它的结构值得单独看：

```markdown
## 0. 一页纸速览

**一句话定位**：一个**多 Agent 协同**的代码审查引擎。一个 PR 进来，5 个专业 Agent
并行审查，结果经去重 / 冲突仲裁 / 误报抑制后回写成 Gitea 评论；全程 traceId 串联，
轨迹落 JSONL 可回放。

**关键数字**（表格：代码规模 / 内置 Agent / 两个线程池 / 单 Agent 超时 /
LLM 框架 / 自建基座 / 测试数）

**架构选型一句话总结**：**请求-响应模型 + 星型并行 + 全量汇聚**，不是事件流、
不是流水线、不是 DAG。这个选择决定了后面所有的设计（为什么用 CompletableFuture
而不是 MQ，为什么要仲裁，为什么超时这么难做对）。
```

**这三段的信息密度是递减的**——这是它能撑住 30 秒版的原因：

1. 第一段是**定位**：给面试官一个坐标系（多 Agent / 代码审查 / 星型）。
2. 第二段是**数字**：给面试官一个规模感（但这些数字会腐烂，见 3.4）。
3. 第三段是**钩子**：明确写出"这个选择决定了后面所有的设计"，并点名三个后果。

**第三段是整页最值钱的一句。** 它做了一件很高级的事：**主动告诉面试官"你应该往这里追问"**。面试官顺着这句话问"为什么不用 MQ"，你就进入了自己准备最充分、也最能体现水平的区域——**你把自己最强的那一问答成了面试官自己想问的问题。**

> **一个可复用的写法**：在自我介绍的最后一句，放一个"这句话决定了后面的 X、Y、Z"。**面试官不需要你在 30 秒里讲完所有东西，他需要知道往哪儿挖。**

### 3.2 15 个问答的三层分工

手册第 9 节是主体，分三层（`:436-500`）：

| 层 | 数量 | 标题里的定位 | 它实际在测什么 |
|---|---|---|---|
| **L1 必答** | Q1–Q4 | "概念与选型" | 你的**判断有没有依据** |
| **L2 深挖** | Q5–Q10 | "权衡与细节" | 你的**系统有没有边界** |
| **L3 压力** | Q11–Q15 | "缺陷与改进" | 你的**认知有没有诚实** |

这三层的差别不是难度，是**面试官想确认的东西不同**：

- **L1 只关心"你是不是真的做过"**。所以 L1 的答案要有"一句话结论 + 三个理由"的形状。看 Q1 的答案（`:441`）——先给结论"三个理由"，再逐条给：① 调用模型是请求-响应不是事件流；② 结果必须全量到齐才有意义，`allOf` 是现成屏障；③ traceId 跨线程传播只要一行，跨进程要序列化重建。**最后还有一句"真正该换 MQ 的时机是……现在一条都不成立"**——这句是在证明"我不是不会用 MQ，是判断不该用"。
- **L2 只关心"边界在哪"**。所以 L2 的答案要主动给出**当时不覆盖的情况**。看 Q6 的答案（`:458`）——讲完 diff 字符预算之后，末尾自己加了一句"**可继续讲的演进**：按 diff 行数分档，超阈值时优先保留『被改方法的完整实现 + 调用链一跳』"。这句是承认"现在的方案只解决了总量问题，没解决优先级问题"。
- **L3 只关心"你会不会骗自己"**。所以 L3 的答案要包含**你主动划出来的诚实边界**。看 Q12 的答案（`:482`）末尾——"**诚实的边界**：Java 的 `CompletableFuture.cancel(true)` 不会中断已开始的线程，所以验收点是『不卡主线程 + 降级可见』，不是『线程被中断』"。

**★ L3 里那句"不是"是整个手册里最专业的一句话。** 它把"我做到了 A"改写成"我做到了 A，没有做到 B，而且我知道 B 在 Java 里做不到"。**主动缩窄自己的功劳，比扩大它更能建立信任。**

### 3.3 三条"缺陷 → 加分项"的完整故事线

手册 L3 里的 Q12/Q13/Q14 是三个 P0 缺陷，它们的答案结构**完全一致**，这是一套可以搬走的模板：

```
① 发现   ——  原来的写法是什么，它为什么看起来是对的
② 为什么危险 —— 如果不修，最坏会发生什么（关键：说清"最坏"为什么难以发现）
③ 修复的取舍 —— 为什么选这个修法，放弃了什么
④ 验证的证据 —— 哪个测试、多少个用例、断言了什么
⑤ 诚实的边界 —— 这个修复没解决什么
```

**逐条看这三条故事线：**

**Q12 · `orTimeout` 挂错位置（手册 `:479-482`）**

| 段 | 手册里的内容 |
|---|---|
| ① 发现 | "它原来挂在 `allOf` 返回的聚合 future 上，只产生一条 warn，不会完成或取消任何单个 future，后面 `join()` 仍然无限阻塞" |
| ② 危险 | 超时"看起来生效了"——因为**日志里确实有一条 warn**。这是最难查的形态：**机制报了警，但机制本身失效** |
| ③ 取舍 | 改成"收集阶段对每个 future 逐个 `get(remaining, MILLISECONDS)` 带超时取（共享 deadline 递减）"，并把超时转成 `AgentResult.degraded` 进报告 |
| ④ 验证 | `CoordinatorTimeoutDegradationTest` 4 例（**本讲实测 `@Test` 计数 = 4，一致**）|
| ⑤ 边界 | "`cancel(true)` 不会中断已开始的线程，所以验收点是『不卡主线程 + 降级可见』" |

**Q13 · 模型全挂返回空串（手册 `:484-488`）**

| 段 | 手册里的内容 |
|---|---|
| ① 发现 | "原来返回空串 `""` 且不抛异常。上层会把它解析成『0 条发现』，最终产生一份『看起来通过』的报告" |
| ② 危险 | **手册的原话是"这是最危险的一个降级 —— 静默失败比报错更糟"**。方向是对的：一份"看起来通过"的安全报告，比一份报错的报告危险得多 |
| ③ 取舍 | 两步：先抛 `ModelUnavailableException`，然后**在 2026-09-03 把 Mock 整类删掉**——`MockProvider`/`MockLlmClient`/`NoOpChatModel` 三个假模型类删除，未配 Key 时**拒绝启动**（fail-fast） |
| ④ 验证 | `ModelGatewayDegradationTest` 4 例（**实测一致**）|
| ⑤ 边界 | 手册写了"Mock 从演示期的权宜变成了正确性事故源，所以整类删掉而不是留开关"——**这句是"取舍"而不是"边界"，但它给出了同一个判据：不留开关** |

**Q14 · 校准空转（手册 `:490-495`）**

| 段 | 手册里的内容 |
|---|---|
| ① 发现 | `calibrate()` 确实被调用，但 `ruleAccuracy` 只能由 `markFalsePositive`/`markTruePositive` 写入，**这两个方法全仓零调用方** → `getOrDefault(ruleId, 1.0)` 恒返回 1.0 → `calibrate` 退化成"乘 1.0"的恒等函数 |
| ② 危险 | **手册的总结句**："代码跑通了、测试绿了、功能看起来有了，但数据链路断在一半，实际效果为零。" |
| ③ 取舍 | 新增 `FeedbackListener` SPI，在 `save` 末尾广播——"**接线点收敛在落库咽喉，入口扩展零改动**" |
| ④ 验证 | `CalibrationFeedbackLoopTest` 8 例（**实测一致**）|
| ⑤ 边界 | 手册提到"防一票否决：误报指数衰减有下限 `MIN_ACCURACY=0.5`"——**这正是第 40 讲算过的那条曲线**（首次落 0.8、6 次到 0.5、正报 15 次才回满） |

**三个故事的共同结构，就是它们的说服力来源**：每一个都是"**机制存在、测试通过、但实际效果为零**"。

> **这是一句值得直接背下来的话**：**"这个 bug 的特征是——所有测试都是绿的。"**
>
> 它同时说明了三件事：你有发现它的眼光、你理解为什么常规手段抓不到它、你把测试补上了。**这是 Agent 工程最核心的一类风险，也是这一整套专栏 42 讲里反复出现的形状**（第 17 讲的内存指标无出口、第 39 讲的 `APPLY` 模式配了却不生效、第 40 讲的第 7 跳断链）。

**★ 一处必须自己复核的数字**：手册 `:536` 的 10 分钟版说"用 **21 例**测试锁定（`CoordinatorTimeoutDegradationTest` / `ModelGatewayDegradationTest` / `CalibrationFeedbackLoopTest` / `ReportDegradationTest`）"。

本讲把四个类的 `@Test` 逐个数了一遍：**4 + 4 + 8 + 5 = 21**。✅ **这个数字是对的**，而且它写在手册里、能被当场 `grep -c` 验证——**它和 3.4 节那五个失效项正好形成对照：同样写在手册里，一个能自证，五个不能。**

### 3.4 ★ 手册的五处失效（全部实测）

现在是本讲最硬的一段。手册的毛病不是"写得不好"——它写得很好。它的毛病是**它没有保鲜机制的执行者**。

先看两处**数字**：

```bash
# ① 测试数：手册说 296 例
$ ls target/surefire-reports/*.txt | wc -l
67
$ grep -h "Tests run:" target/surefire-reports/*.txt | <聚合>
Tests run: 338, Failures: 0, Errors: 0, Skipped: 0
```

**真值 338 例 / 67 类。** 手册（`:25`）写"296 例（281 基线 + 15 例本轮治理新增；含 P0 修复 21 例）"——**它的括号里甚至写了构成，唯独总数是旧的**。这比单纯写错更麻烦：**结构看起来是可核对的，只有结论是过期的。**

> 顺带一提，别用 `grep -c "@Test"` 替代 surefire 输出：本讲实测它数出 **342**，因为注解可能被注释掉、也可能有参数化/继承带来的不等价。**要看"执行了多少"，只能看 surefire。**

```bash
# ② 代码规模：手册说 16,150 行 / 199 个 Java 文件
$ find src/main/java -name "*.java" | wc -l
221
$ find src/main/java -name "*.java" -exec cat {} + | wc -l
22784
$ find src/main/java -name "*.java" -exec cat {} + | grep -cv "^\s*$"
20512
```

**真值 221 个文件 / 22,784 物理行（非空 20,512）。** 手册（`:18`）写"16,150 行 / 199 个 Java 文件"。

> **诚实边界**：`16,150` 与哪个口径都不完全吻合（物理行 22,784、非空行 20,512、粗剔注释后约 14,662）。**无法判断它当初用的是哪种统计方式**，因此本讲只断言"**与今日任何一种口径都对不上**"，不断言它当时算错了。**这个区别很重要——面试时如果面试官问"你这 199 个文件怎么数的"，你要能说清你的口径，而不是猜他想要哪个。**

再看**三处锚点**：

```bash
# ③ 手册 :567 的自证命令
$ grep -n "listener.onFeedback" $SRC/core/feedback/FileFeedbackStore.java
# → 该文件不存在
$ ls $SRC/core/feedback/
FeedbackListener.java  FeedbackStore.java  InMemoryFeedbackStore.java
```

**`FileFeedbackStore` 这个类已经不存在了。** 反馈存储现在有两个实现：生产是 `core/store/PgFeedbackStore`（装配点 `StateStoreConfig.java:79`），测试/无盘环境是 `core/feedback/InMemoryFeedbackStore`（装配点 `StateStoreConfig.java:132`）。

**而残留的引用不止在文档里**：

```java
// core/feedback/InMemoryFeedbackStore.java（类注释，实测）
 * <p>进程重启后数据不保留；生产环境请使用 {@link FileFeedbackStore} 持久化。

// core/feedback/FeedbackStore.java:11（接口注释，实测）
 * 用于抑制重复误报。实现可基于本地文件（{@code FileFeedbackStore}）或内存
```

两处都在指向一个**不存在的类**。区别是：`{@link}` 是**编译期**产物（javadoc 会报错，`mvn javadoc:javadoc` 能抓到），`{@code}` 只是文本，**永远不会报错**。

**这就解释了为什么它能活到被本讲发现**：`{@code}` 里的类名，是一种**看起来像注释、实际是文档承诺**的东西。它既不受编译检查，也不受测试检查。

```bash
# ④ 手册 :22 说单 Agent 超时在 CompletableFutureCoordinator.java:76,375-405
$ sed -n '79,80p' $SRC/core/coordinator/impl/CompletableFutureCoordinator.java
    @Value("${review.agent.timeout-ms:300000}")
    private long timeoutMillis = 300_000L;
$ grep -n "deadline" $SRC/core/coordinator/impl/CompletableFutureCoordinator.java | head -1
477:        long deadline = System.currentTimeMillis() + Math.max(1L, timeoutMillis);
```

- **超时值**：真值 `:79-80`（手册写 `:76`）。
- **限时逻辑**：真值 `:477` 起（手册写 `:375-405`）。

**超时值 300000ms 是对的，类名是对的——只有行号错了。**

> **这正是 2.5 节说的"行号漂移尤其阴险"**：如果面试官按 `:76` 去看，他会看到一行别的代码；但因为类名对上了、300000 这个数字你也说对了，**他会以为自己看错了行**。**行号漂移不会让人质疑你，它会让人质疑自己** —— 这比直接报错更消耗你的可信度，因为对方不会当场指出，只会在心里降低对你的评价。

```bash
# ⑤ 手册 :19 说五个内置 Agent 在 ReviewAgentConfig.java:404,410
$ sed -n '404p;410p' $SRC/config/ReviewAgentConfig.java
    public InjectionDetector injectionDetector() {          # :404
 *                                                          # :410（javadoc 空行）
$ grep -n "public SecurityAgent securityAgent" $SRC/config/ReviewAgentConfig.java
512:    public SecurityAgent securityAgent(LlmClient llmClient,
$ grep -n "public List<ReviewAgent> reviewAgents" $SRC/config/ReviewAgentConfig.java
559:    public List<ReviewAgent> reviewAgents(SecurityAgent securityAgent,
```

**真值**：五个 Agent 的 `@Bean` 在 `:512`（Security）/`:522`（Logic）/`:531`（Performance）/`:540`（Style）/`:549`（Architecture），汇总列表在 `:559`。手册写的 `:404,410` 现在分别是 `injectionDetector()` 的声明和一段 javadoc。

**★ 五处失效的共同点，是这一节真正想说的东西：**

| 失效项 | 失效形态 | 为什么没被发现 |
|---|---|---|
| 296 → 338 | 数字过期 | 括号里写了构成，**看起来是可核对的** |
| 16,150 → 22,784 | 数字过期 | 没有"构成"可对照，**只能重数** |
| `FileFeedbackStore` | 锚点指向已删除的类型 | grep 零输出，**被当成"没匹配到"而不是"文件没了"** |
| `:76,375-405` | 行号漂移 | 类名与数值都对，**读者怀疑自己** |
| `:404,410` | 行号漂移 | 同上 |

**五种失效，没有一种会让任何测试变红。** 而这五处，恰恰是面试官最容易当场验证的五处。

**还有第六处，但它是另一个类别——不是过期，是写错：**

手册第 6 行（使用说明）写的是"**再按第 8 节的 L1/L2/L3 分级准备**"。而 L1/L2/L3 在**第 9 节**：

```bash
$ sed -n '405p;436p' docs/interview-walkthrough.md
## 8. 可观测性：traceId 全链路
## 9. 面试深挖 Q&A
```

**第 8 节是"可观测性"，L1/L2/L3 在第 9 节。** 也就是说，这份手册的第一句话——"告诉读者怎么用它"的那句话——**把读者指向了一个不含 Q&A 的章节**。

它和前五处的差别值得单独说：

| | 前五处 | 第六处 |
|---|---|---|
| 性质 | **过期**（写的时候对，现在不对） | **写错**（写的时候就不对） |
| 发现方式 | 需要外部真值比对（跑 surefire、重数文件、跑 grep） | **只需要通读一遍** |
| 为什么没被发现 | 需要"跑一遍"的成本 | **需要"读一遍"的成本——而作者是唯一读者** |

**这正是 2.5 节第 4 条说的："你不会去质疑一份自己写的、自己看得懂的东西。"** 前五处还能靠"定期跑脚本"防（动手任务第 3 步），**第六处只能靠"换一双眼睛读一遍"** —— 审稿、peer review、或者**把它当别人的文档读一遍**。这是整份手册里最便宜、也最容易被跳过的一道工序。

### 3.5 追问映射：面试官会往哪儿追

手册给的是"答案"，但面试现场是"追问树"。**准备答案的人只准备了第一层，准备追问树的人能扛住三层。**

从手册的 15 个问答里，每条答案都留了一个**明确的追问出口**。把它显式写出来，就是一张追问映射表：

| 你答的是 | 面试官大概率追 | 你的落点应该是 |
|---|---|---|
| Q1 "用 CompletableFuture 不用 MQ" | "那如果 QPS 涨 100 倍呢" | 手册已经埋了答案：**"要横向扩容、要跨语言 Agent、要削峰排队、要改成异步通知"** —— 逐条说明"现在一条都不成立"，但承认"任何一条成立就该换" |
| Q2 "星型汇聚，Agent 之间不通信" | "不通信怎么保证一致性" / "那要 Agent 干什么" | 关键句：**"协作发生在聚合阶段而不是执行阶段"**。不要退让成"其实它们也有点协作" |
| Q5 "`supports()` 内容准入" | "那纯文档 PR 只有 1 个 Agent，是不是漏检" | 手册的答案是**有意的**："只留 Security（注入防护对任意内容都有价值）"。要能说出"为什么是 Security 而不是随便留一个" |
| Q6 "diff 字符预算" | "截断了不怕漏掉问题吗" | 关键设计：**末尾标注"X 个文件完整 / Y 个文件截断，请基于片段审查"** —— **"模型知道 diff 不完整，不会把截断误判成没有变更"**。这是"把不确定性显式传给模型"的范例 |
| Q7 "断点续跑生效了" | "那 headSha 变了怎么办" | 手册已答：**键含 head SHA，换新 commit 会重开审查而不是续跑旧半成品**；并且这是**断点 / 历史判重 / webhook 判重三处同源** |
| Q10 "embedding 维度已锁 1024" | "为什么这就不会错" | 手册的答案是**机制而非巧合**："启动即毁数据级别，所以用 fail-fast 注释 + profile 统一锁死，**而不是靠 profile 碰巧对齐**" |
| Q15 "怎么演进到分布式" | "那你为什么不现在就做" | 手册给了三条路，**但没给"为什么现在不做"** —— 这是**你自己要补的一句**："review 是全量汇聚模型，加消费者前得先解决同一个 PR 的结果怎么汇聚，这个成本现在换不来收益" |

**★ 这张表的用法不是背，是自检**：拿你现在准备的每一条答案，问自己"**如果对方追一步，我有没有下一句**"。有下一句的保留，没有的**要么补上，要么从话术里删掉**——**半截答案比不提更伤**。

### 3.6 反问清单：面试是双向的

手册没有这一节，但方案里第 41 讲明确要"**项目讲述脚本 + 追问映射 + 反问清单**"。补上这一节，因为**反问的质量直接决定你能不能判断这个岗位是不是真的在做 Agent**。

四个能分辨真假的反问（**按"对方的回答能不能证伪"来设计**）：

| 反问 | 真做 Agent 的团队会怎么答 | 只是在套壳/试水的团队会怎么答 |
|---|---|---|
| **"你们线上失败率是多少，是怎么归因的？"** | 会给出具体分层（模型侧 / 工具侧 / 编排侧），并提到 traceId 或等价手段 | "我们模型比较稳定"——**没有失败归因 = 没有生产** |
| **"同一个请求重放，结果一样吗？不一致时你们怎么处理？"** | 会区分"要确定性"和"要多样性"的场景，并提到幂等键或缓存 | "大模型本来就不确定"——**把它当借口而不是问题** |
| **"你们的评测是怎么做的？"** | 会说人工反馈闭环、离线评测集、或者影子回放 | "我们看线上效果"——**没有度量** |
| **"成本怎么控的？"** | 会说档位路由、预算熔断、缓存 | "用量不大，还没管"——**没到过规模** |

**判据**：好的反问能把你自己的经验变成一把尺子。**你问的不是信息，是"你们有没有遇到过我遇到过的那些问题"**——遇到过，说明这是个真战场；没遇到过，说明这里暂时是绿洲，但也可能只是还没到规模。

### 3.7 一页纸之外：这 42 讲本身就是最大的答案库

手册有 15 个问答。**这本书有 42 讲。**

两者的关系值得说清：**手册是"面试时怎么讲"，本书是"被追问时怎么答"。**

- 面试官问"为什么不用 MQ" → 手册 Q1 给一句话，**本书第 15 讲给完整的拓扑权衡**。
- 面试官问"超时为什么难做对" → 手册 Q12 讲故事，**本书第 17 讲给逐 Future 限时的完整实现**。
- 面试官问"注入怎么防" → 手册 Q9 讲三层次，**本书第 35 讲给三个边界的完整对照表**。
- 面试官问"存储怎么选" → 手册没覆盖，**本书第 37 讲整讲在讲"为什么不做自动降级"**。

**所以准备面试最省力的路径不是背手册，而是：把 42 讲的每一讲，压缩成一个"如果被问到，我用哪一句开场"的索引。**

这件事的判据是：**你能不能在 10 秒内说出一讲的核心判据句。**

举几个例子（都来自本书前 40 讲的正文）：

| 讲 | 判据句（10 秒版） |
|---|---|
| 03 | "模型给的 JSON 键名是 snake_case，Kotlin/Java 习惯是 camelCase——同一个字段，两种写法，静默丢失。" |
| 20 | "不该给模型看的内容，不要让它进了上下文再过滤——**在准入阶段就剔除**。" |
| 27 | "`similarity` 必须是真实余弦；RRF 归一化排名分只做融合排序，**绝不参与阈值判断**。" |
| 37 | "回退的触发条件必须是配置，不能是故障。**存储不是可选依赖，它定义了你的系统是什么。**" |
| 40 | "降噪不得覆盖底线，**顺序即优先级**。" |

**这五句话，没有一句是"我们用了什么技术"，每一句都是"我做了什么判断"。** 这就是 2.1 节那三层视角的落点。

## 四、避坑清单

- [ ] **开场先给选型，再给功能。** 判据：30 秒版结束后，面试官能不能问出一个具体的技术问题。只能问"然后呢"就是失败。
- [ ] **在自我介绍的最后一句留钩子。** 句式："这个选择决定了后面的 X、Y、Z。" 主动告诉对方往哪儿追问，**把它变成"他想问的问题"**。
- [ ] **三档讲法要换结构，不是换详略。** 30 秒 = 定位 + 选型；3 分钟 = + 四块能力（每块带"它难在哪"）；10 分钟 = + 三条决策链（约束 → 备选 → 判据）。
- [ ] **缺陷只用"发现 / 危险 / 取舍 / 证据 / 边界"五段式讲。** 缺"取舍"会被当成疏忽，缺"边界"会被当成自夸。
- [ ] **主动缩窄自己的功劳。** 说出"我做到了 A，**但不是 B**，因为 B 在 Java 里做不到"——**这比扩大 A 更能建立信任**。
- [ ] **每条话术都要能在 30 秒内自证。** 一条锚点的三个条件：命令能跑、输出非空、输出内容与说法一一对应。
- [ ] **文档里的自证命令，必须进 CI。** 写在文档里的 grep 没人跑；跑不出来的 grep 和没写等价。**最低成本的做法**：把这些命令收进一个 `verify-doc-anchors.sh`，让 CI 跑，**任何一条零输出即失败**。
- [ ] **警惕"行号漂移"比"类名漂移"更伤**：类名漂移会 grep 零输出（可见），行号漂移会让你看到"类名对、内容不对"，**读者会怀疑自己而不是怀疑文档**。所以锚点优先写**类名 + 方法名 + 关键字**，行号只作辅助。
- [ ] **`{@code ...}` 和 `{@link ...}` 里的类名是真的文档承诺。** `{@link}` 至少 javadoc 会报错，`{@code}` 永远不会——**删类时全局 grep 类名，别只 grep 代码引用**。
- [ ] **会随提交变化的数字，不要在文档里写死。** 要么从源头取（surefire），要么标注"截至某次 commit"。**尤其警惕"总数过期但构成看起来可核对"的写法**——它比纯粹写错更能骗过读者（包括三个月后的你）。
- [ ] **别用 `grep -c "@Test"` 当测试数。** 注解可能被注释、可能参数化。**执行数只信 surefire 输出。**
- [ ] **准备"追问树"，不是"答案"。** 自检方法：拿每一条答案问"如果对方追一步，我有没有下一句"。**没有下一句的答案，要么补上，要么删掉——半截答案比不提更伤。**
- [ ] **反问要按"对方的回答能不能证伪"来设计。** 问"你们失败了怎么归因"而不是问"你们用什么模型"——**前者能分辨真假，后者只能得到宣传**。
- [ ] **面试前跑一遍全部锚点**，并且**逐条读输出**（不是只看"有没有输出"）。这一步花 15 分钟，能避免一场面试里最贵的那种损失。
- [ ] **把 42 讲压成索引**：每一讲准备一句"10 秒判据句"。**判据句里不应该出现技术名词，只应该出现判断。**

## 五、动手任务

>
> 具体动作（四步，每步都能单独验证）：
>
> 1. **修掉本讲实测出的五处失效**：① 测试数 296 → 从 surefire 取；② 代码规模 → 重数并**写清口径**（物理行还是非空行）；③ `$SRC/core/feedback/FileFeedbackStore.java` → 改用 `$SRC/core/store/PgFeedbackStore.java` 或 `InMemoryFeedbackStore.java`；④ 超时锚点 → 改为 `CompletableFutureCoordinator.java:79-80`（值）+ 按方法名定位（`deadline`）；⑤ 五 Agent 锚点 → 改为 `ReviewAgentConfig.java:512-554`（各 `@Bean`）+ `:559`（`reviewAgents`）。
> 2. **顺手修掉两处指向不存在类型的注释**：`InMemoryFeedbackStore` 类注释里的 `{@link FileFeedbackStore}`、`FeedbackStore.java:11` 的 `{@code FileFeedbackStore}`。**前者会让 `mvn javadoc:javadoc` 报错——这是个免费的 CI 检查项。**
> 3. **把 `附：grep 验证清单` 落成一个脚本**：`scripts/verify-doc-anchors.sh`，把手册里那批 `grep`/`ls`/`sed` 全部搬进去，**每条命令断言"输出非空"**（对"应该无输出"的条目断言"输出为空"），末尾汇总通过/失败条数。
> 4. **给手册加一个"最后核对时间 + 提交 SHA"的头**：在文档第 3 行的 `>` 引用块里加一行 `> 最后核对：<commit> @ <date>，锚点已由 scripts/verify-doc-anchors.sh 校验`。**让"过期"这件事有一个可见的年龄。**
>
> **预期结果（都能自证）：**
> - **第 1、2 步之后**：`grep -rn "FileFeedbackStore" src/ docs/` → **在 `src/` 下零命中**（只剩 `docs/` 里的历史叙述，如果有的话，要一并改）；`mvn javadoc:javadoc` → **不再有 "reference not found" 类警告**。
> - **第 3 步之后**：`bash scripts/verify-doc-anchors.sh; echo $?` → **输出 `0` 且打印"全部 N 条锚点通过"**；然后**故意把手册里的 `:79-80` 改成 `:76`**，重跑 → **脚本应报失败并指出是哪一条**（这一步是在验证脚本本身有效，不是在验证手册）。
> - **第 4 步之后**：新同事 clone 仓库后打开手册，**第一眼就能看到"这份东西多久没核过了"**。
>
> **加分项 A（真正的门禁）**：把 `verify-doc-anchors.sh` 挂进 CI（和 `DeadCodeGuardTest` 同一层），**任何一条锚点失效就让构建失败**。这样"文档腐烂"就从"难以发现"变成了"必须当场修"——**第 40 讲的门禁思想，在这里第二次复用**。
>
> **加分项 B（把失效变成度量）**：在脚本里输出每条锚点的"存活状态"，并记录每次 CI 运行时失效条数。**趋势比单次结果有用**：如果失效条数每周增长，说明这个仓库的改动速度已经超过了文档的维护能力，**该考虑的不是"更勤快地改文档"，而是"少写容易腐烂的锚点"（多用方法名/关键字，少用行号）**。

## 本讲小结

1. **"所以你就是调了个 API"这句话之所以能伤人，是因为你讲的是"功能"，而面试官在听"判断"。** 同一个系统要分三层讲：**调用方**（把 LLM 用对）、**编排方**（让多 Agent 协作）、**平台方**（把 LLM 变成别人能用的基建）。"调 API"只对应最低档。
2. **开场必须"先选型、后功能"。** 功能列表面试官记不住，选型判断他会追问。**在最强的答案上留钩子**——句式是"这个选择决定了后面的 X、Y、Z"，把面试官最该问的问题变成他自己想问的。
3. **30 秒 / 3 分钟 / 10 分钟是三种信息结构，不是同一段话的详略。** 30 秒 = 定位 + 选型；3 分钟 = + 四块能力（**每块自带"它难在哪"**）；10 分钟 = + 三条决策链（**约束 → 备选 → 判据**）。判据：听完 30 秒版，对方能不能问出一个具体的技术问题。
4. **15 个问答分三层，测的东西不同**：L1 测"你判断有没有依据"，L2 测"你系统有没有边界"，L3 测"你认知有没有诚实"。**L3 的答案里必须包含你主动划出的诚实边界**——手册 Q12 那句"验收点是『不卡主线程 + 降级可见』，**不是『线程被中断』**"是整份手册最专业的一句。
5. **缺陷 → 加分项的五段式模板**：**发现 → 为什么危险 → 修复的取舍 → 验证的证据 → 诚实的边界**。缺"取舍"会被当成疏忽，缺"边界"会被当成自夸。
6. **三个 P0 故事（`orTimeout` / 空串降级 / 校准空转）的共同结构是它们的说服力来源**：每一个都是"**机制存在、测试通过、但实际效果为零**"。**一句话可以背下来："这个 bug 的特征是——所有测试都是绿的。"**
7. **★ 手册会腐烂，而且五种失效没有一种会让测试变红。** 本讲实测出五处：测试数 **296 → 338**、代码规模 **16,150 行/199 文件 → 22,784 物理行/221 文件**、锚点 **grep `FileFeedbackStore`（类已删除）**、超时行号 **`:76,375-405` → `:79-80`/`:477`**、五 Agent 行号 **`:404,410` → `:512-554`/`:559`**。
8. **★ 行号漂移比类名漂移更伤**：类名漂移会 grep 零输出（**可见**）；行号漂移会让你看到"类名对、内容不对"，**读者会怀疑自己而不是怀疑文档**——对方不会当场指出，只会在心里降低评价。**所以锚点优先写类名 + 方法名 + 关键字，行号只作辅助。**
9. **手册自己有一节 `附：grep 验证清单`，它存在的唯一目的就是防这件事——而它自己没被跑过。** 这与第 40 讲"闭环断在第 7 跳"是同一种病：**机制有了，执行没有。** 只不过上一讲丢的是误报率，这一讲丢的是可信度。
10. **反直觉的一处对照**：手册里"21 例"（`4 + 4 + 8 + 5`）是**能自证且实测正确**的，而测试总数、代码规模这些"看起来更基础"的数字全是错的。**说明"数字对不对"与"数字重不重要"无关，只与"有没有人核过"有关。**
11. **`{@code}` 里的类名是永远不会报错的文档承诺**（`{@link}` 至少 javadoc 会报错）。删类时**全局 grep 类名，别只 grep 代码引用**——本项目里 `InMemoryFeedbackStore` 与 `FeedbackStore` 的注释都还在指向已删除的 `FileFeedbackStore`。
12. **准备"追问树"，不是"答案"。** 自检：拿每条答案问"如果对方追一步，我有没有下一句"。**没有下一句的答案要么补上，要么删掉——半截答案比不提更伤。**
13. **反问要按"对方的回答能不能证伪"设计。** 问"你们失败了怎么归因"能分辨真假，问"你们用什么模型"只能得到宣传。
14. **最省力的准备路径：把 42 讲压成一个索引，每一讲一句"10 秒判据句"。** 判据句里**不应该出现技术名词，只应该出现判断**——例如第 37 讲的"回退的触发条件必须是配置，不能是故障"、第 40 讲的"降噪不得覆盖底线，顺序即优先级"。
15. **手册是"面试时怎么讲"，本书是"被追问时怎么答"。** 手册 15 个问答是树的根，42 讲是每一根枝叶能展开的深度——**而这一讲教你的是怎么让这棵树每年都还能用。**
