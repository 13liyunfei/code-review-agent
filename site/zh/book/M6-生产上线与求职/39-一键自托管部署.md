## 一、痛点

README 里写得很清楚，本地起环境有两条路：

> **方式 B：任意装 Docker 的机器** —— 基础设施用 compose，引擎用 maven 起
>
> ```bash
> cd dev && docker compose -f docker-compose.dev.yml up -d   # PG17+pgvector / Redis / Gitea
> cd .. && ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
> ```

"任何装了 Docker 的机器都能一键起"——这句话是写给**别人**的，所以它得真的成立。

我拿一台干净机器试了一次。compose 起来了，三个容器都 `healthy`。然后：

```
org.postgresql.util.PSQLException: FATAL: password authentication failed for user "yunfei"
```

**因为 compose 起的 PostgreSQL，用户叫 `postgres`、密码是 `codereview`；而应用的配置里，默认用户名是 `yunfei`。**

一个是我自己 Mac 上 Homebrew 装的 PG（`--auth=trust`，所以随便什么用户名都能连，默认值写什么都不影响）；一个是官方镜像（`scram-sha-256` 认证，用户不存在就直接拒绝）。**两条路在"用户名"这一项上，行为完全不同。**

而更麻烦的是**这条错误信息的指向**：`password authentication failed for user "yunfei"` 会让人第一反应去查密码（"我密码设错了吗？"），而不是"这个用户名是从哪来的？"——因为 `PGVECTOR_USERNAME` **从没在任何文档里出现过**，它是 `application.yml` 里一个带作者本机账号的默认值。

**这就是"一键部署"这类交付物最典型的失败方式：它不是在某个环节崩掉，它是"大部分都对、差一步"，而缺的那一步既没写在文档里，也没被任何检查拦住。**

## 二、原理

### 2.1 先把"一键部署"的验收标准写下来

"一键"这个词很容易说，但作为验收标准它是模糊的。这条线必须能自己走完，所以需要一条**可判定的**标准：

> **在一台只装了 Docker 的干净机器上，从 `git clone` 到"能收到审查报告"，只需要复制粘贴命令，不需要读源码、不需要猜配置。**

拆开就是四件事：

| # | 要求 | 反面例子 |
|---|---|---|
| 1 | **镜像能自己构建出来** | 要求宿主机先装 JDK + Maven，且 `target/` 里恰好有 jar |
| 2 | **配置有单一的、可读的入口** | 默认值写成本机值，且没有任何文档提到这个键 |
| 3 | **依赖顺序由编排保证，不靠人** | 应用先起来、PG 还没就绪 → 启动失败 |
| 4 | **每一步失败都能自己诊断** | 报错指向密码，真相是用户名 |

这四条，本讲会逐条对照本项目的现状。**其中第 3 条在第 37 讲已经埋好了前提**：`PgDb` 是 fail-fast 的——**PG 没就绪，应用就起不来**。所以"顺序"这件事不是优化，是**硬要求**。

### 2.2 镜像有两条路线，判据是"构建需要什么"

Dockerfile 有两种根本不同的模型：


<img class="mermaid-svg" src="/zh/book-assets/diag-0094.svg" alt="Dockerfile 有两种根本不同的模型：" />

> **图 39-1**　两条镜像路线。**判据只有一句**：`docker build` 能不能在一台只有 Docker 的机器上跑通？能 → B；不能 → A。**路线 A 不是"不够优雅"，它有三个具体的失败**（下一节逐个拆）。

**判据极其简单：`docker build` 能不能在一台只有 Docker 的机器上跑通？** 能，就是 B；不能，就是 A。

**路线 A 的三个代价**（不是"不够优雅"，是三个具体的失败）：

1. **`docker build .` 在干净 clone 上必然失败**。因为 `target/` 通常在 `.gitignore` 里，clone 下来没有这个目录。
2. **★ 更危险的是"它可能成功，但打进去的是旧 jar"**。如果开发者改了代码、忘了重新 `mvn package`，`docker build` **会成功**——因为 `target/` 里有个旧 jar。于是你得到一个**内容与源码不一致的镜像**，而**构建过程没有任何提示**。这条是最难发现的：`docker build` 输出全绿、镜像能启动、服务能跑、审查结果"看起来正常"。
3. **构建上下文被迫包含 `target/`**。因为 Dockerfile 要 `COPY` 它，所以 `.dockerignore` **不能**忽略它——**一个本该忽略的目录，被一个构建模型的选择留在了上下文里**（见 3.1）。

**路线 B 的代价**是镜像里多一次编译（可以用依赖层缓存摊掉）和 Dockerfile 更长。**用一点构建时间换"只有 Docker 就能构建"，这笔账在做开源交付时几乎总是划算的。**

### 2.3 构建上下文：`.dockerignore` 是"你的构建模型"的自白

`.dockerignore` 看起来是个边角配置，其实它**精确地暴露了你走的是哪条路线**：

- 忽略 `target/` → 你不需要宿主机的产物 → **路线 B**
- **保留 `target/`**（还得写注释解释） → 你必须 `COPY` 它 → **路线 A**

本项目两个仓库正好各一个，方向相反（见 3.1）。而这里有一个量化问题常被忽略：**构建上下文是要交给构建器的**。忽略清单漏一个大目录，每次构建都要为它付传输/扫描成本，而它可能根本不在 `COPY` 的目标里。

### 2.4 容器里的三个默认值，必须显式表态

把一个 JVM 应用塞进容器，有三个"默认值"是错的或至少是需要决定的：

| 项 | 裸跑的默认 | 为什么必须处理 |
|---|---|---|
| **用户** | `root`（`eclipse-temurin` 等基础镜像默认 root） | 容器被突破 = 直接拿到 root；挂载卷里的文件也归 root |
| **PID 1 / 信号** | JVM 就是 PID 1 | JVM 会收 `SIGTERM`（优雅停机可用 ✅），但 **PID 1 必须负责回收孤儿进程**——应用如果 fork 过子进程，僵尸会累积 |
| **内存** | 老版本 JDK 会把宿主机的内存当自己的上限 | 容器内存限制 512MB、JVM 以为有 8GB → OOMKilled |

这三项**都不是"加了更好"**，而是各有一个具体的故障模式。其中前两项在本项目里有一个**很具体的对照物**（见 3.4），因为另一个仓库把它们都处理了。

### 2.5 "能跑"与"可用"：三件容器里才会暴露的事

镜像构建成功、容器起来了，不代表功能可用。这个项目有三个只有进容器才会发现的问题：

1. **沙箱探测恒为不可用**：`SandboxProbe` 探测 `bwrap`/`firejail`/`sandbox-exec`/`docker`，而 JRE 基础镜像里一个都没有 → `sandboxAvailable=false` → 自动修复的 APPLY 被 fail-closed 拒。**这是对的行为**（第 25 讲那套 fail-closed 不变量），但**用户不该靠读日志才知道**。
2. **健康探针没有分层**：标准编排期望区分 liveness（进程活着）与 readiness（可以接流量）。没有 actuator → 只有手写的 `/health`，且它会真的去连 PG。
3. **依赖就绪顺序**：PG 未就绪 → 应用启动失败（第 37 讲的 fail-fast）→ **编排必须显式声明"等 PG healthy"**，否则启动顺序就是靠运气。

## 三、代码

### 3.1 两份 Dockerfile 与两份 `.dockerignore`

**`code-review-agent/Dockerfile`（全 23 行）：**

```dockerfile
# 多 Agent 代码审查服务 —— 生产镜像
# 构建流程：先 `./mvnw -o clean package` 生成 target/code-review-agent-*.jar，
# 再 `docker build -t code-review-agent .`
FROM eclipse-temurin:21-jre

WORKDIR /app

# 复制构建产物（由 mvn package 生成）
COPY target/code-review-agent-*.jar app.jar

# 运行时数据目录（自定义规则/历史/反馈等落盘，生产建议挂卷持久化）
VOLUME /app/data

EXPOSE 8080

# JVM：容器感知内存上限；OOM 即退出便于编排重启；G1 适合大堆与低延迟
# 生产配置通过环境变量注入（GITEA_*/TOKENHUB_*/PGVECTOR_*/REDIS_*），
# 无需额外 profile；默认即生产配置（webhook-allow-unsigned=false、优雅停机）。
ENTRYPOINT ["java", \
  "-XX:MaxRAMPercentage=75", \
  "-XX:+ExitOnOutOfMemoryError", \
  "-XX:+UseG1GC", \
  "-jar", "app.jar"]
```

**`token-factory/Dockerfile`（全 35 行，同一作者、同一天的项目）：**

```dockerfile
# syntax=docker/dockerfile:1

# ---- 构建阶段：与运行环境分离，产物里不带 JDK / Maven 缓存 ----
FROM eclipse-temurin:17-jdk-alpine AS build
WORKDIR /build

COPY pom.xml ./
COPY token-factory-core/pom.xml token-factory-core/pom.xml
COPY token-factory-client/pom.xml token-factory-client/pom.xml
COPY token-factory-server/pom.xml token-factory-server/pom.xml
# 先只拷 POM 把依赖层缓存下来：改代码不会重装依赖
RUN --mount=type=cache,target=/root/.m2 mvn -B -ntp -q dependency:go-offline

COPY token-factory-core/src token-factory-core/src
COPY token-factory-client/src token-factory-client/src
COPY token-factory-server/src token-factory-server/src
RUN --mount=type=cache,target=/root/.m2 mvn -B -ntp -q -DskipTests package

# ---- 运行阶段 ----
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app

# 非 root 运行：容器被突破时不至于直接拿到 root
RUN addgroup -S tf && adduser -S tf -G tf
RUN apk add --no-cache dumb-init

COPY --from=build /build/token-factory-server/target/*.jar app.jar

USER tf
EXPOSE 8090

ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75"

ENTRYPOINT ["/usr/bin/dumb-init", "--"]
CMD ["sh", "-c", "exec java $JAVA_OPTS -jar /app/app.jar"]
```

**逐项对照：**

| 项 | `code-review-agent` | `token-factory` |
|---|---|---|
| 阶段数 | **1（单阶段）** | **2（多阶段）** |
| 构建需要宿主机 JDK+Maven | **是** | **否** |
| 依赖层缓存（`dependency:go-offline` + cache mount） | ❌ | ✅ |
| 运行 JRE | **`21-jre`**（Ubuntu 系） | **`17-jre-alpine`** |
| 编译期 Java 版本（pom） | **17** | 17 |
| 非 root 用户 | ❌（默认 root） | ✅（`USER tf`） |
| `dumb-init`（PID 1 回收） | ❌ | ✅ |
| 内存感知 | `-XX:MaxRAMPercentage=75` ✅ | `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75` ✅ |
| OOM 处理 | `-XX:+ExitOnOutOfMemoryError` ✅（**更好**） | ❌ |
| 镜像体积 | 更大（Ubuntu 系 + JRE 21） | 更小（alpine） |

**先说这四条"两个仓库不一致"里最该改的一条：Java 版本。**

```
code-review-agent/pom.xml:27    <java.version>17</java.version>
code-review-agent/Dockerfile:4  FROM eclipse-temurin:21-jre
token-factory/Dockerfile:20     FROM eclipse-temurin:17-jre-alpine
```

**同一个作者、同一条版本基线（Java 17），两个仓库跑在不同的运行时上。**

- **功能上没有问题**：Java 21 的 JVM 运行 Java 17 字节码是向后兼容的，容器能正常提供服务。
- **但它破坏了"基线"这个概念本身**。这本书第 01 讲把基线锁成 Java 17，读者照着核对 `pom.xml` 会得到一致的答案；但一进容器就是 21。**当"书里写的"和"容器里跑的"不同时，读者在排查环境问题时不知道该信哪一个。**
- **而且它把一类差异藏到了运行期**：GC 默认值（21 的 G1 行为与 17 有调整）、`Thread` API 的可用性、`--release` 未覆盖的新类。这些差异**编译期发现不了**（编译用的是 17），**本地也发现不了**（本地跑的是 `mvnw`，不是镜像）。

**修法**：把 `21-jre` 改成 `17-jre`，或者（如果确实想要 21 的运行时）把 `pom.xml` 的 `java.version` 升到 21 并同步更新全书的基线声明。**两条路都行，唯独不能"声明的是一套、跑的是另一套"。**

**第一份的第一行，把整件事说清楚了**：

**`.dockerignore` 里唯一一条"注释解释为什么要保留某个条目"，指向的正是单阶段构建的成本。** 而第二份可以干净地忽略 `target/`——因为它的产物在容器内产生，宿主机的 `target/` 毫无用处。

**再看量化。** 实测本仓库的构建上下文构成：

| 目录 | 大小 | 在 `.dockerignore` 里？ | 被 `COPY` 用到？ |
|---|---|---|---|
| `site/`（VitePress 站点，含 `node_modules`） | **101 MB** | ❌ **没忽略** | ❌ 完全用不到 |
| `target/` | 4.8 MB | **显式保留**（注释说明） | ✅ 唯一要用的是里面的 jar |
| `docs/` | 3.3 MB | ❌ 没忽略 | ❌ 用不到 |
| `data-admin-test/` | 32 KB | ❌ 没忽略（只忽略了 `data/` 与 `data-dev/`） | ❌ 用不到 |
| `.git/` | 16 MB | ✅ 已忽略 | — |

**`docker build .` 要把约 110 MB 的上下文交给构建器**（BuildKit 有会话缓存可省去重复传输，但内容变化时仍是全量），**而其中真正被 `COPY` 用到的只有 1 个 jar**。而 `site/node_modules` 这一类目录恰恰是**变化最频繁、体积最大**的——依赖一更新，上下文就整块重传。

**修法很简单**（不是仓库现状）：

```
# 追加到 .dockerignore
site/
docs/
data-admin-test/
```

**顺带确认一件事：此刻 `target/` 里没有 jar**（`ls target/*.jar` 无命中）。这不是 bug——单阶段流程要求你先 `mvn package`。但它精确地证明了 2.2 节那句话：**这个镜像是"依赖宿主机产物"的，`docker build .` 在干净 clone 上必然失败。**

### 3.2 compose：两份文件，一份有应用、一份只有基础设施

```yaml
# 本地联调用（生产请改用外部 PostgreSQL 与 Secret 管理）
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: token_factory
      POSTGRES_USER: token_factory

`code-review-agent/dev/docker-compose.dev.yml`（**没有应用**）：

services:

**三处对照：**

1. **`docker-compose.dev.yml` 里没有应用服务** → 所以它不是"一键自托管"，而是"一键起依赖"。应用仍要 `./mvnw spring-boot:run`——**这就要求宿主机有 JDK + Maven + 整个源码树**。这也是方案里"立刻可做的三件事"第一条（补一个含应用的一键编排）的由来。
2. **PG 的 `healthcheck` 两边都写了** ✅，但**消费方式不同**：
   - `token-factory`：`depends_on: postgres: condition: service_healthy` —— **等健康检查通过**
   - `code-review-agent`：`depends_on: - postgres`（列表形式）—— **只等容器"启动"**
   
   这两者在 PG 上差别很大：**PG 容器 `started` 的时刻，`postgres` 进程可能还在做初始化、还没开始接受连接。** 结合第 37 讲的 fail-fast（连不上 PG → 应用启动失败），**这个差别会直接决定"compose up 之后应用能不能起来"**。
   
   **同一个作者，写了同一个 `healthcheck`，一处消费了它、一处没有。** —— 又一次"两套实现必然漂移"，而且这次的载体是 `depends_on` 的**两种写法**（列表 vs 长语法）。
3. **`redis:7`** 还在 compose 里。但 Redis 已经不是系统组件了：`CoreHealthIndicator` 的类注释写着"曾同时检查 Redis（消息队列时代），**2026-09-08 随 `core/mq` 死代码清理移除**——Redis 已无业务消费者，不再是系统组件"。而 Dockerfile 的注释里也还留着 `REDIS_*`。**两处注释/配置描述了一个已经不存在的依赖**——这会让新同事照着 compose 去"排查 Redis 连接问题"。

### 3.3 ★ 两条本地路径，在"用户名"这一项上行为不同

这是本讲开头那个痛点的源码现场。把两条路径的身份信息并排放：

| | 方式 A：`dev/start-all.sh` | 方式 B：`dev/docker-compose.dev.yml` |
|---|---|---|
| PG 来源 | **Homebrew 本地安装**（`/opt/homebrew/var/postgresql@17`） | **`pgvector/pgvector:pg17` 镜像** |
| 初始化 | `initdb ... --auth=trust`（`start-all.sh:88`） | 镜像自带 `POSTGRES_USER/PASSWORD` |
| 建库 | `createdb codereview` + `CREATE EXTENSION vector`（`:94-99`） | `POSTGRES_DB=codereview` 自动建库 |
| **认证方式** | **`--auth=trust`（不校验密码）** | **官方镜像默认 `scram-sha-256`（校验密码）** |

### 3.4 容器里的三个默认值

**① 用户：本项目是 root。**

`code-review-agent/Dockerfile` 里**没有 `USER`**，`eclipse-temurin:21-jre` 默认 root；`VOLUME /app/data` 里的文件也归 root。
`token-factory/Dockerfile` 里有：

```dockerfile
# 非 root 运行：容器被突破时不至于直接拿到 root
RUN addgroup -S tf && adduser -S tf -G tf
...
USER tf
```

**② PID 1 与信号：本项目的 JVM 就是 PID 1。**

`ENTRYPOINT ["java", ...]` 是 **exec 形式**，所以：
- ✅ **好事**：`docker stop` 的 `SIGTERM` 直达 JVM → **`server.shutdown: graceful`（`application.yml:5`）真的能生效**（等在处理中的审查任务跑完）。这个选择是对的，而且它和 `application.yml` 的优雅停机是配套的。
- ⚠️ **代价**：**PID 1 必须负责回收孤儿进程。JVM 不做这件事。**

**本项目会不会 fork 子进程？会。** `SandboxProbe`：

```java
// core/autofix/SandboxProbe.java:61-66
private static boolean commandExists(String cmd) {
    try {
        Process p = new ProcessBuilder("sh", "-c", "command -v " + cmd)
                .redirectErrorStream(true)
                .start();
        int exit = p.waitFor();
```

四个候选（`bwrap`/`firejail`/`sandbox-exec`/`docker`）各 fork 一次（`:29-34`），`waitFor()` 会回收**它自己启动的那个**。所以**正常路径上不泄漏**。

**但这里有两点要说清楚（诚实边界）：**

- 严格说，`waitFor()` 回收的是"这一个直接子进程"。**`sh -c "command -v x"` 如果自己再 fork（比如 command 是 shell 内建时不 fork，不是内建时通常也由 shell 直接 exec）**，一般不会留下孤儿（shell 会自己等）。所以**当前不构成实际泄漏**。
- **真正的问题是"没有防线"**：一个启了 PID 1 却不做 `wait()` 的进程，**只要未来任何一处代码 fork 出比自身寿命长的子进程**（比如为某个工具加一个"跑测试"子进程、加一个 `git` 子进程），僵尸就会累积到容器重启为止。而 `dumb-init` 的价值恰恰是**把这条防线无条件装好**——它只做两件事：转发信号、回收孤儿。

**所以：这不是"正在漏"，是"少了那道不该省的手续"。** `token-factory` 装了它，本项目没装——**两个仓库又一次不一致，而这次不一致的方向是"少了一层保护"。**

**③ 内存：本项目对得比另一个仓库还多。**

```dockerfile
-XX:MaxRAMPercentage=75, \
-XX:+ExitOnOutOfMemoryError, \
-XX:+UseG1GC
```

- `MaxRAMPercentage=75` —— 容器感知，不会把宿主机内存当自己的上限 ✅
- **`ExitOnOutOfMemoryError` —— 这一条 `token-factory` 没有。** 它的作用：OOM 时**直接退出进程**（而不是抛 `OutOfMemoryError` 后让应用在不可预期的状态下继续跑）。配合编排的 `restart: unless-stopped`，**OOM → 重启 → 恢复**，比"带着坏掉的内存继续服务"好得多。**这是本项目在部署上做得最好的一处，值得学。**

### 3.5 沙箱：在镜像里它永远是"不可用"

第 25 讲那套 fail-closed 不变量，在容器里是这样表现的：

```java
// core/autofix/SandboxProbe.java:28-34（探测候选）
/** 探测候选命令（任一存在即视为沙箱可用）。 */
private static final List<String> RUNNERS = List.of(
        "bwrap",        // Linux bubblewrap
        "firejail",     // Linux firejail
        "sandbox-exec", // macOS Seatbelt
        "docker"        // 通用容器兜底
);
```

`code-review-agent` 的运行镜像是 `eclipse-temurin:21-jre`（Ubuntu 系 JRE 镜像）。**这镜像里既没有 bubblewrap、没有 firejail、没有 macOS 的 sandbox-exec，也没有 docker CLI。** 于是：

```
SandboxProbe.detect() → available=false
  → AutoFixEngine 构造时 resolveSandbox(...) 得到 false（:107-115）
  → AutoFixSafetyPolicy.evaluate(APPLY, false) → denied
  → 「APPLY」模式永远无法应用修复
```

而 `AutoFixEngine` 的构造日志是**唯一线索**：

```java
// core/autofix/AutoFixEngine.java:102-103
log.info("[自动修复] 初始化：mode={}, sandboxAvailable={}（fail-closed 边界已启用）",
        mode, sandboxAvailable);
```

**为什么这里值得讲？因为它是一个"正确行为 + 糟糕可发现性"的组合：**

- **fail-closed 完全是对的**：容器里没有隔离能力，就绝不在容器里应用代码变更。**这条不能改。**
- **但默认 `mode` 就是 `SUGGEST`**（`@Value("${review.autofix.mode:SUGGEST}")`）→ 所以在默认配置下，`sandboxAvailable=false` **没有任何影响**，日志读者不会注意到，也没必要注意。
- **一旦有人把 `mode` 改成 `APPLY`**（这是个合理的运维动作：想让它真的改代码），**自动修复会永远不生效**，而**唯一的线索是启动时的一行 `info` 日志**——而且这行日志的措辞是"fail-closed 边界已启用"，读起来像是**功能正常工作**，而不是**功能不可用**。

**修法（不是仓库现状）：把"APPLY 但沙箱不可用"从日志升级为启动失败。**

```java
// 修法示意（不是仓库现状）
if (mode == AutoFixMode.APPLY && !sandboxAvailable) {
    throw new IllegalStateException(
        "配置了 review.autofix.mode=APPLY，但当前环境未探测到任何沙箱 runner"
        + "（bwrap / firejail / sandbox-exec / docker）。容器镜像不含这些命令时，"
        + "请改用 SUGGEST，或显式配置 review.autofix.sandbox-available=true 并自担风险。");
}
```

**理由和 3.3 节的用户名修法完全一样**：**"配了一个不会生效的选项"必须在启动时说出来，不能只留一行读起来像正常的日志。** 配置项的价值在于"配了就生效"；**配了不生效的配置项，比没有这个配置项更糟**——它会让运维以为自己已经打开了某个能力。

顺便：`review.autofix.sandbox-available` 这个配置项**是给这种情况准备的逃生门**（显式覆盖探测结果）。但它**没有任何提示告诉使用者"填 true 意味着在没有隔离的环境里应用代码变更"**——这个键的注释和文档需要写清风险等级（第 25 讲讲过的"红线约束写在接口注释里"是同一个要求）。

### 3.6 健康探针：为什么不建议用这份 `/health` 做 k8s 探针

```java
// api/HealthController.java:9-29
/**
 * 健康检查端点（零依赖，供容器编排存活/就绪探针）。
 *
 * <p>同时暴露 {@code GET /health} 与 {@code GET /actuator/health}（兼容约定路径）。
 * 依赖全部健康时返回 HTTP 200 + {@code {"status":"UP"}}；任一核心依赖异常返回 HTTP 503 + {@code DOWN}。
 */
@RestController
public class HealthController {

    private final CoreHealthIndicator indicator;
    ...
    @GetMapping({"/health", "/actuator/health"})
    public ResponseEntity<HealthResult> health() {
        HealthResult result = indicator.check();
        int code = "UP".equals(result.status) ? 200 : 503;
        return ResponseEntity.status(code).body(result);
    }
}
```

**它"长得像" actuator，但不是。** 本项目**没有 `spring-boot-starter-actuator` 依赖**（`pom.xml` 零命中；对照 `token-factory-server/pom.xml:43` 有）。所以：

| 标准 actuator 提供 | 本项目 |
|---|---|
| `/actuator/health` → `{"status":"UP","components":{...}}` | **自定义 JSON `{"status":"UP","details":{...}}`** |
| `/actuator/health/liveness`（存活分组） | ❌ **不存在** |
| `/actuator/health/readiness`（就绪分组） | ❌ **不存在** |
| `/actuator/info`、`/actuator/metrics` 等 | ❌ 不存在 |
| `probes.enabled=true` 开关 | ❌ 不存在 |

**这带来两个具体问题：**

**① 任何按标准格式解析的监控/编排会读不到东西。** 一个 Kubernetes 的 `readinessProbe` 打到 `/actuator/health` 只会看 HTTP 状态码（200/503），这没问题；但**任何要读 `components` 字段做细粒度判断的采集器，会在自定义 JSON 上得到空**。**接口伪装成标准接口，比用非标准路径更危险**——因为别人会放心地按标准语义用它。

**② 没有 liveness/readiness 分层，就无法区分"进程活着"与"可以接流量"。** 而第 37 讲已经确定了这个系统的启动特性：**PG 不通 → 启动失败**。所以真正的健康判定只有"起来了"和"没起来"两态，**`/health` 在运行期的价值只剩"PG 还通不通"**。

**③ 还有一条容易被忽略的：这个探针会真连 PG，而它用的是 `DriverManager`。**

```java
// config/CoreHealthIndicator.java:47-59（check 方法节选）
public HealthResult check() {
    Map<String, String> details = new LinkedHashMap<>();
    boolean healthy = true;
    if (pgEnabled) {
        try (Connection conn = DriverManager.getConnection(
                "jdbc:postgresql://" + pgHost + ":" + pgPort + "/" + pgDatabase, pgUsername, pgPassword);
             Statement stmt = conn.createStatement()) {
            stmt.execute("SELECT 1");
            details.put("pgvector", "up");
        } catch (Exception e) {
            healthy = false;
            details.put("pgvector", "down: " + e.getMessage());
        }
    }
```

第 37 讲已指出：**它绕过连接池，所以"池耗尽"时探针仍报 UP。** 在容器编排场景下这更值得注意——**一个探针如果用一条独立连接去测"库在不在"，那它测的是库，不是"你的服务能不能干活"。**

**结论（给读者的部署建议）：**

- 用 `/health` 做 **liveness** 是可以的（进程能响应 HTTP 即可）。
- **不要用 `/health` 做 readiness 的唯一判据**——它不反映连接池可用性。要么引入 actuator 并自定义一个基于连接池的 `HealthIndicator`，要么在探针里额外检查你真正关心的资源。
- **注意路径**：如果将来引入 actuator，`/actuator/health` 会**被 actuator 的端点覆盖**（`HealthController` 的映射会冲突）。**这是一个"改名比改造便宜"的时点**——现在就该把它叫 `/health`，别占用标准路径。

### 3.7 `VOLUME /app/data` 的注释，描述的是一个已经不存在的功能

```dockerfile
# 运行时数据目录（自定义规则/历史/反馈等落盘，生产建议挂卷持久化）
VOLUME /app/data
```

对照第 37 讲核对过的现状：

```yaml
# application.yml:133-136
# 数据目录（集群改造后仅剩两个用途）：① review.tools.agent-loop.enabled=true 时作为
# FileReadTool 的默认读取根；② 兼容历史配置读取。断点/经验/校准/反馈/审查历史/轨迹/
# 团队配置/知识元数据已全部迁移到 PostgreSQL（pgvector.enabled=true 时），多实例零本地状态。
data-dir: ./data
```

**Dockerfile 注释里说的"自定义规则/历史/反馈等落盘"——这三类全部已经迁到 PG 了。** 现在的 `data-dir` 只剩"`FileReadTool` 的默认读取根"和"兼容历史配置读取"两个用途。

**后果**：运维读到这条注释，会做一件**看起来必要、实际无用**的事——为 `/app/data` 配一个持久卷、设好备份策略、在灾备演练里把它列进检查项。**多出来的这层运维动作不是无害的：它会让"真正需要备份的东西"（PG）淹没在一堆不需要备份的东西里。**

**修法**：把这行注释改成反映现状，并明确指向真正的持久化位置：

```dockerfile
# /app/data 不再承载业务状态（断点/历史/反馈/经验等已全部落 PG，见 application.yml 的 pgvector 段）
# 仅作为 FileReadTool 的默认读取根与历史配置兼容目录；**真正的持久化对象是 PostgreSQL**
VOLUME /app/data
```

**这是"注释承诺 > 实现"的一个反向变体**：前面各讲遇到的多是"注释承诺了实现没做的事"，这次是 **"注释还在描述实现已经不做的事"**。**方向相反，代价一样——都让人对系统做出错误判断。**

## 四、避坑清单

- [ ] **`docker build` 必须能在只有 Docker 的机器上跑通。** 判据：`git clone` 到全新目录，直接 `docker build .`——需要先装 JDK/Maven 或先跑 `package` 的，就是单阶段路线，改多阶段。
- [ ] **单阶段路线有一个静默风险**：`target/` 里有旧 jar 时，`docker build` 会成功且打出**旧内容**。如果保留单阶段，请把 `docker build` 和 `mvn package` 写在同一条命令里（`./mvnw -o clean package && docker build .`），**不要让它们能被分两次手动执行**。
- [ ] **`.dockerignore` 要覆盖所有体积大且用不到的目录**（站点、文档、`node_modules`、测试数据）。核对方法：`du -sh */` 排序，逐个问"`COPY` 用得到吗？"。
- [ ] **编译期 Java 版本与运行镜像的 Java 版本必须一致**，否则"基线"这个概念就失效了。核对：`pom.xml` 的 `java.version` 对 `FROM ...-jre` 的主版本号。
- [ ] **容器不要用 root 运行**。加 `USER`（并确保 `VOLUME` 目录的属主对得上，否则运行期写不进去）。
- [ ] **用 PID 1 无关的方式装 init**（`dumb-init` / `tini` / `--init`）。**理由不是仪式感**：JVM 作 PID 1 会收信号（优雅停机可用），但**不回收孤儿进程**。只要代码里存在 `ProcessBuilder` / `Runtime.exec`，就装。
- [ ] **JVM 必须容器感知**：`-XX:MaxRAMPercentage` 或 `-Xmx` 显式设置。再加 `-XX:+ExitOnOutOfMemoryError` + 编排的 `restart` 策略——**OOM 就退出重启，优于带着坏内存继续服务**。
- [ ] **`depends_on` 用长语法 + `condition: service_healthy`**，不要用列表形式。列表只保证"先启动"，而 PG/Redis 这类服务从"容器 started"到"能接受连接"之间有窗口期；配合 fail-fast 的应用，这个窗口 = 启动失败。
- [ ] **配置的缺省值不要写成本机特有的值**（用户名、端口、路径）。缺省值必须是"对任何人都有意义的值"，或者干脆留空 + 启动自检给出明确的补救提示。
- [ ] **部署文档要给"最小可用配置清单"**，逐个列出必须设置的键名。否则读者看到 `password authentication failed` 时不知道该改哪个键。
- [ ] **"配了但不生效"的选项必须在启动时失败**。例：`mode=APPLY` 但沙箱不可用 → 抛异常，而不是打一行读起来像正常的 `info`。
- [ ] **健康探针要区分 liveness 与 readiness**，并且**不要绕过连接池**去测依赖——用独立连接测"库在不在"，测不出"服务能不能干活"。
- [ ] **不要占用标准端点路径**（`/actuator/**`）返回自定义结构。要么引入 actuator，要么换一个自己的路径——**伪装成标准接口会让人按标准语义使用它**。
- [ ] **`.dockerignore` 里每一条"为什么保留 X"的注释，都是一次架构自白。** 看到这类注释，就该问一句"这个依赖能不能消掉"。
- [ ] **注释要与实现同步**：`VOLUME` / `REDIS_*` 这类"描述已不存在的功能"的注释，会让运维做无用功（备份一个不需要备份的目录、排查一个已移除的依赖）。

> 1. **补一个仓库根目录的 `docker-compose.yml`**，包含应用本体。要点：

>    - 应用服务用 `depends_on: postgres: {condition: service_healthy}`（**长语法**）；
>    - 应用的环境变量里**显式写出 `PGVECTOR_USERNAME` / `PGVECTOR_PASSWORD`**，与 compose 的 PG 一致；
>    - 应用镜像用 `build: .`，并保证**它不依赖宿主机的 `target/`**（即先把 Dockerfile 改成多阶段）。
> 2. **把 `Dockerfile` 改成多阶段构建**，对照 `token-factory/Dockerfile` 的结构：POM 先拷 + `dependency:go-offline` 缓存依赖层 → 拷源码 → `package` → 运行阶段只拷 jar。顺手补 `USER`（非 root）与 `dumb-init`。
> 3. **补 `.dockerignore`**：加上 `site/`、`docs/`、`data-admin-test/`。
> 4. **修 `application.yml` 的 `username` 缺省值**：改成不带本机账号的值，并在启动自检里对"配了 PG 但没给用户名"给出明确报错（含键名）。
>
> **预期结果（都能自己验证）：**
> - **构建上下文变小**：执行 `docker build .` 时观察输出里的 `transferring context`（或 `docker buildx build --progress=plain` 看上下文大小）——**改 `.dockerignore` 前后对比，应从百 MB 级降到几十 MB 级**。
> - **干净机器可构建**：把仓库 clone 到一个**没有 `target/`** 的目录，直接 `docker build .` → **应该成功**（对比：改之前必然失败在 `COPY target/...`）。
> - **一键起来**：仓库根目录 `docker compose up -d` → 等 PG `healthy` → 应用起来 → `curl localhost:8080/health` 返回 `200` + `{"status":"UP"}`。
> - **顺序被编排保证**：`docker compose down && docker compose up -d`，观察应用容器的日志——**它应该在 PG healthy 之后才开始连库**，而不是先报一次连接失败再重试。
> - **配置错误有明确指引**：把 `PGVECTOR_USERNAME` 删掉再起 → 应该得到一句**指明键名**的启动错误（而不是 `password authentication failed for user "xxx"`）。
>
> **加分项**：写一个最小的"部署自检"脚本（或 CI job），在干净容器里跑上面的流程——**把"一键部署能不能用"变成一个可以被 CI 保证的断言**，而不是每次手测。

## 本讲小结

1. **"一键部署"要有一条可判定的验收标准**：干净机器 + 只有 Docker + 从 `clone` 到"能收到审查报告"，只需复制粘贴。**"大部分都对、差一步"是这类交付物最典型的失败方式**，而缺的那一步既不在文档里、也没被任何检查拦住。
2. **镜像两条路线的判据是"构建需要什么"**：`docker build` 能不能在只有 Docker 的机器上跑通。**单阶段（宿主机出产物）的代价不是"不优雅"，是三个具体失败**：干净 clone 必失败、**可能打出旧 jar 且毫无提示**、`.dockerignore` 被迫保留 `target/`。
3. **★ 同一作者两个仓库、两套 Docker 实践**：`code-review-agent` 单阶段 / root / 无 init / `eclipse-temurin:21-jre` vs `token-factory` 多阶段 / `USER tf` / `dumb-init` / `17-jre-alpine`。**其中 Java 版本不一致最该改**——`pom.xml:27` 写 17、镜像跑 21，**编译期和本地都发现不了**，但它让书里的"基线"概念失效。
4. **★ `.dockerignore` 是构建模型的自白**：本项目那一份的**第一行注释**就是证据——"**注意：保留 `target/`，因为要 `COPY` 其中的 `*.jar`**"。**唯一一条需要解释"为什么保留"的规则，指向的正是单阶段构建的成本。**
5. **★ 构建上下文的量化**：`site/`（101 MB，含 `node_modules`）+ `docs/`（3.3 MB）+ `data-admin-test/`（32 KB）**都没被忽略**，而**真正被 `COPY` 用到的只有 1 个 jar**。补三行 `.dockerignore` 就能省掉约 104 MB 的上下文。
6. **★ 两条本地路径在"用户名"这一项上行为不同，且这是本讲痛点的真因**：`start-all.sh` 用 Homebrew PG + `--auth=trust`（**任意用户名可连，掩盖了默认值问题**）；compose 的 PG 是 `postgres` 用户 + `scram-sha-256`（**`yunfei` 不存在，直接拒绝**）。而 `application.yml:99` 的缺省是 `username: ${PGVECTOR_USERNAME:yunfei}`——**注释上一行写"不要写死"，下一行就写死了缺省值**。
   > **这是第 37 讲那条判据的又一次现身：本地跑通的那条路，把你本该发现的问题挡住了。**
7. **★ 同一个 `healthcheck`，一处消费一处没消费**：`token-factory` 用 `depends_on: {condition: service_healthy}`，`dev/docker-compose.dev.yml` 的 gitea 用列表形式的 `depends_on`（**只保证先启动**）。结合第 37 讲的 fail-fast（PG 不通 → 启动失败），**这个差别直接决定"compose up 之后应用能不能起来"**。
8. **★ 沙箱在镜像里恒为不可用**：JRE 基础镜像里没有 `bwrap`/`firejail`/`sandbox-exec`/`docker` → `sandboxAvailable=false` → APPLY 永久被拒。**fail-closed 完全正确、不能改**；但"配了 `mode=APPLY` 却不生效"应该**启动失败**，而不是只留一行读起来像正常的 `info`（"fail-closed 边界已启用"）。
9. **容器三个默认值**：用户（本项目 root，`token-factory` 有 `USER tf`）、PID 1（本项目 JVM 直收信号 ✅ 优雅停机可用；但**不回收孤儿**，`SandboxProbe` 确实是 fork 点）、内存（`MaxRAMPercentage=75` + **`ExitOnOutOfMemoryError`** ✅ **这一条本项目的做法比另一个仓库更好，值得学**）。
10. **★ `/actuator/health` 是手写的、不是 actuator 的**（本项目无 `spring-boot-starter-actuator` 依赖）。后果：**没有 liveness/readiness 分层**、**自定义 JSON 而非标准 `components`**（按标准解析的采集器会读到空）。**接口伪装成标准接口，比用非标准路径更危险。** 而且探针走 `DriverManager` 绕过连接池——**池耗尽时仍报 UP**。
11. **★ `VOLUME /app/data` 的注释描述了一个已经不存在的功能**：它说"自定义规则/历史/反馈等落盘"，而这三类**全部已迁 PG**（`application.yml:133-136` 的注释明确说 `data-dir` 只剩两个用途）。**后果是运维会去备份一个不需要备份的目录**，而真正的持久化对象（PG）被淹没。**这是"注释承诺 > 实现"的反向变体——注释还在描述实现已经不做的事。**
12. **`REDIS_*` 同时出现在 Dockerfile 注释和 compose 里**，而 Redis 已在 2026-09-08 随 `core/mq` 清理移除、不再是系统组件（`CoreHealthIndicator` 类注释有记录）。**过时的部署配置会让人去排查一个已不存在的依赖。**

**模块六到这里，系统已经能被别人装起来了。** 但"能跑"不等于"有效"——下一讲回到最容易被跳过、也最容易被糊弄的一环：**效果评测与误报治理**。有多少条意见其实不该提？"测试全绿"这句话到底测了什么？以及当"越用越准"这个承诺落到多实例上时，它还剩多少。
