## 一、痛点

书读完了。

合上它的时候，你有两种可能的感觉：

**第一种是"我好像会了"。** 你能讲出星型汇聚、三级降级、fail-fast、误差闭环……每一个概念你都能说三五句。这种感觉很好，也很危险——因为它是 **"能复述"**，不是 **"能判断"**。

**第二种是"我现在要做的东西跟书里不一样"。** 你手上是一个客服机器人、一个数据分析 Agent、一个代码生成工具。书里讲的是代码审查引擎。**你隐约觉得那些判据能迁移，但不确定哪一条能**。

这两种感觉指向同一个空缺：

> **这本书给了你"一个系统是怎么建成的完整路径"，但它没有给你"下一个系统该从哪一步开始"的判断力。**

而更麻烦的是第三件事：**这一行的工具层在以月为单位变化。**

书里锁定了一套基线——Java 17、Spring Boot 3.3.4、PostgreSQL 17.11、pgvector 0.8.6、LangChain4j 1.19.0，加上自研的 `token-factory` 0.1.0 与 `agent-kit` 0.1.1。**这里面任何一个数字，两年后都可能不再是主流选择**，而那个跨进程通信的协议、那家模型供应商的 SDK 形状、那种 prompt 的写法，很可能已经换了。

那这本书还剩什么？

**剩下的东西比你想的多——但前提是你能分辨哪些是会腐烂的、哪些不是。** 这是本讲第一部分要解决的事。

## 二、原理

### 2.1 三层知识：会腐烂的、慢变的、不变的

把这本书里出现过的东西按"保质期"分三层：

| 层 | 内容 | 保质期 | 该用什么态度学 |
|---|---|---|---|
| **工具层** | 版本号、模型名、价格表、SDK 签名、配置项键名、具体的类名 | **月到一年** | **现学**。用到时查文档，不要背，背了也会过期 |
| **约定层** | 协议字段命名习惯、结构化输出的降级套路、网关的分层方式、镜像的构建模型、部署的编排顺序 | **三年到五年** | **理解**。知道它为什么长这样，换一个技术栈你也能自己推出来 |
| **判据层** | "回退的触发条件必须是配置不能是故障"、"降噪不得覆盖底线"、"没有数据与数据是零必须可区分"、"人工输入写入失败必须让调用方知道" | **不腐烂** | **内化**。这是这本书真正的资产 |

**这三层的分辨能力，比任何一层的具体内容都重要。**

因为面试和实战中，**"知道 LangChain4j 1.19.0"是工具层，两个月后就不值钱；而"知道为什么不用 MQ 而用 CompletableFuture"是判据层，五年后依然值钱。**

> **一个自检方法**：把你现在会的东西逐条写下来，然后问一句"**如果换一个语言、换一个模型、换一个云，这条还成立吗？**"成立的进判据层，不成立的进工具层。**如果你写下来的东西 80% 在工具层，说明你学的是操作，不是工程。**

**数量级直觉：工具层腐烂到底多快，值不值得背。**

"以月计"这四个字值得摊到整个职业生命周期上看清，否则它只是形容词：

```text
场景：一个"能背版本号但不懂判据"的工程师 vs 只重判断力的工程师。
- 假设主流基线换代量级 ≈ 18 个月一轮（Java 17→21、Boot 3.3→4.x、PG 17→18 这类）
- 10 年工作 ≈ 120 个月 → 约 6~7 轮换代
- 背工具层的人：每轮换代 = 一次"从头重背"，累计 6~7 次清空重来，中途无资产增值
- 内化判据层的人：6~7 轮换代 = 把同一条判据在 7 个不同技术栈上验证 7 遍 → 判据在使用中被强化
```

> **结论**：工具层的知识是**消耗品**（折旧），判据层的知识是**资产**（换代即复利）。"回退的触发条件必须是配置不能是故障"这一条，换语言、换模型、换云依然成立——**每一轮换代不是推倒重来，而是给这条判据再增加一次被验证过的可信度。** 这也正是本章 3.2 节只保留那 17 条的用意：不是别的句子不对，是它们经得起这种"换代复利"的检验。

### 2.2 从"信号"读下一站：五个本书里已经出现、但没被解决的缺口

判断一个方向值不值得投入，最可靠的方法不是听预测，而是**看你自己的系统里哪些问题反复出现**。下面五条，每一条都能在本书里指到一处"它出现了，但没有被彻底解决"的证据。

**① 上下文工程会取代 prompt 工程成为主战场**

本书第 12 讲（上下文工程）、第 22–29 讲（整个 RAG 模块）都在讲同一件事：**难点不在"怎么问"，而在"给模型看什么"。** 而第 40 讲暴露了一个明确的缺口——

> 这个系统的 RAG 上下文是**按次检索**的：每次审查重新召回、重新重排。它没有"这个仓库过去三个月演化出了什么规律"这种**跨会话的结构化记忆**。

这是一个正在被推进的方向，而且它的判据是清晰的：**当"记忆"从"向量库检索"变成"分层的、有生命周期、有写入门禁的结构"时，它就更像数据库设计，而不像检索引擎。** 本书第 10 讲（记忆系统的生命周期状态机）已经给出了这个形状的雏形，但它当时只是一个组件。

**② 长时任务的编排会成为基础设施，而不是每家的轮子**

本书第 16 讲（Agent 抽象与生命周期）、第 17 讲（并行编排与超时控制）里，那个"逐 Future 独立限时 + 共享 deadline"的修复，是在**自己写一套超时与降级语义**。

而第 40 讲那句总结——"**这个 bug 的特征是：所有测试都是绿的**"——说的正是这类代码的本质困难：**编排逻辑的正确性，用常规测试几乎测不出来。**

这个方向的判据是：**当"断点续跑 + 幂等 + 状态机 + 可回放"被抽成一个独立的、可复用的运行时，而不是散在每个业务系统里时**，这件事才算解决了。本书第 10、16、17 讲的所有内容，都会变成那个运行时的一个特性。

**③ 评测的自动化程度会决定 Agent 能不能上规模**

这是本书里**唯一一条被明确指出"还没解决"的**。第 40 讲整讲都在讲这个：

- Agent 的"正确答案"不存在客观形式，**人的反馈是唯一的数据源**；
- 而这个数据源**极其稀疏**（人只会标误报，几乎不标正报），导致校准曲线是**单向下调**的（6 次误报到下限 0.5，从 0.5 回满需要 15 次正报）；
- 闭环有 8 跳，其中**第 7 跳（落历史）是断的**——连带跨期误报率算不出来。

**判据**：一个 Agent 系统能不能上规模，不看它现在有多准，**看它的"不准确"能不能被度量和收敛**。做不到这点，它就永远停在 demo 阶段——因为它没有自我改进的通路。

**④ 跨进程、跨语言的工具与上下文协议会标准化**

本书第 05 讲（Function Calling）和第 30 讲（LLM 网关）里，工具调用与模型调用都发生在**同一个进程内**。

一旦 Agent 需要调用不属于本进程的工具（别人的服务、别的语言写的分析器、另一个团队的知识库），**"工具长什么样、上下文怎么传、鉴权怎么带"就必须有约定**——否则每接一个工具都是一次定制开发。

**判据**：这个方向成不成立，看一件事——**接一个新工具，是"写一个适配器类 + 加一行配置"，还是"改一遍主流程"？** 本书里已经有一个正面例子：第 39 讲提到的那种"一个适配器类 + 一行配置"的扩展方式，正是这个判据的形态。

> **为什么本讲不点名具体协议**：因为它们正处在快速演进期，**写进书里就是写了一条一年后必然过期的信息**——而这一讲的立论恰恰是"要分辨什么会腐烂"。**方向可以写，名字不该写。**

**⑤ 合规与可审计会从事后补丁变成设计约束**

本书第 35 讲（提示注入防御）把安全做成了**纵深防御**：diff 预检只标注不拦截、写库边界才用完整检测、逐文件 BLOCK/TAG/CLEAN 分级。

这是**防御**。而往下走是**留痕与可追溯**：

- 这个结论是哪个模型、哪个版本、哪次调用产生的？
- 它依据的是哪几段上下文？
- 如果它导致了外部动作，谁批准的？

**判据**：当"这个 Agent 为什么这么决策"成为一个必须回答的问题时，**可观测性（第 36 讲）就不只是运维设施，它变成了产品的一部分。**

**★ 这五条的共同点值得单独说**：它们**没有一条是"新概念"**。全都是你在本书里已经见过的东西——上下文、编排、评测、协议、合规——只不过**每一条都停在了"能用"，还没到"能规模化"**。

**所以"下一站"不是一个你还没学过的领域，而是一个你已经踩到一半的坡。** 判断自己该往哪走，方法很简单：**回头看你的系统，哪一个缺口最常让你在半夜被叫起来，就从那一个开始。**

### 2.3 学习路径：按"你现在卡在哪"排，不按"知识体系"排

大部分学习路径是按学科逻辑排的：基础 → 进阶 → 高级。**这是教材的排法，不是工程的学习路径。**

工程的学习路径只有一条判据：**你现在卡在哪。**

三条常见起点，三条路径：

**路径 A · 后端工程师，想转 Agent 方向**

```
模块一（LLM 接入与协议）→ 模块五（工程化）→ 模块二（单 Agent）→ 模块三（多 Agent）→ 模块四（RAG）→ 模块六（生产上线）
```

**为什么先模块一 + 模块五**：因为你的优势是"工程能力、系统思维"，短板是"LLM 这个不可靠组件怎么用"。**模块一和模块五是这本书里"最像你原来做的后端"的两块**——限流、熔断、鉴权、成本、可观测，你一看就懂；而它们恰好是 LLM 应用最缺的部分。**先在你的优势区建立自信和话语权，再进入不熟悉的编排与检索。**

**路径 B · 已经在做 Agent，想把它推到生产**

```
模块五（工程化）→ 模块六（生产上线与求职）→ 模块三（多 Agent）→ 模块四（RAG）
```

**判据**：如果你已经"能跑通一个 Agent"，那你缺的**不是更多的 Agent 技巧，而是"它为什么不稳"。** 而"不稳"的答案几乎从来不在编排层——**在网关（模型挂了怎么办）、在成本（烧穿了怎么办）、在注入（有人攻击怎么办）、在存储（多实例了怎么办）、在度量（你怎么知道它在变好还是变坏）。** 这五件事全在模块五、六里。

**路径 C · 面试冲刺（时间紧）**

```
第 41 讲（话术地图）→ 第 37/38/39/40 讲（我在生产上做过什么）
                    → 第 17/18/19/20 讲（我在协作上做过什么）
                    → 第 30–36 讲（我把 LLM 变成基建做过什么）
```

**为什么从第 41 讲开始**：因为它告诉你怎么把后面那些讲**翻译成面试场上能说的话**，以及哪些数字必须当场能自证。**先学怎么用，再学内容，效率比反过来高。**

**★ 三条路径的共同点**：都从"你已经在哪"开始，而不是从"知识树的第一层"开始。**这就是判据层知识的用法——它不告诉你"先学什么"，它告诉你"你现在的问题在哪一层"。**

> **一条反直觉的建议**：如果你时间极少，**不要直接读第 41 讲**。因为第 41 讲的价值建立在"你有一批能讲的东西"之上——没有前面的内容，它只是一份漂亮的目录。**时间紧的正确做法是：从路径 C 的第二行开始，读模块六的四讲，每一讲末尾都有"避坑清单"，那些是最能在面试里直接复用的句子。**

三条学习路径用一张表收口（决策 → 适用场景 → 代价）：

| 路径 | 决策 | 适用场景 | 代价 |
|---|---|---|---|
| A · 后端转 Agent | 先模块一 + 五 | 工程强、编写好在"LLM 不可靠组件"，想在优势区建话语权 | 暂时绕过 Agent 核心，需回头补模块二三四 |
| B · 推上生产 | 先模块五 + 六 | 已能跑通 Agent、瓶颈是"不稳"而非"不会" | 跳过学习曲线，得在真实的运维坑里补课 |
| C · 面试冲刺 | 先第 41 讲 + 模块六避坑清单 | 时间以天计，要"能讲的话"不要"能写的系统" | 没有前面内容背书，只能拿到话术层的分数 |

**一张表把三者的共同判断点写在一起：它们都按"你现在卡在哪"起步，而不是按知识树的第一层。** 你只需要做一次这样的分类——"我的瓶颈是领域不会、系统不稳、还是话术不足"——剩下的就是照表选路径。

### 3.2 判据句精选（本书真正的资产）

下面是全书里那些**换语言、换模型、换云都依然成立**的判据。**这里只放本讲能够逐条指回正文的**——其余各讲正文里也各有一句，**但本讲不代为归纳，避免书末出现未经核对的内容。**

| 出处 | 判据句 |
|---|---|
| 第 03 讲 | 模型给的键名和你习惯的键名不一致时，**失败是静默的**——你不会收到错误，你只会收到一个空字段。 |
| 第 20 讲 | 不该给模型看的内容，不要让它进了上下文再过滤——**在准入阶段就剔除。** |
| 第 27 讲 | 融合排序用的分值和判断相似度的分值**必须是两个字段**。归一化的排名分第一名恒为 1.0，拿它比阈值等于**闸门永不关**。 |
| 第 37 讲 | **回退的触发条件必须是配置，不能是故障。** 存储不是可选依赖，它定义了"你的系统是什么"。 |
| 第 37 讲 | 多实现自动降级之所以危险，是因为**它把"失败"翻译成了"成功"**——错误日志为空、HTTP 全绿、连接数下降，**在监控上与"系统变健康"完全一致**。 |
| 第 38 讲 | **在评论里说了一句话**和**在平台上改变了状态**是两件独立、各自可能失败的事。其中"改变状态"这一条，如果失败，**监控上什么也看不见**。 |
| 第 38 讲 | AI 不代替人做阻断决定。**沉默不是中立**——需要你表态的机制里，不主动上报就等于让机制退化。 |
| 第 39 讲 | 判断一份镜像做得好不好，只看一件事：**`docker build` 能不能在只有 Docker 的机器上跑通。** |
| 第 39 讲 | 单阶段镜像最隐蔽的代价不是慢——是**它可能成功，但打进去的是旧 jar，而且没有任何提示**。 |
| 第 40 讲 | **降噪不得覆盖底线，顺序即优先级。** "开发者说这是误报"是统计事实，"这条是 BLOCKER"是安全论断，**前者不该覆盖后者**。 |
| 第 40 讲 | **"没有数据"和"数据是零"必须可区分。** 老记录缺新字段时补一个"未知"，而不是补 0，否则统计会系统性偏低。 |
| 第 40 讲 | **人工输入的数据，写入失败必须让调用方知道。** 人的反馈是"点一次、不会再来第二次"的数据，静默吞掉就是**永久丢失**。 |
| 第 40 讲 | **低频写不能论证读可以不优化。** 写频率和读频率是两个独立的量。 |
| 第 40 讲 | 校准只降不升，就会**单向漂移到底且几乎不回升**。别指望人工补偿——加时间衰减。 |
| 第 41 讲 | **行号漂移比类名漂移更伤**：类名错了会报错（可见），行号错了会让读者**怀疑自己而不是怀疑文档**。 |
| 第 41 讲 | 缺陷只用五段式讲：**发现 → 为什么危险 → 修复的取舍 → 验证的证据 → 诚实的边界**。缺"取舍"是疏忽，缺"边界"是自夸。 |
| 第 41 讲 | **"这个 bug 的特征是——所有测试都是绿的。"** 机制存在、测试通过、但实际效果为零，这是 Agent 工程最核心的一类风险。 |

**★ 注意这一列里反复出现的形状**：**"看起来正常"和"实际正常"的分离。**

- 降级把失败翻译成成功 → 监控上看起来更健康；
- 回写失败时静默 → 评论里看起来已经阻断；
- 单阶段镜像打了旧 jar → 构建看起来成功；
- 校准单向漂移 → 报告里的置信度看起来有值；
- 文档锚点过期 → 手册看起来还能用。

**这条线索贯穿 42 讲。** 如果说这本书有一句总纲，大概是：

> **工程能力的分水岭，不在"能不能让它工作"，而在"能不能知道它没有工作"。**

## 四、避坑清单（给下一个项目的 16 条）

这是全书避坑清单的合并版，**只保留那些换项目依然成立、且能直接搬走的**。

**关于失败**
- [ ] **失败必须可见。** 任何"降级 / 兜底 / 静默返回默认值"的分支，都要问一句：**它失败时，监控上看起来是变坏还是变好？** 如果看起来变好，这条分支就是定时炸弹。
- [ ] **"没有数据"和"数据是零"必须可区分。** 用 `null` / `-1` / 显式的"未知"状态，不要用 `0`。
- [ ] **回退的触发条件必须是配置，不能是故障。** 运行期自动换实现，等于让一个进程的请求跟多个后端说话——**错误日志为空，HTTP 全绿，只有一致性受损**。
- [ ] **人工输入写入失败必须让调用方知道。** 人只点一次的数据，静默吞掉就是永久丢失。检查所有"接收人工输入"的接口，`save` 是否会吞异常。
- [ ] **不要留"演示期权宜"的开关。** 假模型、mock 兜底这类东西，从"方便演示"变成"正确性事故源"只隔一个上线。**要么删掉，要么 fail-fast。**

**关于边界**
- [ ] **任何可以隐式表达业务语义的地方，都要显式化。** "字段为空表示全部"这种约定必须写在参数文档里，更好的做法是用枚举。
- [ ] **不得用无边界匹配。** 后缀匹配（`endsWith`）命中的范围比你想的宽，而**过匹配的后果是漏报**——最难被发现的失败方向。
- [ ] **降噪不得覆盖底线，顺序即优先级。** 抑制误报的机制不能抑制阻断级结论。**而且优先级要写在分层结构里，不能只写在文档里。**
- [ ] **判断差异是对的还是漂移，看它由什么决定。** 由**外部协议**决定的是对的（不同平台判重时机不同）；由 **"没抽公共代码"** 决定的是漂移（同一个功能两套实现必然分叉）。
- [ ] **同一个键，只允许有一个缺省语义。** 同一个配置项在 yml、代码默认值、注释里给出三种不同的缺省，是"看起来配好了但没生效"的标准成因。

**关于度量**
- [ ] **只看"提了多少"是虚荣指标。** 没有"其中多少是错的"这一列，**最该关掉的东西会排在排行榜第一名**——这不是信息不足，是信息足够误导。
- [ ] **数你的闭环跳数，并逐跳检查数据存活。** 每加一层聚合，就问一句"上一层的数据在这一层还在吗"。**断链最难发现的形态是：单次输出完全正常，只有跨期聚合能看到缺口。**
- [ ] **警惕单向漂移的机制。** 只有"降权"没有"回升"，或者只有"上报失败"没有"上报成功"，都会让人为补偿成为必需——而人不会来补偿。
- [ ] **会随提交变化的数字，不要手抄进文档。** 要么从源头取，要么标注"截至某次提交"。**尤其警惕"总数过期但构成看起来可核对"的写法**——它比写错更能骗过包括三个月后的你自己。

**关于交付**
- [ ] **"别人能不能跑起来"和"你能不能跑起来"是两件事。** 判据：在一台只有 Docker 的干净机器上，一条命令能不能起来。
- [ ] **动作派**和**通知派**要分开设计。**"通知某人"失败了有人会发现，"静默地改变状态"失败了没人会发现。**
