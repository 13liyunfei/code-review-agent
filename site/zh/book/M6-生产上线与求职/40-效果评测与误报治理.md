## 一、痛点

季度复盘的时候，有人问了一个很朴素的问题：

> "我们这套东西，误报率是多少？"

我在脑子里过了一遍能查到的东西：

- **单次审查**：报告里有「🚫 被抑制 N 条」区块——所以**某一次**审查有多少条被判定为误报，是查得到的；
- **周报**：`GET /api/quality-report` 能出「审查次数 / 总发现数 / 严重级别分布 / 高频规则 Top10 / 仓库分布」——**每一项都是"我们提了多少意见"**；
- **反馈**：`GET /api/feedback` 能列出全部反馈条目——**一堆流水，没有分母**。

**于是答案只能是这样**：

> "误报率……我可以手动把 feedback 列表数一遍，再跟周报的总发现数比一下。但这两个数不是同一批 PR 的，参考意义不大。"

**问题不在于"没有数据"，而在于"数据在每一跳都被丢了一部分"。** 具体地：

```
① 报告里有「被抑制 N 条」，但落"审查历史"时就丢了
② 历史里有「本次发现 M 条」，但没有「本次抑制 K 条」
③ 周报从历史聚合，所以它能算 M 的分布，算不出 K/M
④ 反馈里有"谁标了误报"，但和"哪个 PR、哪条发现"没有稳定关联（只有 ruleId/file）
```

**任何一环单独看都是"有数据的"。把它们串起来看，那个能回答问题的数字，恰好落在了没有存下来的那个字段里。**

这一讲就来把这条链路走一遍——**顺便把一个更根本的问题讲清楚：为什么"评测"这件事，对 Agent 系统比对传统系统难得多。**

## 二、原理

### 2.1 传统系统评测 vs Agent 评测：差在"标准答案在哪"

自动化测试的经典形态是：

```
输入 X（固定） → 断言 输出 == Y（固定）
```

**这个形态成立的前提是：Y 是已知的、确定的、可写下来的。**

Agent 系统直接把这个前提打破了：

| | 传统服务 | Agent 审查系统 |
|---|---|---|
| 输入空间 | 可枚举（接口参数） | **不可枚举**（任意 diff、任意语言、任意上下文） |
| 输出的正确答案 | **写在断言里** | **不存在客观答案**（"这段代码有风险吗"是判断题） |
| 单次正确性 | 可自动化验证 | **只能靠人** |
| 噪声 | 无 | **有**（同一个 diff 两次 LLM 调用结论可能不同） |
| 效果指标 | 通过率 | **召回率 / 误报率 / 采纳率** |

**最后一行是关键**：Agent 系统的效果指标里，**必然有一个"错"的分量**——不提问题是漏报，提了不是问题的是误报。而"是不是问题"**只有人能判定**。

所以：

> **人的反馈是 Agent 效果评测的唯一数据源。没有反馈闭环，"效果评测"这个词就没有落点。**

这也是为什么"反馈闭环"这件事在 Agent 项目里比在任何 CRUD 项目里都重要——它不是"用户体验优化"，**它是评测的唯一输入端**。

### 2.2 只看"提了多少"是虚荣指标，看"多少是错的"才是质量指标

把能统计的东西列出来，按"能不能反映质量"分个类：

| 指标 | 方向 | 能不能反映质量 | 为什么 |
|---|---|---|---|
| 审查次数 | ↑ | ❌ | 只反映用量 |
| 总发现数 | ↑ | ❌ **甚至是反向的** | 光提得多，可能是噪声多 |
| 每 PR 平均发现数 | — | ❌ | 同上 |
| 严重级别分布 | — | ❌ | 反映的是代码库，不是审查器的质量 |
| 高频规则 Top10 | — | ❌ **误导** | 高频≠高价值，见下 |
| **误报率** | ↓ | ✅ | 直接反映"说错了多少" |
| **漏报率** | ↓ | ✅ | 但需要 ground truth，最难拿 |
| **建议采纳率** | ↑ | ✅ | 行内 `suggestion` 的 Apply 次数——**最便宜的真值** |

**"高频规则 Top10" 是最容易让人做错决定的一个指标。** 它长这样：

```
| 规则 | 次数 |
|------|------|
| SEC-004 | 812 |
| LOGIC-011 | 640 |
| STYLE-002 | 588 |
| ...      | ...  |
```

看到这个表的自然反应是："SEC-004 提了 812 次，说明这条规则最有价值。"

**但如果 SEC-004 的 812 次里有 700 次被开发者标成误报呢？**

**那么这条规则才是第一个该被关掉的。** 而它恰好排在第一名。

**结论：没有"误报率"这一列的高频规则排行，会把最该关掉的规则放到最显眼的位置。** 这不是"信息不够"，这是**信息足够误导**。

**不过——"算出误报率"和"这个误报率可信"是两件事。** 误报率是一个**比例**，而小样本的比例置信区间宽得惊人。用二项比例的正态近似手算一档：

> **场景：一份 20 条发现的审查，人标了其中 6 条是误报 → 实测误报率 p̂ = 0.30。**
>
> - 标准误 `SE = √(p̂(1-p̂)/n) = √(0.30×0.70/20) = √0.0105 ≈ 0.102`
> - 95% 置信区间 ≈ `p̂ ± 1.96×SE ≈ 0.30 ± 0.20 → [0.10, 0.50]`
> - **这个数字对决策约等于没有**：它同时支持"10% 还好"和"一半都在误报"两种结论。
>
> 想把它收紧——季度内让误报率可信到 ±5 个百分点（宽度 0.10）：
> - 需要 `1.96×√(0.30×0.70/n) = 0.05 → √(0.21/n) = 0.0255 → n ≈ 323 条`
> - **也就是说，一个"能拿去开关规则"的误报率，需要跨约 300 条发现的累积**，而不是一份 PR 的 20 条。

| 样本量 n | p̂=0.30 时的 95% 区间 | 宽度 | 能不能做决策 |
|---|---|---|---|
| 10 | 0.30 ± 0.28 → **[0.02, 0.58]** | 0.56 | ❌ 几乎全区间 |
| 20 | 0.30 ± 0.20 → [0.10, 0.50] | 0.40 | ❌ 仍横跨"还行"和"污染" |
| 100 | 0.30 ± 0.09 → [0.21, 0.39] | 0.18 | 😐 只能看出"不是个位数" |
| 323 | 0.30 ± 0.05 → [0.25, 0.35] | 0.10 | ✅ 能作为规则的取舍依据 |

**两条规律**：① 区间宽度 ∝ `1/√n`——**想让误差减半，样本量必须翻四倍**（从 20→80，宽度才从 ±0.20 缩到 ±0.10）；② p̂=0.50 时最难测（此时 `p̂(1-p̂)` 取最大值 0.25）——靠近 0 或 1 的规则区间反而更窄，更容易测准。

> **工程判据：任何一个"比率类"指标（误报率 / 采纳率 / 命中率），在拿它开/关一条规则之前，先算一次置信区间。算出来宽度超过 0.1（10 个百分点）的，就**不要**用它做单一取舍——把它降级成"趋势信号"，只在跨期聚合到足够样本后再动作。** 这份评审它拿不了这个分数：20 条发现的单次误报率，连"这条规则该不该关"都回答不了，更别提回答"系统好不好"。

### 2.3 误报治理要区分三个不同的对象

"治理误报"听起来是一件事，其实是三件，而且**它们的手法完全不同**：

| 对象 | 问题形态 | 治理手法 | 判据 |
|---|---|---|---|
| **规则** | 某条规则系统性不准（写得太宽） | 关闭 / 降权 / 改阈值 | 跨文件、跨时间的**统计** |
| **文件** | 某条规则在某个文件上总是误报（生成代码、样板文件） | **文件级抑制** | 单点事实 |
| **Agent / 维度** | 某个维度的整体可信度低 | 降置信度 / 降仲裁权重 | 跨规则的**聚合** |

**这三种治理需要一个共同的基础设施**：反馈记录里必须能区分"这是针对规则的"还是"针对这个文件上的这条规则的"。本项目的做法是**用可选字段的有无来表达作用域**（见 3.1）——**这是一个成本极低、但语义极重的设计，必须写进文档。**

### 2.4 闭环的判定标准：从"人点了误报"到"下次不再提"，经过几跳？

这是本讲最实用的一个分析工具。**把闭环拆成跳数，然后逐跳检查"数据有没有活到下一跳"。**

本项目的完整链路（第 17 讲讲过 P0-3 修的是"第 3 跳断了"）：

> **图 40-1**　误报反馈闭环的八跳。**第 3 跳曾在此断过（已修），第 7 跳现在是断的**——而且第 7 跳更难发现：第 3 跳断的时候现象是"校准永远不生效"，可以被测试断言；第 7 跳断的时候**单份报告完全正常**，只有"跨期聚合"这一个视角能看到缺口。

**第 3 跳（校准）曾经断过，修好了（第 17 讲）。而第 7 跳是断的**——而且它断得更隐蔽，因为：

- 第 3 跳断的时候，现象是"校准**永远不生效**"——**能用测试断言"改了反馈，置信度应该变"**，可以测出来；
- 第 7 跳断的时候，现象是"**单份报告完全正常**、抑制区块也在、开发者感受不到任何问题"，**只有"跨期聚合"这一个视角能看到缺口**。而跨期聚合**没人写测试**（因为它不是一条业务路径）。

**这是"闭环"类缺陷的共同特征：越靠近数据链路末端的那一跳，越难被察觉，因为它的消费者是"分析"而不是"用户"。**

### 2.5 一道必须显式回答的问题：抑制作用域的语义

在写抑制代码之前，有四个语义必须先定下来。**这四个问题如果不显式回答，代码会用"默认行为"替你回答，而默认行为通常没人知道：**

| # | 问题 | 本项目答案 |
|---|---|---|
| 1 | **作用域**：抑制"这一行"、"这个文件上的这条规则"、还是"这条规则在所有文件"？ | **由反馈里 `file` 是否为空决定**——空 = 全仓库 |
| 2 | **时长**：永久还是过期？ | **永久**（没有 TTL、没有过期字段） |
| 3 | **优先级**：能不能抑制 BLOCKER？ | **不能**（`VetoPolicy` 把 BLOCKER 捞回来） |
| 4 | **可撤销**：标错了能不能改回来？ | **只能靠再标一条正报**（没有"撤销"接口） |

**四个问题本项目都给了答案，而且答案本身都合理。** 问题在于：**第 1 条和第 2 条的语义没有写在任何文档里，第 3 条只体现在代码里。**

**第 1 条最危险**：用户在一个文件上点了"误报"、没填 `file` 字段——他以为自己在说"**这个文件里的这条**不该报"，系统理解成"**这条规则在全仓库都不该报**"。**这两个语义的差距，就是"抑制一条噪声"和"永久屏蔽一个检查项"的差距。**

## 三、代码

### 3.1 抑制链：作用域由"一个可选字段是否为空"决定

聚合阶段的第三步是误报抑制：

```java
// core/report/ReportGenerator.java:19-28（类注释：聚合策略四条）
/**
 * 报告生成器：负责聚合发现、去重、优先级冲突仲裁、误报抑制与分级统计，产出 {@link ReviewReport}。
 *
 * <p>聚合策略（见文档）：
 * <ul>
 *   <li><b>去重</b>：同一文件 + 同一行区间 + 同一规则视为重复，保留置信度更高、严重级别更高者；</li>
 *   <li><b>冲突仲裁</b>：不同 Agent 在同一位置意见冲突时，按优先级权重（见 {@link ArbitrationPolicy}）择高，落败方进入 overriddenFindings；</li>
 *   <li><b>误报抑制</b>：命中开发者已确认误报（{@link FeedbackStore}）的发现被移入 suppressedFindings，不再计入分级；</li>
 *   <li><b>分级定档</b>：按 BLOCKER / MAJOR / MINOR / INFO 统计数量。</li>
 * </ul>
 */
```

```java
// ReportGenerator.java:142-164
// 3. 误报抑制：命中开发者已确认误报的发现移入 suppressedFindings
List<ReviewFeedback> falsePositives = feedbackStore == null
        ? List.of() : feedbackStore.falsePositives(teamId);
List<Finding> suppressed = new ArrayList<>();
List<Finding> kept = new ArrayList<>();
for (Finding f : afterArbitration) {
    if (matchesFalsePositive(f, falsePositives)) {
        suppressed.add(f);
    } else {
        kept.add(f);
    }
}

// 4. 分级统计（仅保留未被抑制的发现）
Map<Severity, Long> severityCount = new EnumMap<>(Severity.class);
for (Severity s : Severity.values()) {
    severityCount.put(s, kept.stream().filter(f -> f.severity() == s).count());
}

return new ReviewReport(prId, repo, kept, severityCount,
        runId, durationMs, arbitrationNotes, overridden, suppressed, VerificationResult.none(),
        List.of(), new ArrayList<>(degradationByStage.values()));
```

注意 `:155` 那句注释：**「分级统计（仅保留未被抑制的发现）」**——报告顶部的严重级别计数是**扣掉误报之后**的数字。这一条对"读报告"是对的（人看到的就是有效意见），但对"算误报率"是个陷阱：**分母已经被扣过了。**

匹配逻辑（这一段是本讲的核心）：

```java
// ReportGenerator.java:166-193
/**
 * 判断某发现是否命中已确认误报。
 *
 * @param f  发现
 * @param fps 误报反馈列表
 * @return 是否应被抑制
 */
private boolean matchesFalsePositive(Finding f, List<ReviewFeedback> fps) {
    for (ReviewFeedback fb : fps) {
        if (!fb.ruleId().equalsIgnoreCase(f.ruleId())) {
            continue;
        }
        if (fb.agentType() != null && !fb.agentType().isBlank()
                && !fb.agentType().equalsIgnoreCase(f.agentType().name())) {
            continue;
        }
        if (fb.file() != null && !fb.file().isBlank()) {
            boolean fileMatch = f.file().equals(fb.file())
                    || f.file().endsWith("/" + fb.file())
                    || f.file().endsWith(fb.file());
            if (!fileMatch) {
                continue;
            }
        }
        return true;
    }
    return false;
}
```

**逐行读这段，会看到三条隐含语义（都很强，但只有一条有文档）：**

**① 匹配是"三段与"：`ruleId` 必中，`agentType` 非空才参与，`file` 非空才参与。**

```java
if (fb.agentType() != null && !fb.agentType().isBlank() && !...) continue;   // 空 → 不参与匹配
if (fb.file()      != null && !fb.file().isBlank())        { ... }            // 空 → 不参与匹配
```

`agentType` 为空的语义**有文档**：

```java
// api/FeedbackRequest.java:8-13
 * @param ruleId          规则 ID（必填，如 SEC-001）
 * @param agentType       来源 Agent 类型（可选，如 SECURITY；为空表示适用全部）
 * @param isFalsePositive 是否误报（true=误报，false=确认有效）
 * @param note            备注（可选）
 * @param file            关联文件（可选，用于文件级精准抑制）
 * @param teamId          团队标识（可选，缺省回退默认团队，用于按团队隔离反馈）
```

**"`agentType` 为空表示适用全部"——写清楚了 ✅。**

`file` 为空的语义**没写**：`@param file 关联文件（可选，用于文件级精准抑制）` 只说了"填了它会怎样"（文件级精准），**没说"不填会怎样"**。

而实现里，`file` 为空 = **不参与匹配** = **该规则在任何文件上都被抑制**。

**两段代码的结构完全一样，文档一半写了一半没写。** 而这两半的后果差异极大：

| 字段 | 为空时实际含义 | 后果 | 有文档？ |
|---|---|---|---|
| `agentType` | 该规则对所有 Agent 适用 | 合理（同一规则通常只由一个 Agent 产出） | ✅ |
| **`file`** | **该规则在全仓库所有文件上都被抑制** | **可能永久屏蔽一个检查项** | ❌ |

**修法：把缺省语义写进文档（一个字段的注释就能解决），或者更彻底——把作用域变成一个显式字段。**

<img class="mermaid-svg" src="/zh/book-assets/diag-0097.svg" alt="修法：把缺省语义写进文档（一个字段的注释就能解决），或者更彻底——把作用域变成一个显式字段。" />

**判据：任何"字段为空"承载业务语义的地方，都要问一句"这个缺省语义有人知道吗？"。** 能写进参数的 `@param` 就写；写不下就用枚举显式表达。

**② 文件名匹配有后缀过匹配。**

```java
boolean fileMatch = f.file().equals(fb.file())
        || f.file().endsWith("/" + fb.file())
        || f.file().endsWith(fb.file());
```

三级 fallback 的意图是"尽量匹配上"（同名的相对路径/绝对路径差异）。但第三级 `endsWith(fb.file())` **没有边界**：

```
fb.file() = "Service.java"            （用户只填了文件名）
f.file()  = "src/main/java/com/x/PaymentService.java"
→ "src/main/java/com/x/PaymentService.java".endsWith("Service.java") == true
→ 抑制

而用户想抑制的是：
f.file()  = "src/main/java/com/x/UserService.java"   ← 也被抑制了
```

**一次以"文件名"为作用域的误报标记，会连带抑制同一仓库下所有以 `Service.java` 结尾的文件上的该规则发现。** 而 `Pay/User/OrderService.java` 在 Java 项目里遍地都是。

**诚实地说**：第二级 `endsWith("/" + fb.file())` 是有边界的（要求路径分隔符），可以挡住大部分；但第三级没有。**所以"填了文件名"这个用法本身就带着一档不可忽略的过匹配风险。**

**危险方向要说清楚**：过匹配的后果是**该报的没报**（漏报），而漏报是这类系统里**最难被发现的失败**——开发者不会为"你没提这条意见"来投诉（第 36 讲那三类"看不见的失败"的同类）。

**修法**：第三级要么去掉，要么加边界条件：

```java

        || f.file().endsWith("/" + fb.file());
// 若确实要支持"只填文件名"，就要求 fb.file() 不含 '/' 时按 basename 精确比较：
//     || Path.of(f.file()).getFileName().toString().equals(fb.file())
```

**③ 这条链是 O(发现数 × 误报条数) 的嵌套循环。**

`:174` 的 `for` 在**每一次** `matchesFalsePositive` 调用时都从头遍历 `fps`。发现数几十、误报几十时无所谓；但它和 3.6 节的全量拉取叠加后，就变成"每次审查 × 每条发现 × 全量反馈"。**这里不是性能问题，是"复杂度随历史增长"的写法**——值得在代码评审里被点出来。

### 3.2 BLOCKER 免疫：抑制不是"最高优先级"

**`VetoPolicy` 把已被抑制的发现再筛一遍：可否决的（BLOCKER）"救回来"（`rescued`），其余保持被抑制。**

所以抑制链是**两道**：

```
① ReportGenerator：按 ruleId + agentType + file 匹配 → 移入 suppressed
② VetoPolicy     ：把 suppressed 里的 BLOCKER 捞回来
```

**这个顺序是对的，而且理由很硬**：

> **"开发者说这是误报"是一个统计事实；"这条是 BLOCKER"是一个安全论断。前者不该覆盖后者。**

因为误报标记是**低成本、可误操作、永久生效**的（见 2.5），而 BLOCKER 意味着"禁止合入"。**如果一次手滑的误报标记能永久屏蔽掉某个 BLOCKER 类检查，那就是把"防止事故的机制"交给了"一次点击"。**

**这一条值得作为正面教材记住**：**在"降低噪声"和"守住底线"冲突时，底线优先，而且这个优先级要写在代码的分层结构里，不能只写在文档里。** `VetoPolicy` 是一个独立的、在 `ReportGenerator` **之后**执行的策略类——**顺序即优先级**。

### 3.5 校准：一条"单向下调"的曲线，而且跨实例不收敛

第 17 讲修好的那个 P0（校准空转）在这里展开。先看它的核心算法：

```java
// core/calibration/ConfidenceCalibrationService.java:37-38
/** 规则准确率下界：一次误报最多把置信度折到 0.5，保留规则继续参与聚合的资格。 */
static final double MIN_ACCURACY = 0.5;
```

```java
// ConfidenceCalibrationService.java:59-84
/**
 * 开发者标记“误报”后调用：降低该规则的置信度基准（指数衰减，下限 {@link #MIN_ACCURACY}）。
 */
public void markFalsePositive(String ruleId) {
    if (ruleId == null || ruleId.isBlank()) {
        return;
    }
    // 首次误报直接落到 0.8，之后每次乘 0.9 衰减，但不再低于 0.5（防一票否决）
    ruleAccuracy.merge(ruleId, 0.8, (old, v) -> Math.max(MIN_ACCURACY, old * 0.9));
    persist();
}

/**
 * 开发者标记“正报”后调用：提升该规则的置信度基准（指数回升，封顶 1.0）。
 */
public void markTruePositive(String ruleId) {
    if (ruleId == null || ruleId.isBlank()) {
        return;
    }
    ruleAccuracy.merge(ruleId, 1.0, (old, v) -> Math.min(1.0, old * 1.05));
    persist();
}
```

**先算清楚这条曲线。** `Map.merge(key, value, remapping)` 的语义是：**键不存在时存 `value`；存在时用 `remapping(old, value)`。** 所以：

| 反馈序列 | `ruleAccuracy` 变化 |
|---|---|
| 初始（`accuracy()` 的 `getOrDefault(..., 1.0)`） | **1.0** |
| 第 1 次误报 | **0.8**（`value` 生效，不是 `1.0 × 0.9`） |
| 第 2 次误报 | `max(0.5, 0.8 × 0.9)` = **0.72** |
| 第 3 次 | **0.648** |
| 第 n 次 | `max(0.5, 0.8 × 0.9^(n-1))` → **趋近并停在 0.5** |

**停在下界 0.5。** 我用算术确认一下"多少次到下限"：需要 `0.8 × 0.9^(n-1) ≤ 0.5` → `0.9^(n-1) ≤ 0.625` → `n-1 ≥ ln0.625 / ln0.9 = (-0.4700) / (-0.10536) ≈ 4.46` → **n = 6 次误报就到下限**。（`0.8×0.9^5 = 0.8×0.59049 = 0.4724 < 0.5` ✅）

**于是有两条结论，一条正面一条负面：**

**①（正面）防一票否决是有效的。** 被标 6 次误报以上的规则，准确率**仍然有 0.5**，`calibrate(ruleId, rawConfidence)` 最多把置信度折半（`:93-97`）：

```java
public double calibrate(String ruleId, double rawConfidence) {
    double accuracy = accuracy(ruleId);
    double calibrated = rawConfidence * accuracy;
    return Math.min(1.0, Math.max(0.0, calibrated));
}
```

**一个 100% 误报的规则，永远保留 50% 的置信度。** 这既是设计意图（"保留规则继续参与聚合的资格"，`:37` 的注释），也意味着：**"关掉一条规则"这件事，不能靠校准自动完成——必须有人显式去关。** 这在产品上是对的（关规则要人决定），但要**明确知道这个边界**：校准只能降权，不能淘汰。

**②（负面）正报是"单向上调且只在被误报过之后才有效果"。**

`markTruePositive` 的 `merge(ruleId, 1.0, (old,v) -> min(1.0, old*1.05))`：
- 对**从未被误报过**的规则（值本来就是 1.0）→ `min(1.0, 1.0×1.05) = 1.0` → **毫无效果**（而且会把这个 1.0 **实体化**写进快照）。
- 对**被误报削过**的规则 → 乘性回升。从 0.5 回到 1.0 需要 `1.05^n ≥ 2` → `n ≥ ln2/ln1.05 = 0.6931/0.04879 ≈ 14.2` → **15 次连续正报**。

**所以"越用越准"这句话在这个项目里的准确含义是：误报让它降得快（6 次到底），正报让它回得慢（15 次回满）。** 这是**保守**的偏向（宁可低估规则的准确性），合理；但：

- **真实使用中，人只会标误报，很少标正报**（这条意见对了是默认预期，不值得点一下）。所以 `markTruePositive` 在实践中的触发频率**远低于** `markFalsePositive`。
- 结合"没有过期"（2.5 节第 2 条）：**一条规则一旦被误报削下去，几乎不会自己回升**。

**修法方向**：给准确率加**时间衰减**（一段时间没有新误报就向 1.0 靠拢），而不是只靠正报抬升。这比"等人去点正报"现实得多。

```java
ReviewFeedback feedback = new ReviewFeedback(

        request.agentType() == null ? "" : request.agentType().trim(),
        request.isFalsePositive(),
        request.note() == null ? "" : request.note().trim(),
        request.file() == null ? null : request.file().trim());
feedbackStore.save(teamId, feedback);
log.info("[API] 团队 {} 收到反馈：ruleId={}，agentType={}，误报={}，文件={}",
        teamId, feedback.ruleId(), feedback.agentType(), feedback.isFalsePositive(), feedback.file());
return ResponseEntity.ok(Map.of(
        "status", "accepted",
        "team", teamId,
        "ruleId", feedback.ruleId(),
        "isFalsePositive", feedback.isFalsePositive()));
```

**`save` 不抛异常**（它在内部 `catch` 掉了），所以**落库失败时接口照样返回 `200 accepted`**，而调用方还会打一行 `[API] 收到反馈` 的 `info` 日志。

**后果**：

```
PG 写入失败（表不存在/连接中断/JSONB 序列化异常）
  → PgFeedbackStore 打一条 WARN
  → 接口返回 200 accepted + "收到反馈" info 日志
  → 开发者以为标记成功了
  → 【这条反馈永久丢失，下次审查照样提这条"误报"】
```

**而且这里的"丢"比别处更贵**：反馈是**人工输入**（有人花了时间点这一下），而不是机器产生的数据。**丢了没有第二次机会**——人不会再点一遍。

对比第 38 讲 `ReviewWorkflowEngine` 忽略 `createCommitStatus` 返回值：**同一个病（外部动作失败但对外声称成功），只是这次发生在"入"的方向而不是"出"的方向。**

**修法**：`FeedbackStore.save` 的契约改成"失败即抛"（或返回 `boolean`），接口在失败时返回 `5xx`：

```java
// 修法示意（不是仓库现状）
// FeedbackStore: void save(...) throws StorageException
// ReviewApiController:
try {
    feedbackStore.save(teamId, feedback);
} catch (Exception e) {
    log.error("[API] 反馈落库失败，已拒绝：team={}, ruleId={}", teamId, feedback.ruleId(), e);
    return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
            .body(Map.of("error", "feedback persistence failed, please retry"));
}
```

**判据（贯穿本书的一条）：凡是"用户手输/手点产生、且不会再来第二次"的数据，写入失败必须让调用方知道。**

### 3.6 误报标记存在 JSONB 里，所以"只取误报"在 SQL 层做不到

回到 3.1 节那句 `feedbackStore.falsePositives(teamId)`。看它的实现：

```java
// core/feedback/FeedbackStore.java:32-40（接口 default 方法）
/**
 * 获取某团队所有被标记为“误报”的反馈，供聚合阶段抑制使用。
 *
 * @param teamId 团队标识
 * @return 误报反馈列表
 */
default List<ReviewFeedback> falsePositives(String teamId) {
    return list(teamId).stream().filter(ReviewFeedback::isFalsePositive).toList();
}
```

**默认实现是"拉全量 → 内存过滤"。而 `PgFeedbackStore` 没有覆写它。** 所以生产上走的就是这条路径：

```java
// core/store/PgFeedbackStore.java:14-21（类注释，它自己的说明）
/**
 * PostgreSQL 反馈存储（多机集群共享实现）。
 *
 * <p>每条反馈一行（{@code review_feedback}），按团队读取全量列表——与既有
 * {@code FeedbackStore} 语义一致（数据量小、低频写入，不做分页）。
 *
 * @param listener 落库监听器（可 null），save 后驱动置信度校准等旁路
 */
```

```java
// PgFeedbackStore.java:51-61
@Override
public List<ReviewFeedback> list(String teamId) {
    try {
        return db.query("SELECT payload FROM review_feedback WHERE team_id = ? ORDER BY id",
                rs -> mapper.readValue(rs.getString(1), new TypeReference<ReviewFeedback>() {
                }), teamId);
    } catch (Exception e) {
        log.warn("[Feedback] 反馈读取失败（返回空）：team={}, 原因={}", teamId, e.getMessage());
        return new ArrayList<>();
    }
}
```

**★ 注释里有一处逻辑错位，值得单独指出来：**

> "按团队读取全量列表——与既有 `FeedbackStore` 语义一致（**数据量小、低频写入，不做分页**）"

**"低频写入"是关于写的前提，而它被用来解释"读不做分页"这个读的设计。** 但读的频率不是写决定的：

| | 频率 |
|---|---|
| 写（人标误报） | **低频** ✅ 注释说的对 |
| **读（每次审查）** | **每次都读**（`ReportGenerator:143-144` 在聚合阶段无条件调用） |

**低频写不等于低频读。** 而这条读路径：
- **没有 LIMIT**（`ORDER BY id` 但无上限）；
- **随历史单调增长**（反馈只增不删，没有归档、没有 TTL）；
- **每次都要反序列化全量**（`mapper.readValue` 逐行）。

**★ 而它无法被优化的根因在数据结构上**：

```sql
-- PgDb.java:144-150（建表）
CREATE TABLE IF NOT EXISTS review_feedback (
    id         BIGSERIAL PRIMARY KEY,
    team_id    TEXT NOT NULL,
    payload    JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
)
```

**整条反馈（含 `isFalsePositive`、`ruleId`、`agentType`、`file`）都在 `payload JSONB` 里。** 所以：

```sql
-- 想这么写，但做不到（isFalsePositive 在 JSONB 里，且没有可用的表达式索引）
SELECT payload FROM review_feedback
WHERE team_id = ? AND payload->>'isFalsePositive' = 'true';
```

**"只取误报"这件事被数据结构挡在了 SQL 层之外**——只能在应用层把全量拉回来再过滤。

**修法（这是第 37 讲那个"jsonb payload + 冗余列"模式的复用）**：

```sql
-- 修法示意（不是仓库现状）
ALTER TABLE review_feedback ADD COLUMN is_false_positive BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE review_feedback ADD COLUMN rule_id  TEXT;
ALTER TABLE review_feedback ADD COLUMN agent_type TEXT;
ALTER TABLE review_feedback ADD COLUMN file_path TEXT;
CREATE INDEX IF NOT EXISTS idx_feedback_team_fp
    ON review_feedback (team_id, is_false_positive) WHERE is_false_positive;
```

然后 `falsePositives` 覆写成 `SELECT payload FROM review_feedback WHERE team_id=? AND is_false_positive` —— **从"每次审查拉全量"变成"只拉那十几条误报"**，而且这个数字**不随历史增长**（误报条数是有界的）。

**★ 这个发现链值得完整记一遍，因为它是"一个数据结构选择如何决定一条查询的性能曲线"的教科书案例**：

```
JSONB-only 建模
   → 无法在 SQL 层过滤"误报"
   → 只能全量拉取 + 内存过滤
   → 每次审查都付这份成本
   → 且成本随历史单调增长（没有上限、没有归档）
   → 而注释把"低频写"当成了"读可以不做优化"的理由
```

**顺带一个更省事的替代修法**（零 SQL 改动）：**在 `ReportGenerator` 之外缓存一层**——把 `falsePositives(teamId)` 的结果按团队缓存几十秒（第 32 讲的 `PricingService` 双检锁那套现成模式）。但**这只是缓解，根因还是 JSONB-only**。

### 3.7 测试数：三个数字，只有一个是真的

"效果评测"里最容易被忽略的一项——**你自己的测试到底有多少**。这个项目里散着三个数字：

| 出处 | 数字 | 性质 |
|---|---|---|
| `docs/test-report-p0-fixes-2026-09-02.md:58-59` | **162 例**（37 类） | 当时的真实值，**已过时** |
| `docs/interview-walkthrough.md` 第 0 节 | **296 例**（281 基线 + 15 例本轮治理新增） | 当时的真实值，**已过时** |
| **surefire 报告实测** | **Tests run: 338 / Failures: 0 / Errors: 0 / Skipped: 0，67 个测试类** | **当前真值** |

**而 `grep -c "@Test"` 会数出 342 个**（`@Disabled` 为 0、`@ParameterizedTest` 为 0），比实际执行数多 4 个。

**所以"测试有多少"这个问题，有三种答法，只有一种是对的：**

```
❌ 抄文档里的数字      → 抄到的是 162 或 296（都过时了）
❌ grep "@Test" 数注解  → 342（不代表实际执行数）
✅ 读 surefire 报告     → 338（Tests run 那一行）
```

**判据：任何会随提交变化的数字，都不能手抄进文档——要么每次从源头取，要么在文档里写清"截至某次 commit"。** 三个数字并存的最坏后果不是"某个数字错了"，而是**读者不知道该信哪个，于是哪个都不信**。

**而"测试多"本身也不等于"效果好"。** 这个项目里更有意义的一类测试是这几类：

| 类别 | 例子 | 它保证的是什么 |
|---|---|---|
| **行为契约测试** | `CoordinatorTimeoutDegradationTest`（4 例）：慢 Agent 阻塞 5s，断言 ~300ms 超时即返回报告、降级进报告、健康 Agent 不受影响 | **降级路径真的会被触发** |
| **闭环保真测试** | `CalibrationFeedbackLoopTest`（8 例）：一次误报 → `accuracy==0.8` 且 `calibrate("SEC-001", 0.9)==0.72`；50 次误报后仍 ≥0.5；正报封顶；**快照重启恢复** | **数据链路真的通到底** |
| **防复发门禁** | `DeadCodeGuardTest`：main 里"生产零引用且非豁免"的类型直接让 CI 失败 | **一类问题不会再出现** |

**这三类比"数量"重要得多**，因为它们各自锁定了一类**只会在生产上显现的失败**：降级不触发、闭环断在中间、死代码复活。

**特别是 `DeadCodeGuardTest` 这一类"门禁型测试"**——它不是验证某个功能，而是**给自己加约束**。这个项目的历史是：清理了 `core/mq/`（664 行从未接线的 MQ 子系统）、`core/tool/ToolDefinition`（9 个"纸面工具"只有声明没有实现）、以及若干 `@Component` 孤儿，**然后加了这个门禁防止复发**。

**门禁的价值在于：它把一次性的清理工作，变成了永久性的约束。** 这是"评测"这个概念的延伸——**不只评测功能，也评测"工程纪律有没有退化"。**

## 四、避坑清单

- [ ] **误报率必须能跨期算出来。** 检验方法：从"原始反馈表"和"审查历史表"出发，**只用 SQL/接口能不能算出过去 7 天的误报率**？算不出来就说明数据链路上有字段丢了。
- [ ] **落历史时不要只存"结论"**：`ReviewHistoryEntry` 这类"给聚合用"的记录，要带上**分母与分子**（发现数 + 抑制数），否则下游永远算不出比率。
- [ ] **"没有数据"和"数据是零"必须可区分**。老记录缺新字段时补 `-1`（未知）而不是 `0`，否则统计会系统性偏低。
- [ ] **高频规则排行必须带"误报率"列**。没有这一列，**最该关掉的规则会排在第一名**——这比"信息不足"更糟，它是误导。
- [ ] **区分三类治理对象**：规则（统计驱动，跨文件跨期）、文件（单点事实）、Agent/维度（聚合）。反馈记录里必须能表达"这次误报是针对规则的还是针对这个文件的"。
- [ ] **任何"字段为空"承载业务语义的地方，都要在参数的 `@param` 里写清缺省含义**。更好的做法是用显式枚举（`SuppressScope`）替代"字段空不空"。本项目：`agentType` 写了"为空表示适用全部"，**`file` 没写"为空 = 全仓库抑制"**。
- [ ] **文件匹配不要用无边界后缀**（`endsWith(name)`）。它会命中的同类文件比你想的多，而**过匹配的后果是漏报**——最难被发现的失败方向。
- [ ] **抑制作用域、时长、优先级、可撤销性——四项都要显式定死并写进文档。** 本项目：作用域（由 `file` 定）、永久（无 TTL）、**BLOCKER 免疫**（`VetoPolicy` 捞回）、只能靠再标正报撤销。
- [ ] **降噪机制不能覆盖底线机制**：误报抑制不得抑制 BLOCKER。**顺序即优先级**——把"底线策略"放在"降噪策略"之后执行。
- [ ] **抑制必须留痕**（报告里列出被抑制的条目），否则就是**静默丢意见**。
- [ ] **人工输入的数据，写入失败必须让调用方知道**。反馈是"人花了时间点一下、不会再来第二次"的数据，`save` 内部吞异常 + 接口返回 `200 accepted` = **永久丢失**。对照检查：所有"接收人工输入"的接口，`save` 是否可能吞异常。
- [ ] **派生状态的多实例一致性**：只读一次、运行期不重载 + 全量推快照 = **实例间互相覆盖 + 学到的东西不收敛**。要么按 key 增量写（让存储层做合并），要么定期重载。
- [ ] **隔离边界必须一致**。本项目：反馈存储按团队、抑制按团队、**校准全局**——同一个功能里出现了第三种口径。
- [ ] **别用"低频写"论证"读可以不优化"**。写频率和读频率是两个独立的量。**核对方法：这个读路径在业务主链路上被调用一次还是每次请求都调用？**
- [ ] **关注"读路径的成本曲线"**：它是否随历史单调增长？有没有 LIMIT / 归档 / TTL？**根因常常在数据结构**（JSONB-only → 无法在 SQL 层过滤 → 只能全量拉）。
- [ ] **校准要有"回得来"的机制**。只有"误报降权、正报升权"而人又很少标正报时，准确率会**单向漂移到底**且几乎不回升。加时间衰减，别指望人工补偿。
- [ ] **测试数不要手抄**：会随提交变化的数字必须从源头取（surefire 的 `Tests run`），或者标注"截至某次 commit"。**grep 注解 ≠ 执行数**（本项目 342 vs 338）。
- [ ] **优先写三类测试**：行为契约（降级真的会触发）、闭环保真（链路通到底）、防复发门禁（纪律不退化）。**它们比"数量"重要得多。**

## 五、动手任务

> **任务：把"误报率"从一个只能手算的数，变成一个能查询的数。**
>
> 仓库位置：`code-review-agent / main`
>
> 具体动作（四步，每步都能单独验证）：
>
> 1. **给 `ReviewHistoryEntry` 加一个抑制计数字段**（建议用 `int suppressedCount`，并约定缺失时为 `-1` 表示"未知"），在写历史的地方把 `report.getSuppressedFindings().size()` 传进去。

> 3. **把反馈的误报标记提成冗余列**：给 `review_feedback` 加 `is_false_positive BOOLEAN`、`rule_id TEXT`（建议再加 `file_path`），建部分索引，并覆写 `PgFeedbackStore.falsePositives(teamId)` 让它走 `WHERE team_id=? AND is_false_positive`。
> 4. **让反馈落库失败可见**：改 `FeedbackStore.save` 的契约（抛异常或返回 `boolean`），`ReviewApiController` 在失败时返回 `503` 而不是 `200 accepted`。
>
> **预期结果（都能自证）：**
> - **第 1、2 步之后**：连续跑几个 PR、标几条误报 → 调 `GET /api/quality-report?range=all` → **表里出现"误报率"列**，且那个被标了多次误报的规则，它的误报率明显高于其他规则。
> - **第 3 步之后**：打印 `PgFeedbackStore.falsePositives(teamId)` 实际执行的 SQL（或在 PG 里开 `log_statement=all`）→ **确认不再出现"全表扫该团队所有反馈"**；再对比改造前后调用的耗时（历史几百条时差距应该开始显现）。
> - **第 4 步之后**：把 `review_feedback` 表临时改个名（或停掉 PG）→ 提交一条反馈 → **接口应返回 `503`，而不是 `200 accepted`**；然后恢复表名，确认正常路径仍然 `200`。
> - **验证"未知"的处理**：把第 1 步之前的旧历史（`suppressedCount = -1`）和新的历史混在一起算误报率 → **确认旧记录被排除在分母之外，而不是被当成 0**。
>
> **加分项 A**：给"高误报率规则"加一个自动告警——某个规则在最近 N 次审查中累计误报率超过阈值时，在周报顶部标出来（**注意：只提示，不自动关规则**——关规则是要人决定的）。
>
> **加分项 B**：把 `ConfidenceCalibrationService` 的 `ruleAccuracy` key 从 `ruleId` 改成 `(teamId, ruleId)`，迁移 `calibration_accuracy` 表（加 `team_id` 列 + 复合主键），并补一个测试断言"团队 A 的误报不影响团队 B 的置信度"。

## 本讲小结

1. **Agent 效果评测与传统系统的根本差别**：输出的"正确答案"不存在客观形式，**只能由人判定**。所以**人的反馈是效果评测的唯一数据源**——反馈闭环在这个领域不是"体验优化"，是**评测的输入端**。
2. **只看"提了多少"是虚荣指标，而且会误导**：**"高频规则 Top10"没有误报率列时，最该关掉的规则会排在第一名。** 这不是信息不足，是**信息足够误导**。
3. **误报治理有三个不同对象**：规则（统计驱动）、文件（单点事实）、Agent/维度（聚合）。反馈记录必须能表达"这次是针对哪个对象的"。
4. **闭环的判定工具是"数跳数并逐跳检查数据存活"**。本项目 8 跳，**第 3 跳（校准）曾断、已修**（第 17 讲）；**第 7 跳（落历史）是断的**——而且它比第 3 跳更难发现，因为**单份报告完全正常，只有"跨期聚合"这一个视角能看到缺口**。
5. **★ 第 7 跳的证据**：`ReviewHistoryEntry` 是 `(prId, repo, runId, timestamp, findings)` —— **五个字段，没有抑制计数**。所以 `QualityTrendReporter` 的五项输出（审查次数/总发现数/严重级别分布/高频规则 Top10/仓库分布）**没有一项是误报**。修法只是给 record 加一个字段（并用 `-1` 区分"未知"与"零"）。
6. **★ 抑制作用域由一个可选字段是否为空决定**：`matchesFalsePositive:182-189` 里 `file` 非空才参与匹配 → **不填 = 该规则在全仓库所有文件上被抑制**。而 `FeedbackRequest:12` 的文档只写了"可选，用于文件级精准抑制"，**没说缺省语义**。对照 `agentType`（`FeedbackRequest:9`："为空表示适用全部"）——**同一套语义，一半写了文档一半没写**。
7. **★ 文件名后缀匹配过匹配**：`f.file().endsWith(fb.file())` 无边界 → 反馈填 `Service.java` 会连带抑制所有 `*Service.java`。**过匹配的后果是漏报**，而漏报是最难被发现的失败方向。
8. **★ 抑制链是两道，顺序即优先级**：`ReportGenerator` 抑制 → `VetoPolicy` **把 BLOCKER 捞回来**。理由很硬：**"开发者说这是误报"是统计事实，"这条是 BLOCKER"是安全论断，前者不该覆盖后者。** 这条要作为正面教材：**降噪不得覆盖底线，而且优先级要写在分层结构里，不能只写在文档里。**
9. **单份报告的抑制是可追溯的** ✅：`ReviewReport:280-293` 渲染出「🚫 被抑制 N 条」并逐条列出（规则 + 文件:行 + 来源 Agent）。**抑制留痕这一步做对了**——否则就是静默丢意见。
10. **★ 校准是"单向下调"的曲线**：`Map.merge` 的语义使首次误报直接落 **0.8**（不是 `1.0×0.9`），之后 `×0.9` 衰减、**6 次到下限 0.5**；正报 `×1.05`，从 0.5 回到 1.0 需要 **15 次**。而现实中**人只会标误报、很少标正报** → 准确率会**单向漂移到底且几乎不回升**。而且校准**只能降权、不能淘汰**（下限 0.5 意味着一票永远不会被否决）。**修法方向：给准确率加时间衰减。**
11. **★「A 机的学习 B 机同样生效」只在重启后成立**：`load()` 只在构造器里调用一次、**运行期永不重载**，而 `persist()` 是**全量推自己的 map**。后果：两个实例各学各的，**同一条规则的更新互相覆盖（lost update）**，且**直到重启都不收敛**。
12. **★ 校准不区分租户，而抑制和反馈存储都按团队隔离**：同一功能里出现了**第三种隔离口径**。`@param teamId（当前校准按规则全局生效，不区分团队）` 这条注释是诚实的 ✅，但它暴露的冲突是真的——**A 团队的偏好会削弱 B 团队的门禁**。
13. **★ 反馈落库失败是全静默的**：`PgFeedbackStore.save` 内部 `catch` 掉异常只打 WARN，而接口返回 **`200 accepted` + 一行"收到反馈"的 info**。后果是**人工输入永久丢失且没人知道**。**判据：人只做一次、不会重做的输入，写入失败必须让调用方知道。**
14. **★ 误报标记存在 JSONB 里，导致"只取误报"无法在 SQL 层完成**：`falsePositives` 的默认实现是"全量拉取 + 内存过滤"，`PgFeedbackStore` 没覆写。**而它的类注释用"低频写入"来解释"读不做分页"**——**低频写不等于低频读**：写是人手点的（低频），读是每次审查都走的（每次）。
    > **完整链条**：JSONB-only 建模 → SQL 无法过滤 → 全量拉取 → 每次审查都付 → **成本随历史单调增长（无 LIMIT、无归档）**。修法是第 37 讲那个"jsonb payload + 冗余列"模式的复用。
15. **测试数有三个版本，只有 surefire 是真的**：旧文档 **162**、面试手册 **296**、**surefire 实测 338（67 类）**，而 `grep -c "@Test"` 会数出 **342**。**任何随提交变化的数字都不能手抄进文档。** 比"数量"更值得看的是三类测试：**行为契约**（降级真的会触发）、**闭环保真**（链路通到底，如 `CalibrationFeedbackLoopTest` 8 例）、**防复发门禁**（`DeadCodeGuardTest`）。
16. **门禁型测试把一次性的清理变成永久约束**——这是"评测"的延伸：**不只评测功能，也评测工程纪律有没有退化。**
