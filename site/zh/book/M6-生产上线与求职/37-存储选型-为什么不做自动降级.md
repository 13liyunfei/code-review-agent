# 第 37 讲 · 存储选型：为什么不做自动降级

> 📌 本讲代码锚点：`code-review-agent / core/store/{StateStoreConfig,PersistenceConfig,PgDb}.java`、`core/memory/PgVectorMemoryStore.java`、`core/rag/PgKnowledgeStore.java`、`config/{InfrastructureConfig,CoreHealthIndicator}.java`、`api/HealthController.java`、`src/main/resources/application.yml`
> 🎯 导读问题：**"你的系统为什么不做多存储自动降级？"** —— 多数人会答"做了更健壮"。这个项目答的是**反过来**：那是制造一整类"看起来正常"的故障。能把这个反过来讲清楚的人，是真的运维过线上。

## 一、痛点

改造之前，这个项目把审查状态（断点、经验、反馈、历史、校准、团队配置、轨迹、知识元数据）存在 `data-dir` 下的**本地 JSON 文件**里。

单机跑得好好的。直到我们想开第二个实例。

上线第三天，运维来问：

> "你们这个服务是不是有时候会重跑？同一个 PR 我看到审了两遍。"

不是有时候。是**每次请求落到另一个实例时**：

```
实例 A 审了 PR #12，把断点写到 A 机磁盘的 ./data/resume/xxx.json
PR 分支推了个新 commit，webhook 重投 → 负载均衡打到实例 B
实例 B 找不到断点 → 从头再审一遍（5 个 Agent 全量重跑）
```

而更隐蔽的是**经验库**：A 机从反馈里学到的经验，B 机永远看不见。**你以为系统在"越用越准"，实际上两个实例正在各自收敛到两个不同的答案。**

于是改造方向很清楚：**把状态收敛到 PG**。改造也确实做完了——`PgDb` + 8 张状态表 + 8 个 `Pg*Store` 实现。

但真正让我在评审会上卡了二十分钟的，不是"要不要用 PG"，而是另一个问题：

> **"如果 PG 连不上，是不是自动退回内存模式？"**

这个问题当时已经有一半的代码如下回答"是"了。而正确答案是**坚决不**。这一讲就是讲清楚为什么。

## 二、原理

### 2.1 「多实现」有两种，一种无害，一种致命

先把"可插拔存储"这件事拆开。它其实包含两种完全不同的机制：

| | 谁在决定用哪个实现 | 决定的时机 | 判定依据 |
|---|---|---|---|
| **A. 配置驱动的选择** | 部署的人 | **进程启动时，一次性** | 配置文件里写了什么 |
| **B. 运行期的自动降级** | 程序自己 | **每次操作时，可能是每次请求** | 运行时探测到"那个后端现在不行" |

**A 是无害的**：它只是把"用哪个实现"变成一个部署参数。同一个 jar，写 `pgvector.enabled=true` 就上 PG，写 `false` 就是本地单机。**关键性质是：它在启动那一刻就定死了，之后再也不变。** 一个跑起来的进程，从头到尾只跟一个后端说话，没有"有时候是 A、有时候是 B"。

**B 是致命的**，因为它把一个**部署期决策**变成了**运行期决策**。而运行期决策一旦由"故障"触发，你就得到了这样一条时间线：

> **图 37-1**　B 类降级的完整时间线。**用户看到的是全部 200 OK**——没有一条错误日志、没有一次告警、没有任何重试，只有一条数据静静地躺在一个即将随进程消失的内存对象里。**这就是它最难查的原因：它没有故障形态。**

**用户看到的是全部 200 OK。** 没有一条错误日志、没有一次告警、没有任何重试——只有一条数据静静地躺在一个即将随进程消失的内存对象里。

### 2.2 为什么这类故障最难查：它没有"故障形态"

我们习惯的故障信号是**报错**。所以我们的排查工具、告警规则、监控看板，全部围绕"有没有报错"来建。

而 B 类降级的特征是：**它把"失败"翻译成了"成功"**。

| 你会去查的 | 实际发生的事 | 你看到的结果 |
|---|---|---|
| 错误日志 | 没有异常，代码按设计走了降级分支 | 空 |
| HTTP 状态码 | 降级分支同样返回 200 | 全绿 |
| 数据库连接数 | 降级之后根本不连 PG 了 | **连接数下降** |
| 磁盘/内存 | 内存实现就是往 `ConcurrentHashMap` 里放 | 内存平稳 |
| 数据一致性 | A 机沉淀 B 机看不见 | **这一项你平时不查** |

**注意倒数第二行**：连接数下降。在一个"看资源指标"的监控体系里，连接数下降是**好事**的方向。也就是说——

> **B 类降级在监控上的表现，与"系统变健康了"完全一致。**

这就是我所说的"一整类看起来正常的故障"：它不是让你看到坏消息，它是**让你看不到消息**。

### 2.3 那为什么还有人做自动降级？因为它在开发期是真的爽

必须公平地说：`pgvector.enabled=false` 时自动退回内存，**在本地开发时的体验确实很好**——不用装 PG，`git clone && mvnw spring-boot:run` 就能跑。

但这个"方便"一旦延伸为"连不上就自动退"，代价就变成：

```
开发机的行为（没装 PG）  = 内存实现
生产机的行为（PG 正常）  = PG 实现
生产机的行为（PG 抖动）  = 内存实现   ← 这一条是新引入的
```

**第三条是前两条里都不存在的东西。** 你在本地永远演练不到它（本地 PG 一直"不在"，走的是配置路径，不是降级路径）；而在生产上它只在"恰好出事"的时候出现。

**本地验过的路径，不是线上跑的路径。** 那么"本地能跑"这个便利，值不值得用一条只有生产才会触发的隐式分支去换？

### 2.4 判据：回退的触发条件必须是「配置」，不能是「故障」

把上面的分析收成一条可执行的规则：

> **允许按配置切换实现；不允许按运行时故障切换实现。**
>
> 配置说用 PG，就连不上就**启动失败**（fail-fast），而不是悄悄退回内存。

这条规则的推论是：

1. **回退必须能被人看见**，而且是在**启动那一刻**看见（进程起不来 / 启动日志告警），不是在故障发生后从数据里反推；
2. **一旦进程成功启动，它的存储后端在整个生命周期内不变**，不存在"这个请求走 PG、那个请求走内存"；
3. **"连不上"的处理方式是失败，不是替换**。

第三点尤其反直觉。因为我们太习惯"降级 = 更健壮"了。但对**状态存储**来说：

> **存储不是"可选的依赖"，它是"你的系统是什么"本身。**
>
> 换个模型供应商，你还是同一个系统（只是答案不同）。换掉状态存储，你**变成了另一个系统**——一个有另一份记忆、另一套断点、另一个经验库的系统。而这次"变形"发生在运行中，没人知道。

### 2.5 三层成熟度：这个项目停在哪一层

用这把尺子量，可插拔存储有三种成熟度：

| 层 | 做法 | 触发条件 | 风险 |
|---|---|---|---|
| **L0** | 运行期探测失败即换实现 | 故障 | 本讲全部问题 |
| **L1** | **配置开关 + 启动自检（fail-fast）** | 配置 | 低：但开关仍在，误配可能 |
| **L2** | **删掉开关，只有一种实现** | 无 | 最低：没有"选错"的可能 |

**本项目停在 L1**，具体来说是：

- `StateStoreConfig`：**两套完整 Bean**（8 个 `Pg*` + 8 个 `InMemory*`），由 `@ConditionalOnProperty` 二选一；
- `PersistenceConfig`：配置说用 PG 时，**建不出连接池/建不出表就抛异常**，让应用**启动失败**；
- 回退分支**每条都带 `log.warn`**，且文案明确写"多实例部署必须启用 PostgreSQL"。

**没有实现 L2**（我在另一个项目 `waterdrop-ad-agent` 里做到了 L2：`StorageConfig` 里既没有开关、也没有默认值、也没有回退分支，连不上 PG 直接启动失败）。

**为什么这本书要保留 L1 而不是直接上 L2？** 因为这两个项目的**前提不同**：

- `code-review-agent` 是**开源仓库**，读者第一件事是"clone 下来跑起来"。强制 PG 会让第一次运行的门槛从"装 JDK"变成"装 PG + 建库 + 装 pgvector 扩展"。**保留一个明确的、默认走内存的开关，是给开源项目的门槛让路。**
- `waterdrop-ad-agent` 是**生产系统**，不存在"读者首次运行"这个场景。所以它可以把开关删干净。

**这就是"同一作者两个项目做法不同"的正当理由——前提不同。** 但无论哪一层，**"按故障降级"都不在其中**。

## 三、代码

### 3.1 两套 Bean 与那个 `matchIfMissing = true`

```java
// code-review-agent / core/store/StateStoreConfig.java:25-38（类注释）
```

注意最后一句：**"该结构使『无本地文件』成为系统默认——审查进程无本地状态"**。这句话是这次改造真正的目标：不是"用上了 PG"，而是 **"进程里不再有只有它自己知道的状态"**。这一句就是 2.1 节里"存储定义了你是什么系统"的工程表述。

配置组：

两个细节值得停一下：

**① `matchIfMissing = true`。** 它意味着 **"配置里没写这个键"= 走内存**。这不是"默认用内存"那么简单，它同时决定了**第 37 讲开头的那个坑**：

```yaml
# application.yml:93-94
pgvector:
  enabled: true          # ← 但 yml 里其实写了 true
```

配置文件的默认是 `true`，Bean 的 `matchIfMissing` 默认是"内存"。**同一个键有两个方向相反的默认值**，谁生效取决于"键在不在"。读者只要把 yml 里这一行注释掉、或者用 `--pgvector.enabled=` 空值覆盖，就会静默退到内存。

**② 只有 3 个回退 Bean 有 `log.warn`**（断点 `:99`、团队配置 `:112`、经验库 `:125`），另外 5 个（轨迹/校准/反馈/历史/知识元数据）**没有**。所以走内存模式时，启动日志里只有三行告警：

```
pgvector 未启用：断点存储回退内存（单机/测试，多实例部署必须启用 PostgreSQL）
pgvector 未启用：团队配置存储回退内存（多实例部署必须启用 PostgreSQL）
pgvector 未启用：经验库回退内存（单机/测试，多实例部署必须启用 PostgreSQL）
```

**"回退必须能被看见"这条，这个项目只做了一半**——8 个回退里告警了 3 个。

### 3.2 启动自检：配置说 PG，就得真的拿到 PG

```java
// core/store/PersistenceConfig.java:25-40
@Bean
@ConditionalOnProperty(name = "pgvector.enabled", havingValue = "true")
public PgDb pgDb(@Value("${pgvector.host:localhost}") String host,
                 @Value("${pgvector.port:5432}") int port,
                 @Value("${pgvector.database:codereview}") String database,
                 @Value("${pgvector.username:}") String username,
                 @Value("${pgvector.password:}") String password) {
    PgDb db = new PgDb(host, port, database, username, password);   // ← 这行在 try 之外
    try {
        db.initSchema();
    } catch (Exception e) {
        log.error("[PgDb] 状态表初始化失败，集群部署将不可用：{}", e.getMessage());
        throw new IllegalStateException("[PgDb] 初始化失败: " + e.getMessage(), e);
    }
    return db;
}
```

**核心是 `throw`。** 这是本节唯一一处"坚决不"：建不出表 → 抛 → `@Bean` 创建失败 → Spring 容器启动失败 → **进程退不出去，而是根本起不来**。

**★ 顺手指出一个真实缺陷**：`new PgDb(...)`（`:32`）**在 `try` 之外**。而 `PgDb` 的构造器里第一件事就是 `new HikariDataSource(cfg)`（`PgDb.java:60`），Hikari 默认会在建池时**真的取一次连接**（`initializationFailTimeout` 默认为 1ms，即 fail-fast）。也就是说：

| 故障 | 异常从哪抛 | 日志里有什么 |
|---|---|---|
| PG 连不上（端口不通 / 认证失败 / 库不存在） | **`PgDb` 构造器**（`:32`，try 之外） | 只有 Hikari 的 `PoolInitializationException` 原始栈 |
| PG 连得上但建表失败（权限不足 / 扩展缺失） | `initSchema()`（`try` 内） | **有** `[PgDb] 状态表初始化失败…` 这句人话 |

**两种都是"启动失败"，但第一种没有那句人话。** 而"PG 连不上"恰恰是**第一次部署时最常发生的那种**——你想让凌晨三点看日志的人读到的是 `[PgDb] 状态表初始化失败`，结果他读到的是 `HikariPool-1 - Exception during pool initialization`。

**修法**（不是仓库现状）：

```java
// 把构造也纳入 try——两种失败都给同一句人话
PgDb db = null;
try {
    db = new PgDb(host, port, database, username, password);
    db.initSchema();
} catch (Exception e) {
    if (db != null) {
        try { db.close(); } catch (Exception ignore) { }
    }
    log.error("[PgDb] 持久化底座初始化失败（连接或建表），集群部署不可用：{}", e.getMessage());
    throw new IllegalStateException("[PgDb] 初始化失败: " + e.getMessage(), e);
}
return db;
```

### 3.3 连接池：`PgDb` 说「单一」，实际有四条路

`PgDb` 的类注释写得非常明确：

```java
// core/store/PgDb.java:20-24
 * <p>背景：改造前审查状态（断点/经验/校准/反馈/历史/自定义配置/轨迹/知识元数据）落在
 * {@code data-dir} 本地文件，多实例部署时 A 机沉淀、B 机不可见，必然分叉。
 * 本类持有单一 HikariCP 连接池，向所有 Pg* 存储实现提供连接与表结构初始化，
 * 使每个实例读写同一份 PG 状态——审查进程无本地状态，A/B 双机共享同一视图。
```

```java
// PgDb.java:46-61（构造器：池参数）
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://" + host + ":" + port + "/" + database);
if (username != null && !username.isBlank()) {
    cfg.setUsername(username);
    cfg.setPassword(password == null ? "" : password);
}
cfg.setPoolName("pg-persistence-pool");
cfg.setMaximumPoolSize(12);
cfg.setMinimumIdle(2);
cfg.setConnectionTimeout(30_000);
cfg.setIdleTimeout(600_000);
cfg.setMaxLifetime(1_800_000);
cfg.setConnectionTestQuery("SELECT 1");
this.hikari = new HikariDataSource(cfg);
log.info("[PgDb] 已创建统一持久化连接池（{}:{}/{}, 最大连接={}）", host, port, database, 12);
```

**"本类持有单一 HikariCP 连接池，向所有 Pg\* 存储实现提供连接"——这句话只对 `core/store/` 包下的 8 个实现成立。** 实际存在四条独立的 PG 连接路径：

| # | 路径 | 池 | 最大连接 | 谁在用 |
|---|---|---|---|---|
| 1 | `PgDb` | `pg-persistence-pool` | **12** | `store/` 包 8 个状态存储 |
| 2 | `PgVectorMemoryStore` | `pgvector-pool`（`:112-119`） | **10** | 向量记忆（每次审查都读） |
| 3 | `PgKnowledgeStore` | `pg-knowledge-read-pool`（`:94-95`） | **8** | RAG 知识库混合检索 |
| 4 | `CoreHealthIndicator` | **无池**（`DriverManager`，`:51-52`） | 每次一条 | `/health` 探针 |

路径 2、3、4 都**不经过 `PgDb`**。原因在装配签名上就能看出来——`InfrastructureConfig` 的 Bean 直接接收连接参数，而不是接收 `PgDb`：

```java
// config/InfrastructureConfig.java:42-52（节选）
@Bean
@ConditionalOnProperty(name = "pgvector.enabled", havingValue = "true")
public MemoryStore pgVectorMemoryStore(EmbeddingClient embeddingClient,
                                       @Value("${pgvector.host:localhost}") String host,
                                       @Value("${pgvector.port:5432}") int port,
                                       ...) {
    ...
    log.info("已启用 PgVector 记忆存储（{}:{}/{}, dim={}, ANN 索引={}）", host, port, database, vectorDim, indexType);
    return new PgVectorMemoryStore(embeddingClient, host, port, database, username, password, vectorDim, indexType);
}
```

**这带来一个可量化的后果：**

```
单实例的池上限 = 12 + 10 + 8 = 30 条常驻连接（+ health 的临时连接）
PostgreSQL 默认 max_connections = 100

→ 3 个实例 = 90 条，加探针与运维连接 ≈ 撞满
→ 第 4 个实例启动即失败（而且失败的是池初始化，见 3.2 的日志问题）
```

**换句话说：调 `PgDb` 的 `maximumPoolSize` 控制不住总连接数**，因为大头在另外两个池里。而且这三个数字是散在三个文件里的——**没有任何一处能让你一眼看到"这个服务一共会占多少 PG 连接"**。

这就是 2.1 节"多实现"的代价在**装配层**的具体形态：不是代码量，是**没有一个地方是"全部"**。

命名是 `readPool`、池名是 `pg-knowledge-read-pool`、日志写"只读检索连接池"。**命名在暗示"这是一个读副本/只读连接"。** 我核对过来：检索（`hybridSearch` 里的 `getConnection()`）和补算余弦（`fillMissingDenseSim`，纯 `SELECT ... FROM memory_store`）**确实都是读**。但有两处例外：

1. `getConnection()`（`:362-363`）就是 `readPool.getConnection()`，而 **`@PostConstruct init()`（`:108-110`）在这个池上执行 `CREATE INDEX IF NOT EXISTS`——DDL 走"只读"池**；
2. 更值得警惕的是**它连的是同一个 host/port/database**（构造函数逐字传入同一组参数），**不是任何形式的读副本**。

```java

 * 启动确保检索所需的 GIN 索引存在（表与向量列由写入器创建/迁移，此处仅补 tsvector 索引）。
```

**为什么这条值得单独拎出来讲？** 因为 `readPool` 这个名字最危险的后果不是技术上的，而是**认知上的**：下一个人读到它，会得出一个错误结论——

> "哦，检索走的是只读池，那我配个只读副本给它就好了。"

然后他会去做一件**在这个代码里会立刻爆炸**的事：给 `pgvector.host` 配只读副本地址。改完之后，检索确实走了副本（因为 host 参数逐字传进去了），但**启动时 `@PostConstruct init()` 会在副本上执行 `CREATE INDEX IF NOT EXISTS` 与 `CREATE EXTENSION`——只读副本大概率没有 DDL 权限**，于是 `:119` 抛 `IllegalStateException` → **整个应用启动失败**。

**这是好事**（fail-fast，不是静默退化），但**排查体验很糟**：错误信息是 `[PgKnowledge] 初始化失败: ERROR: cannot execute CREATE INDEX in a read-only transaction`，而**他想不明白自己只是"配了个只读副本"**——因为代码里从没有一处说过"这个池要执行 DDL"。

**名字承诺 > 实现**——这是我们在这个项目里第无数次遇到同一个失效模式。**区别只是这次的载体不是一个 `@Component` 或一段注释，而是一个变量名。** 而且这次它有一个很具体的下游后果：**读副本这个基础设施决策，在这个代码上是不可做的**（要么给它 DDL 权限——那就不是只读副本了；要么改代码把 DDL 挪到 writer 的池上）。

`PgVectorMemoryStore` 有 `migrate(conn, stmt)`（`:372`）与 `migrateTsvectorTokens(conn)`（`:246`），后者还用了 `rag_schema_migration` 表做幂等标记。**这是一套真的、手写的、带版本标记的迁移机制。**

于是同一个 PG 库里有了两套并存的机制：

| 对象 | 演进机制 | 幂等标记 | 能改列吗 |
|---|---|---|---|
| `store/` 包 8 张状态表 | `PgDb.initSchema` | 无（靠 `IF NOT EXISTS`） | **不能** |
| `memory_store`（向量/知识库） | `PgVectorMemoryStore.migrate` | `rag_schema_migration` | 能（含备份重建） |

**这才是"多实现"最深的代价**：不是多写了几百行代码，而是 **"这个库的 schema 是什么"失去了单一答案**——你得去两个文件里分别读，而且它们**连"怎么演进"的哲学都不同**（一个是声明式幂等建表，一个是命令式带备份迁移）。

### 3.7 对照：`waterdrop-ad-agent` 走到了 L2

同一作者，另一个项目里我把开关**删掉了**。对照不是为了说这个项目做得不好，而是为了说明第 2.5 节那张成熟度表里 L2 长什么样：

| 维度 | `code-review-agent`（L1） | `waterdrop-ad-agent`（L2） |
|---|---|---|
| 配置开关 | `pgvector.enabled` | **没有** |

## 四、避坑清单

- [ ] **回退的触发条件必须是配置，不能是运行时故障。** 允许 `enabled=true/false`，不允许 `catch (Exception e) { return new InMemoryXxx(); }`。
- [ ] **配置说用外部存储时，连不上必须启动失败（fail-fast），不能静默退回。** 失败要发生在 `@Bean` 创建期，这样进程根本起不来——而不是在第一次请求时才暴露。
- [ ] **把"连接失败"和"建表失败"包进同一段错误处理。** 否则最常见的那种故障（端口不通/认证失败）反而没有可读日志。核对：初始化调用的第一行 `new XxxPool(...)` 是否在 `try` 内。
- [ ] **回退分支必须每一条都有启动告警。** 8 个回退里只告警 3 个 = 剩下 5 个静默。文案里要写清后果（"多实例部署必须启用 PostgreSQL"），不要只写"未启用"。
- [ ] **同一个配置键只允许有一个缺省语义。** 检查方法：`grep -rn "pgvector.enabled" src/` 把 yml、每个 `@Value` 的缺省、每个 `@ConditionalOnProperty` 的 `matchIfMissing` 列成一张表，方向必须一致。
- [ ] **统计"这个服务一共占多少数据库连接"时，要 grep 所有建池点**，而不是读主连接池的参数。核对：`grep -rn "HikariDataSource\|DriverManager.getConnection" src/main/java` 有几处池、每处上限多少、加起来离 PG 的 `max_connections` 还有几个实例的余量。
- [ ] **池名与用途必须一致。** 叫 `readPool` 的池不该执行 DDL；如果连接参数跟主库完全相同，就**不要**在名字里暗示"只读副本"——下一个人会据此做出错误的基础设施决策。
- [ ] **健康检查不要绕过连接池。** 每次 `DriverManager.getConnection` 建一条临时连接，意味着**池全满时探针仍然报 UP**（连接池耗尽 ≠ 连不上库）。探针应该去借池里的连接（借不到就是 DOWN）。
- [ ] **schema 演进只允许有一套机制。** 同一个库里存在"幂等建表"和"带备份的手写迁移"两套时，`grep CREATE TABLE` 得到的答案不是"库长什么样"。要么统一上 Flyway/Liquibase，要么明确划出各自的边界。
- [ ] **区分环境变量的"泄漏风险"与"配置陷阱"**：本项目 PG 默认用户是 `yunfei`（作者本机账号）——`username: ${PGVECTOR_USERNAME:yunfei}`。这类"默认值写成本机值"不会造成安全问题，但会让**别人 clone 下来默认连不上**，属于典型的"首次运行体验"坑。

## 本讲小结

1. **"多实现"有两种：配置驱动的选择（无害）和运行期自动降级（致命）。** 前者在启动时定死、之后不变；后者让同一个进程的不同请求可能跟不同后端说话。
2. **自动降级把"失败"翻译成了"成功"**，于是它在所有以"有没有报错"为核心的监控上**与健康完全同形**——连接数下降、内存平稳、HTTP 全绿、日志干净，只有数据在悄悄丢。
3. **判据只有一条：回退的触发条件必须是配置，不能是故障。** 配置说用 PG，连不上就**启动失败**，而不是悄悄退回内存。理由是：**存储不是可选依赖，它定义了"你的系统是什么"。换个模型你还是同一个系统；换掉状态存储，你变成了另一个系统——而且没人知道。**
4. **成熟度分三层**：L0 按故障降级（禁止）→ L1 配置开关 + 启动自检（本项目）→ L2 删掉开关、只有一种实现（另一个项目）。**留在哪一层取决于前提**（开源门槛 vs 生产确定性），但 **"按故障降级"都不在其中**。
5. **`StateStoreConfig` 的设计是对的**：两套 Bean + `@ConditionalOnProperty` + `PersistenceConfig` 的 `throw`。它把"用哪个后端"从运行期决策拉回了启动期决策。
6. **但"能被看见"只做了一半**：8 个回退 Bean 里只有 3 个打了 `log.warn`。走内存模式时，启动日志看不见另外 5 个的状态迁移。
7. **★ `new PgDb(...)` 在 `try` 之外**——最常见的故障（PG 连不上）反而拿不到那句人话日志，只有 Hikari 的原始栈。
8. **★ 四条 PG 连接路径**（`PgDb` 12 / `PgVectorMemoryStore` 10 / `PgKnowledgeStore` 8 / `CoreHealthIndicator` 无池）。`PgDb` 类注释里的"**单一** HikariCP 连接池、向**所有** Pg* 实现提供连接"**只对 `store/` 包成立**。后果：**调 `PgDb` 的池大小控制不住总连接数**，`12+10+8=30` 且散在三个文件里，约 3 个实例就撞 PG 默认上限。
9. **★ `readPool` 这个名字在撒谎**：它是同一个库的第二个池、不是读副本，且 `init()` 在它上面跑 `CREATE INDEX`（DDL）。**名字承诺 > 实现——这次的载体不是注释，是一个变量名。**
10. **★ 同一个键三个缺省**（yml `true` / `@Value` 的 `false` / `matchIfMissing` 的内存）。今天的"一致"是靠 yml 一行显式配置维持的，不是设计保证的。一旦那行没了，**`/health` 会因为"未启用"而跳过检查、恒报 UP**——把一个配置问题伪装成健康状态。
11. **★ 同一个库两套 schema 演进机制**：`PgDb` 用 `CREATE TABLE IF NOT EXISTS`（只能建不能改），`PgVectorMemoryStore` 用手写 `ALTER` + 备份重建 + `rag_schema_migration` 标记。**`grep CREATE TABLE` 得不到"这个库长什么样"的唯一答案。**
12. **健康检查不该绕过连接池。** `CoreHealthIndicator` 用 `DriverManager` 每次新建连接——**池耗尽时探针依然 UP**，而业务已经在排队。

**你现在知道了"存储"这个决定真正的重量**：它不是选一个数据库，是选择"**要不要给同一个系统留出两种可能的过去**"。下一讲换个方向——不再管状态存在哪，而是管**外部世界怎么进来、结果怎么回去**：Webhook 事件接入与平台回写。
