# 第 27 讲 · 切块策略：为什么"按 300 字符切"会毁掉知识库

> **图 27-0**　本讲地图：切块是 RAG 第一道闸门：边界优先级为标题、围栏、段落、句子、硬切。parentSection 写成自己就是假层级，父子检索不可实现；标题必须进正文，嵌模型与 LLM 都要它。

## 一、痛点

知识库里有一条规范，白纸黑字：

> 禁止将外部输入直接拼接进 SQL 语句，必须使用参数化查询（PreparedStatement）或预编译语句。

审查机器人给出的意见是"建议补充注释"。

我把这条规范检索出来一看，它是这样的：

```
...必须使用参数化查
询（PreparedStatement）或预编译语句。
```

**它被从中间切断了。**

更糟的是另一条：把三章内容（"数据库访问" + "安全" + "异常处理"）拼成了一块。检索命中了这一块，然后整块塞进上下文——**模型看到 3 个不同主题、9 条规则，却不知道哪条适用于当前 diff。**

两条故障的病因是同一个：**切块器不知道文档的结构。** 它只认识一个数字：300 字符。

旧实现的注释把它写得很直白（`StructuredChunker.java:13`）：

```java
 * <p>取代旧的「按行聚合固定 300 字符」粗暴切分。遵循 2025 工业级 RAG 共识：
```

**"粗暴"这两个字是作者自己写的**——写下这段注释的时候，他就已经知道问题在哪了。

## 二、原理

### 2.1 切块的三个目标，天然互相冲突

| 目标 | 为什么 | 往哪个方向拉 |
|---|---|---|
| **块要小** | 检索粒度细、命中精确、注入不浪费预算 | 缩小 chunk |
| **块要自洽** | 一块应该是一个完整意思，能被独立理解 | 扩大 chunk |
| **块要有上下文** | 模型看到"禁止字符串拼接"，要知道这是哪一章的约定 | 补上下文（不是扩块） |

**第三个目标和前两个不冲突——它是一个额外的维度。** 很多人把它和"块要大"混为一谈，于是选择"块切大一点"，然后被检索精度反噬。

本项目的解法是**分开处理**：

- 主块保持小（`maxChars = 700`），保证检索粒度；
- 上下文**额外附加**：标题链进正文 + 父章节摘要回填。

### 2.2 固定长度切分的两个致命伤

**致命伤一：边界不认结构。**

按 300 字符一刀切，会：

- 把一句话劈成两半（**语义断裂**，两块都检索不准）；
- 把代码块劈成两半（**语法都不完整了**）；
- 把 Markdown 表格从中间切开（**表头和表体分离**）。

**致命伤二：切完就丢了结构。**

固定长度切分产出的每块，除了文本什么都没有。它不知道自己属于哪一章、上一章是什么、同级还有哪些块。

**这导致两个能力直接不可能实现：**

1. **过滤**——"只在'安全'这一章里检索"做不到（因为没有章节字段）；
2. **父子检索（small-to-big）**——命中叶子块后拿父章节上下文，做不到。

### 2.3 结构感知切分：先认边界，再论长度

正确的顺序是**反的**：

```
固定长度切分：先按长度切，然后听天由命
结构感知切分：先找自然边界（标题/围栏/段落），再在段落内部按长度切
```

本项目的边界优先级：

| 优先级 | 边界 | 处理 |
|---|---|---|
| 1 | Markdown 标题（`#`） | **强制 flush**，并按 `#` 数量维护层级栈 |
| 2 | 代码围栏（成对 ```` ``` ````） | **整段作为一块**，绝不按行/按标题劈断 |
| 3 | 段落/空行 | 天然分段 |
| 4 | 换行 / 句号 | 段落仍超 `maxChars` 时的回退切点 |
| 5 | 硬切 | 以上都找不到（超长无标点文本）才用 |

**注意第 1 级和第 2 级的相对关系**：代码围栏的优先级**高于**标题——因为围栏内的 `#` 是注释/Shebang，不是 Markdown 标题。这个细节在实现里就是一个 `if (!inFence && ...)`。

### 2.4 重叠：为什么是 15%

即便有结构感知，边界处仍可能断句（比如一个长段落被 `splitBySize` 切开）。**重叠是给边界买保险**：

- 太小（<5%）：起不到作用；
- 太大（>30%）：检索结果里出现大量重复块，浪费上下文预算；
- 业界建议 **10%–20%**，本项目取 **0.15**，并把它做成构造参数且**校验范围**。

**把重叠和块大译成 token 账单，你才知道"切多碎"是个变量而不是常数。** 设文档总长 L、块长 maxChars，则块数 ≈ L/maxChars，重叠带来的实付 token 比例 = 重叠比（每块头部都带一块『上一块尾部』，总长度 ≈ L × (1 + overlap)）：

> 固定 **L=14,000 字符**的规范手册，maxChars=700、overlap=0.15：
> 块数 ≈ 14000/700 = **20 块**；每块带 0.15×700 = **105 字重叠**；实付字符横恒 ≈ 14000 × 1.15 ≈ **16100 字**——重叠白付了 **15%** 的 token。
> 若把 maxChars 调小一半到 350：块数翻倍 ≈ 40 块、重叠总量依旧约 15%（L×0.15 不变），但**每块长度减半 → 命中一块时注入的『无关尾/头』更少、检索粒度更细**。
> 所以重叠开销是 **线性且恒定** 的（≈15%），真正要权衡的是：**块越小 → 单块注入越省 token、命中越精，但文档被劈断的次数越多（结构断裂风险↑）**；块越大 → 反之。

**工程判据：** **先定『单次注入的 token 预算』再反推 maxChars——若一次检索要经 MMR 注入 Top-N 块，那么 maxChars 应满足 N × (maxChars + 前缀) ≤ 预算，而重叠开销恒为 overlap×L 不必省；在预算内，把 maxChars 调到『结构不劈断』前提下能取到的最小值，并在重叠比上做『10%~20%』的范围校验、禁止 0 或 >30%。** 一句话：重叠是固定税，块大才是可调的本金。

### 2.5 真层级 vs 假层级（本讲的"高价值细节"）

很多实现会为 chunk 生成一个 `section` 字段（它所属的章节）。但**只有 `section` 是不够的**，原因是父子检索需要**父章节**。

看本项目的类注释自陈的这段历史（`StructuredChunker.java:17-20`）：

```java
 *   <li><b>真层级上下文</b>：按 {@code #} 数量维护标题栈，为每个 chunk 生成
 *       {@code headingPath}（{@code A > B > C}）与<b>真实父章节</b> {@code parentSection}——
 *       早期版本把 {@code parentSection} 直接写成 {@code section}（假层级），
 *       导致「检索到叶子块却拿不到父章节」的父子检索无法实现；</li>
```

**"把 `parentSection` 直接写成 `section`"就是假层级**：字段有、值也在，但**语义是错的**——它声称是"父章节"，实际给的是"自己"。这类字段比没有字段更危险，因为它**会让下游代码以为自己拿到了父章节**。

### 2.6 标题为什么不只放 metadata

同样的思路，`headingPath` 被**写进了正文**（`StructuredChunker.java:21-23`）：

```java
 *   <li><b>标题进正文</b>：chunk 正文前缀携带 {@code 【headingPath】}。
 *       标题只进 metadata 不进 body 会有双重损失——嵌入时丢掉章节语义、
 *       注入时 LLM 看不到该块属于哪一章；</li>
```

**"双重损失"是两个不同的消费者：**

| 消费者 | 只放 metadata 的后果 |
|---|---|
| **嵌入模型**（写入时） | 向量里没有"安全"这个语义 → 检索"安全规则"命中不到这一块 |
| **LLM**（注入时） | 看到"禁止硬编码密码"，不知道这是哪份文档的哪一章 |

**给同一个数据找到两个真实消费者，就能证明它必须进正文。** 这是一个很实用的判断方法。

### 2.7 语境前缀：让每个块自带"它在讲什么"

2.6 说清了标题必须进正文——但那是**切块器**能从文档结构里拿到的信息。`headingPath` 前缀（`StructuredChunker.java:172-187`）回答的是"这块属于哪一章"，它**不回答"这段在讲什么"**。

当块的正文**脱离原文就无法自解释**时，结构信息就到底了。

Anthropic 提出的语境前缀（Contextual Retrieval）补的正是后半句：**由模型为每个块生成一句"它在讲什么"，再拼到块前面**（https://www.anthropic.com/news/contextual-retrieval ）。它和本项目的标题路径前缀是**同一族思想的不同成熟度**：

| 维度 | 本项目：标题路径前缀 | Anthropic：语境前缀 |
|---|---|---|
| 信息从哪来 | 文档结构（`#` 层级栈） | 模型读原文后生成 |
| 回答什么 | 这块属于哪一章 | 这段在讲什么 |
| 单块成本 | 0 次模型调用 | **每块过一次模型** |
| 失败模式 | 结构缺失时无能为力 | 生成句可能失真、要防 ` **"串味"**` |

一句话：**本项目只补了标题路径，Anthropic 补的是由模型生成的语境句。**

**代价是真实的**：写入链路从"纯文本处理"变成"每块一次模型调用"。切块因此从**纯 CPU 操作**变成**带外部依赖的操作**——吞吐不再由本地算力决定，而由模型侧的 QPS 与失败率决定。

**收益场景也是明确的**：只有当块**脱离原文就无法自解释**时，语境句才值这个钱。团队规范里的"禁止字符串拼接"配上 `【数据库访问】` 前缀就够用了；而一条商品描述被切出来后，往往连"这是哪款、哪个规格"都看不出来——那才是语境前缀的主场。这条路线在框架侧与学术侧都有同族实现：LangChain 的父子文档检索先命中子块、再回填父文档（https://python.langchain.com/docs/how_to/parent_document_retriever/ ）；RAPTOR 则把父层直接做成模型逐层摘要出的树（`2401.18059`，https://arxiv.org/abs/2401.18059 ），代价同样压在模型调用上。

### 2.8 增量与重切：内容会变的知识库怎么活

本讲前面所有优化都建立在一个隐含前提上：**文档内容是不变的**。

基座 A 恰好满足这个前提——`code-review-agent` 的知识库以团队规范为主，是**低频变更**（人工评审通过后偶发修订）。但把它整体搬到基座 B（千万 DAU 电商客服知识助手）会立刻崩：B 的知识库以 **UGC 商品/政策文档**为主，**内容随时变化**。**分叉点就在这。**

**先看写入语义。** langchain4j 的 pgvector 存储在写入时用的是 upsert（`langchain4j-pgvector/src/main/java/dev/langchain4j/store/embedding/pgvector/PgVectorEmbeddingStore.java:640`）：

```java
                            + "ON CONFLICT (embedding_id) DO UPDATE SET "
```

**主键冲突就更新，不是删除重建。** 它的价值不在省几行 SQL，而在于**避免重建期间的空窗**——删表重建会让一段时间内一条也检不到。

**更难的是前半句：内容变了，怎么知道要重切？** upsert 只解决了"怎么写入"，没解决"哪些块该重写"。三种判据，粒度与成本各异：

| 判据 | 怎么工作 | 粒度 | 代价 |
|---|---|---|---|
| **内容哈希** | 对原文算 hash，与上次入库比对 | 整篇文档 | 要保存上一版 hash |
| **版本号** | 上游显式递增版本，变了就重切 | 整篇文档 | 依赖上游守约 |
| **失效标记** | 上游在变更事件里带上"这篇失效" | 文档或块 | 需要事件流 |

**三者可叠加，但至少要有一个。** 没有判据的 **"增量更新"** 只有两种结局：**全量重建**（贵），或者**永久陈旧**（更贵）。

读链路的纠正替代不了写链路的判据。CRAG 在检索质量差时会触发纠正——改写查询或降级到网页检索（`2401.15884`，https://arxiv.org/abs/2401.15884 ）——但它纠正的是**这一次查询**；内容没被重切入库，再好的纠正策略也检不到它。若索引结构本身要升级（比如从平铺块改成社区摘要），成本还要再上一个台阶：GraphRAG 给出的正是"什么时候值得上这种重结构"的取舍（`2404.16130`，https://arxiv.org/abs/2404.16130 ）。

### 2.9 一手数据与搬到你自己系统

**先说能复算的数。** 本讲 3.5 已经算过一遍：内置手册 `resources/handbook/java-coding-standard.md` 共 24 行，用默认参数（`maxChars=700`、`overlapRatio=0.15`，见本讲 2.1）切出 **5 个 chunk**（对应 5 个 `##` 章节）。这是全篇最小的一次"块数 × 块长"实测。

把它摊成一条式子，三个量就互相牵动了：

```
块数 N ≈ L / maxChars
向量体积 ≈ N × 维度 × 4 B      （float32，每维 4 B）
单次注入 ≈ Top-N × (maxChars + 前缀)
```

**块长调小 → 块数涨、向量体积涨，但单块注入省、命中更精；块长调大 → 反过来。** 块长是唯一可以直接调的旋钮，另外两个是它的后果。

> **图 27-3**　块数、块长与索引体积的三人舞：块长是唯一可直接调的旋钮，另外两个是它的后果——按单次注入预算反推块长，才不会按下葫芦浮起瓢。

|---|---|---|
| 块长 `maxChars` | 700 | 本讲 2.1 |
| 重叠比 `overlapRatio` | 0.15 | 本讲 2.1 |

**先算基座 A 的一次完整账**（手册 24 行、5 块）：

> **推演**：`5 × 1024 × 4 B = 20,480 B ≈ 20 KB`（假设：5 个块的向量均按 1024 维 float32 存储；基座值见 本讲 3.5 的块数 5 与 `application.yml:197` 的生产嵌入维度 1024；未计 HNSW 图结构与元数据开销）

**换成基座 B，量级立刻换档。** 它的商品/政策文档以百万商家 × 数百 SKU 计：

> **推演**：`10^8 × 1024 × 4 B ≈ 409.6 GB`（假设：商品/政策文档共切出 1 亿个块，每维 float32 占 4 B；基座值见 `application.yml:197` 的生产嵌入维度 1024；未计 HNSW 图结构开销）

> **推演**：`1,000,000 × 300 × 5% = 15,000,000` 篇/日（假设：基座 B 有 100 万在营商家、每商家 300 个在架 SKU、单日 5% 的 SKU 发生描述或价格变更；基座 B 的商家与 SKU 规模为推演假设，无仓库基座值）

> **推演**：`15,000,000 × 2 ≈ 30,000,000` 块/日（假设：单商品文档按 `maxChars=700` 约切成 2 块；基座值见 本讲 2.1 的 `maxChars=700`）

**这三个数指向同一件事**：基座 B 的重切是**持续事件流**，不是发布时的一次操作。于是它必须回答基座 A 不需要回答的问题——**同一天里同一文档被改了多次，要不要重切同样多次？**（削峰与合并。）

| 维度 | A：代码审查助手 | B：千万 DAU 客服助手 | 由此分叉的设计决策 |
|---|---|---|---|
| 内容变更频率 | 团队规范，低频变更 | UGC 商品/政策，随时变化 | 重切必须自动化，不能靠人工重跑 |
| 知识库规模 | 手册级：24 行切出 5 块（见本讲 3.5） | 规模为推演值（见上） | 索引体积升为一等约束 |
| "内容变了"的判据 | 版本号即可 | 内容哈希 + 失效标记 | 判据粒度决定重切成本 |
| 写入语义 | 全量重建可接受 | 必须主键 upsert | 主键覆盖而非删表重建 |
| 语境前缀收益 | 中：标题路径已覆盖归属 | 高：商品块脱离原文即不可辨 | 是否值得为每块付一次模型调用 |
| 单文档多次变更 | 基本不存在 | 一天内反复改 | 重切要削峰、合并 |

**"搬到你自己系统"该问的问题**：

| 工业界 / 本项目的做法 | 你自己系统里该问的问题 |
|---|---|
| 标题路径进正文（`StructuredChunker.java:21-23`） | 你的块的归属信息来自哪里？结构缺失时你补什么？ |
| 语境前缀每块过一次模型 | 你的块脱离原文还能自解释吗？这个钱值不值？ |
| 主键 upsert（`langchain4j-pgvector/src/main/java/dev/langchain4j/store/embedding/pgvector/PgVectorEmbeddingStore.java:640`） | 你的重切是删表重建还是主键覆盖？重建期有没有检索空窗？ |
| 内容哈希 / 版本号 / 失效标记 | 你的"内容变了"由谁发现？现在是全量重建还是永久陈旧？ |
| 块长 700、注入 5（`application.yml:223`） | 你的单次注入预算是多少？反推的块长能否做到结构不劈断？ |

**落地步骤**：

1. **数一遍现在的块**：跑一遍切块，打印块数、平均块长、最大块长，与 `maxChars` 对照——先确认参数语义（`charCount` 是否含前缀）。
2. **做一次断头测试**：随机抽 `inject-top-n`（本项目为 5，见 `application.yml:223`）个块，遮住 `headingPath` 前缀，记下"看不懂"的比例——这就是语境前缀在你语料上的收益上限。
3. **定义"内容变了"的判据**：在内容哈希 / 版本号 / 失效标记里选一个写进设计，别留空。
4. **确认写入语义**：向量表能否按主键 upsert？若只能重建，把重建期的检索空窗量化出来。
5. **算一次索引体积**：`块数 × 维度 × 4 B`，与磁盘/内存预算对照；超了先调块长，而不是先上量化。

一句话收口：切块在基座 A 是**发布期的一次性动作**，在基座 B 是**随内容变化持续运行的在线作业**——RAG 综述把这种从 Naive 到 Advanced 的推进列为同一进程（`2312.10997`，https://arxiv.org/abs/2312.10997 ）。

**判据**：**先判定你的知识库是"低频变更"还是"高频变更"——低频（团队规范一类）可全量重建、补标题路径即可；高频（商品/政策一类）必须落地内容哈希 / 版本号 / 失效标记三选一的重切判据，并把写入做成主键 upsert、把重切做成可削峰的事件流。**

## 三、代码

### 3.1 主循环：三个分支就是三条边界规则

`StructuredChunker.chunk`（`StructuredChunker.java:83-105`）的主循环只有三个分支：

```java
// core/rag/StructuredChunker.java:83-105
for (String line : lines) {
    String trimmed = line.trim();
    // Markdown 标题：作为章节边界，先 flush 旧章节，再按层级维护标题栈
    if (!inFence && trimmed.startsWith("#")) {
        chunkIndex = flush(block, meta, out, chunkIndex, headingStack);
        pushHeading(headingStack, trimmed);
        continue;
    }
    // 代码围栏（成对 ```）：整段作为整体块，不按行/标题劈断
    if (trimmed.startsWith("```")) {
        if (!inFence) {
            inFence = true;
            block.add(line);
        } else {
            block.add(line);
            inFence = false;
            // 闭合围栏：作为一个完整块 flush
            chunkIndex = flush(block, meta, out, chunkIndex, headingStack);
        }
        continue;
    }
    block.add(line);
}
```

**这三个 `continue` 的顺序不能换**：

- `!inFence && trimmed.startsWith("#")` —— **`inFence` 必须在前面**。否则代码块里的 `# comment` 会被当成标题，把代码块劈开。
- 围栏判断在标题判断**之后**——所以围栏起始行的 ```` ``` ```` 不会被标题逻辑吃掉（它不以 `#` 开头，顺序其实不影响，但**读起来必须能自证顺序**）。

**还有一个容易看漏的点：标题行自己被 `continue` 丢掉了，没有进 `block`。**

这意味着：**标题不会作为裸文本出现在任何 chunk 的正文里**。它只通过 `【headingPath】` 前缀出现。这是一个**刻意的设计**，不是遗漏——你可以在 3.3 的 `makeChunk` 里看到它被显式补回来。

### 3.2 标题栈：`#` 的数量就是深度

```java
// core/rag/StructuredChunker.java:121-134
private static void pushHeading(Deque<String> stack, String headingLine) {
    int level = 0;
    while (level < headingLine.length() && headingLine.charAt(level) == '#') {
        level++;
    }
    String title = headingLine.replaceAll("#+\\s*", "").trim();
    if (title.isEmpty()) {
        title = "(root)";
    }
    while (stack.size() >= Math.max(level, 1)) {
        stack.pollLast();
    }
    stack.addLast(title);
}
```

核心是 `while (stack.size() >= Math.max(level, 1)) stack.pollLast();`：

- 遇到 `##`（level=2）时，如果栈里有 `[H1, H2]`（size=2 ≥ 2），弹出 H2——**同级顶掉旧的**；
- 栈变成 `[H1]`，压入新 H2 → `[H1, H2_new]`。

**这就是"文本里没有显式层级、但栈把它还原出来了"**——`#` 的数量是唯一的层级信息源。

`Math.max(level, 1)` 是给 `#` 数量异常（比如 `#######` 七级、或者 `#` 后面跟空标题）留的保护：**level 至少按 1 处理**，避免 `level = 0` 时 `while (stack.size() >= 0)` 永远为真、把栈清空成死循环。

### 3.3 组装 chunk：真层级 + 标题进正文

```java
// core/rag/StructuredChunker.java:172-187
private Chunk makeChunk(String text, Map<String, String> meta, List<String> path, int index) {
    var m = new LinkedHashMap<String, String>(meta);
    String section = path.isEmpty() ? "(root)" : path.get(path.size() - 1);
    // 真层级：父章节取标题栈的上一层（早期版本直接写成 section，父子检索无法成立）
    String parentSection = path.size() >= 2 ? path.get(path.size() - 2) : "(root)";
    String headingPath = path.isEmpty() ? "(root)" : String.join(" > ", path);
    // 标题链进正文：嵌入侧不丢章节语义、注入侧 LLM 看得到归属
    // （只进 metadata 会两头受损：嵌入少语义、LLM 只从 source 括号里猜章节）
    String body = path.isEmpty() ? text : "【" + headingPath + "】\n" + text;
    m.put("section", section);
    m.put("parentSection", parentSection);
    m.put("headingPath", headingPath);
    m.put("chunkIndex", String.valueOf(index));
    m.put("charCount", String.valueOf(body.length()));
    return new Chunk(body, Map.copyOf(m));
}
```

**这一共 5 个 metadata 字段，每个都有下游消费者**（这是判断"字段该不该存在"的标准）：

| 字段 | 消费者 | 用途 |
|---|---|---|
| `section` | 过滤 / 展示 | 当前章节 |
| `parentSection` | **父子检索** | 上一级章节（真层级） |
| `headingPath` | **嵌入 + 注入** | 完整路径，进正文 |
| `chunkIndex` | 溯源 | 块在文档内的序号 |
| `charCount` | 观测 | 块大小（注意：**含前缀**的长度） |

**注意 `charCount` 是 `body.length()`，包含 `【headingPath】` 前缀；而 `maxChars` 只约束 `text`。** 所以"单块上限 700"实际可能到 700 + 前缀长度。这不是 bug（前缀很短），但**配置项的语义要说清楚**——写"块上限 700 字符"是不准确的。

### 3.4 两个坐标系的混用（本讲发现的真实缺陷）

`flush` 里做超长切分和重叠，代码只有 30 行，但有一个**很隐蔽的缺陷**：

```java
// core/rag/StructuredChunker.java:152-169
// 按 maxChars 进一步硬切（长段落）
List<String> path = new ArrayList<>(headingStack);
List<String> pieces = splitBySize(text, maxChars);
int start = 0;
for (int i = 0; i < pieces.size(); i++) {
    String piece = pieces.get(i);
    String withOverlap;
    if (i > 0 && start > 0) {
        int overlapLen = (int) (piece.length() * overlapRatio);
        overlapLen = Math.min(overlapLen, start);
        withOverlap = text.substring(start - overlapLen, start) + "\n" + piece;
    } else {
        withOverlap = piece;
    }
    out.add(makeChunk(withOverlap.trim(), meta, path, chunkIndex++));
    start += piece.length();
}
```

问题在最后一行：**`start += piece.length()`。**

而 `splitBySize` 是这样推进的（`StructuredChunker.java:222-245`）：

```java
int i = 0;
while (i < text.length()) {
    int end = Math.min(i + max, text.length());
    int cut = end;
    if (end < text.length()) {
        int lastNl = text.lastIndexOf('\n', end);
        int lastDot = Math.max(text.lastIndexOf('。', end), text.lastIndexOf('.', end));
        int best = Math.max(lastNl, lastDot);
        if (best > i + max / 2) {
            cut = best + 1;
        }
    }
    pieces.add(text.substring(i, cut).trim());   // ← 关键：.trim()
    i = cut;                                     // ← 用「裁剪前下标」推进
}
```

**两个坐标系：**

- `splitBySize` 内部用 `cut`（**裁剪前的下标**）推进，`pieces` 的每段是 `text.substring(i, cut).trim()`；
- `flush` 用 `piece.length()`（**裁剪后的长度**）累加 `start`。

**`trim()` 会削掉首尾空白**，所以 `Σ piece.length() ≤ 真实偏移量`。于是：

- `start` **始终落后**于真实切点；
- `text.substring(start - overlapLen, start)` 取到的不是"前一块的尾部"，而是**向前漂移了一段**的位置。

**漂移量随空白量累积**：Markdown 里到处是缩进、空行、代码块 —— 每段削掉几十字符很正常，切 10 段后 `start` 可能落后几百字符。这时"重叠区"取到的文本可能已经不属于前一块了。

**正确写法**：让 `splitBySize` 同时返回每段的**起止下标**，或者干脆在 `flush` 里用与 `splitBySize` 相同的 `cut` 逻辑重算偏移量。

```java
// 修法示意（不是仓库现状）：切块器返回「文本 + 真实起止」
record Piece(String text, int start, int end) {}
List<Piece> pieces = splitBySize(text, maxChars);
int prevEnd = 0;
for (int i = 0; i < pieces.size(); i++) {
    Piece p = pieces.get(i);
    String withOverlap = i > 0
            ? text.substring(Math.max(prevEnd - (int) (p.text().length() * overlapRatio), 0), prevEnd)
              + "\n" + p.text()
            : p.text();
    out.add(makeChunk(withOverlap.trim(), meta, path, chunkIndex++));
    prevEnd = p.end();
}
```

**顺带一个口径问题**：类注释（`:26-27`）说"相邻 chunk 保留约 `overlapRatio`（默认 15%）的**尾部文本**作为重叠"，但代码算的是 `piece.length() * overlapRatio`——**当前块长度的 15%**，不是前一块尾部的 15%。数值上两者接近（都约 700 字符），所以**看不出来**；但语义上不是一回事。这是"注释承诺 > 代码实现"在本项目里的**第五次现身**（前四次见第 11、12、19、23 讲）。

### 3.5 small-to-big 回填：一个"默默不生效"的功能

```java
// core/rag/StructuredChunker.java:194-213
private List<Chunk> withParentExcerpts(List<Chunk> chunks) {
    Map<String, String> firstByPath = new LinkedHashMap<>();
    for (Chunk c : chunks) {
        firstByPath.putIfAbsent(c.metadata().getOrDefault("headingPath", ""), c.text());
    }
    List<Chunk> result = new ArrayList<>(chunks.size());
    for (Chunk c : chunks) {
        String parentPath = parentPathOf(c.metadata().getOrDefault("headingPath", ""));
        String excerpt = parentPath == null ? null : firstByPath.get(parentPath);
        if (excerpt == null || excerpt.isBlank()) {
            result.add(c);          // ← 拿不到父章节，静默跳过
            continue;
        }
        ...
    }
}
```

逻辑是：先按 `headingPath` 建索引，取每个路径的**第一个块**作为该章节的"摘要"；然后对每个块，取出它的父路径（`A > B > C` → `A > B`），查索引拿摘要。

**现在看看内置的规范手册会发生什么。** 它的结构是（`resources/handbook/java-coding-standard.md`，共 24 行）：

```
1  # 团队 Java 编码规范（示例）     ← H1，下一行是空行，H1 下面没有任何正文
2  (空行)
3  ## 数据库访问
4  - ...
...
21 ## 代码风格
```

**H1 下面没有正文。** 所以：

- 切块产出 **5 个 chunk**（每个 `##` 一章，共 5 章）；
- 每个 chunk 的 `headingPath` 是 `"团队 Java 编码规范（示例） > 数据库访问"`；
- 每个 chunk 的父路径是 `"团队 Java 编码规范（示例）"`；
- `firstByPath` 里的 5 个 key **全是 `"X > Y"` 形态**，**没有任何一个 key 等于 `"团队 Java 编码规范（示例）"`**；
- 于是 `excerpt == null` → **每个块都被原样返回，`parentExcerpt` 一个都没写。**

**结论：对内置信手自带的语料，`small-to-big` 是 100% 空转的。**

而这个功能的开关**默认是开的**：

```yaml
# src/main/resources/application.yml:216-218
    # small-to-big：为命中的叶子块回填父章节上下文（StructuredChunker 写入的 parentExcerpt）。
    parent-context:
      enabled: ${RAG_PARENT_CONTEXT_ENABLED:true}
```

`RagContextBuilder.appendKnowledgeBlocks`（`:325-345`）里那段 `if (parent == null || parent.isBlank()) continue;` —— **永远走 continue**。

**这就是第 26 讲说的"静默降级"的又一个实例**：功能开了、代码跑了、没有任何报错、`parentExcerpt` 字段在 metadata 里查不到。**唯一的症状是"没效果"。**

**修法有两条**：

1. **语料侧**：给 H1 下面补一段导读正文，让它自己成为一个块；
2. **代码侧**：父摘要的查找加一个"前缀回退"——找不到精确的父路径时，退而取**任意一个以父路径开头的块**：

```java
// 修法示意（不是仓库现状）
String excerpt = firstByPath.get(parentPath);
if (excerpt == null) {
    String prefix = parentPath + " > ";
    excerpt = firstByPath.entrySet().stream()
            .filter(en -> en.getKey().startsWith(prefix))
            .map(Map.Entry::getValue)
            .findFirst().orElse(null);
}
```

**注意代码侧的修法只是"退而求其次"**：取到的其实是兄弟章节的内容，不是父章节。真要 small-to-big，**根因是语料结构**——这也是本讲想让你带走的一句话：**很多 RAG 问题的根因在语料，不在代码。**

### 3.6 一个残留的死注释

`KnowledgeBaseInitializer` 的类末尾（`:84-90`）留着这样一段：

```java
// core/memory/KnowledgeBaseInitializer.java:84-91
    /**
     * 按行聚合切分为约 maxChars 的 chunk。
     *
     * @param text      原文
     * @param maxChars  单 chunk 近似上限
     * @return chunk 列表

**这段 javadoc 下面没有方法。** 它是旧切块器（就是 `StructuredChunker` 注释里说的"按行聚合固定 300 字符"那个）被删掉之后留下的尸体。

**为什么值得单独指出来**：因为它是"重构没扫干净"的**物理证据**。读到它的人会困惑——"这里是不是有个方法被人误删了？"而真相是**它在别处被重写了**（迁到了 `StructuredChunker`）。

**处理方式只有一个：删掉。** 死注释不会报错，但它会让下一个人怀疑代码的完整性。

## 四、避坑清单

- [ ] **切块的边界优先级必须显式排序并写进注释**：标题 > 代码围栏 > 段落 > 句子 > 硬切。顺序错了就是"代码块里 `#` 被当标题"这种事故。
- [ ] **代码围栏必须整段保留**（成对 ```` ``` ````）。切开一个代码块，嵌入的是一段语法都不完整的文本。
- [ ] **`section` 和 `parentSection` 必须是两个字段、两个值。** 把父章节写成自己（假层级）比没有字段更危险——下游会以为拿到了父章节。
- [ ] **层级信息要进正文，不能只放 metadata。** 判断标准是"有几个消费者"：嵌入模型要它算语义，LLM 要它理解归属——两个消费者，就得进正文。
- [ ] **重叠的偏移量必须与切分用同一套坐标系。** 切分用"裁剪前下标"、重叠用"裁剪后长度"累加，会随空白量累积漂移。
- [ ] **`maxChars` 的语义要写清是否含前缀**（本项目 `charCount` 含 `【headingPath】`）。否则容量规划全是错的。
- [ ] **父子回填这类"增强功能"必须有断言能证明它真的产出了。** 至少写一个测试：`assertThat(chunks).anyMatch(c -> c.metadata().containsKey("parentExcerpt"))`。**空转的功能比没有功能更贵**——它占着配置项、占着阅读成本，还给你虚假的安全感。
- [ ] **语料结构是被低估的变量。** "H1 下面没有正文"这种小事，能让一个默认开启的功能全程空转。**上线前用真实语料跑一遍切块，把 chunk 数、平均块长、`parentExcerpt` 命中率打出来。**
- [ ] **删除旧实现时，顺手删掉它的注释。** 死 javadoc 是重构没扫干净的证据，会让人怀疑代码完整性。
- [ ] **"补了标题路径"不等于"补了语境"。** `headingPath` 只回答"这块属于哪一章"，不回答"这段在讲什么"。给块做一次断头测试——遮住前缀还看不懂的块，缺的是模型生成的语境句，不是更长的正文。
- [ ] **内容会变的库，重切判据必须先落地。** 内容哈希 / 版本号 / 失效标记，三者至少有一个。没有判据的"增量更新"只有两种结局：全量重建（贵），或者永久陈旧（更贵）。
- [ ] **重切是 upsert + 旧版本失效，不是删表重建。** 工业做法是 `ON CONFLICT (embedding_id) DO UPDATE SET`（`langchain4j-pgvector/src/main/java/dev/langchain4j/store/embedding/pgvector/PgVectorEmbeddingStore.java:640`）——主键覆盖省掉的不只是几行 SQL，更是重建期间的检索空窗。

> 2. 打印每个块的：
>    - `headingPath` / `section` / `parentSection`；
>    - 正文前 50 字符；
>    - **`parentExcerpt` 是否存在**。
> 3. **统计 `parentExcerpt` 命中率**（有几个块带这个字段）。
>
> **预期结果**：
> - 产出 **5 个 block**（对应 5 个 `##` 章节）；
> - 每个块的 `parentSection` 都是 `"团队 Java 编码规范（示例）"`；
> - **`parentExcerpt` 命中率 = 0/5** —— 这就是 3.5 说的空转。
>
> **对照实验**：在手册第 2 行插入一句 H1 下的导读正文（比如"本规范适用于所有 Java 服务。"），重跑。
> **预期结果**：H1 现在有自己的块了，5 个 `##` 块的 `parentExcerpt` **全部命中**（5/5）。
>
> **第二个实验**：找一份**没有代码块、但每段都很长**的文档，观察重叠区文本是否真的是"前一块的尾部"（用 3.4 的修法前后对比）——你会看到漂移。
>
> **第三个实验**：给这次切块加一项**重切判据**的体检。取同一份文档，做两次改动——改一个正文字符、改一次 `##` 标题——每次算一遍**块内容哈希**与**块数**，然后回答两个问题：这次改动会波及几个块？能不能只 upsert 其中一部分，而不是整篇重切？（基座 A 的规范是低频变更，这一步看着多余；但如果你自己的知识库是**高频变更**，同一天里同一文档被反复改动是常态，没有这条判据就只能全量重建。）

---

## 本讲小结

1. **切块是 RAG 质量的第一道闸门**，边界优先级必须是：标题 > 代码围栏 > 段落 > 句子 > 硬切。固定 300 字符切分输在**不认结构**。
2. **`section` ≠ `parentSection`。** 假层级（父章节填自己）会让父子检索在字段存在的情况下依然不可实现。
3. **层级信息要进正文**——因为它有两个真实消费者：嵌入模型（算语义）和 LLM（理解归属）。
4. **重叠的坐标系必须统一**：本项目用"裁剪后长度"累加偏移、而切分用"裁剪前下标"，`trim()` 造成的漂移会随空白量累积。
5. **默认开启的功能可能一直在空转**：内置手册 H1 下无正文，导致 `small-to-big` 命中率 **0/5**，而没有任何报错。**给增强功能写一个"证明它产出了"的断言。**

下一讲我们沿着写入链路的下一环往下走：**向量化与 pgvector**——一个配置项的默认值不一致，如何把整张表的数据作废。
