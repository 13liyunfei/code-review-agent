## 一、痛点

一个月里，我对 RAG 做了三次改动：

1. 把切块从"按 300 字符"换成"结构感知 + 真层级"；
2. 把 `similarity` 的写入从"RRF 归一化分"改成"真实余弦"（第 31 讲）；
3. 把 `retrieve-k` 从 10 调到 50。

上线时我都"感觉变好了"。

但领导问了一个很朴素的问题：

> **"这三版，哪版效果最好？"**

**我答不上来。**

我有的证据是：

- 三次改动都有"代码更合理"的论证（✅ 可以说服工程师）；
- 三次改动都有"设计上应该更好"的推理（✅ 可以说服我自己）；
- **没有任何一次有"数字上确实更好"的证据。**（❌ 说服不了任何人）

更糟的是——**我甚至不知道第三次改动是不是把前两次的收益吃掉了。** `retrieve-k` 从 10 调到 50，候选变多、噪声也变多；第 31 讲那个"阈值闸门"的 bug 恰恰**会因为候选集变大而被放大**。两次改动互相影响，而我只有"感觉"。

**没有评测的优化，不是优化，是调参。**

## 二、原理

### 2.1 评测的三个层次，别混

| 层次 | 评什么 | 需要的 ground truth | 可自动化 |
|---|---|---|---|
| **检索** | 该找的知识找到了吗？排得靠前吗？ | **相关块的 id** | ✅ 完全可自动化 |
| **生成** | 模型有没有引用正确知识、有没有幻觉？ | 参考答案 / 人工评分 | ⚠️ 半自动（LLM-as-judge） |
| **端到端** | 审查意见对不对、有没有误报？ | **人工判定** | ❌ 只能抽样 |

**三个层次的投入产出比差别很大。** 检索层是**最便宜、最确定、最先该做**的——因为它的 ground truth 就是"哪个块是对的"，这个信息你在**构造测试语料的时候本来就知道**。

**本讲聚焦检索层**，因为它是"可以被数字证明"的那一层。

### 2.2 检索层的三个指标

| 指标 | 定义 | 回答什么问题 |
|---|---|---|
| **hit@k** | 前 k 位里有相关块吗（是/否） | **能不能找到** |
| **MRR** | `1 / 首个相关块的位置` | **排得够靠前吗** |
| **recall** | 命中的相关块数 / 相关块总数 | **相关的一块都没漏吗** |

**为什么 MRR 值得单独说：**

`precision = 命中数 / 返回数`——它**受返回条数影响很大**。你把 Top-N 从 5 改成 50，precision 必然下降，但检索能力一点没变。**`precision` 在"注入 Top-N"的场景下几乎不是一个可比的指标。**

`MRR`（Mean Reciprocal Rank）只问一件事：**第一个相关块排在第几位？**

```
首个相关块在 #1  → MRR = 1.0      （最好）
首个相关块在 #2  → MRR = 0.5
首个相关块在 #3  → MRR = 0.333
首个相关块在 #5  → MRR = 0.2
无相关块        → MRR = 0.0
```

**它对"排序质量"高度敏感，对"返回多少条"不敏感**——这正是精排/融合策略该被衡量的东西。

本项目把它写进了 `RagMetrics`（`RagEvaluator.java:130-140`）。用对象图看一下一次评测产出哪些指标：

<img class="mermaid-svg" src="/zh/book-assets/diag-0145.svg" alt="本项目把它写进了 `RagMetrics`（`RagEvaluator.java:130-140`）。用对象图看一下一次评测产出哪些指标：" />

> **图 33-1**　`RagMetrics` 的指标结构。**字段天然分成两组**：基础统计（`hitCount` / `maxSim` / `avgSim`）只要有候选就能算；而检索质量指标（`precision` / `recall` / `firstHitRank` / `mrr`）必须有 ground truth。**注意右下角那个警示框**——生产调用点传的是 `null`，所以质量指标四个字段全是"未计算"状态（`NaN` 或 `0`），不是"结果为零"。下面详细讲这个坑。

**`hitAtK(k)` 的实现把"hit@k"的语义写死成"首个相关块在前 k 位"。** 严格来说 `hit@k` 的通行定义是"前 k 位里**存在**至少一个相关块"——两者在"只有一个相关块"的 golden 场景下等价；**但在"多个相关块"的场景下，`hitAtK` 会比严格定义更严格**（相关块可能在第 8 位，前 3 位没有，但"前 8 位有相关块"也是 `hit@8`）。

**这是一个"够用但要说明白"的实现**：它当前服务于"一条查询对应一个 ground-truth 块"的评测集，此时完全正确。**如果将来 golden set 变成"一条查询对应多个相关块"，就要重新审视这个定义。**

### 2.3 ground truth 从哪来（这是整个评测的死穴）

**生产流量里没有 ground truth。** 用户提交一个 PR，你知道检索到了什么，但你**不知道"应该"检索到什么**。

三条来源，各有取舍：

| 来源 | 怎么得到 | 优点 | 缺点 |
|---|---|---|---|
| **人工 golden set** | 人工标注"这个查询应该命中哪个块" | 准确、可解释 | 规模小、维护成本高 |
| **反馈回流** | 开发者标记"这条意见是误报" | 真实、持续产生 | **只覆盖"错"的样本**，缺"对"的样本 |
| **合成桩** | 构造语料时**提前知道**哪个块是对的 | **完全确定、可复现** | 只测"链路逻辑"，不测"真实语义质量" |

**本项目的选择很清醒**：生产链路**不传 ground truth**，评测能力落在**测试**里。这一点后面 3.1 和 3.4 会分别看到正反面。

### 2.4 为什么必须用"桩"，而不是真实嵌入

这是评测能不能落地的关键判断。

**真实嵌入是不可复现的**：

- 同一个文本，不同模型版本 → 不同向量；
- 需要外网、需要 API Key → 测试环境不一定有；
- **中文语义相似度**对"离线哈希嵌入"几乎是随机的（第 28 讲：哈希嵌入只有 256 维、且是 token 哈希）。

`RagRecallBaselineTest` 的类注释把这件事说得很清楚：

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:23-28
 * <p>目标：确保「阈值过滤(min-similarity=0.3) + 注入前去重」两项改动不降低召回质量。
 * 中文语义相似度依赖真实子词向量嵌入（生产用 TokenHub），离线哈希嵌入对中文区分度过低，
 * 无法稳定复现。因此本测试用 {@link StubKnowledgeStore} 预设 similarity（模拟真实向量检索结果），
 * 与嵌入实现解耦，确定性验证三层逻辑：
```

**"与嵌入实现解耦"这五个字，是让评测从"跑不了"变成"每次 CI 都跑"的关键。**

**桩测试测什么、不测什么，必须说清楚：**

| 测得到 | 测不到 |
|---|---|
| 阈值过滤逻辑（`sim >= 0.3` 放行） | **真实相似度分布**（阈值 0.3 到底合不合适） |
| 去重逻辑（相同 content 只注入一次） | 切块质量对语义完整性的影响 |
| abstain 行为（全低于阈值返回空） | 排序质量（重排/MMR 的真实收益） |
| **召回通路是否连通** | 嵌入模型换了之后召回是否变好 |

**结论：桩测试是"链路回归基线"，不是"效果评测"。** 两者都要，别互相替代。

### 2.5 `NaN` 与 `0`：未计算 ≠ 算了为零

这是本讲最值得带走的一个工程习惯。

`RagEvaluator.evaluate` 一开始就把两个指标设成 `NaN`：

```java
// core/rag/RagEvaluator.java:86-110（节选）
public RagMetrics evaluate(List<MemoryEntry> passed, java.util.Set<String> groundTruth) {
    double maxSim = passed.stream().mapToDouble(this::parseSimilarity).max().orElse(0.0);
    double avgSim = passed.stream().mapToDouble(this::parseSimilarity).average().orElse(0.0);
    double precision = Double.NaN, recall = Double.NaN;      // ← 未计算
    int firstHitRank = 0;
    double mrr = 0.0;
    if (evalEnabled && groundTruth != null && !groundTruth.isEmpty()) {
        ... // 只有这里才会算出真值
    }
    return new RagMetrics(passed.size(), maxSim, avgSim, precision, recall, firstHitRank, mrr);
}
```

**为什么用 `NaN` 而不是 `0`？**

| 值 | 语义 |
|---|---|
| `0.0` | **算了，结果就是零**（比如"召回率确实是 0%"） |
| `NaN` | **没算**（没有 ground truth，无法评估） |

**如果这里用 `0.0`，你就会得到一份"召回率 0%"的报告——一个看起来极其严重、实际毫无意义的数字。** 接下来一定有人去"修复"这个 0%，把时间浪费在一个不存在的故障上。

**这个设计是对的，值得学习。** 但它在生产里导致了一个**新的问题**——见 3.1。

### 2.6 四层评测：离线桩 / 离线真库 / 影子 / 在线

2.1 已经把评测按  **"评什么"** 分成三层（检索 / 生成 / 端到端）。但真正决定"这件事能不能每天跑、能不能上 CI"的，不是"评什么"，而是 **"在哪儿评"**。同一件事——检索层——用桩跑、用真库跑、用影子跑、用 A/B 跑，成本差一个量级。

| 层 | 本项目载体 | 成本 | 可信度 | 能上 CI 吗 |
|---|---|---|---|---|
| ① 离线桩 | `RagRecallBaselineTest` | 极低：无外网、无 API Key、无 PG | 只对 **"链路逻辑"** 可信 | ✅ 每个 PR |
| ② 离线真库 | `PgRagSemanticsE2eTest` / `PgRagFreshnessE2eTest` | 中：要起真 PG + 真嵌入 | 对 **"语义与排序"** 可信 | ⚠️ 只能 nightly |
| ③ 影子 | 生产流量双写（结果不返回给用户） | 中高：同一查询多跑一遍 | 对 **"真实分布"** 可信 | ❌ 不在 CI |
| ④ 在线 A/B | 分流 + 指标对比 | 最高：要样本量、要等观测周期 | 唯一能证 **"业务变好"** | ❌ 不在 CI |

**成本、可信度、能否上 CI——这三件事必须一起看：**

- 只看可信度 → 你会想直接上 A/B（最贵、最慢）；
- 只看成本 → 你会永远只留桩测试（测不到真实语义）；
- 只看"能不能上 CI" → 你会把真库 E2E 塞进每个 PR，然后因为慢而被人关掉。

**四层是"从便宜到贵"的阶梯，不是"从差到好"的排序。** 上游能拦住的不留到下游：`RagRecallBaselineTest` 用 5 个查询、5 个 `gtSources`（`RagRecallBaselineTest.java:75-82`）把"护栏被拆掉"这类改动在 PR 阶段就红掉，比在 A/B 上等两周便宜得多。

**第 ③ 层在本项目是空的。** 它的两个前提都不成立：生产调用点是 `evaluate(deduped, null)`（`RagContextBuilder.java:219`），而 `eval-enabled: true`（`application.yml:237`）只把开关打开了、并没有喂数据。**影子的本质就是"把那个 `null` 补上，并且不把结果返回给用户"**——它是第 ①② 层与第 ④ 层之间**唯一**能在真实分布上、又不冒业务风险的验证位置。

**工业界对这件事的态度可以看 spring-ai**：它的可观测性是**库的一等公民**（有独立的 observation 包与 convention 接口，`spring-ai/spring-ai-vector-store/src/main/java/org/springframework/ai/vectorstore/observation/AbstractObservationVectorStore.java`）——**而不是"使用方自己打日志"**。本项目 `RagTrace` 定义了却零调用（3.3），恰好站在这个做法的反面。

### 2.7 线上怎么知道变好了：隐式信号与 A/B

生产侧的第一个问题是 **没有 ground truth**（2.3）。所以在线的路只有一条：**不去标注"应该命中什么"，而是观察"命中之后发生了什么"。**

**三类隐式信号（implicit signal）：**

| 信号 | 怎么采 | 回答什么问题 | 偏向 |
|---|---|---|---|
| 命中后是否被采纳 | 审查意见被接受、客服回复被直接用 | 检索到的块有没有帮上忙 | 只看得见"帮上了"，看不见"本可帮上却漏了" |
| 是否被点了  **"误报"** | 显式负反馈入口 | 检索到的块有没有帮倒忙 | 只覆盖"错"的样本（对应 2.3 的"反馈回流"） |
| 上下文块是否被引用 | 输出里的引用标记 / 块 id 回指 | 注入的块有没有真的进到答案 | 受生成侧格式影响，不是纯检索指标 |

**隐式信号只能当弱标签（weak label），不能当 ground truth。** 它有两个结构性缺陷：

- **曝光偏差**：你只能拿到"被检索出来的块"的反馈；**召回漏掉的那些块，永远不会有反馈。**
- **只覆盖一端**：采纳与误报都是有行为的样本；"没说话、也没帮上"的大多数是沉默的。

**所以隐式信号的正确用法是回流成"下一轮 golden set 的候选"，而不是直接算成指标。** 它给阈值 0.3、给 MMR 的 λ、给 `retrieve-k` 提供**真实分布上的偏离证据**，再由人工抽检确认。

**第二个问题：A/B 的分流单位。**

**分流单位必须是查询或会话，不能是用户。**

| 分流单位 | 会发生什么 |
|---|---|
| `userId` | 同一个人的**同一段会话**里，前后提问可能落到不同版本——而 RAG 是带上下文的，**一次会话看到两个版本，你测到的是版本切换的噪声，不是版本差异** |
| `queryId` / `sessionId` | 同一次会话恒定走一个版本，版本差异才可归因 |

**RAG 的多轮特性让"按用户分流"直接失效——这是它与推荐 / 排序 A/B 最不一样的地方。**

**第三个问题：样本量必须显式写。** 不能写"跑一周看看"；要在动手前把最小可检测提升（MDE）算出来。

> **推演**：`16 × 0.6 × 0.4 / 0.02² = 9,600`（假设基线采纳率 60%、要检测的绝对提升是 2 个百分点、95% 置信 + 80% 功效；基座值见 `application.yml:237` 的 `eval-enabled: true`——本项目该开关已打开，但生产 ground truth 恒为 `null`，所以这个样本量目前无处落地）

**双基座对照：**

| 维度 | A：代码审查助手 | B：千万 DAU 客服助手 | 由此分叉的设计决策 |
|---|---|---|---|
| 流量规模 | 团队内部触发，中低 QPS | ≈ 231 QPS（推演，见下） | A 可全量记漏斗日志；B 必须采样后落盘 |
| 分流单位 | 用户数少，**但 RAG 场景仍应按会话** | 必须按 `sessionId` / `queryId` | 两边统一按会话分流，别为了省事引入不可归因 |
| ground truth 来源 | CI 基线（`RagRecallBaselineTest` 的 5 查询 5 `gtSources`） | 隐式信号回流 + 人工抽检 | A 的效果由 CI 守；B 必须建在线信号管道 |
| 评测集扩容 | "手册有哪几章就测哪几类"，人工维护 | UGC 每天新增，**评测集必须能自动扩** | B 要能自动生成"新知识 → 候选查询"，不能靠人写 |
| 多租户 | 多租户（team），规范类语料**低频变更** | 多租户（商家），商品 / 政策**高频变更** | B 的评测集要按租户切分并设定各自复跑频率 |
| 观测周期 | 一个 PR 周期（分钟级） | 天 / 周级（要等样本量凑齐） | 决策节奏不同：A 靠 CI 红绿，B 靠周报 |

> **推演**：`1000 万 × 2 / 86400 ≈ 231` QPS（假设 DAU 1000 万、人均每日 2 次知识问答；基座值见 `application.yml:221` 的 `retrieve-k=50`）

**评测口径的业界出处**（只给直链与 ID，标题以 arXiv 官方返回为准）：

- 指标族：Ragas（`2309.15217`，https://arxiv.org/abs/2309.15217）给出 faithfulness / answer relevance / context precision 这一族指标；
- **不依赖 GPT-4 打分的可复现路线**：ARES（`2311.09476`，https://arxiv.org/abs/2311.09476）——用**小模型 + 少量标注**做评测。这条路线**正对本讲的"生产评估恒空转"**：评测器跑不动，往往不是指标选错了，而是"打分"这一步太贵、太不可复现；
- 检索口径：BEIR（`2104.08663`，https://arxiv.org/abs/2104.08663）是 nDCG / recall 的口径来源；
- 嵌入选型：MTEB（`2210.07316`，https://arxiv.org/abs/2210.07316）是嵌入模型的横评基准——**换嵌入模型前先看它，再决定要不要重建评测集**；
- 检索质量差时触发纠正：CRAG（`2401.15884`，https://arxiv.org/abs/2401.15884）。

**这一节的结论只有一句：** 在线评测的对象不是"检索质量"，而是 **"带偏差的弱标签 + 可归因的分流 + 事先算好的样本量"** 三件套。缺任何一件，A/B 都会退化成"我觉得这版更好"。

**落地步骤（5 步）：**

1. **冻结三个基线数**：跑 `RagRecallBaselineTest` 的 5 个查询，记录 ① `ctx` 非空的查询数（基线 **5/5**）；② 噪声块出现次数（基线 **0**）；③ 去重后 `[sec-sql]` 的出现次数（基线 **1**）（`RagRecallBaselineTest.java:84-92`、`:96-111`）。
2. **验证基线真的会红**：把阈值从 `0.3` 临时改成 `0.9` 重跑——确认 ground-truth 块（sim=0.85）被拦、`ctx` 为空、测试失败（`RagRecallBaselineTest.java:26-28`）。**一个恒绿的数字不是基线。**
3. **补一条负样本用例**：照 `Set.of("does-not-exist")`（`PgRagSemanticsE2eTest.java:211-220`）的做法，加一条"全不命中 → abstain 且 `ctx` 为空"的断言。
4. **做一次真实改动**：把 `retrieve-k` 从 `50` 改成 `20`（`application.yml:221`）重跑，用第 1 步的三个数回答"这版比上版好吗"。
5. **对 `evaluate(deduped, null)`（`RagContextBuilder.java:219`）做显式选择**：要么接上 ground truth，要么明确声明"本系统不采集该指标，效果由 CI 基线保证"，并让日志**不打印**未计算的字段。

**基座 B 在第 5 步上的答案是唯一的。** A 基座的规范类语料低频变更，CI 基线可以一直手工维护；B 基座的知识每天都在进来，人工维护 golden set 一定跟不上：

> **推演**：`50 万 × 10 = 500 万` 篇/天（假设活跃商家 50 万、每家每天新增 10 篇 UGC 文档；基座值见 `application.yml:226` 的 freshness `max-age-days=0`——该配置要求知识"当天有效"，进一步放大了评测集的扩容量）

**所以 B 必须把"隐式信号 → 候选评测集"做成自动管道，A 可以一直靠 CI 基线——这是本讲两个基座最大的分叉。**

**★ 判据：如果一次 RAG 改动跑完，你说不出"哪个数字变了、变了多少"，那这次改动就没有被验收过——它只是又一次"感觉变好了"。**

### 3.1 生产调用点：ground truth 恒为 `null`

`RagContextBuilder.buildContext` 里调用评估器的地方（`RagContextBuilder.java:219`）：

```java
// core/memory/RagContextBuilder.java:218-220
// 7. 评估指标 + 格式化（含 small-to-big 父章节上下文回填）
RagEvaluator.RagMetrics metrics = evaluator.evaluate(deduped, null);
appendKnowledgeBlocks(sb, deduped);
```

**第二个参数是硬编码的 `null`。**

回头看 `evaluate` 的判据（`:92`）：

```java
if (evalEnabled && groundTruth != null && !groundTruth.isEmpty()) {
```

**`groundTruth == null` → 整个 `if` 恒不成立** → `precision` / `recall` 保持 `NaN`，`firstHitRank` / `mrr` 保持 `0` / `0.0`。

**而配置开关是打开的**：

```yaml
# src/main/resources/application.yml:235-237
    # 是否记录 ground-truth 召回评估指标（需候选携带 expectedId 元数据）；
    # true 时 RagEvaluator 在 evalEnabled 下计算 precision/recall，配合回归基线。
    eval-enabled: ${RAG_EVAL_ENABLED:true}
```

**于是：**

| 字段 | 生产值 | 说明 |
|---|---|---|
| `hitCount` | `passed.size()` | **有效**（但它不是"命中数"，见 3.2） |
| `maxSimilarity` | 有效 | 有效 |
| `avgSimilarity` | 有效 | 有效 |
| `precision` | **`NaN`** | **永远不计算** |
| `recall` | **`NaN`** | **永远不计算** |
| `firstHitRank` | **`0`** | **永远不计算** |
| `mrr` | **`0.0`** | **永远不计算** |

**这就是本讲要建立的判断力：一个"设计正确"的机制，可能因为没人喂数据而永远空转。**

**注意这里的微妙之处**：`precision` / `recall` 是 `NaN`（诚实地表示"未计算"），但 `firstHitRank` / `mrr` 是 **`0`**（`int` 和 `double` 的默认值，**看起来像"首个相关块位置 = 0"，而 0 在 `hitAtK` 里被当作"无命中"**）。

```java
// core/rag/RagEvaluator.java:137-139
public boolean hitAtK(int k) {
    return firstHitRank > 0 && firstHitRank <= k;
}
```

**于是 `hitAtK(5)` 在生产数据上恒为 `false`**——而 `false` 的语义是"前 5 位没有相关块"，**不是"没算"**。

**同一个方法里，四个未计算的字段用了两种不同的"未计算"表示**（`NaN` 和 `0`）。`NaN` 的那个是对的；`0` 的那个**会把"未计算"伪装成一个业务结论**。

**修法（两步）：**

1. **要么把 ground truth 接上**——从 `FeedbackStore` 里取"被标记为误报"的块 id 作为负样本、从历史审查被采纳的意见反查"应该命中的块"作为正样本（这是第 22 讲"置信度校准"的同一条数据链）；
2. **要么明确放弃生产指标，只保留测试基线**——那就把 `eval-enabled` 的输出改成 `null` 语义（`RagMetrics` 的字段用 `Double` 包装类型而非基本类型，`null` 表示未计算），并且**在日志里不要打印未计算的字段**。

**最不该做的是现在这样**：既算了（返回一份 `RagMetrics`）、又没算（一半字段是默认值）、还把它打进了日志。

### 3.2 `hitCount` 不是"命中数"

```java
// core/rag/RagEvaluator.java:109
return new RagMetrics(passed.size(), maxSim, avgSim, precision, recall, firstHitRank, mrr);
```

**第一个参数的位置上是 `hitCount`，传入的值是 `passed.size()`。**

| 字段名承诺 | 实际值 |
|---|---|
| `hitCount` —— "命中数" | **通过阈值的块数**（= 放行数） |

**"放行"和"命中"是两回事：**

- **放行**：这个块通过了相似度阈值（它"看起来相关"）；
- **命中**：这个块**确实是** ground truth（它"真的相关"，需要标注才知道）。

**这是"名字承诺 > 实现"在本项目里的第九次现身**（前八次：第 11、12、19、23、27、29、32 讲，加上本讲的 `RagTrace`）。

**危害形态和前几次一样**：读日志的人看到 `hitCount=18`，会理解成"找到了 18 条相关知识"，而真相是"18 条候选通过了 0.3 的阈值，其中有多少真的是需要的**没人知道**"。

**这个数字在当前链路里没有被打印**（`RagContextBuilder` 打印的是 `passed.size()` 和 `deduped.size()`，用的是自己的变量，没读 `hitCount`），所以危害目前是**潜在的**：一旦有人读 `metrics.hitCount()` 写进监控看板，就会得到一个错误口径的指标。

**修法（一行）**：改名。`hitCount` → `passedCount` 或 `candidateCount`。**名字是最便宜的文档。**

2. 删掉 `RagTrace`，承认"日志就够了"。

**最不该做的是留着它、并在注释里继续承诺它。**

### 3.4 真正的评测闭环：`RagRecallBaselineTest`

**这一节是本讲的正面教材。** 前四节都是"哪里没做到"，这一节是"做到的样子"。

`RagRecallBaselineTest` 的核心设计是**用一个 stub 知识库替换真实检索，把 `similarity` 直接预设好**：

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:39-53
/** 预设相似度的 stub 知识库：返回预置块（模拟真实向量检索结果）。 */
static class StubKnowledgeStore implements KnowledgeStore {
    private final List<MemoryEntry> entries;
    StubKnowledgeStore(List<MemoryEntry> entries) { this.entries = entries; }
    @Override public int saveKnowledge(String teamId, String doc, Map<String, String> meta) { return 0; }
    @Override public void deleteByMetadata(String teamId, String key, String value) {}
    @Override
    public List<MemoryEntry> searchKnowledge(String query, int topK, String teamId, boolean includeGlobal) {
        return entries; // 直接返回预置块（已带 similarity 元数据）
    }
}
```

**这个 stub 有三层价值：**

**① 解耦了嵌入模型。** 测试不依赖外网、不依赖 API Key、不受模型版本影响——**每次 CI 都能跑，且结果完全确定**。

**② 它把"检索"这件事抽象成了"一组带 similarity 的块"。** 于是测试可以**精确控制**每个块的相似度——这是真实嵌入做不到的（第 31 讲用过同样的手法：受控向量桩）。

**③ 它测的是"三层逻辑"，而不是"嵌入质量"**——类注释说得很清楚：

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:29-31
 *   - 阈值过滤：sim >= 0.3 放行，sim < 0.3 拦截（abstain 抑制噪声）；
 *   - 去重：重叠切块（content 归一化相同）只注入 1 次，不丢语义；
 *   - 召回：5 个典型查询的 ground-truth 相关块（sim=0.85）全部被放行并注入（recall=1.0）。
```

**然后看它的断言——这是"评测闭环"真正落地的地方：**

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:84-92
for (int i = 0; i < queries.length; i++) {
    String ctx = builder.buildContext("teamA", "MULTI-AGENT",
            List.of(new CodeDiff("Demo.java", queries[i])));
    assertFalse(ctx.isBlank(), "查询[" + i + "] 应召回相关知识，不应 abstain");
    assertTrue(ctx.contains("[" + gtSources[i] + "]"),
            "查询[" + i + "] 应召回 ground-truth 源 " + gtSources[i] + "，实际注入:\n" + ctx);
    // 噪声块不应出现在任何注入中
    assertFalse(ctx.contains("[misc]"), "查询[" + i + "] 噪声块（sim=0.15）应被阈值拦截");
}
```

**注意这三个断言分别锁住了什么：**

| 断言 | 锁住的行为 |
|---|---|
| `ctx` 非空 | **召回通路连通**（不是 abstain） |
| `ctx` 含 ground-truth 的 `source` | **正确的块被召回并注入**（hit） |
| `ctx` 不含 `[misc]` | **噪声被阈值拦截**（闸门生效） |

**注意第二个断言的精妙之处**：它断言的不是"注入了 N 条"，而是 **"注入了 `[sec-sql]` 这个源的块"**——也就是说，**ground truth 是用 `source` 元数据表达的业务身份，而不是内部 id**。这比断言 id 更接近"人怎么判断检索对不对"。

**5 个查询覆盖了 5 类典型问题**（`:75-82`）：

```java
String[] queries = {
        "String sql = \"select * from user where id=\" + id; SQL 拼接",
        "private String password = \"123456\"; 明文密码",
        "System.out.println(\"debug\"); 打印日志",
        "catch (Exception e) { e.printStackTrace(); } 空 catch",
        "// TODO 临时实现 待优化"
};
String[] gtSources = {"sec-sql", "sec-secret", "style-log", "style-exc", "proc-todo"};
```

**SQL 注入 / 硬编码密码 / 日志规范 / 异常处理 / TODO 标记**——**这五类正好对应内置手册的五个章节**。所以这份 golden set 不是随便编的，它是 **"手册有哪几章，就测哪几类问题"**。

**而且它带了一个反向边界用例**（`:96-111`）：

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:95-125（节选）
@Test
void dedupRemovesIdenticalOverlapChunks() {
    // 真实场景：handbook 重叠切块产出 content 完全相同的重复块（PR#26 实测 5→2）。
    // 三个块 content 完全一致，去重后应只注入 1 次，且不丢语义。
    ...
    int occurrences = ctx.split("\\[sec-sql\\]").length - 1;
    assertEquals(1, occurrences, "content 完全相同的重叠块去重后应只注入 1 次，实际 " + occurrences + " 次");
}

@Test
void dedupKeepsDistinctChunks() {
    // 反向边界：content 不同的块（部分重叠但非完全相同）应分别保留，不去重。
    ...
    assertEquals(2, ctx.split("\\[sec-sql\\]").length - 1, "不同 content 的块应各自保留，不去重");
}
```

**一对正反边界**：去重**必须删掉完全重复的**，**又不能删掉"部分重叠但不同"的**。**只测前一半，你会写出一个"删太多"的去重器；只测后一半，你会写出一个"什么都不删"的去重器。**

**这是写好评测用例的通用方法：每个规则配上它的反向边界。**

**最后，容器化装配让测试和生产用同一套参数：**

```java
// src/test/java/com/codereview/agent/core/rag/RagRecallBaselineTest.java:37-38
/** 真实链路配置：min-similarity=0.3，evalEnabled=true（application.yml 已落地）。 */
private static final double MIN_SIM = 0.3;
```

**"真实链路配置"这行注释很重要**——它声明了"测试里的阈值和生产一致"。**如果测试用 0.3 而生产配了 0.05，这个测试就在保护一个不存在的场景。**

**（顺带说：这个常量是硬编码的，没有从 `application.yml` 读。所以"测试与生产阈值一致"这件事靠注释承诺，不靠机制保证。更稳的做法是从同一份配置读，或者至少在测试里加一个断言去读 yml 校验。这是这个优秀测试里唯一的松点。）**

### 3.5 真库上的对照：`PgRagSemanticsE2eTest`

桩测试是"链路回归"，真库 E2E 是"语义验证"。后者**会真的传 ground truth**：

```java
// src/test/java/com/codereview/agent/e2e/PgRagSemanticsE2eTest.java:211-220（节选）
Set<String> groundTruth = Set.of(String.valueOf(goldHit.id()));
RagEvaluator.RagMetrics m = evaluator.evaluate(hits, groundTruth);
...
RagEvaluator.RagMetrics none = evaluator.evaluate(hits, Set.of("does-not-exist"));
```

**注意第二行**：`Set.of("does-not-exist")` —— 用一个**故意不存在的 id** 当 ground truth，用来验证"无命中时 `mrr=0`、`firstHitRank=0`"这条路径。

**这是"反向用例"的第二次出现**（第一次是 3.4 的去重正反边界）。**负样本用例（"应该没有命中"）常被忽略，但它才是验证"闸门真的会关"的唯一手段**（第 31 讲用受控向量桩做过同一件事）。

**所以本项目的评测布局是这样的：**

| 层次 | 载体 | 覆盖 |
|---|---|---|
| 链路逻辑回归 | `RagRecallBaselineTest`（桩） | 阈值 / 去重 / abstain / 召回通路 |
| 语义与排序 | `PgRagSemanticsE2eTest`（真库） | `similarity` 语义、MRR、无命中路径 |
| 新鲜度 | `PgRagFreshnessE2eTest`（真库） | `max-age-days` 过滤 |
| 生产指标 | **无**（`precision`/`recall` 恒 `NaN`） | ❌ |

**前三行是它的优点，第四行是它的空缺。** 而**空缺是否可接受，取决于你的运维模型**：如果你的答案是"效果靠 CI 基线守，生产只看漏斗日志"，那这个空缺是**有意为之**；如果答案是"我想在生产看到召回率曲线"，那就必须把 ground truth 接上。

**本讲的观点是：这两种答案都可以，但不能"不说"。** 现在代码的状态是"配置项写着 `eval-enabled: true`，实际永远算不出来"——**这是"没说"，而不是"选择了前者"。**

## 四、避坑清单

- [ ] **上线前先建基线，否则你无法回答"这版比上版好吗"。** 三条最低配的用例：① 该命中的命中（hit）；② 不该命中的不命中（噪声拦截）；③ 全不命中时 abstain。
- [ ] **每个规则都配一个反向边界。** 去重"必须删完全重复的"+"不能删部分重叠的"；阈值"必须拦低分的"+"必须放高分"。
- [ ] **评测必须与嵌入实现解耦。** 真实嵌入不可复现（模型版本、外网、中文区分度），用 stub 预设 `similarity` 才能断言。**"跑不动的测试等于没有测试。"**
- [ ] **桩测试和效果评测是两件事，别互相替代。** 桩测"链路有没有通"，真库 E2E 测"语义对不对"，人工抽样测"业务好不好"。
- [ ] **`NaN` 表示"未计算"，`0` 表示"算了为零"，绝不能用 `0` 顶替 `NaN`。** 一份"召回率 0%"的假报告会让人去修一个不存在的故障。
- [ ] **`int` / `double` 字段的默认值会伪装成业务结论。** `firstHitRank = 0` 让 `hitAtK(5)` 恒 `false`——而 `false` 的语义是"前 5 位没有相关块"。**未计算必须用包装类型的 `null` 显式表达。**
- [ ] **配置项打开了、数据源没接上，是最容易被忽略的一类空转。** `eval-enabled: true` + `evaluate(..., null)` = **一个永远不可能算出结果的评估器**。
- [ ] **字段名必须能被信任。** `hitCount` 实际是 `passed.size()`（放行数）——**"放行"不是"命中"**。改名的成本是一行，误解的成本是一个错误口径的监控看板。
- [ ] **grep 你的"给人看的方法"（`summary()` / `toXxx()` / `format()`）。** 没有调用方，说明这个可观测能力从未接线——它当初是为解决某个具体排查困难而写的。
- [ ] **"测试参数与生产一致"要靠机制而不是注释。** 硬编码 `MIN_SIM = 0.3` 并注明"与 application.yml 一致"，是注释承诺；从同一配置源读取才是保证。
- [ ] **负样本用例（"应该没有命中"）是验证闸门唯一的办法。** 正样本只能证明"能召回"，证明不了"该拦的拦住了"。
- [ ] **评测集的覆盖面要跟着语料走。** 本项目 5 个查询对应手册的 5 个章节——**"手册有哪几章，就测哪几类问题"，这是最不容易偏的 golden 集构造法。**
- [ ] **评测要分四层，别拿一层的结论去回答另一层的问题。** 桩测试（`RagRecallBaselineTest`）只证明"链路逻辑对"，证明不了"语义好"；真库 E2E 证明"语义对"，证明不了"业务好"。**成本、可信度、能否上 CI 三者要一起看，别指望一层包打天下。**
- [ ] **A/B 的分流单位必须是查询或会话，不能是用户。** RAG 是带上下文的：同一次会话看到两个版本，你测到的是版本切换的噪声，不是版本差异。**这是 RAG 与推荐 / 排序 A/B 最不一样的地方。**
- [ ] **隐式信号只能当弱标签，不能当 ground truth。** 采纳、误报、引用回指都只覆盖"被检索出来"的那部分样本——**召回漏掉的块永远不会有反馈。** 它该回流成下一轮 golden set 的候选，而不是直接算成召回率。

## 本讲小结

1. **没有基线的优化是调参。** 检索层是最该先做评测的一层——它的 ground truth 在构造语料时就已经知道了。
2. **`hit@k` 测"能不能找到"，`MRR` 测"排得够不够靠前"，`recall` 测"有没有漏"。** `precision` 在 Top-N 注入场景下几乎不可比（受 N 影响太大）。
3. **`NaN` 与 `0` 必须严格区分**：`0` 是"算了，结果是零"，`NaN` 是"没算"。**用 `0` 顶替会让"没评估"伪装成一个严重故障。** 本项目 `precision`/`recall` 用 `NaN`（对的），但 `firstHitRank`/`mrr` 用 `0`（会让 `hitAtK` 返回一个"看起来是业务结论"的 `false`）。
4. **评测必须与嵌入解耦。** `RagRecallBaselineTest` 用 stub 预设 `similarity`，把 5 个查询的召回、噪声拦截、去重正反边界都锁成断言——**这是本讲的正面教材，也是"回归基线"的正确形态**。
5. **生产链路的评估目前是空的**：`evaluate(deduped, null)` + `eval-enabled: true` = **一个永远算不出结果的评估器**。要么接上 ground truth，要么显式声明"靠 CI 基线守效果"——**不能"不说"**。
6. **`hitCount` 实际是放行数、`RagTrace` 从未被接线**——本讲又抓到两处"名字/注释承诺 > 实现"。**`grep` 你的 `summary()` / `toXxx()` 方法有没有调用方，是一个成本极低、收益很高的检查动作。**
