## 二、原理

### 2.1 为什么要"重排"：双塔与交叉编码器的差别

初检（向量检索）用的是**双塔（bi-encoder）** 结构：


<img class="mermaid-svg" src="/zh/book-assets/diag-0043.svg" alt="初检（向量检索）用的是双塔（bi-encoder） 结构：" />


> **图 28-1**　**双塔（bi-encoder）**：查询与文档各自独立编码。编码文档时它**不知道**将来会有什么查询来问它——**这既是它快的原因（向量可离线预计算、建索引），也是它精度的天花板。**

**关键特征：查询和文档是"各自独立编码"的。** 编码文档的时候，它**不知道**将来会有什么查询来问它。所以：

- 优点：文档向量可以**离线预计算、建索引**，检索是 O(log n) 级别的近邻查询——**快**；
- 缺点：**没有查询与文档的交互**。一切语义对齐都得靠"两个独立向量恰好靠近"。

**Cross-encoder（交叉编码器）** 换了一种做法：


<img class="mermaid-svg" src="/zh/book-assets/diag-0044.svg" alt="Cross-encoder（交叉编码器） 换了一种做法：" />


> **图 28-2**　**交叉编码器（cross-encoder）**：把查询和文档拼在一起送进模型。**精度显著更高，代价是每一对都要现算**——所以它只能出现在精排阶段，承担不了初检。

把查询和文档**拼在一起**送进模型，让注意力机制在两者之间自由交互。**精度显著更高**，但代价是：

- **无法预计算**——每个 (查询, 文档) 对都要跑一次前向；
- **成本与候选数成正比**——50 个候选就是 50 次推理。

**所以工业界统一用两阶段：**

| 阶段 | 结构 | 候选数 | 目标 |
|---|---|---|---|
| **召回** | 双塔（向量 / BM25） | 宽（50–200） | 别漏（高 recall） |
| **精排** | cross-encoder | 窄（10–20） | 排准（高 precision） |

`Reranker.java:10-11` 的接口注释引用了一个业界经验值：

```java
 * <p>初检（向量 / 混合）通常召回 10~50 条候选，但 LLM 上下文窗口有限且对噪声敏感，
 * cross-encoder 重排能比简单点积排序把精度再提升 20~35%（代价约 200~500ms）。
```

**这个 20~35% 是注释里引用的业界经验值，不是本项目实测数据**——引用外部数字时必须标明来源，否则读者会以为是你的实测结果。

### 2.2 三种重排实现，选型看约束

| 实现 | 精度 | 成本 | 依赖 | 本项目角色 |
|---|---|---|---|---|
| **启发式**（词重叠 + 元数据加权） | 低 | ≈0 | 无 | **默认 / 兜底** |
| **托管 API**（Cohere / Jina） | 高 | 每千次调用计费 + 200~500ms | 外网 + API Key | 可选（默认开，无 Key 自动降级） |
| **本地 cross-encoder** | 高 | GPU/CPU 推理 | 模型权重 + 运行时 | 未采用 |

**为什么本项目选"启发式默认 + 托管 API 可选"**：重排是**质量闸门，不是可用性依赖**。

**这个区分很重要**（第 17、20 讲反复出现过）：

- **可用性依赖**（LLM 网关、数据库）挂了 → 整个链路必须停或降级；
- **质量闸门**（重排、阈值过滤）挂了 → 结果差一点，但**链路必须继续**。

所以 `ApiReranker` 的降级路径特别多——**四条**：


### 2.3 为什么还需要"多样性"：MMR

**重排只解决"相关性"，不解决"信息量"。**

`rerank` 的目标函数是"让更相关的排前面"——它**完全没有"避免重复"这一项**。而 Top-N 的相关性排序天然会导致**同质化**：

- 同一个章节的相邻切块，内容高度相似 → 相关性也都高 → **一起挤进 Top-N**；
- 结果：注入 5 条 = 1 个知识点 × 5 种说法。

**MMR（Maximal Marginal Relevance）** 在目标函数里加了惩罚项：

```
MMR(d) = λ · relevance(d, query) − (1 − λ) · max_redundancy(d, selected)
```

- **第一项**：这个块和查询有多相关（**要**）；
- **第二项**：这个块和"已经选中的块"最高有多像（**不要**）；
- **λ ∈ [0,1]**：平衡系数。`λ=1` 退化为纯相关性；`λ=0` 退化为"选最不相关的"。

**本项目 `λ = 0.7`**（`RagContextBuilder.java:76-77`）：

```java
/** MMR 相关性权重（1-λ 为冗余惩罚权重），业界常用 0.7。 */
private static final double MMR_LAMBDA = 0.7;
```

**贪心流程**（每次选当前 MMR 最高的一个，选完再更新）：

```
1. 从候选池里，对每个候选算 MMR（与查询的相关性 − 与已选集合的最大冗余）
2. 选中 MMR 最高的那个，加入已选集合
3. 重复，直到选满 topN
```

**这是一个 O(topN × 候选数) 的贪心算法**——不是全局最优，但在"挑选"场景下足够好，且实现简单。

### 2.4 MMR 成立的前提：冗余度量必须真的能算出"像"

MMR 的第二项叫 `max_redundancy`。**冗余怎么算？** 本项目用 **Jaccard 相似度**（词集合的交集 / 并集）。

**这里有一个致命前提：分词必须对语料有效。**

在本项目的历史上，这个前提**曾经不成立**。`HeuristicReranker` 的注释如实记录了这次事故（`:71-76`）：

```java
/**
 * 简易分词：非字母数字（含中文）粗切 → <b>中文 bigram</b> + camelCase / snake_case
 * 子词拆分（再统一小写），使代码审查场景下的 {@code getUserById} 与 {@code user_service} /
 * {@code getuserbyid} 能共享子词（get/user/by/id），提升标识符召回；
 * 中文则不再整段成词（否则 Jaccard 重叠对中文恒为 0，启发式重排全程空转）。
 */
```

**"中文则不再整段成词（否则 Jaccard 重叠对中文恒为 0，启发式重排全程空转）"**——这句话描述的是**曾经的实现**：粗切之后，一整段中文（没有空格）就是**一个 token**。

后果是双重的：

| 受害功能 | 症状 |
|---|---|
| **启发式重排** | 所有候选的 `overlap` 都 ≈ 0 → 分数几乎相同 → 排序 ≈ 原顺序（**重排空转**） |
| **MMR** | `max_redundancy` 恒为 0 → 第二项被抹掉 → MMR 退化为纯相关性排序（**MMR 空转**） |

**两个功能一起静默失效，没有任何报错。** 这正是第 22 讲说的"RAG 的失败是静默的"——这次是**两个环节同时静默**。

修法就是现在代码里的做法（`:77-80`）：**分词统一委托给与 PG 检索同一个 `TextTokenizer`**：

```java
// core/rag/HeuristicReranker.java:77-80
public static Set<String> tokenize(String text) {
    // 统一委托 TextTokenizer（中文 bigram + 标识符子词），与 PG 全文检索 / 内存 BM25 同口径。
    return TextTokenizer.tokenize(text);
}
```

**"同口径"三个字是整个修法的关键**——写入侧（PG tsvector）、稀疏检索（`to_tsquery`）、重排（Jaccard）、MMR（Jaccard）**必须用同一套分词**。否则会出现"检索命中了、重排又把它排后面了"这种诡异现象，因为两个环节对"词"的理解不同。

## 三、代码

### 3.1 启发式重排：三个加权项

```java
// core/rag/HeuristicReranker.java:47-69
private double score(MemoryEntry e, Set<String> qTokens) {
    if (qTokens.isEmpty()) {
        return 0.0;
    }
    Set<String> cTokens = tokenize(e.content());
    if (cTokens.isEmpty()) {
        return 0.0;
    }
    // 词重叠比例（Jaccard 风格，∈ [0,1]）
    Set<String> inter = new HashSet<>(qTokens);
    inter.retainAll(cTokens);
    double overlap = (double) inter.size() / Math.max(qTokens.size(), cTokens.size());

    // 元数据加权（∈ {0,1}）
    Map<String, String> meta = e.metadata() == null ? Map.of() : e.metadata();
    double boost = PRIORITY_TYPES.contains(meta.getOrDefault("type", "")) ? 1.0 : 0.0;

    // 长度适配因子：过短（<50）或过长（>2000）轻微降权，∈ (0,1]
    int len = e.content().length();
    double lengthPenalty = (len < 50 || len > 2000) ? 0.5 : 1.0;

    return 0.7 * overlap + 0.2 * boost + 0.1 * lengthPenalty;
}
```

**打分模型（`HeuristicReranker.java:18-22` 的类注释）：**

```
score = 0.7 × tokenOverlapRatio      // 与查询的词重叠比例
      + 0.2 × metadataBoost          // 命中高优先级 type 取 1，否则 0
      + 0.1 × lengthPenalty          // 长度适配因子
```

**逐项看的三个问题：**

**① `overlap` 用的是 `Math.max(qTokens.size(), cTokens.size())` 做分母。**

这是"Jaccard 风格"，**不是真正的 Jaccard**——真 Jaccard 的分母是**并集**（`|A ∪ B|`），这里用的是**较大的那个集合的大小**（`max(|A|,|B|)`）。

两者关系：`|A ∪ B| = |A| + |B| - |A ∩ B|`，而 `max(|A|,|B|) ≤ |A ∪ B|`。

**所以这里算出来的重叠率 ≥ 真 Jaccard**，而且**不对称**（交换 A、B 结果不变，因为用了 max——这点其实比真 Jaccard 更"温和"）。**它有意放宽了相似度判据**（因为审查场景下知识块通常比查询长得多，用并集做分母会让所有重叠率都趋近 0）。

**但注释写的是"Jaccard 风格"，代码里的 `mmrSelect` 用的却是真 Jaccard**（`RagContextBuilder.java:307-316` 有 `union`）：

```java
// core/memory/RagContextBuilder.java:307-316
private static double jaccard(java.util.Set<String> a, java.util.Set<String> b) {
    if (a.isEmpty() || b.isEmpty()) {
        return 0.0;
    }
    java.util.Set<String> inter = new java.util.HashSet<>(a);
    inter.retainAll(b);
    java.util.Set<String> union = new java.util.HashSet<>(a);
    union.addAll(b);
    return union.isEmpty() ? 0.0 : (double) inter.size() / union.size();
}
```

**同一个概念（"两个词集有多像"），项目里有两个不同口径**：重排用 `max` 分母、MMR 用 `union` 分母。**这是"同口径"原则的一个反例**——第 2.4 节强调了分词要同口径，但**分母口径没统一**。

**后果**：同两个块的"相似度"，在重排和 MMR 里算出不同的值。MMR 的 `λ=0.7` 是在 `union` 口径下调的，而重排的 0.7 权重是在 `max` 口径下调的——**两个 0.7 的含义不同**。

**修法**：把分母口径也统一（抽成一个共享的 `Similarity.jaccard()`），并在注释里说明为什么选它。

**② `lengthPenalty` 是阶跃函数，边界处会反向跳跃。**

```java
double lengthPenalty = (len < 50 || len > 2000) ? 0.5 : 1.0;
```

- 49 字符的块 → **0.5**
- 50 字符的块 → **1.0**
- 2000 字符 → **1.0**
- 2001 字符 → **0.5**

**在 49→50 这个边界上，块变长了反而得分更高。** 幅度很小（`0.1 × 0.5 = 0.05` 的差），所以不致命；但**阶跃惩罚在边界附近会制造非单调的排序抖动**——两个内容几乎一样的块，长度差 1 个字符，排序可能互换。

**更好的写法是连续函数**（比如 `1 - |len - target| / target` 并 clamp 到 `[0.5, 1]`），或者至少**把阈值写进注释说明为什么是 50 / 2000**。

**③ 三个权重（0.7 / 0.2 / 0.1）之和为 1，但没有任何依据说明为什么是这个比例。**

这是启发式的本质——**它不追求理论最优，追求"可解释、可调、可测试"**。但**0.7 与 MMR 的 λ=0.7 数值相同、语义无关**，这是巧合，容易让人误以为"这两个 0.7 是同一个东西"。

### 3.2 `PRIORITY_TYPES`：一个硬编码的语义偏好

```java
// core/rag/HeuristicReranker.java:28-30
/** 元数据加权：命中这些 type 的块额外加分。 */
private static final Set<String> PRIORITY_TYPES =
        Set.of("coding_standard", "security_rule", "best_practice");
```

**这三个字符串必须和写入侧的 `meta.put("type", ...)` 对得上。** 内置手册写的是 `coding_standard`（`KnowledgeBaseInitializer.java:62`），**能对上**：

```java
// core/memory/KnowledgeBaseInitializer.java:60-63
Map<String, String> meta = new LinkedHashMap<>();
meta.put("source", "handbook");
meta.put("type", "coding_standard");
int chunkCount = knowledgeStore.saveKnowledge(Teams.GLOBAL, handbook, meta);
```

**但这是一个"字符串约定"级别的耦合**：没有枚举、没有常量共享、没有编译期检查。**如果你新摄取一份文档写了 `security_guideline`，它不会获得 boost——而没有任何提示。**

**建议**：这几个 type 值应该抽成共享常量（或枚举），由写入侧和重排侧共同引用。**字符串字面量作为跨模块契约，是特别容易腐烂的东西。**

### 3.3 一个真实的降级 bug：把 JSON 当查询传进去了

这是本讲发现的**最值得单独讲**的缺陷。先看 `parseResponse` 的签名：

```java
// core/rag/ApiReranker.java:133
private List<MemoryEntry> parseResponse(String json, List<MemoryEntry> candidates, int topN) {
```

**注意：这个方法的参数里没有 `query`。**

再看它的三条降级路径（`:140-141`、`:157-159`、`:162-164`）：

```java
// core/rag/ApiReranker.java:137-165（节选，三条降级路径）
JsonNode results = root.get("results");
if (results == null || !results.isArray()) {
    log.warn("[Rerank] 响应缺少 results 数组，降级启发式重排");
    return fallback.rerank(json, candidates, topN);          // ← 传的是 json！
}
...
if (out.isEmpty()) {
    log.warn("[Rerank] 解析结果为空（index 越界或结构异常），降级启发式重排");
    return fallback.rerank(json, candidates, topN);          // ← 传的是 json！
}
...
} catch (Exception e) {
    log.warn("[Rerank] 响应解析失败（{}），降级启发式重排", e.getMessage());
    return fallback.rerank(json, candidates, topN);          // ← 传的是 json！
}
```

**`Reranker.rerank` 的第一个参数是 `query`**：

```java
// core/rag/Reranker.java:28
List<MemoryEntry> rerank(String query, List<MemoryEntry> candidates, int topN);
```

**所以这三处降级，是把"API 返回的 JSON 响应体"当成了检索查询**，去做词重叠打分。

**后果链条：**

1. `HeuristicReranker` 对 `json` 分词 → 得到的是 `results`、`index`、`relevance_score` 这类**英文字段名**；
2. 知识块是中文规范 → **交集几乎为空** → `overlap ≈ 0`；
3. 于是 `score ≈ 0.2 × boost + 0.1 × lengthPenalty` —— **排序几乎完全由"是不是优先类型"和"长度是否在区间内"决定**；
4. 大量分数相等 → Java 的 `List.sort` 是**稳定排序** → **相等分数的块保持传入顺序**（即初检的相似度顺序）；
5. 最终结果：**"重排"退化成"原样返回"**，而日志里写的却是 `降级启发式重排`。

**为什么这个 bug 特别值得学：**

| 特征 | 说明 |
|---|---|
| **编译器帮不上忙** | 三个参数都是 `String` / `List` / `int`，`json` 和 `query` 类型相同——**类型系统无法发现** |
| **根因是签名** | `parseResponse` 里**根本没有 `query` 可传**。作者不是"传错了"，是"只能传 json" |
| **同类里两种写法** | `rerank` 方法体里三处降级都正确传了 `query`（`:94`、`:111`、`:116`），只有 `parseResponse` 里三处传错——**同一个类、同一个 fallback、两种写法** |
| **静默** | 降级日志是 WARN，看起来"成功降级了"；实际效果是"没重排"，而"没重排"不会报错 |

**修法（两行）：把 `query` 穿进签名。**

```java
// 修法示意（不是仓库现状）
private List<MemoryEntry> parseResponse(String query, String json,
                                       List<MemoryEntry> candidates, int topN) {
    ...
    return fallback.rerank(query, candidates, topN);   // ← 三处都改
}
// 调用点
return parseResponse(query, resp.body(), candidates, topN);
```

**验证方法**：写一个"返回非法 JSON"的 stub HTTP 服务，让 `ApiReranker` 降级，然后**断言排序结果与"直接用 query 调用启发式重排"的结果一致**。**现在的代码会断言失败——这就是这个 bug 的可复现证明。**

### 3.4 MMR 挑选：为什么用下标而不是对象

```java
// core/memory/RagContextBuilder.java:265-305（节选）
private List<MemoryEntry> mmrSelect(List<MemoryEntry> candidates, String query, int topN) {
    java.util.Set<String> qTokens = TextTokenizer.tokenize(query);
    // 候选词集预计算一次：MMR 是 O(topN × 候选) 的贪心，
    // 若每轮外层都重新分词，长内容会被重复解析 topN 次（纯浪费且随块长放大）。
    List<java.util.Set<String>> candTokens = new java.util.ArrayList<>(candidates.size());
    for (MemoryEntry c : candidates) {
        candTokens.add(TextTokenizer.tokenize(c.content()));
    }
    List<MemoryEntry> selected = new java.util.ArrayList<>();
    List<java.util.Set<String>> selectedTokens = new java.util.ArrayList<>();
    // rest 存候选下标而非对象：①可直接复用预计算的词集；②避免按对象 remove（
    // MemoryEntry 是 record，同内容条目 equals 相同，按对象删会误删/删错）。
    List<Integer> rest = new java.util.ArrayList<>();
    for (int i = 0; i < candidates.size(); i++) {
        rest.add(i);
    }

    while (selected.size() < topN && !rest.isEmpty()) {
        int bestPos = 0;
        int bestIdx = rest.get(0);
        double bestScore = Double.NEGATIVE_INFINITY;
        for (int p = 0; p < rest.size(); p++) {
            java.util.Set<String> cTokens = candTokens.get(rest.get(p));
            double rel = jaccard(qTokens, cTokens);
            double redundancy = 0.0;
            for (java.util.Set<String> s : selectedTokens) {
                redundancy = Math.max(redundancy, jaccard(s, cTokens));
            }
            double mmr = MMR_LAMBDA * rel - (1 - MMR_LAMBDA) * redundancy;
            if (mmr > bestScore) {
                bestScore = mmr;
                bestIdx = rest.get(p);
                bestPos = p;
            }
        }
        selected.add(candidates.get(bestIdx));
        selectedTokens.add(candTokens.get(bestIdx));
        rest.remove(bestPos);      // ← 按下标删，位置安全
    }
    return selected;
}
```

**注意 `rest` 用下标而不是对象**，注释给了两个理由：

**① 复用预计算词集**——`candTokens` 是按原候选列表下标建的，用下标才能直接取。

**② 避免 `List.remove(Object)` 删错**——这是**很值得学的一点**：

`MemoryEntry` 是 Java `record`。**record 的 `equals` 是"逐字段相等"**。如果候选中出现两个内容完全相同的块（**重叠切块会产出近似块，加上去重前的候选池，这是会发生的**），那么 `list.remove(someEntry)` 会删除**第一个 equals 为 true 的元素**——**可能不是你打算删的那个**。

**用下标删，就绕开了整个 `equals` 语义问题。** 这个思考在项目里是第 23 讲那个"重叠坐标系"的**正确示范版**——同样是"身份靠下标传递"，一个踩了坑（漂移），一个避了坑（`rest` 用下标）。

### 3.5 一个顺序问题：去重放在 MMR 之后

看 `RagContextBuilder.buildContext` 里的实际顺序（`:165-178`）：

```java
// core/memory/RagContextBuilder.java:165-178
// 4. Cross-Encoder 重排：开 MMR 时给更大的候选池，否则 MMR 没有挑选余地
int rerankPool = mmrEnabled
        ? Math.min(passed.size(), Math.max(injectTopN * 3, injectTopN))
        : injectTopN;
List<MemoryEntry> reranked = reranker.rerank(query, passed, rerankPool);
// 5. MMR 多样性挑选（相关性 − 冗余度）：避免 Top-N 被同章节高度相似的碎片占满
List<MemoryEntry> picked = (mmrEnabled && reranked.size() > injectTopN)
        ? mmrSelect(reranked, query, injectTopN) : reranked;
// 6. 注入前去重：按 content hash 去除 handbook 重叠切块产生的重复块（避免同一段注入多次）
List<MemoryEntry> deduped = dedupeByContent(picked);
if (deduped.size() < picked.size()) {
    log.info("[RAG] 去重：注入前剔除 {} 个重复块（重叠切块导致），{} → {}",
            picked.size() - deduped.size(), picked.size(), deduped.size());
}
```

**顺序是：重排 → MMR → 去重。**

**问题在于：MMR 已经在"避免冗余"了，去重却排在它后面。**

MMR 从 15 条里精挑 5 条；如果它挑出的 5 条里有 2 条内容几乎一样（MMR 是**贪心 + 近似**，不保证一定不重复；而且 `λ=0.7` 对冗余的惩罚只有 0.3，相关性足够高时仍可能被选中），去重会把它们**剔掉一条**——**最终注入 4 条，而没有人去补第 5 条。**

**`inject-top-n=5` 的配置项，实际注入条数可能少于 5，且不告警。**

**更合理的顺序是"先去重 → 再 MMR"：**

```
passed → 去重（剔除内容完全相同的） → 重排 → MMR → 注入
```

理由：

1. **去重是"确定性"的**（内容 hash 完全相同才删），**不涉及打分和阈值**，越早做越干净；
2. 去重之后 MMR 的挑选池更"真实"——**它不会把"同一段内容的副本"当成一个独立候选来占位**；
3. **保证注入数量达标**——MMR 挑的每条都是唯一的，最终就是 `inject-top-n` 条。

**注意日志是好的**（`:175-178` 会打印"剔除 N 个重复块"）——**说明作者观察到了重复现象**，但选择的是"加日志 + 事后去重"，而不是"调整顺序 + 事前净化"。**这是一个典型的"治症状" vs "治病因"的分歧点**，很值得在评审里讨论。

### 3.6 `rerankPool` 里的一个冗余表达式

```java
int rerankPool = mmrEnabled
        ? Math.min(passed.size(), Math.max(injectTopN * 3, injectTopN))
        : injectTopN;
```

**`Math.max(injectTopN * 3, injectTopN)` 在 `injectTopN >= 0` 时恒等于 `injectTopN * 3`**——因为 `3x >= x` 当 `x >= 0`。

所以整个表达式等价于：

```java
int rerankPool = mmrEnabled ? Math.min(passed.size(), injectTopN * 3) : injectTopN;
```

（`inject-top-n=5` 时 → `rerankPool = 15`。）

**`Math.max` 那层在保护什么？** 只有 `injectTopN < 0` 时它才会产生不同结果（`max(3x, x) = x` 当 `x < 0`）——那时 `rerankPool` 变成负数，`HeuristicReranker.rerank` 里 `subList(0, 负数)` 会抛 `IllegalArgumentException`。

**所以这层保护既不解决负值问题（只是换了个更晚的报错点），又增加了阅读成本。** 要么删掉它，要么在配置绑定时就校验 `inject-top-n > 0`（**后者的做法更正确**——把校验前移到配置入口）。

## 四、避坑清单

- [ ] **"召回"和"注入"是两个独立的质量维度。** 召回看 recall（别漏），注入看 precision + 信息增益（别有噪、别重复）。
- [ ] **重排是质量闸门，不是可用性依赖。** 它必须能失败降级，且**降级不能让链路停**。
- [ ] **降级路径的每一个参数都要核对。** `ApiReranker.parseResponse` 把 `json` 当 `query` 传给了 fallback——**同一个类里其它降级点传的是 `query`，只有它传错**。降级路径的正确性必须用测试锁定。
- [ ] **给降级路径写测试的方法**：构造一个必然失败的输入（非法 JSON / 非 200 / 超时），断言"降级后的结果 == 直接用正确 query 调用 fallback 的结果"。**没有这个断言，降级路径就是未测代码。**
- [ ] **分词口径全链路统一**：写入（tsvector）、稀疏检索（`to_tsquery`）、重排（Jaccard）、MMR（Jaccard）必须用同一个 `TextTokenizer`。**任何一处不对齐，就会产生"检索命中了、重排又排后面"的诡异现象。**
- [ ] **相似度的"分母口径"也要统一。** 重排用 `max(|A|,|B|)`、MMR 用 `|A ∪ B|`——**同名的"相似度"算出不同值**，导致两个 `0.7` 参数含义不同。
- [ ] **`record` 元素做 `List.remove(Object)` 会删错。** record 的 `equals` 是逐字段相等，内容相同的两个块会互相误删。**用下标（`List<Integer>`）或 `Iterator.remove`，别用 `remove(Object)`。**
- [ ] **长度惩罚用连续函数，不用阶跃。** 阈值型惩罚在边界处会反向跳跃（49 字符得 0.5、50 字符得 1.0）。
- [ ] **跨模块的字符串契约要抽常量。** `PRIORITY_TYPES` 里的 `"coding_standard"` 与写入侧的 `meta.put("type", "coding_standard")` 靠字面量对齐——写错一个字符，boost 静默消失。
- [ ] **"事后去重"和"事前净化"要选对。** 去重排在 MMR 之后，会导致注入条数少于 `inject-top-n` 且不补位；**先去重再 MMR** 才能保证数量达标。
- [ ] **配置项的合法性在入口校验，不要在深处用 `Math.max` 兜。** 负的 `inject-top-n` 应该在配置绑定时就被拒绝。
- [ ] **引用外部经验数据（如"提升 20~35%"）必须标明来源是"业界经验"还是"本项目实测"。** 混在一起会让读者误以为是你测的。

## 本讲小结

1. **双塔（召回）与 cross-encoder（精排）的分工是结构决定的**：前者能预计算所以快、但查询与文档无交互；后者有交互所以准、但无法预计算。**两阶段是成本与精度的折中，不是"多此一举"。**
2. **重排是质量闸门，必须能失败降级。** 本项目有 4 条降级路径——**其中 3 条把 JSON 响应体当成了查询**（根因是 `parseResponse` 的签名里没有 `query`）。这个 bug 类型系统发现不了，**只能用测试锁定**。
3. **重排优化"相关性"，MMR 优化"信息增益"。** `λ=0.7` 的含义是"相关性权重 0.7、冗余惩罚权重 0.3"。
4. **MMR 与启发式重排都依赖分词**：历史上分词对中文"整段成词"，导致 `Jaccard` 恒为 0 → **两个功能同时空转**。修法是全链路统一 `TextTokenizer`——但**分母口径仍未统一**（`max` vs `union`）。
5. **`record` + `List.remove(Object)` 会删错元素。** 用下标删是正确做法——**这也是"身份靠下标传递"这个模式唯一一次被用对了。**
6. **去重排在 MMR 之后会导致注入条数少于配置值且不补位**；"先去重再 MMR"才会数量达标。

模块四到这里就完整了：**切块（第 23 讲）→ 向量化（第 24 讲）→ 混合检索（第 25、26 讲）→ 语义铁律（第 27 讲）→ 重排与多样性（第 28 讲）→ 评测（第 29 讲）**。

下一讲是模块四的收口：**评测闭环**——怎么证明"你改的这一版比上一版更好"，以及为什么本项目的评估指标在**打开开关的情况下恒为 `NaN`**。
