## 一、痛点

灰度上到第 40 个团队的那个季度，检索开始偶发返回空。

先是一次凌晨的索引迁移。我把 `ivfflat` 换成 `hnsw`，一条 `CREATE INDEX` 直接跑在千万行的 `memory_store` 上——**没加 `CONCURRENTLY`，整张表在重建期间写不进去**。写请求全部排队，P99 从几十毫秒涨到 8 秒多，告警响了两轮。事后我看 pgvector 的 README 才知道，官方在 "Production" 那一节把这件事写成了第一条建议。

然后是"搜不到"。某个团队来问：**"为什么这条规范搜不到了？"** 我去查，向量还在索引里——那份文档两周前被删了，**索引没重建**。删除在向量库里不是"删掉一行"这么简单，这是本讲 2.4 要讲清的事。

再然后是"什么都不返回"。某次 embedding 服务抖动十分钟，**整条 RAG 链路直接 abstain**——而我们的稀疏路（BM25）本来可以兜住这十分钟。**链路上有一半能力，却没有任何降级路径。**

最后一个最隐蔽：**有些团队的查询稳定返回 0 条候选。** 不是没有知识，也不是阈值太高——是 `WHERE team_id = ?` 这个条件**被放在了索引扫描之后**，它把候选窗按选择性**线性打折**了。

**这四个故障没有一个是"算法错了"。** 它们全部是架构问题：部署形态、过滤顺序、索引生命周期、降级路径。**本讲要回答的就是这四件事怎么从零搭起来。**

## 二、原理

### 2.1 单表的三级演进：分区、分片、副本

本书的主线系统是**物理共享一张 `memory_store` 表**——`KnowledgeStore` 的注释把这件事写得很直白：

`KnowledgeStore.java:20-24`

```java
 *   <li>生产实现（{@code PgKnowledgeStore}）与记忆实现（{@code PgVectorMemoryStore}）
```

两个实现、两套接口，**底下是同一张表**，靠 `agent_type` 和 `team_id` 做逻辑隔离。这在第 26 讲的规模下没问题。**但 pgvector 官方明确承认了它的代价。**

`pgvector/README.md:470` / `:472`

> For applications with multiple tenants, sharing an approximate index between tenants means vectors from one tenant can affect recall (and speed) for other tenants.
>
> For tenant isolation, use [list partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) or separate tables.

**"vectors from one tenant can affect recall (and speed) for other tenants"**——这句话是官方给的，不是我的推演。共享一张 HNSW 索引意味着**别人的向量会占用你的图节点**：租户越多，每个租户的候选越少，而图本身的搜索路径被无关向量带偏。

官方给的两条路是**分区**（list partitioning）和**分表**（separate tables）。把水平扩展的完整路径也放在同一页：

`pgvector/README.md:760`

> Scale horizontally with [replicas](https://www.postgresql.org/docs/current/hot-standby.html), or use [Citus](https://github.com/citusdata/citus), [PgDog](https://github.com/pgdogdev/pgdog), or another approach for sharding ([example](https://github.com/pgvector/pgvector-python/blob/master/examples/citus/example.py)).

**这三条路解决的是三个不同的问题，不能互相替代：**

<img class="mermaid-svg" src="/zh/book-assets/diag-0151.svg" alt="这三条路解决的是三个不同的问题，不能互相替代：" />

> **图 34-1**　单表到可水平扩展的三级演进：分区解决"共享索引里的租户互相干扰"，分片解决"单机装不下"，副本解决"读 QPS 上不去"——每一步都在换一个新的代价。

**判据在三者的问题域上，不在性能上：**

| 演进 | 解决什么 | 解决不了什么 |
|---|---|---|
| **分区** | 索引隔离 + 单分区清理（`DROP PARTITION` 比 `DELETE` 快） | 单机容量上限 |
| **分片** | 单机装不下（Citus / PgDog） | 跨分片事务与 join 会消失 |
| **副本** | 读 QPS（只读副本分担检索） | 写入仍是单点 |

**先问"我缺的是哪个"，再谈选哪个。** 本项目单表跑得好，是因为第 40 个团队之后**过滤的选择性**开始生效（2.2）——那是索引层的问题，分区就能解；而分片要等到单机装不下才需要。

**最新的 pgvector 也把这条写在了 "Scaling" 一类的小节里**（`pgvector/README.md:760`）——`ddl-partitioning` 与 `hot-standby` 都是 PostgreSQL 官方文档，读者可以直接对着看。

### 2.2 ACL 前置：post-filter 的线性打折与 pre-filter 的代价

**过滤条件写在 `WHERE` 里，它在索引扫描之后才生效。** 这句看起来像常识的话，pgvector 官方给了量化后果。

`pgvector/README.md:450`

> With approximate indexes, filtering is applied *after* the index is scanned. If a condition matches 10% of rows, with HNSW and the default `hnsw.ef_search` of 40, only 4 rows will match on average. For more rows, enable [iterative index scans](#iterative-index-scans), which will automatically scan more of the index when needed.

**10% 的选择性 × 40 的动态候选表 = 4 条。** 这不是"少一点"——**是少一个数量级**。而候选项被过滤掉之后，`LIMIT 100` 是补不回来的：**`LIMIT` 限制的是返回行数，不是索引探了多少节点。**

**为什么这是"业界议题"而不是本书独有的坑：** 在 HNSW 这种图结构上做可过滤检索，本身就有一个公开的工程权衡——**过滤器选择性很低时，图上的搜索会被大量不符合条件的节点"堵住"**（Qdrant 的 *Filtrable HNSW* 一文专门讨论了这个权衡，https://qdrant.tech/articles/filtrable-hnsw/；Weaviate 也有一节讲同一件事，https://weaviate.io/developers/weaviate/concepts/filtering）。**两家独立实现都在讲"过滤前置"，这是行业共识，不是某家的实现怪癖。**

<img class="mermaid-svg" src="/zh/book-assets/diag-0152.svg" alt="为什么这是&quot;业界议题&quot;而不是本书独有的坑： 在 HNSW 这种图结构上做可过滤检索，本身就有一个公开的工程权衡——过滤器选择性很低时，图上的搜索会被大量不符合条件的节点&quot;堵住&quot;（Qdrant 的 Filtrable HNSW 一文专门讨论了这个权衡，https://qdrant.tech/articles/filtrable-hnsw/；Weaviate 也有一节讲同一件事，https://weaviate.io/developers/weaviate/concepts/filtering）。两家独立实现都在讲&quot;过滤前置&quot;，这是行业共识，不是某家的实现怪癖。" />

> **图 34-2**　同一个 `WHERE team_id = ?` 的两个位置：放在索引扫描之后，候选按选择性线性打折（`40 × 10% = 4`）；前置成分区 / 分表，扫描空间本身就是这个租户的，候选不打折——代价是分区与索引数量上涨。

**工业界的接口层怎么处理这件事？** spring-ai 的检索器把过滤器做成了**按请求懒求值的 `Supplier`**：

`spring-ai/spring-ai-rag/src/main/java/org/springframework/ai/rag/retrieval/search/VectorStoreDocumentRetriever.java:67-70`

```java
	// Supplier to allow for lazy evaluation of the filter expression,
	// which may depend on the execution content. For example, you may want to
	// filter dynamically based on the current user's identity or tenant ID.
	private final Supplier<Filter.Expression> filterExpression;
```

**注释里点名的动机就是 tenant ID。** 而它是**每请求重算**的（同文件 `:110-119`）——这一点比"过滤放在哪一层"更基础：**如果过滤器是构造期常量，你在多租户下从第一天就是错的。**

**把这条判据钉死：多租户过滤器必须是"每请求求值"的，不能是"启动期绑定"的。** 至于它是拼进 SQL 还是下推成分区裁剪，是第二层问题。

**本项目的现状在这两层的哪一层？** 它把租户条件拼进了 SQL 字符串（`teamFilter`，见第 29 讲引用的两条 SQL，`PgKnowledgeStore.java:202-221`），入参在链路入口被 `Teams.sanitize(teamId)` 处理过一次（`RagContextBuilder.java:181-235`，第 26 讲已逐字引用）——**"每请求求值"这一层是对的；"过滤前置"这一层还没做。** 所以它属于图 34-2 里的**路线 A**，而路线 A 在 A 基座上够用、在 B 基座上不够用——这个分叉在 2.6 的三元表里给出。

### 2.3 建索引的四个不可逆点

**索引不是"加个配置项"，它是一次不可逆的资源操作。** 把它拆成四个点看，每个点都对应一条官方文档。

**① 参数不可事后改，只能 `DROP` 重建。**

`pgvector/src/hnsw.h:54` / `:57`

```c
#define HNSW_DEFAULT_M	16
#define HNSW_DEFAULT_EF_CONSTRUCTION	64
```

这不是"越大越好"的连续旋钮——**它是有硬上限的三档参数**，同文件给了上界：

`pgvector/src/hnsw.h:55` / `:56` / `:59` / `:62`

```c
#define HNSW_MIN_M	2
#define HNSW_MAX_M		100
#define HNSW_MAX_EF_CONSTRUCTION		1000
#define HNSW_MAX_EF_SEARCH		1000
```

**`m` 最大 100、`ef_construction` 最大 1000。** 而这两个值**写进索引结构、建完之后改不了**——想改就重建。IVFFlat 更极端，它的两个默认值分别是 `100` 和 `1`：

`pgvector/src/ivfflat.h:55` / `:58`

```c
#define IVFFLAT_DEFAULT_LISTS	100
#define IVFFLAT_DEFAULT_PROBES	1
```

**`probes` 默认是 1。** 意思是：默认建出来的 IVFFlat 索引，查询时**只探一个聚类中心**——召回率低到你会以为向量能力坏了。官方给的经验法则把它讲清了：

`pgvector/README.md:340-342`

> 1. Create the index *after* the table has some data
> 2. Choose an appropriate number of lists - a good place to start is `rows / 1000` for up to 1M rows and `sqrt(rows)` for over 1M rows
> 3. When querying, specify an appropriate number of [probes](#query-options) (higher is better for recall, lower is better for speed) - a good place to start is `sqrt(lists)`

**注意第 1 条**："先有数据再建索引"——这句话后面 2.4 会用到。

**还有一堵硬墙在维度上：**

`pgvector/src/hnsw.h:33`

```c
#define HNSW_MAX_DIM 2000
```

README 把四种类型的分档列在一起（`pgvector/README.md:252-255`）：`vector` 2000 维、`halfvec` 4000 维、`bit` 64000 维、`sparsevec` 1000 个非零元素。**本书用的 1024 维安全；换成 3072 维的模型（OpenAI `text-embedding-3-large`）就建不出 `vector` 类型的 HNSW 索引，必须走 `halfvec`。** 这和第 28 讲的"维度是三方契约"是同一件事的另一个落点：**维度不只是契约，它还是"能不能建出索引"的开关。**

**② 写锁不可跳过：唯一不阻塞写入的建法是 `CONCURRENTLY`。**

`pgvector/README.md:704` / `:707`

> In production environments, create indexes concurrently to avoid blocking writes.
>
> ```sql
> CREATE INDEX CONCURRENTLY ...
> ```

**这就是痛点里那次事故的答案。** 普通的 `CREATE INDEX` 会持有写锁，全程阻塞写入；`CONCURRENTLY` 是生产环境唯一可用的姿势——**代价是它更慢、且失败会留下一个 invalid 索引需要手工清理**。

**③ 内存与并行度不可回收：不够会发 NOTICE，并行默认只有 2。**

`pgvector/README.md:291`

> Indexes build significantly faster when the graph fits into `maintenance_work_mem`

而"不够"这件事**是会被主动告诉你的**（`pgvector/README.md:300-302`）：

> ```text
> NOTICE:  hnsw graph no longer fits into maintenance_work_mem after 100000 tuples
> DETAIL:  Building will take significantly more time.
> HINT:  Increase maintenance_work_mem to speed up builds.
> ```

并行度也在同一节（`pgvector/README.md:309` / `:312` / `:315`）：

> You can also speed up index creation by increasing the number of parallel workers (2 by default)
>
> ```sql
> SET max_parallel_maintenance_workers = 7; -- plus leader
> ```
>
> For a large number of workers, you may need to increase `max_parallel_workers` (8 by default)

**并行 worker 默认 2，`max_parallel_workers` 默认 8。** 这两个数是"建索引慢"最常见的两个原因，而它们都在 PostgreSQL 侧、不在 pgvector 侧——**所以调它们的时候你其实在调数据库，不是在调向量库。**

**④ 进度只能查，不能猜。**

`pgvector/README.md:326` 给了建索引期间看进度的入口，配套的 PostgreSQL 官方文档是 `pg_stat_progress_create_index`（https://www.postgresql.org/docs/current/progress-reporting.html）。

<img class="mermaid-svg" src="/zh/book-assets/diag-0153.svg" alt="`pgvector/README.md:326` 给了建索引期间看进度的入口，配套的 PostgreSQL 官方文档是 `pg_stat_progress_create_index`（https://www.postgresql.org/docs/current/progress-reporting.html）。" />

> **图 34-3**　索引运维的四个不可逆点：参数（建了不能改）、写锁（不加 `CONCURRENTLY` 就阻塞）、内存（不够会发 NOTICE）、进度（只能查 `pg_stat_progress_create_index`）——四条合起来说明"建索引"是一次性且不可逆的操作。

**最后一件要看清的事：主流框架只负责把索引建出来，不负责让它好用。**

`spring-ai/vector-stores/spring-ai-pgvector-store/src/main/java/org/springframework/ai/vectorstore/pgvector/PgVectorStore.java:512-525`


**这条 `CREATE INDEX` 不带任何 `WITH (...)` 子句**——不设 `m`、不设 `ef_construction`、不设 `lists`。而且 spring-ai 的 `spring-ai-pgvector-store` 模块里**没有 `ef_search`、没有 `iterative_scan`、没有任何 `SET LOCAL`**（已用 `git grep` 全量确认）。

**结论就是一句话：`ef_search`、`iterative_scan`、`lists` / `probes` 这些真正决定 P99 与召回的参数，框架一个都不设——全都要你自己设。** 这解释了为什么"我用了 spring-ai 的向量库"和"我的检索是好用的"是两件事。

**回看本项目：同一个类里，两种迁移两种态度。** `ivfflat → hnsw` 的索引重建**没有行数上限**（`PgVectorMemoryStore.java:178-211` 的注释自己写着"数据量大时仍会执行"），而同一个类里的 `search_vector` 分词重建**有** `MAX_MIGRATE_ROWS = 100_000` 的上限（`PgVectorMemoryStore.java:240-297`，第 30 讲引过）。

**同一个文件、同一个作者、两套标准——说明"要不要为大表做保护"这个问题在本项目里没有被统一回答过。** 这是评审时该问出口的问题。

### 2.4 蓝绿索引与删除语义：为什么"删"比"写"难

**写入有工业标准答案，更新也有。** langchain4j 的 pgvector 存储用的是 upsert：

`langchain4j/langchain4j-pgvector/src/main/java/dev/langchain4j/store/embedding/pgvector/PgVectorEmbeddingStore.java:640`

```java
                            + "ON CONFLICT (embedding_id) DO UPDATE SET "
```

**"按主键 upsert，而不是先删后插"** ——这是增量索引写入语义的工业做法，它天然幂等，重跑不会产生重复。

**但"删除"没有这个答案。**

原因在 2.3 第 1 条那句话里：**"Create the index *after* the table has some data"**（`pgvector/README.md:340-342`）——**索引是建在"某一时刻的数据快照"上的。** 删掉一个向量，索引**不会**自动把自己重组成"一张没有它的图"。pgvector 只能在查询时跳过被删除的点，**而这些点会继续在索引里占位**。

于是"删除"的代价是这样的：

| 动作 | 索引侧发生什么 | 代价 |
|---|---|---|
| **插入 / 更新** | `ON CONFLICT DO UPDATE` 走 upsert（`PgVectorEmbeddingStore.java:640`），索引增量维护 | 低，可在线做 |
| **删除** | 标记为不可见，**索引结构不变** | **低，但索引里的"空洞"会累积** |
| **让空洞消失** | 只能**重建索引**——而重建就是 2.3 的四件事 | 高，`CONCURRENTLY` 也要占 CPU 与 IO |

**所以删除的问题不是"删不掉"，是"删了之后索引会慢慢变差"。** 标记删除的点越多，图上的搜索路径就越容易被无效节点挡路——**召回率随时间下降，而没有任何一条日志会告诉你。**

**这就是痛点里"搜不到那条规范"的第二半**：文档删了，向量被标记了，但**索引没重建**，所以"看起来还在"。更麻烦的是相反方向的问题——**内容更新了但索引没跟上**，用户搜到的是旧版本文档，"内容随时变化的 B 基座"上这会变成一类持续存在的脏召回。

**蓝绿索引的三阶段**（图 34-4）：**打补丁 → 建新索引 → 切换**。

<img class="mermaid-svg" src="/zh/book-assets/diag-0154.svg" alt="蓝绿索引的三阶段（图 34-4）：打补丁 → 建新索引 → 切换。" />

> **图 34-4**　索引生命周期的三阶段：日常靠 `ON CONFLICT DO UPDATE` 打补丁；当参数要改、或者删除累积太多时，用 `CREATE INDEX CONCURRENTLY` 建一张"蓝索引"，再原子切换、`DROP` 旧索引——而"删除"这件事只能靠这条重建路径变干净。

**三阶段的关键是"切换要原子、旧索引要延迟删"**：新索引建好之前，老索引必须继续服务（这就是"蓝绿"的含义）；切换之后别立刻 `DROP`，留一个回滚窗口。**用空间换"改索引不中断"——这是唯一能在线改索引参数的办法。**

### 2.5 降级链：embedding 挂了走 BM25，以及 iterative scan 的真相

**先看一个"降级"的正面范式。** spring-ai 的多查询扩展在校验失败时**打 WARN 降级，不抛异常**：

`spring-ai/spring-ai-rag/src/main/java/org/springframework/ai/rag/preretrieval/query/expansion/MultiQueryExpander.java:118-131`

```java
		if (CollectionUtils.isEmpty(queryVariants) || this.numberOfQueries != queryVariants.size()) {
			...
				logger.warn("Query expansion result does not contain the requested " + this.numberOfQueries
```

**"降级不是异常路径，是设计出来的一条正常路径"**（第 32 讲已经把这个范式引过一次）。放到本讲，检索层的降级链应该是三级：

| 级 | 条件 | 走什么 | 必须打的标记 |
|---|---|---|---|
| **① 全功能** | embedding 可用 | 稠密 + 稀疏 + RRF | `retrieval.mode=hybrid` |
| **② 降级** | embedding 超时 / 报错 | **只走稀疏路（BM25 / `ts_rank`）** | `retrieval.mode=sparse_only` |
| **③ 兜底** | 两路都空 | abstain（明确回答"没找到"） | `retrieval.mode=none` |

**关键判据：第 ② 级是否存在于你的链路里，决定了 embedding 抖动时你是"效果差一点"还是"全线不可用"。** 本项目当前没有这一级——痛点里那次十分钟抖动，本可以被稀疏路兜住。

**然后拆掉一个流行的错误答案："打开 iterative scan 就好了。"**

iterative index scan 是 pgvector 0.8.0 引入的：

`pgvector/CHANGELOG.md:37` / `:39`

```
## 0.8.0 (2024-10-30)

- Added support for iterative index scans
```

机制说明在 `pgvector/README.md:480`：

> With approximate indexes, queries with filtering can return less results since filtering is applied *after* the index is scanned. Starting with 0.8.0, you can enable iterative index scans, which will automatically scan more of the index until enough results are found (or it reaches `hnsw.max_scan_tuples` or `ivfflat.max_probes`).

**它听起来像是"自动解决 post-filter 打折"。但看两处细节就知道它是个受控的补偿，不是无限的补偿。**

**第一处：跨索引类型能力不对等。** HNSW 的迭代扫描有三档：

`pgvector/src/hnsw.h:163-165`

```c
	HNSW_ITERATIVE_SCAN_OFF,
	HNSW_ITERATIVE_SCAN_RELAXED,
	HNSW_ITERATIVE_SCAN_STRICT
```

而 IVFFlat 只有两档：

`pgvector/src/ivfflat.h:116-117`

```c
	IVFFLAT_ITERATIVE_SCAN_OFF,
	IVFFLAT_ITERATIVE_SCAN_RELAXED
```

**`ivfflat` 没有 `strict`。** 用法上（`pgvector/README.md:487` / `:493` / `:495`）：

```sql
SET hnsw.iterative_scan = strict_order;
```
```sql
SET hnsw.iterative_scan = relaxed_order;
# or
SET ivfflat.iterative_scan = relaxed_order;
```

**如果哪天你为了兼容把索引从 HNSW 迁到 IVFFlat，`strict_order` 会静默消失。** 这是"迁移会悄悄丢掉一个能力"的典型例子——不是报错，是行为变化。

**第二处：它是双重熔断，而且内存预算是连接级的。**

`pgvector/src/hnsw.c:102-105` / `:107-109`

```c
	DefineCustomIntVariable("hnsw.max_scan_tuples", "Sets the max number of tuples to visit for iterative scans",
							NULL, &hnsw_max_scan_tuples,
							20000, 1, INT_MAX, PGC_USERSET, 0, NULL, NULL, NULL);

	/* Same range as hash_mem_multiplier */
	DefineCustomRealVariable("hnsw.scan_mem_multiplier", "Sets the multiple of work_mem to use for iterative scans",
							 NULL, &hnsw_scan_mem_multiplier,
							 1, 1, 1000, PGC_USERSET, 0, NULL, NULL, NULL);
```

真正的停止判据在扫描器里（`pgvector/src/hnswscan.c:259`）：

```c
			if (so->tuples >= hnsw_max_scan_tuples || MemoryContextMemAllocated(so->tmpCtx, false) > so->maxMemory)
```

而这个 `maxMemory` 是算出来的（`pgvector/src/hnswscan.c:155`）：

```c
	maxMemory = (double) work_mem * hnsw_scan_mem_multiplier * 1024.0 + 256;
```

**两个熔断条件同时成立才继续扫：元组数到 20,000（默认），或者内存超预算。而内存预算 = `1 × work_mem`。**

**这就是"打开 iterative scan 就好了"错在哪：**

- 它是**双重熔断**——元组数和内存，两个之中任何一个先到就停；
- 内存预算挂在 **`work_mem` 上，而 `work_mem` 是连接级参数**——意味着**同一个查询在不同连接上可能扫出不同的结果**，P99 取决于连接池的配置。这是"结果不可复现"的又一种来源。

**判据：iterative scan 是"允许自动多扫一批"，不是"把 post-filter 变成 pre-filter"。** 它能把 `40 × 10% = 4` 抬上去，但抬多少取决于 `max_scan_tuples` 与 `work_mem`——**而这两个数你不显式设，就是 20,000 和连接默认值。** 想真正解决低选择性过滤，还是得回到 2.1 / 2.2 的分区与前置。

| 维度 | A：代码审查助手 | B：千万 DAU 客服助手 | 由此分叉的设计决策 |
|---|---|---|---|
| 租户数与过滤选择性 | 团队级，`team_id` 过滤命中率接近 100%，post-filter 几乎不打折 | 商家级，单商家文档占全表比例极低（推演见下） | A 可以继续用 `WHERE` 拼接；B 必须分区 / 分表把过滤前置 |

| 索引重建频率 | 低频：规范文档几乎不改，删除少 | 高频：UGC 商品 / 政策随时增删，标记删除累积快 | A 的重建可以放到发版窗口做；B 必须常备蓝绿索引 + 在线重建 |
| 索引重建方式 | 启动时一次性（`PgVectorMemoryStore.java:178-211`），无上限也可接受 | 千万行表上必须 `CONCURRENTLY`（`pgvector/README.md:704`）并显式抬并行度 | "启动时重建"这个做法在 B 上根本不可用 |
| embedding 抖动 | 中低 QPS，抖动影响面小 | 高 QPS，抖动会成片失败 | A 可以只重试；B 必须有第 ② 级降级（只走稀疏路） |
| 内容变更时效 | `max-age-days=0` 已要求"当天有效"（`application.yml:226`） | 同一约束，但写入量级完全不同 | B 的 freshness 过滤必须走索引列，不能是全表扫描 |

> **推演**：`(1000 万 × 2 ÷ 86,400) × 3 ≈ 694` 次/秒（假设：千万 DAU 人均每日 2 次知识问答、峰值取均值 3 倍；基座值见 `application.yml:221` 的 `retrieve-k=50`）

> **推演**：`40 × 0.1% ≈ 0.04` 条（假设：B 基座单个商家的知识块占全表约 0.1%，即租户过滤的选择性为 0.1%，基座值 `ef_search=40` 见 `pgvector/src/hnsw.h:60`；基座 B 无仓库可复算，该选择性亦为推演值）

> **推演**：`50 万 × 10% = 5 万` 篇/天（假设：B 基座活跃商家 50 万、每家每天删改约 10% 的 UGC 文档；基座值见 `application.yml:226` 的 freshness `max-age-days=0`——该配置要求知识"当天有效"，会加速标记删除的累积）

> **推演**：`100 ÷ 50 万 = 0.0002`（即单个 list 分区的索引体量约为未分区单表的万分之二，假设 B 基座按 50 万活跃商家均分为 50 万个分区；基座值见 `application.yml:197` 的 `dim=1024`）

**四行推演连起来是一个判断：B 基座上，"共享一张表 + post-filter + 启动时重建索引"这三件事同时不成立，而且失效的方式是静默的**——选择性低到 `0.1%` 时，`ef_search × 选择性 ≈ 0.04`，你会看到"几乎检索不到任何东西"，而日志里没有任何一行会告诉你原因。

|---|---|

| post-filter 按选择性线性打折（`pgvector/README.md:450`） | 我 `WHERE` 里那个过滤条件的选择性是多少？算过 `ef_search × 选择性` 吗？ |
| 过滤器必须是每请求求值的 `Supplier`（`VectorStoreDocumentRetriever.java:67-70`） | 我的多租户过滤器是启动期常量还是每请求计算？ |
| spring-ai 建索引不带任何 `WITH (...)`，全模块不设 `ef_search`（`PgVectorStore.java:512-525`） | 我的 `ef_search` / `lists` / `probes` 是谁设的？有人在设吗？ |
| IVFFlat `probes` 默认 1（`pgvector/src/ivfflat.h:58`） | 我如果用了 IVFFlat，`lists` 和 `probes` 算过吗（`README.md:340-342`）？ |
| `CREATE INDEX CONCURRENTLY`（`pgvector/README.md:704`） | 我的建索引脚本在生产环境会阻塞写吗？ |
| upsert 是写语义、重建是删语义（`PgVectorEmbeddingStore.java:640`） | 我的删除是标记删除还是真删？索引里的"空洞"多久清一次？ |
| iterative scan 是双重熔断 + 连接级 `work_mem`（`pgvector/src/hnswscan.c:155` / `:259`） | 我是不是以为"开了 iterative scan 就解决了过滤"？ |
| 降级链三级（同族范式见 `MultiQueryExpander.java:118-131`） | embedding 挂掉时，我的链路是"效果差一点"还是"全线不可用"？ |

**落地步骤（五个动作）：**

1. **先算过滤选择性**：`该租户的候选条数 ÷ 全表候选条数`，再用 `ef_search × 选择性` 估"过滤后平均剩几条"。低于你的 `retrieve-k`，就说明这个窗口是假的。
2. **给建索引脚本加 `CONCURRENTLY` 与显式并行度**：把 `SET max_parallel_maintenance_workers` / `maintenance_work_mem` 写进脚本，**并把 `NOTICE: hnsw graph no longer fits into maintenance_work_mem` 接成告警**（`pgvector/README.md:300-302`）。
3. **补上降级链的第 ② 级**：让 embedding 超时 / 报错时**只走稀疏路**，并给每一级打独立标记 `retrieval.mode`——**降级率必须是指标，不是日志行**。
4. **为索引变更准备蓝绿路径**：把"建新索引 → 切换 → 延迟 `DROP` 旧索引"写成一个可重复执行的脚本，而不是每次手工 `DROP` + `CREATE`。
5. **对"大表重建"做一次显式决策**：本项目 `migrateTsvectorTokens` 有 `MAX_MIGRATE_ROWS = 100_000`、索引重建没有——**要么给索引重建也加上限（超限 WARN 跳过并提示手工分批），要么在注释里写清"为什么不加"。别维持两套标准。**

**★ 判据**：**如果你的 `WHERE` 里带着低选择性的租户条件、而建索引脚本里没有 `CONCURRENTLY`，那么你的向量检索在"能跑"和"能扩"之间就没有桥——A 基座上你只会偶尔漏一条规范，B 基座上它会稳定地表现为"检索不到任何东西"，并且日志里一个字都不会说。**

## 三、代码

### 3.1 一张 `memory_store`：三级演进的 DDL 起点

演进的起点就是这一张表：

`PgVectorMemoryStore.java:354-368`

```java
private void createTable(Statement stmt) throws SQLException {
    stmt.execute("""
            CREATE TABLE IF NOT EXISTS memory_store (
                id        BIGSERIAL PRIMARY KEY,
                agent_type VARCHAR(100),
                team_id    VARCHAR(100) NOT NULL DEFAULT '__global__',
                content   TEXT NOT NULL,
                metadata  JSONB DEFAULT '{}',
                level     VARCHAR(20) NOT NULL,
                created_at TIMESTAMPTZ DEFAULT now(),
                embedding vector(%d),
                search_vector tsvector
            )
            """.formatted(vectorDim));
    log.info("[PgVector] 已创建 memory_store 表（vector({}) + tsvector）", vectorDim);
}
```

**要把这张表变成"可水平扩展"，动的是三处、不是一处：**

| 演进 | 对这张表要做的改动 | 对应官方依据 |
|---|---|---|
| **分区** | 表声明改成 `PARTITION BY LIST (team_id)`，每个租户（或租户组）一个分区 | `pgvector/README.md:472` + https://www.postgresql.org/docs/current/ddl-partitioning.html |
| **分片** | 把 `team_id` 作为分片键交给 Citus / PgDog；表结构本身不变 | `pgvector/README.md:760` |
| **副本** | 表结构不变，检索查询路由到只读副本 | https://www.postgresql.org/docs/current/hot-standby.html |

**注意 `team_id` 的 `NOT NULL DEFAULT '__global__'`**（第 28 讲讲过它的风险）。在分区方案里这个默认值会变成**一个真实的技术约束**：分区键不允许为 NULL，而 `'__global__'` 这个值必须**自己独占一个分区**——否则"忘记传 team 的写入"会全部落到某一个租户分区里。**第 28 讲说它是"数据可见性"问题；到分区这一步，它先是"能不能建出分区表"的问题。**

**所以第 28 讲那条"`team_id` 的默认值会掩盖忘记传团队"的建议，在本讲升级成一条硬要求：分区键必须先有确定的、非默认的取值语义。**

### 3.2 过滤前置：`Supplier` 懒求值 vs SQL 字符串拼接

**工业界的接口层把"每请求求值"这件事写进了类型系统**（`VectorStoreDocumentRetriever.java:67-70`，逐字见 2.2）。它的落点是：

`spring-ai/spring-ai-rag/src/main/java/org/springframework/ai/rag/retrieval/search/VectorStoreDocumentRetriever.java:110-119`

**每次检索都重新调用这个 `Supplier`**——所以"当前用户是谁"这个问题在那一次请求的上下文里回答，而不是在 Bean 初始化时回答。

**本项目的对应写法是"拼 SQL 字符串"**（`PgKnowledgeStore.java:202-221`，第 29 讲逐字引过）。两条 SQL 都用 `.formatted(teamFilter, freshSql)` 把租户条件拼进去：

```java
// core/rag/PgKnowledgeStore.java:201-208（节选，第 29 讲已逐字引用）
String denseSql = """
        SELECT id, agent_type, team_id, content, metadata, level, created_at,
               1 - (embedding <=> ?::vector) AS sim
        FROM memory_store
        WHERE agent_type = 'RAG' AND %s %s
        ORDER BY embedding <=> ?::vector
        LIMIT ?
        """.formatted(teamFilter, freshSql);
```

而入参在链路入口被处理过一次（`RagContextBuilder.java:181-235`）：

```java
// core/memory/RagContextBuilder.java:181-235（节选，第 26 讲已逐字引用）
List<MemoryEntry> candidates = knowledgeStore.searchKnowledge(query, retrieveK,
        Teams.sanitize(teamId), true, maxAge);               // ← ⑤ 初检，候选窗 50
```

**两种写法的差别不在"哪个更优雅"，在"过滤发生在哪一层"：**

| 维度 | spring-ai 的 `Supplier<Filter.Expression>` | 本项目的 `teamFilter` 字符串 |
|---|---|---|
| 求值时机 | 每请求（`:110-119`） | 每请求（每次检索都重新 `formatted`） |
| 过滤在索引的哪一侧 | 取决于底层 store 的 SQL 组装 | **确定在索引扫描之后**（`WHERE`） |
| 能否做分区裁剪 | 取决于底层实现 | 可以——**只要表按 `team_id` 分区，PG 会自动裁剪** |
| 注入风险 | 表达式对象，无字符串拼接 | 已由 `Teams.sanitize` 处理，但仍是字符串拼接 |

**关键的一格是第三行：`WHERE team_id = ?` 在"单表"下是 post-filter，在"分区表"下会变成 partition pruning——同一条 SQL，两者语义完全不同。** 这就是 2.1 与 2.2 的交汇点：**分区不是"把表切开"，而是"把过滤这一层从扫描之后搬到扫描之前"**，而 SQL 一个字都不用改。

**这也是为什么"先分区、后分片"是对的次序**：分区用一条 DDL 就能让现有 SQL 变成 pre-filter；分片要改的是连接路由与事务边界。**先做便宜的那件。**

### 3.3 建索引：主流框架只建不调

`PgVectorStore.java:512-525` 的 `CREATE INDEX`（逐字见 2.3）是**不带任何 `WITH (...)` 的**。对照本项目：

`PgVectorMemoryStore.java:178-211`（注释节选，第 28 讲已引用）

```java
/**
 * 确保向量 ANN 索引存在且为期望类型（hnsw / ivfflat），幂等。
 * ...
 *   <li>索引不存在 → 直接按期望类型创建（hnsw 失败则 WARN 回退 ivfflat，老 pgvector 无 hnsw）；</li>
 *   <li>存量库为 ivfflat 而期望 hnsw → DROP 后重建迁移（启动时一次性，数据量小时可接受；
 *       数据量大时仍会执行——hnsw 在 pgvector 0.5+ 均可用，迁移收益明确）；</li>
 * ...
 */
```

**两边的共同点是"都没调参"**；区别是**本项目在启动时做**（因此有"启动被拖死"的风险），**框架不建**（把调参完全交给使用方）。

**把三方放在同一张表上看"索引参数谁负责"：**

| 同题 | pgvector | langchain4j | spring-ai | 本项目 |
|---|---|---|---|---|
| `m` / `ef_construction` | 显式 SQL（`src/hnsw.h:54` / `:57` 给默认值） | 不设 | **不设**（`PgVectorStore.java:512-525`） | 未调 |
| `lists` / `probes` | 显式 SQL（`src/ivfflat.h:55` / `:58` 给默认值） | `lists` 由构造参数传入 | 不设 | 未调 |
| `ef_search` | 会话级 GUC（`src/hnsw.h:60` 默认 40） | 不设 | **全模块 0 处** | 未设 |

**这张表是本节最该带走的东西：三方实现里，只有 pgvector 自己（作为扩展）暴露了这些参数，两个主流 Java 框架一个都不设。** 也就是说——**"我用的是框架推荐的向量库"这句话，在索引参数这件事上不构成任何保证。**

**那"该设成多少"？** pgvector 只在 IVFFlat 上给了经验法则（`pgvector/README.md:340-342`：`lists` 起步取 `rows / 1000`（≤1M 行）或 `sqrt(rows)`（>1M 行），`probes` 起步取 `sqrt(lists)`）。**HNSW 的 `m` / `ef_construction` 它没给公式，只给了默认值与硬上限**（2.3 已列）——**这意味着 HNSW 的这两颗参数只能靠自己的数据实测。**

**所以第 3 步的落地动作是：建索引脚本里必须显式写 `WITH (...)`，把参数从"默认值"变成"决定"。** 一个把 `m=16` 写进脚本的人，和一个"什么都没写、用的是默认 16"的人，**在表结构上一模一样，在决策上是两种状态。**

### 3.4 降级链与迭代扫描：三档、双重熔断、连接级预算

**降级链的第 ② 级怎么落？** 它不需要新的存储能力——本项目**已经有两路**（`PgKnowledgeStore.java:202-221` 的 dense / sparse 两条 SQL）。第 ② 级的做法是：embedding 不可用时**直接跳过 dense 路**，只执行 sparse 路，并把 `retrieval.mode` 标成 `sparse_only`。

**这条路是通的，因为第 29 讲的 RRF 融合天然容忍"只来一路"**：`sparseRank` 有内容、`denseRank` 为空，`rrf.merge` 那一行（`PgKnowledgeStore.java:275-285`）照样产出融合分。**所以降级链的第 ② 级是"删掉一次查询"，不是"写一段新逻辑"——这是低成本的改造。**

**同一节要拆掉的那个错误答案，在代码里是这样的。** 想开 iterative scan，你得显式设 GUC（`pgvector/README.md:487` / `:493` / `:495`），而它的两个熔断参数同样是 GUC（`pgvector/src/hnsw.c:102-105` / `:107-109`）：

```c
	DefineCustomIntVariable("hnsw.max_scan_tuples", "Sets the max number of tuples to visit for iterative scans",
							NULL, &hnsw_max_scan_tuples,
							20000, 1, INT_MAX, PGC_USERSET, 0, NULL, NULL, NULL);
```

停止判据是"两个条件取或"（`pgvector/src/hnswscan.c:259`）：

```c
			if (so->tuples >= hnsw_max_scan_tuples || MemoryContextMemAllocated(so->tmpCtx, false) > so->maxMemory)
```

内存上限来自**连接级**的 `work_mem`（`pgvector/src/hnswscan.c:155`）：

```c
	maxMemory = (double) work_mem * hnsw_scan_mem_multiplier * 1024.0 + 256;
```

**三行代码连起来是一个很硬的结论：`iterative_scan` 的"多扫多少"不是常数，它同时受"元组数上限"和"当时这个连接的 `work_mem`"约束。** 所以同一个查询在不同连接上可能返回不同结果——**这不是不确定，这是配置决定的，只是配置在连接池那一侧。**

**跨索引类型的能力差也要在这里再看一次：** 如果索引是 IVFFlat，你能设的只有 `relaxed_order`（`pgvector/src/ivfflat.h:116-117`），**没有 `strict_order`**（`pgvector/src/hnsw.h:163-165` 才有三档）。**这就是"迁移索引类型会静默丢能力"——不报错，只是你写的那条 `SET hnsw.iterative_scan = strict_order` 从此没有意义。**

**把它写进流程：索引类型是一条要进 ADR 的决策，不是"性能偏好"。** 它决定了你能用哪些 GUC、能用哪些参数。

## 四、避坑清单

- [ ] **共享一张表一个索引时，租户会互相干扰。** 这是 pgvector 官方承认的（`pgvector/README.md:470`）——**要么分区、要么分表，别指望 `WHERE` 能兜住。**
- [ ] **`WHERE` 里的租户条件不改"索引探几个节点"，它是 post-filter。** 官方量化例子是 `40 × 10% = 4`（`pgvector/README.md:450`）——**候选被线性打折，`LIMIT` 补不回来。**
- [ ] **多租户过滤器必须每请求求值，不能是构造期常量。** spring-ai 用 `Supplier<Filter.Expression>` 就是为了这个（`VectorStoreDocumentRetriever.java:67-70`），注释里点名的动机就是 tenant ID。
- [ ] **生产环境建索引必须 `CONCURRENTLY`。** 普通 `CREATE INDEX` 全程持写锁（`pgvector/README.md:704`）——痛点里那次"P99 涨到 8 秒"就是这个。
- [ ] **把 `maintenance_work_mem` 的 NOTICE 接成告警。** pgvector 会主动告诉你"图装不进内存了、构建会显著变慢"（`pgvector/README.md:300-302`）——**这是免费的构建降速信号，别只让它印在日志里。**
- [ ] **并行 worker 默认只有 2。** 大表建索引要显式 `SET max_parallel_maintenance_workers`（`pgvector/README.md:309` / `:312`），并确认 `max_parallel_workers` 够用（默认 8，`:315`）。
- [ ] **IVFFlat 的 `probes` 默认是 1。** 默认建出来的 IVFFlat 只探一个聚类中心，召回极低（`pgvector/src/ivfflat.h:58`）——`lists` 与 `probes` 必须按 `rows / 1000` / `sqrt(rows)` / `sqrt(lists)` 算（`pgvector/README.md:340-342`）。
- [ ] **HNSW 的 `m` / `ef_construction` 建完改不了，且都有硬上限。** `m` 上限 100、`ef_construction` 上限 1000（`pgvector/src/hnsw.h:55` / `:56` / `:59`）——想改就是重建。**把参数写进建索引脚本，让"用默认值"是一个显式决定。**
- [ ] **框架只建索引、不调参。** spring-ai 的 `CREATE INDEX` 不带任何 `WITH (...)`（`PgVectorStore.java:512-525`），且全模块 0 处 `ef_search` / `iterative_scan` / `SET LOCAL`。**`ef_search` / `lists` / `probes` 这些决定 P99 的参数，框架一个都不设——全要你自己设。**
- [ ] **索引重建要能用"蓝绿"做：建新索引 → 原子切换 → 延迟 `DROP` 旧索引。** 别在生产上手工 `DROP` + `CREATE`——**那是把一次可回滚的变更做成了不可回滚的宕机。**
- [ ] **"删除"在向量库里是标记删除，"清理"只能靠重建。** 写入有 upsert 的工业答案（`PgVectorEmbeddingStore.java:640`），删除没有——**空洞累积会让召回率随时间下降，且没有日志告诉你。**
- [ ] **`iterative_scan` 不是 post-filter 的解药：它是双重熔断，内存预算挂在连接级 `work_mem` 上。** 停止条件是"元组数 ≥ `max_scan_tuples` 或内存超预算"（`pgvector/src/hnswscan.c:259`），预算 = `1 × work_mem`（`:155`）。**而且 IVFFlat 没有 `strict_order` 档（`pgvector/src/ivfflat.h:116-117`）——迁移索引类型会静默丢能力。**
- [ ] **同一套迁移策略别在一个类里写两遍。** 本项目 `migrateTsvectorTokens` 有 `MAX_MIGRATE_ROWS = 100_000`、索引重建没有（`PgVectorMemoryStore.java:240-297` / `:178-211`）——**大表保护要显式决策，别默认"反正能跑"。**
- [ ] **降级链的第 ② 级（只走稀疏路）必须存在。** 否则 embedding 一抖动就全线 abstain——**而你的链路里本来就有一半能力可以兜住它。** 每一级都要有独立标记 `retrieval.mode`（范式见 `MultiQueryExpander.java:118-131`）。

## 五、动手任务

> **任务**：在 `memory_store` 上做一次"受控的索引重建"，并量化 post-filter 的打折与降级链的收益。
>
> **仓库位置**：`code-review-agent`（`core/memory/PgVectorMemoryStore.java:178-211` 的索引迁移、`core/rag/PgKnowledgeStore.java` 的两条 SQL、`src/main/resources/application.yml:221` 的 `retrieve-k`）
>
> **操作**：
> 1. **量一次隔离度**：在库里执行
>    ```sql
>    SELECT agent_type, count(*) FROM memory_store GROUP BY agent_type;
>    SELECT team_id, count(*) FROM memory_store GROUP BY team_id ORDER BY 2 DESC LIMIT 10;
>    ```
>    算出**过滤选择性** = 最大团队的行数 ÷ 表总行数。
> 2. **量一次打折**：用 `SET hnsw.ef_search` 分别在 `40`（默认，见 `pgvector/src/hnsw.h:60`）与 `400` 下跑同一条检索，记录"每路命中数 + P95 延迟"。用 `ef_search × 选择性` 估"过滤之后平均还剩几条"，和第 1 步算出的选择性对照。
> 3. **改建索引脚本**：把迁移里那条 `CREATE INDEX` 改成 `CREATE INDEX CONCURRENTLY`（`pgvector/README.md:704`），并在前面加 `SET max_parallel_maintenance_workers = 7;`（`:309` / `:312`）；同时把 `maintenance_work_mem` 的 NOTICE（`:300-302`）接成告警——**用日志采集规则匹配 `hnsw graph no longer fits into maintenance_work_mem` 即可。**
> 4. **补上降级链的第 ② 级**：在 `PgKnowledgeStore` 的检索入口加一个开关，模拟 embedding 超时时**只执行 sparse 那条 SQL**（第 3.1 节的第二条），并打 `retrieval.mode=sparse_only`；对照 `hybrid` 与 `sparse_only` 两种模式在 5 个基线查询上的召回差异。
> 5. **做一次"标记删除"观察**：删掉一小批知识块（`deleteByMetadata`），然后**不重建索引**，重跑第 2 步的检索，看召回有没有变化；再重建索引后跑一次。
>
> **预期结果**：
> - 第 1 步会给出一个**具体的选择性数字**——A 基座上它接近 100%（每个团队的行数占比高），这就是"为什么开发机上感觉不到 post-filter"的答案；
> - 第 2 步里，如果发现"`ef_search` 从 40 调到 400 而召回几乎没动"，说明瓶颈不在索引层，而在**过滤顺序**——回到 2.1 / 2.2 考虑分区；
> - 第 4 步的 `sparse_only` 模式**应当仍然返回非空结果**（稀疏路是独立的一路）——它证明降级链的第 ② 级是可行的，而不是一次"功能减半"；
> - 第 5 步是本次任务最该记下来的一次观察：**删除后不重建，召回"看起来没变"**——这正是删除语义最危险的地方，它不报错、不掉指标。
>
> **关键对照**：把第 2 步的"选择性 + `ef_search` + 每路命中数"写成一份实验记录。下一次有人问"为什么某条知识搜不到"，你能直接回答是"选择性打折"、"索引里的空洞"，还是"embedding 降级了"——**这三者在这份记录出现之前，是三个长得一模一样的症状。**

## 本讲小结

1. **单表在开发机上够用，在生产上会塌。** pgvector 官方自己承认共享索引会让租户互相干扰（`pgvector/README.md:470`）——演进方向是**分区（索引隔离）→ 分片（单机装不下）→ 副本（读 QPS）**，三步解决三个不同的问题。
2. **过滤条件放在 `WHERE` 里就是 post-filter，候选按选择性线性打折。** `40 × 10% = 4`（`pgvector/README.md:450`）——**而分区会让同一条 SQL 变成 partition pruning，一个字都不用改。** 先做这件便宜的事。
3. **多租户过滤器必须每请求求值。** spring-ai 用 `Supplier<Filter.Expression>` 是为了这个（`VectorStoreDocumentRetriever.java:67-70`），注释里直接点名 tenant ID。**构造期常量式过滤器在多租户下从第一天就是错的。**
4. **建索引是四个不可逆点：参数、写锁、内存、进度。** `CONCURRENTLY` 是唯一不阻塞写的建法（`pgvector/README.md:704`）；`m` / `ef_construction` 建完改不了（`pgvector/src/hnsw.h:54` / `:57`）；`NOTICE` 会主动告诉你内存不够（`:300-302`）。
5. **框架只建索引、不调参。** spring-ai 的 `CREATE INDEX` 不带任何 `WITH (...)`（`PgVectorStore.java:512-525`），全模块 0 处 `ef_search` / `iterative_scan` / `SET LOCAL`——**`ef_search`、`lists` / `probes` 这些决定 P99 的参数，框架一个都不设。**
6. **"打开 iterative scan 就好了"是错的，删除比写入难。** iterative scan 是**双重熔断**且内存预算挂在连接级 `work_mem` 上（`pgvector/src/hnswscan.c:155` / `:259`），IVFFlat 还没有 `strict_order` 档（`pgvector/src/ivfflat.h:116-117`）；而删除只能标记、清理只能靠重建——**空洞累积会让召回率静默下降。**
7. **降级链的第 ② 级（embedding 挂了只走稀疏路）是低成本、高收益的一次改造。** 它只需要"跳过一次查询"，而不是新写一段逻辑——**因为第 29 讲的 RRF 融合天然容忍只来一路。**

下一讲我们把这条链路当成一个**生产系统**来运营：算清嵌入 / 存储 / 检索 / 重排 / 注入各自花掉多少钱，用三层缓存（嵌入缓存、语义缓存、结果缓存）把重复劳动挡在前面，再把第 33 讲的隐式信号接成在线闭环——以及回答一个最实际的问题：**索引、模型、参数这三类变更，回滚的代价为什么完全不同。**
