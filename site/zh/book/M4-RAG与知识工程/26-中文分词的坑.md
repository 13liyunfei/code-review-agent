## 一、痛点

我在知识库里灌了一条团队规范，白纸黑字：

> **禁止使用字符串拼接的 SQL，必须使用参数绑定。**

然后我提交了一个 PR，里面有一段用 `+` 拼出来的 SQL。审查机器人扫过了，也提了意见——但意见是"建议补充注释"。

**它压根没引用那条规范。**

我去查检索环节。混合检索是两条腿走路：稠密向量（权重 0.7）+ 稀疏 BM25（权重 0.3）。

- **稠密向量这条腿**：能召回一些语义相近的条目，但那条规范没进来（"参数绑定"和"字符串拼接"在向量空间里的距离，并不像人以为的那么近）。
- **稀疏 BM25 这条腿**：**完全空转**。

我一开始以为是"效果差"。直到我在真库上跑了一句 SQL，才发现真相比"效果差"严重得多。

## 二、原理

### 2.1 先说清楚：`simple` 词典到底做了什么

PostgreSQL 的全文检索有两个层次，很多人把它们混为一谈：

| 层次 | 作用 | `simple` 在这里做什么 |
|---|---|---|
| **解析器（Parser）** | 把文本切成 token | `simple` **管不着**——它用的是默认解析器 |
| **词典（Dictionary）** | 对 token 做归一化 | `simple`：只做**小写化**，不做词干还原、不管停用词 |

**关键就在这里**：`simple` 是**词典**，不是**解析器**。所以"用 `simple` 就能支持中文"这个想法，从根上就是错的。

那默认解析器怎么切中文？它按 **Unicode 字符类别**切分：

- CJK 表意文字 → 归类为 "word"（词）
- Latin 字母 → 也归类为 "word"

既然都是 word，**它们就连成一个 token**。所以：

```sql
SELECT to_tsvector('simple', '禁止使用字符串拼接的SQL，必须使用参数绑定');
```

在 PG 17.11 上，真实输出是：

```
+--------------------------------------------------+
|                    raw_vector                    |
+--------------------------------------------------+
| '必须使用参数绑定':2 '禁止使用字符串拼接的sql':1 |
+--------------------------------------------------+
```

**看到问题了吗？**

- 整句没有按词切，只被**逗号**切了一次，得到 **2 个词位**；
- `禁止使用字符串拼接的SQL`（13 个字符）是**一个**词位，被整体小写成了 `禁止使用字符串拼接的sql`；
- `必须使用参数绑定` 也是**一个**词位。

### 2.2 这意味着什么：`@@` 比的是词位，不是子串

全文检索的匹配运算是 `@@`，它比的是**词位（lexeme）是否相等**——**不是子串包含**。

于是灾难发生了：

| 你想查的词 | 文档里的词位 | 结果 |
|---|---|---|
| `参数绑定` | `必须使用参数绑定` | **不命中**（不是同一个词位） |
| `SQL` | `禁止使用字符串拼接的sql` | **不命中**（不是同一个词位） |

**注意第二行**：连 `SQL` 这种英文词都命中不了。因为文档里根本没有独立的 `sql` 词位，只有那个 13 字符的整体串。

我在真库上做的对照实验（可直接复现）：

```sql
SELECT
  (to_tsvector('simple','禁止使用字符串拼接的SQL，必须使用参数绑定')
     @@ plainto_tsquery('simple','参数绑定'))                       AS before_cn,
  (to_tsvector('simple','禁止使用字符串拼接的SQL，必须使用参数绑定')
     @@ plainto_tsquery('simple','SQL'))                            AS before_en,
  (to_tsvector('simple','禁止 使用 字符 串拼 接的 sql 必须 使用 参数 绑定')
     @@ to_tsquery('simple','参数 | 数绑 | 绑定'))                   AS after_cn,
  (to_tsvector('simple','禁止 使用 字符 串拼 接的 sql 必须 使用 参数 绑定')
     @@ to_tsquery('simple','sql'))                                 AS after_en;
```

```
+-----------+-----------+----------+----------+
| before_cn | before_en | after_cn | after_en |
+-----------+-----------+----------+----------+
| f         | f         | t        | t        |
+-----------+-----------+----------+----------+
```

**修复前：中文词 `f`，英文词也 `f`。修复后：双双 `t`。**

**手算：一句话的中文，四种"count"天差地别。** 拿一句真实的约 40 字规范「禁止在热路径中使用 N+1 查询，必须改成批量预编译」，分别数：

> 你的直觉：**1 个"整句"**；
> LLM 词元：40 个汉字 ≈ **30~40 token**（中文 BPE 约 1 字 ≈ 0.7~1.1 token，比英文"4 字符约 1 token"贵得多）；
> PG `simple`（不修复）：**1 个词位**（无逗号的连续长串就是 1）；
> 应用层 bigram：**L−1 = 39 个词位**（连续 CJK 的 `N 字 → N−1 个二元组`）。
>
> 于是检索侧用 OR 就变得必要：39 个候选词位里**任一命中即召回**，由 ts_rank 把多词位命中的文档排前。**若换成 AND，要求 39 个词位全部命中——一个 diff 几乎不可能逐 bigram 同时含整句，必然零命中。**
>
> 反观英文：同一信息约 20 个词天然按空格切，个位数词位就够，AND 甚至还能用。**这就是"中文必须 bigram + OR、英文默认词就够"这条经验的数量级来源。**

> **顺带回答"中文分词对不同切块策略的影响"**：它影响的是**稀疏路（BM25）**的词位数量与查询形态，**不影响稠密路（向量）**——中文 bigram 让稀疏路"敢召回、不奢求精确"，这和第 23 讲切块粒度针对的是两套不同机制。

### 2.3 为什么它比"效果差"危险

因为**它不报错**。

BM25 空转的后果不是"报错"，而是**召回质量悄悄下降 30%**（稀疏路权重 0.3）——你只会觉得"这个 RAG 好像不太行"，然后去调 prompt、换模型、加数据，永远想不到问题在分词上。

**这就是这一讲要教的核心方法：出问题先做对照实验，别急着调参。**

## 三、代码

### 3.1 `TextTokenizer`：不装扩展，自己分词

要在不安装 `zhparser` / `pg_jieba` 的前提下让中文可用，思路是：**在应用层把文本切好，再交给 PG 的 `simple` 词典**。

`TextTokenizer` 做三件事：

```java
// core/rag/TextTokenizer.java:33-41
public final class TextTokenizer {

    /** 粗切分隔符：非字母、非数字、非 CJK 的一切（空格/标点/代码符号）。 */
    private static final Pattern NON_TOKEN = Pattern.compile("[^a-zA-Z0-9\\u4e00-\\u9fa5]+");
    /** camelCase 边界 / snake_case 下划线。 */
    private static final Pattern CAMEL_OR_SNAKE = Pattern.compile("(?<!^)(?=[A-Z])|_+");
    /** ASCII 子词最小长度（低于此值视为噪音）。 */
    private static final int MIN_ASCII_LEN = 2;
```

**(1) 中文：bigram（二元组）**

```java
// core/rag/TextTokenizer.java:131-140
/** CJK 段按 bigram 展开（单字直接保留）。 */
private static void addBigrams(Set<String> out, String cjk) {
    if (cjk.length() == 1) {
        out.add(cjk);
        return;
    }
    for (int i = 0; i + 2 <= cjk.length(); i++) {
        out.add(cjk.substring(i, i + 2));
    }
}
```

`参数绑定` → `参数` / `数绑` / `绑定`。

为什么"不讲词法、只切二元组"反而好用？

- **不需要词典**：中文分词的最大成本就是词典（还要处理新词、人名、行业术语）；
- **不漏**：任意长度 ≥2 的子串，一定包含某个二元组。查 `参数` 能命中 `参数绑定`，查 `数绑` 也能；
- **这是业界标准做法**：MySQL 的 ngram 全文索引、Elasticsearch 的 CJK bigram 都是这个思路。

代码注释里也点明了这一点：

```java
// core/rag/TextTokenizer.java:20-25（节选）
// 中文：连续 CJK 段按 bigram 切（"参数绑定" → 参数/数绑/绑定）——
//       业界无词典分词场景的标准做法（MySQL ngram、ES CJK bigram），
//       既避开词典依赖，又保证任意子串查询都能命中；
// 英文/数字/标识符：按非字母数字粗切，再做 camelCase / snake_case 子词拆分并转小写
//       （getUserById → get/user/by/id），让代码符号与规范文档共享词位；
// 单字 CJK 保留；ASCII 子词长度 ≥2 才保留（抑制噪音）。
```

**(2) 英文/标识符：camelCase / snake_case 子词拆分**

```java
// core/rag/TextTokenizer.java:142-153
/** 英文/数字段：camelCase / snake_case 子词拆分 + 小写。 */
private static void addAsciiSubwords(Set<String> out, String seg) {
    // 全大写的缩写词（SQL / URL / HTTP / ID）不能被 camelCase 规则按大写边界切碎——
    // 「SQL」会变成 S/Q/L 三个单字母再被长度阈值丢弃，导致代码审查最高频的术语消失。
    if (isAllUpperCaseAscii(seg)) {
        addLower(out, seg);
        return;
    }
    for (String sub : CAMEL_OR_SNAKE.split(seg)) {
        addLower(out, sub);
    }
}
```

**这一段是我踩坑之后才补上的**，值得单独讲：

`getUserById` 按 camelCase 规则拆成 `get`/`user`/`by`/`id` —— 这是对的。

但 `SQL` 也是大写字母，会被**同一个规则**按大写边界切碎成 `S` / `Q` / `L` 三个单字母，然后被 `MIN_ASCII_LEN = 2` 的阈值**全部丢弃**。

**结果是：代码审查里最高频的那个术语，消失了。**

所以有了 `isAllUpperCaseAscii()` 这个特判：**全大写的缩写词整体保留**（`SQL` → `sql`，`HTTP` → `http`，`URL` → `url`）。

这类 bug 特别值得警惕：**规则在一种输入上是对的，在另一种输入上会静默产生错误结果。**

`toTokenString()` 就是把词集合用**空格**连起来。PG 的 `simple` 词典拿到「已分词 + 空格分隔」的文本，只需按空格切即可生成正确的词位：

```java
// core/rag/TextTokenizer.java:77-79
public static String toTokenString(String text) {
    return String.join(" ", tokenize(text));
}
```

### 3.3 检索侧：必须是 OR，不能是 AND

```java
// core/rag/TextTokenizer.java:95-103
public static String toTsQueryOr(String text, int maxTerms) {
    Set<String> toks = tokenize(text);
    if (toks.isEmpty()) {
        return "";
    }
    List<String> limited = new ArrayList<>(toks);
    int n = Math.min(maxTerms, limited.size());
    return String.join(" | ", limited.subList(0, n));
}
```

原来用的是 `plainto_tsquery('simple', ?)`，它生成的是 **AND** 查询。而 RAG 的查询往往是**整段 diff 或长句**——AND 要求**所有词都命中**，长查询几乎必然零命中。

**这是"稀疏路失效"的第二种形式**，比分词问题更隐蔽：分词修好了，AND 还在那里默默把所有长查询干掉。

改成 OR 之后，任一关键词命中即可召回，再由 `ts_rank` 把多词命中的文档排到前面：

```java
// core/rag/PgKnowledgeStore.java:189-193
// 稀疏路查询串：中文 bigram + 标识符子词，用 OR 连接。
// 用 OR 而非 plainto_tsquery 的 AND：RAG 查询是整段 diff/长句，AND 要求全部词命中，
// 长查询几乎必然零命中（另一种形式的稀疏路失效）；OR 保证「任一关键词命中」即可召回，
// 由 ts_rank 负责把多词命中的文档排到前面。
String sparseTsQuery = TextTokenizer.toTsQueryOr(query, SPARSE_QUERY_MAX_TERMS);
```

顺便说一个**安全设计**，代码注释里专门写了：

```java
// core/rag/TextTokenizer.java:88-89
// 安全性：输出仅含 CJK / 字母 / 数字，不含 & | ! ( ) : 等 tsquery 语法字符，
// 不存在 tsquery 注入面。
```

因为 `toTsQueryOr` 的输出**只可能是分词结果**，而分词器把一切非字母数字 CJK 的字符都当分隔符丢掉了——所以 `|` 只能是我们自己拼的，用户输入里的 `&`、`!`、`(` 根本进不来。**用"构造方式本身"来保证安全，比事后转义更可靠。**

### 3.4 存量数据必须迁移

改完了分词器，**老数据仍然是按旧方式建的索引**——不迁移等于白改。

```java
// core/memory/PgVectorMemoryStore.java:246-252

    final String name = "tsvector-tokenize-v1";
    try (Statement s = conn.createStatement()) {
        s.execute("""
                CREATE TABLE IF NOT EXISTS rag_schema_migration (
                    name varchar(128) PRIMARY KEY,
                    applied_at timestamptz NOT NULL DEFAULT now()

```

三个设计点：

- **幂等**：用 `rag_schema_migration` 表记录已执行的一次性迁移，重复启动不会重跑。日志实测输出为：
  ```
  [PgVector] 迁移：已按分词器重建 316 行的 search_vector（中文/标识符 BM25 生效）
  ```
- **有上限**：`MAX_MIGRATE_ROWS = 100_000`，超过就跳过并提示手工分批，避免大表把启动拖死；
- **失败只 WARN 不阻断启动**：

```java
// core/memory/PgVectorMemoryStore.java:244
// <p>失败只 WARN 不阻断启动：迁移失败仅影响中文 BM25 召回质量，不应让引擎起不来。
```

**这三条的取舍逻辑值得学**：一次数据迁移的失败，不该让整个服务起不来——但要**大声告警**。

### 3.5 最硬的一条铁律

> **写入侧与检索侧必须使用同一个分词器。**

如果写入时用 `TextTokenizer`、检索时用原文，倒排词位对不上——**后果比不分词更隐蔽**（因为看起来"两边都处理了"）。

代码注释把这句话写在了类头：

```java
// core/rag/TextTokenizer.java:29
// <p>写入侧与检索侧<b>必须使用同一分词器</b>，否则倒排词位对不上（比不分词的后果更隐蔽）。
```

### 3.6 分词策略一张表看清（PG 下中文全文检索选型速查）

不要以为只有"应用层 bigram"一条路——业界还有 `zhparser` / `pg_jieba`，它们和本项目方案的关键差异在一个字：**要不要装扩展、要不要养词典**。

| 维度 | PG `simple` 裸串 | 应用层 bigram+标识符拆分 | `zhparser` | `pg_jieba` |
|---|---|---|---|---|
| **需要装扩展** | 否 | **否**（纯应用层） | 是（且要配 dict 词库） | 是（且要配分词词典） |
| **中文长串的词位数** | 1（整串） | N−1（二元组） | 按词切（依赖词表命中） | 按词切（依赖词典命中） |
| **英文/标识符** | 不拆 camelCase | camelCase/snake_case 子词拆分 | 多交给 PG 默认规则 | 同上 |
| **新词 / 行业术语** | 无 | 天然覆盖（无需词典） | 易漏（词典外的字串切不出） | 易漏 |
| **引入成本** | 0 | 应用层几十行 + 存量迁移 | PostgreSQL 扩展 + 词库维护 | 扩展 + 词典 + 版本耦合 |
| **与稠密路的互补** | 空转 | 正常互补 | 互补但受词表限制 | 互补但受词典限制 |
| **跨环境一致性** | 是 | 是（纯代码，无扩展依赖） | 依赖每台环境装扩展 | 依赖扩展与词典 |
| **匹配** | 无 | **无侵入、最稳的默认** | 愿长期养词库的团队 | 低频、短文档场景 |

> **结论不出预料：未遇到"必须按词切、bigram 撑不住"的明确需求前，应用层 bigram 是既有性价比又有一致性的默认；`zhparser`/`pg_jieba` 是"你愿意为一个准确分词付词典维护税"时才上的选项**——而且要记住规则，**一上就必须写入侧和检索侧同改，否则口径分叉比原来更糟**（第 3.5 节）。

**工程判据（这一讲唯一要背的验收规则）：** **上中文 RAG 前，先拿一句 40 字的真实规范跑 `SELECT to_tsvector('simple', '你的句子');`，数词位——若输出 ≤3 个词位，你的稀疏路是废的；修复后的验收标准是『查询任取其中的 2 字 bigram 都能命中，且全大写缩写词（SQL / HTTP）能单独命中』。** 这一条同时覆盖了分词、OR、缩写特判三条坑。

## 四、避坑清单

- [ ] **不要以为 `simple` 词典支持中文。** 它是**词典**不是**解析器**——中文分词发生在解析器层，`simple` 管不着。
- [ ] **上中文 RAG 前，先跑这句验证**：`SELECT to_tsvector('simple', '你的中文句子');` 看输出是几个词位。如果整句只有一两个词位，你的稀疏路就是废的。
- [ ] **写入侧与检索侧必须同口径。** 这是最容易犯、后果最隐蔽的一条。
- [ ] **查询用 OR 不用 AND。** `plainto_tsquery` 是 AND，长查询必然零命中。
- [ ] **全大写缩写词要特判保留。** 否则 `SQL` / `HTTP` / `URL` 会被 camelCase 规则切碎后丢弃。
- [ ] **改分词器 = 必须迁移存量。** 用迁移表做幂等标记，设行数上限，失败只告警不阻断。
- [ ] **别急着调参。** RAG 效果差，先做对照实验定位是哪条腿瘸了，再动手。
- [ ] **如果将来引入 `zhparser` / `pg_jieba`，必须同时改写入侧和检索侧**——口径一致性高于分词质量。

## 本讲小结

1. **`simple` 词典不做中文分词**，无空格的中文长串会变成**一个**词位；连 `SQL` 这种英文词都匹配不上。
2. 修复方案是**应用层分词 + PG 侧空格串**：中文用 bigram（无词典、不漏召回），标识符拆 camelCase/snake_case 子词。
3. **两个附带的坑**：全大写缩写词要整体保留；查询要用 OR 不能用 AND。
4. **铁律**：写入侧与检索侧必须同口径；改分词器必须迁移存量数据。
5. **方法论**：RAG 效果问题先用**对照实验**定位，不要一上来就调参。这张 `f/f → t/t` 的表，就是面试里最有说服力的答案。
