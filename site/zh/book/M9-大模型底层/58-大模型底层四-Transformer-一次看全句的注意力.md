## 一、痛点

你已经在 M4 为"上下文"操碎了心：三层漏斗、压缩、检索、为什么窗口是硬限制。但你有没有停下来问那个最底下的问题：**"为什么模型一定要吃这么多 token？为什么不能书越读越多但内存不涨？"**

两个常见误区：

**误区一："上下文窗口是厂商拍脑袋定的，越大越好。"** → 你把上下文当"规格参数"去攀比，却没看到它和模型结构之间的矛盾。

**误区二："上下文=给模型更多资料，多多益善。"** → 于是你拼命塞 context，忽略第 44 讲的"准入+分层+投放"——**塞得越多，噪音和成本一起涨，还未必更聪明。**

本讲要破除的是"上下文是可用可不用、多大都行"的错觉。真相是：

> **上下文窗口不是厂商炫技，而是 transformer 的『注意力』架构的直接代价——因为它要让每个位置一次看清整句话，所以整句话的全部 token 就必须同时存在于内存里。** 你为上下文做的所有工程——压缩、检索、分层——不是在"优化性能"，而是在**驯服这个架构本身的固有成本**。

## 二、原理

### 2.1 注意力：直接看全局，而不是一步传一步

在 transformer 之前，处理序列常用 **RNN**：一个字一个字地走，把前面的信息"存"在内部状态里传给下一个。问题是**它必须一步步串行**，且**越远的信息越容易在传递中丢失**。

Transformer 的**注意力机制（Attention）**改变了这个根本局限：

> **序列里每一个位置，都可以『直接』看所有其他位置的向量，并按与自己的"相关程度"加权组合。** 不再需要一步步传，每个位置都能一次摸到整句话——这让模型能同时捕捉"这个代词指代前文谁""这个词和后面哪个词呼应"这类全局依赖。**这就是"一次看清全句"的含义，也是它理解上下文能力远超旧模型的原因。**

### 2.2 拆开注意力：Q、K、V 三个矩阵到底在算什么

"相关程度加权"落到代码，就是**三个投影 + 一个缩放点积 + 一个 softmax**。对第 55/57 讲那条线，这里第一次出现具体公式：

给定一层里 n 个 token 的表示 X（n×d 矩阵），先各自投影成三份：

```
Q = X·W_Q   （Query  查询：我这个位置"想找什么"）
K = X·W_K   （Key    键：每个位置"是什么"）
V = X·W_V   （Value  值：每个位置"携带什么内容"）
```

然后每个位置的输出就是"**用我的 Q 去和所有人的 K 算相关度，再用相关度去加权所有人的 V**"：

```
Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k ) · V
```

逐项拆给有算法背景的你：

1. **`Q·Kᵀ`（相关度打分）**：Q 的第 i 行（第 i 个 token 想找什么）和 K 的第 j 行（第 j 个 token 是什么）做点积，得到一个标量，代表 i 和 j 的"相关程度"。全部两两算一遍，就得到一个 **n×n 的注意力分矩阵**——这就是"每个位置看全句"的物理形态：**一行就是"这一个 token 对整句话所有 token 的注意力分布"**。

2. **`/√d_k`（缩放）**：d_k 是每个头的维度。点积会随维度变大而数值变大，进入 softmax 的饱和区（梯度消失）。除以 √d_k 把它拉回一个数值合理的区间，稳定训练。**别小看这一小步——去掉它，深模型很容易训不动。**

3. **`softmax(·)`（归一化成权重）**：把一行打分变成"和为 1 的非负权重"，于是每个 token 输出的是"整句话所有位置 V 的加权平均"。**注意力不是"挑一个最相关的看"，而是"按相关度做一次软加权"**——这才是它能捕捉长距离、模糊依赖的原因。

4. **`· V`（加权求和）**：用权重把 Value 加起来，得到这个 token 的新表示——**"我关注的那些位置，把它们的语义按关注度混合进我"**。

**多头注意力（Multi-Head）** 就是把上面这件事并行做 h 次（每组各自有 W_Q/W_K/W_V），再把 h 个头拼起来过一个 W_O。**为什么多头**：单头只能捕捉一种"相关"模式；多个头允许不同的头关注**句法、指代、位置、语义**等不同关系，拼起来表达能力更强。工程上 h 通常取 32~128 不等。

**注意力数值直觉：3 个 token 的手算例子。** 用一个极简的 3-token 句子（`猫 / 坐在 / 垫子上`），单头、维度 d_k=2，把注意力完整走一遍：

> **输入 X**（3 个 token，每个 2 维）：
> - x₁ 猫 = [1, 0]
> - x₂ 坐在 = [0, 1]
> - x₃ 垫子上 = [1, 1]
>
> **投影矩阵**（W_Q, W_K, W_V 都是 2×2，这里取简单值演示）：
> - W_Q = [[1, 0], [0, 1]]（恒等，Q = X）
> - W_K = [[1, 0], [0, 1]]（恒等，K = X）
> - W_V = [[1, 0], [0, 1]]（恒等，V = X）
>
> **第一步：算 Q·Kᵀ（3×3 注意力分矩阵）**
> Q·Kᵀ = X·Xᵀ =
> 「猫·猫=1  猫·坐=0  猫·垫=1」
> 「坐·猫=0  坐·坐=1  坐·垫=1」
> 「垫·猫=1  垫·坐=1  垫·垫=2」
>
> **第二步：除以 √d_k = √2 ≈ 1.414**（缩放，防止 softmax 饱和）
> 分数矩阵 ≈
> 「0.707   0      0.707」
> 「0      0.707   0.707」
> 「0.707  0.707   1.414」
>
> **第三步：softmax 归一化（按行）**
> 以第 1 行为例：exp(0.707)≈2.028, exp(0)=1, exp(0.707)≈2.028，和≈5.056
> 权重 = [2.028/5.056, 1/5.056, 2.028/5.056] ≈ **[0.40, 0.20, 0.40]**
>
> 解释：**"猫"这个位置把 40% 注意力放在自己身上、20% 放在"坐在"、40% 放在"垫子上"**——因为"猫"和"垫子上"的向量更相似（都有第一个维度=1），所以互相"看"得多。这就是注意力的直觉：**相似的向量互相关注。**
>
> **第四步：用权重加权 V**
> 输出₁ = 0.40 × [1,0] + 0.20 × [0,1] + 0.40 × [1,1] = [0.80, 0.60]
>
> 原来"猫"是 [1, 0]，经过注意力后变成了 [0.80, 0.60]——**它把"坐在"和"垫子上"的语义按关注度混进了自己**。这就是"上下文理解"的最底层形状：每个 token 的表示都被全句其他 token 按相关度加权混合了一遍。

从这个手算里你能得到三个深层直觉：**① 注意力的本质是"按相似度加权混合"**——不是"挑选"，是"软混合"；**② 相似度是向量空间里的点积**——这和你 RAG 里的余弦相似度是同族运算；**③ 注意力分矩阵是 n×n 的**——序列越长，这个矩阵越大，计算和显存都平方增长——这直接引出了下一节的 KV cache。

### 2.3 位置从哪来：RoPE 让"次序"编码进向量

注意力本身是**对位置不敏感的**——把一句话里的词全打乱，QK^T 的结果会变（因为向量不同），但**"谁在第几个位置"这个次序信息没有被显式编码**。于是必须有**位置编码（positional encoding）**补上。

早期用**正弦位置编码**（sinusoidal）：给第 m 个位置加一个固定频率的向量。现代主流——尤其你要能看懂开源模型配置的——是 **RoPE（旋转位置编码）**：

> RoPE 不"加"位置向量，而是**把 Q 和 K 按位置 m 旋转一个角度**。于是 Q·K 的点积结果里自然带入了 (m−n) 的**相对位置差**，让注意力对"相对距离"敏感、对"绝对位置"不敏感。

旋转角度由一组几何衰减的频率给出：

```
θ_i = base^(−2i/d)，  常取 base = 10000， i 走遍每个维度对
```

**对你的工程意义**：RoPE 是"可外推上下文"的关键杠杆——通过调整 base 或内插位置尺度，可以在不重训的情况下把窗口从 4k 拉到 32k/128k。**你看到模型卡上写"支持 128k 上下文、基于 YaRN/RoPE 外推"，读到这里你就知道它在操作什么了。** 这也是为什么"上下文长度"不是铁板一块的参数，而是一个能通过位置编码技巧调的东西。

### 2.4 代价：计算 O(n²)，显存要靠 KV cache 省

"一次看清全句"的代价是实打实的，两个数你该会算：

**计算复杂度 O(n²·d)**：对 n 个 token，注意力分矩阵是 n×n——**序列长度翻一倍，注意力这一步的计算量翻四倍**。这就是为什么长上下文"贵",而且不是线性地贵。你的 RAG 正是靠"只喂相关的那几条"来躲开这个 n²（第 25 讲混合检索的初衷之一）。

**显存靠 KV cache**：自回归生成时，每一步都只新预测一个 token，但注意力要重复"算新 token 和所有旧 token 的相关度"。如果每步都重算所有 K、V，就是灾难性的重复。**KV cache 把已经算过的每层 K、V 缓存下来，新步只算新 token 的 K、V，再和缓存的旧 K、V 拼起来**。代价是缓存本身要吃显存：

```
KV cache 显存 ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 每个参数的字节数
```

（2 = K 和 V 两份；batch=1 时）。**这一条直接把"上下文长度"翻译成了"显存预算"**：同样一张卡，层数越深、头越宽，能塞下的 context 就越短。于是第 12 讲三层漏斗、第 44 讲准入分层投放，都不是"洁癖",而是在这条显存公式上做预算分配。

**KV cache 显存手算例题：Llama 3 家族的真实账本。** 把真实模型参数代入公式，你就能算出"长上下文到底有多贵"。先给三个典型模型的配置（简化版）：

| 模型 | 层数 L | 头数 h | 头维度 d_head | d_model | 参数量（约） |
|---|---|---|---|---|---|
| Llama 3 8B | 32 | 32 | 128 | 4096 | 8B |
| Llama 3 70B | 80 | 64 | 128 | 8192 | 70B |
| DeepSeek-V3（激活） | 61 | 128（GQA） | 128 | 7168总/37B激活 | 671B总/37B激活 |

**以 FP16 / BF16（每个参数 2 字节）为例，手算 KV cache：**

> **例 1：Llama 3 8B，4K 上下文**
> KV = 2 × 32层 × 32头 × 128维 × 4096序列 × 2字节
>    = 2 × 32 × 32 × 128 × 4096 × 2
>    = **2 GB**
>
> **例 2：Llama 3 8B，128K 上下文**
> KV = 2 × 32 × 32 × 128 × 131072 × 2
>    = **64 GB** ← 刚好塞爆一张 A100 80G 的大半显存
>
> **例 3：Llama 3 70B，4K 上下文**
> KV = 2 × 80 × 64 × 128 × 4096 × 2
>    = **10 GB**
>
> **例 4：Llama 3 70B，128K 上下文**
> KV = 2 × 80 × 64 × 128 × 131072 × 2
>    = **320 GB** ← 需要 4 张 A100 80G 才能装下纯 KV cache（还没算模型权重）

**这个手算直接解释了三件工程事实**：① 为什么 70B 模型跑长上下文要用张量并行（多张卡分摊 KV）；② 为什么 GQA / MLA 是刚需——把 KV 头数砍到 1/8 甚至更多，显存直接按比例降；③ 为什么"上下文压缩"是真的在省钱——把 128K 压到 8K，KV cache 直接省 16 倍，这是纯物理的减法。

**工程判据**：**评估一个长上下文方案的成本，先算 KV cache 显存——它是线性增长的（n 序列长度），比注意力计算的 n² 在推理阶段更占大头。** 你的系统里"上下文预算"这个词不是比喻，是 GPU 显存账单。

### 2.5 这一讲如何串起 M9 与你的系统

| 本讲概念 | 连到哪 |
|---|---|
| Q/K/V + softmax 软加权 | 解释"相关度"为何是连续的、可排序的（第 25/27 讲相似度同源）|
| 注意力分矩阵 n×n | 计算 O(n²) → RAG 只喂相关条目的动机 |
| RoPE 相对位置 | 长上下文外推的 lever，理解模型卡的 128k 由来 |
| KV cache 显存公式 | 上下文窗口 = 显存预算，第 12/44 讲的存在理由 |
| token 都要喂进去 | 第 32 讲成本计量（token 即成本）|

**这一讲把第 55–57 讲的碎片桥到一起**：词向量（57）进入模型 → 注意力（58）让它们彼此的语义在一个窗口里被"看全" → 然后在第 55 讲的"预测下一个 token"里被用到。**而"看全"的两个代价（O(n²) 计算 + KV cache 显存）是你在 M4 里为上下文做的所有工程的物理根源。**

**判据句（本讲收口）**：**模型理解上下文的"聪明"（并行全局注意力）与它的两个固有成本（平方计算、KV 显存）是同一件事的两面——任何"提高上下文利用率"的手段（压缩、检索、分层、位置外推）都在对冲这两个成本，而不是在优化一个可有可无的参数。**

### 2.6 前沿深挖：2023–2025 年架构演进的三条主线——长上下文、KV cache、MoE

Transformer 的"骨架"没变，但 2023 年后三件工程大事都围绕**把注意力的成本和上下文长度往极致推**：

**① 位置编码的外推：从 NTK 到 YaRN。** RoPE 在训练长度外直接外推会崩（分布偏移）。**YaRN**（[arXiv:2309.00071](https://arxiv.org/abs/2309.00071)）的解法是**按维度分段处理**：高频维度接近直接外推、低频维度保留插值稳定性，再加温度缩放补偿。**工程上这意味着"4K 训练的模型扩到 128K"不再需要全量重训**——Llama / Qwen 的长上下文版本都用这类插值方案。你看到的"某模型支持 1M context"，背后几乎都是 RoPE 插值 + 少量长文微调，而不是从头训一个 1M 窗口。

**② KV cache 的压缩：MHA → GQA → MQA → MLA。** 第 2.4 节算了 KV cache 的账，业界这几年就在砍这笔账：GQA/MQA 让多个 query 头共享 K/V（Llama 3 全系用 GQA）；DeepSeek-V2/V3 的 **MLA（Multi-head Latent Attention）** 走得更远——**把 K/V 压缩到一个低维 latent 向量缓存，推理时缓存的是压缩态**（[DeepSeek-V3 技术报告，arXiv:2412.19437](https://arxiv.org/abs/2412.19437)）。同样显存下能塞的上下文长度成倍增长，这是 DeepSeek 能把 API 价格打到地板的结构性原因之一。再看推理框架侧：**vLLM 的 PagedAttention**（[arXiv:2309.06180](https://arxiv.org/abs/2309.06180)）把 KV cache 按固定大小 block 分页管理、消除显存碎片并支持跨请求共享——操作系统虚拟内存的思想原样搬进了 GPU。**FlashAttention**（v3：[arXiv:2407.08608](https://arxiv.org/abs/2407.08608)）则从另一个角度出手：不改算法改 kernel，用分块计算+异步低精度把 attention 的显存带宽压力压下去。三者叠加，才把"百万 token 推理"从论文搬进账单。

**③ MoE：用稀疏激活换参数规模。** Mixture-of-Experts 让每个 token 只激活全部专家的一小部分——总参数巨大、单 token 计算量可控。DeepSeek-V3 的 **Node-Limited Routing** 限制每个 token 发往的节点数来压通信成本。**对你的工程含义：MoE 模型的"激活参数"（如 37B）而非总参数（671B）决定单次推理成本**——看模型规格书时别把这两个数搞混。

**接回你的系统**：这三条线共同回答了一个问题——"为什么 2024 年后长上下文模型又便宜又快"。理解了 MLA + PagedAttention + 插值外推，你就明白第 44 讲"上下文压缩"省下的每一个 token 真实值多少钱：**它省的不是抽象额度，是 KV cache 的显存和 attention 的 FLOPs。**

- [ ] **别"多多益善"地塞上下文**——塞得越多，噪音与成本一起涨，还未必聪明（第 44 讲）。

- [ ] **解释"为什么窗口这么小"要用注意力代价**——而不是含糊地说"厂商限制"。
- [ ] **"相关度"概念与注意力同源**——理解这点，你对第 25/27 讲相似度会更笃定。

- [ ] **KV cache 显存要亲手算一遍**——层数×头数×头维度×序列长度×字节数×2，把结果和你实际显存预算对一对，别等到 OOM 才发现上下文窗口设大了。
## 四、动手任务

> **目标**：用"注意力=一次看全句+全 token 驻留"，解释并优化你上下文的使用。

**步骤 1：解释你的窗口策略**

用本讲的代价观，解释你当前上下文窗口设置：**为什么是这个大小？它对应多少 token 成本？** 答不上来，说明窗口只是"抄了个默认值"。

**步骤 2：按"稀缺"重审一次上下文**

挑一次长上下文使用场景，用第 44 讲的"准入+分层+投放"重新设计，说明**每一个放进上下文的 token 都要有理由**。

**步骤 3：量化 token 成本**

打开你的计费（第 32 讲），算一次"核心对话"大概吃掉多少 token、多少钱。**把"成本"和"注意力要驻留全部 token"这两件事对上。**

## 本讲小结

1. **Transformer 的核心是注意力机制**——每个位置一次直接看全句，突破旧模型一步传一步的局限。
2. **代价是全部 token 必须同时驻留**——上下文窗口因此是物理硬上限，上下文因此稀缺。
3. **你在 M4 做的上下文工程，是在驯服这个固有成本**——压缩/检索/分层是对冲，不是可选项。
4. **"相关度"与注意力同源**——RAG 相似度是同一个"找相关"思想的检索版。
5. **上下文管理要按"稀缺资源"来**——每个进来的 token 都要有理由、要算账。
