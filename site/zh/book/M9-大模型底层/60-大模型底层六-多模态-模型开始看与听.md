## 一、痛点

你在 `waterdrop-ad-agent` 里处理过视频生成候选链，在 `code-review-agent` 里给模型配过 `supports_vision`——但有没有想过那背后的原理：**"模型凭什么能看图？为什么有的模型不能看？"**

两个错误认知：

**错误一："多模态就是把图片也当输入，反正都是喂东西。"** → 你把"看图"当成"多输入一个文件",没看到图片进模型前还要**变成向量**这一道关键转换。于是设计 Agent 时想当然"把图丢给它就行"。

**错误二："模型能看图 = 真的会看图，跟人一样。"** → 你高估了"视觉理解",以为它能像人一样"看懂"复杂画面、推理"画面里没说的事"。→ 但第 55 讲已经立下底线：它仍是"预测下一个 token",只是这些 token 可能来自图像。

本讲要破除的是"多模态=直接喂文件" 和 "能看图=真会看图"两个错觉。真相是：

> **多模态模型把文字、图像、音频分别编码成**同一种向量表示**（视觉编码器 + 对比学习对齐），送到同一个 transformer 里，从而让模型"用处理文字的方式"去理解和生成图像。但它不是真的『看见』，它仍是第 55 讲那个『预测下一个 token』——只是把图像也变成了可预测的一串 token。** 这决定了它在"看图"上的能力范围与局限，也决定了你为什么要在工程上做 `supports_vision` 的分层。

## 二、原理

### 2.1 图像怎么变成 token：Vision Transformer 的 patch 编码

第 57 讲讲"词变向量"——每个词查一张词表，变成一个向量。图像没有"词表"，所以要走一步**"把图切成块再当词"**，这就是 **Vision Transformer（ViT）** 的核心：

1. **切块（patchify）**：把一张 H×W×C 的图（C 是通道，通常 RGB=3）切成若干个 **P×P 的方块（patch）**。每个 patch 就像文本里的一个"词"。
2. **展平 + 线性投影**：每个 patch 的像素值被展平成一维向量，再过一个线性层 W，映射到模型维度 d——**这就是这个"视觉 token"的初始向量**（对应第 57 讲词向量的"查表嵌入"）。
3. **加位置编码 + 分类 token**：和文本一样，补一个位置编码（第 58 讲），并常在开头加一个特殊的 `[CLS]` token 承载整图语义。然后这一串向量进 transformer。

**一条你必须会心算的公式**——一张图是多少个 token：

```
token 数 ≈ (H/P) × (W/P) + 1（分类 token）
```

代数字进去，感受这个量级：

```
224×224 的图，patch=16×16：
  (224/16) × (224/16) + 1 = 14 × 14 + 1 = 197 个视觉 token
```

**这两行数字对你的工程是硬约束**。ViT 标准配置 patch=16，分辨率越高、patch 越小，token 就越多：

| 分辨率 | patch | 视觉 token 数 |
|---|---|---|
| 224×224 | 16×16 | 197 |
| 512×512 | 16×16 | 1025 |
| 1024×1024 | 16×16 | 4097 |
| 224×224 | 14×14（更高密度） | 257 |

一张高清图动辄**上千 token**，而一段文字可能只要几十 token。**这就是为什么"看图"特别贵**（呼应第 32 讲的成本计量）——它本质是"塞进了上千个词"。所以工程上要"能少用多模态就少用"。

**ViT 参数量手算：从 patch 到视觉编码器的完整账。** 你已经会算 token 数了，再往前走一步，就能估算一个视觉编码器有多大。以 ViT-Base（最经典的基线配置）为例：

> **配置**：输入 224×224×3，patch=16×16，模型维度 d=768，层数 L=12，头数 h=12
>
> **第一步：patch 投影（把像素映射到 d 维）**
> 每个 patch 的像素数 = 16 × 16 × 3 = 768
> 投影矩阵 W_patch 的参数量 = 768 × 768 = **590K**
> （768 像素 → 768 维，刚好是一个方阵投影）
>
> **第二步：位置编码**
> token 数 = 196 + 1(<[BOS_never_used_51bce0c785ca2f68081bfa7d91973934]>) = 197
> 位置编码参数量 = 197 × 768 = **151K**
>
> **第三步：一个 Transformer 编码器层的参数量**
> - 自注意力：Q/K/V 投影各 768×768 = 3 × 768² = **1.77M**，加输出投影 768² = 0.59M，共约 **2.36M**
> - MLP：通常是 4× 膨胀 → 两个线性层：768×3072 + 3072×768 = **4.72M**
> - LayerNorm 两个，可忽略
> - 每层总计 ≈ **7M** 参数
>
> **第四步：12 层总参数量**
> 12 × 7M ≈ **86M**
> 加上 patch 投影和位置编码 ≈ 0.75M
> ViT-Base 总参数量 ≈ **86M**
>
> **对照**：ViT-Large（L=24, d=1024, h=16）≈ 307M；ViT-Huge ≈ 632M。

**这个手算给你两个工程直觉**：① **视觉编码器的参数量和文本编码器在同一量级**（ViT-Base 86M ≈ 一个小语言模型），所以"加一个视觉编码器"不是加个小插件，是加了**一整个模型**；② **patch 大小决定 token 数，token 数决定计算量**——把 patch 从 14 加到 16，token 数从 257 降到 197，计算量直接省 23%，这是视觉模型里最划算的旋钮之一。

### 2.2 图和文怎么对齐进同一个空间：CLIP 对比学习

光把图变成 token 还不够——**要让"图 token"和"词 token"进同一个语义空间**，模型才能"看图说话"。**CLIP** 是这背后的关键方法，它用**对比学习（contrastive learning）**把图文拉进同一个向量空间：

- 训练数据是**海量的 (图像, 配文) 对**。
- 训练目标是：**让配对的图文向量"彼此靠近"，不配对的"彼此推开"**。具体用 **InfoNCE 损失**——对每一对正确的图文，在整批样本里"挑出"它来。

```
L = − (1/N) Σᵢ log [ exp( sim(vᵢ, tᵢ)/τ ) / Σⱼ exp( sim(vᵢ, tⱼ)/τ ) ]
```

- `vᵢ` / `tᵢ`：第 i 张图的向量 / 第 i 段文本的向量；
- `sim(·,·)`：余弦相似度（第 57 讲的 cos）；
- `τ`：温度参数（第 55 讲的采样温度同一个"温度"家族，控制分布的锐利度）；
- 分母对所有 j 求和——**逼模型在"一个 batch 里把所有非配对的都判为负样本"**。

**一句话读这条式子**：让"正确的图文对"的相对相似度尽可能大——这和第 55 讲 softmax、第 56 讲交叉熵是同一套"拉大正确项、压低错误项"的结构。**训练完，图像向量和文字向量就在同一个空间里可比了**——这正是"用处理文字的方式处理图像"的技术底座：不是把图当文件，而是把图**映射成了文字空间里的一个点**。

### 2.3 图文怎么融合进 LLM：三条路线

有了"图 token"和"文字空间对齐",还差最后一步：**怎么把视觉 token 塞进一个本来是纯文本的 LLM**。有三条主流路线，各有代价，读懂它们你才能判断一个多模态模型"大概是什么架构"：

> **图 60-1**　图文融合的三条路线：LLaVA 式用一个小 MLP 把视觉 token 投影到 LLM 输入空间（参数最少、当下开源主流）；Flamingo 式冻结 LLM、插入交叉注意力层专项看图；早期融合最直白但跨模态对齐最弱。它们共同的结论是——**"看图"是有额外架构成本的，不是所有模型都付了这个价**。

- **MLP 投影（LLaVA 式）**：视觉编码器 → 一个**线性/MLP 适配器**把视觉 token 映射到 LLM 的输入维度 → 和文本 token 拼一起进 LLM。**参数最少、训练最省，是当前开源多模态模型的主流**。
- **Cross-Attention（Flamingo 式）**：冻结 LLM，在它中间**插入交叉注意力层**，让语言 token 去"查询"视觉 token。**LLM 主体不动，只在需要时"看"一眼图**——但架构改动大、工程复杂。
- **早期融合**：图 token 和词 token 在输入层直接拼接，靠 transformer 自己学跨模态。**最直白，但无显式对齐机制，效果通常不如前两者。**

三条路线的**共同工程含义**：**"看图"不是免费的插件**——要么加适配器、要么改架构、要么付训练成本。这直接解释了你项目里那条铁律为什么成立：**模型支不支持视觉，是一个必须显式建模（`supports_vision`）的能力边界，而不是"反正丢进去试试"。**

### 2.4 但它仍是"预测下一个 token"，不是"真看见"

守住第 55 讲的底线，就明白了多模态的**局限来源**：

> 模型处理完视觉 token 之后，还是要**预测下一个 token**（不管是文字回答，还是继续生成图像/视频的 token）。它的"视觉理解"受限于"它学到的图像统计规律"（CLIP 只教了"图文配对",没教"画面里的因果与常识"），因此：
> - 它能"看到"很多细微之处（因为训练见过海量图像）；
> - 但它**没有真正的视觉推理**，复杂画面里需要"人脑补"的东西它仍可能推错。

这对你的工程有直接含义——**不要把"模型看过图"当成"模型真的理解了这图"**，尤其在做视觉相关 Agent 评测时（呼应第 40 讲）。第 60 讲的"判据句"和第 58 讲的上下文窗口、"第 55 讲预测 token"是同一根线：**能力有边界，你要显式建模边界而不是赌。**

### 2.5 工程现实：不是所有模型都支持看图

多模态能看图，**但这不是免费的、也不是所有模型都有**。这就解释了 `code-review-agent` 里为什么要有 `supports_vision`：

- **`supports_vision=true`**：模型支持看图，可以把图像作为输入直接喂给模型。
- **`supports_vision=false`**：模型不支持，直接喂会 400（"This model does not support image"）——**所以要用本地 OCR（macOS Apple Vision）把它先转成文字再送**，而不会硬喂图片报错。

这条你在项目记忆里固化过的铁律（"不支持视觉的模型先走本地 OCR"），**根就是多模态的"支持与否是模型能力的一种边界"**。它和第 24 讲"维度是三方契约"是同一类：**模型的能力边界是你系统必须显式建模（用一个标志）的东西，不能隐式赌它有。**

**判据句**：**凡是跨模态的 Agent，都要显式区分『这个模型支不支持这个模态』，并对不支持的情况给替换路径（如 OCR）——能力边界要建模，不能赌。**

### 2.6 前沿深挖：2024–2025 多模态的两个工程拐点——动态分辨率与 sigmoid 对比

**① 固定分辨率死了：Qwen2-VL 的 Naive Dynamic Resolution。** 早期 VLM 把任意图片缩放到固定 224/336 再切 patch——小字票据、长截图被压成浆糊。**Qwen2-VL**（[arXiv:2409.12191](https://arxiv.org/abs/2409.12191)）的 Naive Dynamic Resolution 让**任意分辨率图像映射为可变长度的 visual token 序列**，并配套 **mRoPE**（多模态 RoPE，把位置编码拆成时间/高/宽三个通道）。**Qwen2.5-VL**（[arXiv:2502.13923](https://arxiv.org/abs/2502.13923)）进一步加上**绝对时间编码**，能对数小时视频做秒级事件定位。**工程含义：视觉 token 数不再是常数，而是随图片分辨率浮动——你的 token 预算公式（第 44 讲）在多模态场景必须改成"按图估算"而非按固定值。**

**② CLIP 的 softmax 对比正在让位给 sigmoid。** CLIP 用 InfoNCE（softmax 对比），batch 内归一化带来大 batch 依赖。**SigLIP 系改用 sigmoid 对比损失**，损失不再依赖 batch 内其他样本，训练更高效、小 batch 也稳；**SigLIP 2**（[arXiv:2502.14786](https://arxiv.org/abs/2502.14786)）又叠加了 decoder-based 预训练、自监督损失与主动数据筛选，成为 2025 年后新 VLM 的主流视觉编码器选型。**选型判据：新起一个多模态项目，视觉编码器先看 SigLIP 2 / 国产同代编码器，别再默认 CLIP-ViT-L。**

**③ 视觉 token 压缩是下一个成本战场。** 高分辨率动态化后，一张图动辄上千 visual token，LLM 侧上下文压力陡增。业界的对冲是视觉 token 压缩（池化、Q-Former 式查询压缩、按信息量筛选）——本质上和文本侧的上下文压缩（第 44 讲）是同一场战争的两个战场：**一切进 LLM 的东西都是稀缺预算，无论它来自文字还是像素。**

**接回你的系统**：第 2.5 节讲"不支持视觉的模型要先 OCR 再进上下文"，在动态分辨率时代依然成立，而且更要算清账——**一张高分辨率截图进支持视觉的模型可能吃掉几千 token，比 OCR 出的文本贵得多；成本和精度要按场景权衡，不是"能看图就一定看图"。**

> - Qwen2.5-VL 技术报告（绝对时间编码/长视频定位）：[arXiv:2502.13923](https://arxiv.org/abs/2502.13923)

## 三、避坑清单

- [ ] **别把"看图"当"喂个文件"**——图像要先变"视觉 token"进向量空间，不是所有模型都做了这一步。
- [ ] **别把"能看图"当"真会看图"**——它仍是预测 token，没有真正的视觉推理。
- [ ] **用 `supports_vision` 显式建模模型能力边界**——不能隐式赌它支持。
- [ ] **不支持视觉的模型，先本地 OCR 转文字再送**——而不是硬喂图片报 400。
- [ ] **为"看图"单独算 token 账**——一张 224×224 就是 ~197 个视觉 token，高清图上千，别把它当"一个文件"的成本。
- [ ] **视觉 Agent 评测要对"看的局限"设预期**——别把模型"看过图"当"真懂图"。

- [ ] **接入视觉模型前先过三张验图**——文字截图、含图表的界面截图、真实场景照片，三张都符合预期再上线，别只测了第一种就以为"能看图"。
## 四、动手任务

> **目标**：用"模态统一在向量层 + 能力边界要建模 + 图 token 是真成本"重审你的视觉/多模态处理。

**步骤 1：显式列出每个模型的模态能力**

为你系统接入的每个模型列一张**模态能力表**：支持文本/图像/音频？对应 `supports_vision` 怎么配的？没有这张表，就是你在隐式赌。

**步骤 2：给"不支持"留替换路径**

挑一个模型不支持视觉的路径，确认它有**本地 OCR 兜底**（把图先转文字），而不是跑着跑着 400。

**步骤 3：按 token 账审查一次视觉任务**

挑一个你依赖模型"看图"的任务，先心算它**一张图吃多少 token**（patch 公式），再评估它是否**真需要视觉**，还是 OCR/文字信息就够——**能少用多模态就少用**，既省钱（第 32 讲）又少踩"看错"的坑。

## 本讲小结

1. **多模态 = 文字/图像/音频统一成向量，进同一个 transformer**——用处理文字的方式处理图像。
2. **ViT 把图切成 patch 当"视觉词"**——224×224 的图 patch=16 就是 ~197 个 token，这是"看图贵"的物理根源。
3. **CLIP 用对比学习（InfoNCE）对齐图文向量**——这才让图 token 和词 token 可比。
4. **它不是真的"看见"**——仍是预测下一个 token，视觉理解受限于模型的图像统计规律。
5. **支持与否是能力边界**——要用 `supports_vision` 显式建模，不支持时走本地 OCR 兜底。
