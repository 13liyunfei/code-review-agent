## 一、痛点

你读完前面 61 讲，已经**亲手建了一个 Agent**——有工具、有记忆、有多 Agent 协作、有 Harness 六大机制。这让你处在一个微妙的境地：

面对"LangChain / LangGraph / DeepAgents"这些名字，你会有两种不适：

**不适一："我是不是应该用框架而不是自己写？"** 你开始怀疑自己没跟上"主流",觉得"真懂 Agent 的人都会用 LangChain"。→ 但你刚建的东西是**针对特定审查场景、能指着行号讲清每个决定**的真实系统；框架是**通用打包**。这两者不冲突，冲突的是你想用"用没用框架"来判定能力。

**不适二："反正我不会用 Python，这些框架跟我无关。"** 假如你的技术栈是 Java，你可能直接关掉这些名字。→ 但它们的**设计取向**（链 vs 图 vs 多 Agent）跟你**怎么编排**Agent 完全同源，读懂它们能反过来帮你审视自己的编排。

本讲要建立的，是**第三条路**：

> **Agent 框架不是敌人也不是圣物——它是『把六大 Harness 机制打包成开箱即用』的产物。你看它们的方式，不应该是『要不要改用』，而是『它把六大机制堵成了什么样、那个取向适不适合你的场景』。** 这样读，LangChain/LangGraph/DeepAgents 就成了你审视自己系统的三面镜子，而不是三个门槛。

## 二、原理

### 2.1 框架到底替你打包了什么

拆开任何一个 Agent 框架，你会发现它不是"新东西"，而是**把你在前 61 讲建过的机制打包**成了接口：

| 框架的组件（常见命名）| 对应你已建的机制 |
|---|---|
| LLM 调用封装 | M1 模型调用 / token-factory |
| Tool / Function 定义 | M2 工具系统 / `ToolRegistry` |
| Memory / 会话记忆 | M2 记忆 / 第 10、47 讲 |
| Chain / Agent loop | Agent 循环（第 8 讲）|
| 多 Agent 编排 | M3 多 Agent 协作 / `CompletableFutureCoordinator` |

**关键认知**：你用 `agent-kit` 建的 `ToolRegistry`、`TaskPlanner`、`CompletableFutureCoordinator`，和 LangChain 的 `Tool`、`Planner`、`AgentExecutor`、LangGraph 的 `Graph/Node/Edge`，**是同一套抽象的不同命名**。你"自己写"不是"没有框架",而是**为一个具体场景手搭了轻量编排**；框架则是**可复用的通用编排**。

### 2.2 三个框架的"设计原语"各是什么

上一节的表格还停在"机制对应"。有架构背景的你，必须再下一层——**问每个框架的核心抽象（设计原语）是什么**，因为"原语"决定了它能表达什么、不能表达什么：

| 框架 | 核心原语 | 它把编排表达成什么 | 一句话定位 |
|---|---|---|---|
| **LangChain** | **Runnable（可运行件）** | `prompt \| llm \| parser` 用管道串起来 | 把步骤抽象成可组合的**链** |
| **LangGraph** | **StateGraph（带状态的图）** | 节点 + 边 + **共享 State** + checkpointer | 把流程抽象成**有状态、可回退的图** |
| **DeepAgents** | **Main Agent + Subagents** | 一个主 Agent 调度多个**上下文隔离**的子 Agent | 把任务抽象成**可拆分的多 Agent** |

三个原语的差别，就是你判断"该用哪个"的底层依据：

- **Runnable**：强调**可组合、可复用**（每个步骤是独立可测的件，管道负责串）。代价是**默认只有顺序**，回退/循环要靠额外机制补。
- **StateGraph**：强调**状态显式、路径显式**（谁能到谁、共享什么状态、怎么持久化）。代价是**概念更重**，小流程还用链更省。
- **Main+Subagents**：强调**上下文隔离与分工**（每个子 Agent 只看到它该看的）。代价是**协调与通信成本**。

**这条路你怎么看**：你的 `CompletableFutureCoordinator` 从"原语"上最接近**图**——它显式声明了"5 个 Agent → 汇聚 → 仲裁分支"，只是你用手写的 future + 状态机表达了这个图。**选择原语，不是选框架，是选"你的流程本质上是链、是图、还是多 Agent"。**

### 2.3 三个框架把"六大机制"分别堵成了什么

不满足于贴标签，再落到每个框架对"六大 Harness 机制"的**具体落点**（这些名字值得你记住，面试拆框架时用得上）：

| Harness 机制 | LangChain 的落点 | LangGraph 的落点 | DeepAgents 的落点 |
|---|---|---|---|
| 模型调用 | `ChatModel` 封装 + LCEL 调用 | 作为图节点里的模型调用 | 主/子 Agent 各自的模型 |
| 上下文/记忆 | `ConversationBuffer/SummaryMemory` 等内存对象 | **Checkpointer**（状态持久化到线程级检查点） | **子 Agent 上下文隔离**（每个只见自己的上下文） |
| 工具 | `Tool` + `@tool` 装饰器 | 工具作为**节点**，用条件边决定调不调 | 子 Agent 各自绑定自己的工具集 |
| 权限 | 基本未内建，靠调用方自包 | `interrupt()` **人机确认**回插 | 子 Agent 作用域隔离（权限=边界） |
| 编排 | `Chain` / `AgentExecutor`（ReAct 循环） | 图：节点/边/条件边/环 | 主 Agent 调度（handoff/supervisor） |
| 技能 | 无原生的"技能"概念（用 chain 拼） | 子图/可复用节点 | 子 Agent 本身即"能力封装" |

**记住这张表的用法**：任何一个框架摆到你面前，你都能把它的组件名**映射回这张表**，看它"哪几个 Harness 机制做得重、哪几个做得轻甚至根本没有"。**重重地做在编排上、却对权限/技能几乎不内建**——这种分布本身就是一份"它把哪些控制权留给了你"的答案。

### 2.4 别被 marketing 带走：抽象的成本也要算

**框架的抽象是"有代价的好处"**。它在入口处替你省掉"重写通用编排"，但在深处藏了一个代价——**隐式魔法**：

> 框架替你做的每一步（链怎么跳、状态怎么存、工具怎么绑），如果你没读懂它的默认行为，出问题时你排查的就不再是自己的代码，而是**一个你半懂不懂的框架内部**。

这就是 M7 判断力的用武之地：**你对六大机制的"对不对"有独立判断，才不会被框架的默认值反噬**（例如"它的默认记忆其实是无限累加、会爆 token"——对应第 44 讲）。**用框架的正确姿势，永远是你先懂机制，再用框架提速；而不是用框架替代理解。**

**判据句**：**看任何 Agent 框架，先问『它把六大 Harness 机制（模型调用 / 上下文 / 工具 / 权限 / 记忆 / 技能）堵成了什么、默认值是什么、我怎么覆盖』，再把『抽象替我省的』和『抽象藏起来的』一起算，而不是被它的包装与生态热度带走。**

具体问四个问题，就能快速给一个框架"定位"（无论它多花哨）：

1. **循环**：它默认是"调一次"还是"闭环循环"？（对应第 8 讲）
2. **工具**：工具怎么声明、怎么校验、怎么防越界？（对应第 45/51 讲）
3. **记忆/上下文**：它怎么处理长上下文？（对应第 44/47 讲）
4. **多 Agent**：它默认单 Agent 还是支持编排？编排是星型还是图？（对应第 15 讲）

**这四个问题，就是你在 M7 建好的 Harness 判断力，直接拿去读任何框架。** 有这把尺子，LangChain 不神秘，DeepAgents 也不吓人。

### 2.5 前沿深挖：2025 年框架战争的真正变量——协议分层与大厂重写潮

框架地图之外，2025 年有两个结构性变化必须补进你的认知：

**① 协议层的出现把"框架竞争"变成了"分层卡位"。** **MCP**（Anthropic 主导，模型↔工具）与 **A2A**（Google 主导，Agent↔Agent，JSON-RPC 2.0 over HTTP + Agent Cards 能力发现，0.3 版加 gRPC 与签名安全卡片）把生态切成三层：**工具接入层（MCP）、Agent 互联层（A2A）、编排层（LangGraph/CrewAI/AutoGen 等）**。框架的竞争焦点从"谁的 API 好"变成"谁在协议层卡住了位"。**对你的架构判据：自建系统对接外部生态时，优先实现协议（MCP server/client）而不是绑定某个框架的 SDK——协议是公共地板，框架是私人家具。**

**② 大厂的"重写潮"说明第一版抽象全错了。** 微软 **AutoGen 0.4**（2025）把 0.2 的对话式 GroupChat 推倒重写为**事件驱动 actor 框架（Core API）+ 上层 AgentChat** 的分层架构；**OpenAI 把 Swarm 收敛为 Agents SDK**（精简到 Agent/Handoff/Guardrail 三原语）；**LangChain 1.0**（2025-10）把"万物皆 chain"收敛为 agent loop + middleware。**三个头部玩家不约而同地从"丰富抽象"撤退到"最小内核"**——这是框架领域最贵的一课：**第一版的抽象几乎必然过度，能活下来的框架都是敢于删自己 API 的。**

**③ 一个数据点用来校准期望**：社区统计 MCP 公共 server 已达数千到上万量级、SDK 月下载量以千万计——但口径混杂（官方 registry / GitHub topic / 厂商报告各不相同）。**引用生态规模数据时，永远带上口径和来源。**

## 三、避坑清单

- [ ] **别用"用没用框架"判断能力**——你针对场景的轻量编排，不比换个框架更高贵/更低级。
- [ ] **看框架先拆六大机制**——别被 marketing 和生态热度带走，先问它堵成了什么。
- [ ] **LangChain/Graph/DeepAgents 是取向不是升级**——固定管线用链，有分支回退用图，多 Agent 才多 Agent。
- [ ] **别把框架的默认值当最佳实践**——它的默认记忆/权限可能不适合你，要按自己的判据覆盖。
- [ ] **算清"抽象的成本"**——框架藏起的隐式行为，会变成你未来的排查债；先懂机制再用框架。
- [ ] **读框架的四问**：循环 / 工具 / 记忆上下文 / 多 Agent——这是把 Harness 判断力用在任何框架上。

## 四、动手任务

> **目标**：用"六机制四问 + 原语判断"，把 LangChain 快速"定位"，并对照你自己的系统。

**步骤 1：用四问问 LangChain**

**步骤 3：给你自己的系统判"原语"**

用第 2.2 节的三个原语（Runnable / StateGraph / Main+Subagents），判断**你的 `CompletableFutureCoordinator` 本质最接近哪个**。这比"我该不该用 LangGraph"更有价值——它帮你对象化你已经在做的东西。

## 本讲小结

1. **Agent 框架 = 六大 Harness 机制的开箱即用打包**——不是魔法。

4. **看任何框架先问六机制**，别被 marketing 带走；**算清抽象藏起的成本**。
