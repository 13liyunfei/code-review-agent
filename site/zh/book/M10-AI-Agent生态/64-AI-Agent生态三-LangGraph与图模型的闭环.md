# 第 64 讲 · LangGraph 与"图模型"的闭环

> 🎯 导读问题：**"LangGraph 比 LangChain 强在哪？"** ——能答出"LangChain 是『链』：顺序步骤、一条道走完；**LangGraph 是『图』：把每一步变成节点，用边定义谁能到谁，支持条件分支、循环、回退（状态图上回退）**，所以它更像『Agent 循环』本身该长什么样"——就把两者的根本差别讲清了。**本讲判据：当你的流程出现『要回看、要分叉、要重试』，就从『链』升级到『图』——图的价值不在更花哨，在它把『闭环』做成了头等公民。**
> 🎯 进阶追问（面向系统架构师）：**"LangGraph 的 State / Reducer / Checkpointer 分别解决了编排里的哪三个真问题？"** ——能答出"**State** 是整张图共享的一份显式状态，节点读写它、条件边读它做判断——解决『状态藏在哪』；**Reducer** 定义『多个并发更新写同一个 key 时怎么合并』（如 add_messages 追加而非覆盖）——解决『并发汇合时的写冲突』；**Checkpointer** 把每个节点执行后的状态存成检查点，支持失败重放、时间旅行、断点续跑——解决『状态怎么持久化与恢复』"——这三个概念一报，架构师就知道你把图的并发与持久化都读透了。

## 一、痛点

上一讲我们看清了 LangChain 的"链"，也知道了它的边界——**默认不擅长闭环与回退**。这一讲看 LangGraph 之前，先回答大多数人卡住的两处：

**痛点一："LangGraph 就是换个名字的 LangChain 吧？"** 你听说 LangGraph 是同一家出的，于是以为只是"2.0"，换汤不换药。→ **它确实是同一家的，但模型从『链』换成了『图』**——这不是补丁，是根本换了编排的原语（顺序数组 → 有环的图）。把两者混为一谈，你会错过图模型真正解决的那个问题。

**痛点二："图听起来好高级，但跟我有什么关系？"** 你是 Java 系、自建系统，觉得 LangGraph 是 Python 世界的玩具。→ 但你第 8 讲那个"带工具的循环"、第 15 讲的 DAG/星型拓扑、第 17 讲的并行编排，**全都在做"让流程能分叉、能回退"这件事**。LangGraph 只是把这件事做成了框架原语，你完全能指着你自己的协作者去对照。

本讲要建立的是一把干净的尺子：

> **LangGraph 的价值不是『图比链更高级』，而是『把你的流程从一条道走到底，升级成显式声明谁能到谁、能分叉能回退』。它在做的，正是你第 8 讲那个『带工具的循环』和第 15、17 讲那个『拓扑 + 并行编排』，只是它们把『闭环』做成了图的第一等公民。** 读它，是在看一条比你手写更显式的路径；理解它，能反过来让你审视自己的 coord 是不是把闭环/分支写清楚了。

## 二、原理

### 2.1 从链到图：编排原语的升级

链（Chain）把任务切成**一串顺序步骤**；图（Graph）把这串步骤变成**一组节点 + 一组边**：

```
链：  Start → A → B → C → End            （顺序，一条道）
图：  Start → A → ? → B → ... → End      （边 + 条件，可分叉可回环）
                        ↑___循环回退___|
```

图模型的两件套是**节点（Node）**与**边（Edge）**：

- **节点**：一个可执行的步骤（一次模型调用、一个工具、一段逻辑）。
- **边**：显式说明"哪个节点完成后，可以走到哪个节点"。
- **条件边（条件分支）**：不是固定走到下一个，而是**根据上一步的状态/结果，决定下一步跳去哪**。

**关键**：边是**显式声明**的。你一眼能看出一张图"能走哪几条路、会不会成环、卡在哪"——这是链做不到的（链只能看顺序）。

**这条路你怎么看**：你在 `agent-kit` 的 `CompletableFutureCoordinator` 里写"并行跑 5 个 Agent → 各自完成 → thenCombine 聚合 → 按仲裁决定要不要补充/重试"，这**就是一张隐式的小图**：5 个 Agent 是 5 个输入节点，聚合是汇聚边，仲裁决定是条件分支。LangGraph 只是把这张"藏在你代码里的图"用 Node/Edge 显式画了出来。

### 2.2 图的"状态三件套"：State / Reducer / Checkpointer

有架构背景的你，看图最该问的是**三个真问题**，LangGraph 分别用三个概念给了标准答案：

**① State（共享状态）——解决"状态藏在哪"**。整张图共享一份显式的状态（一个类型化的 dict），每个节点**读**它、执行完**写回**它，条件边**基于它**决定下一跳。这和你 `TaskPlanner` 里"全局可见的任务上下文"是同一件事，但 LangGraph 把它**显式成了类型化的一等公民**——不再是散落各处的局部变量。

**② Reducer（合并器）——解决"并发写冲突"**。当你有一张图多个节点**并行更新同一个 key**（对应你第 17 讲 5 个 Agent 并行回结果、往同一个集合里写），默认"后写覆盖"会丢数据。Reducer 定义了**怎么合并**：比如 `add_messages`（把新消息**追加**到列表尾，而不是覆盖）。这和你 `CompletableFutureCoordinator` 里"各 future 的结果要 `thenCombine` 合并进一个容器"是**同一个问题**，LangGraph 用 Reducer 把它规范化了。

**③ Checkpointer（检查点）——解决"状态怎么存、怎么恢复"**。每次一个节点执行完，Checkpointer 就把整份 State **存成一个检查点**。它带来三样你第 5/30/47 讲反复要的能力：

- **失败重放**：从某个检查点重新开始，不用重跑前面的（对应第 30 讲网关重试）。
- **时间旅行（time-travel）**：回到任意历史状态，检查"当时为什么这样决策"（对应你排查评论丢失时翻日志锚点）。
- **断点续跑 / 人机介入**：停在某点等你确认再继续（下一节的 interrupt）。

**这三件套本质上是你手写并发编排时"埋在代码里的隐性约定"，被拎出来显式成了框架机制**。看懂它们，你就懂了自己 coord 里那些该死的"合并容器""死信重跑""状态快照"其实在干嘛。

### 2.3 图把"闭环"做成头等公民

链的坑是默认缺闭环；图模型的翻身仗，正是把闭环变成**语言本身**：

- **循环（Loop）**：边可以指回前面的节点，形成"再做一次"。对应你第 8 讲"观察结果 → 决定要不要再来一轮"。
- **回退（Fallback）**：某节点失败/结果不合要求，沿边**回到上游节点**换路径重做。对应你第 5 讲"结构化失败 → 降级重试"、第 30 讲"网关 openai→fallback"。
- **状态（State）**：整张图共享一份状态，节点读写它，条件边读它做判断。对应你 `TaskPlanner` 里全局可见的任务上下文。

**这就是图相对链的根本不同**：链你只能用"提前写好的固定顺序"模拟回退；图里回退是**第一等操作**，你声明"这条边可以回退"，运行时天然支持。

**这正是你系统里早就做对、只是没叫"图"的地方**：你在第 15 讲选了星型拓扑，第 17 讲给了逐 future 独立限时 + 共享 deadline，第 18 讲做了仲裁——**这些都在定义"谁能到谁、并行怎么聚、结果怎么回流决策"**。你不是没用图，你是**用手写 future + 状态机实现了一个最小图**。

### 2.4 一个经典的"图 Agent 循环"长什么样

把第 8 讲那个循环画成 LangGraph 的图，你会得到一个**教科书式的骨架**（这也是 LangGraph 官方最常见的 Agent 例）：

```
START → (agent 节点：模型决定下一步是调工具还是收尾)
             │  条件边：看 state 里有没有 tool_calls
             ├── 有 tool_calls ──→ (tools 节点：执行工具，结果写回 state)
             │                          │
             └──────────────────────────┘ 回边：回到 agent 节点，再来一轮
             └── 没有 tool_calls ──→ END
```

**这四块正好是你 2.2 节三件套 + 闭环的合体**：`agent` 和 `tools` 是两个节点；"看有没有 tool_calls"是**条件边**；执行结果写回 state 是**State + Reducer**；绕回去是**循环边**。**你在第 45 讲写的那个 `while(true){ msg=llm.next(); if(!toolcall) return; result=guard.invoke(); context.append(result); }`，就是这个图的命令式版本**——一个用图显式写，一个用循环隐式写，语义完全一致。

### 2.5 图的权限/人机介入：interrupt 与你的 ApprovalGate 同源

图模型还有一个链没有的能力，对应你 M7 权限机制的**动作审批**：LangGraph 的 **interrupt()** 允许一个节点**在执行到关键动作前主动"暂停"**，把控制权交回给外部（等人工批准或外部系统判据），批准后再 resume。这和你在第 46 讲里的 **ApprovalGate（先批再动）**、第 18 讲 BLOCKER 强否决，是**同一个"在不可逆动作前设人机/规则闸门"的思想**：

```
关键节点（如：写文件 / 调删除）→ interrupt() 暂停 → 外部批准 → resume 继续
                                         ↑
              对应你 ApprovalGate 的"先批再动"，BLOCKER 的一票否决
```

**这说明"图"不仅是编排，它把"安全暂停点"也纳入了编排原语**——当你的流程里有不可逆动作，图的 interrupt 就是那个"能停下来等人"的钩子。你手写时用状态机冻结 + 人工队列实现了同一件事，LangGraph 把它做成了内建能力。

### 2.6 什么时候该用图、什么时候链就够了

**判据句**：**链 vs 图的取舍，不在于"谁更高级"，而在于『你的流程会不会因为这一步的结果，改变下一步的选择』。如果会——你要的是图（或你自己的闭环写法）；如果不会——链够了。**

用第 8 讲那句判据，一测便知：

> **删掉本轮输出，下一轮输入会不会变？** 会变 → 你的流程有闭环 → 需要一个能表达"循环/分叉/回退"的编排（图，或你手写的等价物）。不会变 → 纯链够了。

**对你的启示**：审查这类任务——**骨架是固定管线（取→析→审→报），但每个审查 Agent 在自己的环节内是闭环的（要观察、要重试）**——最适合的形态正是"**骨架固定 + 局部小图**"：全局是一条稳定的信息流，局部是能分叉回退的图。**这正是 `code-review-agent` 的形态**，也解释了为什么它既不是纯链，也不是纯自由图。

### 2.7 前沿深挖：LangGraph 的 durability 四档，以及与 Temporal 的本质分野

**① durability 是一个四档旋钮，不是有无问题。** LangGraph 官方文档把持久化拆成 `exit / sync / async / selective` 四档：每一步 super-step 何时落盘（退出时/同步立即/异步后台/按节点选择）。**这实质是吞吐、恢复成本、恢复语义三者的权衡旋钮**——sync 最安全但每步付写盘延迟，async 最快但崩溃窗口内丢状态。对照你的系统：审查聚合的断点续传（BatchCoordinator 的 breakpoint）相当于手动实现了 selective 档——**你早已在做这个权衡，只是没用它这个名字。**

**② Checkpointer 的数据模型值得抄：Thread → Checkpoint → Super-step。** 快照按 thread（会话线）组织，每个 checkpoint 记录一个 super-step 的完整状态，支持 replay（重放）、update（注入修改）、human-in-the-loop（interrupt 后人工接管再继续）。**这是"Agent 执行历史"的标准建模方式——你的审查事件流（第 27 讲可观测性）若要支持"失败重放/时间旅行调试"，这套三段模型是最小完备参照。**

**③ LangGraph vs Temporal：两种"持久执行"的血统差异。** Temporal 的核心是 **Workflow-as-Code + deterministic replay**：编排逻辑必须确定性，非确定性的外部交互隔离在 Activity 里，Worker 崩溃后**重放历史事件而不重跑已完成的外部调用**。LangGraph 的 interrupt/replay 形似，但没有确定性约束——**LangGraph 假设节点里装着不确定性的 LLM，Temporal 假设 Workflow 里不该有不确定性**。这个血统差异决定选型：**编排"人/系统/定时任务"用 Temporal 一族，编排"模型调用"用 LangGraph 一族；混合场景里两者可以套娃（Temporal 管外壳流程，LangGraph 管模型子图），且已有官方集成先例。**

## 三、避坑清单

- [ ] **别把 LangGraph 当 LangChain 2.0**——它换了编排原语（顺序数组 → 有环+有状态的图），解决的问题不同。
- [ ] **别以为"图"="更高级就应该用"**——判据是"流程会不会因上一步结果改变下一步选择"，不是热度。
- [ ] **别忽略显式边的价值**——图把"谁能到谁"显式化，排错、审计、画架构都比藏在代码里的隐式流程好。
- [ ] **理解 State/Reducer/Checkpointer 三件套**——它们分别解决"状态藏哪、并发合并、持久化恢复"，是你手写编排时埋在代码里的隐性约定被显式化。
- [ ] **把 interrupt 看成"安全闸门"**——不只有编排价值，更是不可逆动作前的人机介入点（对应第 46 讲 ApprovalGate）。
- [ ] **别把图与"多 Agent"混淆**——LangGraph 可以是单 agent 内的循环，也可以编排多 agent；两者是不同维度（下一讲展开）。
- [ ] **用第 8 讲判据测**"要不要闭环"：删本轮输出，下一轮输入会不会变。

## 本讲小结

1. **LangGraph = 链 → 图**：节点 + 边 + 条件分支，把流程编排从"顺序"升级为"显式连通"。
2. **状态三件套**：State（共享状态）、Reducer（并发合并）、Checkpointer（持久化/重放/时间旅行）。
3. **图把闭环做成头等公民**：循环、回退、状态天然支持——这是链缺的。
4. **你系统的 coord 就是一张隐式小图**：future + 状态机手搭了"并行 + 聚合 + 分支"。
5. **链 vs 图**：流程会不会因上一步结果改变下一步选择——会就用图（或你的闭环写法）。
6. **判据**：固定管线用链，有闭环用图；"骨架固定 + 局部小图"是你审查系统的生产形态。
