## 一、痛点

上一讲我们立了"看框架先问四问"。这一讲要问 LangChain 的"循环"。但在你能问到点子上之前，往往先卡在两个地方：

**痛点一："LangChain 是行业标准，我该无脑跟。"** 你可能被它的生态与教程量淹没，觉得"不学它就不算会 Agent"。→ 于是你把它当真理，把它的默认形态直接搬进系统，而不知道它的默认"链"到底替你做足了多少、缺了什么。

**痛点二："反正我不写 Python，听懂它干嘛？"** 你可能是 Java 系，把它划到窗外。→ 但你那条取数→分析→出报告的固定管线，和 LangChain 的"链"是**同一个思维**。读它，是在看一面照你自己的镜子。

本讲要建立的，是拆掉"无脑跟"和"与我无关"两个墙，把它落到一个具体的判断：

> **LangChain 最典型的形态是『链』——把一次任务切成固定顺序的步骤，每步可单独替换、测试。它省的是『我要写一遍通用的顺序编排』，它的边界是『默认不擅长有分支回退的循环』。** 而你用 `agent-kit` + code-review-agent 建的审查管线（取 → 析 → 审 → 报）正是同类"链"，区别是**你在上面自己加了循环闭环（第 8 讲）**。

## 二、原理

### 2.1 链（Chain）：把"固定管线"打包

链路子的核心直觉是**步骤化**：

```
输入 → 步骤1(取数据) → 步骤2(分析) → 步骤3(生成结论) → 输出
```

每个步骤是一个小块（prompt + 模型，或一个功能），链把这些小块**串起来**。好处很实在：

- **每步可单独测试、单独替换**（换个 prompt 不用动整条链）。
- **可复用**：同一条链换个数据源就能服务不同任务。
- **组件与第三方好接**：生态大，工具多。

**这条路你怎么看**：你在 `code-review-agent` 里那条"接收 PR → 各 Agent 分析 → 聚合报告"的管线，本质就是一条**针对审查场景的链**。你写它，不是因为你没用框架，而是**你手搭了一条该场景的链**。

### 2.2 链的"可组合"到底怎么实现：LCEL 的 Runnable 管道

LangChain 让"链"可组合，靠的是 **LCEL（LangChain Expression Language）** 和一个核心抽象 **Runnable**。一个 Runnable 是"一个能用统一接口调用的件"，统一接口只有几种**调用形态**：

```
invoke()   同步调一次      → 对应你第 45 讲工具的"一次调用"
stream()   流式逐 token    → 对应你 M1 的流式返回
batch()    批量并发        → 对应第 17 讲的并行编排
ainvoke()  异步            → 对应 CompletableFuture 的异步
```

而"链"就是把这些 Runnable 用 **管道符 `|`** 串起来：

```python
chain = prompt | llm | output_parser   # 三个件，串成一条链
result = chain.invoke({"question": "..."})
```

**这里值得你理解的是统一接口的力量**：因为每个件遵循同一个 `invoke/stream` 契约，所以**任意组合、任意替换**都不改调用方——这和第 24 讲你坚持的"维度是三方契约"是同一个思想：**用统一契约换取可组合性**。你在 `agent-kit` 里给 `Agent`、`Tool` 定的接口，就是同一个道理。

**但注意它的编排边界**：LCEL 的 `|` 串起来的是**一条有向的线性流**。它天然表达"下一步是谁"是**写死的**，要表达"根据结果选下一步"，得靠别的机制——这正是链的边界。

### 2.3 AgentExecutor：藏在"链"里的那个循环，其实是 ReAct

LangChain 并非没有循环——它的 `AgentExecutor`（最常用的"Agent"形态）内部**就是一个循环**。这个循环有名字：**ReAct（Reasoning + Acting）**，跑的是四步反复：

```
Thought（思考）→ Action（选工具）→ Action Input（工具参数）→ Observation（观察结果）
        ↑                                                        │
        └──────────────────── 回灌上下文，再来一轮 ────────────────┘
```

直到模型输出 **Finished（完成）** 才停。**这套结构和你在第 8 讲亲手写的"带工具的循环"、第 45 讲 GuardedTool 的三层校验，是同一个东西**：

```
while true:
    thought = model.reason(history)          # Thought
    if thought.finished: break                # 模型软终止
    observation = tool.execute(thought.action) # Action → Observation
    history.append(observation)               # 回灌（第8讲）
```

**关键点**：循环是**有的，但它是 AgentExecutor 这一个特定的类内部写死的**，不是"链"这个原语自带的。于是出现一个断层——**你用"链"拼多步骤时，默认得不到这个循环；要用循环，你得转而用它那个"特例"AgentExecutor**。这个"普适件（链）不含循环、特例件（Executor）含循环"的错位，正是它后来要再出一个 LangGraph 的根因。

### 2.4 记忆的四个档位：框架怎么做上下文压缩

上一讲的四问里，"记忆/上下文"在 LangChain 里落成一个可替换的 **Memory** 对象。它准备了四档，正好对应你第 44 讲"上下文是有预算的"这个铁律：

| Memory 类型 | 策略 | 对应你第 44 讲的概念 |
|---|---|---|
| **ConversationBuffer** | 全量累积，什么都不丢 | 无压缩——token 无限涨，最危险 |
| **ConversationBufferWindow** | 只留最近 k 轮 | 窗口截断（保留最近，丢弃最旧） |
| **ConversationSummary** | 全部压成一段摘要 | 摘要压缩（auto-compact） |
| **ConversationSummaryBuffer** | 摘要 + 最近几轮原文 | 你第 44 讲的"分层：摘要当底 + 近期原文" |

**这段价值在于**：你第 44 讲的上下文漏斗，框架早已把它做成了"换一个 Memory 类"这种开关。**但——默认通常是 Buffer（全量累加）**。这就是"别把框架默认值当最佳实践"的活证据：一个没读过文档的人，可能开着默认 Buffer 跑长会话，**token 悄悄涨到爆**还不知道——而这正是你 M7 判断力要拦下的坑。

### 2.5 边界：默认链不擅长"闭环回退"，RouterChain 只是补丁

链模型的坑，第 8 讲已经预警过了——**Agent 的本质是"带工具的循环"，不是"顺序调用一次"**。链的默认形态是**一条道走到底**：

- **缺闭环**：步骤 1 的结果不对，它不会"回头重做"。
- **缺分支回退**：遇到该换路径的情况，默认链不会自己判断跳转。
- **要 Plan→Execute→Observe**：你需要显式在链里做"规划→执行→观察→回灌"的循环，而**默认链不给你这个**。

LangChain 为"分支"打过一个补丁，叫 **RouterChain**——用一个"路由"模型先决定"这条输入该走 A 链还是 B 链"。**它解决的是"入口分叉"（一次选择），不是"中途回退"（反复观察再决定）**。所以它仍补不上真正的闭环。**这就解释了为什么后来要 LangGraph：图才是把"回退/循环"做成原语的那个东西（下一讲）。**

**这正是你系统里比"纯链"更进一步的地方**：你在链里嵌了 Agent 循环（第 8 讲），让每步**能观察结果、能决定是否继续/重试**，而不是傻串。**如果你只用了 LangChain 的原始 Chain 且不自己加工，你很可能得到一个"顺序调用"而不是"Agent"。**

### 2.6 什么时候链是对的、什么时候不是

**判据句**：**链适合『固定管线』——流程确定、步骤顺序基本不变；不适合『要回看、要试错』的 Agent 核心循环——那需要显式的分支、回退、闭环。**

用第 8 讲那句判据判断你该不该用"链"形态：

> **删掉本轮输出，下一轮输入会不会变？** 如果会变（闭环），你要的是 Agent 循环而不是纯链；如果不会变，纯链够了。

**对你的启示**：审查这类"固定管线 + 结果最终靠人裁定"的任务，**链骨架 + 关键点加循环**往往是最佳组合——**这正是 `code-review-agent` 的形态**：固定分流（supports）之后，各 Agent 在自己环节内闭环，最后聚合。**它不是纯链，也不是纯自由 Agent，而是一条"骨架固定、局部闭环"的混合体。**

### 2.7 前沿深挖：LangChain 1.0 的"自我否定"与抽象泄漏的十年教训

LangChain 是 Agent 框架里被骂得最多、也用得最多的一个。理解它的最好方式是看它在 1.0（2025-10）里**删掉了什么**：

**① 从"万物皆 chain"撤退到 agent loop + middleware。** 1.0 的 `langchain` 包收敛为三件事：**标准 agent 循环、provider 无关的 tool calling 抽象、middleware（自定义逻辑的挂载点）**。早期的 `Chain / RunnableSequence / Serializable / RunnableLambda` 深层组合被明确降级。官方承诺 2.0 之前无破坏性变更——**这等于公开承认：API churn 本身已经成为采用的最大障碍。**

**② 社区批评的核心：抽象泄漏。** 长年的"LangChain sucks"式批评指向同一个机制问题——**prompt、工具、输出被层层包装后，真实发给 LLM 的内容与你的代码脱耦**：trace 是可读的，但调试从"业务逻辑问题"退化为"框架层定位问题"。**判据：一个抽象如果让"实际发给模型的字符串"需要三层跳转才能看到，它就是负资产。** 这也是你的系统坚持"显式 prompt 组装"（第 11/12 讲）的正确性背书。

**③ LangSmith 是 LangChain 真正的护城河。** 框架可以换，但 `LANGSMITH_TRACING=true` 一键开启的 tracing → 在线 eval → dashboard → 回归测试闭环，是生产团队真正离不开的部分。**启示：框架的竞争力最终会落在可观测性与评测闭环上，而不是编排语法上**——这与你在第 27/40 讲自建评测闭环的判断一致。

## 三、避坑清单

- [ ] **别把 LangChain 当无脑行业标准**——它的默认"链"只覆盖固定管线，不覆盖 Agent 闭环。
- [ ] **别以为"用了链"="做了 Agent"**——默认链是顺序调用，要 Agent 循环得用 AgentExecutor 或自己加闭环。
- [ ] **警惕默认 Memory（Buffer 全量累加）**——token 会悄悄涨爆，按第 44 讲主动换成摘要/窗口档。
- [ ] **用第 8 讲判据判断**"要不要循环"：删本轮输出，下一轮输入会不会变。
- [ ] **链适合固定管线，不适合要回看的循环**——别用错形态。
- [ ] **"骨架固定 + 局部闭环"往往是生产最优解**——你的审查系统正是这个形态。

## 四、动手任务

> **目标**：审视你自己的"链"，确认它不是"假 Agent 顺序调用"，并识别你自己的"上下文压缩档位"。

**步骤 1：画出你的主流程**

把 `code-review-agent` 的主流程画成一条链（输入→步骤→输出）。标出**哪些环节有闭环/回退、哪些只是顺序**。

**步骤 2：用第 8 讲判据核对**

对每个环节问"删本轮输出，下一轮输入会不会变"。**该闭环的地方如果没有闭环，就是'顺序调用'冒充 Agent**——补上。

**步骤 3：定位你的"ReAct 循环"和"记忆档位"**

指出**你的系统里哪个循环等价于 AgentExecutor 的 ReAct 四步**（Thought/Action/Observation），以及你**用的是哪一档"记忆压缩"**（对应第 44 讲还是第 47 讲的经验库）。答得出，说明你真正读懂了自己。

**步骤 4：给"该不该用链"立判据**

写一条你自己的判断：**什么任务用链（固定管线），什么任务要加循环**。别等被框架的默认带偏。

## 本讲小结

1. **链 = 把固定管线切成顺序步骤**，可复用、每步单独改；靠 LCEL 的 Runnable 契约（invoke/stream/batch）实现可组合。
2. **AgentExecutor 内部其实有循环**——ReAct 四步（Thought→Action→Observation→回灌），但它是特例类，不是"链"原语自带。
3. **记忆有四档（Buffer→Windowed→Summary→SummaryBuffer）**，默认 Buffer 全量累加会爆 token——对应第 44 讲的上下文压缩。
4. **"用了链"≠"做了 Agent"**——默认链是顺序调用，要闭环得自己加。
5. **判据**：固定管线用链，要回看作循环；用第 8 讲"会不会变"判断。

下一讲看链的"进化版"：**LangGraph——把步骤变成有分支、有环的图**，补上链缺的闭环与回退。
