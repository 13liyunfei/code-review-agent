# 第 66 讲 · Jev 与"决策层"：把"判断"从"生成"里拆出来

> 🎯 导读问题：**"Jev 凭什么比大模型快两个数量级——是它更小更弱，还是它压根没干同一件事？"** ——能答出"不是'小号 LLM'，是**换了任务形态**。LLM 的输出是**长度不确定的文本**，必须逐 token 自回归解码；Jev 的输出是**你在请求里预先写死的选项空间上的概率分布**——它不生成任何一个字，只在一个请求里并行评估你给的每个问题。所以快不是'算力省了'，是'解码这一步根本不存在'"——就把"决策模型"和"更便宜的对话模型"彻底分开了。**本讲判据：凡是"答案空间可以事先写死"的地方，都不该付生成的钱——把"判断"从"生成"里拆出来。**
> 🎯 进阶追问（面向系统架构师）：**"它唯一的输出是概率和置信度，那'谁来负责动作'？把它接到一个已经有仲裁、有权限收敛的审查系统上，插点在哪？"** ——能答出"**Jev 只负责判断，动作必须留给确定性代码**——官方自己把这条写成了'四种活分四样东西干'：精确规则用代码、有界判断用 Jev、要产出语言才用生成模型、不可逆的决定交给人。接到这套系统上正好四个插点：**① 模型档位路由**（现在的 `ModelGateway` 只按'谁没熔断、谁还有配额'轮转，不按'这道题值得哪个档'选）、**② 工具风险前置闸门**（工具真正执行前问一次'这动作是否危险、是否越权'）、**③ 注入的语义复核**（`SemanticInjectionDetector` 现在是本地向量余弦 0.85 卡阈值，换成 Jev 就是一次类型化判断）、**④ 评审结论的可信度分**（接回第 19 讲的置信度校准，从离线校准走向在线推断）"——就把"一个新产品"落成了"我系统里四个具体的洞"。

> **模块十 · 进入方式**：模块十已经用 **「六机制四问」**这把尺子照过三个框架——**LangChain 是链、LangGraph 是图、DeepAgents 是多 Agent**。这一讲换一个物种：**Jev**。它既不是编排框架，也不是对话模型，而是**「决策模型」**——TypeSafe AI 在 2026 年 9 月推出的第一个 **System One** 模型：**读得懂自然语言，但只回类型化判断和校准概率，一个字都不生成。** 前四讲读的是"别人怎么把 Agent 编起来"，这一讲读的是"**Agent 里那些不该由生成模型做的判断，该交给谁**"。读完，你手上那张"读懂任何 Agent 系统"的地图会多出一条**垂直轴**：不只是横向比框架，还能纵向切一刀——**在一次 Agent 运行里，哪些步骤是生成、哪些是判断、哪些必须交回代码。**

## 一、痛点

前四讲我们一直在问"别人怎么把 Agent 编起来"。这一讲要问的是一个你在前 65 讲里**从没正眼看过**的问题——而它恰恰是你系统里最贵、最不稳、最难调的那部分。

**痛点一：你一直在用"会写作文的模型"做"填选择题"的活。** 回想你在第 6 讲建的那条链：让模型返回一段 JSON，然后**解析、校验 schema、失败重试**。你在那里立过判据——"**模型说人话和不说错话是两件事**"。可现在回头看，这条判据还留着一个没堵完的口子：**我们从来没有质疑"这件事该不该用生成模型做"**。让模型判断"这段代码是不是 SQL 注入"、"这次请求危不危险"、"这条 PR 该走哪个审查档位"——**这些问题的答案空间，我们事先就知道全部可能取值**（是 / 否；五个档位之一；1 到 5 分）。而我们付出了什么？**prompt 里写一遍格式要求、输出里生成一段解释、程序里把解释切掉、schema 不对再重试一次。** 你为一段你根本不要的"理由"付了 token，还得自己把它摘干净，然后祈祷第一个 token 没有把后面的结构带跑偏。

**痛点二：你的"置信度"只在离线管用，线上没有一个"当场识别"的接口。** 你在第 19 讲建了 `ConfidenceCalibrationService`——**事后算账**：规则准不准，靠人工标记的误报/正报慢慢校准，`calibrated = rawConfidence × historicalAccuracy`（`code-review-agent` / `core/calibration/ConfidenceCalibrationService.java:93`）。它解决的是"**同一规则长期准不准**"，但它回答不了另一个问题：**"就这一段代码、就这一次判断，模型自己有多确定？"** 而你现在拿到的是什么？——`LlmFindingParser` 里模型不给 `confidence` 时，**默认兜底 0.75**（`core/llm/LlmFindingParser.java:74`）。**一个"默认值"混进了本该表达不确定性的字段**：0.75 既不是模型的判断，也不是历史准确率，它只是一个占位符。于是一条"模型其实很含糊"的发现，和一条"模型很确定"的发现，在你系统里长得一模一样。

本讲要建立的，是一条能把这两个痛点一次切开的判据：

> **"判断"和"生成"是两种活，不该用同一种模型干。** 凡是答案空间**可以事先写死**的判断——是不是、选哪个、打几分——都应该走**决策模型**：不生成文本、直接回类型化答案和校准概率、一次请求并行问完。生成模型只留给你真的需要"产出语言"的地方。你系统里那些"用生成模型做选择题 + 解析 + 重试 + 兜底 0.75"的地方，就是这条判据的靶心。

## 二、原理

### 2.1 它是什么：一句接口，把整件事讲完

Jev 的官方定义只有一句：**System One 模型读得懂自然语言，但返回类型化答案和概率，而不是生成的文本**（TypeSafe AI 官方文档 `docs.typesafe.ai/concepts/system-one`）。它的接口形状更短——**一个端点、一次往返**：

```
POST https://api.typesafe.ai/v1/systemone

{
  "model": "jev-latest",
  "state": { "ticket_message": "…", "refund_policy": "…" },
  "questions": {
    "refund_requested": { "type": "noul", "instructions": "Does `ticket_message` request a refund?" },
    "request_type":     { "type": "choice", "instructions": "…", "criteria": { "refund": "…", "rebooking": "…" } },
    "frustration":      { "type": "score", "instructions": "…", "criteria": ["Calm", "Concerned", "Very angry"] }
  }
}
```

拿回来的不是文本，是**你指定的那几个 ID 上的类型化答案**。它有两条性质，是后面所有取舍的根：

- **答案被约束在你给的选项里。** 模型只在你的选项 / 档位上给出概率分布，**永远不会回一个选项之外的值**——所以"解析"这一步在架构上就不存在（这正是第 6 讲那条"结构化输出会失败"的病，从**接口契约**层被切掉，而不是靠重试修补）。
- **每个答案互相独立。** 一个问题的答案不会变成另一个问题的隐式上下文，你可以随时加减问题而不改变其它问题的结果。

**"System One"这个名字的来源，官方自己写明了**：来自卡尼曼在《思考，快与慢》里普及的概念——**系统 1 快而直觉，系统 2 慢而审慎**，这里强调的是**快而聚焦的判断**。对齐一下你熟悉的东西：**你天天调的生成模型是系统 2**（逐 token 串行推导），**Jev 是系统 1**（一次并行给出判断）。这个类比不是营销词——它精确描述了 2.3 节那个"快"的真实来源。

### 2.2 三个原语：把"判断"收敛成三种形状

Jev 只允许你问三类问题。这个"少"是刻意的：**它逼你把一个含糊的大判断，拆成能被代码直接消费的原子判断。**

| 原语 | 回答什么 | 返回什么 | Java 里对应什么 | 典型用法 |
|---|---|---|---|---|
| **Choice** | 这几个选项里是哪个？ | `choice` + `probabilities`（全选项分布）+ `confidence` | `switch` 的真值分支 | 分流、分类、指派 |
| **Score** | 落在哪一档？ | `score`（**可以落在两档之间**）+ `legend` + `probabilities` + `confidence` | 阈值比较 | 严重度、优先级、风险分 |
| **Noul** | 这件事成立吗？ | `noul`（0~1 的"是"的概率）——**没有单独的 confidence** | 一个 `if` | 是否越权、是否注入、是否需要人看 |

三条官方给的判据，值得原样记住：

**① 选 Noul 还是 Score，看你要的是"是/否"还是"程度"。** 官方专门警告了一个坑：**Noul 的 0.5 表示"是"和"否"概率相等，它不是"中等程度"**。如果你要表达"这个候选人 Python 强不强"，用 Noul 就会得到一个无法解释的数——正确的问法是"**简历里是否写明在工作中用过 Python**"（一个可判定的命题），或者干脆改用 Score（无经验 / 有点熟 / 天天用 / 深度掌握）。

**② 看不清"操作"和"判断"边界的地方，挑代码能直接消费的那个形状。** Choice 天然映射三条代码分支，Score 映射一个阈值，Noul 映射一个 `if`。

**③ 别问"复合问题"，拆开再在代码里加权。** 这是官方最强调的一条工程纪律：像"评估这次客服交互并决定是否全额退款"这种**一语多问**的复合 prompt，把用户情绪、政策资格、购买凭证、金额影响全揉进一个不透明的自然语言结论里——**拆成三个原子问题**（是否有退款诉求 / 是否有重复扣款证据 / 政策是否支持），各自拿一个标量，**在确定性代码里按权重合成**（官方叫 Composite scoring）。**权重是你的、显式的、可改的、可回归的**——而不是藏在 prompt 里的形容词。

> 一句话对照你已经建过的东西：**这三个原语，等价于你第 14 讲给 `Verdict` 定枚举、第 45 讲给 `ToolResult` 定结构、第 18 讲给仲裁定权重**——你早就在这么干了，只是干在了"自己写的规则"上；Jev 把这一步做成了一个不用你写规则的接口。

### 2.3 为什么快：不是"更小的模型"，是"砍掉了整个解码环节"

这是本讲最值钱的一段，也是最容易被说成营销话术的一段。我们把它拆成可判据的两层。

**第一层（机制层，可以讲硬）：生成模型的慢是架构性的，不是配置问题。** 自回归模型生成 n 个 token 就要 n 次串行前向——每一步都要把前面所有 token 的 KV cache 从显存读一遍算注意力。它**在原理上不可并行**。所以当你让一个生成模型返回一段 150 token 的 JSON 时，你付的是**150 次串行内存往返**。而 Jev 的接口文档说得非常直白：**它一次摄入 `state`，然后对每个问题并行评估**（`docs.typesafe.ai/models`）。官方给的口径是 **70~500 ms 端到端，且与问题数量几乎无关**；端到端延迟**与问题的个数基本解耦**——所以"多问一个问题"接近免费。

**第二层（数字层，必须打折再看）：厂商数字与独立复测，要分开摆。**
- **厂商口径**：TypeSafe 自测最快 **约 193 倍**、成本最低 **约 444 倍**（官方基线）；定价是**输入 $0.042 / 百万 token，输出免费**（`docs.typesafe.ai/models`，模型 `jev-1.13.0`）。
- **独立复测**：有开发者拿它和 Gemini 做商务邮件分类的对照，结论是 **Gemini 略准，但贵 10~20 倍**；让这位开发者印象最深的不是价格，而是**它是唯一一个真的把概率交回来的模型**。
- **准确率不看厂商自夸**：在 TypeSafe 自己发布的 4 工作流基准上，Jev 是 **67.8%**，与 GPT-5.6 Terra（67.9%）**基本打平**，低于 GPT-5.6 Sol（74.1%）和 Opus 5（73.1%）。

**把这两层合起来，才是正确的结论**：Jev 赢在**形态**，不在**智力**。它**不是"更便宜地做同一件事"，而是"做一件本来不该用生成模型做的事"**。所以判据也是一句可操作的话：

> **若一个判断的答案空间可以事先写死，用 Jev 是"换工具"；若一个任务需要产出语言、需要推理链、需要解释，用 Jev 是"用错工具"——那部分必须留给生成模型。**

### 2.4 probability 与 confidence：把"我不确定"变成一个能被代码判断的数

这一段是全讲的**合页**——它把 Jev 缝到你在第 19 讲立的那套置信度思考上。官方把两个概念分得很清（`docs.typesafe.ai/confidence`）：

- **`probabilities` 是分布本身**：Choice 给的是你所有选项上的概率分布，Score 给的是所有档位上的分布。
- **`confidence` 是把这个分布"尖不尖"压成的一个 0~1 的数**：**全部分布压在一个选项上就是 1.0，越摊平越低**。官方给的三选项近似算法是 `(3 × 最大概率 − 1) / 2`。
- **Noul 没有 `confidence`**——因为概率本身就是答案。

官方给的用法是三档，而三档的**分界线随风险走**：

| 档位 | 行为 | 官方口径 |
|---|---|---|
| 高置信 | 自动执行 | 模型读得清，无需人介入 |
| 中置信 | 谨慎推进 | 让用户确认 / 标记待审 / 补信息 |
| 低置信 | 不执行 | 转人工、要求澄清、回退到别的系统 |

而且**同一个系统里，不同动作的阈值不应该是一个数**：官方示例里 `confidence < 0.5` 一律转人工（"模型自己说不确定就不要猜"）；**低风险动作**（比如展示余额，错了可恢复）在中置信就执行；**高风险动作**（比如批准转账）要求 **0.9 以上**才自动放行，否则先让人确认——**风险容忍度写在你的代码里，是你可以读、可以改、可以回归的数字。**

**这里有一条官方声明，是整段最该抄进你笔记的一句**：

> **校准是"跨预测群体"的度量——它不保证单个答案是对的。**（Calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct.）
>
> 顺带一句同样重要的：**你并没有被锁死在官方那个 `confidence` 算法上**——完整分布也一并给你了，你要自己定义更合适的"确定性度量"，随时可以。

对照你的系统，这段的落点非常清楚：**第 19 讲的 `calibrate()` 是"这条规则历史上准不准"（规则级、离线、事后）；Jev 的 `confidence` 是"就这一次判断，模型自己有多确定"（实例级、在线、当场）。** 两者是**同一条轴线上的两端**——而不是两套互相竞争的做法。你过去只有左端，右端靠一个 `0.75` 的默认值硬撑；**这就是"当场识别"缺的那一环**（第 40 讲评测闭环管事后算账，这里管回写 PR 之前就给输出打一个可信度分）。

### 2.5 四个插点：把它接到你自己的系统上

产品好不好用是一回事，**它在你系统里补的是哪个洞**是另一回事。对着真实代码找，正好四个，而且每个都能指出**现在缺什么**。

**插点①：模型档位路由——你的网关现在是"可用性路由"，不是"语义路由"。** 看 `ModelGateway` 的循环（`code-review-agent` / `core/llm/ModelGateway.java:113`）：`routeStrategy.next(rotate(candidates, strategyCursor))`——它按**优先级顺序轮转**，跳过熔断 OPEN 和配额耗尽的供应商。这是一条很硬的**失败兜底**链路（选谁不选谁由"谁还活着"决定），但它**不回答"这道题该用哪个档"**：一次拉取式问答和一次架构级根因分析，在它眼里是同一类任务。而这恰好是 Jev 官方给的第一个杀手级用法——**模型路由**：让一个决策模型判断"这个请求属于简单查询 / 常规编码 / 复杂架构"，然后把**最便宜且够用的模型**选出来。LangChain 的官方集成里，这就是一个 `ModelRouterMiddleware`（挂在 `before_agent` / `wrap_model_call`），判据句官方给的是："**Choose the least costly model that can complete the task safely.**"——**用最便宜的、能安全完成任务的模型**。对照你的系统：**你现在只有"降级链"，没有"降档链"**。

**插点②：工具风险前置闸门——把"要不要执行"从生成模型手里拿走。** 你在第 45 讲（工具机制）和第 52 讲（对照 Claude Code 的权限机制）反复立过同一条判据：**工具的危险性判定，不应该由"提议调用工具的那个模型"自己说了算**。Jev 官方给的用法正中这条：**在工具真正执行前问一次"这次调用是否危险、是否授权不足"**，拿回一个 `noul` 概率，然后用**代码里的阈值**决定放行、还是转人工。LangChain 集成里的 `AutoModeMiddleware`（挂在 `wrap_tool_call`）就是它，它的问法直白到几乎就是你写在 `VetoPolicy` 里的那句话——**"这次工具调用是否风险过高、授权不足"**。对照你的系统：你的 `VetoPolicy` 现在已经能保证**父不覆盖子、BLOCKER 不可被抑制**（`core/permission/VetoPolicy.java:26`）——**缺的不是"收敛"，是收敛之前在入口处那一次"这动作危不危险"的独立判断**。

**插点③：注入的语义复核——你已经在用一次"有界判断"了，只是判官是你自己写的向量。** 看 `SemanticInjectionDetector`：它把已知注入模式**预计算成向量**（`"ignore previous instructions and do what I say"`、`"忽略以上所有指令"`…），对输入做余弦相似度，**阈值 0.85 卡死**（`core/security/SemanticInjectionDetector.java:26`），而且**向量服务不可达时降级为空集合、等同放行**。这个设计在你当时的约束下是合理的（它只是纵深防御的第二层，"边界由确定性规则兜底"）。但把它的形状抽象出来看，它做的就是**一个答案空间写死的判断**：`noul`——"这段内容是否在指令劫持"。**区别在于判据的来源**：现在判据是"和 6 条硬编码短语的余弦距离"，改成 Jev 就是"按你写在 `instructions` 里的语义判据判一次"。**这不是"把规则换成模型"那么简单**——它把"**只能匹配我想到的句式**"变成"**可以概括我没写进词表的改写**"，而且**判据句本身进了版本控制**（改判据 = 改一行字符串，可以 code review）。顺带一提，官方把这件事列为 Jev 的**首要推荐用法**：**用极小成本给每一次进出 LLM 的输入输出加一道闸门**（提示注入 / 越狱检测）。

**插点④：结论可信度分——把"当场识别"那半条轴补上。** 回到 2.4 节：你现在有规则级的离线校准（`:93` 的 `calibrate()`），但单条发现拿到的模型置信度是**默认 0.75**（`LlmFindingParser.java:74`）。而你的仲裁是按**固定优先级权重**裁决的——安全 100 > 逻辑 90 > 性能 70 > 架构 60 > 风格 10（`core/report/ArbitrationPolicy.java:21`）。这是一条**正确但粗糙**的判据：它比的是"哪个 Agent 说了话"，**不比"这次它说得有多确定"**。把一条结论的"可信度"补上，你的仲裁就能从"**谁的优先级高**"升级成"**优先级 × 这次判断的确定性**"——**而这一层，恰恰是 2.4 节那个 `confidence` 天然能喂进来的输入**。

### 2.6 前沿深挖：边界、反方证据，和那条必须自己测的前提

产品好用，但把边界讲清才是"深挖"。以下每一条都来自官方文档或公开复测，**并且按"谁说的"分开放**。

**① 它不解释自己——这是最硬的一条限制。** 官方原话：**System One 模型不写回复、不产出代码、不解释自己的推理。** 你拿到的是一个数，不是一个理由。所以但凡你的流程需要"给个说法"（给用户看的说明、给审计的论证、给下一个 Agent 的上下文），**你必须再挂一个真正的 LLM**——这不是缺陷抱怨，而是**架构结论：Jev 是链路上的一颗判断件，不是一个可以单独顶上去的系统。**

**② 答案空间必须"事先有界"，且边界由你负责。** 官方明说：Jev **不会替你写 schema**——你必须在调用前就想清楚所有合法取值。这就带来一个**设计责任在前置**的后果：**问不出好问题的团队，用 Jev 只会得到一个精确的坏答案。** 官方给的两个具体量：Choice 的选项集合超过 **255 个**时，得先做**两段式打分**再显式选择（这会同时改变延迟与实现）；Score 的档位官方支持 **2~10 档**。**"问题设计属于系统容量的一部分"**——这句话就是这条限制的工程翻译。

**③ 它只收文本，且英文最好——这一条是你必须自己先测的前提。** 官方文档明确：**输入目前仅文本**（字符串 / JSON 对象 / 文本数组），图像、音频、视频都不支持，非文本输入要**先你自己转成文本或结构化字段**。更要紧的是语言支持那一节——**英文是主要训练语言、目前准确率最好；包括 CJK 在内的其它语言"能处理，但不如英文好"，并且官方直接建议：在依赖它处理非英文负载之前，先在自己的内容上测，并特别关注 confidence。** 你这条专栏、你这套审查系统，**输入面全是中文代码评审文本**——所以这条不是"备注"，是 **"能不能用"的前置条件**。

**④ 上下文与版本：两个"会静默影响你阈值"的量。** 官方口径是**每请求 64k token 上限**，构成是 **32k 给 `state` + 最长的那一个问题**（不是每个问题各给 32k）。另外**别名会漂移**：`jev-latest` / `jev-preview` 都指向版本化的 `jev-1.13.0`，官方明确提醒——**"别名会随新版本发布而移动，你背后的答案会在你毫无改动的情况下变化"**，所以 **"如果你已经把 confidence 阈值调到了一某个版本上，就钉死版本号，而不是用别名"**。这条对你这种"阈值写进配置、要能回归"的系统是致命的细节。

**⑤ 训练方法与评测口径：官方披露到哪里，我们就知道到哪里。** 官方说明训练方法是 **RLCD（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习）**，**不做微调 / 不加 LoRA、所有账号共用同一套权重**（你要适配领域，只能通过 `state` 放材料、通过 `instructions` 和 `criteria` 写规则、通过代码组合多个原子问题）。同时要诚实地摆出**它没给的**：**没有公开权重、没有公开论文、没有公开排行榜**，性能评测目前**主要来自厂商自己**（有德语媒体 heise 也指出过这一点）。所以正确的读法是：**机制层可以信（并行评估、类型化输出、校准概率是写在接口里的）；数字层要打折，且必须用自己的数据重测。** 名字来源上还有个有意思的解读：有分析认为 **Jev 取自经济学家 William Stanley Jevons**（Jevons 悖论：让一种资源急剧变便宜，总消耗反而上升）——**这是第三方解读，不是官方口径**，但它和这个产品的赌注对得上：**当一次"判断"便宜两个数量级，你会在原来根本不会调模型的地方开始调模型。**

**⑥ 工程侧的现实：它是"一天就长出生态"的那种东西，也是"还没长出官方 Java 支持"的那种东西。** 2026-09-15 上线时还要排队，到 **2026-09-21 就取消候补、任何人可注册**（新账号给 $5 额度）。官方 SDK 是 **Python 与 JavaScript**；**Java / Kotlin / Scala 的官方指引是"直接调 HTTP API"**——于是社区补上了第一个 JVM 客户端（`typesafe-ai-java`，MIT，`com.jamilxt:typesafe-ai-java-core:0.1.1`，附 Spring Boot starter 与 Spring AI 桥接）。**那个 SDK 作者做得最对的一个决定，恰好是本讲 2.1 节那条判据的答辩**：他**拒绝**把它建在 Spring AI 的 `ChatModel` 抽象上——理由是架构性的而非风格的：`ChatModel` 假设的是"消息进、生成文本出、支持流式"，**而 Jev 没有消息、没有生成、没有流**；硬塞进去就得**把问题藏进 prompt、再从一段假装的生成里把答案抠出来**，**正好丢掉类型化问题和一等公民的概率**。**"抽象不能吞掉你能 debug 的可见性"**——这是模块十第 62 讲就立过的规矩，在这里得到了一个具体的案例。

**把 2.5 和 2.6 合起来，一句话收束**：

> **Jev 的价值不在"更便宜的大模型"，而在"把判断从生成里拆出来"这件事终于有了一个直接的接口。** 它的边界同样清晰：**不解释、不写 schema、只吃文本、别名叫不准、数字要自己测。** 所以采用它的正确姿势不是"替换"，而是"**在你的链路里找出那些本来就该是选择题的地方，把它们从生成模型手里拿走，然后把动作留在代码里。**"

## 三、避坑清单

- [ ] **别把 Jev 当"更便宜的大模型"用**——它不做生成、不做推理链、不解释。判据是那句：**答案空间能不能事先写死**；写不死，就是选错工具。
- [ ] **别拿 Noul 当"程度"用**——`noul = 0.5` 是"是/否各半"，**不是"中等"**。要程度就用 Score，并把每一档的含义写成**可观察的环境事实**（"4 = 数据外泄尝试"），而不是主观形容词。
- [ ] **别问复合问题**——"评估这次交互并决定是否退款"必须拆成三个原子问题，**在代码里按权重合成**。权重是你的、显式的、可回归的。
- [ ] **别把它的概率当"这次一定对"**——官方明说**校准是跨预测群体的度量，不保证单个答案正确**。要自己定义确定性度量、自己画置信度-准确率曲线。
- [ ] **别把阈值钉在别名上**——`jev-latest` 会随新版本漂移，**答案会在你零改动的情况下变化**；要调阈值就钉 `jev-1.13.0` 这样的版本号。
- [ ] **别在中文负载上直接上线**——官方明说英文最好、**CJK"能处理但不如英文好"，并建议先自测**。先用你自己的评审文本跑一批、看置信度分布，再决定它能不能进链路。
- [ ] **别让它"自己决定自己的事"**——判断归判断、动作归代码。**工具执行前的风险判定、权限放行、不可逆操作**这三件事，判断可以交给它，**决定必须留在代码或人手里**。
- [ ] **别把厂商数字当结论**——"193 倍 / 444 倍"是厂商口径；独立复测里它是"略逊于对手的准确率 + 10~20 倍的价格优势"。**买的是形态，不是智力**。
- [ ] **别忽略"谁给的判据"这件事**——把 6 条硬编码短语的余弦匹配换成 Jev，收益不只是"更鲁棒"，更是**判据句进了版本控制、可以 code review**；但代价是**判据的模糊性从 0 变成了一点点**，边界那一层确定性规则**不能撤**。

## 四、动手任务

> **目标**：不动生产链路，只做一件你现在就能做完的事——**在自己系统里找出"本该是选择题"的地方**，并给每一处写出可落地的 Jev 调用设计与阈值策略。

**步骤 1：做一张"生成 / 判断"切分表**

把 `code-review-agent` 的一次完整审查流程摊开，逐环节标注它属于哪种活：

| 环节 | 现在谁干 | 属于 | 该不该交给决策模型 |
|---|---|---|---|
| 代码摘要 / 建议生成 | 生成模型 | 生成 | 否 |
| 这条代码是不是 SQL 注入 | 规则 + 生成模型？ | **判断** | 是 |
| 这段自定义 Agent 描述是否指令劫持 | `SemanticInjectionDetector`（余弦 0.85） | **判断** | 是，见插点③ |
| 这次工具调用危不危险 | ？ | **判断** | 是，见插点② |
| 这次请求该用哪个模型档 | 无（只有降级链） | **判断** | 是，见插点① |
| 多个 Agent 结论冲突听谁的 | `ArbitrationPolicy` 固定权重 | **判断 + 策略** | 判断可交，**策略留在代码** |

**要求：凡标"判断"的行，必须写出这个判断的完整选项空间**（noul 还是 choice 还是 score、选项/档位清单）。**写不出选项空间的，说明这个判断还不够原子，继续拆。**

**步骤 2：给四个插点各写一次请求草稿**

按 2.5 节四个插点，各写一段不超过 20 行的请求草稿（用 2.1 节的接口形状）。**每一步都必须回答两个问题**：① 这个判断的 `instructions` 里，判据句是什么（一句话，能 code review）；② 拿到答案之后，**代码**要根据哪个阈值做什么动作。

**步骤 3：把阈值写成配置，并声明回退**

为步骤 2 的每个插点写一张阈值表：`动作 | 置信度阈值 | 越界动作`。**高风险动作的阈值必须显著高于只读动作**（官方示例的形态是：0.5 以下一律转人工，只读动作中置信放行，不可逆动作要求 0.9 以上）。同时写下**回退策略**：Jev 不可用时，这个插点退回到什么（你现在 `SemanticInjectionDetector` 的做法是"降级为放行"——**把你系统里每一个这样的"静默放行"都找出来，明确它是不是可接受**）。

**步骤 4：写"不采用"的理由**

至少写出一条**你决定不用 Jev** 的判断，并给出理由（例如：需要理由说明、选项空间无法枚举、中文负载信心不足、不可逆操作必须人工）。**这一步的产出和步骤 1–3 同样重要**——它证明你是在做架构判断，不是在追新产品。

## 本讲小结

1. **Jev 是决策模型，不是小号 LLM**：只收 `State + 类型化问题`，只回类型化答案与校准概率，**不生成任何文本**；System One 的命名来自卡尼曼的系统 1。
2. **快的根因是"没有解码这一步"**：自回归模型生成 n 个 token 就要 n 次串行前向，原理上不可并行；Jev 一次摄入 `state`、**并行评估所有问题**，所以 70~500 ms 且与问题数几乎无关。
3. **三个原语把判断收敛成三种形状**：Choice（选一）/ Score（打分，可落在档间）/ Noul（是/否概率，**0.5 不是"中等"**）；**复合判断必须拆成原子问题、在代码里加权合成**。
4. **`confidence` 把"我不确定"变成代码能判断的数**，且**阈值随风险走**；但官方明确：**校准是群体度量，不保证单个答案正确**——要自己定义度量、自己验证。
5. **它是"换工具"，不是"省成本"**：厂商口径 193 倍 / 444 倍要打折看；独立复测里它的准确率与主流模型打平、价格低 10~20 倍——**赢在形态**。
6. **接回你的系统有四个真实插点**：模型档位路由（现在只有降级链、没有降档链）、工具风险前置闸门、注入语义复核、结论可信度分——**第四个正是第 19 讲"置信度校准"缺的在线那一半**。
7. **边界同样清楚**：不解释、不写 schema、只吃文本、CJK 需自测、别名叫不准、数字要自己测。**判断归 Jev，动作归代码，不可逆的交给人。**

**模块十至此五讲**：总纲给了尺子（六机制四问），LangChain / LangGraph / DeepAgents 各照出一种编排取向，这一讲补上**垂直轴**——**一次 Agent 运行里，哪些步骤是生成、哪些是判断、哪些必须交回确定性代码**。横向比框架、纵向切职责，你手上这张图的用法就完整了：**读任何 Agent 系统，先问它把判断放在了哪一层。**
