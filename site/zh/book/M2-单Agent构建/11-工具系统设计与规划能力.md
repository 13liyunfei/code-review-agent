# 第 11 讲 · 工具系统设计：让模型能"动手"，还要能"规划"


> 🎯 相关面试考点：**"多 Agent 系统里，你怎么决定用固定流程还是动态规划？"**

<img class="mermaid-svg" src="/zh/book-assets/diag-0046.svg" alt="🎯 相关面试考点：&quot;多 Agent 系统里，你怎么决定用固定流程还是动态规划？&quot;" />

> **图 11-0**　本讲地图：工具的缺口不在功能而在声明：一份 schema 喂两类消费者，校验器的实际能力必须等于文档承诺。规划不是更聪明，它是用一次模型调用换取对未知依赖结构的推断。

## 一、痛点

四个真实的小事故，都发生在"把工具接进来"这件事上。

**事故一：工具被静默换掉了。**

有人为了调试，注册了一个只打印参数的假 `file_read`。他没删掉，直接上线了。真实实现被覆盖了——**因为 `ToolRegistry` 用 `Map.put`，同名会覆盖后一个。**

日志里有一条 `WARN 工具 file_read 被重复注册，覆盖前一实现`。但没人会去读启动日志里的 WARN。

**事故二：模型把 `lines` 参数写成了 `"全部"`。**

工具的 schema 声明 `lines` 是 `integer`，模型传了字符串。执行时 `Integer.parseInt("全部")` 抛异常——而这个异常被 `safeExecute` 吞掉变成了一条观察，模型以为工具坏了，又试了两次，又失败两次。

**一个参数类型错误，浪费了三轮调用和 30 秒。**

**事故三：工具数量从 6 涨到 23。**

模型开始选错工具，选了 `regex_scan` 却想做文件读取。**而代码里没人改动过任何东西。**

**事故四：上了 DAG 规划器之后，审查变慢了。**

原本 5 个 Agent 固定并行、20 秒结束。上了规划器之后，先花 8 秒让 LLM 拆解任务，拆出 4 个子任务，其中 3 个有依赖关系——**于是从"5 路并行"变成了"3 个串行 + 2 个并行"，总耗时反而涨到 40 秒。**

**"更智能"没有带来更快，因为它把一个本来可并行的任务拆成了串行。**

这一讲回答两个问题：**工具系统该怎么立规矩，以及什么时候你真的需要"规划"。**

## 二、原理

### 2.1 注册中心：唯一性、清单、查找

`ToolRegistry` 只有三个职责，但每一个都有明确的语义：

```java
// toolcalling/ToolRegistry.java
/**
 * 工具注册中心：Agent 可用工具的唯一清单，供 {@link ToolCallingLoop} 查找与生成决策上下文。
 *
 * <p>线程安全；同名重复注册后者覆盖并告警。
 */
public void register(AgentTool tool) {
    AgentTool prev = tools.put(tool.name(), tool);
    if (prev != null) {
        log.warn("[ToolRegistry] 工具 {} 被重复注册，覆盖前一实现", tool.name());
    }
}
```

**"覆盖并告警"这个选择本身值得讨论。** 有三种可能的策略：

| 策略 | 后果 |
|---|---|
| 静默覆盖 | **事故一**。上线时你最不希望的行为。 |
| **覆盖 + 告警（当前）** | 运行时能发现，但需要有人看日志。 |
| 抛异常 | 最安全，但会让"测试里替换实现"变得很难。 |

当前选的是第二种。**它有明确的局限：告警在启动时打，而没人读启动日志。**

> **一个更好的做法（本章末尾会作为动手任务）**：把重复注册的**次数**暴露成一个可查询的指标（`ToolRegistry.duplicates()`），让健康检查端点能读到它。**"有没有重复注册"应该是一个可断言的事实，而不是一条可能被忽略的日志。**

清单生成是第二个职责：

```java
/** 生成给 LLM 的工具清单文本（决策上下文的一部分）。 */
public String describeForPrompt() {
    List<String> lines = new ArrayList<>();
    for (AgentTool t : list()) {
        lines.add("- " + t.name() + ": " + t.description() + " 参数: " + t.parameterSchema());
    }
    return String.join("\n", lines);
}
```

**注意它是从 `list()`（即 `Map.values()`）遍历的**——顺序是 `ConcurrentHashMap` 的内部顺序，**不稳定**。

这带来一个副作用：**同一个进程重启后，工具清单在 prompt 里出现的顺序可能不同**。对模型来说，工具顺序的微小变化一般不影响结果，但它会让"两次运行的 prompt 完全一致"这个假设不成立——而**这个假设是"可复现调试"的前提**。

（第 14 讲会再遇到一次"顺序不稳定"的问题，那里它的后果更严重。）

### 2.2 工具 Schema 的两种消费者

同一个工具，要同时喂给两类消费者：

```java
// model/ToolSchema.java
/**
 * 工具参数 JSON Schema（原生函数调用协议用）。
 *
 * <p>从 {@link AgentTool#parameterSchema()} 的简易文本形态（{"a":"string"}）
 * 提升为完整 JSON Schema（type=object / properties / required），供
 * OpenAI 等供应商的原生 tools 参数使用。
 */
public record ToolSchema(String name, String description, Map<String, Object> parameters) {

    /** 从简易文本 schema 构造（{"path":"string","lines":"integer"}）。 */
    public static ToolSchema from(AgentTool tool) { ... }

    /** 转成 OpenAI tools 参数条目。 */
    public Map<String, Object> toOpenAiTool() { ... }

    /** 转成 prompt 文本清单（回退模式用）。 */
    public String toPromptText() { ... }
}
```

**这是一个"一份声明、两种消费"的设计。** 工具的 `parameterSchema()` 只写一次（简易形态），`ToolSchema` 负责把它升格成两份：

- `toOpenAiTool()` → 给**原生 tools 协议**（第 06 讲路线 B）；
- `toPromptText()` → 给 **prompt 文本模式**（第 06 讲路线 A）。

转换里有三个细节：

**细节一：简易形态的字段一律标必填。**

```java
public static ToolSchema from(AgentTool tool) {
    Map<String, Object> props = new LinkedHashMap<>();
    List<String> required = new ArrayList<>();
    Map<String, String> parsed = parseSimple(tool.parameterSchema());
    parsed.forEach((k, v) -> {
        props.put(k, Map.of("type", normalizeType(v)));
        required.add(k);                     // ← 所有字段都进 required
    });
    ...
}
```

和第 07 讲 `JsonSchemas` 那条"惯例"是同一个取向：**对模型严格，对自己宽容。** 简易 schema 没地方表达"可选"，那就全部当必填，让模型尽量给全，代码里再判空。

**细节二：类型归一化。**

```java
private static String normalizeType(String t) {
    if (t == null) {
        return "string";
    }
    return switch (t.toLowerCase()) {
        case "int", "integer", "long", "number" -> "number";
        case "bool", "boolean" -> "boolean";
        case "object" -> "object";
        case "array", "list" -> "array";
        default -> "string";
    };
}
```

**两个动作值得注意**：

- `int / long / integer` **全部归到 `number`**。JSON Schema 只有 `integer` 和 `number` 两个数值类型，而 `long` 在 JSON 里就是 `number`。归一是对的——但要注意 **Java 侧仍应做范围校验**，因为 `number` 不区分大小。
- **`default -> "string"`**。未知类型的兜底是字符串。这和第 04 讲"未识别的状态码按不可重试处理"是同一个取向：**不确定时选一个保守的默认值，而不是抛异常。**

**细节三：解析失败静默降级为空 schema。**

```java
/** 解析简易 schema：字段名 -> 类型名。非法输入按空 map 处理（不阻断注册）。 */
private static Map<String, String> parseSimple(String text) {
    Map<String, String> out = new LinkedHashMap<>();
    if (text == null || text.isBlank()) {
        return out;
    }
    try {
        JsonNode node = MAPPER.readTree(text);
        if (node.isObject()) {
            node.properties().forEach(e -> out.put(e.getKey(),
                    e.getValue().isTextual() ? e.getValue().asText()
                            : e.getValue().path("type").asText("string")));
        }
    } catch (Exception ignored) {
        // 无法解析则空 schema（模型可能不调用该工具，但不炸流程）
    }
    return out;
}
```

**注释里把取舍写清楚了**："模型可能不调用该工具，但不炸流程"。

**这是对的**——工具注册不该因为一处 schema 写错就失败。但它的副作用是：**一个 schema 写错的工具，会以"没有参数"的形态出现在模型面前，然后被模型忽略**。

**这就是"静默降级"的代价**：故障的表现是"这个工具从不被调用"，而不是"这个工具有问题"。所以这类降级**必须配一条日志**（哪怕是 debug 级），否则你会花一个小时去查"为什么模型不用我的工具"。

### 2.3 校验器的实际能力 ≠ 它名字承诺的能力

这是这一讲最值得停下来看的一处。校验器的文档写的是：

```java
/**
 * 工具参数校验器：按 {@link ToolSchema} 校验参数（必填 / 类型），
 * 并对字符串参数做危险模式拦截（命令注入 / SQL 注入 / 路径穿越）。
 */
public static Validation validate(ToolSchema schema, Map<String, Object> args) {
    Map<String, Object> props = schema.parameters() == null ? Map.of()
            : (Map<String, Object>) schema.parameters().get("properties");
    if (props == null) {
        props = Map.of();
    }
    List<?> required = schema.parameters() == null ? List.of()
            : (List<?>) schema.parameters().get("required");
    if (required != null) {
        for (Object r : required) {
            if (args == null || !args.containsKey(r.toString())) {
                return new Validation(false, "缺少必填参数: " + r);
            }
        }
    }
    if (args == null) {
        return Validation.ok();
    }
    for (Map.Entry<String, Object> e : args.entrySet()) {
        Object v = e.getValue();
        if (v instanceof String s) {
            for (String bad : DANGEROUS) {
                if (s.toLowerCase().contains(bad.toLowerCase())) {
                    return new Validation(false,
                            "参数 " + e.getKey() + " 含危险模式: " + bad);
                }
            }
        }
    }
    return Validation.ok();
}
```

**现在仔细看：`props` 变量被赋值了……然后呢？**

从第 30 行赋值之后，**`props` 再也没被使用过**。整个方法实际只做了两件事：

1. **必填参数存在性检查**（`required` 循环）；
2. **字符串参数的危险子串扫描**。

**"类型"这一项，文档承诺了，代码没有实现。**

这就是事故二的根因：模型把 `lines` 传成 `"全部"`，校验器**放行了**——因为它只检查"这个 key 在不在"，不检查"value 的类型对不对"。

**这类缺陷叫"能力分级未显式化"，它有三个危险特征：**

1. **名字和文档承诺的能力高于实际能力**（叫 `Validator`，文档写"必填 / 类型"，实际只有必填 + 危险串）；
2. **不会被任何测试抓到**，因为"少校验"不产生错误，只产生"通过"；
3. **下游会替它兜底**，于是故障现场被转移了——真正的报错发生在 `Integer.parseInt` 那一层，而不是校验层。

> **一个校验器的文档必须精确描述它实际做了什么。** 如果它只做"必填 + 危险串"，那文档就该写这句话——**而不是写一个"更完整"的承诺。**
>
> 这不是吹毛求疵：**"校验通过"这四个字的含义，是整个调用链的信任基础。** 如果它的含义是"必填项都在"，下游就必须自己再判类型；如果它的含义是"类型也对了"，下游就可以不判。**含义模糊时，下游一定会做错假设。**

正确的处置有两种，选哪一种都可以，但**必须选一个并写清楚**：

- **补齐能力**：真正读 `props`，比对 `args` 的 value 类型（`number` 检查是否为数字、`boolean` 检查是否布尔）；
- **降级承诺**：把文档改成"必填参数存在性 + 危险模式拦截（**不做类型校验**）"，并在类名/注释上体现。

**唯一不能接受的是保持现状**——因为现状是"文档说了，代码没做，而没人知道"。

（本章的动手任务就是把这件事变成一个可断言的事实。）

### 2.4 危险模式拦截：它在防什么

```java
/** 危险子串（命令注入 / SQL 注入向量）。 */
private static final List<String> DANGEROUS = List.of(
        ";", "&&", "||", "`", "$(", "rm -rf", "drop table", "truncate table",
        "delete from", "union select", "..\\", ".." + java.io.File.separator);
```

**这是一份黑名单，而黑名单永远不完整。** 那它有什么价值？

价值在于**它拦的是"形态"，不是"具体攻击"**：

| 子串 | 拦住的行为形态 |
|---|---|
| `;` `&&` `\|\|` `` ` `` `$(` | **命令串联**（任何 shell 注入都离不开这些） |
| `rm -rf` `drop table` `truncate table` `delete from` | **破坏性操作**（即使不是注入，也该拦） |
| `union select` | **SQL 注入的经典形态** |
| `..\` `../` | **路径穿越** |

**所以它的定位是"廉价的第一道网"**，而不是"安全边界"。真正的安全边界在工具实现里（第 06 讲的 `resolve → normalize → startsWith`）。

这里有一条**两条防线必须方向一致**的原则：

- 校验器拦 `../`；
- 工具自己再 `normalize + startsWith` 拦一次。

**为什么两道都要有？** 因为绕过其中任意一道的方式不同：黑名单可以被编码绕过（`..%2f`），而 `normalize + startsWith` 不能——但 `startsWith` 又依赖工具实现者写对。**两道都留着，是因为它们防的是不同的绕法。**

### 2.5 何时真的需要"规划"

这是这一讲的第二个主题，也是最容易用错的地方。

先给结论，再给判据。

**三种编排形态，对应三类任务**：

| 形态 | 适用 | 判据 |
|---|---|---|
| **固定并行** | 子任务**相互独立、维度固定** | 你在写代码时就知道有几个维度（安全/逻辑/性能/规范/架构） |
| **ReAct 循环** | **下一步取决于上一步的结果** | 你无法预先写出第二步要做什么 |
| **Plan-and-Execute（DAG）** | 子任务**有依赖关系，但依赖结构可以先想清楚** | 你能在拿到任务后、执行前就画出依赖图 |

**痛点里的事故四是典型的用错**：代码审查的 5 个维度**本来就相互独立**（安全审查不需要等逻辑审查完成），所以固定并行是最优的。用 LLM 去"拆解"，等于：

1. 花一次 LLM 调用把"已经知道的结构"重新推导一遍（**纯浪费**）；
2. 而 LLM 推导出来的 DAG **可能引入伪依赖**（比如让逻辑审查排在安全审查之后）——**把并行变成串行**。

> **规划器不是"更聪明"，它是"用一次 LLM 调用换取对未知依赖结构的推断"。当依赖结构已知时，这次调用是纯亏损。**

**判据可以压缩成一句话**：

> **如果你能提前写出依赖图，就不要让模型去猜依赖图。**

### 2.6 规划必须能降级，且计划必须先校验

如果确实需要规划（比如目标是用户自由输入的复杂任务），`TaskPlanner` 的实现方式值得照抄：

```java
// planning/TaskPlanner.java
/**
 * <p>LLM 输出 JSON：{@code {"tasks":[{"id":"t1","description":"...","dependsOn":[],"assignee":"LOGIC"}]}}。
 * 解析失败 / 校验失败（含环）一律优雅降级为**单任务直通计划**（交给默认 Agent 整体处理），
 * 绝不让规划失败阻塞业务——与系统「可降级」原则一致。
 */
public TaskPlan plan(String goal, String availableAgents) {
    try {
        String prompt = """
                你是任务规划器。把目标拆解为可并行的子任务 DAG。
                可用执行者: %s
                仅输出 JSON：{"tasks":[{"id":"t1","description":"做什么","dependsOn":[],"assignee":"执行者"}]}
                依赖用 id 引用；无依赖则 dependsOn 为空数组；拆成 2-4 个粒度适中的任务。
                目标：%s""".formatted(...);
        JsonNode json = parseJson(chatModel.chat(prompt));
        if (json == null || !json.has("tasks") || ...) {
            return fallback(goal, "LLM 未返回有效任务数组");
        }
        List<TaskPlan.TaskNode> nodes = new ArrayList<>();
        for (JsonNode t : json.get("tasks")) { ... }
        TaskPlan plan = TaskPlan.of(goal, nodes); // 校验失败会抛出，进入 catch 降级
        log.info("[Planner] 目标拆解为 {} 个子任务", plan.tasks().size());
        return plan;
    } catch (Exception e) {
        return fallback(goal, e.getMessage());
    }
}

private TaskPlan fallback(String goal, String reason) {
    log.warn("[Planner] 拆解失败（{}），降级为单任务直通", reason);
    return TaskPlan.singleStep(goal, "默认Agent");
}
```

**四个设计点：**

1. **提示词里写死了"拆成 2-4 个"**——这是**给模型的粒度约束**。不约束的话，模型可能拆出 12 个任务，其中一半是"分析这个文件"级别的碎片。
2. **校验失败走 catch 降级**（`TaskPlan.of` 会抛），**不在这里自己判环**。校验逻辑只有一份，在 `TaskPlan` 里。
3. **降级目标不是"空计划"，而是"单任务直通"**——`TaskPlan.singleStep(goal, "默认Agent")`。**降级后仍然能完成任务**，只是失去并行度。这和第 07 讲"结构化输出是增强而非必需"是同一个取向。
4. **降级打 WARN 并带原因**——你不会想知道"这次为什么没并行"，除非日志告诉了你。

而计划本身的校验放在 `TaskPlan.of`：

```java
// planning/TaskPlan.java
/**
 * <p>通过 {@link #of} 工厂创建，构造时完成三项校验：id 唯一、依赖必须存在、**无环**
 * （Kahn 拓扑校验）——非法输入直接拒绝，保证 {@link DagExecutor} 无需重复防御。
 */
public static TaskPlan of(String goal, List<TaskNode> tasks) {
    Map<String, TaskNode> byId = new HashMap<>();
    for (TaskNode n : tasks) {
        if (n.id() == null || n.id().isBlank()) {
            throw new IllegalArgumentException("任务 id 不能为空");
        }
        if (byId.putIfAbsent(n.id(), n) != null) {
            throw new IllegalArgumentException("重复任务 id: " + n.id());
        }
    }
    for (TaskNode n : tasks) {
        for (String dep : n.dependsOn()) {
            if (!byId.containsKey(dep)) {
                throw new IllegalArgumentException("任务 " + n.id() + " 依赖不存在的节点: " + dep);
            }
        }
    }
    detectCycle(byId);
    return new TaskPlan(goal, List.copyOf(tasks));
}
```

**"构造时校验，执行器无需重复防御"——这是把校验前置到最边界处的经典做法。**

如果不在构造时校验，`DagExecutor` 就必须处理"依赖的节点不存在"（空指针）和"有环"（`compute` 递归会栈溢出）。**把这两种情况挡在构造期，执行器就能写得非常干净。**

环检测用 Kahn 拓扑：

```java
/** Kahn 拓扑校验：无法消完全部节点即存在环。 */
private static void detectCycle(Map<String, TaskNode> byId) {
    Map<String, Integer> indegree = new HashMap<>();
    Map<String, List<String>> dependents = new HashMap<>();
    byId.values().forEach(n -> indegree.putIfAbsent(n.id(), 0));
    for (TaskNode n : byId.values()) {
        for (String dep : n.dependsOn()) {
            indegree.merge(n.id(), 1, Integer::sum);
            dependents.computeIfAbsent(dep, k -> new ArrayList<>()).add(n.id());
        }
    }
    List<String> ready = indegree.entrySet().stream()
            .filter(e -> e.getValue() == 0).map(Map.Entry::getKey).collect(...);
    int removed = 0;
    while (!ready.isEmpty()) {
        String cur = ready.remove(ready.size() - 1);
        removed++;
        for (String next : dependents.getOrDefault(cur, List.of())) {
            if (indegree.merge(next, -1, Integer::sum) == 0) {
                ready.add(next);
            }
        }
    }
    if (removed != byId.size()) {
        throw new IllegalArgumentException("任务计划存在循环依赖");
    }
}
```

**判据是 `removed != byId.size()`——消不掉全部节点就说明有环。** 这个判据比"检测到某个节点 indegree 永远 > 0"更简洁，而且**天然覆盖了"不连通的孤立环节点"**。

### 2.7 执行器：失败传播的语义要明确

```java
// planning/DagExecutor.java
/**
 * DAG 执行器：按依赖拓扑并行执行 {@link TaskPlan}（入度为零的节点并行跑）。
 *
 * <p>失败传播语义：某节点失败（或其任一上游失败）时，**下游节点标记为跳过**而不执行，
 * 不影响无依赖关系的其他分支。计划在 {@link TaskPlan#of} 已校验无环，此处无需重复防御。
 */
private CompletableFuture<TaskResult> compute(TaskPlan.TaskNode node,
                                              Map<String, TaskPlan.TaskNode> byId,
                                              Map<String, CompletableFuture<TaskResult>> futures,
                                              Function<TaskPlan.TaskNode, TaskResult> runner) {
    if (futures.containsKey(node.id())) {
        return futures.get(node.id());        // ← 同一节点只建一个 Future
    }
    List<CompletableFuture<TaskResult>> depFutures = new ArrayList<>();
    for (String dep : node.dependsOn()) {
        depFutures.add(compute(byId.get(dep), byId, futures, runner));   // ← 递归建图
    }
    CompletableFuture<TaskResult> future = CompletableFuture
            .allOf(depFutures.toArray(new CompletableFuture[0]))
            .thenApplyAsync(v -> {
                boolean depsOk = depFutures.stream().allMatch(d -> d.join().success());
                if (!depsOk) {
                    return TaskResult.fail(node.id(), "上游任务失败，跳过");
                }
                try {
                    return runner.apply(node);
                } catch (Exception e) {
                    log.warn("[DagExecutor] 任务 {} 执行异常：{}", node.id(), e.getMessage());
                    return TaskResult.fail(node.id(), "执行异常: " + e.getMessage());
                }
            }, executor);
    futures.put(node.id(), future);
    return future;
}
```

**四个设计点：**

1. **递归建图 + `futures` 缓存**（第一行的 `containsKey` 检查）。这保证了**指向同一节点的多条依赖只建一个 Future**——否则菱形依赖会让同一个任务被执行多次。

   **这是最容易写错的地方**：`A → C`、`B → C`、并且 `C → D`。如果没有缓存，`compute(C)` 会被调用两次，`C` 的 `runner` 执行两次。

2. **"上游失败 → 下游跳过"而不是"整图失败"。** 一条分支断了，其它分支照跑。这是**部分可用**的语义。

3. **"跳过"被表达为 `TaskResult.fail(id, "上游任务失败，跳过")`**——注意它用的是 `fail` 而不是一个新的 `skipped` 状态。

   **这里有一个可讨论的设计缺口**：跳过和失败被压成了同一个状态。消费者无法区分"这个任务执行了但失败了"和"这个任务根本没执行"。如果下游有"失败重试"逻辑，它会对一个**从未执行**的任务发起重试。

   **更准确的做法**是加一个 `skipped` 标志（或者用三态枚举）。这不是 bug，但它是一处**语义损失**——而语义损失在排障时会变成"为什么这个任务被重试了但它其实没跑过"。

4. **`runner.apply` 的异常被吞成失败结果。** 同第 06、10 讲。

### 2.8 工具分发的规模问题：500 个工具怎么让模型看见

本讲 §2.1 讲的注册中心只有三个职责，但它的输出——**工具清单**——会出现在**每一次**决策上下文中。于是工具数量变成一个成本与准确率的双重问题：

- **成本**：清单进 prompt，prompt 的这部分随工具数**线性增长**，而且**每一轮都付**；
- **准确率**：候选越多，模型选错的概率越高（本讲痛点三：工具从 6 涨到 23，模型开始选错）。

先把量级算清楚。本项目的三个内置工具，描述加参数 schema 一共 **179 字符**（`agent-kit/src/main/java/com/codereview/kit/toolcalling/BuiltinTools.java:27-80`，3 个 `description()` + 3 个 `parameterSchema()` 的字面量长度之和），折算约 **60 字符/工具**。真实生产工具的描述远不止这个长度，**保守按 100 token/工具**估：

| 工具数 | 清单 token（@100/工具） | 占 128k 窗口 |
|---|---|---|
| 3（本项目） | 300 | 0.2% |
| 23（痛点三） | 2,300 | 1.8% |
| 100 | 10,000 | 7.8% |
| **500** | **50,000** | **39%** |

**39% 这个数说明了什么**：在 500 个工具的系统里，**光是"让模型知道有哪些工具"，就吃掉了近四成的上下文窗口**——而且这部分内容在每一轮都要重新计费。这不是"描述写得不够精简"能解决的问题，这是**分发方式**的问题。

<img class="mermaid-svg" src="/zh/book-assets/diag-0047.svg" alt="39% 这个数说明了什么：在 500 个工具的系统里，光是&quot;让模型知道有哪些工具&quot;，就吃掉了近四成的上下文窗口——而且这部分内容在每一轮都要重新计费。这不是&quot;描述写得不够精简&quot;能解决的问题，这是分发方式的问题。" />

> **图 11-1**　工具分发的两条路。**这张图真正要说的是右下那条虚线**：按意图检索只有在"索引成本被摊薄"时才划算——如果每轮都要重建索引，你只是把"prompt 变长"换成了"每轮多一次检索开销"。**所以判据不是"要不要检索"，而是"工具集变更的频率"**：工具集稳定 ⇒ 索引建一次用很久，检索是纯赚；工具集每轮都在变（比如动态从 MCP 拉），检索反而更贵。

**工业界的答案是"工具检索"，而且已经内建成框架能力**：

```text

 * indexes available tools at the start of a conversation, exposes a "toolSearchTool" for
 * searching tools based on natural language queries, and manages the selection and
 * injection of discovered tools into the conversation flow.
```

`spring-ai/advisors/spring-ai-tool-search-advisor/src/main/java/org/springframework/ai/chat/client/advisor/toolsearch/ToolSearchToolCallingAdvisor.java:62-67`

**注意这句话里的三件事，每一件都是设计决定**：

1. **"indexes available tools at the start of a conversation"**——索引在**会话开始时**建，不是在每次请求时建；
2. **"exposes a 'toolSearchTool'"**——检索能力本身被暴露成**一个工具**（名为 `toolSearchTool`，`:85`），于是模型用同一套工具调用协议检索工具，**不需要新的协议**；
3. **"injection of discovered tools"**——检索到的工具被**注入后续轮次**，而不是只返回一个名字。检索的产物是"下一轮能直接调用的工具"，不是"一份名单"。

**而"什么时候重建索引"这件事，工业界用了一个非常值得抄的判据**：

```text

	 * for each session. A fingerprint match means the session's index is still valid and
```

实现是 **SHA-256 指纹**（同类 `:333` 注释 `Computes a stable SHA-256 fingerprint for the given tool set. Tools are sorted by …`），并且**按会话（session）分别记录**（`:112` 的 `for each session`）。而索引本身的淘汰策略有默认值：

```text
		private ToolIndexEvictionStrategy evictionStrategy = new LruEvictionStrategy(1000);
```

`spring-ai/advisors/spring-ai-tool-search-advisor/src/main/java/org/springframework/ai/chat/client/advisor/toolsearch/ToolSearchToolCallingAdvisor.java:387`

**这三个数／机制连起来读，是一套完整的账**：

| 机制 | 值 | 它在解决什么 |
|---|---|---|
| 索引指纹 | 工具名+描述的排序哈希 | **工具集没变就不重建**（把"重建"的触发条件从"每次请求"降为"工具集真变了"） |
| 淘汰策略 | `LruEvictionStrategy(1000)` | **最多保留 1000 个会话的索引**——这是内存上界，不是数量目标 |
| 检索工具 | `toolSearchTool`（一个普通工具） | 复用既有协议，不引入新概念 |

**1000 这个数字特别值得注意**：它说明**工具索引是"每会话一份、且会在内存里堆积"的东西**。如果你的会话数是 10 万，这个默认值意味着"最近 1000 个活跃会话有索引，其余的每次都要重建"——**这不是 bug，是一个必须知道的容量事实**。本讲 §2.1 那条"注册中心要留下可断言的痕迹"，在工业界这里的对应物就是**索引的命中率与重建次数**——它们才是这个子系统真正的健康指标。

> **推演**：若工具集在开发期每天变 1 次、而索引"每会话一份"，则每个新会话第一次请求都要付一次索引构建；按 1000 个活跃会话、每个会话平均 20 轮算，**索引成本被摊到 `20/1 = 20` 轮里**——**每轮摊销成本 = 构建成本 / 20**。反之若工具集每轮都变（指纹永不命中），摊销比降到 1，检索从"省钱"变成"多花钱"（假设：索引构建成本与工具数成正比；指纹命中率由工具集变更频率决定，无实测数据，此处为量级推演）。

### 2.9 工业界怎么做：工具结果的截断与摘要

工具调用的另一半成本在**回灌**：`ToolCallingLoop` 把每一次工具输出拼进 `transcript`，`NativeToolCallingLoop` 把它作为 `[观察]` 追加进消息序列（本讲 §2.7 讲过）。**工具输出是外部世界的原样复制**——一个 `file_read` 可能返回 200 行代码，一个 `regex_scan` 可能命中 500 行。这些东西一旦进上下文，就按 §2.8 的账开始计费，而且**在后续每一轮重复计费**。

工业界对"回灌量"的处理是三级阶梯：

<img class="mermaid-svg" src="/zh/book-assets/diag-0048.svg" alt="工业界对&quot;回灌量&quot;的处理是三级阶梯：" />

> **图 11-2**　工具结果的三级阶梯（上排）与**本项目的实际截断口径**（下排）。**下排三个分支是本讲最实用的一张对照**：本项目现在**同时存在两种单位、四个数值**——按字符 800 / 2000，按行 100 / 20——而它们**都不按 token**。第三级"摘要"（最省，但产出不可预测）本项目**没有实现**：这意味着一旦某个工具返回的信息是"必须压缩才能用"的密度，你现在的选择只有"原样塞进去"或"粗暴截断"。

四个数值的出处，逐个可复算：

| 位置 | 数值 | 单位 | 出处 |
|---|---|---|---|
| 工具观察回灌（prompt 文本模式） | **800** | 字符 | `agent-kit/src/main/java/com/codereview/kit/toolcalling/ToolCallingLoop.java:123` |
| 工具观察回灌（原生 tools 模式） | **2000** | 字符 | `agent-kit/src/main/java/com/codereview/kit/toolcalling/NativeToolCallingLoop.java:174` |
| `file_read` 工具自身 | **100** | 行 | `agent-kit/src/main/java/com/codereview/kit/toolcalling/BuiltinTools.java:74` |
| `regex_scan` 工具自身 | **20** | 行 | `agent-kit/src/main/java/com/codereview/kit/toolcalling/BuiltinTools.java:46` |

**同一件事有四个上限，本身就是一条结论。** 更要紧的是这两层截断**方向相反**：

- **调用方截断**（800 / 2000 字符）是**无差别**的——它不知道截的是什么，只能从头切；
- **工具自身截断**（100 / 20 行）是**有语义**的——`regex_scan` 知道"命中行列表"比"原文"更有用，所以它先 `filter` 再 `limit(20)`（`:46`）。

> **所以截断必须发生在工具这一侧，而不是调用方。** 因为只有工具知道"这段输出的哪一部分是结论、哪一部分是原料"。调用方按字符截断，最常见的后果是把一个 JSON 截成半个——**模型拿到的不是"不完整的信息"，而是"看起来完整、实际语法残缺的信息"**，后者更贵：它以"模型理解错了"的形式表现出来，而不是以"报错"的形式。

**框架的做法给出了第三种单位**：

```text
	public class LastMaxTokenSizeContentPurger {
```

`spring-ai/spring-ai-client-chat/src/main/java/org/springframework/ai/chat/client/advisor/LastMaxTokenSizeContentPurger.java:34`

注意名字本身：**`TokenSize`**。它的判定与丢弃都在 token 口径下完成（`doEstimateTokenCount` 走 `TokenCountEstimator`，同类 `:66-68`），并且**从头部丢掉、保留尾部**（`:50-54` 的 `index++` 与 `:61` 的 `subList(index, size)`）。

**两种路径的取舍是这样的**：

| | 按字符 / 行（本项目） | 按 token（框架） |
|---|---|---|
| 成本 | 零（`substring`） | 需要 tokenizer（估算器） |
| 与账单的关系 | **间接**——`800 字符`不等于`固定 token` | **直接**——判的就是账单单位 |
| 中英混排的稳定性 | 差（中文 1 字符 ≈ 1.5–2 token） | 好 |
| 适用 | 单模型、语料同构 | 多模型、语料异构 |

**判据**：**如果你的系统里"截断阈值"是用字符数写的，它就不是一个成本上界，只是一个长度上界。** 想把它变成成本上界，要么换成 token 口径，要么至少把"字符数 → token"的换算关系写成一条注释并定期复核。

而"摘要"这一级为什么最难做，也值得说清：**截断是可复算的（给同样输入得到同样输出），摘要是不可复算的（多一次模型调用，且这次调用本身会失败、会串味、会引入幻觉）。** 所以工程上的常见做法是**不在链路里做摘要，而是把"该怎么压缩"下放给工具**——工具自己返回"已经压缩好的结论"，而不是返回原文让链路去压。本项目 `regex_scan` 的 `filter + limit` 就是这个形态的最小例子。

### 2.10 搬到你自己系统：工具注册中心的验收清单

工具系统的缺陷有一个共同特征：**它们都不报错**。重复注册只打一条启动 WARN；校验器少做一项校验只产生"通过"；schema 解析失败静默降级为空；截断阈值取 800 还是 2000 都不影响任何测试。**所以验收必须靠机械项，而不是靠"跑一遍看看"。**

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| 索引按"工具集指纹"决定是否重建（`ToolSearchToolCallingAdvisor.java:111-112`） | 你什么时候重建工具索引？按请求、按时、还是按变更？ |
| 索引淘汰默认 `LruEvictionStrategy(1000)`（`:387`） | 你的工具索引/工具缓存的上界是多少？超了会怎样？ |
| 检索本身是一个普通工具（`toolSearchTool`，`:85`） | 你引入"工具检索"时，是新增协议还是复用既有调用协议？ |
| 本讲 §2.1：覆盖要留痕 | 你的重复注册是可查询的指标，还是一条没人看的 WARN？ |
| 本讲 §2.3：校验器能力必须等于文档承诺 | 你的校验器实际做了几项？哪一项是可以被测试证明"没做"的？ |
| 本讲 §2.9：工具侧截断优先于调用方截断 | 你的截断发生在工具里还是链路里？单位统一吗？ |

**搬到你自己系统**，五步：

1. **给工具清单算一个 token 预算**：`工具数 × 单工具 schema token`，和你模型窗口对比。**超过 10% 就该考虑检索**，超过 30% 就必须改分发方式（§2.8 的表）。
2. **把"重复注册次数"变成健康检查能读到的数**（这是本讲动手任务一的延伸）。**"有没有重复注册"应该是可断言的事实，不是一条日志。**
3. **写一个测试，断言你的校验器"实际做了哪几项"**——包括断言它**不做**的那一项（比如类型校验）。**能把"没做"断言出来的测试，比断言"做了"的测试更值钱。**
4. **统一截断口径**：把链路里所有截断阈值列成一张表（像上面那张四行的表），标出单位和位置。**同一件事有多个不同数值，就要先决定"哪一个才是契约"。**
5. **把"截断"从链路下沉到工具**：让每个工具返回"它认为该返回的东西"，链路只做兜底截断（例如按 token 的硬上限），而不是按字符无差别切。

**判据**：**"我的工具系统是受控的"这句话，只有在你能列出"工具数 / 清单 token / 重复注册次数 / 校验项清单 / 截断阈值表"这五项时才算成立。** 这五项没有一项需要跑流量才能得到——**它们全部是静态可查的，所以没有理由不知道。**

## 四、避坑清单

- [ ] **工具同名覆盖必须留下可断言的痕迹**（计数器/指标），不能只是一条启动 WARN。
- [ ] **工具清单的顺序要不稳定也接受，但要知道它不稳定**——影响"两次运行 prompt 完全一致"的假设。
- [ ] **一份 schema 声明，两种消费者**（原生 tools / prompt 文本）。不要维护两份。
- [ ] **类型归一化要保守兜底**（未知类型 → string），但要记得 Java 侧仍需范围校验。
- [ ] **schema 解析失败静默降级必须配日志**，否则故障表现为"这个工具从不被调用"。
- [ ] **校验器的文档必须精确描述它实际做了什么。** 名字承诺 > 实际能力 = 一整类不被测试发现的缺陷。
- [ ] **校验的"能力分级"要显式化**：必填 / 类型 / 危险模式，做了哪几项就写哪几项。
- [ ] **黑名单与白名单边界（`normalize + startsWith`）两道都要有**，它们防的是不同的绕法。
- [ ] **依赖结构已知时不要用 LLM 规划。** 规划是"用一次调用换对未知依赖的推断"；已知时是纯亏损。
- [ ] **LLM 规划必须能降级到"单任务直通"**，而不是降级到"空计划"。
- [ ] **计划的校验放在构造期**（id 唯一 / 依赖存在 / 无环），执行器无需重复防御。
- [ ] **建 DAG 的递归要缓存已建的 Future**，否则菱形依赖会重复执行同一节点。
- [ ] **"跳过"与"失败"是两个状态**，不要压成一个。否则下游重试逻辑会对从未执行的任务发起重试。
- [ ] **别用"空集合"表达多种状态**（未启用 / 失败 / 无结果）。要一个显式的状态值。
- [ ] **别把"工具清单"当成免费的上下文。** 500 个工具按每工具 100 token 估，清单本身就吃掉约 **39%** 的 128k 窗口，而且是**每轮重复计费**；工具数上到三位数就该考虑按意图检索。（§2.8）
- [ ] **别在"工具集每轮都在变"的系统里做检索。** 索引的价值来自"建一次、用很多次"；指纹永不命中时，检索只是把"prompt 变长"换成了"每轮多一次检索开销"。（§2.8）
- [ ] **别让截断发生在调用方。** 调用方只能按字符无差别切，最常见的后果是把 JSON 截成半个——**模型拿到的是"看起来完整、实际语法残缺"的信息**，它表现为"理解错了"而不是"报错"。（§2.9）
- [ ] **别让同一件事有多个不同的截断阈值。** 本项目同时存在 800 / 2000 字符与 100 / 20 行四个值，**且都不按 token**；阈值多到没人能说出"哪一个才是契约"时，成本上界就已经失效。（§2.9）
- [ ] **别指望"多跑一遍"能发现工具系统的缺陷。** 重复注册、缺类型校验、schema 静默降级、阈值不一致——**这四类缺陷全都不报错**，只能靠机械项验收。（§2.10）

## 五、动手任务

> **任务一：把"校验器实际做了什么"变成一个可断言的事实。**
>
> **仓库位置**：`agent-kit / toolcalling/ToolSchemaValidator.java`
>
> **操作**：
> 1. 写一个测试：构造 `ToolSchema`（含 `{"properties":{"lines":{"type":"number"}},"required":["lines"]}`）。
> 2. 用 `validate(schema, Map.of("lines", "全部"))` 调用它 —— **`lines` 存在，但类型是字符串**。
> 3. 断言返回的 `valid()`。
>
> **预期结果**：**`valid() == true`**，即校验通过。因为类型校验没有实现（`props` 变量被赋值后未被使用）。
> **然后读一遍第 30–34 行**——你会发现 `props` 只在这几行出现，之后再无引用。**这就是"文档承诺 > 实际能力"的证据。**
>
> **任务二（选一个方向补齐它）：**
> - **补齐能力**：读 `props`，对 `args` 里每个值做类型比对（`number` 检查是否为数字类型，`boolean` 检查是否为布尔），不匹配返回 `new Validation(false, "参数 x 类型应为 number，实际 ...")`。
> - **或降级承诺**：把类文档改成"必填参数存在性 + 危险模式拦截（**不做类型校验**）"。
>
> **无论选哪个，都要能让"当前能力"被一个测试断言出来。** 这是本任务真正的目的。
>
> **任务三：造一个环，看它在构造期就被拦下。**
> ```java
> TaskPlan.of("目标", List.of(
>     new TaskNode("t1", "A", List.of("t2"), "X"),
>     new TaskNode("t2", "B", List.of("t1"), "Y")));
> ```
> **预期结果**：抛 `IllegalArgumentException("任务计划存在循环依赖")`——**在构造期**，`DagExecutor` 一行都不会跑。
> 再试 `dependsOn: ["t3"]`（不存在的 id）→ 抛 `"任务 t1 依赖不存在的节点: t3"`。
>
> **任务四：验证菱形依赖只执行一次。**
> 构造 `A→C`、`B→C`，其中 `C` 的 `runner` 用一个 `AtomicInteger` 计数。
> **预期结果**：计数恒为 1。**把 `compute` 第一行的 `if (futures.containsKey(...))` 删掉，计数变成 2** —— 这就是"递归建图必须缓存"的原因。

## 本讲小结

1. **注册中心的三个职责**：唯一性（覆盖要留痕）、清单生成、查找。**"覆盖 + 告警"不够，应该变成可断言的指标。**
2. **一份 schema 声明，两种消费者**（原生 tools / prompt 文本）。类型归一化保守兜底，解析失败静默降级但**必须配日志**。
3. **校验器的文档必须等于它的实际能力。** `ToolSchemaValidator` 承诺"必填 / 类型"，实际只做"必填 + 危险串"——**这一处缺口就是事故二的根因**。这类缺陷不会被测试抓到，只会让下游替它兜底。
4. **黑名单拦形态，白名单边界拦实质**，两道都要有。
5. **规划不是"更聪明"，是用一次 LLM 调用换取对未知依赖结构的推断。** 判据：**能提前写出依赖图，就不要让模型去猜。**
6. **规划必须降级到"单任务直通"**，且**计划校验放在构造期**（id / 依赖 / 无环）。
7. **建 DAG 要缓存 Future**（否则菱形依赖重复执行），**"跳过"和"失败"要分开**，**别用空集合表达多种状态**。
