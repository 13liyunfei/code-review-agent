## 一、痛点

你的审查 Agent 上线三个月，学会了"从历史经验里学习"：每次审查完做一次反思，把"问题模式 → 建议"沉淀下来；下次遇到相似的代码，就把相关经验注入提示词。

第四个月，质量开始下降。抽样看报告的注入段落：

```
【历史经验参考】
- 空指针风险 → 建议判空
- 空指针风险 → 建议判空
- 空指针风险 → 建议判空
- 未使用变量 → 建议删除
- 空指针风险 → 建议判空
```

**注入的 5 条里，4 条是同一句废话。**

打开经验库：

```
$ select count(*), stage from experience_entry group by stage;
 count |  stage
-------+----------
  4137 | active
     0 | archived
```

**4137 条 active，0 条 archived。三个月只增不减。**

再往下查，发现了三件事：

1. **所有条目都是 `active`**——从没有一条被降级。因为从来没有人反馈误报（反馈入口在控制台里，没人用过）。
2. **有一批条目 `evidence_pos = 3`**，但它们的来源是"某一次审查里同一个 pattern 命中了 3 次"——**被当成了 3 次复现。**
3. **没有任何条目被清理过**。维护任务在跑，日志里是 `debug` 级别的"无需要遗忘的条目"。

**这三件事合起来，就是一个"只增不减、不问质量、还自我强化"的记忆系统。**

这一讲要解决的就是这三件事：**怎么升级、怎么降级、怎么遗忘。**

## 二、原理

### 2.1 记忆不是"存下来"，是一条有生命周期的记录

大部分"Agent 记忆"的实现只有两个操作：`save` 和 `search`。这是把它当成数据库用了。

**而记忆系统的真实形态应该是一台状态机：**


<img class="mermaid-svg" src="/zh/book-assets/diag-0095.svg" alt="而记忆系统的真实形态应该是一台状态机：" />


> **图 10-1**　记忆的四态生命周期。**`ARCHIVED` 不是终点，`PURGED` 才是**——前者只是"退出检索面"，后者是"物理删除、不可恢复"。

但上面的图只画了"四个状态之间怎么跳"，它欠了三个东西：**谁把经验送进来、谁依据什么判定升级、还有谁会亲手去动这条命**。把这三个角色补上，才是一张能对着实现的完整图：

<img class="mermaid-svg" src="/zh/book-assets/diag-0096.svg" alt="但上面的图只画了&quot;四个状态之间怎么跳&quot;，它欠了三个东西：谁把经验送进来、谁依据什么判定升级、还有谁会亲手去动这条命。把这三个角色补上，才是一张能对着实现的完整图：" />


> **图 10-2**　记忆生命周期的完整形状（与 `docs/business-flow.html` 的 L6b 同源）。四个入料口（反思 / 跨 PR 复现 / 人工正报 / 人工误报）把证据喂进状态机；升级与降级都在 SQL 内原子判定（`CASE WHEN`）；遗忘分两层——软删（180d 无命中）与硬删（90d 保留期）；三个外部角色贴着它转：**注入点（读侧）、维护任务（时侧）、管理接口（手侧）**。下面三节把它们逐个拆开。

看代码，这是四个状态：

```java
// memory/ExperienceStage.java
/**
 * <p>设计对齐「五态生命周期」的最小子集，证据驱动而非时间空转：
 * <ul>
 *   <li>{@link #CANDIDATE} —— 反思/审查沉淀的候选经验（未经验证）；</li>
 *   <li>{@link #ACTIVE}    —— 证据驱动升级：跨 PR 复现或人工正报确认后转正，
 *        检索注入时权重最高；</li>
 *   <li>{@link #ARCHIVED}  —— 遗忘（软删）：人工误报累计达到阈值，或超过 TTL
 *        无命中/无更新（记忆衰退），检索不再注入，等待物理清理或人工恢复审视；</li>
 *   <li>{@link #PURGED}    —— 物理删除（硬删）：ARCHIVED 超保留期由维护任务清理，不可恢复。</li>
 * </ul>
 */
public enum ExperienceStage {
    CANDIDATE,
    ACTIVE,
    ARCHIVED,
    PURGED;
```

**注意类注释里那六个字："证据驱动而非时间空转"。** 这是整台状态机的设计立场，下一节展开。

先看两个方法——它们是"状态机"落到存储层时必须处理的细节：

```java
    /** 数据库列值（小写）。 */
    public String db() {
        return name().toLowerCase();
    }

    /** 由数据库列值解析（未知回落 CANDIDATE）。 */
    public static ExperienceStage from(String s) {
        if (s == null) {
            return CANDIDATE;
        }
        try {
            return valueOf(s.toUpperCase());
        } catch (IllegalArgumentException e) {
            return CANDIDATE;
        }
    }
```

**为什么需要 `db()` / `from()`？** 因为枚举名是 `ACTIVE`，而数据库里的值是 `'active'`——**大小写映射必须集中一处，否则每次读写都要记得 `.toLowerCase()`，漏一处就是一个查不到的记录。**

**"未知回落 CANDIDATE"**：读到不认识的 stage 值时，按"候选"处理。这是**fail-safe 的取向**——把未知状态当成"最保守、最不信任"的那一档。如果回落到 `ACTIVE`，一个脏值就会让一条未验证的经验直接生效。

### 2.2 升级靠证据，不靠时间

"证据驱动而非时间空转"是什么意思？

对比两种设计：

| | 时间驱动（❌） | 证据驱动（✅） |
|---|---|---|
| 升级条件 | 存满 7 天 → ACTIVE | 跨 PR 复现 3 次 / 人工正报 → ACTIVE |
| 问题 | **时间不是质量信号。** 一条永远不对的经验，放 7 天也不会变对 | 需要更多字段与写入路径 |

**时间驱动的致命问题**：它会让"沉淀得早的错经验"自动获得最高权重。而讽刺的是——**错的建议往往更容易被反复沉淀**（因为模型容易重复犯错，同一个错 pattern 会反复出现）。

看 `ExperienceEntry` 携带的证据字段——把它画成对象图，一眼就能看清"一条经验记录"由哪几类信息拼成：

<img class="mermaid-svg" src="/zh/book-assets/diag-0097.svg" alt="看 `ExperienceEntry` 携带的证据字段——把它画成对象图，一眼就能看清&quot;一条经验记录&quot;由哪几类信息拼成：" />


> **图 10-3**　`ExperienceEntry` 的对象形态。**三类信息流是拆开的**：`id/teamId/pattern/advice/source` 决定"这条经验是谁的、讲什么"；`stage` 决定"它现在在哪一阶段"；而 `evidencePos`、`evidenceNeg`、`hitCount/lastHitAt` 是三条**独立的证据流**——把"质量上升 / 质量下降 / 使用"彻底分开，正是从源头堵住"命中被当成升级证据"的口子。下面这张表把这三条信息流讲透：

**三个字段，三条独立的信息流：**

| 字段 | 来源 | 作用 |
|---|---|---|
| `evidencePos` | **跨 PR 复现 + 人工正报** | 驱动**升级** |
| `evidenceNeg` | **人工误报** | 驱动**降级** |
| `hitCount` / `lastHitAt` | **检索命中** | 驱动**反遗忘**（不驱动升级） |

**最后一行是设计上最容易做错的一处。**

**检索命中不能算正证据。** 为什么？因为它是一个**自我强化循环**：

```
经验在库里 → 被检索到 → 注入上下文 → 命中计数+1 → 权重更高 → 更容易被检索到 → ...
```

如果命中就涨 `evidencePos`，那么**一条被错误升级的经验，会因为"总被检索到"而永久锁死在最高权重**——即使它对审查没有任何帮助。

**所以命中只刷新"遗忘时钟"（spaced repetition），不涨"质量分"。** 这两个概念必须严格分开：

- **"我最近被用到过"**（`lastHitAt`）→ 影响**是否被遗忘**；
- **"我被证明是有用的"**（`evidencePos`）→ 影响**是否生效**。

而 `retrievable()` 就是检索面的**唯一准入判据**（图 10-3 最下方那个方法框，`stage ∈ {CANDIDATE, ACTIVE}`）。

**注意它同时包含 CANDIDATE 和 ACTIVE。** 也就是说，候选经验**也会被注入**——只是权重低（这个"权重低"由检索层实现）。

**这是一个有意的选择**：如果候选经验不注入，那它就永远拿不到"复现证据"（因为复现是靠检索命中的 pattern 匹配来的），会永远停在 CANDIDATE。**注入是它获得验证的唯一途径。**

### 2.3 阈值必须防"单次审查内虚高"

这是本讲最值得记住的一个坑，它被写在常量的注释里：

```java
// core/store/PgExperienceLibrary.java:26-29
/** 复现/正报次数达到该值自动升级 ACTIVE（防单次审查内同 pattern 多次命中造成的虚高）。 */
static final int ACTIVE_EVIDENCE = 3;
/** 人工误报达到该值自动降级 ARCHIVED。 */
static final int ARCHIVE_NEGATIVE = 2;
```

**"防单次审查内同 pattern 多次命中造成的虚高"——这句话描述的就是痛点里的第 2 件事。**

场景：一次审查里，`LogicAgent` 对这个 PR 报了 3 条"空指针风险"（3 个文件都有同样的问题）。沉淀逻辑按 pattern 去重写入，`evidencePos` 变成 3——**刚超过阈值，这条经验立刻从 CANDIDATE 升级为 ACTIVE。**

**但它只被"验证"了一次**：一次审查、一个 PR、一个模型的一次判断。

**这就是"计数口径"和"语义口径"不一致造成的虚高**：

- 计数说的是"这条经验出现过 3 次"；
- 你希望的是"这条经验在 3 个独立场景里被验证过"。

**修法有两种，都需要显式设计**：

| 方案 | 做法 |
|---|---|
| **计数去重到"PR 维度"** | 复现只在**一个新的 PR** 里第一次命中时 +1；同一 PR 内重复命中不计 |
| **抬高阈值** | 阈值设成 3，并接受"一次审查贡献 1 分"的口径（即同 PR 内先去重） |

**当前实现里，`upsertReflection` 是"同 pattern 就 +1"（见 3.2 节），并没有按 PR 去重。** 所以这个坑是**真实存在**的——注释认识到了风险，但代码没实现去重。

> **"知道坑在哪"和"堵上坑"是两件事。** 注释的价值是把风险显式化，让后来的人能看见；但如果代码没堵，那这条注释就成了"历史遗留的自白书"。
>
> **补法其实很便宜**：给 `upsertReflection` 加一个 `prId` 参数，用一张 `experience_evidence(team_id, pattern, pr_id)` 表做唯一约束，同一个 PR 对同一 pattern 只计一次。**这是一个字段 + 一张小表的改动。**

### 2.4 遗忘必须分两层，而且"软删"要能真的软

```java
// memory/MemoryMaintenanceScheduler.java
/**
 * <p>两层遗忘（对齐五态生命周期的遗忘侧）：
 * <ol>
 *   <li><b>软删（TTL 衰减）</b>：CANDIDATE/ACTIVE 条目超过 {@code experience-idle}
 *       无命中/无更新 → ARCHIVED，退出检索注入面。被反复使用的条目每次命中都刷新
 *       updatedAt（spaced repetition），因此不会误删常用经验——遗忘只作用于「记忆衰退」；
 *       </li>
 *   <li><b>硬删</b>：ARCHIVED 超过 {@code purge-after} → 物理删除，不可恢复。</li>
 * </ol>
 */
public MemoryMaintenanceScheduler(ExperienceLibrary library,
                                  @Value("${review.memory.experience-idle:180d}") Duration idle,
                                  @Value("${review.memory.purge-after:90d}") Duration purgeAfter) {
```

**默认参数：软删 TTL 180 天，硬删 TTL 90 天。**

**为什么必须分两层？** 因为两层服务于**不同的风险**：

| 层 | 操作 | 可恢复 | 目的 |
|---|---|---|---|
| 软删 | `stage = 'archived'` | ✅ 可以人工恢复 | **止损**：让错经验立刻停止影响审查 |
| 硬删 | `DELETE FROM ...` | ❌ | **回收**：清掉长期无用的数据 |

**如果只有硬删**：一条错经验在被判定"没用"的瞬间就永久消失——**而"判定它没用"这个判断本身可能是错的**（比如误报是某个人手滑点的）。你就失去了纠错的机会。

**如果只有软删**：归档条目永远躺在库里，`count(*)` 只增不减，运维无法判断"这张表到底健康不健康"。

**两层合起来才有完整的语义：先用最低成本止损，等够久再真正删除。**

现在看软删的 SQL——**这里面藏着一个非常隐蔽、但致命的细节**：

```java
// PgExperienceLibrary.java:193-206
public int archiveIdleAll(Duration idle) {
    if (idle == null || idle.isNegative() || idle.isZero()) {
        return 0;
    }
    try {
        Timestamp cutoff = Timestamp.from(Instant.now().minus(idle.toMillis(), ChronoUnit.MILLIS));
        List<Integer> rows = db.query("""
                        UPDATE experience_entry
                        SET stage = 'archived', updated_at = now()
                        WHERE stage IN ('candidate', 'active') AND updated_at < ?
                        RETURNING id
                        """,
                rs -> rs.getInt(1), cutoff);
        return rows.size();
    } catch (Exception e) { ... }
}
```

**注意 `SET stage = 'archived', updated_at = now()`——归档的时候，把 `updated_at` 刷新成了当前时间。**

**这一行是"承重墙"。看清理的 SQL：**

```java
// PgExperienceLibrary.java:231-245
public int purgeArchivedAll(Duration purgeAfter) {
    ...
    Timestamp cutoff = Timestamp.from(Instant.now().minus(purgeAfter.toMillis(), ChronoUnit.MILLIS));
    List<Integer> rows = db.query(
            "DELETE FROM experience_entry WHERE stage = 'archived' AND updated_at < ? RETURNING id",
            rs -> rs.getInt(1), cutoff);
    return rows.size();
    ...
}
```

**硬删的判据也是 `updated_at`。**

于是：

- **默认配置下**：`idle = 180d`、`purge-after = 90d`。**软删的 TTL 比硬删的 TTL 更长。**
- 归档时刷新 `updated_at = now()` → 条目获得**全新的 90 天**存活期。
- **如果这一行被删掉**（"归档只是改状态，为什么要写时间戳？"）→ 条目被归档时的 `updated_at` 还是 180 天前 → **它同时满足 `updated_at < now() - 90d`** → **在这一次维护任务里被立刻物理删除。**

> **删掉那一行看起来"多余"的 `updated_at = now()`，软删就变成了硬删，而且不报任何错。**

这个坑特别值得记住，因为它具备"静默故障"的全部特征：

1. 代码改动看起来是**无意义的优化**（省一次写）；
2. **测试很难覆盖**——你需要在同一个测试里把 TTL 配成"软删 TTL > 硬删 TTL"，才可能观察到；
3. 表现是**数据消失**，而不是报错；
4. 而 `idle=180d > purge-after=90d` 这个默认配置**恰好**让这个坑必然触发。

**这条经验可以推广成一条通则**：

> **当两个 TTL 用同一个时间戳字段时，中间状态必须重置这个字段。** 否则"两阶段删除"会退化成"一阶段删除"。

### 2.5 维护任务的四条纪律

```java
// MemoryMaintenanceScheduler.java
/** 每日清理一次（默认 03:40）。 */
@Scheduled(cron = "${review.memory.cleanup-cron:0 40 3 * * *}")
public void maintain() {
    try {
        int archived = library.archiveIdleAll(idle);
        int purged = library.purgeArchivedAll(purgeAfter);
        if (archived + purged > 0) {
            log.info("[Memory] 记忆遗忘维护完成：TTL 归档 {} 条（idle={}），物理清理 {} 条（purgeAfter={}）",
                    archived, idle, purged, purgeAfter);
        } else {
            log.debug("[Memory] 记忆遗忘维护完成：无需要遗忘的条目（idle={}, purgeAfter={}）", idle, purgeAfter);
        }
    } catch (Exception e) {
        log.warn("[Memory] 记忆遗忘维护异常（本轮跳过）：{}", e.getMessage());
    }
}
```

**四条纪律，逐条看：**

**① 错峰。** 类注释：

> 跨团队执行（团队集合由仓库映射动态产生，无固定枚举）。与 {@link ResumeJanitor} 错峰（默认 03:40，避开断点清理 03:30 与巡检 02:00）。

三个维护任务：巡检 **02:00**、断点清理 **03:30**、记忆维护 **03:40**。**每个任务各自跑，不会同时压 PG。**

**② 异常不阻断。** `catch (Exception e) { log.warn(...) }` —— 清理是**旁路维护**，它的失败不该影响任何审查请求。而"本轮跳过"这个措辞明确了：**下一轮会再来，不需要人工介入。**

**③ 零结果用 `debug`，非零用 `info`。**

这是一个很实用的日志分级习惯：**"什么都没发生"不该占用 `info` 的信噪比。** 否则每天的 `info` 日志里有一堆"无需要遗忘的条目"，真正的"归档了 4137 条"会被淹没。

**④ ……这里有一个缺口。**

对比一下隔壁的断点清理任务：

```java
// resume/ResumeJanitor.java
/**
 * 单轮清理数量超过该值即告警：说明不是偶发崩溃，而是清理链路本身没在正常工作
 * （比如 TTL 配错、或者大量审查卡死后无人重试）。
 */
private static final int NOISY_THRESHOLD = 100;
...
} else if (removed > NOISY_THRESHOLD) {
    log.warn("[Resume] 残留断点清理完成：删除 {} 个（TTL={}），数量异常偏高，请检查是否有审查持续崩溃",
            removed, maxAge);
}
```

**`ResumeJanitor` 有"清理量异常告警"，而 `MemoryMaintenanceScheduler` 没有。**

**这个缺口是真实存在的**，它的后果就是本章开头那个痛点：**4137 条经验一次被归档时，日志只是 `info` 一行数字——没有"请检查为什么积了这么多"的提示。**

> **清理量是一个健康指标，不只是一个执行结果。** 一天删 3 条是正常运维；一天归档 4000 条说明**某个上游环节长期没在工作**（比如反馈入口没人用、或者 TTL 配错导致该早删的没删）。

**把 `NOISY_THRESHOLD` 那条判断搬到记忆维护上是本章最便宜的一处改进。**

### 2.6 三层记忆的分工（本讲的边界）

`MemoryLevel` 只有两个值：

<img class="mermaid-svg" src="/zh/book-assets/diag-0098.svg" alt="`MemoryLevel` 只有两个值：" />


**但枚举里只有"短期/长期"两个值，而文档说的是"三层"。** 这个不一致值得点出来——**枚举名和文档不同步，是"多来源真相"的典型信号**：

- 短期：单 PR 内的上下文（`ChatSession` / `MemoryId`，第 05 讲的 `@MemoryId` 就是它）；
- 长期：跨 PR 的经验与知识（就是本讲的 `experience_entry`）；
- "第三层"：通常是**知识库/RAG 检索到的外部知识**——而它在代码里**不是** `MemoryLevel` 的一个值，而是 `KnowledgeStore` 的独立体系（第 22–29 讲）。

**所以"三层"不是这个枚举的职责，而是"三个不同子系统"的合称。** 读代码时如果按枚举去理解架构，你会漏掉第三层。

**本讲的边界**：只讲**长期记忆（经验）的生命周期状态机**。知识库的检索细节在第 22–29 讲；向量底座在第 24 讲。

## 三、代码

### 3.1 `ExperienceLibrary`：接口暴露的是"生命周期动作"，不是 CRUD

<img class="mermaid-svg" src="/zh/book-assets/diag-0099.svg" alt="### 3.1 `ExperienceLibrary`：接口暴露的是&quot;生命周期动作&quot;，不是 CRUD" />


> **图 10-4**　`ExperienceLibrary` 的接口形态。六个方法全部是**语义动作**，没有一个 CRUD 动词。

**注意接口上一个 `update` / `delete` / `save` 都没有。**

**这就是"状态机接口"和"CRUD 接口"的区别**：你无法直接改一条经验的 `stage`——你只能通过**语义动作**（复现、反馈、命中、归档、清理）来推动状态机。

> **接口设计在这里起到了强制作用**：如果接口暴露了 `update(entry)`，那么某一天就会有人写 `entry.setStage(ACTIVE)` 来"临时解决一个问题"，整套生命周期设计当场作废。
>
> **不给那个方法，就没人能用它。**

**再看 `list` 与 `listAll` 的分离**——这是"同一份数据、两个消费视图"的典型：

| 方法 | 消费者 | 内容 |
|---|---|---|
| `list` | **检索链路** | 只含未遗忘（CANDIDATE + ACTIVE） |
| `listAll` | **管理界面** | 含归档，按最近更新倒序 |

**如果只有一个 `list`**（返回全部），那么检索链路就必须自己过滤 `stage`——**而"记得过滤"这件事，迟早会有人忘。** 把"检索视图"做成一个独立方法，等于把过滤规则固化进了接口。

### 3.2 `upsertReflection`：一条 SQL 完成"插入 or 升级"

```java
// PgExperienceLibrary.java:37-56
@Override
public void upsertReflection(String teamId, String pattern, String advice) {
    try {
        db.update("""
                        INSERT INTO experience_entry
                            (team_id, pattern, advice, stage, evidence_pos, source, updated_at)
                        VALUES (?, ?, ?, 'candidate', 1, 'reflection', now())
                        ON CONFLICT (team_id, pattern) DO UPDATE SET
                            advice = EXCLUDED.advice,
                            evidence_pos = experience_entry.evidence_pos + 1,
                            stage = CASE WHEN experience_entry.evidence_pos + 1 >= ?
                                         THEN 'active' ELSE experience_entry.stage END,
                            source = 'reflection',
                            updated_at = now()
                        """,
                teamId, pattern, advice, ACTIVE_EVIDENCE);
    } catch (Exception e) {
        log.warn("[Experience] 经验复现/沉淀失败（不阻断审查）：team={}, 原因={}", teamId, e.getMessage());
    }
}
```

**一条 SQL 里有四处值得学的东西：**

**① `ON CONFLICT (team_id, pattern) DO UPDATE`——"同 pattern 就是同一条经验"。**

这条唯一约束定义了"什么算同一条经验"：**`(team_id, pattern)` 而不是 `pattern`**。团队隔离**内建在唯一键里**——这意味着"跨团队经验不可见"是数据库层保证的，而不是应用层记得加 `where team_id = ?`。

**这是最可靠的做法**：把隔离条件放进约束，而不是放进查询条件。

**② 升级判断在 SQL 里用 `CASE WHEN`，而不是"先查再改"。**

```sql
stage = CASE WHEN experience_entry.evidence_pos + 1 >= ?
             THEN 'active' ELSE experience_entry.stage END
```

**这是一个原子的"条件更新"**，避免了"读到 2 → 加 1 → 判断 ≥3 → 写回"这种 check-then-act 的竞态。

**注意它用的是 `experience_entry.evidence_pos + 1`**（旧值 + 1）而不是 `EXCLUDED.evidence_pos`——因为 `EXCLUDED` 是"新插入的那一行"，它的 `evidence_pos` 恒为 1。**写错这个引用，`evidence_pos` 会永远停在 1，永远升不了级。**

**③ `source = 'reflection'` 会覆盖掉原来的 source。**

如果一条经验最初来自 `seed`（种子）或 `feedback`，一次复现后它的 `source` 就变成 `reflection` 了。**这是一个语义损失**——你无法再回答"这条经验最初是哪来的"。

**更准确的做法**是分成两个字段：`source`（首次来源，不可变）与 `lastSource`（最近来源）。**这不是 bug，但它会让"追溯经验来源"这件事做不到。**

**④ 异常只 WARN，不抛。**

```java
log.warn("[Experience] 经验复现/沉淀失败（不阻断审查）：team={}, 原因={}", teamId, e.getMessage());
```

**"不阻断审查"——记忆是增强，不是必需。** 这条原则在第 06 讲（结构化输出）、第 08 讲（Agent 循环）、第 09 讲（规划）已经出现过三次，这是第四次。

### 3.3 `recordFeedback`：正报"立即 ACTIVE"，误报"计数到阈值"

```java
// PgExperienceLibrary.java:58-99（结构摘要）
@Override
public void recordFeedback(String teamId, String ruleId, boolean falsePositive) {
    List<ExperienceEntry> candidates = new ArrayList<>();
    try {
        for (ExperienceEntry e : db.query(
                "SELECT * FROM experience_entry WHERE team_id = ? AND stage <> 'purged'",
                this::rowMapper, teamId)) {
            if (matchesRule(e.pattern(), ruleId)) {
                candidates.add(e);
            }
        }
    } catch (Exception e) {
        log.warn("[Experience] 反馈关联经验查询失败：team={}, ruleId={}, 原因={}", teamId, ruleId, e.getMessage());
        return;
    }
    for (ExperienceEntry e : candidates) {
        try {
            if (falsePositive) {
                db.update("""
                                UPDATE experience_entry
                                SET evidence_neg = evidence_neg + 1,
                                    stage = CASE WHEN evidence_neg + 1 >= ?
                                                 THEN 'archived' ELSE stage END,
                                    updated_at = now()
                                WHERE team_id = ? AND id = ?
                                """,
                        ARCHIVE_NEGATIVE, teamId, e.id());
            } else {
                db.update("""
                                UPDATE experience_entry
                                SET evidence_pos = evidence_pos + 1,
                                    stage = 'active',
                                    updated_at = now()
                                WHERE team_id = ? AND id = ?
                                """,
                        teamId, e.id());
            }
        } catch (Exception ex) {
            log.warn("[Experience] 经验证据更新失败：team={}, id={}, 原因={}", teamId, e.id(), ex.getMessage());
        }
    }
}
```

**注意 `falsePositive = false` 时（人工正报）：`stage = 'active'`——无条件直接转正，不看计数。**

**这是一个有意的"人力优先"设计**：

| 证据来源 | 判定方式 | 理由 |
|---|---|---|
| 自动复现 | 计数 ≥ 3 | 需要多次独立验证才可信 |
| 人工正报 | **一次即转正** | 人已经确认过了，不需要"验证 3 次" |
| 人工误报 | 计数 ≥ 2 | **要两次才降级** |

**"正报一次即升、误报两次才降"——这个不对称是本讲的第三个设计要点。**

**为什么误报要两次？** 因为**误报的代价不对称**：

- 把一条好经验误判为坏（误报），代价是**失去一条有用的建议**——而且可能是"暂时看不懂它的价值"；
- 让一条坏经验继续生效，代价是**继续产生误报**——但这个代价是渐进的。

**所以降级的门槛要略高于升级的门槛**，给"一次手滑"留缓冲。**1 次就降级，会让"某人手滑点错一次"直接毁掉一条经验。**

再注意循环里的 `try/catch` **在循环体内部**：

```java
for (ExperienceEntry e : candidates) {
    try { ... } catch (Exception ex) { log.warn(...); }
}
```

**同第 06 讲 `LlmFindingParser` 的"逐条隔离"**：一条经验更新失败，不影响其余匹配到的经验。

**最后是那个前缀匹配：**

```java
/** pattern 形如 "ruleId title file"：以 ruleId 为前缀即视为同规则经验。 */
private static boolean matchesRule(String pattern, String ruleId) {
```

**`pattern` 的格式是约定出来的（`ruleId + title + file` 拼接），并靠 `startsWith` 关联。**

**这个约定很脆弱**：它把"结构化信息"编码进了"一个字符串的前缀"。改一下 `pattern` 的拼接格式（比如把 title 放前面），匹配就全线失效——**而且失效方式是"匹配不到任何经验"，不会报错。**

**更结实的设计**是把 `rule_id` 做成独立列 + 索引。**当前实现的代价是：一次全表扫描 + 一个字符串前缀匹配**（`SELECT * FROM experience_entry WHERE team_id = ?` 然后 Java 里循环匹配）。

**在小库上没问题；4137 条时还能忍；到十万条时，每次反馈都要把整个团队的经验全捞进内存。**

### 3.4 那个从未被写入的状态

回到 `ExperienceStage`：

<img class="mermaid-svg" src="/zh/book-assets/diag-0100.svg" alt="回到 `ExperienceStage`：" />


**四个状态里，`PURGED` 从未被任何写入路径使用过。**

因为硬删的实现是 `DELETE FROM experience_entry`——**行被物理删掉了，就不会有任何一行以 `stage = 'purged'` 存在。**

**这是一个"声明了但未实现"的状态**，而它的存在会带来一个具体的误导：

> 读到状态机图（`... → ARCHIVED → PURGED`）的人，会以为存在"已删除但保留痕迹"的中间态——**于是可能写出 `WHERE stage <> 'purged'` 这样的过滤**（`recordFeedback` 里就真的有这一句：`WHERE team_id = ? AND stage <> 'purged'`）。

**这句过滤是冗余的，但它不是错的**——它表达了作者的意图"不要处理已删除的"。**问题在于：它给人一个错误的心智模型**，让人以为删除是"改状态"而不是"删行"。

**两类处置都可以**：

- **要么真的用上它**：硬删改成 `stage = 'purged'` + 定期物理清理（获得"删除留痕"能力，代价是表会长）；
- **要么删掉它**，并在状态机图上明确"ARCHIVED → 物理删除"。

**唯一不能接受的是留着它、让读者猜。** 这是第 09 讲那个"能力分级未显式化"的同一个病——**声明与实现不一致，且不一致本身不可见。**

## 四、避坑清单

- [ ] **记忆必须是状态机，不能只有 `save` / `search`。**
- [ ] **升级靠证据，不靠时间。** 时间不是质量信号，而错的建议往往更容易被反复沉淀。
- [ ] **检索命中不能算正证据**（会形成自我强化循环）。命中只刷新遗忘时钟。
- [ ] **"被用到过"和"被证明有用"是两个概念**，必须用不同字段承载。
- [ ] **计数口径要和语义口径一致。** "同一 PR 内命中 3 次" ≠ "3 次独立验证"——**这个虚高坑在当前实现里是真实存在的。**
- [ ] **遗忘必须分两层**：软删（可恢复，用于止损）+ 硬删（不可恢复，用于回收）。
- [ ] **两个 TTL 用同一时间戳字段时，中间状态必须重置该字段。** 归档时不写 `updated_at = now()`，软删会静默变成硬删（且默认配置必然触发）。
- [ ] **查不到/不认识的状态值要回落到最保守的一档**（未知 → CANDIDATE），而不是最宽松的。
- [ ] **保留检索视图与管理视图两个方法**，别让检索链路自己去过滤。
- [ ] **把隔离条件（team_id）放进唯一约束**，而不是放进查询条件。
- [ ] **升级条件判断放在 SQL 的 `CASE WHEN` 里**，避免 check-then-act 竞态。
- [ ] **正报一次即升、误报要两次才降**——误报的代价不对称，降级门槛应高于升级门槛。
- [ ] **维护任务要错峰、异常不阻断、零结果用 debug。**
- [ ] **清理量是健康指标，要配异常告警**（`ResumeJanitor` 有 `NOISY_THRESHOLD`，记忆维护没有——这是一个真实缺口）。
- [ ] **别把结构化信息编码进字符串前缀**（`pattern` 靠 `startsWith` 匹配规则）。它会随拼接格式变化而静默失效。
- [ ] **枚举里声明了的状态必须真的会被写入**，否则会给人错误的心智模型。

## 本讲小结

1. **记忆是状态机**：CANDIDATE → ACTIVE → ARCHIVED → PURGED。**接口只暴露语义动作，不暴露 CRUD**——不提供 `update`，就没人能绕过状态机。
2. **升级靠证据不靠时间**。而三条信息流必须分开：`evidencePos`（质量 → 升级）、`evidenceNeg`（质量 → 降级）、`hitCount/lastHitAt`（使用 → 反遗忘）。
3. **检索命中绝不能算正证据**——会形成自我强化循环。
4. **计数口径要和语义口径一致**。"同一 PR 内命中 3 次"被算成 3 次复现，是一个**真实存在**的虚高坑。
5. **遗忘分两层**：软删止损（可恢复）、硬删回收（不可恢复）。**而"归档时重置时间戳"是承重墙**——删掉它，软删静默变成硬删。
6. **正报一次即升、误报两次才降**——误报的代价不对称。
7. **清理量是健康指标**。`ResumeJanitor` 有阈值告警，记忆维护没有——**这是一个可修补的真实缺口**。
8. **声明必须等于实现**：`PURGED` 从未被写入，`pattern` 靠字符串前缀匹配规则，`source` 会被覆盖——**三处都不是 bug，但都是"读代码的人会猜错"的地方。**

下一讲处理"给模型的每一句话"：**提示词模板怎么外置、怎么版本化、以及灰度到底该怎么做。**
