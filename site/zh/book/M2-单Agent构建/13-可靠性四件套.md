## 一、痛点

**故障一：一次审查卡死了。**

有个 PR 的审查请求，20 分钟没有返回。运维重启了服务。

查日志，看到的是：

```
[Coordinator] 子Agent[SECURITY] 开始审查（并行执行）
[Coordinator] 子Agent[LOGIC] 开始审查（并行执行）
[Coordinator] 子Agent[PERFORMANCE] 开始审查（并行执行）
（然后什么都没有）
```

**三个 Agent 都没有"完成"的日志。**

代码里明明配了超时（`review.agent.timeout-ms:300000`）。为什么没生效？

**故障二：同一个 PR 被审了两遍。**

用户把 PR 重新推了一次（amend 提交），系统又审了一遍——**并且把同一批问题又评论了一遍**。用户很不高兴。

**故障三：断点续跑功能从来没有生效过。**

你写了断点续跑（`ResumeStore`），测试里也验过。但线上三个月，**日志里从来没出现过"检测到断点"这句话**。

**故障四：一个"降级"的 Agent 在续跑时被跳过了。**

某次审查里，安全 Agent 超时降级了。你期望下次续跑时**重新审一遍安全维度**——但续跑日志显示"已完成 5 个 Agent"，安全被算作"已完成"。

**这四个故障，是同一个模块的四个不同层次的错。** 合起来就是"可靠性四件套"：**幂等、重试、超时、兜底。**

## 二、原理

### 2.1 四件套各管什么

| 件 | 回答的问题 | 失效后的症状 |
|---|---|---|
| **幂等** | 同一个输入被执行两次，会发生什么？ | 重复评论、重复计费、重复写库 |
| **重试** | 失败一次之后要不要再试？ | 可用性低（一次抖动就失败） |
| **超时** | 最多等多久？ | **线程耗尽、请求挂死**（故障一） |
| **兜底** | 全都失败了怎么办？ | 静默通过 / 静默失败（第 06、07 讲） |

**四件套的顺序是有依赖的**：

```
幂等 ──► 重试（重试的前提是"重复执行安全"）
           │
           └──► 超时（重试必须有上限，否则等于无限重试）
                  │
                  └──► 兜底（超时之后要有明确的结果）
```

**注意这个依赖链的起点是幂等。** 如果你先做重试、后做幂等，那么每一次重试都在制造重复副作用——**而这类问题在"重试不常发生"的环境里会潜伏很久**（只有 1% 的请求重试，所以只有 1% 的请求会重复评论）。

### 2.2 超时：`orTimeout` 挂在 `allOf` 上为什么没用

这是本讲最重要的技术点，也是 P0-1 的完整解释。类注释和行内注释都写到了：

```java
// CompletableFutureCoordinator.java
/**
 * <p>设计要点（见文档）：
 * <ul>
 *   <li>为每个 Agent 创建一个 Future，并行执行审查；</li>
 *   <li>使用<b>逐 Future 独立限时等待</b>（共享 deadline 递减，默认 5 分钟）实现超时控制；
 *       修复前曾用 {@code allOf + orTimeout}，但那只作用于聚合节点，后续 {@code join()} 仍会无限阻塞；</li>
 */
```

```java
// CompletableFutureCoordinator.java:473-476
// 2. 并行结果收集：每个 Future 独立限时等待，超时/异常 → 该 Agent 标记为「降级」并入报告。
//    修复前（P0-1）：orTimeout 挂在 allOf 聚合 future 上只触发一条 warn，随后的 join()
//    无超时仍会无限阻塞；advancedFuture 也没进超时体系。现在以同一 deadline 逐个限时取结果，
//    超时即 cancel(true) 中断底层执行线程，绝不无限等待，且降级在报告/轨迹中如实可见。
```

**为什么 `allOf + orTimeout` 是错的？三层原因，逐层看：**

**第一层：`allOf(...)` 返回的是一个"新的" future。**

```java
CompletableFuture<Void> all = CompletableFuture.allOf(f1, f2, f3);
```

`all` **不是** `f1/f2/f3` 中的任何一个。它只是一个"当它们都完成时我也完成"的哨兵。

**所以 `all.orTimeout(...)` 只让这个哨兵超时完成** —— `f1/f2/f3` 完全不受影响。

**第二层：`orTimeout` 不会取消底层任务。**

这是最容易误解的一点。假设你写的是：

```java
List<AgentResult> results = all.orTimeout(5, MINUTES)
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList())
        .join();                        // ← 你以为超时会抛在这里
```

`all.orTimeout(5, MINUTES)` 到期后，**`all` 会以 `TimeoutException` 异常完成**。

**但底层的三个 Agent 任务还在跑。** `orTimeout` 的语义只是"让这个 future 以超时结束"，它**不打断**正在执行的任务——**它甚至不知道任务在哪。**

于是：

- `thenApply` 不会执行（因为 `all` 异常完成了）——
- **但 `join()` 抛异常的位置是 `all`，不是原始 future**；
- **而三个 Agent 线程仍在占用线程池。**

**这就是故障一的真相**：代码"看起来配了超时"，日志里可能还有一条 `WARN`（"只触发一条 warn"），但**请求线程仍在等，工作线程仍在跑**。

**第三层：如果 `join()` 的是原始 future，就完全没有超时。**

```java
// 这是更常见的写错方式
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).orTimeout(5, MINUTES);
// 然后……
for (CompletableFuture<AgentResult> f : futures) {
    results.add(f.join());          // ← 这个 join 跟上面的 orTimeout 毫无关系
}
```

**`join()` 挂在 `f` 上，而 `f` 上没有任何超时。** 上面那行 `orTimeout` 纯属装饰。

> **一句话总结：`orTimeout` 是"给某个 future 的等待设上限"，不是"给一段代码设上限"。**
> 你要给谁设上限，就必须在他身上设。

### 2.3 正确做法：共享 deadline + 逐个 `get(remaining)` + `cancel(true)`

```java
// CompletableFutureCoordinator.java:477-507
long deadline = System.currentTimeMillis() + Math.max(1L, timeoutMillis);
List<AgentDegradation> degradations = new ArrayList<>();
for (int i = 0; i < futures.size(); i++) {
    CompletableFuture<AgentResult> future = futures.get(i);
    ReviewAgent agent = effectiveAgents.get(i);
    long remaining = Math.max(deadline - System.currentTimeMillis(), 1L);
    try {
        AgentResult result = future.get(remaining, TimeUnit.MILLISECONDS);
        mainResults.add(result);
        saveCheckpoint(runId, pr, teamId, resumedResults, mainResults);
    } catch (TimeoutException te) {
        future.cancel(true); // 中断底层执行线程，避免任务泄漏
        String reason = "执行超时（" + timeoutMillis + "ms）";
        log.warn("[Coordinator] 子Agent[{}] 超时（{}ms），已中断并标记降级", agent.getType(), timeoutMillis);
        mainResults.add(AgentResult.degraded(pr.id(), agent.getType(), reason));
        degradations.add(new AgentDegradation(agent.getType().name(), reason));
        if (recorder != null) {
            recorder.append(runId, "agent.degraded", Map.of(
                    "agentType", agent.getType().name(), "reason", reason));
        }
    } catch (Exception e) {
        String reason = rootMessage(e);
        log.warn("[Coordinator] 子Agent[{}] 异常，已标记降级：{}", agent.getType(), reason);
        mainResults.add(AgentResult.degraded(pr.id(), agent.getType(), reason));
        degradations.add(new AgentDegradation(agent.getType().name(), reason));
        ...
    }
}
```

**七个正确的设计动作，逐条看：**

**① 共享 deadline，而不是每个 Agent 各自超时。**

```java
long deadline = System.currentTimeMillis() + Math.max(1L, timeoutMillis);
```

**如果每个 Agent 各自等 5 分钟，5 个 Agent 最坏就是 25 分钟。** 而 `deadline` 是一个**绝对时刻**，所有 Agent 共享它——**总耗时上界是 5 分钟，与 Agent 数量无关。**

> **"总预算"和"每步预算"是两个不同的东西。** 分布式系统里绝大多数超时应该按"总预算"设计，因为用户感知的是总耗时。

**② 每次都重算 `remaining`。**

```java
long remaining = Math.max(deadline - System.currentTimeMillis(), 1L);
```

**不是用固定的 `timeoutMillis`，而是 `deadline - now`。** 这样：

- 第 1 个 Agent 用了 90 秒 → 第 2 个只剩 210 秒可等；
- 前 4 个都用满了 → 第 5 个只剩 1 毫秒（`Math.max(..., 1L)` 保证不出现 0 或负数）。

**`Math.max(..., 1L)` 这一层兜底很重要**：如果 remaining 是 0 或负，`future.get(0, MILLISECONDS)` 会**立刻抛 `TimeoutException`** —— 语义上"没时间了，直接降级"，这其实是对的；但 `get(-1, ...)` 会抛 `IllegalArgumentException`，**就变成了一个不该出现的异常**。

**③ 用 `get(timeout)` 而不是 `join()`。**

`join()` 是"无限等"；`get(timeout, unit)` 是"最多等这么久"。**要带超时就只能用 `get`。**

**④ 超时后必须 `cancel(true)`。**

```java
future.cancel(true); // 中断底层执行线程，避免任务泄漏
```

**这一行是"超时"和"线程泄漏"的分界线。**

`cancel(true)` 的语义是"尝试以中断的方式取消任务"。对 `CompletableFuture.supplyAsync(...)` 提交的任务，它会**尝试中断执行该任务的线程**。

**注意"尝试"——`cancel(true)` 不是强杀。** 如果任务里有阻塞在 `InterruptedException` 之外的代码（比如一个不响应中断的 IO），它不会被立刻打断。**但它至少做了一次努力，而且把 future 标记为 cancelled。**

**如果不 cancel**：请求线程走了（因为 `get` 超时抛了），**工作线程还在跑**——它可能还要跑 3 分钟。**在高峰期，这就是"线程池被慢慢吃光"的机制。**

**⑤ 超时被转化成"降级结果"，而不是异常。**

```java
mainResults.add(AgentResult.degraded(pr.id(), agent.getType(), reason));
degradations.add(new AgentDegradation(agent.getType().name(), reason));
```

**这是"部分可用"的实现**：一个 Agent 超时，其他四个的结果照常进入报告。**而超时的那个在报告里被明确标注。**

**⑥ 每次都存断点。**

```java
saveCheckpoint(runId, pr, teamId, resumedResults, mainResults);
```

**注意它在 `try` 里、在 `get` 成功之后** —— **每个 Agent 成功就落一次盘。** 于是如果第 4 个 Agent 时进程被杀，前 3 个的成果已经保存了。

**这是"断点续跑"能真正省事的根本原因**：断点不是"最后存一次"，而是**增量地存**。

**⑦ 异常也走同一条降级路径。**

```java
} catch (Exception e) {
    String reason = rootMessage(e);
    ...
    mainResults.add(AgentResult.degraded(pr.id(), agent.getType(), reason));
```

**超时和异常的处理几乎完全一样**（都是降级 + 记轨迹），唯一的差别是超时那次要额外 `cancel(true)`。

**而 `rootMessage` 是必要的**——因为 `get()` 抛出的异常是被包装过的：

```java
/**
 * 从 {@link CompletableFuture#get} 抛出的包装异常中解出真正原因。
 * {@code ExecutionException} 包裹的是 Agent 执行体抛出的异常，直接取 cause 才有人类可读信息。
 */
private static String rootMessage(Throwable e) {
    Throwable cause = e;
    while ((cause instanceof ExecutionException || cause instanceof java.util.concurrent.CompletionException)
            && cause.getCause() != null) {
        cause = cause.getCause();
    }
    String msg = cause.getMessage();
    return (msg == null || msg.isBlank()) ? cause.getClass().getSimpleName() : msg;
}
```

**两个细节：**

- **循环解包**（`while` 而不是一次 `getCause()`）——因为 `join()` 抛的是 `CompletionException`，`get()` 抛的是 `ExecutionException`，**而它们可能嵌套**；
- **`msg` 为空时回退类名**——否则报告里会出现"降级原因：（空）"这种毫无信息的告警。

**⑧ 高级静态分析也纳入同一个 deadline。**

```java
// 2.1 高级静态分析同样纳入限时等待（修复前 join() 无超时，可能无限阻塞主线程）
if (advancedFuture != null) {
    long remaining = Math.max(deadline - System.currentTimeMillis(), 1L);
    try {
        results.addAll(advancedFuture.get(remaining, TimeUnit.MILLISECONDS));
    } catch (TimeoutException te) {
        advancedFuture.cancel(true);
        ...
        degradations.add(new AgentDegradation(AgentDegradation.STAGE_ADVANCED_ANALYSIS, reason));
```

**注释点出的教训**："修复前 `join()` 无超时，可能无限阻塞主线程"，以及"`advancedFuture` 也没进超时体系"。

**这是超时类 bug 最典型的样子：你修了一处，但同一个模式在同一个文件里还有第二处。** 修超时问题时，**必须把所有 `join()` / `get()` 无超时的调用点一起找出来。**

### 2.4 同一形状的残留：`DagExecutor`

**这是一个值得单独拎出来的诚实发现。**

`agent-kit` 的 DAG 执行器里，是同一个形状：

```java
// planning/DagExecutor.java
public Map<String, TaskResult> execute(TaskPlan plan, Function<TaskPlan.TaskNode, TaskResult> runner) {
    ...
    Map<String, CompletableFuture<TaskResult>> futures = new LinkedHashMap<>();
    for (TaskPlan.TaskNode n : plan.tasks()) {
        compute(n, byId, futures, runner);
    }
    CompletableFuture.allOf(futures.values().toArray(new CompletableFuture[0])).join();   // ← 无超时
    ...
}
```

**`allOf(...).join()` —— 没有超时。**

`DagExecutor` 的契约是"调用方提供 `Executor`"，而**超时控制完全不在它的职责里**。

**在主线系统里这没问题**，因为 `TaskPlanningSupport` 是**在 Coordinator 的 deadline 内被调用**的——规划路径的结果最终也会被……等一下，**不会。**

看第 09 讲引用过的那段：

```java
// CompletableFutureCoordinator.java:431-436
List<AgentResult> plannedResults = planningSupport == null ? List.of()
        : planningSupport.planAndExecute("审查 PR #" + pr.id() + "：" + pr.title(),
                diffs, enrichedCtx, effectiveAgents, pr.id(), recorder, runId);

List<AgentResult> mainResults = new ArrayList<>();
if (!plannedResults.isEmpty()) {
    mainResults.addAll(plannedResults);
}
```

**`planningSupport.planAndExecute(...)` 是同步调用的**，它在 Coordinator 的主线程上执行，**而 `DagExecutor.execute` 内部的 `join()` 没有超时**。

**于是：规划路径下，"超时体系"不生效。** 如果某个子任务的 `runner` 卡住，**整个审查会一直挂在那里**——正是故障一的形状，只是换了条路径。

> **这是"修了一处，同一形状在别处还有"的第二个例子，而这个例子更值得记住：因为它跨越了仓库边界。**
>
> 在 `code-review-agent` 里做的超时修复，**无法覆盖 `agent-kit` 里那个"由调用方负责超时"的约定** —— 因为约定是隐式的（写在谁的脑子里？），而不是写在类型或文档里。

**补法有两个方向：**

| 方向 | 做法 |
|---|---|
| **把 deadline 传下去** | `execute(plan, runner, Deadline)`，让 `DagExecutor` 自己感知预算 |
| **在调用点包一层** | 用一个带超时的 `CompletableFuture.supplyAsync(() -> planningSupport.planAndExecute(...), executor).get(remaining, MS)` |

**第二个更便宜，且不改 `agent-kit` 的签名**——但它需要调用方**记得包**。而"记得"是不可靠的，所以**更好的是第一个方向**（把 deadline 变成类型系统的一部分，而不是一个需要记住的约定）。

### 2.5 幂等：为什么"随机 traceId"让断点续跑永远是死代码

这是故障三的完整解释，注释写得极其坦率：

```java
// CompletableFutureCoordinator.java:295-302
// 断点续跑幂等键（关键修正）：
// 旧实现直接取 TraceContext.ensure()——那是每次请求随机生成的 traceId。
// 崩溃后「同 PR 重试」是新的 HTTP 请求，拿到的是另一串随机 traceId，
// 于是 resumeStore.load(runId) 永远查不到断点，断点续跑在生产上永远不生效
// （典型的「feature 只在测试里跑过、线上是死代码」）。
// 改为从 PR 身份派生稳定键：同一 PR（owner/repo + 编号 + head SHA）的多次审查共享同一 runId，
// 崩溃恢复时才能命中上次落盘的断点；traceId 仍写入 MDC 供日志链路关联。
String runId = resumeKey(pr);
TraceContext.set(runId);
```

**这段注释里的"典型的『feature 只在测试里跑过、线上是死代码』"，是这一讲最值得带走的一句诊断模板。**

**为什么测试能过？** 因为测试里通常会写成：

```java
// 测试（能过）
String runId = "test-run-1";
coordinator.review(pr);          // 存入断点
resumeStore.load(runId, teamId); // 查得到 → 测试绿
```

**测试用了同一个硬编码的 `runId`，所以永远能命中。** 而生产里 `runId` 每次请求都不同——**测试和生产走了两条不同的路径。**

> **这是一个非常常见的测试盲区：测试自己构造了"本应由生产逻辑生成"的键。**
>
> **判据**：如果一个测试里的某个值，在生产里需要通过一段逻辑计算得到，**那么测试必须调用那段逻辑**，而不是自己写死一个值。

**修法的核心是"从业务身份派生稳定键"：**

```java
/**
 * 断点续跑幂等键：从 PR 身份派生，而非随机 traceId。
 *
 * <p>设计要点：
 * <ul>
 *   <li>必须稳定——同 PR 的多次审查（含崩溃后重试）算出同一个键，才能命中上次落盘的断点；
 *       用随机 traceId 当键是此前断点续跑「永远不生效」的根因。</li>
 *   <li>含 head SHA——同 PR 换了新的 commit 应重开审查而非续跑旧断点，
 *       避免沿用上一个 commit 的半成品（残留断点仍会被 ResumeJanitor 按 TTL 回收）。</li>
 *   <li>headSha 缺失时回落到 {@code repo#id}，保证旧调用方（不带 SHA）也能复用同一键。</li>
 * </ul>
 */
private static String resumeKey(PullRequest pr) {
    return PullRequest.resumeKey(pr.repo(), pr.id(), pr.headSha());
}
```

**三个设计要点，逐条看：**

**① "必须稳定"** —— 这是幂等键的第一属性。同一个逻辑实体 → 同一个键。

**② "含 head SHA" —— 这一条同时解决了故障二（重复评论）。**

设想：用户 amend 了提交，PR 编号没变，但代码变了。

- **如果键是 `repo#id`**：系统会认为"这个 PR 我审过了"，然后**要么跳过、要么续跑旧断点**——**结果是用旧代码的结论去评论新代码。**
- **如果键是 `repo#id#headSha`**：新的 commit 意味着**新的键**，于是**重开一次完整审查**。

**这才是"PR 更新后重新审查"的正确语义。**

**③ "headSha 缺失时回落"** —— 向后兼容。旧调用方不传 SHA 时仍然能用，只是失去了"换 commit 应重开"的能力。

**再看那个"键"和"traceId"的分离：**

```java
String runId = resumeKey(pr);      // 幂等键（业务身份派生，稳定）
TraceContext.set(runId);           // 同时用作 traceId（日志链路关联）
```

**注意这里把 `runId` 当作 `traceId` 用** —— 也就是**日志的链路 ID 等于业务幂等键**。

**这是一个可讨论的取舍**：

| | 好处 | 代价 |
|---|---|---|
| **runId = traceId（当前）** | 日志和断点用同一个 ID，排障时不用做映射 | **同一个 PR 的多次审查，日志链路 ID 相同** → 无法区分"这一次"和"上一次" |
| 分离（runId 稳定、traceId 每请求唯一） | 每次执行可独立追踪 | 需要维护两个 ID 的映射 |

**当前选择的默认值牺牲了"区分单次执行"的能力。** 而这对排障是有影响的：

> 用户报"我这次审查有问题"。你去搜日志，`grep runId` 会返回**这个 PR 历史上所有审查的日志** —— 而你需要的是**这一次**。

**注释里说"traceId 仍写入 MDC 供日志链路关联"**，这确实做到了关联。**但它没有解决"单次执行不可区分"这个问题** —— 而这正是"重试/续跑"场景下你最需要的。

**一个便宜的补法**：在 MDC 里额外放一个 `attemptId`（每次请求新生成），日志同时打两个 ID：`runId`（业务）+ `attemptId`（这一次）。

### 2.6 兜底：降级的 Agent 不能算"已完成"

这是故障四，实现只有几行：

```java
/**
 * 保存断点快照：已完成 Agent 类型 + 已产出发现（供崩溃后同 runId 续跑）。
 * 仅统计主审查 Agent（高级静态分析每次重跑，不参与断点）。
 */
private void saveCheckpoint(String runId, PullRequest pr, String teamId,
                            List<AgentResult> resumed, List<AgentResult> mainResults) {
    if (resumeStore == null) {
        return;
    }
    Set<AgentType> done = new HashSet<>();
    List<Finding> findings = new ArrayList<>();
    for (AgentResult r : resumed) {
        if (r.degraded()) {
            continue;
        }
        done.add(r.agentType());
        findings.addAll(r.findings());
    }
    for (AgentResult r : mainResults) {
        if (r.degraded()) {
            continue; // 降级（超时/异常）的 Agent 不写入断点：续跑时应重试而不是当作已完成
        }
        done.add(r.agentType());
        findings.addAll(r.findings());
    }
    resumeStore.save(new ResumeState(runId, pr.id(), pr.repo(), teamId, done, findings,
            System.currentTimeMillis()));
}
```

**两处 `if (r.degraded()) { continue; }`，注释把理由写清楚了：**

> 降级（超时/异常）的 Agent 不写入断点：**续跑时应重试**而不是当作已完成。

**这是"降级"和"完成"必须严格区分的第二个理由**（第一个是第 06/07 讲的"报告里要如实标注"）。

**如果这里不 continue**：一个超时的安全 Agent 会被记为"已完成"，于是**续跑时它被跳过** —— 用一份"没有安全审查"的报告宣布"审查完成"。

> **"完成"这个词的含义必须精确：它应该是"成功地完成了"，而不是"尝试过了"。**
>
> 一个 `Set<AgentType> done` 如果既装"成功的"又装"失败的"，那么它之上构建的所有逻辑（续跑、覆盖率统计、SLA）都会跟着错。

**断点还有一处生命周期动作：正常完成要清理。**

```java
// 6. 落地本轮审查历史（供下次复检与质量趋势统计）
if (historyStore != null) {
    historyStore.save(teamId, new ReviewHistoryEntry(
            pr.id(), pr.repo(), runId, System.currentTimeMillis(),
            toSummaries(report.getFindings())));
}

// 6.1 正常完成 → 清理断点（不留脏状态）
if (resumeStore != null) {
    resumeStore.complete(runId, teamId);
}
```

**"正常完成 → 清理断点（不留脏状态）"** —— 这一行和 `saveCheckpoint` 配对：**断点的生命周期是"从第一次保存到正常完成"，而不是"永久保留"。**

**注意它放在"落地审查历史"之后** —— **顺序是对的**：先保存最终结果，再清理中间状态。反过来的话，如果清理成功但保存历史失败，你就同时失去了断点和最终结果。

### 2.7 兜底的兜底：孤儿断点的回收

**`complete()` 只在"正常完成"时被调用。** 那么进程被杀、机器重启之后呢？

看 `ResumeJanitor` 的类注释，它把问题分析得很完整：

```java
// resume/ResumeJanitor.java
/**
 * 断点残留清理任务（孤儿断点的兜底回收）。
 *
 * <p>{@link ResumeStore#complete} 只在审查<b>正常完成</b>时被调用。进程被杀、机器重启之后，
 * 若那个 runId 再也不被触发（PR 被关闭 / 合并 / 换了新的 commit），断点就会永远残留在存储中。
 * 文件存储最容易被忽略的运维问题不是性能、不是一致性，而是这种<b>缓慢的泄漏</b>：
 * 每次崩溃漏一个，攒几个月就攒出一堆垃圾（PG 行版同样需要兜底回收）。
 *
 * <p>为什么不放进 {@code ScheduledScanService}：那是技术债务巡检服务，装配需要
 * {@code GiteaApiClient} / {@code Coordinator} 一整套依赖，且 {@code scan.enabled=false} 时整体跳过。
 * 断点清理是存储自身的生命周期管理，与是否开启巡检无关，必须独立。
 *
 * <p>为什么不会误删正在进行的审查：判据是断点最后更新时间，只要审查还在推进就会不断
 * {@link ResumeStore#save} 覆盖刷新，超过 TTL 没有任何写入就等价于「这次审查已经死了」。
 */
```

**三个问题，三个回答，都是可复用的判断：**

**① 泄漏的形态是"缓慢的"。** "每次崩溃漏一个，攒几个月就攒出一堆垃圾" —— **这类问题的特点是"永远不会在测试环境出现"**（测试环境每天重启，每天也不是崩溃几次）。

**② "为什么不放进已有的巡检任务"** —— 因为**职责不同**：

| | 巡检服务 | 断点清理 |
|---|---|---|
| 职责 | 技术债扫描 | **存储自身的生命周期管理** |
| 依赖 | `GiteaApiClient` + `Coordinator` 一整套 | **只有 `ResumeStore`** |
| 开关 | 受 `scan.enabled` 控制 | **必须独立于任何功能开关** |

**"与是否开启巡检无关，必须独立"** —— 这是一个很实用的架构判断：**一个清理任务不应该因为"用户关掉了某个功能"就停止工作**，否则垃圾会开始堆积。

**③ "为什么不会误删正在进行的审查"** —— 判据是"最后更新时间"：

> 只要审查还在推进就会不断 `ResumeStore#save` 覆盖刷新，超过 TTL 没有任何写入就等价于「这次审查已经死了」。

**这就是 2.3 节那个"每次都存断点"（`saveCheckpoint` 在循环里）的第二个收益**：它**同时充当了心跳**。

**如果断点只在最后存一次**，那么"最后更新时间"就毫无意义——它无法区分"审查已经死了"和"审查正在慢慢跑"。

> **幂等 + 心跳 + TTL 回收，是三个设计咬合在一起的结果。** 单独看 `saveCheckpoint` 在循环里，你会觉得"为什么要存这么多次"；结合 `ResumeJanitor` 看，才知道那是**心跳**。

最后看 TTL 和那个告警阈值：

```java
/**
 * 单轮清理数量超过该值即告警：说明不是偶发崩溃，而是清理链路本身没在正常工作
 * （比如 TTL 配错、或者大量审查卡死后无人重试）。
 */
private static final int NOISY_THRESHOLD = 100;

private final Duration maxAge;

public ResumeJanitor(ResumeStore store,
                     @Value("${review.resume.ttl:24h}") Duration maxAge) {
    this.store = store;
    this.maxAge = maxAge;
}

@Scheduled(cron = "${review.resume.cleanup-cron:0 30 3 * * *}")
public void purge() {
    int removed;
    try {
        removed = store.purgeExpired(maxAge);
    } catch (RuntimeException e) {
        // 清理属于旁路维护，绝不影响审查主链路
        log.warn("[Resume] 残留断点清理异常（本轮跳过）：{}", e.getMessage());
        return;
    }
    if (removed == 0) {
        log.debug("[Resume] 残留断点清理完成：无残留（TTL={}）", maxAge);
    } else if (removed > NOISY_THRESHOLD) {
        log.warn("[Resume] 残留断点清理完成：删除 {} 个（TTL={}），数量异常偏高，请检查是否有审查持续崩溃",
                removed, maxAge);
    } else {
        log.info("[Resume] 残留断点清理完成：删除 {} 个（TTL={}）", removed, maxAge);
    }
}
```

**TTL = 24 小时，cron = 03:30（错峰，记忆维护在 03:40）。**

**`NOISY_THRESHOLD = 100` 这条告警的设计思路值得再强调一次**（第 10 讲也提过）：

> **清理量是一个健康指标，不只是一个执行结果。**

- 删 3 个 → 正常（偶发崩溃）；
- **删 150 个 → 不是"删了多少"的问题，而是"为什么积了这么多"** —— 日志直接给出排查方向："请检查是否有审查持续崩溃"。

**而它的实现成本是 3 行代码。** 这是"把运维经验编码进日志"的典型例子。

### 2.8 把超时、降级、断点、留痕串起来看

**一次超时发生后，系统里同时发生了七件事**（对照 2.3 节的代码）：

| # | 动作 | 目的 |
|---|---|---|
| 1 | `future.cancel(true)` | **止损**：不让线程泄漏 |
| 2 | `AgentResult.degraded(...)` | **如实**：报告里标注"这次没看成" |
| 3 | `AgentDegradation` 进入 `degradations` | **汇总**：报告顶部告警块 |
| 4 | `recorder.append(runId, "agent.degraded", ...)` | **留痕**：轨迹可回放 |
| 5 | **不写进断点** | **可重试**：续跑时重跑这个维度 |
| 6 | `log.warn(..., timeoutMillis)` | **可观测**：日志里有具体数字 |
| 7 | `saveCheckpoint(...)` 保存其他成功的 Agent | **不浪费**：已完成的成果保留 |

**这七件事缺任何一件，都会留下一个具体的后果**：

- 缺 1 → 线程泄漏；
- 缺 2 → "0 条发现"被读成"代码没问题"；
- 缺 5 → 续跑时用残缺的报告宣布完成；
- 缺 7 → 一次崩溃白跑全部。

> **这就是"可靠性"的工程含义：不是"不出故障"，而是"出故障时，系统的每一个部分都还在正确的状态上"。**

## 三、代码：一张表看清四件套在本项目的落点

| 件 | 实现位置 | 关键动作 |
|---|---|---|
| **幂等** | `PullRequest.resumeKey(repo, id, headSha)` | 从业务身份派生稳定键；含 headSha 使"换 commit 重开" |
| **重试** | `ModelGateway`（第 07 讲）+ 断点续跑 | 临时错误退避重试；崩溃后同 runId 续跑剩余 Agent |
| **超时** | `CompletableFutureCoordinator` 共享 deadline | `get(remaining)` + `cancel(true)`；`remaining` 每次重算；`Math.max(..., 1L)` 兜底 |
| **兜底** | `AgentResult.degraded` + `AgentDegradation` + `ResumeJanitor` | 降级标注入报告；降级不写断点；孤儿断点 TTL 回收 |

## 四、避坑清单

- [ ] **`orTimeout` 不打断底层任务。** 它只让那个 future 以超时结束，工作线程继续跑。
- [ ] **`allOf(...)` 返回的是新 future**，在它上面设超时对原始 future 无效。
- [ ] **`join()` 永远不超时。** 要超时只能用 `get(timeout, unit)`。
- [ ] **用共享 deadline，不用"每步各自超时"。** 后者最坏耗时 = 步数 × 单步超时。
- [ ] **每次重算 `remaining = deadline - now`**，并用 `Math.max(..., 1L)` 兜住 0 和负数。
- [ ] **超时后必须 `cancel(true)`**，否则是线程泄漏。
- [ ] **`get()`/`join()` 的异常要循环解包**（`ExecutionException` / `CompletionException` 可能嵌套），消息为空时回退类名。
- [ ] **修超时问题时要找出"同一形状的所有调用点"** —— 同一个文件里往往还有第二处（本项目是 `advancedFuture`，跨仓库还有 `DagExecutor`）。
- [ ] **幂等键必须从业务身份派生，不能用随机 ID**（traceId / UUID / 时间戳）。用随机 ID 的后果是"功能只在测试里跑过"。
- [ ] **幂等键要含"会改变结论的版本维度"**（这里是 headSha），否则会用旧结论评论新代码。
- [ ] **测试不要自己硬编码那些"生产里需要计算得到"的键**，否则测试和生产走了两条路径。
- [ ] **"降级"绝不能写进"已完成"集合。** 续跑时必须重试降级的维度。
- [ ] **断点要在循环里增量保存**（每个 Agent 成功就存），它同时是**心跳**。
- [ ] **先保存最终结果，再清理中间状态**（顺序反了会双输）。
- [ ] **清理任务要独立于功能开关**，别让"关掉某个功能"导致垃圾堆积。
- [ ] **清理要有 TTL 判据（最后更新时间）**，而它能成立的前提是"有增量心跳"。
- [ ] **清理量要配异常阈值告警**——它是健康指标，不是执行结果。
- [ ] **一个 traceId 同时当幂等键，会牺牲"区分单次执行"的能力**。重试/续跑场景下应额外带一个 attemptId。

## 五、动手任务

> **任务一：亲手复现 P0-1（这一讲必须做的实验）。**
>
> **仓库位置**：`code-review-agent`（或一个独立的 Java 类）
>
> **操作**：写一段代码，三个任务分别 sleep 30 秒：
> ```java
> List<CompletableFuture<String>> futures = IntStream.range(0, 3)
>         .mapToObj(i -> CompletableFuture.supplyAsync(() -> {
>             try { Thread.sleep(30_000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
>             return "task-" + i;
>         }))
>         .toList();
>
> // ❌ 错误写法
> long t0 = System.currentTimeMillis();
> CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
>         .orTimeout(1, TimeUnit.SECONDS);
> List<String> r = futures.stream().map(CompletableFuture::join).toList();   // ← 这里还是等 30 秒
> System.out.println("耗时 " + (System.currentTimeMillis() - t0) + "ms");
> ```
>
> **预期结果**：**耗时约 30000ms**——`orTimeout` 那行完全没有作用。
>
> **然后改成正确写法**：
> ```java
> long deadline = System.currentTimeMillis() + 1000;
> for (CompletableFuture<String> f : futures) {
>     long remaining = Math.max(deadline - System.currentTimeMillis(), 1L);
>     try { r.add(f.get(remaining, TimeUnit.MILLISECONDS)); }
>     catch (TimeoutException e) { f.cancel(true); r.add("degraded"); }
> }
> ```
> **预期结果**：**耗时约 1000ms**，三个结果都是 `degraded`。
> **追加验证**：在 `cancel(true)` 后打印 `f.isCancelled()`，并在任务里打印 `Thread.currentThread().isInterrupted()`——**你会看到"取消"确实传到了工作线程。**
>
> **任务二：验证"随机幂等键 = 死代码"。**
> 1. 写一个 `InMemoryResumeStore`，用 `"run-1"` 作 key 存一个断点。
> 2. 让"第二次请求"用 `UUID.randomUUID().toString()` 当 key 调 `load(...)`。
> 3. 断言返回的 `Optional` 是否为空。
>
> **预期结果**：**为空**——于是"检测到断点"这段逻辑永远不会执行。
> **思考题**：如果你的测试写的是 `String runId = "test-run-1"`（两次都用同一个），它会通过。**这就是"feature 只在测试里跑过"的机制。正确的测试应该调用 `PullRequest.resumeKey(...)` 来取键。**
>
> **任务三：验证"降级不写断点"。**
> 1. 构造两个 Agent：一个正常返回、一个抛异常。
> 2. 跑一次 `review`，然后读 `resumeStore.load(runId, teamId)`。
> 3. 断言 `doneAgents()` 的内容。
>
> **预期结果**：**只包含那个正常的 Agent。** 异常的那个不在集合里 —— 于是续跑时它会被重试。
> **把 `saveCheckpoint` 里那两个 `if (r.degraded()) continue;` 删掉**，断言变成 2 个 —— 这就是"用残缺报告宣布审查完成"。
>
> **任务四：给 `DagExecutor` 加上 deadline。**
> 参照 2.4 节的两种方向，选一个实施，并用一个"永不返回的 runner"验证。
> **验收标准**：`execute(...)` 在预算耗尽后返回（而不是永远挂住），且被跳过的任务在结果里**能被区分出"未执行"**（提示：这也是第 09 讲那个"跳过与失败被压成一个状态"的缺口）。

## 本讲小结

1. **四件套的顺序是幂等 → 重试 → 超时 → 兜底**，起点必须是幂等（否则每次重试都在制造重复副作用）。
2. **`orTimeout` 不打断底层任务、`allOf` 返回的是新 future、`join()` 永不超时** —— 这三点合起来解释了故障一。
3. **正确做法：共享 deadline + 每次重算 `remaining` + `get(remaining)` + 超时后 `cancel(true)`。**
4. **"总预算"和"每步预算"是两个概念**。用户感知的是总耗时，所以超时应该按总预算设计。
5. **修超时问题要找出同一形状的所有调用点**——本项目里 `advancedFuture` 是第二个，`DagExecutor`（跨仓库）是第三个。
6. **幂等键必须从业务身份派生，并包含会改变结论的版本维度**（headSha）。用随机 traceId 会导致"功能只在测试里跑过"。
7. **测试不要硬编码那些生产里需要计算得到的键** —— 这是"测试绿、线上死"的机制。
8. **"降级"绝不进"已完成"集合**；**断点要增量保存**（它同时是心跳，`ResumeJanitor` 的 TTL 判据依赖它）。
9. **清理任务要独立于功能开关，并给清理量配阈值告警**——清理量是健康指标。
10. **可靠性的工程含义不是"不出故障"，而是"出故障时每个部分都还在正确的状态上"**：止损、如实、留痕、可重试、不浪费。

模块二到此结束。你现在有了一个**完整的单 Agent 骨架**：循环、工具、记忆、提示词、上下文、可靠性。

**从第 14 讲开始，我们把一个 Agent 变成五个——并处理随之而来的新问题：谁说了算、怎么并行、结果怎么合。**
