## 一、痛点

RAG 上线了。日志显示每次审查都成功注入了 5 条相关知识。你挺满意的。

然后你抽查了一份报告的实际 prompt，看到注入段落是这样的：

```
【相关规范与历史知识（RAG 检索，仅供参考，不替代代码事实）】
- [handbook/java-coding-standard.md] 4.2 异常处理：捕获异常后必须记录日志或重新抛出，禁止吞掉异常。
- [handbook/java-coding-standard.md] 4.2.1 禁止 catch (Exception e) {} 这类空捕获块。
- [handbook/java-coding-standard.md] 4.3 日志规范：异常日志必须包含上下文信息，如入参与关键变量。
- [handbook/java-coding-standard.md] 4.2 异常处理：捕获异常后应当记录日志或向上抛出，不要静默忽略。
- [handbook/java-coding-standard.md] 4.2.2 空捕获块是最常见的异常处理缺陷，评审时必须指出。
```

**"注入了 5 条" —— 但它们全都来自 `4.2 异常处理` 这一节。**

而你这次审查的关键问题是**并发安全**（diff 里有一个 `HashMap` 被多线程写）。

**5 条知识，覆盖了 1 个知识点，而真正需要的那一个知识点没进来。**

这一讲就讲清楚：**从"检索到 50 个候选"到"注入 5 条"，中间那些被缩掉的 45 条是怎么缩的、以及为什么不能只按"相关性"排序。**

## 二、原理

### 2.1 上下文预算是三层漏斗，不是一次筛选

`RagContextBuilder` 的类注释直接给出了链路：

```java
// memory/RagContextBuilder.java
/**
 * <p>审查前检索规范文档 / 历史 PR / 安全 Wiki，将相关内容作为【相关历史知识】注入提示词。
 * 内部链路对标业界最佳实践：
 * <pre>
 *   提取查询 → [查询改写(可选)] → 混合检索(向量+BM25,RRF融合) → 阈值过滤(abstain)
 *        → Cross-Encoder重排 → Top-5格式化
 * </pre>
 */
```

**这条链里有三个数量级不同的窗口：**


<img class="mermaid-svg" src="/zh/book-assets/diag-0034.svg" alt="这条链里有三个数量级不同的窗口：" />

> **图 12-1**　上下文的三级收窄：从 50 条候选，到 15 条精排，到 5 条注入。**每一级都是一次不可逆的淘汰**——被淘汰的候选，后面的环节再聪明也拿不回来。

```java
/** 初检召回数（重排前）。业界召回窗 Top-50~200 再精排，默认 50（可配 {@code review.rag.retrieve-k}）。 */
@Value("${review.rag.retrieve-k:50}")
private int retrieveK = 50;
/** 最终注入 Top-N（精排输出）。 */
@Value("${review.rag.inject-top-n:5}")
private int injectTopN = 5;
```

**为什么不能一步到位——直接把 50 砍成 5？**

因为 **"相关"和"该给模型看"是两个不同的问题**：

| 阶段 | 优化目标 | 手段 |
|---|---|---|
| 召回（50） | **不要漏**（召回率） | 宽窗口 + 混合检索 |
| 精排（15） | **把最相关的排前面** | Cross-Encoder 重排 |
| 注入（5） | **信息量最大化 + 不冗余** | MMR 多样性 + 去重 + 格式化 |

**如果只有"召回 + 注入"**，你注入的就是"按向量相似度排的前 5 名"——**而向量相似度天然倾向于"同一段话的不同说法"**，因为它们在向量空间里挨得很近。**这就是痛点里那 5 条全都来自同一节的原因。**

**精排窗的存在意义是"给多样性留挑选余地"**，看代码：

```java
// RagContextBuilder.java:165-172
// 4. Cross-Encoder 重排：开 MMR 时给更大的候选池，否则 MMR 没有挑选余地
int rerankPool = mmrEnabled
        ? Math.min(passed.size(), Math.max(injectTopN * 3, injectTopN))
        : injectTopN;
List<MemoryEntry> reranked = reranker.rerank(query, passed, rerankPool);
// 5. MMR 多样性挑选（相关性 − 冗余度）：避免 Top-N 被同章节高度相似的碎片占满
List<MemoryEntry> picked = (mmrEnabled && reranked.size() > injectTopN)
        ? mmrSelect(reranked, query, injectTopN) : reranked;
```

**注释里那两句话是同一个设计的两个必要部分：**

> "开 MMR 时给更大的候选池，否则 MMR 没有挑选余地"
> "避免 Top-N 被同章节高度相似的碎片占满"

**如果 `rerankPool == injectTopN == 5`，那么重排只返回 5 条，MMR 面对"只有 5 个候选、要挑 5 个"的处境——它什么都挑不了，只能原样返回。** MMR 就退化成了一次空转。

> **一条通用的经验：任何"从 N 个里挑 K 个"的算法（MMR、去重、采样、限流），它的上游窗口必须显著大于 K。否则它不报错，它只是什么都不做。**

**而 `Math.min(passed.size(), Math.max(injectTopN * 3, injectTopN))` 这个表达式里，外层的 `Math.max(topN*3, topN)` 是冗余的**（`topN*3` 恒 ≥ `topN`，除非 `topN` 为 0 或负）。真正起作用的是 `Math.min(passed.size(), injectTopN * 3)`。

**这类"冗余的 max"不是 bug，但它是"表达式在表达意图时不够干净"的信号**——读代码的人会花几秒去确认"是不是有 topN 为负的情况"。**简化成 `Math.min(passed.size(), injectTopN * 3)` 语义完全相同。**

### 2.2 查询质量决定一切：旧的"截 diff 前 500 字符"

这是本讲里**收益最大的一处修复**，注释写得非常直接：

```java
// RagContextBuilder.java:244-253
/**
 * 从代码变更中提炼检索查询（<b>结构化</b>：文件 / 类 / 方法 / 符号）。
 *
 * <p>旧实现直接把 diff 拼起来取前 500 字符——里面塞满 {@code +/-}、行号与上下文噪音，
 * 拿这段噪声去撞以自然语言术语为主的规范库，语义鸿沟极大，而且截断后真正改动的方法
 * 常常根本没被包含。现委托 {@link DiffQueryExtractor} 提炼成贴近知识库措辞的查询。
 */
private String extractQueryFromDiffs(List<CodeDiff> diffs) {
    return DiffQueryExtractor.extract(diffs);
}
```

**"旧实现直接把 diff 拼起来取前 500 字符"——这一句描述了三重错误：**

| 错误 | 后果 |
|---|---|
| 查询里是 diff 原文（`+` / `-` / 行号 / 上下文噪音） | 与规范库的**术语体系完全不同**，向量空间里根本挨不上 |
| 截断取**前** 500 字符 | **真正改动的方法常常在 500 字符之外** —— 查询指向的是无关内容 |
| 不分文件/类/方法边界 | 检索结果**无法定位到具体维度**（安全？并发？异常？） |

**这三重错误叠加起来，就是"检索经常返回看似相关其实无关的东西"的根因。**

**修法是"把查询从原始形态翻译成知识库的措辞形态"** —— 这正是"查询改写"（query rewrite）在工程上的具体含义。

### 2.3 查询改写：可选的增强，失败即恒等降级

```java
/** 查询改写器（默认恒等；由容器按配置注入 LLM 实现，无 Spring 时测试可 new 后覆写）。 */
private ReviewQueryRewriter queryRewriter = new IdentityQueryRewriter();

/**
 * 容器注入查询改写器（{@code review.rag.query-rewrite.enabled=true} 时由配置类装配
 * LLM 实现；否则容器无此 bean，required=false 保留默认恒等，链路零感知）。
 */
@Autowired(required = false)
public void setQueryRewriter(ReviewQueryRewriter queryRewriter) {
    if (queryRewriter != null) {
        this.queryRewriter = queryRewriter;
    }
}
```

**这里有三个值得学的设计动作：**

**① 默认是"恒等改写"（`IdentityQueryRewriter`），不是 null。**

恒等改写的语义是"输入什么就输出什么"。**于是整条链路永远不需要判空** —— 这是"用空对象代替 null"的经典应用。

**② `@Autowired(required = false)` + setter 注入，而不是构造器注入。**

因为查询改写是一个**可选能力**：容器里没有这个 bean 时，链路的其他部分照常工作。**用 setter 注入 + `required = false`，就实现了"有则用、无则保留默认"。**

> **这和 `ReviewEnhancements`（第 13 讲会细讲）是同一个手法**：**把可选能力做成一个"可空字段 + 显式空实现"，而不是散落各处的 null 判断。**

**③ 失败降级是"绝不劣化"。**

```java
// RagContextBuilder.java:146-153
// 1b. 查询改写：diff 形态 → 规范术语形态（可选；失败降级恒等，绝不劣化）
String query = queryRewriter.rewrite(rawQuery);
if (!query.equals(rawQuery)) {
    log.info("[RAG] 查询改写（{} → {}）：{} 字符 → {} 字符",
            queryRewriter.name(), agentType, rawQuery.length(), query.length());
}
```

**"失败降级恒等，绝不劣化"——这六个字是一条硬约束。**

**为什么强调"绝不劣化"？** 因为 LLM 改写有可能**把查询改得更差**（引入幻觉的词、丢掉关键标识符）。所以：

- 改写的实现**必须保证"最坏情况等于原查询"**（比如：LLM 调用超时/失败/输出为空时，返回输入原样）；
- 并且**要记录改写的长度变化**，这是一个便宜的"是否跑偏"的信号（`rawQuery.length() → query.length()`，如果从 200 字变成 8 字，基本可以断定丢信息了）。

**注意这里只记录了"变了"，没有记录"变了什么"。** 如果日志里带上两段文本的前若干字符，排障会容易得多——**这是本章可以做的一个小改进。**

### 2.4 MMR：为什么"相关性排序"不够

```java
// RagContextBuilder.java:255-305
/**
 * MMR（Maximal Marginal Relevance）挑选：
 * {@code argmax( λ·relevance(块, 查询) − (1−λ)·max redundancy(块, 已选集合) )}。
 *
 * <p>解决的问题：重排后的 Top-N 经常被同一章节的相邻碎片占满（内容高度雷同），
 * 看似注入了 5 条，实际只覆盖 1 个知识点。MMR 在「相关」与「信息量新增」之间取平衡。
 */
```

**MMR 的公式只有两个项，但它的直觉非常重要：**

```
score(候选) = λ × 相关性(候选, 查询) − (1−λ) × 最大冗余(候选, 已选集合)
```

- 第一项：**"它和问题有多相关"**（越大越好）；
- 第二项：**"它和已选的那些有多像"**（越大越扣分）。

**λ = 0.7**（`MMR_LAMBDA`）：

- λ 越接近 1 → 越只看相关性 → 退化成纯排序（回到痛点）；
- λ 越接近 0 → 越只看多样性 → 会选出一堆"互不相似但也不相关"的东西。

**0.7 是业界常用的折中**：相关性是主导因素，但冗余要扣分。

**MMR 是贪心的：每轮选一个分最高的加入已选集合，然后重新计算。** 所以它是 `O(topN × 候选数)`。

**实现里有两处细节值得逐字读。**

**细节一：候选词集必须预计算一次。**

```java
java.util.Set<String> qTokens = TextTokenizer.tokenize(query);
// 候选词集预计算一次：MMR 是 O(topN × 候选) 的贪心，
// 若每轮外层都重新分词，长内容会被重复解析 topN 次（纯浪费且随块长放大）。
List<java.util.Set<String>> candTokens = new java.util.ArrayList<>(candidates.size());
for (MemoryEntry c : candidates) {
    candTokens.add(TextTokenizer.tokenize(c.content()));
}
```

**注释把浪费量算清楚了**：如果不预计算，每个候选会被分词 `topN` 次。候选池 15 条、topN 5 → **75 次分词，而不是 15 次**。而分词的代价随文本长度线性增长——**所以这个浪费会随着块变长而放大。**

**细节二（本讲最精妙的一处）：`rest` 存的是下标，不是对象。**

```java
// rest 存候选下标而非对象：①可直接复用预计算的词集；②避免按对象 remove（
// MemoryEntry 是 record，同内容条目 equals 相同，按对象删会误删/删错）。
List<Integer> rest = new java.util.ArrayList<>();
for (int i = 0; i < candidates.size(); i++) {
    rest.add(i);
}

while (selected.size() < topN && !rest.isEmpty()) {
    int bestPos = 0;
    int bestIdx = rest.get(0);
    double bestScore = Double.NEGATIVE_INFINITY;
    for (int p = 0; p < rest.size(); p++) {
        java.util.Set<String> cTokens = candTokens.get(rest.get(p));
        double rel = jaccard(qTokens, cTokens);
        double redundancy = 0.0;
        for (java.util.Set<String> s : selectedTokens) {
            redundancy = Math.max(redundancy, jaccard(s, cTokens));
        }
        double mmr = MMR_LAMBDA * rel - (1 - MMR_LAMBDA) * redundancy;
        if (mmr > bestScore) { bestScore = mmr; bestIdx = rest.get(p); bestPos = p; }
    }
    selected.add(candidates.get(bestIdx));
    selectedTokens.add(candTokens.get(bestIdx));
    rest.remove(bestPos);              // ← 按下标删，不按对象删
}
```

**`rest.remove(bestPos)` —— `List<Integer>.remove(int)` 是按索引删。**

**如果 `rest` 是 `List<MemoryEntry>`，那么 `rest.remove(candidate)` 会是 `remove(Object)` —— 而 `MemoryEntry` 是 `record`，它的 `equals` 是"字段全等"。**

**于是 "删掉这个对象"会变成"删掉所有与它字段相同的对象"。** 而 dedupe 之前的候选里，**内容相同的块是完全可能存在的**（下一节就讲这个）。**结果是：你以为删了一个，实际删了两个甚至三个，MMR 的输出数量不对，而且不报错。**

> **`List.remove` 的两义性是 Java 里一个经典的静默陷阱**：`remove(int)` 删索引，`remove(Object)` 删元素。
>
> **当泛型参数是 `Integer` 时，这个两义性最危险**——`list.remove(1)` 到底是"删下标 1"还是"删值为 1 的元素"？**答案是前者**（因为 `int` 更具体）。**这行代码看起来完全合理，但它删的东西可能不是你想的那个。**

**这里的解法是"用下标列表避免这个问题"**，同时顺手获得了复用预计算词集的好处。**两个收益一次改动拿到——这是很好的工程判断。**

### 2.5 注入前去重：重叠切块的副作用

```java
/**
 * 按内容去重：handbook 等被重叠切块后，同一语义段会产出多个近似块，
 * 重排后 Top-N 可能被同源重复块占满，导致注入内容高度雷同。此处按 content 归一化后去重。
 */
private List<MemoryEntry> dedupeByContent(List<MemoryEntry> entries) {
    List<MemoryEntry> out = new java.util.ArrayList<>();
    java.util.Set<String> seen = new java.util.HashSet<>();
    for (MemoryEntry e : entries) {
        if (e == null || e.content() == null) {
            continue;
        }
        String key = e.content().trim().replaceAll("\\s+", "");
        if (seen.add(key)) {
            out.add(e);
        }
    }
    return out;
}
```

**"重叠切块"是切块策略（第 23 讲）的产物**：为了让边界处的句子不被切碎，相邻块之间会有 **15% 的重叠**（这是本项目的默认值）。

**副作用是**：一段 700 字符的规范，如果横跨两个块的边界，会产出两个"看起来很不一样的块"——但**它们有一段完全相同的文字**。

**如果这两个块都进了 Top-5**，模型会看到同一段话两遍。**这既浪费 token，又会让模型误以为这件事特别重要**（重复出现天然被理解为"强调"）。

**去重的键是"归一化后的内容"**：

```java
String key = e.content().trim().replaceAll("\\s+", "");
```

**`replaceAll("\\s+", "")` 把所有空白字符（空格、换行、Tab）全部删掉再比较。** 这比"trim 后比较"更宽松——因为两个块可能只差换行位置。

**但注意这是一个"精确匹配"的去重，不是"近似"去重。** 如果两个块的内容差一个标点，去重就会漏掉。

**这里有一个可讨论的取舍**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **内容 hash 精确去重（当前）** | 便宜、可预测、无误杀 | 漏掉"近似但不完全相同"的重复 |
| 相似度阈值去重（如 Jaccard > 0.9） | 覆盖近似重复 | 需要算相似度；阈值需要调；可能误杀相邻但独立的条款 |

**当前选择便宜方案是对的**——因为它的定位是"兜底防止明显重复"，而不是"完整的去重"。而更深的重复问题由 MMR 处理（MMR 的 redundancy 项本来就会压制高度相似的候选）。

**两层的分工是：**

- **MMR**：在**挑选**阶段，让高度相似的候选不容易同时被选中（软约束）；
- **dedupeByContent**：在**注入前**，硬性剔除完全相同的块（硬约束）。

**一软一硬，覆盖了"近似"和"完全相同"两种重复。**

### 2.6 small-to-big：给孤立条款补上它所属的章节

```java
/**
 * 格式化知识块（含 <b>small-to-big</b> 父章节上下文回填）。
 *
 * <p>命中叶子块时，仅凭一条孤立条款往往看不出它属于哪一章的什么约定；
 * 此处把 {@code StructuredChunker} 写入的 {@code parentExcerpt} 附在块后，
 * 同一父摘要只追加一次（多个兄弟块共享同一父章节）。
 */
private void appendKnowledgeBlocks(StringBuilder sb, List<MemoryEntry> blocks) {
    java.util.Set<String> appendedParents = new java.util.HashSet<>();
    for (MemoryEntry e : blocks) {
        java.util.Map<String, String> meta =
                e.metadata() == null ? java.util.Map.of() : e.metadata();
        sb.append("- [").append(meta.getOrDefault("source", "knowledge"))
                .append("] ").append(e.content()).append('\n');
        if (!parentContextEnabled) {
            continue;
        }
        String parent = meta.get("parentExcerpt");
        if (parent == null || parent.isBlank()) {
            continue;
        }
        String excerpt = parent.length() > PARENT_CONTEXT_MAX
                ? parent.substring(0, PARENT_CONTEXT_MAX) : parent;
        if (appendedParents.add(excerpt)) {
            sb.append("    ↳ 所属章节上下文：").append(excerpt.replace('\n', ' ')).append('\n');
        }
    }
}
```

**"small-to-big"的含义是**：检索时用**小块**（叶子，精准匹配），注入时**带回大块**（父章节，提供语境）。

**为什么需要它？** 因为一条孤立条款往往不够：

```
【只有叶子】
- 4.2.1 禁止 catch (Exception e) {} 这类空捕获块。

【加上父章节后】
- 4.2.1 禁止 catch (Exception e) {} 这类空捕获块。
    ↳ 所属章节上下文：4.2 异常处理。本章约定：任何异常都必须被处理、记录或向上传播；
      禁止静默忽略。空捕获块是最常见的形式，此外还包括...
```

**第二种写法让模型知道"这条规则的上级约定是什么"** —— 而这往往决定了它会不会把某个情况判为违规。

**四处实现细节：**

1. **父章节摘要由切块阶段写入 `metadata.parentExcerpt`**，而不是检索时现算。**这是"写入时算好、读取时直接用"的取向** —— 检索是热路径（要快），写入是冷路径（可以慢）。
2. **`PARENT_CONTEXT_MAX = 300`** —— 父摘要也截断，防止一个长章节把预算吃光。
3. **`appendedParents.add(excerpt)` 去重** —— "多个兄弟块共享同一父章节"，所以同一段父摘要只追加一次。**这和第 2.5 节的按内容去重是同一个思路，但这次作用于父摘要。**
4. **`parent.replace('\n', ' ')`** —— 换行转空格。父章节是多行文本，注入时压成一行，**避免破坏"每条一块"的格式可读性**。

**还有一个"优雅降级"的写法**：

```java
if (!parentContextEnabled) {
    continue;
}
```

**父上下文是个可配置的能力（`review.rag.parent-context.enabled:true`）**，关掉就跳过。**注意它是 `continue` 而不是 `break`** —— 只跳过父摘要的追加，**当前块的正文已经追加过了（在 continue 之前）**。

**如果这里写成 `break`，就会把剩下的所有块都丢掉。** 一个字母的差别，后果完全不同。

### 2.7 freshness：默认值是个陷阱

```java
/** freshness：知识块最大入库年龄（天），0 = 不过滤。 */
@Value("${review.rag.max-age-days:0}")
private long maxAgeDays = 0;
```

```java
// RagContextBuilder.java:43-45
/**
 * <p><b>freshness（知识时效）</b>：{@code review.rag.max-age-days} 控制召回的知识块最大入库年龄
 * （默认 0 = 不过滤），检索侧（Pg/InMemory 的 {@code searchKnowledge} 5 参重载）按 created_at 过滤，
 * 避免过期历史 PR 复盘 / 旧版规范污染当前审查。
 */
```

**默认值是 `0`，含义是"不过滤"。**

**这个默认值的方向值得警惕**：它意味着**开箱状态是"最宽松"的**。

所以：一份 2024 年的旧规范、一次已经作废的历史 PR 复盘，**都会以相同的权重进入检索**。而模型无法分辨"这条规范是当前的还是两年前的"。

**为什么默认设成 0？** 有两个合理的理由：

1. **它需要知识库有可靠的 `created_at`**——如果很多存量数据的时间戳是导入时间而非内容时间，开了过滤反而会误伤；
2. **过滤掉太多会让召回变少**——调大 `max-age-days` 是"用召回率换准确率"，不应该默认开。

**但从"默认值应该是安全的"这个角度看，`0` 是有风险的。** 更保守的默认值可能是 `730`（两年）——**它几乎不会误伤（两年内的规范一般都还有效），但能挡住"上古残留"。**

**这是一条通用的判据：**

> **默认值应该是"安全的那一侧"，而不是"不放限制的那一侧"。**
> 因为**用户不改配置**是常态——默认值就是绝大多数人的生产配置。

### 2.8 中文场景的相似度必须同口径

MMR 的注释里有一句非常关键的话：

```java
/**
 * <p>文本相似度用 {@link TextTokenizer}（中文 bigram + 标识符子词）的 Jaccard——
 * 与启发式重排同口径，中文场景下才不会恒为 0。
 */
```

**"中文场景下才不会恒为 0"——这六个字背后是一个具体的故障。**

如果 MMR 的相似度用默认的"按空格/字符切分"来计算（比如 `String.split(" ")` 或者按字符集合算 Jaccard），那么：

- 一段中文文本被当成**一整个 token**（因为没有空格）；
- 任意两段中文的 Jaccard **恒为 0**（除非整段完全相同）；
- 于是 MMR 的 `redundancy` 项**恒为 0**；
- **MMR 退化成纯相关性排序** —— 又回到了痛点。

**而它不会报错、不会告警**，只是"多样性完全没有生效"，而你以为它在工作。

**这和第 10 讲"同一 PR 内命中 3 次算 3 次复现"、第 09 讲"类型校验没实现"是同一类问题：**

> **一个环节静默失效，上游看不出任何异常，下游得到的是一个"看起来正常但质量更差"的结果。**

**而"同口径"是这里的核心**：

> MMR 的相似度、重排的相似度、检索的相似度——**它们必须用同一套分词**。

否则会出现"重排觉得这两块很像，MMR 觉得它们毫不相干"这种**内部矛盾**——最后的表现是"结果不稳定、难以复现"。

**这个坑的完整机制在第 26 讲（PG 的 `simple` 词典不切中文）会展开。** 这里只需要记住结论：

> **凡是"算文本相似度"的地方，都要先问"中文会被怎么切"；而所有地方必须切得一样。**

### 2.9 abstain 是一等公民

```java
// RagContextBuilder.java
@return 检索到的相关知识文本（无则返回空串，即选择性回答 abstain）
```

```java
// RagContextBuilder.java:158-163
// 3. 阈值过滤（低于 minSimilarity 的块剔除；全低于则 abstain）
List<MemoryEntry> passed = evaluator.filterByThreshold(candidates);
StringBuilder sb = new StringBuilder();
if (passed.isEmpty()) {
    log.info("[RAG] 无相关知识（候选 {} 条均低于阈值或为空），知识分区 abstain, 耗时 {}ms",
            candidates.size(), System.currentTimeMillis() - t0);
}
```

**"宁可不注入，也不硬塞"——这是 RAG 系统里最重要的一条质量原则。**

**为什么？** 因为**低相关度的知识比没有知识更糟**：

- 没有知识时，模型用自己的常识判断，**通常会给出保守的结论**；
- 有一堆"看起来相关其实不相关"的知识时，模型会**被误导着给出具体但错误的结论**，而且**因为有"知识"背书，结论显得更可信**。

**这就是"hallucination 被外部文本放大"的机制。**

`RagContextBuilder` 的实现是"返回空串"（abstain），而不是"返回最相关的几条"。**而这里有一个可讨论的细节：空串意味着模板里那一节会变成空标题**（第 11 讲 2.3 节讲的坑）。**两者放在一起看，正好构成一个完整的改进点：abstain 时应该连章节标题一起省略。**

### 2.10 历史经验独立于知识 abstain

```java
// 7. 历史经验回流（记忆闭环读侧；独立于知识 abstain——经验命中仍注入）
appendExperience(sb, teamId, agentType, rawQuery);
```

```java
/**
 * 经验条目通道注入：反思沉淀的「问题模式 → 建议」命中项以【历史经验参考】分区回流审查提示词。
 * 命中即由 {@link ExperienceStore} 刷新 recordHit（spaced repetition 反遗忘）。
 * 失败只 WARN 不阻断主链路（与知识通道同级的降级策略）。
 */
private void appendExperience(StringBuilder sb, String teamId, String agentType, String query) {
    if (experienceStore == null || query == null || query.isBlank()) {
        return;
    }
    try {
        String exp = experienceStore.getRelevantExperiences(Teams.sanitize(teamId), query);
        if (!exp.isBlank()) {
            if (!sb.isEmpty()) {
                sb.append('\n');
            }
            sb.append("【历史经验参考】\n").append(exp).append('\n');
            log.info("[RAG] 历史经验注入：team={}, agent={}, 命中 {} 字符",
                    teamId, agentType, exp.length());
        }
    } catch (Exception e) {
        log.warn("[RAG] 经验检索失败，跳过注入（不影响主审查）：{}", e.getMessage());
    }
}
```

**"独立于知识 abstain——经验命中仍注入"**：知识库没检索到东西，**不影响**历史经验的注入。

**为什么？** 因为它们是**两个不同的信息源**，服务于不同的目的：

| 通道 | 内容 | 性质 |
|---|---|---|
| 知识分区 | 规范 / 手册 / 历史 PR（**权威文档**） | 需要高相关度才敢注入 |
| 历史经验参考 | 反思沉淀的"模式 → 建议"（**团队自己的教训**） | 相关性门槛可以更低 |

**把两个通道的 abstain 决策绑在一起，等于用"文档检索失败"去否决"团队经验"。** 这是不必要的耦合。

**另外注意 `if (!sb.isEmpty()) { sb.append('\n'); }` —— 只有当知识分区有内容时才加分隔换行。**

**这是一个很小的格式正确性动作**：如果知识分区 abstain（`sb` 为空），那么就不该在开头多一个空行。**这类"边界处的空白字符"处理，是格式化代码里最容易漏的一类——而它的后果是 prompt 里多一行空行，无害但显得不专业。**

`appendExperience` 的降级也和知识通道同级：**`catch (Exception e) { log.warn(...) }`，绝不阻断**。

### 2.11 可测试性：一组 `with*` 方法

```java
/** 测试 / 工具用：直接设定改写器与窗口（跳过 Spring 装配）。 */
public RagContextBuilder withQueryRewriter(ReviewQueryRewriter rewriter) { ... }

/** 测试 / 工具用：直接设定检索窗口。 */
public RagContextBuilder withRetrievalWindow(int retrieveK, int injectTopN) { ... }

/** 测试 / 工具用：直接设定 freshness 天数。 */
public RagContextBuilder withMaxAgeDays(long days) { ... }

/** 测试 / 工具用：是否启用 MMR 多样性挑选。 */
public RagContextBuilder withMmr(boolean enabled) { ... }

/** 测试 / 工具用：是否回填父章节上下文（small-to-big）。 */
public RagContextBuilder withParentContext(boolean enabled) { ... }
```

**五个 `with*` 方法，全是返回 `this` 的链式 setter，注释统一写着"测试 / 工具用（跳过 Spring 装配）"。**

**它们解决的是一个很实际的问题**：`RagContextBuilder` 的字段是 `@Value` 注入的（`@Value("${review.rag.retrieve-k:50}")`），**在没有 Spring 容器的单测里，这些字段只会是它们的 Java 默认值**（也就是 `0`）。

**`retrieveK = 0` 意味着"召回 0 条"** —— 一个不设 `with*` 方法的测试，会静默地测一个"什么都检索不到"的场景。

> **这解释了一个现象：为什么很多 RAG 测试"通过"了却没有验证任何东西。** 因为默认值是 0 / false，链路每一步都直接返回空。
>
> **一组显式的 `with*` 方法，把"如何配置被测对象"变成了测试代码里可见的一行。** 它同时是一份文档：**看一遍这五个方法，你就知道这个类有哪些可调项。**

**`@Value` 字段 + 显式 `with*` 的组合，比"构造器注入全部参数"更适合这个类** —— 因为参数会不断变多（五个已经不少了），而构造器会变成一个十几参数的巨签名。

## 三、代码：一次完整的 `buildContext` 逐行

把整个方法按步骤编号读一遍（代码里真的有 1 / 1b / 2 / 3 / 4 / 5 / 6 / 7 / 7 的编号）：

```java

    long t0 = System.currentTimeMillis();
    // 1. 从代码提取查询意图（diff 形态）
    String rawQuery = extractQueryFromDiffs(diffs);
    // 1b. 查询改写：diff 形态 → 规范术语形态（可选；失败降级恒等，绝不劣化）
    String query = queryRewriter.rewrite(rawQuery);

    List<MemoryEntry> candidates = knowledgeStore.searchKnowledge(query, retrieveK,

    List<MemoryEntry> passed = evaluator.filterByThreshold(candidates);
    StringBuilder sb = new StringBuilder();
    if (passed.isEmpty()) { ...abstain 日志... }
    else {
        // 4. Cross-Encoder 重排
        // 5. MMR 多样性挑选
        // 6. 注入前去重
        // 7. 评估指标 + 格式化（含 small-to-big 父章节上下文回填）
    }
    // 7. 历史经验回流（记忆闭环读侧；独立于知识 abstain）
    appendExperience(sb, teamId, agentType, rawQuery);
    String result = sb.toString().trim();
    ...
    return result;

```

**四个值得注意的工程动作：**

**① `Teams.sanitize(teamId)` —— 团队标识必须净化后再进检索。**

出现在两处（检索、经验）。**`teamId` 来自外部（webhook 头 / API 参数），不净化直接拼进查询是注入风险。**

**② `true` 这个参数**（`searchKnowledge(query, retrieveK, teamId, true, maxAge)` 的第四个）。

**一个裸布尔字面量作为参数**——从调用点看不出它是什么。**这属于"参数名缺失"的可读性问题**：如果是一个 `RetrievalOptions` 对象或者至少有注释，读代码的人不用跳进接口签名去猜。（第 22 讲会看到这个参数是 `includeGlobalBaseline` 之类的语义。）

**③ 计时点：`t0` 一路传到日志里。**

```java
log.info("[RAG] 上下文构建：team={}, agent={}, 查询={}字符, 候选 {} → 放行 {} → 注入 Top-{} (maxSim={}), 耗时 {}ms",
        Teams.sanitize(teamId), agentType, query.length(), candidates.size(),
        passed.size(), deduped.size(),
        String.format("%.4f", metrics.maxSimilarity()),
        System.currentTimeMillis() - t0);
```

**这一行日志回答了整条链路的每一个问题**：

- 查询多长 → 改写是否跑偏；
- 候选多少 → 召回是否正常；
- 候选 → 放行 → 注入 的三级数量 → **哪一层缩得太狠**；
- `maxSim` → 最高相似度是多少（判断"闸门是不是设太高了"）；
- 耗时 → 检索是否成为瓶颈。

**这是"一行日志覆盖整条链路规格"的范例。** 排障时你几乎不需要加任何日志——**每次审查都有一条。**

**④ `result = sb.toString().trim()` 再判空。**

```java
if (!result.isBlank()) {
    log.info("[RAG] 注入上下文合计 {} 字符（知识分区 + 历史经验参考）, 总耗时 {}ms",
            result.length(), System.currentTimeMillis() - t0);
}
return result;
```

**只有真的注入了东西才打日志。** 因为"注入了 0 字符"这件事在上面的 abstain 日志里已经体现过了——**不重复打日志，是保持信噪比的基本功。**

## 四、避坑清单

- [ ] **上下文预算要三层漏斗**（召回宽 / 精排中 / 注入窄），别一步砍到最终数量。
- [ ] **任何"从 N 挑 K"的算法，上游窗口必须显著大于 K**，否则它不报错、只是空转。
- [ ] **查询质量决定检索质量**。别拿 diff 原文当查询；要提炼成"知识库的措辞形态"。
- [ ] **查询改写必须是"失败降级恒等，绝不劣化"**，并记录长度变化作为跑偏信号。
- [ ] **相似度口径必须全链路一致**（重排 / MMR / 检索用同一套分词），否则内部自相矛盾。
- [ ] **中文场景下按空格分词的 Jaccard 恒为 0** → MMR 静默退化成纯排序。
- [ ] **`List.remove` 有两义性**。泛型是 `Integer` 时 `remove(1)` 删的是索引；`record` 的 `equals` 是字段全等，按对象删会误删同内容元素。**用下标列表。**
- [ ] **贪心算法里要预计算可复用的中间结果**（如候选词集），否则复杂度被放大 K 倍。
- [ ] **重叠切块会产生近似重复块**，注入前要按归一化内容去重（软硬两道：MMR + 内容去重）。
- [ ] **small-to-big 要在写入时算好父摘要**（检索是热路径），并给它自己的上限（`PARENT_CONTEXT_MAX`）。
- [ ] **父摘要去重要按内容**（多个兄弟块共享同一父章节）。
- [ ] **跳过父摘要用 `continue` 而不是 `break`** —— 别把剩下的块一起丢掉。
- [ ] **`max-age-days` 默认 0（不过滤）是有风险的默认值**。默认值应取"安全的那一侧"。
- [ ] **abstain 是一等公民**：低相关度的知识比没有知识更糟。**而 abstain 时要连章节标题一起省略**（配合第 11 讲那个占位符问题）。
- [ ] **不同信息源的 abstain 要独立**（知识库没检索到 ≠ 团队经验也不该注入）。
- [ ] **`@Value` 字段必须配显式的测试 setter**，否则单测会静默测"值为 0 的场景"。
- [ ] **一行日志覆盖整条链路的规格**（三级数量 + 最高相似度 + 耗时）。

## 本讲小结

1. **上下文预算是三层漏斗**：召回（50，宽）→ 精排（15，中）→ 注入（5，窄）。**任何"从 N 挑 K"的算法，上游窗口必须显著大于 K**，否则它只是空转。
2. **查询质量决定一切**。"拿 diff 原文取前 500 字符"这个旧实现犯了三重错误：术语不匹配、截断位置错、无结构。**修法是把 diff 翻译成知识库的措辞形态。**
3. **查询改写必须"失败降级恒等，绝不劣化"**，并记录长度变化作为跑偏信号。
4. **MMR 解决"相关性排序不够"的问题**：Top-N 经常被同章节碎片占满（看似 5 条、覆盖 1 个知识点）。λ=0.7。
5. **`List.remove` 的两义性 + `record` 的 `equals` = 静默误删**。用下标列表，顺带复用预计算。
6. **重复有两层防线**：MMR（软，压制近似）+ 内容去重（硬，剔除完全相同）。
7. **small-to-big 要在写入时算好父摘要**，且跳过用 `continue` 不用 `break`。
8. **`max-age-days` 默认 0 是有风险的默认值**——默认值应取"安全的那一侧"。
9. **abstain 是一等公民**：低相关度知识比没有知识更糟，因为它给错误结论背书。
10. **中文场景的相似度必须同口径**，否则 MMR 静默空转——这是第 26 讲那个坑的第一次露面。
11. **一行日志覆盖整条链路规格**（候选 → 放行 → 注入 + maxSim + 耗时）。

下一讲把模块二收口：**可靠性四件套——幂等、重试、超时、兜底，以及那个"orTimeout 挂在 allOf 上"的经典陷阱。**
