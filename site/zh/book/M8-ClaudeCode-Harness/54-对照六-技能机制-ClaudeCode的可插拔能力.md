# 第 54 讲 · 技能机制对照：Claude Code 的可插拔扩展能力

## 一、痛点

第 48 讲我们读技能机制，落点是 `SkillRegistry`：技能是"名称 + 描述 + 指令"的**声明单元**，可插拔、可启用/停用、可灰度上线，且**加载净化**防注入。这是一套"能力可被声明式管理"的机制。

现在用 Claude Code 做第二参照物。它的技能/插件机制是整个行业最有名的"终端 Agent 开放扩展"：第三方生态给这个 Agent 加工能力，通过公开的技能声明让能力可被发现、可被上下文使用。

于是你有两个错误倾向：

**倾向一："技能机制就是插件系统，我们没那生态，学不了。"** 你看 Claude Code 靠生态把技能做繁荣，觉得自己没有第三方贡献，技能机制就没价值。于是不去把能力抽象成可声明单元，继续用一堆 if-else 硬编码判断"这个场景该有什么能力"。

**倾向二："技能=会多少能力，越多越好。"** 反过来，你把技能数量当成 Agent 强弱，拼命堆能力。**结果跟第 48 讲警告的一致：能力堆到上下文塞不下，声明混乱，可校验性、可灰度性全丢。**

本讲要破除的，正是这两个极端。真相是：

> **技能机制的魂是『能力=可插拔的声明单元』，不是『能力数量』，更不是『有没有第三方生态』。** Claude Code 靠生态走向繁荣，但它的骨架——能力用名称+描述+指令声明、可被发现、可被使用——和你的 `SkillRegistry` 是同一个东西。**有没有生态改变繁荣度，不改变『能力该不该声明化』这个判据。**

## 二、原理

### 2.1 骨架同构：技能=名称+描述+指令

无论哪一种实现，一个"技能"的本质都是同一份声明。你家的 `Skill` 契约在 `code-review-agent` 里是**两个方法就够**：

```java
public interface Skill {
    SkillMetadata getMetadata();                          // 名称 + 描述 + 分类
    List<SkillResult> execute(List<CodeDiff> diffs, ReviewContext ctx); // 确定性扫描
}
```

关键在 `Skill` 的 Javadoc 里那句定义——**"每个 Skill 是一段确定性的静态扫描能力（如密钥检测、SQL 注入检测），由 Agent 在调用 LLM 之前预执行"**。这句话揭示了技能的真正身份：**它是一段可在 LLM 之外独立执行、产出高置信可解释结果的确定性代码，不是"喂给模型的一段提示词"**。这对你的认知是有分量的：技能的价值在于它能给出**可解释、可审计的固定动作**，而不是让模型"自由发挥"。

| 维度 | `Skill` / `SkillRegistry`（第 48 讲）| Claude Code 技能形态 |
|---|---|---|
| **名称** | `SkillMetadata.name()` 唯一标识，注册用 | 技能名，能被发现 |
| **描述** | `SkillMetadata.description()` 说明何时用、价值 | 说明何时用、价值 |
| **指令/行为** | `execute()` 确定性扫描，产出 `SkillResult` | 运行说明/入口，进上下文即用 |
| **如何生效** | 注册 + 启停 + 进上下文 | 声明 + 进上下文即可用 |

**第 48 讲反复强调"描述决定模型会不会用这个技能，因为它只看得见你写的那段描述"**——这条在 Claude Code 完全成立：技能要能被模型选中，靠的是描述写得清不清楚，而不是底层实现有多强。**这一条就是宣称『技能机制相同』的最硬证据。**

### 2.2 你家的"可插拔 + 可灰度"是怎么写进代码的：两处真实的装配点

**装配点一：`SkillRegistry` 用"内置 + 自定义"两分，且启停按团队叠加。** 看它的真实设计：

- **内置技能**由 Spring 注入的 `List<Skill>` 提供（安全/逻辑/性能/规范/架构五类），**全局共享**；
- **自定义技能**是团队在前端提交的 `CustomRule`，运行时编译为正则技能，**按团队隔离**；
- **启停状态与自定义规则经 `TeamConfigStore` 落共享存储**（生产为 PG 的 `team_kv` JSONB 行），进程内保留内存态做高频读，读带 **`REFRESH_MS = 2000`（2 秒）短 TTL 惰性重载**——于是集群下 A 实例改配置，B 实例最迟 2 秒后生效，**多实例行为一致，不靠各算各的**；
- 审查时 `getEnabledSkillsForCategory(teamId, category)` **实时取用已启用技能**，支持运行期动态增删。

这四个细节合起来，就是第 48 讲"可插拔、可灰度、声明可用"的**代码化**：**能力是"名称 + 声明"，启停是可持久化、可跨实例一致、可 2 秒生效的开关**——不是写死在 if 里。

**装配点二：`ExtensionPoint` 用 `order()` 把"叠加"做成有序织入。** 在 `agent-kit` 里，横切扩展（`LlmInterceptor` 防注入、`RagEnhancer` 重排、`AgentProvider` 自定义 Agent、`MemoryStrategy`、`StageHook`）都实现一个标记接口：

```java
public interface ExtensionPoint {
    String name();   // 唯一，用于日志与治理
    int order();     // 越小越先执行：标准实现 100，项目自定义 0-50
}
```

`ExtensionRegistry` 按 `order` 升序返回织入链，**运行期注册即生效**。这里藏着一个很妙的约定：**标准实现用较大的 order（100），项目自定义用较小的 order（0-50）**——于是项目自定义天然排在标准之前，"标准之上叠加自定义"被一条 order 约定就表达清楚了，不需要改框架代码。**这就是"加一个能力是加一个扩展点、不是改主流程"的工程化落点。**

### 2.3 工程化 vs 生态化：两个方向的正确取舍

Claude Code 的技能机制强在**生态**——开放、第三方活跃、能力如雨后春笋。这是它的护城河。

而你在第 48 讲建的 `SkillRegistry` 强在**工程化**——声明可用、可灰度、可校验、加载净化防注入。这是你（和多数自建 Agent）该守住的护城河。

**判据句：**

> **能力必须声明化（这是底线，两边都一样）；但声明化之后的治理——校验、灰度、审计——按你的场景取舍。** 面向单人自用的技能，灰度与净化可以轻；面向对外开放/多租户的技能，校验、注入防护、启停审计一样都不能省（第 48 讲 `SkillRegistry` 的加载净化正是干这个）。

**别把"我要生态所以技能机制才算数"变成偷懒借口**——那等于把你最该守住的工程化（可校验、防注入、可审计）也一起丢掉了。换个角度：**Claude Code 走向开放生态的前提，恰恰是它把技能的"载体"做成声明单元**——如果能力是写死的 if，第三方根本进不来。生态是声明化之后长出来的果，不是声明化的替代品。

### 2.4 技能的"边界与注入"是共同的隐性难题

技能声明一旦**可来源于外部（第三方/用户上传）**，就同时打开注入风险——这正是第 48 讲 `SkillRegistry` 加载净化要防的：**注入的技能指令可能诱导 Agent 越权。** Claude Code 靠开放生态受益，也必须面对同款风险（非可信技能的恶意指令）。

**对照第 35 讲提示注入的分层定界，技能是一个天然的注入面**：它是一段会进上下文的"指令区文本"。所以技能机制的工程化从来不只是"能不能加这个技能",还有"**这个技能的声明我可不可信、校验过没、放进上下文的边界在哪**"。

这跟第 52 讲 2.4 节的 `ContentInjectionDetector` 四道闸是同一件事的两种落点：那边防的是"外部来的内容槽",这边防的是"外部来的技能声明"——**两者的共同判据是一样的：凡是会变成系统指令/上下文的一等文本，进上下文前都要过一遍"来源可不可信、要不要净化"。** 这是第三方生态与自建治理共同绕不开的承重墙。

### 2.5 前沿深挖：Claude Code 技能生态的完整形状——frontmatter 字段清单与"runtime 封装"趋势

把第 2.x 节的"工程化 vs 生态化"再推一步，看 Claude Code 技能/subagent 声明的**完整字段清单**（plugins 官方文档）：`name / description / model / effort / maxTurns / disallowedTools / allowedTools`。

这张字段表藏着一个重要的范式信号：**技能声明已经不再是"提示词+触发词"，而是一个微型 runtime 的规格书**——

| 字段 | 封装的维度 | 对应你系统的哪个机制 |
|---|---|---|
| `model` | 模型选型（这个技能用哪个模型跑） | 路由表（第 43 讲） |
| `effort` | 推理预算 | 成本计量（第 32 讲） |
| `maxTurns` | 循环硬终止 | 工具循环上限（第 45 讲） |
| `disallowedTools` | 权限白名单 | 护栏/审批（第 45/46 讲） |
| `description` | 加载时机判据（模型据此决定调不调它） | Skill.supports()（第 48 讲） |

**一个声明文件把六大机制里的五个都打包了。** 这就是"技能封装的终局形态"：**能力单元 = 提示词 × 模型 × 工具边界 × 终止条件 × 加载判据**。你的 Skill 接口目前只封装了"加载判据 + 执行"，对照这张表能直接看到自己的扩展路线。

另一个值得注意的生态动向：Anthropic 官方《Steering Claude Code》把 **hooks（生命周期事件回调）** 提升为与 skills 并列的控制面——PreToolUse / PostToolUse / Stop 等钩子点允许外部命令在关键生命周期拦截。**这与你系统的 ExtensionPoint 是同族设计，但 Claude Code 把钩子放在了"进程边界"上（外部脚本），换取零耦合；你的 ExtensionPoint 在进程内，换取性能与类型安全。**

## 三、避坑清单

- [ ] **别把"技能=插件生态"当成不声明化的借口。** 骨架是声明，生态只是繁荣度。
- [ ] **技能是「名称 + 描述 + 指令」的声明单元**，不是写死的 if-else。
- [ ] **描述决定模型用不用这个技能**——写清楚"何时用、价值"，模型才选得中。
- [ ] **可校验、可灰度、可启停**——尤其面向多租户/外部时，工程化一项不能省。
- [ ] **技能是注入面**：外部得来的技能声明必须加载净化、放对上下文边界（对照第 35 讲）。
- [ ] **对照第 48 讲别造两套真理**：开放技能与自建技能是同一机制，只是生态 vs 治理的取舍。

## 四、动手任务

> **目标**：把 Agent 的能力，从"写死的 if"升级成"可插拔的声明单元"。

**步骤 1：盘点你的能力**

列出现在 Agent 做得出的每一件能力。凡是实现是 `if (你是某种场景) 就有这能力` 的，就是"写死的 if"——它该被抽成技能声明。

**步骤 2：抽象成「名称+描述+指令」**

把每个能力抽成一份声明。命名有唯一标识，描述写"何时用、价值"，指令写执行要点。这段描述就是模型选它的依据，第 48 讲 `SkillRegistry` 的形态直接可用。

**步骤 3：补校验与启停**

给技能加**校验/净化**，尤其是声明可能来自外部的。给你发"启用/停用"的开关，让能力可灰度、可审计——像 `SkillRegistry` 那样。

**步骤 4：对照 Check**

对每个技能问：**它是不是声明单元？描述能不能让模型选得中它？来源可不可信、放进上下文的边界在哪？** 答不出就补。

## 本讲小结

1. **技能机制的魂是"能力=可插拔的声明单元"，不是能力数量。**
2. **骨架同构**：名称+描述+指令，`SkillRegistry` 与 Claude Code 是同一个东西。
3. **生态 vs 治理是两个方向**：Claude Code 强在生态，你的自建系统强在可校验、可灰度、防注入。
4. **技能是注入面**：外部声明的技能必须加载净化、放对上下文边界。
5. **能力永远声明化**：有没有生态，改变不了这个判据。
