# 第 49 讲 · 模型调用对照：Claude Code 的"连谁"与"不连谁"

> 🎯 导读问题：**"拿 Claude Code 举例，它的模型调用机制和我们有什么一样、有什么不一样？"** ——能答出"机制在**别家也要有**、但**落点随场景变**：我们为『网关给别人调』建路由表，Claude Code 为『一个终端里的个人助手』把决策链压到最少配置、最多兜底"，就算把机制和场景分开了。**本讲要建立的判据是：机制不变，但『复杂度该放在哪一层』由产品形态决定。**

## 一、痛点

第 43 讲我们立下判据：**一次模型调用是一条可判定的决策链**——连谁、这一路行不行、挂了退避几次、成败都记账。这套判据在网关里天经地义。

可当你看一个终端 Agent（比如 Claude Code）时，第一反应往往是两类相反的疑问，而**两类都是陷阱**：

**第一类："它看起来好简单，是不是没有这些机制？"** 你在终端里输一句"帮我查这个 bug"，它就干活了。看不到路由表、看不到熔断、看不到账本……于是你怀疑：是不是只有大型网关才需要 Harness，终端助手根本不做？

**第二类："它内部一定藏着花哨的东西，我们学不来。"** 反过来，你把不理解的复杂度都归因于"闭源的黑科技"，于是放弃了把自家机制做扎实。

本讲要破除的就是这两类错觉。真相是：

> **Claude Code 在"连谁"这件最小的事上，展现的恰恰是同一套机制判断力——只是把复杂度按『终端个人助手』的产品形态，重新分配了落点。**

它怎么暴露配置、怎么在失败时兜底、怎么让人在 30 秒内换一条路，每一个决定背后，都是你在第 43 讲读过的同一句话：**"连哪家模型"必须可改、可查、可审计，只是在终端场景里，它选择把『可查可审计』让位给『零配置上手』。**

## 二、原理

### 2.1 先对答案：Claude Code 的"连谁"暴露成什么

Claude Code 把模型路由的**配置面**压得非常薄——公开文档的核心就是几类**环境变量**：

| 你会在第 43 讲问到的问题 | Claude Code 暴露的形态 | 对照你的 `token-factory` |
|---|---|---|
| 连谁？ | `ANTHROPIC_MODEL` / `ANTHROPIC_BASE_URL`（指向 中继/自建网关/Bedrock/Vertex） | `RouteTarget.providerCode / upstreamModel` |
| 用什么密钥？ | `ANTHROPIC_API_KEY` | `AccessKeyInterceptor` / Key 管理 |
| 走代理不？ | `ANTHROPIC_BASE_URL` + HTTP(S)_PROXY | 网关内联的代理通道 |
| **用哪家云托管？** | `CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX`（切 AWS/GCP 通道） | `providerCode`（多 provider 抽象） |

最后一行是 Claude Code 里**最像"路由表"的一处公开配置**：它支持把调用从 Anthropic 直连切到 **AWS Bedrock 或 GCP Vertex** 这两条"云托管通道"。这和 `token-factory` 的 `providerCode` 是同构的——**"连谁"这件事，在终端里一样需要"换一家"的能力**，只是换的粒度是"换托管云"，不是"换具体上游节点"。

注意这里的分野：**网关把『连谁』做成一张可热改、可审计的路由表**（第 43 讲 2.2 节的 `Function` 实时查库）；而 Claude Code 把它**降成几个环境变量**，改完重开进程即生效。

**这不是"Claude Code 退化了"，这是它的产品形态决定的**：终端助手是**单用户、单会话、短生命周期**——它不需要支撑 5 个并行 Agent 各自选 provider，也不需要给运营留审计账本。**它把『路由』这个机制换成了『一段你能改的配置』，代价是路由粒度变粗、无热改、无审计，收益是 30 秒可上手。**

**Harness 判据句（对两边的实现都成立）**：**模型路由的决策必须集中在「一处可改、一处可查」的地方。** 网关把它做细做成热表，终端把它做粗做成环境变量——但**都不允许散落在 if-else 里**。你 review 时看到 `if (provider.equals("deepseek"))` 写死在代码里，无论网关还是终端，都是 Harness 的倒退。

### 2.2 更深一层的对照：Claude Code 有"分级路由"，你没有

只对照"连谁"，会漏掉一个 Claude Code 公开行为里**很有意思、但很多人没意识到它是"路由"** 的机制：**主模型 / 快速模型的分级调用。**

Claude Code 在处理一个任务时，会**按任务难度调度不同档次的模型**：简单、低风险的操作（生成 commit message、总结一段代码、查一个符号）用**便宜又快的模型**（默认是 Haiku 系），复杂推理（排查 bug、设计重构）才用**主模型**（Sonnet/Opus）。这个"快速模型"由 `ANTHROPIC_SMALL_FAST_MODEL` 环境变量控制。

**这其实是第 43 讲"路由"的一个新维度。** 我们第 43 讲的路由轴是 **"哪个 provider 活着、优先级/权重"**——是**可用性**维度；Claude Code 这条轴是 **"这个任务值不值得用贵模型"**——是**成本/难度**维度。

把它翻译成你系统里的语言：

- 你的 `token-factory` 路由是"**同一份任务，选哪条路走**"（主备、分流）；
- Claude Code 的分级是"**不同难度的任务，选不同档次的模型**"（贵事用贵模型、贱事用贱模型）。

**这两条轴可以正交叠加，也常常被混为一谈。** 一个成熟的网关，最终会同时要这两条轴：一条按可用性选通道（主备/熔断），一条按任务难度选模型档（省钱的"快速模型"）。**只做一条轴的网关，要么在可用性上裸奔，要么在成本上浪费。** 这是对照 Claude Code 时，比"它也有路由"更有价值的一条发现。

### 2.3 再看"不连谁"：失败时的兜底哲学

第 43 讲 2.3 节讲失败要**分类**（429/5xx 重试、4xx 不重试）。Claude Code 的产品行为同样体现这个判断力，但落点是"**给用户可读的下一步**"而不是"自动重试 N 次"：

- **找不到/配错 API Key** → 回到第一性：明确提示缺了哪个配置，而不是无限重试烧钱。
- **上游限流/超时（瞬时故障）** → 自动重试，且按透明退避，跟你说"正在重试"。
- **模型/请求本身错（4xx）** → 不重试，把错误原文展示给你，等你改。

对照你在第 43 讲画的那张分类表，**判断骨架完全一致**：该重试的（瞬时）重试、不该重试的（配置/请求错）不重试。差别只在**终端把"分类的结论"优先暴露给人类用户看**，而网关把它**喂给下一级自动化**。

这给出一条可迁移的判据：

> **「失败分类」的结果流向，取决于这一环的消费者是谁。** 终端 Agent 的消费者是**人**，所以要可读、要能接着操作；网关/编排的消费者是**下一级自动化**，所以要进状态机、可查询。**用错流向就是错**——把给人看的重试日志喂进熔断状态机，或把机器的失败码丢给你肉眼读，都是同一类错误。

### 2.4 共同的底线：没有"记录"的调用等于没发生

第 43 讲最后一条判据是**可审计**。在 Claude Code 里，你可以通过 `--debug` 输出、日志、以及 `~/.claude/` 下的会话记录看到**每次调用的来龙去脉**——虽然不是账本形态，但 **"留痕"这个原则在**：一个决定若无法回答"它当时连了哪家、为什么这样",在网关和终端里同样不可接受。

**区别只是记账的重心**：网关记 token 数与金额（`TokenUsageRecorder` + 第 32/33 讲的成本计量），终端记会话与回溯能力。共同点是：**任何 I/O 决策都不许静默发生。**

这里可以再往前推一层，得到一个"取舍边界"的判据——**"零配置上手"什么时候不该再让位给"可审计"？**

> 答案在**产品形态发生变化的那个时刻**：当终端助手从"单用户、个人用"变成"团队用、企业用"，它的"无热改、无审计"就从"合理的取舍"变成了"合规的漏洞"。所以企业版/团队版几乎必然会**重新长出**路由表、用量账本、审批流——**那不是"复杂度又回来了"，是"场景变了，复杂度的落点必须跟着迁移"。** 理解了这一点，你就不会再问"到底该像网关还是像终端"，而是问"**我的产品现在处于哪个形态，复杂度该落在哪一层**"。

### 2.5 前沿深挖：从"分级路由"到"学习型路由"——Claude Code 与 RouteLLM 之间隔着什么

Claude Code 的两级路由（主模型 + haiku 级快模型）是**静态分工**：后台任务（标题生成、话题检测）永远走快模型，主循环永远走主模型。它不判断"这条用户消息难不难"——**判断发生在你选择打开 Claude Code 而不是 chat 网页版的那一刻**。

学术界把这个判断做进了路由层：**RouteLLM**（[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)）训练路由器预测"这个查询派给强模型的胜率提升值不值差价"，公告数据是在多个基准上**成本降 85% 而质量基本不掉**。但 2025 年的鲁棒性研究（[arXiv:2504.07113](https://arxiv.org/abs/2504.07113)）给出冷水：**路由器的收益高度依赖查询分布**——分布外场景省的钱可能腰斩。

**三方的取舍对照**：

| 方案 | 判据形式 | 成本收益 | 风险 |
|---|---|---|---|
| Claude Code 静态分级 | 按任务类型硬编码 | 稳定可预期 | 简单消息也花主模型的钱 |
| RouteLLM 学习型 | 按查询内容预测 | 纸面最大 | 分布漂移即失效 |
| 你的网关规则路由 | 按优先级+权重+熔断 | 无（不省钱，保命） | 不省钱 |

**可迁移判据**：**路由智能度与可审计性成反比。** 静态分级每一分钱都解释得清，学习型路由省的钱最多但你要拿自己的流量回放去验证。**工程落地的正确顺序是：先把静态分级做对（Claude Code 的位置），再记账沉淀数据（你的位置），数据够了再谈学习型（RouteLLM 的位置）——三级台阶，跳级必摔。**

> **延伸阅读**
> - RouteLLM：[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)
> - Router 鲁棒性：[arXiv:2504.07113](https://arxiv.org/abs/2504.07113)

## 三、避坑清单

- [ ] **别用产品形态判断机制有无。** 终端助手"看起来没路由"，不是没有 Harness，而是把决策链压缩到配置层了。
- [ ] **别把别家的复杂度归因于"闭源黑科技"。** 想不通时先问"它的产品形态允许复杂度放哪一层"。
- [ ] **路由有两条轴，别只做一条**：可用性轴（主备/熔断）+ 任务难度轴（贵模型/快速模型）。Claude Code 的分级调用就是后者。
- [ ] **模型路由永远集中在「一处可改、一处可查」的地方**，网关做热表、终端做环境变量，都不许散在 if-else。
- [ ] **失败分类的结论，流向取决于消费者是谁**：给人看优先可读，给机器用进状态机。
- [ ] **留痕是底线**：无论网关账单还是终端会话，一次决定不能静默发生。
- [ ] **"零配置"的让位有边界**：产品从个人变企业，就该把审计账本、审批流重新长回来。
- [ ] **引用 Claude Code 行为时，只引公开文档/公开形态**，不要给它编造函数名和行号。

## 四、动手任务

> **目标**：用一个"第二视角"，检验你第 43 讲的决策链是不是真的可判定。

**步骤 1：写出你的"配置面"**

把你第 43 讲实现的模型路由，列成一张表：**每个『决定』对应哪个配置/哪个数据结构、改它要不要重启**。若答案是"要重启"或"写死在某处 if 里",标出来——那是 Harness 的倒退。

**步骤 2：走一遍"人"视角**

假设你的 Agent 是个终端助理：找一个失败路径，走一遍它给"用户"的提示。**是可读的、能接着操作的，还是把堆栈丢给人看？** 若是后者，把失败分类的"结论流向"补一条给人看的出口。

**步骤 3：对照环境变量，重读你的路由表**

用 Claude Code 的 `ANTHROPIC_MODEL / BASE_URL / API_KEY` 三个变量，对照你 `RouteTarget` 的字段：**你有没有把"连谁 / 用谁 / 走哪"三件事拆开？** 拆开，才可能在换一家供应商时只动一处配置。

**步骤 4：检查你有没有"分级路由"这条轴**

回答：你的系统里，**简单任务有没有用更便宜/更快的模型？** 如果没有，算一笔账——那些"查个符号、生成 commit message"的简单任务，和复杂审查用同一个贵模型，是不是在浪费成本。如果值得，把"任务难度 → 模型档"这条轴加进去。

## 本讲小结

1. **模型调用机制不变，落点随产品形态变。** 网关做可热改的路由表 + 审计账本，终端助手压成环境变量 + 可读兜底。
2. **路由有两条轴**：可用性（主备/熔断）+ 任务难度（贵模型/快速模型）。Claude Code 的分级调用揭示了常常被忽略的第二条。
3. **判断机制有无，不能看"看起来有没有"。** 终端"没路由"不是没 Harness，是把决策链压缩到配置层。
4. **「一处可改、一处可查」是两边共有的底线**；散在 if-else 里无论哪边都是倒退。
5. **失败分类的结论流向由消费者决定**：给人看优先可读，给机器用进状态机，用错就是错。
6. **留痕不可省略**，只是账本 vs 会话的重心之别；"零配置让位"在个人→企业的形态切换处要收回来。
