# 第 53 讲 · 记忆机制对照：Claude Code 怎么"记得住"而不"记得乱"

## 一、痛点

第 47 讲我们读记忆机制，落点是生命周期状态机：**候选→激活→归档→清除**，每次迁移由证据驱动，且检索命中不能算正证据。这是一套"记忆自己会老化、会淘汰"的机制。

现在用 Claude Code 做第二参照物。它的记忆是"**会话即记忆**"——你在一连串对话里不断喂它上下文，它"记得"前面说过什么；需要用 `--continue` / 显式指令来固化长记忆。

两个错误倾向随之而来：

**倾向一："Claude Code 会一直记得，不需要状态机。"** 你羡慕它上下文延续得天衣无缝，觉得你的状态机"刻意记、刻意忘"很笨拙。于是你不再设计记忆的淘汰与老化，指望上下文"凭感觉记得住"。

**倾向二："会话丢了就全忘，太脆弱。"** 反过来，你觉得一个依赖会话的 Agent 记忆不可靠，必须把所有东西都永久落库才安心。于是记忆无限膨胀，没有生命周期，越记越乱。

本讲要破除的，正是"记忆=存多少/会不会忘"的两个极端。真相是：

> **记忆机制的真题目是『一条信息凭什么算可用的记忆』，而不是『能存多少』。** 上下文延续和状态机不是对立的——前者管"当前怎么记",后者管"跨会话怎么不记乱"。两者都要守住同一个判据：**告诉我这条信息是该记住、还是该忘，你的判据在哪里。**

## 二、原理

### 2.1 两种记忆，落点不同

| 维度 | 第 47 讲状态机 | Claude Code 会话记忆 |
|---|---|---|
| 记忆住哪 | 落库（PG/内存），跨会话存活 | 当前上下文，会话内延续 |
| 怎么记 | 状态迁移，证据驱动 | 对话里自然进入 + 显式命令固化 |
| 何时忘 | 生命周期裁决（归档/清除）| 会话结束/上下文被压缩 = 自然遗忘 |
| 判据 | 候选≥3 激活、负证≥2 归档、闲置 180d 归档、90d 硬删 | "这条是否还在当前上下文里" |

**关键的分野在"判据的位置"**：状态机把"该不该记住"做成**独立的裁决规则**（阈值写在代码里、迁移由维护任务执行）；Claude Code 把它**隐含在"上下文还在不在"里**——上下文里还能看到=记得，被压出/会话结束后=忘了。

### 2.2 你家的记忆状态机：阈值不是拍脑袋，是四个可判定的迁移边

第 47 讲的状态机在源码里长这样——`ExperienceStage` 四个状态，每条迁移边都有一个**写死的数字阈值**，落在 `InMemoryExperienceLibrary`（与 PG 版共用同一套规则）：

| 迁移边 | 触发条件（真实代码常量）| 谁触发 |
|---|---|---|
| CANDIDATE → ACTIVE | `evidencePos + 1 >= ACTIVE_EVIDENCE(3)` | `upsertReflection` 复现、`recordFeedback` 正报 |
| CANDIDATE/ACTIVE → ARCHIVED | `evidenceNeg + 1 >= ARCHIVE_NEGATIVE(2)` 或 `updatedAt < now - idle(180d)` | 人工误报、`MemoryMaintenanceScheduler` TTL 衰减 |
| ARCHIVED → PURGED | `updatedAt < now - purgeAfter(90d)` | `MemoryMaintenanceScheduler` 物理清理 |

看这段 `upsertReflection` 的真实判定——**升级靠证据累加，不靠时间空转**：

```java
// upsertReflection：同 pattern 再次出现 = 跨 PR 复现证据 +1
oldE.evidencePos() + 1 >= ACTIVE_EVIDENCE ? ACTIVE : oldE.stage()
```

四个阈值分别是**三档证据 + 两档时间**：

- **正证阈值 3**：一条候选经验，要跨 3 次 PR 复现、或 1 次人工正报，才从 CANDIDATE 转正为 ACTIVE。**检索命中不算正证**（第 47 讲那句铁律的代码化）：`recordHit` 只刷新 `lastHitAt/hitCount`，不动 `evidencePos`——被检索到只说明"这条存在且被用到了",不说明它"可信得值得转正"。
- **负证阈值 2**：累计 2 次人工误报就降级 ARCHIVED，退出检索注入面。
- **闲置阈值 180d / 硬删 90d**：一个 CANDIDATE/ACTIVE 条目超过 180 天既没被命中也没被更新，说明"这条记忆在衰退",软删成 ARCHIVED；再滞留 90 天物理删除。**这两个数字给了"遗忘"一个时间出口，防止记忆无限膨胀。**

**真正精巧的是"越用越不掉"这条反直觉设计**：`recordHit` 每次检索命中都刷新 `updatedAt`。于是 `archiveIdle` 的判据 `updatedAt < now - 180d` 对**常用记忆永远不成立**——因为它天天被命中，`updatedAt` 天天在更新。**这是一套 spaced-repetition 反遗忘：常用的经验永不衰退，冷门的经验先软删再硬删。** 遗忘不是按"最早产生的那条先死",而是按"最久没被测过的那条先死"。

维护任务 `MemoryMaintenanceScheduler` 把这些边交给一个**每日 cron**（默认 `0 40 3 * * *`，即凌晨 03:40），与断点清理（03:30）、巡检（02:00）**错峰**执行：

```java
@Scheduled(cron = "${review.memory.cleanup-cron:0 40 3 * * *}")
public void maintain() {
    int archived = library.archiveIdleAll(idle);      // 软删：TTL 衰减
    int purged   = library.purgeArchivedAll(purgeAfter); // 硬删：物理清理
}
```

**这就是"记忆自己会老化、会淘汰"的完整代码证据**：判定是确定性可回溯的（四个阈值 + 一条 cron），不是"凭感觉记得住/忘掉"。

### 2.3 "当前记住了" ≠ "这条是可信记忆"

上下文延续有一个隐蔽陷阱：**模型"看到过"不等于"记得准"**。第 47 讲有句铁律"检索命中绝不能算正证据"——因为**被检索到只说明存在，不说明可信**。同理，Claude Code 上下文里有条信息，也不代表它一定可靠：可能是旧约束、可能是已撤销的指令。

所以无论哪种形态，"可用记忆"都得再走一道"**可信性/相关性的判断**"——这正是状态机里 `ACTIVE` 所代表的那道筛选。**Claude Code 靠上下文压缩策略（第 50 讲的 auto-compact）做这道取舍，你靠状态机的证据门槛做。机制不同，判据不能缺。**

这里还能看出一个更深的对照：Claude Code 的"记忆"大多是**会话内短生命周期**的（`--continue` 续上，或 `CLAUDE.md` 长期固化），它的遗忘是**隐式的**——"被压出上下文就忘了";你的状态机把遗忘做成**显式的、有阈值和 cron 的**。**两种都不是错，对应两种部署形态**：交互式终端 Agent 的会话本来就短，天然不需要 180d 的归档策略；而一个 7×24 在线、跨 PR 复用的审查服务，记忆会一直积压，必须有人（维护任务）定期裁决谁该死。**"记忆要不要长大寿命",取决于你的 Agent 活多久。**

### 2.4 可迁移的判据

把第 47 讲的核心判据提炼，放到任何记忆形态上都成立：

> **一条信息能不能进"可用记忆"，必须有一道可见的判据——要么状态机的证据门槛，要么"还在当前上下文"的相关性裁决。** 没有判据地记住，等于把记忆当成日志堆着，既没用又迟早拖垮决策质量。

再补一条第 47 讲同款告诫：**"记得住"和"记得准"是两回事**。状态机用证据迁移避免"记得乱",上下文形态更要靠压缩取舍避免"记得旧但错"。**任何形态的 Agent，记忆的老化、失效、撤回都必须有出口，否则它永远带着过期决策前进。**

而"判据"要有形状，就回到四个可回答的问题：**升级靠什么（正证阈值）？降级靠什么（负证阈值）？衰退靠什么（闲置 TTL）？多久扫一次（cron）？** 答得出这四条，你的记忆才不是"会忘的日志",而是"有生命周期的经验"。

### 2.5 前沿深挖：把 Claude Code 的记忆放回产业坐标系——Letta / mem0 / Zep 三角对照

Claude Code 的记忆（CLAUDE.md + 会话历史 + auto-compact）是"**人写给人看的记忆**"——用户显式维护规范文件，模型被动加载。产业界另外三股力量押了完全不同的注：

| 系统 | 记忆哲学 | 写入机制 | 读取机制 | 时间维度 |
|---|---|---|---|---|
| **Claude Code** | 用户显式维护 | 人写 CLAUDE.md | 分层常驻加载 | 无（文件即现状） |
| **Letta (MemGPT)** | 模型自主管理 | 模型调记忆工具主动写 | Core 常驻 + Recall/Archival 检索 | 无 |
| **mem0** | 写入时巩固 | 判重后 ADD/UPDATE/DELETE/NOOP | 语义检索（+图） | 无 |
| **Zep** | 时态知识图谱 | 实体-关系抽取 | 图遍历+语义 | **双时态**（何时为真/何时入库） |
| **你的系统** | 证据驱动状态机 | 计数+阈值状态迁移 | 注入钩子自动进上下文 | 闲置归档 TTL |

**三个值得抄的机制级差异**：

- **mem0 的写入判重**（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)）：新记忆写入前先语义检索近邻，由模型判定"新增/更新/删除/忽略"——**记忆系统在写入路径上就该判重，而不是等库里堆出三座重复山头再清理**。你的 upsertReflection 是字符串级 pattern 判重，mem0 是语义级，后者能认出"换了措辞的同一条经验"。
- **Zep 的双时态**：事实不被删除，而是标记 valid_to——"北京办公室在朝阳区"在搬家后依然可查，只是标记了失效时间。**这对审查经验尤其合适："这个团队曾经在模块 X 上频繁出空指针"是一条会过期但不该被遗忘的经验。**
- **Letta 的"记忆即工具"**：模型自己决定何时翻记忆——与你的"注入钩子自动注入"是两个极端。**自动注入适合高置信小记忆（你的场景），自主翻页适合大记忆库；判据是记忆库规模与单次注入成本的比。**

**一个诚实的定位**：CLAUDE.md 路线在"规范类记忆"（团队约定、代码风格）上依然是最优解——因为它**可读、可审、可进 git 评审**。自动化记忆系统目前都还替代不了"人写下规范"的权威性。**两条路线是分工，不是胜负。**

## 三、避坑清单

- [ ] **别把"上下文延续"当成不需要记忆机制。** 判据只会换位置，不会消失。
- [ ] **也别把"会话即记忆"当不可靠而无限落库。** 没有生命周期的记忆会越积越乱。
- [ ] **"看到过"≠"记得准"。** 上下文里有，不代表可信；要再走一道可信/相关性判断。
- [ ] **记忆必须有老化与失效出口**（状态机的归档/清除，或上下文的自然遗忘）。
- [ ] **区分两种可靠性**：能召回的和能信得过的，分别交给检索与裁决两件不同的事。
- [ ] **对照第 47 讲别造两套真理**：会话记忆与状态机是同一机制，只是判据放的位置不同。

## 四、动手任务

> **目标**：给你的记忆系统，补上"凭什么是可用记忆"的判据。

**步骤 1：定位你记忆的判据**

回答：**你系统里一条信息"该记住"是由什么决定的？** 是状态机的阈值、还是上下文还在不在、还是根本没有？没有就补。

**步骤 2：加"记得改、记得撤"的出口**

确保过时/撤回的信息能被淘汰。若你依赖上下文延续，验证被压出会话的信息对后续决策有没有影响——有影响就要配老化的回查出口（对照第 50 讲的"史料可回查"）。

**步骤 3：校验"记得准"**

挑一条你系统里长期生效的记忆，验证：它是否曾"被记着但已过期或错误"。若出现过，说明缺可信性判据，补一道裁决。

**步骤 4：对照 Scheduler**

用 `MemoryMaintenanceScheduler` 的调度思想，给你这套记忆画一条"信息从产生到淘汰"的迁移路径，确保每一步都有触发条件。

## 本讲小结

1. **记忆的真问题是"凭什么算可用记忆",不是"能存多少"。** 判据必须可见。
2. **状态机与上下文延续是同一机制，判据位置不同**：前者独立裁决，后者隐含在上下文里。
3. **"看到过"≠"记得准"**：要再走可信/相关性判断。
4. **记忆必须有老化、失效、撤回的出口**，否则永远带着过期决策前进。
5. **别造两套真理**：会话记忆与状态机共用同一套记忆判据。
