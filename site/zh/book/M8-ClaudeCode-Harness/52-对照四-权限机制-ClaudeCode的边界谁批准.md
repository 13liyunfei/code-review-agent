# 第 52 讲 · 权限机制对照：Claude Code 的边界谁批准、凭什么

> 🎯 导读问题：**"Claude Code 的权限模型，和我们 Agent 的多租户授权比，强在哪弱在哪？"** ——能答出"强在把『是否可信』的判断**拆成一层层可叠加的决策**；弱在它是个人助手、没有『团队基线』这种半结构化的分层。**权限机制的真问题从来不是『能不能做』，而是『凭什么这次能做』——必须可回溯到某条规则。"**

## 一、痛点

第 46 讲我们读权限机制，落点是 `TeamResolver` 的**多租户基线叠加**：一个请求能做什么，由内置基线 + 全局基线 + 团队私有基线一起决定，且**每条授权都能追溯到某条规则**。这是"团队系统"的权限：用户多、租户多、要隔离。

现在用 Claude Code 做第二参照物，一个**个人终端权限**的极端样本。它只有"一个用户 + 一台机器"——听起来权限简单到不该有故事。

于是你有两个错误倾向：

**倾向一："个人工具哪有什么权限，就是'能干就干'。"** 你觉得单用户系统不需要权限模型，于是它的授权逻辑散落在 if 里、凭感觉放行。**丢了"凭什么这次能做"的可回溯性，连个人工具都会出错——比如一次误伤真文件。**

**倾向二："Claude Code 一堆确认弹窗，是它权限做得粗糙。"** 反过来，你把"常常问你要不要"看成它的弱点，觉得权限做得好就该"全自动、不问人"。**这恰好反了。**

本讲要破除的，就是"单用户 = 不需要权限 / 问人 = 权限粗糙"两个错觉。真相是：

> **权限机制的真问题永远是『凭什么这次能做』，而不是『能不能做』。** 哪怕只有一个用户、一台机器，每一次放行的依据也必须**落到一条可查、可撤销的规则上**。Claude Code 那些确认弹窗，正是它把『这次放行』做成『一条可见、可由你撤销的决策』的证据——不是粗糙，是本就该有的可回溯性。

## 二、原理

### 2.1 单用户 ≠ 零权限：权限的粒度更细了

一个终端 Agent 会碰你的真文件、真命令、真网络。它面对的是**"同一个用户授权的不同强度"**，而不是"不同用户的不同权限"。所以它的权限粒度体现在**操作级别**而不是用户级别：

| 操作 | Claude Code 公开行为 | 你要防的越界 |
|---|---|---|
| 读文件 / 查代码 | 通常放行，进上下文 | 读了不该读的敏感文件 |
| 改文件 / 跑命令 | **显式确认**（先问再做）| 改错文件、跑破坏命令 |
| 长时间自动作业 / 角色 | **agent 授权 / 角色化委托**（承诺能力边界）| 在无人看管下越权 |

第 46 讲的 `TeamResolver` 用"租户"隔离用户；Claude Code 用"**操作强度**"在同一用户内切分授权。**两者其实是同一个问题的两面：把"放行"做成按维度可叠加、可撤销的决策，只是切分的维度一个是用户、一个是操作。**

### 2.2 你家的"可回溯"是怎么写进代码的：三层判定

"每次放行依据哪条规则"不是口号，在你家仓库里有**三个真实的落点**，正好对应权限的三个切面。

**第一层：租户解析是可判定、可回退的级联。** `TeamResolver` 把一个请求"属于哪个团队"解析成一条**确定性的回退链**：

```java
// TeamResolver.resolve(owner, repo)
if (mapping.containsKey(owner + "/" + repo)) return sanitize(那个);  // ① 精确仓库
if (mapping.containsKey(owner))              return sanitize(那个);  // ② 组织兜底
return defaultTeam;                                                  // ③ 默认团队
```

三个特点值得记住：**① 精确优先、组织次之、默认兜底**——任何请求最终都落得到"某个团队"，绝不会空；**② 每个返回值都过 `Teams.sanitize()`**——外部进来的 `X-Team-Id` 覆盖值先净化再生效，防止越权注入；**③ 这条链是纯函数**——同样的 (owner, repo) 永远解到同一个团队，**"归属"是可回溯的，不是随机的**。这就是"凭什么这个请求按这个团队授权"的代码级答案。

**第二层：冲突仲裁是带权重的可判定裁决。** 多 Agent 都说话时，谁的"放行/否决"算数？`ArbitrationPolicy` 用一张**固定的权重表**回答：

```
安全(SECURITY)=100 > 逻辑(LOGIC)=90 > 性能(PERFORMANCE)=70
  > 架构(ARCHITECTURE)=60 > 风格(STYLE)=10
```

且 `isConflict()` 要求三条同时成立才判冲突：**不同 Agent 类型 + 同一文件 + 行区间重叠 + 建议文本不同**；`winner()` 的裁决顺序是**先权重、再严重级别、再置信度**。**这套东西的精髓是：即使两个 Agent 打架，最终"谁赢"也能被指到一条明确规则，而不是"协调员拍脑袋"。**

**第三层：BLOCKER 是强否决，父不覆盖子。** `VetoPolicy` 守的是权限里的**红线圈**：

```java
// VetoPolicy.isVetoable：仅阻断级是"不可覆盖的强否决"
return f.severity() == Severity.BLOCKER;
```

聚合阶段里，总审查员可以把某些发现"误报抑制"或"优先级仲裁覆盖"掉，但**只要任何 Agent 给出了 BLOCKER 级结论，它就必须被回收回最终报告，不可被抑制、不可被覆盖**。**这是权限里最难写的一格——"越级放行"的闸门：下面的专家说你这里会越权，上面的总协调员不许当没看见。** 它和你想象中 Claude Code 的"危险命令不许悄悄放行"是同一个精神。

### 2.3 Claude Code 的授权：把"可信度"拆成可叠加的旋钮

Claude Code 没有多租户，但它的授权同样不是"临场判断"，而是把"是否可信"拆成**一层层可叠加、可撤销的决策**：

- **显式确认**：这一次要不要做，是**一条刚产生的、看得见的决策**——你批准了，它有据可查（并可按 `always allow` / `deny` 固化成规则）；你拒绝了，同样有据可查。
- **规则列表（allow / ask / deny）**：不希望它碰的东西写进 deny，它就不会碰；希望它闭嘴别问的写进 allow。这是一条**事先定死、事后可改的规则**，对应你 `ArbitrationPolicy` 那类"写死在表里的裁决依据"。
- **权限模式（第 51 讲的 `default/acceptEdits/plan/bypassPermissions`）**：把"整条边界的自动化程度"做成一个**全局旋钮**，从"逐条问"到"只读"到"全放行"，每一档都是显式选择，不是悄悄变化。
- **角色化 / MCP 作用域授权**：在自动化场景用特定角色运行，或给 MCP server 声明它能碰的作用域，把授权做成"**这个角色/这个服务器被允许做什么**",而不是"这次随心放行"。

把这四件套一起看，它搭出了跟 `TeamResolver + ArbitrationPolicy + VetoPolicy` **同构的三层**：**归属判定（回退链）+ 裁决依据（权重表/规则）+ 红线圈（强否决）**。区别是维度从"多租户"换成"单用户的操作强度",但"可回溯到某条规则"这条底线一个不少。

### 2.4 权限还有一条隐形的边：输入注入检测

谈权限的人常盯着"输出能不能做",漏掉**"输入该不该信"**——而后者恰恰是注入类越权的入口。第 35 讲把提示注入做成了分层防御，落到 `ContentInjectionDetector` 是**四道按成本递增排序的闸**：

| 层 | 探针 | 判据 | 为什么放这层 |
|---|---|---|---|
| ① | `StegInjectionScanner` | 零宽字符 / Bidi / 危险控制符 | **零误报的确定性信号**，且零宽可拆词绕过后面所有可见字符规则，必须最先拦 |
| ② | `AnomalyDetector` | 超长填充 / 编码绕过 / 重复填充 | 纯离线，省去下游向量化调用 |
| ③ | `KeywordInjectionDetector.domainHit` | 领域攻击句式（"忽略以上指令"等）| 只拦**确定性攻击句式**，基座词表（越权/admin mode）在审查域是业务词不硬拦 |
| ④ | `SemanticInjectionDetector` | 语义复核"是否接近指令劫持意图" | 最贵，放最后；正常业务内容与注入模式语义距离远，零误伤 |

**这四层的顺序本身就是一个权限判据的示范：先用零成本的确定性信号拦，再用贵一点的语义信号兜底，绝不"一刀切硬拦业务词"。** 权限和注入是一体两面——"这个输入能不能信"决定了"后面那些动作该不该放行"。这也是为什么 Claude Code 把"技能/插件声明可能来自第三方"当作天然的注入面来防（第 54 讲会收口）。

### 2.5 可迁移的判据

**第 46 讲那句"越权判定必须可指到规则"，在个人终端里同样成立**，且更难得——因为没人盯着。提炼成判据：

> **每次放行的『依据』都必须是某一条看得见、可撤销的规则，而不是运行时的临场判断。** 临场判断第一次碰巧对，第二次就可能越界；规则可以撤销，临场判断收不回来。

**判断一个 Agent 的权限健不健康，问的不是『它权限大不大』而是『这次让它做了 X，依据是哪条规则、我能不能马上撤销』。** 依据答不出来，或撤不掉，权限设计就是失效的——跟第 46 讲多租户系统的判据一模一样。而"依据"要有形状，就回到三件套：**归属怎么判定（回退链）、冲突谁说了算（权重表）、红线圈谁都不能碰（强否决）。**

### 2.6 前沿深挖：注入防御的天花板在哪——CaMeL 与 OWASP 2025 给的坐标系

第 2.4 节讲了 Claude Code 和你的系统都在做"输入注入检测"。2025 年这条线有两个必须知道的坐标：

**① OWASP LLM Top 10 2025：注入仍是榜首，但含义变了。** LLM01 Prompt Injection 连续三年霸榜，但对 Agent 的解读已经从"骗模型说错话"变成"**驱动模型做错事**"——配合 LLM06（Excessive Agency，过度授权），注入的杀伤力 = 攻击者指令 × 你给的工具权限。**这条乘法关系是关键判据：降风险可以打两头——拦注入（难，概率性），或者收缩工具权限（易，确定性）。Claude Code 的权限模式和你的白名单护栏，打的都是乘法里的第二个因子。**

**② CaMeL：第一个"按设计免疫"的防御架构。** Google DeepMind 的 CaMeL（[arXiv:2503.18813](https://arxiv.org/abs/2503.18813)）放弃了"在文本里识别恶意指令"这条概率性路线，改做**架构级隔离**：可信指令进 Privileged LLM 生成计划；不可信数据进 Quarantined LLM 且全程携带来源标记（provenance）；**被污染的数据一旦要进入控制流位置（决定调什么工具、写什么路径），策略引擎确定性拒绝**。它把注入防御从"检测"变成了"数据流策略"——**这和你的 ContentInjectionDetector 不是替代关系而是叠加关系：你管第一层（模型输入前的概率性过滤），CaMeL 式策略管第二层（动作执行前的确定性拦截）。**

**③ 对 Claude Code 权限模式的再理解**：default / acceptEdits / plan / bypassPermissions 四档本质上是**"审批密度"旋钮**——而 CaMeL 给出了旋钮背后的理论答案：**审批密度应该正比于"不可信数据进入控制流"的概率**，而不是正比于动作表面上的危险程度。一个只读工具在充满不可信输入的环境里，可能比写工具在干净环境里更需要审批。

> **延伸阅读**
> - CaMeL：[arXiv:2503.18813](https://arxiv.org/abs/2503.18813)
> - OWASP Top 10 for LLM Applications 2025：genai.owasp.org

## 三、避坑清单

- [ ] **别因"单用户/单机"就跳过权限模型。** 粒度更细，不是更省。
- [ ] **把授权切分成可叠加的决策**：显式确认 + 拒绝列表 + 角色授权，不同维度各管一段。
- [ ] **每次放行都能回溯到一条规则**：回答"依据是哪条、谁批准、何时"。
- [ ] **授权必须可撤销**：随时能把刚放行的能力收回，否则就是临场判断。
- [ ] **危险操作落"显式确认"**：像改文件/跑命令，先问再做，留下批准痕迹。
- [ ] **对照第 46 讲别造两套真理**：多租户和个人终端是同一权限机制，只是切分维度不同。

## 四、动手任务

> **目标**：给 Agent 的权限，从"临场放行"升级成"可回溯的规则"。

**步骤 1：列出所有"放行点"**

把你 Agent 会碰的每个敏感操作列出来：读文件 / 改文件 / 跑命令 / 碰网络。每个点问一句：**这次放行的依据是什么？**

**步骤 2：把临场判断改成规则**

凡是没有明确依据的，要么加**显式确认**、要么写进**拒绝/允许列表**，让"放行=命中一条规则"。

**步骤 3：补可撤销**

给每类授权补一个"撤销出口"：怎么把刚允许的能力收回来。收不回的，回到避坑 4。

**步骤 4：对照 TeamResolver**

用 `TeamResolver` 的"基线叠加"思想，给你这套授权画"权限 = 基线与规则叠加成可查结果"的图，确保每条授权都能指到来源。

## 本讲小结

1. **权限的真问题不是"能不能",而是"凭什么这次能做"。** 必须可回溯到规则。
2. **单用户 ≠ 零权限**：粒度从"用户"变细到"操作强度"。
3. **可叠加的决策**：显式确认 + 拒绝列表 + 角色授权，各管一段。
4. **每次放行都能撤销**：临场判断收不回来，规则可以。
5. **多租户与个人终端是同一机制**，只是切分维度不同；别造两套真理。
