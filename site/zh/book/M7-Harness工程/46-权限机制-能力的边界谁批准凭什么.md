# 第 46 讲 · 权限机制：能力的边界，谁批准，凭什么

> 📌 本讲代码锚点：`token-factory-server/src/main/java/io/tokenfactory/server/security/AccessKeyInterceptor.java`（调用面鉴权）、`server/security/AdminKeyInterceptor.java`（管理面鉴权，未配即 403 fail-closed）、`code-review-agent/src/main/java/com/codereview/agent/core/security/ContentInjectionDetector.java`（写库边界三探针：超长/填充/重复）、`agent-kit/src/main/java/com/codereview/kit/security/OutputGuardInterceptor.java`（输出护栏）、`kit/security/InjectionGuardInterceptor.java`（注入护栏）、`kit/approval/ApprovalGate.java`（对外动作审批）、`code-review-agent/src/main/java/com/codereview/agent/core/permission/VetoPolicy.java`（否决策略）
> 🎯 导读问题：**"你的 Agent 怎么保证安全？"** ——只答"我加了鉴权"是及格;能答出"**权限要分三层:谁能调用(认证)、Agent 能碰什么(能力边界)、Agent 往外做什么要谁批准(动作审批)**,而且每一层的默认值都是拒绝"才算真的想清楚了。

> **为什么归 Harness 工程**：权限机制回答的是"**这个 Agent 的能力边界在哪"**——不做权限,Agent 就是一匹没有缰绳的马。Harness 的三个字放在权限上,是要把"能力"变成"被授权的能力"。

## 一、痛点

模块五你已经见过 `token-factory` 的鉴权：调用面用 `AccessKeyInterceptor`(Bearer AK),管理面用 `AdminKeyInterceptor`(X-Admin-Key,未配置 → 403 fail-closed)。做完这些,你觉得自己"安全了"。

但 Harness 视角会把三个穿透漏洞一个个摊开：

**漏洞一:认证 ≠ 授权。** 你能证明"调用者是谁",不等于"他有权做这件事"。一个拿到 AK 的人,能调用你所有模型——**"认了你是谁"和"授权你干什么"是两码事。**

**漏洞二:Agent 的能力没有边界。** 你的 Agent 不止会调模型,它会读 diff、会写评论、会调用工具。**有人往 diff 里塞注入指令怎么办?** 模块四的 `ContentInjectionDetector` 能拦 BLOCK,但那只是"输入"这一面——Agent 的"输出"谁管?

**漏洞三:Agent 往外做动作,没有审批。** 高权限的 Agent 会回写代码平台、会改状态。**"AI 不代替人做阻断决定。沉默不是中立——需要你表态的机制里,不主动上报就等于让机制退化。"** 这句第 38 讲的判据,是权限机制里最容易被人忽视的一层。

## 二、原理

### 2.1 第一层 · 认证：默认拒绝，且"钥匙本身"也要加密

先看默认值哲学。`AdminKeyInterceptor` **没配置就 403**,而不是"没配置就不鉴权"。

```java
// 示意：管理面密钥缺失 → 直接拒绝，而不是放行
if (adminKey == null || adminKey.isBlank()) {
    throw new ResponseStatusException(HttpStatus.FORBIDDEN,
        "管理面密钥未配置，拒绝请求（fail-closed）");
}
```

**fail-closed(未配即拒)是这里唯一的正确默认值。** 任何一个"忘了配就悄悄放行"的钥匙,都等于门锁是装饰。**判据:一切与安全相关的默认值,都必须是拒绝。**

但认证这一层还有第二个、经常被当成"细节"忽略的深度点——**钥匙本身不能存明文**：

> `token-factory` 里，调用方的 AK **只存 SHA-256 哈希**，上游厂商的密钥**只存环境变量名**（不存值本身）。这不是洁癖，是一条安全基线：**数据库一旦泄露，明文密钥等于把"认证"这扇门直接拆了。** 存哈希，泄露后攻击者拿到的是"不可逆的摘要"，无法用它直接冒充调用方。

这一条和 fail-closed 是**同一个思想的两面**：fail-closed 管的是"没钥匙时的默认行为"，存哈希管的是"钥匙本身被偷时的破坏半径"。缺了任何一个，"认证"都是有洞的。

而双面钥匙(调用面 Bearer / 管理面 X-Admin-Key 独立)说明一件事:**权限要按"干什么"分角色,而不是一把 key 走天下。** 调用方和管理员是两种不同的主体——前者是"消费模型"的，后者是"改路由/改熔断/看账单"的。共用一把钥匙，意味着任何一个调用方拿到的那把钥匙都能干管理员的事，**最小权限原则（least privilege）从根上就被破坏了。**

### 2.2 第二层 · 能力边界:输入与输出都要管

能力边界有两面,Input 和 Output。

**输入面(有人往内容里塞指令)——`ContentInjectionDetector`：**

它的三探针(超长/填充/重复，熵判据仅限纯 ASCII)在**写库边界**做完整检测,逐文件 BLOCK / TAG / CLEAN。关键点是**分阶段**：

> diff 预检只做 Keyword 离线标注,**不拦截**;真正的 BLOCK 发生在**写库边界**——因为只有到那里，才有**完整的文件上下文**可以做"这是不是注入"的可靠判断。预检阶段的上下文不全，冒然 BLOCK 会有大量误杀；写库边界的上下文完整，才能把"确定恶意"和"存疑"分开。**检测的精度，取决于你把它放在"信息有多完整"的哪一环。**

还有一个极易踩的边界（模块四/第 35 讲都强调过）：**基座词表里的「越权」「admin mode」这类词，在代码审查这个领域里是正常的业务词**。如果你把它们当注入硬拦截，等于把"审查越权漏洞"这个正常审查任务也一起拦了。**内容边界禁止硬拦截业务词——检测要分"领域无关的恶意"和"领域内的正常词"，两者不能混判。**

**输出面(Agent 会不会吐出不该吐的)——`OutputGuardInterceptor`：**

模型拼好了输出,会不会含敏感信息、越权内容?输出护栏在**发出去之前**再拦一次。它的判据同样要是"可枚举的规则"（敏感信息模式、越权动作、超出审查范围的越界输出），而不是"模型你自觉点"。

这两个护栏共同说明 Harness 权限的核心洞察:**输入要防注入(它把不该读的读进来),输出要防泄露(它把不该说的说出去)。** 只做一面,权限就漏了一半。

### 2.3 第三层 · 动作审批:往外做的事,要有人批，且有"权重"而非"平票"

最高权限的 Agent 会"发声"——回写代码平台、改审批状态、发订阅。这些动作 Harness 视角必须过审批链。

`ApprovalGate` / `VetoPolicy` 定义了"谁批准、谁一票否决"：

- **ApprovalGate(先批再动)**：某些动作**不自动做**,挂起等人批。它把"AI 能不能决定改生产状态"的最终决定权交回给人工。
- **VetoPolicy(一票否决)**：一个"谁的意见算数"的决策要**有权重,不是一人一票平票**。

这里的"权重"不是抽象比喻——`code-review-agent` 的仲裁权重是**真实的数字**：

| 审查维度 | 仲裁权重 |
|---|---|
| Security（安全） | 100 |
| Logic（逻辑） | 90 |
| Performance（性能） | 70 |
| Architecture（架构） | 60 |
| Style（规范） | 10 |

而且 **BLOCKER 级别是强否决、不可抑制的**：即使性能/风格这些子 Agent 想覆盖,BLOCKER 也压得住——**降噪不得覆盖底线,顺序即优先级。** 这个"权重 + 强否决"的设计，表达的是权限机制里的一条深层原则：**"谁说了算"必须是显式的、有优先级顺序的，而不是靠"投票数量多"或"谁嗓门大"。** 安全的问题权重最高，是因为它的破坏是不可逆的——一个风格的争议可以降噪，一个安全漏洞的漏报可能直接打穿系统。

为什么动作要审批?因为第 38 讲那条判断在这里是活的:**如果你让 AI 默认就有"改变平台状态"的权限,又没让它在失败时上报,那么 AI 的每一次"静默成功"都可能是一次没人看得见的错误动作。** 审批,是把"可逆性"还给人工的最后一道闸门。

### 2.4 三层的共同骨架：默认拒绝 + 显式授权

把三层摆在一起，会发现它们共享同一个骨架：

| 层 | 管什么 | 默认值 | 谁来做决定 |
|---|---|---|---|
| 认证 | 谁在调用 | 拒绝（未配即 403） | 系统（拦截器） |
| 能力边界 | 能碰什么 | 拒绝（白名单/BLOCK） | 系统（护栏） |
| 动作审批 | 往外做什么 | 挂起（等人批） | 人工（ApprovalGate）+ 规则（Veto） |

**这个"默认拒绝 + 显式授权"的骨架，就是 Harness 权限机制的全部。** 它对应一条可以放进 review 的通用判据：**任何安全相关的逻辑，先问"它的默认值是拒绝还是放行"，再问"放行的条件是不是显式的、可审计的"。**

### 2.5 前沿深挖：Agent 安全的两个新坐标——OWASP LLM Top 10 (2025) 与 CaMeL 的"特权隔离"

**① OWASP LLM Top 10 2025 版把 Agent 的风险从"说什么"移到"做什么"。** 对 Agent 系统最关键的三条：**LLM01 Prompt Injection**（注入不再只是骗模型说错话，而是驱动它做错事）、**LLM05 Improper Output Handling**（Agent 的"输出"不是给用户看的文本，而是直接驱动工具/文件系统/数据库的指令——输出不校验等于 RCE 的前厅）、**LLM06 Excessive Agency**（过度授权：给的工具比任务需要的多）。这三条正好对应本讲三层——输入注入检测、输出护栏、动作审批——**业界共识与你已经建成的骨架是同一个形状**。

**② CaMeL：把"不可信数据"关进隔离的 LLM，用数据流追踪代替关键词拦截。** Google DeepMind 的 CaMeL（[arXiv:2503.18813](https://arxiv.org/abs/2503.18813)）是目前最有工程感的注入防御方案，机制值得细看：**可信用户指令进 Privileged LLM 生成执行计划；不可信外部数据进 Quarantined LLM 处理，且每个变量携带 provenance（来源标记）随数据流传播；当被污染的数据要进入"控制流位置"（比如决定调用哪个工具、文件路径）时，策略引擎直接拒绝**。这与本讲的关键词/熵检测是**两个层面**的防御：你是在模型层内做概率性过滤，CaMeL 在模型层外做确定性的数据流策略——**"非确定性防御 + 确定性外带策略"双层叠加，才是 2025 年后注入防御的完整形态。**

**③ 沙箱是"审批之外的最后一米"。** 高危动作（跑 shell、写文件）即使有审批，执行环境也应隔离——业界做法是 gVisor/Firecracker 级沙箱或至少容器隔离 + 最小权限 token。你的系统目前是"审批+权重仲裁"，可以把"执行环境隔离度"作为权限成熟度的第四层来规划：**认证（你是谁）→ 边界（你能碰什么）→ 审批（这件事谁批）→ 隔离（批了也在笼子里跑）。**

## 三、避坑清单

- [ ] **认证 ≠ 授权。** "知道你是谁"和"授权你干什么"是两个独立关,别混成一把 key。
- [ ] **钥匙不能存明文。** AK 存 SHA-256、上游密钥存环境变量名——泄露数据库不等于泄露认证。
- [ ] **安全相关默认值必须是拒绝。** fail-closed,不 fail-open。没配 Admin-Key = 403。
- [ ] **按"干什么"分钥匙。** 调用面和管理面独立,别一把 key 走天下（最小权限）。
- [ ] **输入要防注入,输出要防泄露。** 只做一面,权限漏一半。
- [ ] **检测精度取决于放置位置。** 预检只标注、写库边界才 BLOCK——因为那里才有完整上下文。
- [ ] **别把业务词当注入硬拦截。** 「越权/admin mode」在审查域是正常词，硬拦会误杀正常任务。
- [ ] **仲裁要有权重、有强否决,不是平票。** BLOCKER 强否决不可抑制,降噪不得覆盖底线。
- [ ] **往外做的动作要过审批。** ApprovalGate 先批再动。
- [ ] **"沉默不是中立"。** 需要 AI 表态的机制里,不主动上报 = 机制退化。

## 四、动手任务

> **目标**：把你 Agent 的权限,从"加了个鉴权"升级成"三层各自 fail-closed"。

**步骤 1:审计默认值**

grep 你的所有鉴权/拦截逻辑,逐个回答:**"这个默认值是拒绝还是放行?"** 凡是放行的,标出来并改成拒绝。

**步骤 2:审计钥匙的存储**

检查你的 AK/密钥是不是明文存库或明文写在配置里。改用哈希（AK）或环境变量名（上游密钥），让"泄露数据库"不等于"认证失守"。

**步骤 3:补输出护栏**

如果你现在只做了输入注入检测,加一个 `OutputGuardInterceptor`:模型输出发出去之前,检查越权/敏感内容。

**步骤 4:给高权限动作挂审批**

列出你的 Agent 会"往外发声"的动作(写库/回写/发消息/改状态),为每一个回答:**"它会自动执行,还是等人批?"** 把"改变状态"这一类挂上 ApprovalGate。

**步骤 5:给仲裁定义权重**

如果你的多 Agent 有"意见冲突怎么办"的问题，确认它是**有权重、有强否决**的，而不是平票。给"不可逆破坏"的维度（安全）最高权重、给强否决项（BLOCKER）明确不可抑制。

**步骤 6:验证 BLOCK 进不了上下文**

构造一个含注入的 diff,验证 `ContentInjectionDetector` 把它标成 BLOCK 后,**该片段确实没进 LLM 上下文**(而不是只打个日志)。

## 本讲小结

1. **权限是三层:认证(谁)- 能力边界(能碰什么)- 动作审批(往外做什么谁批)。** 每层默认都拒绝。
2. **fail-closed 是唯一正确默认值，钥匙本身也要防泄露**——AK 存 SHA-256、上游密钥存环境变量名。
3. **按"干什么"分钥匙。** 调用面与管理面独立（最小权限）。
4. **输入防注入、输出防泄露,两面都要管。** 检测精度取决于放置位置；别把业务词当注入硬拦。
5. **往外做的动作要过审批。** ApprovalGate 先批再动,Veto 有权重 + 强否决（安全 100 > 逻辑 90 > …），BLOCKER 不可抑制。
6. **"沉默不是中立"。** 该表态的机制不主动上报 = 退化。
