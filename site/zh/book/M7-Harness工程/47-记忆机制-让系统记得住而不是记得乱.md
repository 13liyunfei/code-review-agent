## 一、痛点

"Agent 要有记忆"——这句话谁都会说,但 Harness 视角要问的是**三类问题,答案完全不同**：

**问题一：这一次对话里,模型记得刚才说过什么吗?**
这是**会话记忆**。答案是"靠把历史塞进上下文"——顺理成章,但 token 有成本,满了要滚动。

**问题二：系统能不能检索到该参考的知识?**
这是**知识记忆**。模块四的 RAG 全在做这件事——向量化、召回、重排。

**问题三：系统会不会因为过去的结果而变好?**
这是**经验记忆**——"上一次我给这个仓库提过类似意见,这次该不该复用那条经验?"**这一层最容易被做成`只写不读`。** 模块五的经验总结里,有一句你建这个系统时的血泪：**"同一病复现 N 次:读侧无现成钩子必漏接线;验收须真实形态输入 + 生产接线 + 真实探针三件套。"**

三者的区别如果不能明确,就会出现一个典型翻车：**会话记忆断成一段段、知识记忆什么都能查到、经验记忆写了没人读。** "记得乱",比"记不住"更糟。

## 二、原理

### 2.1 三类记忆,别混装——读法不同，是它们最本质的分界

| 类型 | 放什么 | 生命周期 | 怎么读 |
|---|---|---|---|
| **会话记忆** | 本轮对话历史 | 随会话流动,满了滚动 | 直接拼进上下文 |
| **知识记忆** | 项目规范、文档、既往发现 | 持久,按检索召回 | 向量/混合检索(模块四) |
| **经验记忆** | 复盘沉淀的"下次该注意什么" | **真正有生命周期状态机** | 注入上下文的【历史经验参考】 |

前两类你在模块二、模块四都建过了。**Harness 视角的增量在第 ③ 类**——它把"记忆"从"存储"升级成"会变好的系统能力"。

但这里有一个**隐含的分界，比"分三类"更深**：这三类记忆的**读法（怎么取）决定了它们本质上是不同的东西**：

- **会话记忆是"拼"**——历史消息原样进上下文，是线性的、随对话滚动的；
- **知识记忆是"检索"**——按相似度召回，是**模糊匹配**，越像越靠前；
- **经验记忆是"注入"**——它不是"检索出来"，而是走一条**显式的钩子**直接注入到上下文末尾。

**为什么经验记忆不走"向量检索"这条路？** 这是本项目踩出来的一个关键教训：

> 一开始"经验"也被做成向量通道——存进 pgvector、按相似度检索。但向量检索做的是**语义相似**：一条经验和"当前这个 PR 有多像"。而经验想要的其实是 **"这条经验是否被反复验证为正确"**（用 `pos/neg` 计数表达的**质量**），不是"它和当前问题像不像"。**用向量去检索经验，等于用"相似度"这个错误的维度去替"可信度"做决定**——所以最后向量经验通道被废弃，改成在 `RagContextBuilder.buildContext` 末尾显式注入【历史经验参考】。

这条教训的通用形式是：**先想清楚"这个记忆是按什么维度被取用的"，再决定它该用什么存储。** 按相似度取的（知识）用向量库；按"可信度/频率"取的（经验）用计数 + 状态机；按顺序取的（会话）用滚动列表。**存储形态是"读法"的结果，不是起点。**

### 2.2 经验记忆的生命周期:能升级、能降级、能淘汰——而且判定要"原子"

`ExperienceStage` 定义了一条**四态状态机**——这才是"经验记忆"和"乱堆"的分水岭：

```
CANDIDATE（候选）── pos≥3 ──▶ ACTIVE（生效）
     ▲                              │  neg≥2
     └────────── ARCHIVED（归档）◀──┘
                        │ 闲置 180 天归档 / 90 天硬删
                        ▼
                    PURGED（清理）
```

三件事把"堆着"变成了"驯化过程"：

1. **写入有门禁**：一条经验不是一上来就"生效"。它先当 `CANDIDATE`,用得多了(`pos≥3`)才升为 `ACTIVE`。**这就是"写入门禁"——只有被反复证明有用的,才配进系统提示。**
2. **能降级淘汰**：一条经验被否了很多次(`neg≥2`),就降到 `ARCHIVED`;闲置久了就 `PURGED`。**"该忘的必须能忘"——没有人收敛的记忆,三年后全是互相矛盾的僵尸条目。**
3. **时机是规划好的**：`MemoryMaintenanceScheduler` 每天 03:40 跑一次归档/清理。**淘汰不是随缘,是定时任务。**

而"状态机"能成立，还有一个**存储层的硬要求**：**状态切换必须是原子的**。`pos/neg` 计数、`stage` 字段的更新，在 PG 里全走**行级 UPSERT / ON CONFLICT**，而不是"先查再改再写"三步：

> 如果升级判定是"读一次计数 → 判断是否到 3 → 写回 ACTIVE"这三步，并发下会有**丢失更新**（两个请求同时读到 pos=2，都认为自己该升级，写两次）。行级 UPSERT 把"计数 +1、判断阈值、翻转状态"压进**一条原子语句**里，才能保证 `pos≥3 → ACTIVE` 这个判定在并发下不丢、不重、不错。

**判据句**：**记忆的状态机，只有架构在"原子判定"之上才可信。** 阈值（pos≥3 / neg≥2 / 180 天 / 90 天）是 SQL 常量、不是散落在代码里的魔法数——因为它们既是"业务规则"，也是"并发安全"的载体。

读这条状态机和第 10 讲(记忆系统)最大的差别是定位:第 10 讲你在**建组件**,这一讲你在问 **"这条经验凭什么有资格告诉我下次该注意什么?"**——答案就是:因为它在状态机里活过了 `CANDIDATE`,被证明有价值。

### 2.3 经验记忆的"读"要靠注入钩子,否则必然只写不读

这是本项目踩过的真实坑,也是 Harness 视角最血泪的一条：

> 经验仓库(`ExperienceStore`)建好了、写也写了,但 **"同一病复现 N 次"** 才发现——**没人读它**。

修复 = 找"本应注入的钩子":`RagContextBuilder` 的 `buildContext` 末尾追加【历史经验参考】分区。**它不是藏在流程里,而是你**特意**给它留了一个注入点。**

**判据(带血的)**：**任何"为未来而写"的机制,都必须有一个"本应被注入"的读侧钩子。** 如果你写完一个记忆/沉淀功能,找不到它该挂在哪读出来,那它 90% 会变成僵尸数据。验收不是"能写进去",而是 **"真实形态输入 + 生产接线 + 真实探针"三件套**——能证明它真的被读进了上下文。

### 2.4 该忘的和该留的,要分开放——存储层还有一个隐蔽的"维度陷阱"

`MemoryMaintenanceScheduler` 的归档/硬删阈值(闲置 180 天归档、90 天硬删)说明一个取舍:**记忆不是越多越好,是"活的"才值钱。** 如果一条经验三个月没被用到,它大概率已经和现在的仓库脱节了——留着它,下次检索就多一分噪音。

除了"该忘的要能忘"，向量知识记忆这一侧还踩过一个**更隐蔽、只有做过 pgvector 才懂的坑**：

> **向量维度不一致会静默毁数据。** 如果你的 embedding 模型实际输出 1024 维，但 pgvector 列建表时默认成了 256 维（或反过来的任何不一致），写入时要么报错、要么更糟——**在上一次"启动时备份重建向量列"的逻辑里，维度不一致会直接毁掉整列数据**。`pgvector` 的 `vector-dim` 必须和你的 embedding 真实维度对齐，且这个对齐要成为**迁移脚本里的显式断言**，而不是"靠默认值碰运气"。

这是一条和"状态机要原子"并列的**存储层纪律**：**记忆系统的正确性，一半在业务状态机，一半在存储层的数据校验。** 状态机再漂亮，向量列维度错了照样把知识记忆清空。

### 2.5 前沿深挖：三大开源记忆系统的架构对照——Letta、mem0、Zep 各自押了什么注

你的经验记忆（证据驱动状态机）是一条路；开源界的三个主流记忆系统各自押了不同的注，对照看能校准你的设计：

**① Letta（MemGPT 血统）：三层内存 = RAM / 聊天记录 / 硬盘。** Core Memory 始终在上下文内（模型的"常驻内存"，容量小但永远在场）；Recall Memory 是会话历史（靠搜索召回）；Archival Memory 是无限大的归档（语义检索）。**机制要点：记忆进入上下文是"显式的页换入"，模型自己通过工具调用决定把哪段记忆调入 Core——记忆管理本身被做成了 Agent 的工具。** 这与你的"读侧注入钩子"是两种哲学：你是系统自动注入，Letta 是让模型主动翻页。

**② mem0：写入时的巩固决策——ADD / UPDATE / DELETE / NOOP。** mem0 的论文（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)）给生产级记忆补了关键一环：**新事实写入前先语义检索相近记忆，再让模型判定四选一——新增、更新旧记忆、删除矛盾记忆、或什么也不做**。"记忆巩固"不是定时摘要任务，而是**写入路径上的一次判重与合并**。mem0g 变体再把记忆组织成实体-关系图。**对你的经验库：这等价于在 upsertReflection 之前加一道"语义近邻判重"——你的证据计数是字符串级 pattern 匹配，mem0 是语义级合并，后者抗"同一经验换了措辞"的重复写入。**

**③ Zep：双时态知识图谱——旧事实不删，只标记"何时不再为真"。** Zep 的差异在**时间维度**：事实带 valid_from/valid_to，旧版本保留，于是 Agent 能回答"上个季度我们认为 X 是什么"。**这是"记忆会过期"的最严谨建模：不是删除，是时效化。** 你的 ARCHIVED 状态是软删除的雏形，但缺少"何时失效"的时间轴。

**④ 一个诚实的边界**：spaced repetition（间隔重复抗遗忘）目前在 Letta/mem0/Zep 的 production 机制里都没有真正落地，**它在你的系统里（闲置 180d 归档 + 证据计数）反而是更靠前的实践**——把它当"未来实验方向"写进 roadmap 是准确的，别说成业界标配。

> - mem0 论文（含 ADD/UPDATE/DELETE/NOOP 巩固）：[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)
> - Letta（MemGPT）三层记忆：letta.com 官方博客与文档

## 三、避坑清单

- [ ] **三类记忆要分装:会话 / 知识 / 经验。** 混装 = 检索噪音 + 上下文浪费。
- [ ] **先想"按什么维度取"，再定"用什么存储"。** 按相似度→向量库；按可信度→计数+状态机；别拿向量去检索"经验"。
- [ ] **经验写入要有门禁。** `CANDIDATE` 过了 `pos≥3` 才升 `ACTIVE`，别让"只出现一次"的经验进系统提示。
- [ ] **状态切换要原子。** 阈值判定走行级 UPSERT / ON CONFLICT，别"先查再改再写"三步（并发丢失更新）。
- [ ] **记忆要能降级、能淘汰。** 淘汰要定时（调度器），不是随缘；没人收敛的记忆会变僵尸。
- [ ] **向量维度必须和 embedding 对齐。** pgvector `vector-dim` 用迁移脚本显式断言，别靠默认值。
- [ ] **警惕只写不读。** 写完记忆功能，问你一句"它挂在哪被读出来?"找不到钩子就是僵尸数据。
- [ ] **验收用三件套:真实形态输入 + 生产接线 + 真实探针。** 别只验证"能写进去"。

## 四、动手任务

> **目标**：给"经验"这条链路,补上生命周期 + 读侧钩子 + 存储层校验。

**步骤 1:给经验定义状态机**

如果你有条目是"直接塞进上下文的",给它加 `CANDIDATE→ACTIVE→ARCHIVED` 三态,定义升级/降级阈值。**并确认这些阈值是 SQL 常量、更新走原子语句**，而不是"先查再改"。

**步骤 2:问一句"我为什么用向量/列表存它"**

对你现有的每一类记忆，写下它的**取用维度**（相似度？可信度？顺序？）。如果"经验"被塞进了向量库、按相似度取，标记出来——那大概率是维度用错了。

**步骤 3:找读侧钩子**

打开你注入上下文的地方(类似 `RagContextBuilder`),确认经验/历史沉淀**真的被读出来了**——不是关在仓库里。

**步骤 4:写三件套验收**

为记忆读侧写验收:**真实形态输入**(真实入库数据)、**生产接线**(走真实注入路径)、**真实探针**(查日志/返回里能看到经验被注入)。没有三件套,等于没验证。

**步骤 5:加淘汰 + 维度断言**

给过期条目加一条定时销毁:闲置多久降级、多久硬删。并给你的向量列加一个"维度与 embedding 一致"的显式断言。

## 本讲小结

1. **记忆分三类:会话(流动)/ 知识(检索)/ 经验(沉淀)。** 读法不同是它们最本质的分界。
2. **先想读取维度，再定存储形态**——按相似度用向量库，按可信度用计数+状态机，别拿向量去检索经验。
3. **经验记忆要有状态机**:`CANDIDATE→ACTIVE→ARCHIVED→PURGED`,用 `pos`/`neg` 阈值驱动，判定必须原子（UPSERT/ON CONFLICT）。
4. **写入要有门禁、该忘的必须能忘**——淘汰挂在定时任务。
5. **存储层要校验**：pgvector `vector-dim` 必须与 embedding 对齐，否则静默毁数据。
6. **任何"为未来而写"的机制,都要有一个"本应被注入"的读侧钩子。** 找不到钩子 = 僵尸数据。
7. **验收用三件套:真实形态输入 + 生产接线 + 真实探针。**

下一讲拆最后一个机制:**技能机制**——`ExtensionPoint` / `ExtensionRegistry` / `Skill` / `DeclarativeReviewAgent` 怎么让 Agent 的能力"可插拔、可灰度、声明可用"。
