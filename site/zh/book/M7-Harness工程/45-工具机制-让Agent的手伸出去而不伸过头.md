# 第 45 讲 · 工具机制：让 Agent 的手伸出去而不伸过头

> 🎯 导读问题：**"Agent 怎么调用你的工具？"** ——只答"模型返回 function_name,我查表调用"是及格;能答出"**工具调用是一个带护栏的循环:声明 → 校验 → 调用 → 降级**,每个工具都有能力边界和失败兜底"才算真的做过。

> **为什么归 Harness 工程**：工具是 Agent 的"手"——它能碰到的每一样东西都是能力。**Harness 的三个字,在工具机制上就是:让手伸得出去(能接各种工具),又伸不过头(每个工具能干什么、干砸了怎么办都明确)。**

## 一、痛点

第 05 讲你已经见过了 Function Calling：模型在输出里说"我要调 `get_repo_info`",你的代码收到一个 JSON,查表、调用、把结果塞回上下文。

如果工具机制只到这个程度,那它太简单了——但它在生产里崩的地方,几乎都藏在三个"没人提前想"的问题里：

**问题一:谁保证模型传进来的参数是对的?**

模型说 `files = ["src/Main.java"]`,但如果你不校验,它可能传一个不存在的路径、一个越权的路径、一组会导致你工具炸掉的参数。**模型的幻觉会直接传染给工具参数。**

**问题二:工具失败了,Agent 怎么办?**

工具抛了异常,你是让整个 Agent 流程一起崩,还是让 Agent"知道这个工具没成功、换一条路"?模块四那条经验——**"这个 bug 的特征是:所有测试都是绿的"**——在工具机制上同样成立:工具调用失败被吞掉,从监控上看根本发现不了。

**问题三:工具是依赖还是能力?**

同一个"发消息"动作,是本地类还是远端 MCP?**如果工具是写死在 `if` 里的调用,每接一个工具都要改一遍主流程**;如果工具是可声明的、可插拔的,接一个新工具 = "写一个适配器 + 加一行配置"。

**问题四（最隐蔽）：这个循环什么时候停？**

模型说"我要调工具"，你的循环调完、把结果塞回去，模型又可能说"我还要再调一个工具"……那它到底什么时候才算"干完了"？**没有一个明确的终止条件，你的 Agent 要么无限循环烧钱，要么一句话就草草收场。** 这是工具机制区别于"单次函数调用"的真正的难题。

## 二、原理

### 2.1 工具调用的四步循环

`ToolCallingLoop` 把一次工具调用拆成四步,每一步都明确、可测：

| 步 | 做什么 | 判据 |
|---|---|---|
| ① 声明 | 把工具的能力讲给模型听 | name / description / 参数 schema 完整 |
| ② 校验 | 模型传的参数先过护栏 | 类型、存在性、越权检查(白名单) |
| ③ 调用 | 执行真实工具 | 本地直调 或 MCP 远端 |
| ④ 降级 | 失败时怎么办 | 结果可回填上下文,不炸主流程 |

`GuardedTool` 就是"护栏"这二字的实现——它把真实工具包一层,在**调用前拦截**这件事(参数校验、权限检查),而不是把护栏散落在每个工具里。**这让"安全"成为工具的公共属性,而不是每个工具的自觉。**

### 2.2 循环的终止条件：工具机制真正的灵魂

四步之外，`ToolCallingLoop` 最核心的设计其实是一个**循环不变式**：**每一轮都由模型决定"要不要继续调用工具"，而系统用一个硬性的 `max_iterations` 兜底。**

循环的每一轮是一个完整的"问模型 → 判断 → 调用 → 回填"：

```
while (true) {
    msg = llm.next(...);              // ① 问模型：接下来干什么
    if (!msg.hasToolCall()) return msg;   // ② 模型不再要求调工具 → 结束
    if (iterations++ >= max) throw ...;   // ③ 达到硬上限 → 强行终止
    result = guard.invoke(msg.toolCall);  // ④ 校验 + 调用
    context.append(result);               // ⑤ 结果回填，进入下一轮
}
```

这里有两个终止条件，**性质完全不同，缺一不可**：

1. **模型自己停**（`hasToolCall() == false`）：这是正常结束——模型觉得信息够了，开始输出最终回答。这是"软终止"，由模型的意图决定。
2. **系统强制停**（达到 `max_iterations`）：这是兜底——模型陷入了"调工具 → 不满意 → 再调"的循环，或者干脆在一个幻觉参数上反复卡死。不设这个上限，**一次任务可能烧掉几十轮调用、几十倍的钱，而且永远不会自己停**。

**`max_iterations` 的取值是一门取舍科学**：太小 → 模型还没拿到足够信息就被掐断、答错；太大 → 失控成本的天花板变高。它的本质是 **"你愿意为一次任务的正确率，承担多少次模型调用（多少 token / 多少钱）的上限"**——和第 32 讲的成本计量、第 43 讲的退避上限，是同一个"经济账"思想。

> 判据句：**工具循环必须有两个终止条件——模型说停（软），系统说停（硬）。** 只有前者，会无限循环；只有后者，会过早收场。

### 2.3 护栏的三层校验：不是"一个 if"，是"一段 pipeline"

`GuardedTool` 的"校验"不是一个笼统的动作，它实际上是**三层递进**的拦截，每一层挡住一类错误：

| 层 | 拦住什么 | 典型判据 |
|---|---|---|
| ① 类型/结构 | JSON 反序列化都过不了的参数 | 参数 schema 不匹配、缺必填字段 |
| ② 存在性/合法性 | 引用了一个不存在/非法的实体 | `file` 路径不存在、ID 查无 |
| ③ 越权（白名单） | 引用了一个"存在但不该碰"的实体 | 路径越出授权目录、操作无权限 |

前两层是"格式"问题，第三层是"权限"问题。**很多实现只做了前两层，漏掉了第三层——而第三层恰恰是安全问题的高发地**：一个路径"存在且合法"不代表"这个 Agent 能读"。护栏的价值，就是把这三层**集中、显式**地表达出来，而不是指望每个工具作者都记得。

### 2.4 工具的能力边界是白名单,不是黑名单——回收 ToolExposure 三级

这是 Harness 工程在工具机制上最核心的判据。**你定义"这个工具能碰什么",而不是"这个工具不能碰什么"。**

- 白名单：`canRead(path)`、`hasPermission(action)`——**列允许的**,默认拒绝。
- 黑名单：`if (path.startsWith("/etc")) throw ...`——**列禁止的**,默认放行。

为什么必须是白名单?因为**黑名单总有漏网之鱼**,而"能碰什么"一旦默认放行,一个幻觉就能让 Agent 访问它不该碰的东西。**审计安全性的一个朴素判断:你拦截的逻辑,是"默认拒绝"还是"默认放行"?**

第 05 讲那个 `ToolExposure` 三级枚举（`DIRECT` / `DEFERRED` / `CODE_MODE`）在这里回收——它是"白名单"思想在**工具暴露面**上的推广：

- `DIRECT`：轻量工具，默认可用；
- `DEFERRED`：重工具，**默认拒绝（fail-closed）**，需显式授权；
- `CODE_MODE`：代码模式专用，仅显式进入时才暴露。

注意 `DEFERRED` 的默认值是"拒绝"而不是"放行"——**这正是白名单原则的具象**：你没有显式说"这个工具可以用"，它就不可用。把"默认拒绝"作为工具暴露的基线，是把幻觉可能造成的破坏面降到最小。

### 2.5 本地工具与 MCP 工具,是同一套护栏的两种手

工具机制的另一个分界是**工具的归属**：

| 维度 | 本地工具 | MCP 工具 |
|---|---|---|
| 在哪里跑 | 同一个进程内 | 另一个进程/服务 |
| 怎么声明 | 直接实现接口 | `McpToolAdapter` 桥接 |
| 怎么接新的 | 写一个类 | `HttpMcpClient` + 一句配置 |
| 生命周期 | 随应用 | 独立服务 |

`McpToolAdapter` 的存在说明一件重要的事：**接一个 MCP 工具 ≈ "写一个适配器类 + 加一行配置",而不是改一遍主流程。** 这正是第 42 讲里那条跨进程协议判据的形态——**接一个新工具是"加",不是"改"。**

MCP 的"跨进程"不是一句抽象，它背后有一条**真实的握手 + 调用序列**：

1. **连接**：`McpClient` 与 MCP Server 建立会话（`HttpMcpClient` 走 HTTP，也支持 stdio 本地进程）；
2. **列举**：客户端请求 `tools/list`，拿到远端暴露的工具清单（name + description + inputSchema）；
3. **桥接**：`McpToolAdapter` 把远端这个工具**包成本地 `AgenterTool` 同款接口**——这一步是关键的抽象，它让"MCP 工具"和"本地工具"对上层（`ToolCallingLoop`、护栏）**看起来完全一样**；
4. **调用**：本地护栏校验通过后，适配器把它翻译成 `tools/call` 发给远端，拿回结果。

**桥接（第 3 步）是整个设计的灵魂**：正因为 MCP 工具被适配成和本地工具同一种接口，第 2.3 的护栏、第 2.4 的白名单才能**对两种工具一视同仁**——权限检查不会因为"工具来自另一个服务"就放水。

### 2.6 工具的失败必须是 Agent 的"输入",不是系统的"异常"

回到问题二。Harness 视角的处理不是"吞掉异常",而是把失败变成一个 Agent 能读取、能继续的**结果**。

这要求工具调用返回的不是裸的"返回值或异常"，而是一个**结构化的 `ToolResult`**，至少含三层信息：

- `success`（这次调用到底成没成）
- `output`（成功时的产出）
- `error`（失败时的原因 + 诊断信息）

有了这个结构，**"失败"才能成为一个可回填的输入**：模型读到 `error`，可以决定"换一个参数再试""换一条路径"，或者诚实地回答"我做不到，因为 X"。

这条和模型调用机制(第 43 讲)是同一个思想:**失败不是流程的终点,是决策链的一个输入。** 区别只在于——模型调用的失败由系统判定(熔断/退避),工具调用的失败由 Agent 判定(能不能换条路)。

### 2.7 前沿深挖：MCP 一年四版补齐"身份与异步"，但安全研究显示工具元数据本身就是攻击面

**① MCP 正在从"调用工具"长成"工具生态协议"。** 对照 MCP 2025-11-25 版规范的 changelog（modelcontextprotocol.io），一年内的机制级变化包括：**OpenID Connect Discovery 支持（身份）、incremental scope consent（增量授权）、sampling 支持 tools/toolChoice（服务端可反向驱动模型带工具调用）、experimental tasks（异步任务）、JSON Schema 2020-12 成为默认 schema dialect（更强的参数校验表达力）**。含义很清楚：MCP 不只是函数调用的转发协议，它在逐版补齐**身份、权限、异步、schema 治理**四块企业级拼图——第 2.5 节你的 MCP 适配层，未来对接的就是这套越来越完整的规范。

**② 工具元数据不是文档，是模型执行路径的输入——因此它是攻击面。** 2025 年的安全研究把两类 MCP 攻击讲透了：**tool poisoning**（[arXiv:2506.01333](https://arxiv.org/abs/2506.01333)）——恶意 MCP server 在 tool description / 参数 schema / 返回值文档里藏隐含指令，模型会把元数据当行为指令执行；**rug pull**——server 在你授权之后**动态修改**工具的能力与数据访问范围，"审批过一次"根本覆盖不了长期信任。**对你的护栏设计，这两条各加一个判据：工具元数据必须当不可信输入处理（进上下文前过注入检测）；工具的 schema 与权限声明必须按版本钉死并在变更时重新审批。**

**③ 循环终止的工程实践比 max_iterations 复杂。** 业界 harness 工程实践（如公开的 agentic-loop 指南）给出的终止设计是组合件：**max_turns 只是硬兜底**，还要叠加**工具错误去重**（同一工具同一参数连续失败 N 次直接拒绝再试）、**观察窗口**（检测"模型在原地打转"的重复 action 模式）、**kill switch**（外部可介入的强制终止）。你的工具循环目前是"软终止+硬上限"两道，可以对照补齐后两道——**原地打转检测本质上是一个"观察历史的状态机"，和熔断器是同族思想。**

## 三、避坑清单

- [ ] **护栏是工具的公共属性,不是每个工具的自觉。** 用 `GuardedTool` 这种包装,别要求每个工具作者自己记得校验。
- [ ] **护栏是三层 pipeline**（类型 → 存在性 → 越权），别只做"格式校验"漏掉"越权白名单"。
- [ ] **能力边界是白名单,不是黑名单。** 默认拒绝;别用 `endsWith` 黑名单,过匹配的结局是漏报。
- [ ] **工具循环必须有硬性 `max_iterations`。** 只有"模型说停"这一个软终止，会无限循环烧钱。
- [ ] **工具参数必须先校验再调用。** 模型的幻觉会传染给工具参数。
- [ ] **工具失败要能回填上下文,不炸主流程。** 用结构化的 `ToolResult(success/output/error)`，失败是 Agent 的输入。
- [ ] **接新工具应该是"加"不是"改"。** 如果每接一个工具都要改主流程,你的工具机制退回了 if-else。
- [ ] **MCP 与本地工具共用一套护栏。** 靠 `McpToolAdapter` 把两种工具归一成一种接口，别因为归属不同而放水。

## 四、动手任务

> **目标**：把你的工具调用,从"查表调用"升级成"带护栏 + 可降级 + 可插拔"的循环。

**步骤 1:给每个工具定义白名单**

列出 Agent 所有工具,为每个回答:`它默认拒绝什么?` 凡是答不上来的,默认是放行的——先改成白名单。

**步骤 2:给工具循环加硬性上限**

找到你的工具调用循环，确认它**除了"模型说停"，还有一个 `max_iterations` 硬兜底**。没有就加上，并写一个"模型反复调同一个工具"的测试，验证它最终会被掐断而不是死循环。

**步骤 3:把护栏拆成三层**

把你现在的"参数校验"拆成"类型 → 存在性 → 越权"三层，逐层确认：前两层拦格式，第三层拦越权（白名单）。别让越权检查缺席。

**步骤 4:给工具调用加失败回填**

当工具抛异常时,把它变成"失败 + 你能做什么"的结构化结果（`success=false` + `error` 原因）回填给模型,而不是让整个流程崩掉或静默吞掉。加一个测试:工具挂了,Agent 还能继续。

**步骤 5:让工具可插拔**

如果你现在工具是 `if (action.equals(...))`,抽出统一的声明(接口/注册表),让"接一个新工具"变成"写一个类 + 注册一行"。

**步骤 6:挑一个真实远端工具走 MCP**

用 `McpToolAdapter` / `HttpMcpClient` 把某个"别的进程/别的语言"的能力接进来,验证跨进程工具和本地工具走同一套护栏。

## 本讲小结

1. **一次工具调用 = 声明 → 校验 → 调用 → 降级。** 每一步明确、可测。
2. **工具循环有两个终止条件**：模型说停（软）+ `max_iterations`（硬）。只有前者会无限循环。
3. **护栏是三层 pipeline**：类型 → 存在性 → 越权（白名单），越权层是安全高发地。
4. **工具的能力边界是白名单,不是黑名单。** 默认拒绝;`ToolExposure.DEFERRED` 的 fail-closed 是同一思想。
5. **本地工具与 MCP 工具是同一套护栏的两种手。** `McpToolAdapter` 把两种工具归一成一种接口，接新 MCP ≈ 一个适配器 + 一行配置。
6. **工具的失败是 Agent 的输入,不是系统的异常。** 用结构化 `ToolResult` 回填。
7. **接新工具是"加"不是"改"。** if-else 调工具是 Harness 的倒退。
