## 一、痛点

前四个模块里,你是**调用方**：要把一个模型调对、调稳。到模块五你把视角切成**平台方**,把 `token-factory` 做成网关。现在换第三个视角——**Harness(驾驭)**：**不看"这段代码对不对",看"这个决定是怎么做出来的"。**

这三个视角差在哪?

- **调用方关心**：这次调用成功了吗?
- **平台方关心**：这条路在别家挂了时会不会把整个团队拖死?
- **Harness 视角关心**：连谁、什么时候不连了、什么时候放弃——这些到底是不是**可判定的**?还是散落在 if-else 里拍脑袋定的?

第三层的问题,往往是前两层暴露不出来的。拿一个真实例子：

`RoutingEngine` 的路由表,不在启动时加载,而是**包成一个 `Function`,每次请求实时查库**：

```java
Function<String, List<RouteTarget>> routesByAlias = alias ->
        routes.findEnabledByAlias(alias).stream()
                .map(r -> new RouteTarget(r.alias(), r.providerCode(), r.upstreamModel(),
                        r.priority(), r.weight(), r.enabled()))
                .toList();
```

运行时的注释写得很直白：**"改完路由立刻生效,运维不用重启网关。"**

很多人在第一次读这段时,会下意识觉得这"要么是聪明的优化,要么是偷懒"。**Harness 视角不这么问。它问的是：这条链上，所有"决定"都集中在一个可改、可查、可审计的地方吗？**

答案是：是的——因为**所有 `new` 都发生在 `GatewayConfig` 这一个装配点**(第 30 讲讲过)。路由、熔断、退避、重试分类器,全是构造器注入的普通实例。**决定不在代码里,决定在"喂给这些构造器的参数"里。**

这就是 Harness 工程和普通开发的分野：**普通开发写"这次调 A 模型";Harness 工程写"A 模型不可用时,系统会自动做什么,而且这个"自动"本身有判据、有留痕。**

下面我们把这条链上的**每一个判据**都拆到"算法/源码"这一层——因为只停在"要有判据"是不够的，真正的深度在于：**这个判据具体是怎么算的、为什么这么算、算错了会发生什么。**

## 二、原理

### 2.1 把"一次调用"拆成四道门

以 `ChatController` 为入口,`RoutingEngine` 为引擎,`token-factory` 里"一次调用"实际走四道门：

| 门 | 角色 | 判据 | 对应代码 |
|---|---|---|---|
| ① 路由 | 决定连谁 | 当前有哪个 enabled 的候选通道 | `RoutingEngine` / `PriorityRouteStrategy` |
| ② 熔断 | 决定这一路还值不值得试 | 该 provider 最近失败是否已达阈值 → OPEN | `CircuitBreakerRegistry` |
| ③ 退避重试 | 决定尝试几次、隔多久 | 按分类器是否属于可重试错误,退避递增 | `DefaultRetryClassifier` / `BackoffPolicy` |
| ④ 上报 | 决定这次花了多少钱、失败了几次 | 无论如何都要记账 | `TokenUsageRecorder` |

四道门不是四个独立模块，而是**一条有依赖顺序的流水线**：路由先选出"要连谁"，熔断决定"这条路现在敢不敢走"，退避决定"这条路由失败后多长时间再试"，最后上报把前面所有决定都落成一份可查的账。任何一道门拍脑袋，整条链的"可判定性"就断了。

### 2.2 第一道门：路由——"权重随机"到底是怎么算的

`PriorityRouteStrategy` 这个名字已经泄露了算法的一半：**先按 priority 排序，再在同 priority 里按 weight 加权随机。**

很多人把"加权随机"想象成"随便抽一个"，但它的实现是有正式的算法语义的。标准做法是**累加权重 + 一次随机落点**：

```java
// 伪代码：同 priority 组内的加权随机
int total = targets.stream().mapToInt(RouteTarget::weight).sum();
int point = random.nextInt(total);        // 0..total-1 之间落一个点
int acc = 0;
for (RouteTarget t : targets) {
    acc += t.weight();
    if (point < acc) return t;            // 落在 [acc-weight, acc) 区间内
}
```

这段代码看似简单，却藏着三个 Harness 视角必须追问的细节：

1. **weight 是可变的**：路由表是"查出来的函数"，所以 `weight` 是可以动态调比例的。这直接催生了"灰度/切流"能力——你想让新模型先吃 10% 流量，就把新通道 `weight=1`、旧通道 `weight=9`，让概率自己跑，而不写任何 `if`。
2. **weight=0 的语义**：累加到 `total` 里不贡献概率，等价于"下线但不删记录"。这比把 `enabled` 直接置 `false` 更温和——它保留了"我随时能通过改一个数字把它拉回来"的能力。
3. **priority 的语义是"硬切"而非"软分"**：不同 priority 之间**不是**按比例分流的，而是**高优先级的通道活着，低优先级的就完全不参与**。这才能表达"主备切换"：主通道 priority=1、备通道 priority=2，主通道可用时备通道永远轮不到；主通道一 OPEN（见 2.3），才自动落到备通道。**分比例流量用 weight，做主备用 priority，两者是正交的两根轴。**

**判据句（放这里成立，换任何网关成立）**：**"连哪家模型"必须是一个运行时可改的配置，而不能是一段写死的代码。** 如果哪天你在 review 时看到 `if (provider.equals("deepseek"))`,给它标出来——那是 Harness 的倒退。

### 2.3 第二道门：熔断——三态状态机的精确转移条件

第 ② 道门值得单独强调：熔断状态是"可判定"这件事的典型代表。它把"这一路是不是挂了"这个模糊问题,翻译成了 `CLOSED / OPEN / HALF_OPEN` 三个**可枚举、可查询、可测试**的状态。

但"三个状态"只是表象——真正的深度在于**状态之间转移的精确条件**，以及**为什么是这三个、不是两个或四个**。

> **图 43-1**　熔断器三态状态机。关键不是"有三个状态"，而是**每一条有向边都对应一个可精确判定的条件**：连续失败数、冷却期、试探结果。没有这些精确条件，"熔断"就只是"大概挂了"的布尔。

这个状态机里有三个决策点，每一个都有它"为什么这么设计"的深层理由：

**决策点一：用什么指标判定"该开了"——连续失败，还是失败率？**

如果你的熔断靠"最近 100 次里失败 30%"这种**失败率**，你就要额外维护一个滑动窗口，而且低流量时 1 次失败就能让失败率飙到 100%。`token-factory` 选的是**连续失败计数**（第 36 讲的 `ProviderHealthView` 里那个 `consecutiveFailures` 就是它）：

> 连续失败 N 次 → OPEN。语义直观，实现极简，且天然适配"模型网关"这种**错误基本是独立事件**的场景。

它的代价是"偶发一次成功"会重置计数——这本就是你要的：一次成功说明那条路又通了。

**决策点二：为什么要有 HALF_OPEN 这个中间态？**

假设只有 CLOSED / OPEN 两态，冷却期一到你想"再试试这条路通没通"，只能**全量放行**——如果它根本没修好，你等于把一整批流量砸进一个还坏着的上游。HALF_OPEN 的语义就是"**用小流量试探**"：放行极少量请求（比如 1~2 个），它们都成功了才转回 CLOSED，任何一个失败立即重开。**这是"熔断"和"降级"能安全自动化的关键一环。**

**决策点三：冷却期（openDuration）为什么必须有？**

没有冷却期的 OPEN 态，要么永久拒绝（配置问题还没修就永远进不来），要么需要一个外部信号才能恢复。冷却期把它变成**自愈**：过一段时间自动给一次"试探机会"。这个时长是"工程师愿意为'自动恢复'承担多少'可能又砸一次'的窗口"的直接表达。

而"累计失败要有窗口"这条，是模块五做熔断时就埋下的：失败数**必须在时间窗口内衰减**,否则一次"昨天挂了很久"会让熔断器今天还开着。**连续失败计数 + 时间窗口，两个维度缺一不可——前者是"开的条件"，后者是"不会永久钳死"的保险。**

### 2.4 第三道门：退避——指数退避的公式与"为什么要有抖动"

`BackoffPolicy` 的四个参数（第 30 讲 `GatewayConfig` 里见过）是 `baseMillis / multiplier / maxMillis / jitterRatio`。它生成的第 `n` 次重试间隔是：

```
delay(n) = min( maxMillis,  baseMillis × multiplier^n )
```

以 `base=500ms, multiplier=2, max=2000ms` 为例，就是第 43-0 图里那串 `500 → 1000 → 2000 → 2000 …`：先指数增长，撞到 `maxMillis` 后封顶。

这段公式里最容易被忽略、也最容易被删掉的是 **jitter（抖动）**：

> 如果成千上万个并发请求在**同一时刻**因为上游 429 而一起进入退避，且它们都用**完全相同的公式**算出"500ms 后重试"，那么 500ms 后它们会**同时**再次涌向上游，形成一次新的尖峰——这叫**惊群（thundering herd）**。

jitter 的做法是给 `delay` 乘一个 `(1 - jitterRatio)` 到 `(1 + jitterRatio)` 之间的随机系数，把"同时重试"打散成"在一段区间里分散重试"。**删掉 jitter 不会立刻报错，但会在流量高的某天把上游二次压垮——这正是"源码机制级深度"才能看清的、藏在参数里的工程判断。**

除了这个"自算"的退避，模型网关还有一条**上游说了算**的退避来源：`429` 响应头里的 `Retry-After`。**优先用它**——因为这是上游明确的"请你慢点、什么时候再来"的约定，比你自算的公式更贴近它的真实限流节奏。第 34 讲那个 `UpstreamException` 里的 `retryAfterMillis` 就是从这来的（那一讲还讲了它"只夹下界、不夹上界"的事故，可见退避参数本身就是生产风险源）。

**判据句**：**重试的判据是"失败的种类",不是"失败了这个事实"。** 把 4xx 也塞进重试,等于**用钱和时间重复犯同一个错误**——而退避参数（base/multiplier/max/jitter）则是"重试这个决定"的经济账本：它规定了"为一次可能自愈的失败，我愿意等多久、花多少时间"。

### 2.5 失败分类——分类器的实现形态

`DefaultRetryClassifier` 决定**哪种失败值得重试**。这一步很容易被做成"遇到异常就重试",但 Harness 视角要求**给失败分门别类**：

| 失败类型 | 该重试吗 | 理由 |
|---|---|---|
| 429 / 限流 | 是,且要退避（用 Retry-After） | 上游在"请你慢点",重试有意义 |
| 5xx / 网关超时 | 是,退避 | 瞬时故障,重试常有收益 |
| 4xx / 请求本身错 | **否** | 重试一百次也是同一个错误,纯浪费钱 |
| 鉴权失败 401/403 | **否** | 这是配置问题,不是瞬时故障 |

分类器内部的实现形态，不应该是一个散落的 `if-else`，而是一个**显式的判定函数**：输入一个失败（状态码/异常类型），输出第 34 讲见过的那个 `RetryDecision(retryable, backoffMillis, reason)`。

这里有个 Harness 视角的关键设计：**判定结果里必须带 `reason`。** 它看起来只是一串字符串，但它是"为什么要重试/为什么不重试"这个决定能被**事后审计**的唯一载体——没有它，账本里只剩一个 `retryable=true/false`，你永远无法回答"当时那个 401 为什么没重试"。

### 2.6 第四道门：记账——留痕的字段与语义

`TokenUsageRecorder` 的存在说明一件事：**一次调用的"结果"不只是给调用方看的,也是给运营看的。** 即便调用失败,消耗的 token(如果上游返回了 usage)也要记下来。

这背后是第 32、33 讲的成本计量与用量上报。Harness 视角把它补成一句更狠的判据：

**没有"记录"的调用等于没发生。** 如果一个决定不被任何日志/埋点/账本记录,你就永远无法回答"它当时为什么连了这家、花了多少"。**可审计,是 Harness 工程对一切"I/O 决策"的底线。**

记账这件事在模型网关里有两个容易被砍、但砍了就失去"可审计"的细节：

1. **失败也要记 usage**：上游在返回错误时，有时仍会带上已消耗的 token 数（用户请求进来它就烧了）。如果只在成功路径记 usage，那些"失败了但钱照花"的调用就会变成账本上的黑洞。
2. **估算要打标记**（第 33 讲的 `estimated`）：有些上游根本不回 usage，网关只能按"3 字符/token"这种规则估算。这条记录如果不标 `estimated=true`，就会污染你的成本报表——**估算值和真实值是两种数据，混在一起就再也分不开了。**

### 2.7 把整条链形式化：一次调用的完整生命周期

把上面四道门拼起来，一次调用在 happy path 和降级 path 下的完整生命周期是这样：

| 阶段 | 判定输入 | 判定逻辑 | 判定输出 | 落痕 |
|---|---|---|---|---|
| 路由 | alias + 管理面配置 | priority 选存活组，组内 weight 加权随机 | 一个 `RouteTarget` | 选中了哪家 provider/model |
| 熔断 | provider 的连续失败计数 | `≥ N` → OPEN | 放行 or 抛 `CircuitOpenException` | 状态 + 转换原因 |
| 调用 | 上游 HTTP | 正常收发 | 响应 or 失败 | statusCode / 耗时 |
| 退避重试 | 失败种类 | 分类器 + BackoffPolicy + Retry-After | `RetryDecision` | retryable + backoff + reason |
| 记账 | usage / estimated | 累加成本 | 一行用量 | provider/model/token/耗时/重试 |

**这张表就是 Harness 工程对"一次模型调用"的完整答卷。** 读者是研究员或架构师时，你要能对着每一行说出：**输入是什么、判定怎么算、算完了落到哪个字段、这个字段能被谁查。**

### 2.8 前沿深挖：路由正在从"规则"走向"学习"，开源网关的重试链路值得抄

**① 学习型路由：RouteLLM 把"选强模型还是弱模型"训成分类器。** 前面讲的是规则路由（优先级+权重）。学术界更进一步：**RouteLLM**（[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)）用偏好数据训练一个路由器，预测"这个查询派给强模型值不值"，在保持质量的前提下把成本砍掉一大截。但要警惕 2025 年的 follow-up《How Robust Are Router-LLMs?》（[arXiv:2504.07113](https://arxiv.org/abs/2504.07113)）：**路由器的泛化随查询分布漂移而衰减**——在训练分布上省 50% 成本的路由器，换到你的业务语料上可能只剩 15%。**判据：上学习型路由前，必须用自己的真实流量回放评估，别信论文里的平均数。**

**② 开源网关的失败处理链路比你想的完整。** LiteLLM 的 Router 把 retry/fallback/预算/限流收进同一组件；Portkey 则把 **Fallback、Automatic Retries、Circuit Breaker、Load Balancing** 分成四层独立可配。两者共同的工程范式值得抄进你的网关：**失败处理不是一招"重试"，而是一条分层链——单点瞬时错误先重试（退避+抖动）→ 连续失败触发熔断（cooldown）→ 熔断后 fallback 到下一个 provider → 全程限流与预算兜底**。你的 `LlmGateway` 已有熔断+记账，对照这条链查缺：fallback 的触发条件是否独立于重试？预算超支是否能参与路由决策？

**③ 判据句收口**：**路由的成熟度分三级——规则路由（能用）→ 学习型路由（会省）→ 带预算感知的路由（能算账）。你的系统走到哪一级，取决于记账（第 2.6 节）有没有沉淀足够的路由决策数据。**

## 三、避坑清单

- [ ] **路由表必须是运行时可改的。** 判断标准："改这个配置需不需要重启?"需要,就要问为什么。
- [ ] **分清 weight 和 priority 的两根轴**：分流量用 weight（软分），做主备用 priority（硬切）。把"主备"做成"99:1 的比例分流"是经典误解。
- [ ] **失败要分类,别一刀切重试。** 4xx 不该进重试——那是用钱重复同一个错误。
- [ ] **熔断状态要可枚举、可查询、可测试。** `CLOSED / OPEN / HALF_OPEN`,而不是一个"大概挂了"的布尔。
- [ ] **累计失败要有窗口衰减。** 没有窗口,昨天的故障会捂死今天的开关。
- [ ] **退避必须有 jitter。** 删掉它不会当场报错，但会在高并发时制造惊群、二次压垮上游。
- [ ] **429 优先读 Retry-After**，而不是只顾自算的退避公式。
- [ ] **重试退避必须可注入时间。** 测试里验证"500→1000→2000"不需要真的等 3.5 秒。
- [ ] **估算的用量必须打 `estimated` 标记**，别让估算值混进真实成本报表。
- [ ] **调用必须记账,无论成败。** 没有记录的决定等于没发生。

## 四、动手任务

> **目标**：亲手把你的一次模型调用,升级成一条"可判定 + 可审计"的决策链。

**步骤 1：给失败分类**

找你的模型调用封装,把 `catch (Exception e)` 拆开——**按 `429/5xx/4xx/鉴权` 分类**,并给"该不该重试"各写一条规则。用 `DefaultRetryClassifier` 的形态（输出带 `reason` 的 `RetryDecision`）,而不是散落的 if。

**步骤 2：让路由可热改，并分清两根轴**

如果你现在 `if ("deepseek"...)` 写死了 provider,把它改成一查配置。然后回答两个问题：**你的"候选通道"是主备关系（该用 priority）还是分流关系（该用 weight）？** 别把两者混成同一个参数。

**步骤 3：给熔断画出状态机**

把你现有的熔断逻辑画成一张 `stateDiagram`（照图 43-1 的模板）。**每条边都标上精确条件**：连续失败数阈值、冷却期、试探结果。画不出来，说明你的熔断还没有可判定的边界。

**步骤 4：加一张调用账本**

给每次调用记一行：`provider / model / 输入token / 输出token / 耗时 / 是否重试 / 是否估算 / 最终结果`。先写日志都行,但**必须留痕,且估算要打标**。

**步骤 5：验证"挂了换路"**

把主通道的 `enabled` 置 `false`,观察流量是否平滑切到候选通道,且账本里能查到这次降级（含原因）。

## 本讲小结

1. **一次模型调用是一条决策链**,连谁 → 这一路行不行 → 挂了退避几次 → 成败都记账。Harness 工程的第一道闸门是"**它到底连哪家、什么条件不连了**"。
2. **路由是"priority 硬切 + weight 软分"两根轴**：主备用 priority，分流量用 weight，别混为一谈。
3. **熔断是三态状态机，每条边都有精确条件**：连续失败 N 次开、冷却期到半开、试探成回闭/败重开。
4. **退避 = base×multiplier^n 封顶 + jitter**；429 优先读 Retry-After。删 jitter 会在高并发制造惊群。
5. **失败分类是"该不该重试"的唯一判据**，4xx 重试是拿钱重复犯错；判定结果必须带 `reason` 才能审计。
6. **成功失败都必须留痕**——没有记录的决定等于没发生,可审计是 I/O 决策的底线。

下一讲我们把第二道闸门拆开:**上下文压缩机制**——`RagContextBuilder` 到底怎么决定"给模型看什么",以及压缩为什么不是"截断"而是"准入 + 分层 + 投放"。
