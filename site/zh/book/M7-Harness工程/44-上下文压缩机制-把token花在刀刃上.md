# 第 44 讲 · 上下文压缩机制：把 token 花在刀刃上

> 🎯 导读问题：**"你的 Agent 上下文为什么不够用？"** ——只答"上下文窗口就那么大,超了截断"是及格;能答出"**上下文管理 = 准入 + 分层 + 投放**三件事,截断是最后的手段不是第一手段"才算真的做过 Agent 工程。

> **为什么这一讲归在 Harness 工程**：模块四你已经把 RAG 做好了——切块、向量化、召回、重排。这一讲换个角度问**钱的事**：模型对上下文是**按 token 计费的**,而"给模型看什么"这件事,本质是**用最少的 token 达成最高的正确率**。**Harness 视角 = 把"上下文"当成一种稀缺的、有价的资源来管理,而不是当成一个能无限塞的口袋。**

## 一、痛点

"上下文窗口不够用"——这是 RAG 用户最常抱怨的一句话。但模块四的整条经验告诉我们,真正的病根几乎从不在"窗口不够大"：

> 第一版 RAG 上线两周,"机器人提的意见跟规范对不上"。我连换了三样东西：加了 300 篇文档、换了更强的模型、甚至想换向量库。**最后把链路铺开一看：规范根本没被检索出来。** 向量库没问题、模型没问题、文档数量没问题——**问题在链路。**

模块四解决的是"**怎么让该被检索的文档被检索出来**"(召回)。而 Harness 工程要解决的,是比召回更前面、也更省钱的三个问题：

| 你以为是 | 其实是 | 花在哪 |
|---|---|---|
| 上下文不够,得换大窗口 | 塞了不该看的进去了 | 每 token 都算钱,垃圾进 context 是纯烧钱 |
| 相关文档多了点没关系 | 每次投票都被无关片段稀释 | 检索命中 50 条,相关度排序没做好 |
| 塞得越多越聪明 | 超过模型"有效注意力"后就下降 | 不是越多越好,是"对的多"才越好 |

**一句话总结痛点**：上下文是**有价的稀缺资源**,但 90% 的系统把它当免费的口袋用。下面每一层，我们都往下钻一层，看"准入/分层/投放"在源码里到底是怎么被**精确判定**的——因为只喊"要少给"是口号，能答出"少给什么、按什么标准少给"才是工程。

## 二、原理

### 2.1 压缩 = 准入 + 分层 + 投放,截断是最后手段

Harness 视角给"上下文管理"定了一个三层模型。**注意顺序:越靠前越便宜。** 越靠前，砍掉内容的单位成本越低——准入阶段砍掉的是"还没花召回和排序的钱"的内容，投放阶段砍掉的已经是"花完全部检索成本"的内容了。

### 2.2 第一层 · 准入：进 context 之前就砍，靠的不是"关键词"而是"异常判定"

第 20 讲的判据在这里回收：**"不该给模型看的内容,不要让它进了上下文再过滤——在准入阶段就剔除。"** 这一次剔除,省的是**白花的 token 钱 + 白带的噪音**。

`RagContextBuilder` 的准入有两道，各自守不同的门：

**准入一：`ContentInjectionDetector`——把"恶意/无效内容"挡在检索入口。**

它的判据不是简单的关键词黑名单，而是三类**可精确判定的异常（Anomaly）**：

| 异常类型 | 判据 | 为什么能拦注入 |
|---|---|---|
| 超长（长度异常） | 单文件/单段远超常规代码长度 | 注入 payload 往往靠"海量填充"挤掉真实指令 |
| 填充/重复 | 高比例重复字符或模板串 | 攻击者用重复文本淹没系统设定 |
| 熵异常 | 香农熵落在异常区间（**仅限纯 ASCII**） | 高频重复字符会让熵异常地低 |

这里有个`code-review-agent` 踩出来的、极容易被忽略的细节——**熵判定只对纯 ASCII 生效**：

> 中文字符本身的熵天然就高（一个 UTF-8 中文字节序列的信息量远大于 ASCII），如果你拿英文的熵阈值去卡中文内容，会把**合法的中文代码/注释误杀成"注入"**（实测中文熵 > 5.5 就会误杀）。所以这个判据的适用域必须是"纯 ASCII 输入"，这就是"源码机制级"才能看清的边界——**判据不是普适的，它有一条隐藏的适用范围**。

检测的结果也不是"通过/拦截"二值，而是三档处置：

- **BLOCK**：确定性恶意，**直接不进检索、不进上下文**——在入口就挡掉；
- **TAG**：可疑但不确定，**标注后放行**（spotlighting，第 35 讲）；
- **CLEAN**：干净，正常走。

**BLOCK 和 TAG 的区别，就是 2.1 说的"越靠前越便宜"的具象**：BLOCK 省的是"检索 + 排序 + 调用"全链路成本，TAG 只是"提醒模型注意"，成本一分没省。所以只有**高置信恶意**才该 BLOCK。

**准入二：`supports()` 的 `containsCodeFile`——把"纯文档 PR"整个剔除在语义 Agent 之外。**

逻辑/性能/风格/架构这些语义 Agent 覆写了 `containsCodeFile`，判定规则是 **language ≠ unknown 即算代码**（xml、sql 也算代码）。于是：**一个纯文档的 PR（比如只改了 README），根本不会进语义 Agent 的上下文**——直接跳过整次 LLM 调用。

这条判据的工程价值在于它把"这个 PR 值不值得花 LLM 的钱"提前到**调度之前**判定，而不是"先调一轮、发现没代码、白花钱"。

> 注意 Security Agent 是**不参与这个剔除的**（它恒跑）——因为"纯文档里也可能藏注入"，安全审查不能因为"没有代码"就豁免。这一个例外，正是"准入判据必须按审查维度分别定义"的证据：**"该不该进来"没有一个全局答案，它取决于"进来之后要干什么"。**

### 2.3 第二层 · 分层：四种内容四个生命周期，不进同一个口袋

上下文不是一层,是**分层的**。Harness 视角规定四种东西各住各的层,不进同一个口袋：

| 层 | 放什么 | 生命周期 | 例子 |
|---|---|---|---|
| 系统提示 | 恒定的规范、红线、协议 | 跨会话不变 | 指定的输出格式、禁止事项 |
| 对话层 | 本轮临时信息 | 随对话流动、用完即弃 | 当前 diff、本轮检索片段 |
| 知识层 | 检索出来的"可能相关" | 有价、要排序、要预算 | RAG 命中文档 |
| 经验层 | 历史沉淀的"这次该注意什么" | 长时稳定、末尾追加 | 【历史经验参考】 |

`RagContextBuilder` 的 `buildContext` 末尾追加【历史经验参考】分区,就是一个**活的例子**：它把"过去学到的经验"作为**独立、靠后**的一层追加进去——不和检索正文混,因为它来源和生命周期都不同。

分层这件事，源码级要回答的深层问题是：**为什么是"末尾追加"而不是"开头"或"混在正文里"?**

答案藏在"模型的注意力分布"里：**越靠后的内容往往对最后生成的回答影响越大**（这就是为什么 few-shot 样例、最重要的指令通常放最后）。"历史经验"是"这次要多注意什么"的提醒，属于**高优先指令**，所以放末尾让它"临门一脚";而如果把经验混进检索正文中间，它会被当作"又一段候选材料"和几十条检索结果一起被稀释。

> **你读它时会发现:给模型看什么,从来不是"拿一个数组拼起来",而是"按生命周期的不同,分门别类地投喂"。** 生命周期的差异，决定了它该占哪个"槽位"，而不是简单地 `String.join("\n", everything)`。

### 2.4 第三层 · 投放：漏斗四数字 + 预算截断的精确逻辑

模块四的漏斗四个数字——**候选 / 放行 / 重排 / 注入**——正是"投放"的可观测化。这四个数字不是四个装饰性埋点，它们对应检索链路上**四个会"掉量"的节点**，任何一个断层，你都能立即定位问题出在哪一步：

| 漏斗节点 | 含义 | 掉了说明什么 |
|---|---|---|
| 候选 | 混合检索（dense + BM25）召回的总条数 | 召回不足——该进来的没进来 |
| 放行 | 过了相似度/准入阈值后保留的条数 | 阈值过严 or 真没相关内容 |
| 重排 | HeuristicReranker 重排后按新序保留的条数 | 排序策略是否在起效 |
| 注入 | 最终塞进上下文的条数（受预算约束） | 预算是否卡掉了有效内容 |

投放的判据是两件事，各有精确语义：

1. **排序**：按重排后的相关度从高到低注入，**不是召回顺序、也不是相似度原始值顺序**。这里有个必须知道的坑（第 25 讲也提过）：混合检索里 BM25 的分和 dense 的余弦分**量纲不同、不能直接比**，所以要过 **RRF（倒数排名融合）** 归一到一个可比的排名分。而 RRF 归一后"第一名恒等于 1.0"——**这只是一个排名，不是一个真实的语义相似度**。真正的余弦相似度单独存在 `similarity` 字段里。**拿 RRF 的归一分数去卡"相似度 ≥ 0.3"这种阈值，是把"排名"当"距离"用，闸门永远关不上。**

2. **预算**：不超过单次调用的 token 预算。超预算的做法是**按重排顺序截到预算上限**——先放进确定有价值的，而不是"硬塞"或"随机砍"。截断的位置是**确定的**（从头截），不是不可复现的。

### 2.5 压缩的对象是"切出来的块"，切块算法有它的数学账

`StructuredChunker` 把文档切成 **700 字符、15% 重叠**的块,按标题/围栏/空行切,硬切回退句子边界。这三个参数都不是拍脑袋：

- **700 字符为什么不是 200 或 2000**：块太小 → 一个语义单元被拆碎，召回的每一块都"只对了一半"；块太大 → 一个块里混进多个主题，向量被平均掉，检索相关性下降。700 是这个场景（代码 + 中文文档混合）下"语义完整"和"检索精准"的折中。
- **15% 重叠为什么必须有**：一刀切会把一句话/一个函数从中间断开。15% 重叠让相邻两块共享边界附近的上下文，保证**跨块边界的语义（如"它"指代前一句的主语）不丢失**。重叠率太高会浪费 token（重复内容被重复计费），太低又接不上。
- **"按结构切、失败才硬切"为什么重要**：优先在标题/代码块围栏/空行处切，是因为这些边界是**语义的自然断层**——在这儿切，块才"自成一句完整的话"。硬切（按字符一刀断）是**回退兜底**，不是首选。**回退路径的存在，说明这个算法有"优雅路径 + 保底路径"两层，而不是赌输入永远是规整的。**

**判据句**：切块的粒度,决定了压缩的下限。**切得碎,等于用金价买散装垃圾。**

### 2.6 中文的 token,天生比英文贵——这是预算要用真实 token 的原因

模块四第 26 讲的中文分词坑,在 Harness 视角下有一个更功利的后果：**中文没有一个字一个 token**,一个 4 字符的成语可能占 6~8 个 token。同样的语义,中文比英文贵。

`TextTokenizer` 用 **中文 bigram + 标识符子词**（全大写缩写整体保留），而不是按空格分词。为什么中文不能简单按空格切：

> 中文没有天然的空格分隔，"按空格切"会把一整句切成一个 token，`plainto_tsquery` 一查就得全句匹配（AND），等于检索永远零命中。bigram 的做法是**相邻两个字组成一个词元**（"上下文压缩" → "上下""下文""文压""压缩"），既不用维护一个大词表，又能覆盖任意新词。这是中文分词在"召回率 vs 维护成本"上的经典取舍。

而这条对 Harness 的直接后果是：**预算不能按"字符数"估，必须按"真实 token 数"估。** 一个按字符数设预算的系统，一旦喂进中文，真实 token 会超预算 50% 以上——因为它的"1 字符 = 1 token"假设在中文下彻底失效。第 32 讲成本计量的那笔账，在这里接上了：**所有 token 成本预估，都要用真实 tokenizer 结果，而不是字符数近似。** 检索两侧若不用同一套 tokenizer，等于**花双份钱检索单份内容**。

### 2.7 前沿深挖：context engineering 成为显学——Anthropic 的官方判据与"context rot"

**① Anthropic 的官方立场：上下文不是越长越好，是"让必要约束优先加载"。** Anthropic 在 context engineering 官方博客（《The new rules of context engineering for Claude 5 generation models》，claude.com/blog）披露了一个反直觉数字：**他们为新一代模型移除了 Claude Code 中 80% 以上的 system prompt，代码评测没有可测损失**。这直接印证本讲的预算截断逻辑——**系统提示不是资产清单，是预算消耗项**；能被即时检索/按需加载替代的内容，就不该常驻。

**② "lost in the middle"与 context rot：位置本身就是变量。** 研究界早已证实模型对长上下文**开头和结尾的召回显著好于中段**（lost-in-the-middle），社区进一步把"长会话质量随轮次衰减"统称为 **context rot**。**工程含义：CLAUDE.md / 系统提示里最重要的规则不要放在中段；加载顺序与槽位本身就是召回率变量。** 这正是本讲"投放层做相关度排序"之外还缺的一条判据——**排序之外还有位置学**。

**③ Context folding：多步任务的历史不该逐条保留。** 2025 年的 Context Folding 工作（[arXiv:2510.11967](https://arxiv.org/abs/2510.11967)）把子轨迹完成后**折叠为结构化摘要**——活跃上下文只保留摘要与未决约束，而不是全部历史操作。这与你系统的分层投放同构但更激进：不只是"选哪些块进上下文"，而是**"已完成子任务整体坍缩成一条摘要"**。多步代码重构、长审查会话这类场景，folding 比 window 截断保真度高得多。

**接回你的系统**：本讲的漏斗四数字（候选/放行/重排/注入）现在可以加第五个视角——**位置**：放行后的块在上下文里的摆放顺序，同样影响模型召回。判据句补一条：**上下文工程 = 选什么（准入）× 放多少（预算）× 摆在哪（位置）× 何时坍缩（folding），四件事独立可判。**

## 三、避坑清单

- [ ] **默认立场是"少给",不是"多给"。** 每一条塞进上下文的内容,都要能说出"它帮正确率做了什么"。说不出的就是噪音+钱。
- [ ] **准入要在进入前,不进上下文再过滤。** `ContentInjectionDetector` 的 BLOCK 是在入口挡,不是事后清。
- [ ] **熵判据只对纯 ASCII 生效。** 拿英文熵阈值卡中文会误杀正常内容（中文熵天然高）。
- [ ] **准入判据要按审查维度分别定义。** "纯文档剔除"不适用于 Security（文档也能藏注入）。
- [ ] **分层别混装。** 恒定规范进系统提示、临时信息进对话、检索进知识层、沉淀进经验层。混装既浪费又稀释；高优先经验放末尾（注意力靠后）。
- [ ] **别把 RRF 排名分当相似度用。** 归一后第一名恒为 1.0，拿它卡"≥0.3"闸门永远关不上。
- [ ] **投放要按预算截断,按相关度排序。** 超预算 = 按顺序截,不是全塞。
- [ ] **切块粒度决定压缩下限。** 块要"自成一句完整的话",别把句子切两半；结构切优先，硬切兜底。
- [ ] **中文别当英文算 token。** 预算按真实 token 估,不按字符数；检索两侧用同一套 tokenizer。

## 四、动手任务

> **目标**：给你的 RAG 上下文,补上"准入 + 分层 + 投放"三件事,并把漏斗数字露出来。

**步骤 1:审计你的注入点**

打开 `RagContextBuilder`(或你自己的),把注入上下文的每一段标上**它属于哪一层**(系统/对话/知识/经验)。凡是标不出来的,问它一句"它对正确率做了什么"。特别注意：**经验/高优先指令有没有放在注意力最敏感的靠后位置。**

**步骤 2:加漏斗四个数字**

在检索链路里埋点:**候选命中数 / 放行数 / 重排后保留数 / 实际注入数**。四个数字必须可查询。造一次"该召回却没召回"的 case，看四个数字里是哪一个先掉。

**步骤 3:给注入加预算**

给单次调用的知识层注入设一个 token 预算,超预算时**按重排顺序截断**而不是全塞。用真实 usage 验证截断后正确率不掉。**预算必须按真实 token 算,不是字符数。**

**步骤 4:验证中文 token**

把一段中文文本按字符数和真实 token 数各算一遍,体会"字符 ≈ token"这个假设在中文下有多离谱。用它对一次调用做成本预估,和真实账单对比。

**步骤 5:检查你的"相似度阈值"用的是哪个分**

翻出你卡阈值的那个数字，确认它是**真实余弦相似度**，而不是某个归一化后的排名分。两者混用，是 RAG 最隐蔽的 bug。

## 本讲小结

1. **上下文是稀缺资源,不是免费口袋。** 它按 token 计费,垃圾进 context 是纯烧钱。
2. **压缩 = 准入 + 分层 + 投放,截断是最后手段。** 越靠前越便宜。
3. **准入靠"异常判定"而非关键词**：超长/填充/重复/熵异常，BLOCK/TAG/CLEAN 三档；熵判据仅限纯 ASCII。
4. **准入判据按维度定义**：纯文档剔除不适用于 Security（文档也能藏注入）。
5. **分层按生命周期分槽位**，高优先经验放末尾（注意力靠后）；投放按预算截断、按重排序注入。
6. **别把 RRF 排名分当相似度**；切块粒度决定压缩下限；中文 token 天生比英文贵。
