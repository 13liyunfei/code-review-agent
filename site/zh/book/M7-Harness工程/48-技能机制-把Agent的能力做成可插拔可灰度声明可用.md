# 第 48 讲 · 技能机制：把 Agent 的能力做成可插拔、可灰度、声明可用

> 🎯 导读问题：**"你的 Agent 怎么扩展？"** ——只答"做接口、加实现"是及格;能答出"**扩展要三层：能力封装（Skill）→ 能力挂载（ExtensionPoint）→ 能力灰度（Feature Flag）,并且"声明式"让非核心开发者也能写 Agent**"才算真的把它做成了"平台"而不是"自己的一亩三分地"。

> **为什么归 Harness 工程**：六讲到这里收口。技能机制回答的是"**Agent 的能力怎么被包起来、怎么被打开、怎么被安全地放量**"——这是 Harness 工程里最接近"平台"的一环,也是你从一个写 Agent 的人,变成一个"让别人也能写 Agent"的人的分水岭。

## 一、痛点

到这一讲,你已经亲手建过一个能跑、能查、能降级、能上生产的 Agent 系统。现在把镜头拉远,问一个"你自己用 vs 别人用"的问题：

**你自己写 Agent 时,一个功能从"能用"到"变强",是全在一个代码库里改——这没问题。但当你希望"业务方、团队里的别人"也能给这个系统加能力时,三种翻车就出现了：**

**翻车一:能力没有封装,是散落的代码。**
"给 Agent 加个'安全审查'的能力",如果它意味着在代码库里到处 new 组件、改主流程,那它就不是一个"能力",而是一次改版。

**翻车二:能力一上就全量。**
你把"规划能力"加进去,没想清楚就默认所有请求都启用。结果某一天它在某个仓库上表现不稳——因为**没有灰度,**它永远没有回来的机会。

**翻车三:只有你会写 Agent。**
如果加一个"业务方自定义 Agent"需要会 Spring Bean、会写 Java 装配,那它就是给你一个人用的系统,不是平台。**"声明式"才是平台的门槛**——让懂业务不懂框架的人,用描述/配置就能声明一个 Agent。

## 二、原理

### 2.1 封装：能力强成一个"Skill"——契约里到底有什么

`Skill` 是能力的最小封装单位——它把"这个能力是什么、怎么声明、边界在哪"包成一份契约。Skill 之所以是"能力"而不是"类",关键在于:**它对外暴露的是"声明"与"边界",不是"实现细节"。**

那这份"契约"具体包含什么？一个合格的 `Skill` 至少要回答四个问题：

| 契约字段 | 回答的问题 | 被谁消费 |
|---|---|---|
| 唯一标识 + 名称 | 这个能力叫什么、怎么被引用 | 注册表、配置 |
| 能力描述 | 这个能力能干什么 | **模型**（决定它是否被选中，同第 5 讲的 `description`） |
| 触发/适用条件（`supports()`） | 什么场景下才该用这个能力 | 调度器（省 LLM，同第 44 讲的准入） |
| 行为契约 | 输入什么、输出什么、边界在哪 | 调用方 |

**注意：`Skill` 的 `supports()` 和第 44 讲 `containsCodeFile` 是同一个东西的代际重复**——都在问"这个能力/Agent 适不适用于当前输入"。这说明技能机制和上下文准入、内容准入是**同一条"先判定再用"的原则**在不同抽象层上的投影：**任何"能用但未必该用"的能力，都要有一个可判定的适用条件，而不是默认全量调用。**

这和 `ExtensionPoint` 是同一件事的两面:`ExtensionPoint` 定义"哪里能长出能力",`Skill` 定义"长出来的是什么样的能力"。它们合起来回答——**系统的扩展面在哪里、扩展物的形状是什么。**

### 2.2 挂载：注册表 vs SPI——为什么选"注册表"而不是"扫 classpath"

`ExtensionRegistry` 是能力的"总目录"——所有能力在这里**注册、可查询、可枚举**。一个能力是否被加载,不靠"代码里恰好 new 到了",而靠注册表里有没有它。

这里有个架构师一定会问的对比题：**"为什么要显式注册，而不是像 Java SPI 那样扫 classpath 自动发现？"** 两者都能解耦，但取舍不同：

| 维度 | 显式注册表（本项目选） | SPI 自动发现（ServiceLoader） |
|---|---|---|
| 谁决定加载什么 | 装配点显式列出 | classpath 里有什么就发现什么 |
| 可预测性 | 高——注册=启用，一眼可见 | 低——加了 jar 就"自动"进来了 |
| 审计/灰度 | 天然支持（注册就是开关） | 需要额外机制才能关 |
| 启动开销 | 无（不扫描） | 扫描 META-INF 有开销 |

**Harness 工程选"显式注册"，本质和第 43 讲"路由是配置不是代码"、第 48 讲"新能力默认关"是同一个哲学**：**"加载了什么"应该是显式、可审计、可灰度的，而不是"classpath 里恰好飘进来了什么"。** 自动发现是便利，但便利的代价是"你不知道系统里到底有哪些能力在跑"。

这套带来的能力是第 45 讲那条"加不是改"的升级版：

- **本地写一个 `Skill` 实现 → 往 `ExtensionRegistry` 注册一行** —— 新能力上来了;
- **不想用了 → 从注册表摘除一行** —— 能力下来了。

**判据：接/退一个能力,是"加一行注册",不是"改一遍主流程"。** 你的系统在哪个工具/技能/Agent 的接入上能做到这一点,它就在那个维度上配叫"平台"。

### 2.3 灰度：能力默认关，"关"和"没有"是两回事

再看 `ReviewAgentConfig` 里那排开关：

```
review.planning.enabled          default false
review.reflection.enabled        default false
review.eval.enabled              default false
review.tools.agent-loop.enabled  default false
```

**四盏灯,全部默认关。** 这不是保守,是 Harness 工程的灰度假说：“**一个能力没有在真实流量里跑稳之前,不配默认开。**”

为什么默认关这么重要?因为一个新能力(比如"规划 DAG 路由")一旦默认全开:

- 它出问题时,影响的是**所有请求**,不是一小撮;
- 它和旧行为混在一起后,你**没法判断变好是它带来的还是运气的**;
- 最糟的是——一旦全开,加回了"关掉"的难度,因为大家都依赖它了。

灰度还不止"全关/全开"一个开关这么简单。真正可运营的灰度，是**分级放量**：

1. **默认关**：新能力 code review 合入后不生效；
2. **内测**：只对少数内部仓库/团队放开（用 `X-Team-Id` 之类维度圈定一小撮）；
3. **灰度**：按比例或按团队逐步放大观察指标（正确率、成本、失败率）；
4. **全量**：多窗口数据稳定后才默认开。

而**"默认关"这个姿态,和"新能力默认缺席"是两回事**：关了不代表没有——它已注册、可查询、可一键打开；"没有"是它压根不在系统里。这个区分对应的是一条测试纪律：**关着的时候，请求里必须完全没有它的痕迹**（而不是"它还在跑、只是结果被忽略"）。

### 2.4 声明式：让别人也能写 Agent——但要"骨架不可覆盖"

`DeclarativeReviewAgent` 这个名字已经点了题。它不是让你继承一个抽象类去写 Java,而是**用"声明"来描述一个 Agent**——回顾第 16 讲的 `CustomAgentDef` record，一个业务方自定义 Agent 声明的内容是：

- **标识**：`id` / `teamId` / `name`；
- **角色与能力**：`description`（角色描述）、`focusPoints`（审查要点清单）；
- **行为偏好**：`severityBias`（严重级别偏好）；
- **生命周期**：`enabled` / `createdAt` / `updatedAt` / `version`（乐观锁）。

`CustomAgentStore` 让业务方可以**在不改主代码的前提下,注册自己的自定义 Agent**(走 `X-Team-Id` 隔离,不覆盖核心骨架——这正是架构图里那条 `custom-agent: 骨架不可覆盖` 的含义)。

这里有两个"为什么"，是技能机制的高级考点：

**其一，为什么声明式必须配"骨架不可覆盖"？** 声明式把"能写 Agent"的门槛降到了"会描述就行"，但同时也把"注入危险行为"的门槛降到了同样低。如果业务方声明一个 Agent 就能覆盖系统的安全骨架（比如把 Security 审查换成"只查风格"），那声明式就从"平台能力"变成了"绕过护栏的后门"。所以：**业务方只能填充内容槽（描述/要点/偏好），不能改系统硬编码的指令骨架**——骨架是护栏，槽位是自由度，两者必须分开（第 36 讲 `CustomAgentDef` 的三个内容槽就是这条的具象）。

**其二，为什么用 `version` + 乐观锁？** 一个可以被外部改的声明，必然面临"并发改同一份配置"和"改坏了要回滚"的问题。`version` 字段让更新走乐观锁（读到旧版本就拒绝覆盖），`updatedAt` 让"谁在什么时候改过"可审计。**声明式可扩展的前提，是这份声明本身被当成一等公民的数据来治理**——有版本、有隔离、可审计，而不是一段没人管的自由文本。

### 2.5 声明式不是银弹——它和代码式有明确的边界

把镜头再拉远一点，技能机制的最终形态不是"全声明式"，而是**声明式和代码式的正确分工**：

| 适合声明式（描述） | 适合代码式（实现） |
|---|---|
| 角色描述、审查要点、级别偏好 | 新的审查算法、新的检索策略 |
| 组合已有原子能力 | 创造底层没有的能力 |
| 表达的是"偏好和配置" | 表达的是"新逻辑" |

**声明式的表达力是有上限的**——它能"调整"和"组合"已有能力，却造不出"全新的能力"。把复杂算法硬塞进声明里，只会得到一个"看起来像配置、实际是伪代码"的怪物。成熟平台的正确姿势是：**用扩展点（ExtensionPoint）承载代码式的新能力，用声明式承载业务方的偏好组合，两者通过注册表和 Feature Flag 汇到同一套灰度体系里。**

**为什么声明式是平台的门槛?** 因为一个平台的复用极限,是"会配不用会写"还是"会写才用得了"。声明式把它推进到了"**会描述就能用**"。但一个真正的平台，不会让声明式去干代码式的活——它分得清"哪些留给懂业务的、哪些留给懂架构的"。

### 2.6 前沿深挖：Claude Code 把"行为控制"拆成七个面，技能封装的终局是"可调用 runtime"

**① Claude Code 的行为控制有七个不同的面，权威性和加载时机各不相同。** Anthropic 官方《Steering Claude Code》把控制面拆成：**CLAUDE.md（常驻规范）、rules（路径级规则）、skills（按需加载的技能包）、subagents（隔离上下文的子代理）、hooks（生命周期事件回调）、output styles、system prompt**。关键不在"有七个"，而在**它们的区分维度：加载时机（常驻 vs 按需 vs 路径触发）、compaction 后是否保留、上下文成本、权威性等级**。这恰好印证本讲的 Skill 四要素设计——supports() 是"加载时机"的判定，灰度是"权威性/成本控制"的判定。

**② 技能封装的终局形态：把模型、工具、权限、终止条件打包成一个可调用的 runtime。** 看 Claude Code 的 subagent/plugin 声明（YAML frontmatter）：`name / description / model / effort / maxTurns / disallowedTools`——**一个声明文件同时指定了用哪个模型、花多少力气、最多转几圈、禁止哪些工具**。这超越了"技能 = 一段提示词"的朴素理解：**成熟的技能封装是把"模型选型 + 工具白名单 + 权限边界 + 循环终止条件 + 上下文加载时机"整体打包**。你的 CustomAgentDef 内容槽+骨架设计已经在路上，对照这个字段清单可以查缺：你的声明式 Agent 能指定 maxTurns 和 disallowedTools 吗？

**③ 生态侧的对照样本**：OpenCode 读项目根的 `opencode.md`（等价于 CLAUDE.md 的开源平替）；Aider 的 **Architect mode** 把规划模型与执行模型分离——**"想"和"做"用不同模型**，这与第 49 讲 Claude Code 的主/快模型分级路由是同族思想。生态的共识正在收敛：**能力封装单元 = 声明文件 + 隔离上下文 + 受限工具集 + 明确终止条件。**

## 三、避坑清单

- [ ] **能力要封装成 Skill(声明 + 边界),不是散落的代码。** 扩散的 new 是能力丢失的信号。
- [ ] **Skill 要有适用条件（supports）**，别默认全量调用——这和上下文准入是同一原则。
- [ ] **能力要挂注册表,可查询、可枚举。** 接/退能力 = 一行注册,不是改主流程；显式注册优于 classpath 自动发现（可审计）。
- [ ] **新能力默认关。** `enabled override false`,跑稳了再放量。默认全开是大事故的温床。
- [ ] **灰度要分级放量，且"关着"要无痕。** 关着时请求里不能有它的影子。
- [ ] **灰度要能回退。** 一个能力放量后,保留"一键关掉"的路径,别让依赖绑架你。
- [ ] **声明式必须配"骨架不可覆盖"**——业务方只填内容槽，不能覆盖安全骨架。
- [ ] **外部可改的声明要有版本 + 乐观锁 + 隔离。** 声明是一等公民数据，别当自由文本。
- [ ] **声明式和代码式各司其职。** 声明式做组合/偏好，代码式做新逻辑，别让声明式变成伪代码。
- [ ] **"别人能加能力"才是平台。"只有你会写"是个人系统。** 用声明式把门槛降下来。

## 四、动手任务

> **目标**：把某个"你自己写好才有的能力",改造成"别人也能加"。

**步骤 1:抽一个 Skill**

选一个你现在"写死在 main 流程里"的能力,抽成 `Skill`(声明 + 边界 + `supports()` 适用条件),注册到 `ExtensionRegistry`。

**步骤 2:给它加开关**

给该能力加 `xxx.enabled`(默认 false)。写一个测试:关着的时候,请求里完全没有它的痕迹。

**步骤 3:声明一个"别人写的 Agent"**

用 `DeclarativeReviewAgent` / `CustomAgentStore` 声明一个不含 Java 装配逻辑的自定义 Agent——验证"懂业务的开发者"能不能只靠描述注册它（填内容槽即可）。

**步骤 4:验证骨架不可覆盖**

让自定义 Agent 试图覆盖核心逻辑,验证它被拦下(骨架不可变),而不是静默替换。

**步骤 5:给声明加版本化**

确认你的自定义 Agent 声明有 `version` + 乐观锁 + `X-Team-Id` 隔离，能做"谁改过、能否回滚"的审计。

## 本讲小结

1. **技能机制四步:封装(Skill)→ 挂载(ExtensionPoint/Registry)→ 灰度(默认关)→ 声明式(配置即 Agent)。**
2. **Skill 是"声明 + 边界 + 适用条件"的契约**，`supports()` 和上下文准入是同一原则。
3. **能力通过注册表挂载，显式注册优于 classpath 自动发现**——可审计、可灰度。
4. **新能力默认关 + 分级放量 + 可回退**——没有在真实流量里跑稳,不配默认开。
5. **声明式要配"骨架不可覆盖"**，业务方只填内容槽；声明要版本化 + 乐观锁 + 隔离。
6. **声明式做组合、代码式做新逻辑**。"别人能加能力"才是平台。

**模块七 · 模块小结**：六大机制——模型调用、上下文压缩、工具、权限、记忆、技能——其实是一条线的六个切面:**把 Agent 的每一个"决定"都变成可判定、有边界、可审计、能灰度的东西。** 前 42 讲你学会"让一个系统能用",模块七你学会"让理解一个系统的方式能复用"。
