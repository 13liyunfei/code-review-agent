## 一、痛点

周四下午三点，某个大模型厂商的华东区网关抖动。

你的审查服务本身**没有任何改动**，但十分钟内它整个不可用了。运维在群里问：

> "你们服务是不是有死循环？线程数打满了，CPU 反而不高。"

查日志，满屏都是同一个异常：

```
java.net.SocketTimeoutException: Read timed out
```

以及更奇怪的：**同一条 PR 的纯规则审查（SQL 注入检查、硬编码密钥检查——这些根本不调大模型）也一起超时了。**

根因不复杂：每个失败的 LLM 调用都要**等满读超时**（默认 60 秒）才抛出异常，然后**再等下一个供应商**，再等 60 秒。Tomcat 的请求线程池被这些"正在等待"的请求全部占满。线程池是**所有请求共享的**，所以连不需要大模型的路径也拿不到线程。

一句话总结这个故障的形状：

> **上游的故障，通过"等待"传染给了与它无关的功能。**

这一讲解决三件事：**超时该挂在哪里、流式为什么不能随便开、熔断器怎么阻止这种传染。**

## 二、原理

### 2.1 超时不是一个数字，是一份预算

绝大多数项目里"超时"被当成一个配置项：`timeout: 60000`。但网络调用实际上有**三个不同的时间**，混在一起就必然配错：

| 名字 | 回答的问题 | 典型值 | 配错的后果 |
|---|---|---|---|
| 连接超时（connect） | "能不能和对方建立 TCP 连接" | 5s | 配太大：对方 IP 不可达时，每个请求先卡 60s |
| 读超时（read） | "连上了，但对方多久不回话算死" | 60–180s | 配太小：大模型正常生成长文本被误杀 |
| 请求总超时（request） | "从发出到放弃的总时长" | ≥ read | 缺了它：connect + read 叠加，实际等待翻倍 |

在 `token-factory` 里，HTTP 客户端把这两个时间**同时**设上：

```java
// token-factory-server/.../upstream/HttpJson.java
HttpClient client = HttpClient.newBuilder().connectTimeout(timeout).build();
HttpRequest.Builder builder = HttpRequest.newBuilder(URI.create(url))
        .timeout(timeout)                      // ← 请求总超时
        .header("Content-Type", "application/json")
        .header("Accept", "application/json");
```

而 timeout 的值不是硬编码，来自**每个供应商自己的配置**：

```java
// token-factory-server/.../upstream/UpstreamRegistry.java:74
Duration.ofMillis(Math.max(1_000L, provider.timeoutMs()))
```

**这一段是设计的核心**：超时不是全局常量，是**供应商维度的属性**。因为不同厂商的 P99 差异巨大——一个国内小厂的 60s 读超时是常态，而一个海外大厂的正常生成可能 120s 才结束。用一个全局值，必然出现"对小厂太宽松、对大厂太严格"。

调用方（SDK 侧）的默认值则区分得更明确：

```java
// token-factory-client/.../TokenFactoryClient.java:308-309
private Duration connectTimeout = Duration.ofSeconds(5);
private Duration requestTimeout = Duration.ofSeconds(180);
```

**5 秒 vs 180 秒，差 36 倍**——这不是拍脑袋：连不上是**配置/网络问题**，5 秒足够暴露；而大模型生成 3000 token 用掉 90 秒是正常的，卡到 180 秒是给最长的那一档留余量。

还有一个容易漏的点：**传输层故障没有 HTTP 状态码**。

```java
// HttpJson.java（catch 分支）
} catch (IOException e) {
    // 连不上 / 读超时：没有 HTTP 状态码，按可重试的传输层故障处理
    throw new UpstreamException(providerCode, "上游请求失败: " + e.getMessage());
}
```

把"没有状态码"归到 `isTransportError()`，后续的重试分类器才能正确判断它是**临时故障**（该退避重试）而不是永久故障。

### 2.2 流式：为什么这个网关选择"明确不支持"

SSE（Server-Sent Events）流式输出是聊天类产品的标配。但在这个网关上，它是**故意被拒绝**的：

```java
// ChatController.java:54-59
if (body.isStream()) {
    // 流式要边收边算 token，计量口径与网关的「响应后计价」不同；
    // 与其给出一个计量不准的实现，不如明确不支持，避免账单对不上。
    throw new ResponseStatusException(HttpStatus.NOT_IMPLEMENTED,
            "暂不支持 stream=true，请改用非流式调用（流式计量口径见 ROADMAP）");
}
```

**这里的取舍值得逐字读三遍。** 它给出了一条很重要的判断标准：

> 当你的实现质量达不到你承诺的语义时，**明确报错比"做了个大概"更好。**

为什么流式和计量冲突？因为网关的计价时机是"响应回来后，读 `usage` 算钱"：

```java
// GatewayService.java:58-66
ChatResponse response = engine.complete(request);
Money cost = pricing.price(response.providerCode(), response.upstreamModel(), response.usage());
metering.record(UsageRecord.success(... promptTokens, completionTokens, cost.micros(), ...));
```

非流式：一次响应里带完整 `usage`，计价是**精确**的。
流式：`usage` 只在**最后一个 chunk** 出现，而且 OpenAI 兼容协议要求请求侧显式打开 `stream_options.include_usage`——很多厂商的实现并不返回它。拿不到 `usage` 就只能**估算**，而估算意味着账单和上游账单不一致。

如果这里"聪明地"支持了流式并用估算计价，会发生什么？

- 财务对账时，网关记的数和上游的账单**永远差几个百分点**，且无法解释；
- 差额随模型、随文本长度漂移，无法归因；
- 最糟的是**没人报错**——报告看起来正常，只是总数不对。

**这就是"假功能"的典型形态。** 而 501 是一个**诚实**的响应：调用方立刻知道要改用非流式，而不是三个月后发现账对不上。

### 2.3 熔断器：把"已知坏掉"变成零成本

重试和熔断经常被混为一谈，它们解决的问题完全不同：

| | 重试（Retry + Backoff） | 熔断（Circuit Breaker） |
|---|---|---|
| 针对 | **单次抖动** | **持续不可用** |
| 时间尺度 | 秒级 | 分钟级 |
| 手段 | 等一会儿再来一次 | 直接不试了 |
| 失败时的代价 | 一次等待 | **零**（快速失败） |

熔断器的价值可以用一句话概括：**它让"已知坏掉"的供应商在冷却期内被零成本跳过。**

没有它时，每个请求都要实打实地等满超时；有它之后，第一个请求触发熔断，后续请求**立刻**被拒绝——**这正是上面那个"线程池被榨干"故障的解药**。

## 三、代码

### 3.1 `CircuitBreaker.java`：状态机本身没什么魔法，细节才是

熔断器本身的骨架是标准的，所以我只挑**三个容易写错的地方**。

**第一处：半开状态下的名额控制。**

```java
// CircuitBreaker.java:54-72
public synchronized void acquire() {
    long now = nowMillis.getAsLong();
    if (state == CircuitState.OPEN) {
        long elapsed = now - openedAtMillis;
        if (elapsed < config.openDurationMillis()) {
            throw new CircuitOpenException(providerCode, config.openDurationMillis() - elapsed);
        }
        // 冷却期结束：转半开，放行有限的探测请求
        state = CircuitState.HALF_OPEN;
        halfOpenInFlight = 0;
        halfOpenSuccesses = 0;
    }
    if (state == CircuitState.HALF_OPEN && halfOpenInFlight >= config.halfOpenMaxCalls()) {
        throw new CircuitOpenException(providerCode, 0L);
    }
    if (state == CircuitState.HALF_OPEN) {
        halfOpenInFlight++;
    }
}
```

半开的语义是"**放进去几个探路的**"。`halfOpenMaxCalls` 默认是 **1**（`TokenFactoryProperties.Breaker`），意味着**只有一个请求能去试探上游是否恢复**。如果这里不限制名额，冷却期一结束，积压的所有请求会**同时**涌向刚恢复的上游——把它再打挂一次。这就是"**惊群**"。

**第二处：半开状态下失败一次立刻重新打开，不累计。**

```java
// CircuitBreaker.java:89-99
public synchronized void recordFailure() {
    long now = nowMillis.getAsLong();
    lastFailureAtMillis = now;
    if (state == CircuitState.HALF_OPEN) {
        trip(now);                 // ← 立刻回 OPEN，不等 failureThreshold
        return;
    }
    if (++consecutiveFailures >= config.failureThreshold()) {
        trip(now);
    }
}
```

判据很清晰：**半开时的那个探测请求本身就是一个"我们不确定上游好没好"的赌注。它失败了，说明还没好——没有任何理由再试第二个。** 而 CLOSED 状态下累计到阈值才打开，因为单次失败可能只是抖动。

**第三处：把时间源做成可注入的。**

```java
// CircuitBreaker.java:31-43
public CircuitBreaker(String providerCode) {
    this(providerCode, CircuitBreakerConfig.DEFAULTS, System::currentTimeMillis);
}

public CircuitBreaker(String providerCode, CircuitBreakerConfig config, LongSupplier nowMillis) { ... }
```

类注释里写了理由：

> 时间源可注入（`nowNanos`），便于在测试里用假时钟推进，不用真的 sleep。

**这是一个值得直接抄走的工程习惯**：任何"和时间有关的逻辑"（熔断冷却、退避、租约、窗口限流），都把时钟抽成 `LongSupplier`。否则你想测"冷却 30 秒后是否半开"，测试就得真的 `Thread.sleep(30_000)`——而这种测试在 CI 里会被所有人想删掉。

### 3.2 `RoutingEngine.java`：把"选路 → 熔断 → 重试 → 切换"串成一条链

这是整个模块一最值得读的一个类。它的类注释直接给出了执行链：

```java
// RoutingEngine.java:26-36
/**
 *   请求(别名)
 *     └─ 路由表查候选落点 → RouteStrategy 排序（熔断中的排后）
 *          └─ 逐个落点尝试
 *               ├─ 熔断器 acquire()：OPEN 直接跳过（零超时成本）
 *               ├─ 成功 → 记 success，返回
 *               └─ 失败 → 记 failure（达阈值即熔断）
 *                          ├─ 可重试 → 退避后在同一供应商再试（最多 maxAttempts）
 *                          └─ 不可重试 / 次数用尽 → 切下一个落点
 *     └─ 全部失败 → AllUpstreamsFailedException（携带每一跳原因）
 */
```

**两个循环，分工明确**：外层遍历候选供应商（failover），内层在同一家上退避重试。这是"重试"和"切换"唯一正确的嵌套顺序——**反过来（先切一圈再重试）会把故障放大 N 倍**。

**第一处细节：区分"被熔断挡下"和"真的调用后失败"。**

```java
// RoutingEngine.java:116-119
// 是否所有落点都是「被熔断挡下」而非「真的调用后失败」——两者对调用方的含义完全不同：
// 前者是快速失败（重试无意义，等冷却即可），后者是上游确实出了问题。
boolean allCircuitOpen = true;
long maxRemainingMillis = 0L;
```

然后在收尾处：

```java
// RoutingEngine.java:172-179
if (allCircuitOpen && !failures.isEmpty()) {
    String codes = ordered.stream().map(RouteTarget::providerCode).distinct()
            .reduce((a, b) -> a + "," + b).orElse("-");
    throw new CircuitOpenException(codes, maxRemainingMillis);
}
throw new AllUpstreamsFailedException(
        "模型别名 '" + request.model() + "' 的所有供应商均调用失败", failures);
```

**为什么这个区分重要？** 因为调用方的处置动作完全不同：

- `CircuitOpenException` → **别重试**，等冷却期（`remainingMillis` 明确告诉你要等多久）；
- `AllUpstreamsFailedException` → **上游真有问题**，该告警、该值班介入。

如果统一抛一个"调用失败"，调用方只能盲目重试——**而盲目重试恰好是压垮刚恢复的上游的最后一根稻草。**

**第二处细节：`HARD_ATTEMPT_CAP`。**

```java
// RoutingEngine.java:49-50
/** 单落点尝试次数的硬上限：防止自定义 RetryClassifier 永远返回「可重试」导致死循环。 */
private static final int HARD_ATTEMPT_CAP = 10;
```

```java
// RoutingEngine.java:157-159
if (!decision.retryable() || attempt >= HARD_ATTEMPT_CAP) {
    break;
}
```

这是一个**防御性设计**：`RetryClassifier` 是 SPI 可插拔的，别人可以实现一个"永远可重试"的分类器。硬上限保证**引擎自身的循环一定会终止**——不管外面接了什么。

> 这个习惯的通用名字叫 **"不信任扩展点"**：只要你的循环终止条件取决于外部实现，就必须有一条**你自己控制的**终止线。

**第三处细节：`RuntimeException` 兜底也算失败。**

```java
// RoutingEngine.java:161-168
} catch (RuntimeException e) {
    // 适配层的非预期异常（序列化失败、NPE 等）同样计为失败并熔断，
    // 否则坏掉的供应商会一直被选中
    allCircuitOpen = false;
    breaker.recordFailure();
    failures.add(target.providerCode() + ": 非预期异常 "
            + e.getClass().getSimpleName() + " - " + e.getMessage());
    break;
}
```

**这条注释点出了一个隐蔽的后果**：如果适配层因为"报文格式和预期不一样"抛了 NPE，而你不把它算作失败——那么熔断器就不会打开，**这个坏掉的适配器会被每一个请求反复选中**，反复抛 NPE。故障不会自愈，只会一直重复。

### 3.3 `DefaultRetryClassifier.java`：按 HTTP 语义分类，而不是按"是不是异常"分类

```java
// token-factory / core/resilience/DefaultRetryClassifier.java:64-82
int status = ex.statusCode();
return switch (status) {
    case 408, 409 -> RetryDecision.retry(backoff.nextDelayMillis(attempt),
            status + " 临时故障，退避后重试");
    case 429 -> RetryDecision.retry(
            ex.retryAfterMillis() > 0 ? ex.retryAfterMillis() : defaultRateLimitBackoffMillis,
            "429 限流，等待 " + (...));
    case 400, 401, 403, 404, 422 -> RetryDecision.noRetry(
            status + " 属永久故障，重试无意义，直接切换供应商");
    default -> {
        if (status >= 500) {
            yield RetryDecision.retry(backoff.nextDelayMillis(attempt),
                    status + " 上游服务端故障，退避后重试");
        }
        yield RetryDecision.noRetry("未识别状态码 " + status + "，按不可重试处理");
    }
};
```

三个判断值得点出来：

1. **`401 / 403` 被归为"永久故障"**，类注释给了理由：*"鉴权失败，重试只会继续失败，而且会加速触发上游风控。"* **重试一个鉴权失败的请求，等于把一个错误的令牌连续甩给对方 N 次**——这在风控系统眼里就是攻击特征。
2. **`429` 尊重上游给的 `Retry-After`**，没给才用默认值。注释写得很直白：*"指数退避解决不了『告诉你 30 秒后再来』的明确指令。"* 上游明确告诉你什么时候来，你却按自己的算法 500ms 后又敲一次——这是标准的"不礼貌客户端"。
3. **未识别的状态码按"不可重试"处理**。这是 **fail-closed** 的取向：不确定能不能重试时，选择不重试。因为"错重试"的代价（放大故障、浪费配额）比"少重试"（一次 failover）更高。

### 3.4 `BackoffPolicy.java`：抖动不是可选项

```java
// token-factory / core/resilience/BackoffPolicy.java:5-13
/**
 * <p><b>为什么必须加抖动</b>：纯指数退避会让所有客户端在同一时刻重试，形成「重试风暴」，
 * 把刚恢复的上游再打挂一次。抖动把重试时间打散到一个区间内，是分布式系统的基本功。
 *
 * <p>公式：{@code delay = min(maxMillis, baseMillis * multiplier^(attempt-1))}，
 * 再乘以 {@code [1-jitter, 1+jitter]} 区间内的随机系数。
 */
```

默认参数：**500ms 起步、2 倍递增、上限 8s、±30% 抖动**（`BackoffPolicy.exponential()`）。

假设有 1000 个并发请求同时失败：

| | 第 1 次重试 | 第 2 次重试 | 第 3 次重试 |
|---|---|---|---|
| 无抖动 | 全部在第 500ms 涌入 | 全部在第 1500ms 涌入 | 全部在第 3500ms 涌入 |
| ±30% 抖动 | 分散在 350–650ms | 分散在 1050–1950ms | 分散在 2450–4550ms |

**无抖动时，重试本身就是一个"精准的定时攻击"**：上游刚恢复，500ms 后收到全量请求，再次过载，再次全挂，再次同时重试。这个循环可以无限持续。

还有一个实现细节：`rawDelayMillis()` 与 `nextDelayMillis()` 是分开的两个方法——

```java
// token-factory / core/resilience/BackoffPolicy.java:58-65（javadoc + 方法体）
/** 不含抖动的确定性退避值，便于断言。 */
public long rawDelayMillis(int attempt) { ... }
```

**把"随机"和"可断言"分开**，测试里断言 `rawDelayMillis(3) == 2000`，业务里用 `nextDelayMillis(3)`。这是"可测试性"落实到方法粒度的一个例子。

### 3.5 `ModelGateway.java`：调用方自己的那套（在同一进程里）

`code-review-agent` 这边还有一层自己的网关（原因见第 07 讲）。它的配额窗口翻转处有一个**值得单拎出来的并发坑**：

```java
// ModelGateway.java:266-274
private void incQuota(String name) {
    QuotaState qs = quotas.computeIfAbsent(name, k -> new QuotaState());
    // 必须在同一把锁内做「窗口翻转 + 自增」：若只自增不翻转，会与 quotaExceeded 的
    // 窗口重置竞争——旧窗口的计数在翻转瞬间被清零，导致该窗口实际调用数被低估而超发。
    synchronized (qs) {
        refreshWindow(qs);
        qs.count.incrementAndGet();
    }
}
```

**注释把 bug 说尽了**：如果"读计数"和"翻窗口"不在同一把锁里，"翻转"会把这个窗口已经花掉的额度清零——结果是**本窗口实际调用数被低估，配额超发**。

而这个 bug 的表现形态特别讨厌：**它只在窗口边界（第 60 秒）附近的高并发下出现**，平时完全正常，压测也很难复现。它不会让你"看到错"，只会让你"少扣一点"。

## 四、避坑清单

- [ ] **区分 connect / read / request 三个超时**，并且**按供应商分别配置**。用一个全局值必然错。
- [ ] **给所有网络调用加"传输层异常"这一分支**（`IOException` / `SocketTimeoutException`）——它们没有 HTTP 状态码，必须单独归类为可重试。
- [ ] **重试在外层还是内层？答案是：同一家内层重试，全部失败后外层切换。** 顺序反过来会把故障放大 N 倍。
- [ ] **加指数退避时一定加抖动。** 没有抖动的重试是"定时攻击"。
- [ ] **尊重上游的 `Retry-After`**，它比你的退避算法更权威。
- [ ] **401/403 绝不重试。** 重试鉴权失败 = 加速触发风控。
- [ ] **未识别的状态码按不可重试处理（fail-closed）**。
- [ ] **半开状态只放行 1 个探测请求**，否则冷却期一结束就是惊群。
- [ ] **半开时探测失败立刻重新打开**，不要继续消耗探测名额。
- [ ] **任何"和时间有关"的逻辑都把时钟抽成可注入的 `LongSupplier`**，否则测试只能 `sleep`。
- [ ] **只要循环的终止条件依赖外部 SPI，就必须有一条自己控制的硬上限。**
- [ ] **适配层的非预期异常也要计入熔断**，否则坏掉的适配器会被反复选中。
- [ ] **实现质量达不到语义承诺时，宁可明确报错（501），不要做"大概对"的实现。** 假功能比没有功能更贵。

## 五、动手任务

> **任务一：亲手制造一场"上游雪崩"，并观察熔断器如何止住它。**
>
> **仓库位置**：`token-factory / token-factory-core`
>
> **操作**：
> 1. 写一个测试，构造一个**永远抛 `UpstreamException`（5xx）** 的假上游，注册进 `RoutingEngine`。
> 2. 注入一个**假时钟**（`LongSupplier`），不要用真实时间。
> 3. 连续发起 6 次调用（默认 `failureThreshold = 5`），记录每次的耗时与异常类型。
> 4. 然后**把假时钟往前推 30 秒**（`openDurationMillis = 30_000`），再调一次。
>
> **预期结果**：
> - 第 1–5 次：每次都是 `AllUpstreamsFailedException`，且**每次都要走完退避**（用假 Sleeper 计数就能看到睡眠次数）。
> - 第 6 次：异常类型**变成 `CircuitOpenException`**，且**没有任何退避睡眠**——这就是"零超时成本"。
> - 推进 30 秒后的一次：进入 `HALF_OPEN`，只放行 1 个请求。
> - 让这次探测也失败 → 立刻回到 `OPEN`，并且 `remainingOpenMillis()` 重新变成 30 秒——**验证"半开失败立刻重开"**。
>
> **任务二：验证抖动真的把重试打散了。**
> 1. 调 `BackoffPolicy.exponential().nextDelayMillis(1)` 1000 次，统计最小值和最大值。
> 2. 对比 `rawDelayMillis(1)`。
>
> **预期结果**：`rawDelayMillis(1)` 恒为 500；`nextDelayMillis(1)` 落在 **350–650** 之间。若你把 `jitterRatio` 改成 0，两者会完全一致——**这就是"没有抖动就是定时攻击"的可视化。**

## 本讲小结

1. **超时是按供应商配置的预算**，不是全局常量；connect 与 read 必须分开，传输层异常要单独归类。
2. **流式在这个网关上被明确 501**——因为计量口径对不上。**"明确报错"优于"做了个大概"**，假功能比没有功能更贵。
3. **重试解决抖动，熔断解决持续不可用。** 熔断器的核心价值是让"已知坏掉"变成**零成本跳过**，这正是止血"线程池被上游拖死"的关键。
4. 三个必须做对的细节：**半开只放 1 个探测**（防惊群）、**半开失败立刻重开**、**时钟可注入**（否则逻辑无法测试）。
5. **只要循环终止条件依赖外部 SPI，就必须有自己控制的硬上限**（`HARD_ATTEMPT_CAP`）。
