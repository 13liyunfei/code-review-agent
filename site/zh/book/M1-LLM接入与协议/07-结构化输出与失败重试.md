> **图 07-0**　本讲地图：结构化输出的失败分四种，处置完全不同。其中「**空输出必须当失败**」是本讲最便宜、收益最高的一处修复。

## 一、痛点

上线两周后，你收到一条反馈：

> "最近几周的审查报告怎么感觉……变水了？全是 MAJOR 级别，建议都很空。"

你打开报告抽样，看到这样的发现：

| severity | confidence | title | description |
|---|---|---|---|
| `MAJOR` | `0.75` | LLM 发现 | *（空）* |
| `MAJOR` | `0.75` | LLM 发现 | *（空）* |
| `MAJOR` | `0.75` | LLM 发现 | *（空）* |

**所有字段都是默认值。**

这不是模型变笨了——是模型的输出**没能被解析**，而解析器**没有报错**。它按"宽松解析"的原则给每个缺失字段填了默认值：

```java
Severity severity = parseSeverity(text(node, "severity", "MAJOR"));   // ← 缺了 → MAJOR
double confidence = node.path("confidence").asDouble(0.75);           // ← 缺了 → 0.75
String title = text(node, "title", "LLM 发现");                        // ← 缺了 → 这个
String description = text(node, "description", "");                   // ← 缺了 → 空串
```

于是一份"解析完全失败"的输出，被包装成了一组**格式合法、看起来正常、但内容全是占位符的发现**。

这就是这一讲要处理的故障形状：

> **解析失败没有变成错误，而是变成了"内容平庸"。** 而"内容平庸"是无法告警的——你没法给"title 等于『LLM 发现』"配一条 PagerDuty 规则。

## 二、原理

### 2.1 结构化输出的失败有四种，处置方式完全不同

把"让模型返回 JSON"当成一件单一的事，是这一讲所有坑的源头。它其实是四种不同的失败，混在一起处理必然出错：

| 类型 | 现象 | 谁的问题 | 正确处置 |
|---|---|---|---|
| ① 调用失败 | 超时 / 429 / 网关全挂 | **基础设施** | 走第 04 讲的重试与 failover；**不要**在这里重试 |
| ② 非 JSON 输出 | 一堆自然语言，或 Markdown 包裹的 JSON | 提示词 / 模型能力 | 宽容解析 → 剥围栏；真没有就**降级** |
| ③ JSON 合法但内容不符 | `severity: "严重"` 而不是 `BLOCKER` | schema 约束不够 | 枚举进 schema，减少瞎编 |
| ④ 空输出 | 返回 `""` | 上游异常 | **必须当失败**（见 3.5） |

**第 ① 类最容易被错处理。** 看 `StructuredChatModel` 里这个 catch：

```java
// StructuredChatModel.java（核心循环）
String resp;
try {
    resp = delegate.chat(currentPrompt);
} catch (RuntimeException e) {
    // 模型调用失败不是格式问题——直接向上抛，交由调用方的降级链处理
    throw e;
}
```

**注释里的判断是这个类最重要的设计决策之一**：超时和 429 **不是"格式问题"**，在这里重试等于在错误的层做重试——重试同一个已经全挂的网关，只会浪费更多时间。它应该原样抛出去，由第 04 讲那套熔断/failover 处理。

**只有 ②③④ 才该在这里重试。**

### 2.2 重试必须带反馈，否则是浪费时间

一个很自然但错误的实现是"失败就重发同一个提示词"：

```java
// ❌ 原样重发
for (int i = 0; i < maxRetries; i++) {
    String resp = model.chat(prompt);   // 同一个 prompt
    if (canParse(resp)) return parse(resp);
}
```

**为什么这几乎无效？** 因为大模型是采样器。同样的输入、同样的温度，**大概率得到同样的输出**。你会花掉 3 倍的钱，得到同一个错误答案。

正确的做法是把**上一次的错误输出与失败原因回灌**：

```java
// StructuredChatModel.java（核心循环末尾）
// 重试前把上一次的错误输出与原因回灌给模型，否则原样重发大概率得到同样结果
currentPrompt = base
        + "\n\n你上一次的输出无法解析，失败原因：" + lastError
        + "\n上一次的输出是：\n" + truncate(resp, 800)
        + "\n请严格只输出符合上述 JSON Schema 的 JSON 对象，不要任何额外文字。";
```

**这段 prompt 里有三样东西，缺一不可：**

1. **失败原因**（`lastError`）——告诉模型"错在哪"；
2. **上一次的输出**（截断到 800 字符）——让模型看到自己写了什么，而不是抽象地"你错了"；
3. **重复约束**——把"不要 Markdown 围栏、不要解释"再强调一遍。

**这不是玄学，是给模型提供了新的上下文。** 没有新信息，采样结果不会变；有了"你上次错成这样"这个新信息，它才可能收敛。

类注释把这条经验直接写在了设计说明里：

> **重试带反馈**——把上一次的错误输出与失败原因回灌给模型，而不是原样重发同一个提示词（原样重发大概率得到同样的错误结果）。

### 2.3 schema 不该手写，应该由类型推导

早期版本的 API 要求调用方手工拼 schema：

```java
// StructuredChatModel.java（已废弃的旧 API）
@Deprecated
public <T> T chatStructured(String prompt, Map<String, Object> schema, Class<T> type, int maxRetries)
```

`@Deprecated` 的理由写在注释里：

> 推荐改用 `chat(String, Class, int)` 让 schema 由类型推导，**避免手写 schema 与 DTO 脱节**。

`JsonSchemas` 用 Jackson 的 `introspect` 遍历属性，从 Java 类型生成 schema：

```java
// JsonSchemas.java
/**
 * <p><b>为什么需要它：</b>早期 API 要求调用方手工拼 {@code Map<String,Object>} schema。
 * 一旦目标类型出现<b>嵌套</b>（如审查结果里含 {@code List<Finding>}），
 * 手写 schema 既冗长又极易与类型脱节——改了 DTO 忘了改 schema，
 * 而这类不一致往往要到线上才暴露。
 */
```

**"改了 DTO 忘了改 schema"——这是一类非常典型的、只在运行时暴露的故障。** 而且它的表现是"模型输出的字段名和你的对象对不上"，又回到了第 03 讲的"静默 null"。

推导规则（同文件注释）：

```
嵌套 record / POJO 自动展开为 object
List<T>、数组展开为 array + items
枚举展开为 enum 取值列表（显著减少模型瞎编取值）
基础类型映射为 string / integer / number / boolean
```

**其中"枚举展开为 enum 取值列表"是第 ③ 类失败（瞎编取值）的直接对策。** 你的 `Severity` 是 `BLOCKER / MAJOR / MINOR / INFO` 四个值——如果不告诉模型可选值，它可能输出 `"严重"`、`"HIGH"`、`"critical"`。schema 里带上 `enum`，这些都会被大幅压制。

还有两处工程细节值得单独看：

```java
/** 递归深度上限：防御类型自我引用导致的无限展开。 */
private static final int MAX_DEPTH = 6;

if (depth >= MAX_DEPTH) {
    // 到达深度上限：退化为 object，避免自我引用类型无限展开
    out.put("type", "object");
    return;
}
```

**类型可以自我引用**（`A` 里含 `List<A>` 是完全合法的）。不做深度上限，schema 生成会**栈溢出**——而且是在"启动后第一次调用模型"时才炸，测试里根本发现不了。

```java
/**
 * <p><b>惯例：</b>属性是否必填由 {@code required} 列表承载——
 * 目前把所有属性都列为必填，以最大化模型输出字段的完整性；
 * 调用方拿到对象后再做业务层的空值兜底（这也是更稳妥的做法：
 * 信任边界上的容错放在自己代码里，而不是指望模型）。
 */
```

**这条"惯例"值得记住**：它选择**在边界处严格、在自己代码里容错**。也就是——对模型说"所有字段都必须给"，但自己拿到对象后仍然到处判空。

为什么这是对的？因为**信任边界上的宽松是双输**：你对模型宽松，模型就更随意；你对自己严格，代码就更脆弱。反过来（对模型严格、对自己宽容）两个方向都变好。

### 2.4 结构化输出是"增强"，不是"必需"

这是 `StructuredChatModel` 类注释最后一段，也是整个模块一反复出现的同一条原则：

```java
/**
 * <p><b>设计原则：</b>结构化输出是增强而非必需。因此默认 API 不抛异常——
 * 增强失败时，调用方仍应能走没有它时本该走的通路。
 */
```

落实到 API 上是**三种用法、三种容错诉求**：

```java
// StructuredChatModel.java（类注释）
* <h3>三种用法，覆盖不同容错诉求</h3>
* <ol>
*   <li>{@link #chat(String, Class, int)} —— <b>推荐</b>。失败不抛异常，
*       返回 {@link StructuredResult}，调用方可拿 {@code rawResponse} 回退文本解析。</li>
*   <li>{@link #require(String, Class, int)} —— 结构化输出是<b>硬需求</b>时用，
*       重试耗尽抛 {@link IllegalStateException}。</li>
*   <li>{@link #chatWithSession(ChatSession, String, Class, int)} —— 需要<b>多轮记忆</b>时，
*       结构化输出与 {@link ChatSession} 结合，本次对话自动写入会话。</li>
* </ol>
```

**默认推荐的那个是"不抛异常"的。** 这个默认值的选取本身就是设计立场：**生产系统里"模型这次没返回合法 JSON"是常态，不是异常。**

`require` 的注释也很克制：

> 仅在结构化输出是**硬需求**时使用（如必须得到分类结果才能继续的流程）；一般场景请用 `chat`。

## 三、代码

### 3.1 `StructuredResult.java`：不抛异常的理由，写在类头

<img class="mermaid-svg" src="/zh/book-assets/diag-0030.svg" alt="### 3.1 `StructuredResult.java`：不抛异常的理由，写在类头" />

> **图 07-1**　`StructuredResult<T>` 的五个字段：`ok` / `value` / `rawResponse` / `attempts` / `error`。**`attempts` 不是重试计数器**，它指向根因——重试率过高说明提示词或 schema 正在**系统性地**让模型困惑，而这个趋势比"这一次结果对不对"更值得盯，因为它只会持续恶化。

**第 2 条是最有价值的一条，也是最容易被忽略的一条。**

`attempts` 记录"实际调用了几次模型"（1 表示首次即成功）。它的用途不是"重试了就好"，而是：

> **重试率过高说明提示词或 schema 有问题。**

这是一个**指向根因的质量指标**。如果线上 20% 的请求需要重试——你多花了 20% 的钱和延迟，但更重要的是：**这说明你的提示词在系统性地让模型困惑**。这个信号比"最终结果正确"更有价值，因为它会持续恶化。

三个便捷方法也各有用途：

```java
/** 成功返回值，失败返回兜底值。 */
public T orElse(T fallback) { return ok ? value : fallback; }

/** 失败时改用原始文本自行解析（回退通路的入口）。 */
public <R> R onFailureParseRaw(Function<String, R> rawParser, R fallback) { ... }

/** 是否重试过（首次即成功为 false）。 */
public boolean retried() { return attempts > 1; }
```

**`onFailureParseRaw` 就是"降级通路"的正式入口**：结构化解析失败了，但模型给的原始文本里可能还有能用的信息——回到第 03 讲那种宽松的文本解析去捞一遍，总比丢掉整轮结果强。

### 3.2 宽容解析：剥两次壳

```java
// StructuredChatModel.java
/** 宽容解析：剥离 Markdown 围栏与前后闲聊，再定位 JSON 对象。 */
private <T> T parseLenient(String text, Class<T> type) throws Exception {
    if (text == null || text.isBlank()) {
        return null;
    }
    String t = text.trim();
    // 剥离 ```json / ``` 围栏
    if (t.contains("```")) {
        int start = t.indexOf("```");
        int afterFence = t.indexOf('\n', start);
        int end = t.lastIndexOf("```");
        if (afterFence > 0 && end > afterFence) {
            t = t.substring(afterFence + 1, end).trim();
        }
    }
    int s = t.indexOf('{');
    int e = t.lastIndexOf('}');
    if (s < 0 || e <= s) {
        return null;
    }
    JsonNode node = mapper.readTree(t.substring(s, e + 1));
    return mapper.treeToValue(node, type);
}
```

**两道剥离对应模型两种最常见的"包装行为"：**

1. **Markdown 代码块围栏**——模型被告知"不要用 ```` ``` ```` 包裹"，但它还是会（训练数据里 JSON 几乎总是被围栏包着）。剥掉。
2. **前后闲聊**——"好的，我来分析一下这段代码。{...} 希望这个分析对你有帮助。" 取**首个 `{` 到末个 `}`**，中间那段就是 JSON。

**`indexOf` + `lastIndexOf` 这个组合有个隐含前提**：模型只输出**一个**顶层 JSON 对象。如果它输出了两个对象（`{...}\n{...}`），首尾取出来的字符串会是 `{...}\n{...}`，`readTree` 直接失败。

这是**有意的取舍**——它用"简单 + 覆盖 95% 情况"换了"完备 + 复杂"。而兜底还在：解析失败 → 带反馈重试 → 还不成 → `StructuredResult.failure` → 调用方降级。

**「宽容解析 + 明确重试 + 显式降级」这三段式，是处理 LLM 输出不确定性的标准结构。**

### 3.3 主线系统的另一条路：LangChain4j 的声明式结构化输出

`code-review-agent` 里还有一条**完全不同**的实现路线，值得对照着看：

<img class="mermaid-svg" src="/zh/book-assets/diag-0031.svg" alt="`code-review-agent` 里还有一条完全不同的实现路线，值得对照着看：" />

> **图 07-2**　LangChain4j 声明式结构化输出的返回类型约束：`CodeReviewAiService` 返回 `ReviewResultDto`，而 `ReviewResultDto` 里再包一层 `List<ReviewFindingDto>`。**为什么不能直接返回 `List`**——`AiServices` 的返回类型必须是单个对象，这是框架约束而不是设计偏好；不知道这条约束，会在这上面试掉一小时。

注意 `ReviewResultDto` 外面包了一层——注释给了理由：

> AiServices 的返回类型必须是单个对象，故用 record 包裹 `List`。

**这是一个很小的框架约束，但如果你不知道，就会花一小时去试"为什么不能直接返 `List<ReviewFindingDto>`"。**

**两条路线并存，本身就是设计上的正确答案**：

| | LangChain4j AiService | 自研 `StructuredChatModel` |
|---|---|---|
| 声明方式 | 接口 + 注解 | 一行方法调用 |
| schema | 框架从返回类型推导 | `JsonSchemas` 从类型推导 |
| 重试 | 框架行为，可控性弱 | 自己做，**带反馈** |
| 依赖 | 引入 LangChain4j | **零依赖** |
| 适用 | 主线系统的业务调用 | 基座库（不能绑死框架） |

**根因是"依赖方向"**：`agent-kit` 是要发布到 Maven Central 的基座库，它**不能绑定 LangChain4j**——否则所有使用者都被迫接受这个依赖。而 `code-review-agent` 是应用，它可以自由选择。

**这是模块五"平台方视角"的预演**：当你造一个给别人用的库时，"能不能用某个框架"从来不是技术偏好问题，而是**依赖契约问题**。

### 3.4 `LlmFindingParser.java`：宽松解析的正确姿势（逐条隔离）

回到开头那个痛点。这个类的解析循环有一处关键设计：

```java
// LlmFindingParser.java:51-57
for (JsonNode node : arr) {
    try {
        findings.add(toFinding(node, agentType, category));
    } catch (Exception ex) {
        log.debug("[LLM] 跳过无法解析的条目：{}", ex.getMessage());
    }
}
```

**注意 `catch` 在 `for` 循环体内部。** 这意味着：**一条坏数据只丢一条，不影响其余条目。**

对比一下错误写法（`try` 包住整个循环）：**数组里第 7 条有个格式问题，整批 20 条全部丢弃**。而且因为异常被吞掉，你甚至不知道丢了 20 条还是 0 条。

**"逐条隔离"是解析不可信输入的通用原则**，和 `NativeToolCallingLoop.executeInParallel` 里"逐个 `f.get()`"是同一个动作。

它还有一层防御：

```java
// LlmFindingParser.java:42-45
String json = extractJsonArray(llmResponse);
if (json == null) {
    return findings;              // ← 空列表
}
```

```java
// LlmFindingParser.java:99-109
/**
 * 从可能含代码块/说明的文本中抽取首个 JSON 数组子串。
 */
private static String extractJsonArray(String text) {
    int start = text.indexOf('[');
    int end = text.lastIndexOf(']');
    if (start < 0 || end <= start) {
        return null;
    }
    return text.substring(start, end + 1);
}
```

**注意是 `[` 和 `]`**——因为这个路径解析的是 **JSON 数组**（`[{...},{...}]`），而 3.2 节的 `StructuredChatModel` 解析的是**单个对象**（`{...}`）。**两处的首尾字符不同，不是笔误。**

而类注释点明了它和结构化路线的分工：

> 解析失败不影响主流程——返回空列表，Agent 仍保留规则型发现。

**"Agent 仍保留规则型发现"是这个系统的一条底层设计**：审查有**规则型**（正则匹配 SQL 注入、硬编码密钥）和**语义型**（LLM）两条腿。LLM 那条腿瘸了，规则那条还在——**所以这个系统永远不会因为模型抽风而变成"什么都没审"。**

### 3.5 空输出必须当失败（一行注释，一个 P0）

这是这一讲我最想让你记住的一处代码：

```java
// LangChain4jChatProvider.java
ChatResponse response = chatModel.chat(ChatRequest.builder()
        .messages(UserMessage.from(prompt))
        .build());
String text = response == null || response.aiMessage() == null
        ? null
        : response.aiMessage().text();
if (text == null || text.isBlank()) {
    // 空结果必须当失败——否则上层会拿一个空串去解析，产出「看起来通过」的报告
    throw new IllegalStateException(name + " 返回空内容");
}
```

**"否则上层会拿一个空串去解析，产出『看起来通过』的报告"——这一句解释了一整类 P0。**

顺着这个逻辑推一遍：

1. 上游因为某种原因返回了 `""`（内容过滤、模型内部错误、协议不一致，都可能）；
2. 如果不判空，这个空串会正常返回给 `ModelGateway`，被当成**一次成功调用**（还会记一次用量、算一次钱）；
3. `LlmFindingParser.parse("")` 走到 `llmResponse.isBlank()` → 返回**空列表**；
4. 空列表 = **这个维度没有问题**；
5. 报告显示："逻辑审查通过 ✅"

**而事实是：逻辑审查根本没跑。**

这就是"**静默通过**"——比"静默失败"危险得多，因为**失败至少会让审查变慢或报错，而"通过"会让人放心地合并代码。**

报错之后，`ModelGateway` 会把它计为一次失败、走到下一个供应商（`available` 那个逻辑），或者最终抛 `ModelUnavailableException` → 协调器把该 Agent 标记为**降级** → **报告里明确标注"逻辑维度未完成审查"**。

**从"看起来通过"到"明确标注未完成"，就是这一行判空的价值。**

### 2.6 校验失败之后：重试、降级、还是拒绝

解析失败之后有三条路，它们的**代价结构完全不同**——不是"哪个更好"，而是"你愿意付哪种代价"：

<img class="mermaid-svg" src="/zh/book-assets/diag-0033.svg" alt="解析失败之后有三条路，它们的代价结构完全不同——不是&quot;哪个更好&quot;，而是&quot;你愿意付哪种代价&quot;：" />

> **图 07-4**　三条处置路径与它们各自的前置条件：**重试的前提是"错误信息回灌"**（否则模型只会用同样的方式再错一次）；**降级的前提是"原始文本被保留"**（本讲 §3.1 的 `rawResponse` 字段就是为它准备的）；**拒绝的前提是"失败可观测"**（否则你只是把问题藏起来了）。三条路的取舍判据是：**这一条失败，值不值得为它多花一次调用。**

**最贵的一种组合，是"看起来像降级、实际是静默失败"**：解析失败 → 返回空列表 → 上层把它当成"没有问题"。**空列表是合法结果，空输出不是。** 这条界线必须由代码来划，不能靠约定：

```java
        if (llmResponse == null || llmResponse.isBlank()) {
```

`LlmFindingParser.java:39`

**这一行是本讲最便宜的一处修复**——它把"模型什么都没说"和"模型说了没有问题"分成了两件事。在前者的情况下抛失败、走降级；在后者的情况下返回空列表。**两者在日志里长得一模一样，在行为上差一个事故。**

### 2.7 一手数据与搬到你自己系统：解析器的验收样本集

把上面三段折成可验收的东西。**解析器的正确性不能靠"跑几个真实的 PR 看看"，要靠一份固定的样本集**——因为真实的输出会变，样本集不会。

> **一手数据（可复算）**：本书的宽容解析器 `LlmFindingParser.java` **共 111 行**，其中空输出判据落在第 **39** 行；结构化结果的包装类型 `StructuredResult` 有 **5 个字段**（`ok` / `value` / `rawResponse` / `attempts` / `error`，见本讲 §3.1 的类头；`rawResponse` 是降级通路唯一的入口）。
> 复算方式：`wc -l src/main/java/com/codereview/agent/core/llm/LlmFindingParser.java` 与 `grep -n "isBlank()" src/main/java/com/codereview/agent/core/llm/LlmFindingParser.java`。

| 样本类别 | 构造方式 | 期望行为 |
|---|---|---|
| **正常** | 完整 JSON | 解析成功，字段齐全 |
| **空输出** | 空串 / 纯空白 | **当失败**（不可降级为空列表） |
| **缺字段** | 少一个可选字段 | 用默认值补齐，不算失败 |
| **类型错** | 数字写成字符串 | 宽容解析或当失败，**不能崩** |
| **包裹噪声** | JSON 外有一层解释文字 | 剥壳成功 |
| **截断** | 半个 JSON | 当失败，并保留 `rawResponse` |
| **多对象** | 一次返回多个 finding | 逐条隔离：一条坏不影响其他 |

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| OpenAI schema 强制全字段 required（`StructuredOutputs.kt:216`） | 你的"可选字段"打算怎么表达？ |
| `BeanOutputConverter` 从 Bean 推 schema | 你的 schema 是手写的还是从类型推的？ |
| 三条处置路径各有前置条件 | 你现在的失败处置，走的是哪条？前提具备吗？ |
| 空输出当失败（`LlmFindingParser.java:39`） | 你的代码能区分"没说"和"说了没有"吗？ |
| 逐条隔离 | 一条解析失败会让整批结果都没了吗？ |

**搬到你自己系统**，五步：

1. **建一份样本集文件**（JSON 或 YAML），把上表七类各写 1–3 条。
2. **给每一类写一条断言**，特别是"空输出必须失败"这一条——**它是七条里唯一一条"不做就会静默出事"的**。
3. **把 `rawResponse` 存下来**（哪怕只存到日志），因为降级路径没有它就走不通。
4. **给解析加一个 `attempts` 计数并上报**。重试率上升是提示词漂移的**最早信号**，比最终结果对不对更早。
5. **把样本集挂进 CI**：样本集全过才允许合并提示词或 schema 的改动。

**判据**：**能区分"没说"与"说了没有"的解析器，才算合格。** 分不清这两件事的系统，最终一定会用"误报"或"漏报"的形式把它还给你。

## 四、避坑清单

- [ ] **把"调用失败"和"格式失败"分开。** 超时/429/全挂不要在这里重试，原样抛给熔断/failover 层。
- [ ] **重试必须带反馈**：失败原因 + 上一次的输出 + 重复约束。原样重发同一个提示词 ≈ 白花钱。
- [ ] **空输出必须当失败。** 一行 `isBlank()` 判空，避免"看起来通过"的报告。
- [ ] **schema 由类型推导，不要手写。** 手写 schema 与 DTO 脱节是只在运行时暴露的故障。
- [ ] **枚举一定要进 schema 的 `enum` 列表**，否则模型会瞎编取值（`"严重"` / `"HIGH"` / `"critical"`）。
- [ ] **类型推导 schema 必须有深度上限**，否则自我引用的类型会在首次调用时栈溢出。
- [ ] **对模型严格、对自己宽容**：schema 里标所有字段必填，代码里仍然到处判空。
- [ ] **结构化输出默认不抛异常**，返回结果对象携带 `ok / raw / attempts / error`，让调用方能降级。
- [ ] **把 `attempts` 当质量指标看**，不只看最终是否正确。重试率高 = 提示词或 schema 在系统性误导模型。
- [ ] **宽容解析要剥两层壳**：Markdown 围栏 + 前后闲聊。
- [ ] **解析循环的 try/catch 要放在循环体内部**，一条坏数据只丢一条。
- [ ] **保留一条"不需要结构化输出"的降级通路**（文本解析 / 规则型发现），让模型抽风时系统仍然可用。
- [ ] **基座库不绑定具体 LLM 框架**。"能不能用某个框架"是依赖契约问题，不是技术偏好问题。
- [ ] **别用 JSON mode 去扛"字段必须齐全"的需求。** 它只保证"能解析"，**空对象也是合法 JSON**；需要强保证就得走 schema 约束或函数调用。（§2.5）
- [ ] **"说了没有问题"和"什么都没说"必须是两件事。** 前者返回空列表，后者**当失败**——两者在日志里长得一样，在行为上差一个事故。（§2.6）
- [ ] **重试必须回灌错误信息。** 不带反馈的重试，只是用同样的方式再错一次；而**重试率上升是提示词漂移的最早信号**，比最终结果更早。（§2.6）

## 五、动手任务

> **任务一：看着"静默通过"发生，再把它变成"明确未完成"。**
>
> **仓库位置**：`code-review-agent`
>
> **操作**：
> 1. 写一个假的 `ChatModel`（LangChain4j 的 `ChatModel` 接口），`chat(ChatRequest)` 返回一个**内容为空串**的 `ChatResponse`。
> 2. 用 `LangChain4jChatProvider` 包装它，调一次 `chat(...)`。
> 3. 记录**抛出的异常类型与消息**。
> 4. 然后把判空那三行注释掉（改成直接返回 `text`），再调一次。
>
> **预期结果**：
> - 有判空：抛 `IllegalStateException`，消息是 `xxx 返回空内容`。
> - 无判空：**正常返回 `""`**——然后把它喂给 `LlmFindingParser.parse("")`，你会看到它返回**空列表**。
> - **思考题**：空列表在报告里会被渲染成什么？去读一遍 `Coordinator` / `ReportGenerator` 里对空 `findings` 的处理——**你会看到"逻辑审查通过"是怎么被渲染出来的。这就是"静默通过"的完整路径。**
>
> **任务二：验证"带反馈重试"和"原样重发"的差别。**
> 1. 写一个**脚本化假模型**：第 1 次返回 `我分析了一下，嗯，这段代码看起来没问题。`（非 JSON），第 2 次返回合法 JSON。
> 2. 用 `StructuredChatModel.chat(prompt, SomeRecord.class, 2)` 调一次，打印 `StructuredResult` 的 `ok / attempts / retried()`。
> 3. 在假模型里**把收到的 prompt 打印出来**（第 2 次调用时）。
>
> **预期结果**：
> - `ok == true`、`attempts == 2`、`retried() == true`。
> - 第 2 次的 prompt 里能看到三个新增段落：**"你上一次的输出无法解析，失败原因：…"**、**"上一次的输出是：…"**、**"请严格只输出…"**。
> - **如果去掉带反馈重试那段代码**（把 `currentPrompt = base` 保持不变），第 2 次收到的 prompt 与第 1 次**完全一致**——**这就是"原样重发大概率得到同样结果"的证据。**
>
> **任务三（进阶）：看枚举进 schema 的差别。**
> 调 `JsonSchemas.fromType(ReviewFindingDto.class)`，把结果序列化打印出来，找到 `severity` 字段。
>
> **预期结果**：它应该是 `{"type":"string","enum":[...]}`，而 `enum` 里正好是 `Severity` 枚举的全部取值。**如果这里只有 `{"type":"string"}`，模型输出 `"严重"` 你一点都不该意外。**

## 本讲小结

1. **结构化输出的失败有四种**（调用失败 / 非 JSON / 内容不符 / 空输出），必须分开处置。**调用失败不属于这一层。**
2. **重试必须带反馈**——失败原因 + 上一次输出 + 重复约束。原样重发等于白花钱。
3. **schema 由类型推导，枚举要展开**，并且必须防自我引用（深度上限）。
4. **默认 API 不抛异常**，返回携带 `raw / attempts / error` 的结果对象；`attempts` 是**指向提示词质量的质量指标**。
5. **空输出必须当失败**。一行判空，把"看起来通过"变成"明确标注未完成"——这是本讲最便宜、收益最高的一处修复。
6. **永远保留一条不需要结构化输出的降级通路**（文本解析 + 规则型发现），让模型抽风时系统仍然可用。

下一讲把模块一收口：**当你有多个通道、多个档位、多个模型时，请求该走哪一条——以及全部失败时你能不能诚实地说出来。**
