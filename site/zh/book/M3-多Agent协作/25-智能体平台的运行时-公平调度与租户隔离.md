# 第 25 讲 · 智能体平台的运行时：公平调度与租户隔离

> 🎯 导读问题：**"同一个进程里，一个租户能不能把其他所有租户的服务质量拖到零——而且从头到尾不报一个错？"**

<img class="mermaid-svg" src="/zh/book-assets/diag-0109.svg" alt="🎯 导读问题：&quot;同一个进程里，一个租户能不能把其他所有租户的服务质量拖到零——而且从头到尾不报一个错？&quot;" />

> **图 25-0**　本讲地图：**"一个大租户不能拖垮全部租户"这句话，是一条可以被证伪的判据——判据是"租户 A 打满自己的额度时，租户 B 的 P99 有没有动"。** 这张图把它拆成五个必须先答的问题：资源分几类（它们的占用方式不一样）、公平到底是什么意思、舱壁按什么粒度切、占了不还怎么办、出事后靠什么归因。五个问题里有四个的正确答案都不在"隔离数据"那一侧，而在"分配运行时"这一侧。

## 一、痛点

第 24 讲解决的是**数据**隔离：一份系统里，A 团队不能看见 B 团队的行。那一讲的判据是"跨租户查询有没有被挡住"。

这一讲要解决的是**运行时**隔离：同一份系统、同一组线程池、同一个数据库连接池，A 团队不能把 B 团队的请求挤出去。它的判据完全不同——**不是"看见了什么"，而是"还算不算得动"**。

两者的失败模式也不同源。数据隔离失败会留下痕迹（跨租户记录进了响应体，一眼可见）；运行时隔离失败**什么痕迹都不留**，只有一堆分布变差的延迟，和一台没有报警的机器。

先把这一讲要解释的三个故障摆出来。它们都发生在 `code-review-agent` 现成的配置上，都用不上任何极端假设。

**故障一：队列丢的是"新来的"，而队列已经被一个人占满了。**

Agent 池是 64 线程 + 512 队列（`ProductionExecutorConfig.java:41-42`），队列是 `ArrayBlockingQueue`——**严格 FIFO**：

```text
    @Bean(name = "agentExecutor", destroyMethod = "shutdown")
    public Executor agentExecutor(
            @Value("${review.concurrency.agent-threads:64}") int threads,
            @Value("${review.concurrency.agent-queue-capacity:512}") int capacity) {
        return bounded("agent", threads, capacity);
    }
```

`ProductionExecutorConfig.java:39-44`

于是"池的在飞上限"是 `64 + 512 = 576` 个任务。现在假设某一个租户一次提交了 600 个任务：

- 前 64 个立刻拿到线程；
- 接着 512 个进入队列；
- **剩下的 24 个被丢弃**——`600 − 64 − 512 = 24`。

丢谁？不是丢队首（队首是最旧的），是丢**刚刚提交的那个**：

```text
        return new ThreadPoolExecutor(n, n, 0L, TimeUnit.MILLISECONDS, queue, factory,
                new ThreadPoolExecutor.DiscardPolicy() {
                    @Override
                    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
                        log.warn("线程池[{}]任务队列已满({}/{}), 丢弃任务", prefix, e.getQueue().size(), capacity);
                        super.rejectedExecution(r, e);
                    }
                });
```

`ProductionExecutorConfig.java:61-68`

**`DiscardPolicy.rejectedExecution` 是一个空方法**——`super.rejectedExecution(r, e)` 什么也不做。它丢掉的 `r` 就是本次被拒绝的、**新提交**的那个任务。

把两件事放在一起，就得到这一讲最不直觉的一条：**FIFO 队列 + "丢新来的"，等于"先到者不但排在前面，还能把后来者彻底关在门外"**。在队列被消费完之前，**其他所有租户提交的任务会被立刻丢弃，一个都进不去队列**。而它自己的前 576 个任务会被正常执行。

这不是"不公平"，这是**完全排斥**。而且没有一个请求失败——被丢的那些，调用方连异常都拿不到。

**故障二：连接池才是真瓶颈，而它比线程池小一个数量级。**

四个池加起来 **136 个线程**（`8 + 32 + 64 + 32`），而全部 `Pg*` 存储共用的那**一个**连接池上限是 **12**：

```text
        cfg.setPoolName("pg-persistence-pool");
        cfg.setMaximumPoolSize(12);
        cfg.setMinimumIdle(2);
        cfg.setConnectionTimeout(30_000);
        cfg.setIdleTimeout(600_000);
        cfg.setMaxLifetime(1_800_000);
        cfg.setConnectionTestQuery("SELECT 1");
```

`PgDb.java:53-59`

`136 / 12 ≈ 11.3` —— **线程侧的并发预算比连接侧大了十倍以上。**

> **推演**：若某实例上 64 个 Agent 池线程同时进入"要写一次 PG"的段落，则同时最多 12 个能拿到连接，其余 52 个在 `getConnection()` 上排队；按 `connectionTimeout = 30_000`，它们最迟在 30 秒后以 `SQLException` 结束（假设：Agent 池的任务在结束阶段各写一次状态；基座值 `maximumPoolSize=12` 见 `PgDb.java:54`、`agent-threads=64` 见 `ProductionExecutorConfig.java:41`）

注意这里没有一个数字是"配置错了"。两个池各自都合理，**错的是它们之间没有对账**。而更要紧的是那句 `setConnectionTimeout(30_000)`：**线程池满了是"立刻丢弃"，连接池满了是"等 30 秒再抛"**。同一个系统里，两种资源对"满了"的反应是两个极端——一种让调用方完全不知道，一种让调用方白等 30 秒。

**故障三：所有证据里都没有租户。**

被丢弃时留下的唯一痕迹是这一行：

```text
                        log.warn("线程池[{}]任务队列已满({}/{}), 丢弃任务", prefix, e.getQueue().size(), capacity);
```

`ProductionExecutorConfig.java:65`

`prefix` 的取值只有四个：`webhook` / `review` / `agent` / `io`（`ProductionExecutorConfig.java:29/36/43/50`）。线程名也一样：

```text
            Thread thread = new Thread(runnable, "code-review-" + prefix + "-" + THREAD_ID.incrementAndGet());
```

`ProductionExecutorConfig.java:57`

**日志里没有租户，线程名里没有租户，指标里也没有租户。** 于是你能看见"有人在丢"，永远看不见"谁在被丢"；你去 dump 线程栈，能看见 64 个 `code-review-agent-N`，看不出哪个租户在占。

三个故障有一个共同根因，而且它不是"配置没调好"：

> **线程池、连接池、信号量这些容器，天生只有一个"资源"维度，没有"身份"维度。**

`ThreadPoolExecutor` 认识"线程"和"队列"，不认识"谁"。`HikariDataSource` 认识"连接"，不认识"谁"。所有按租户分配的能力，都必须**在池子之外另造一层**——要么造 N 个池（每租户一个），要么造一个能按身份计数的准入门。这一讲就是把这两种做法讲清楚，并说明各自会在哪里失效。

这一讲要回答五个问题：

1. **一个 Agent 进程里到底有哪几类资源？** 它们的"占用方式"并不一样。
2. **"公平"在运行时里是什么意思？** 先到先得、按身份配额、优先级抢占，代价各不相同。
3. **舱壁按什么粒度切？** 本项目的四个池是按"任务类型"切的——它防不住什么？
4. **占了不还怎么办？** 并发额度会泄漏，而 TTL 又会引入第二个问题。
5. **出事后怎么归因？** 为什么"丢弃计数"必须挂在租户对象上，而不是打在日志里？

> **判据**：**"我们做了多租户隔离"这句话，只有在你能同时说出"租户 A 打满它自己的额度时，租户 B 的 P99 没有变化"和"如果 P99 变了，我能从一份数据里指出是哪个租户"时，才算成立。** 第一句验的是分配，第二句验的是归因。少任何一句，隔离都只是配置里的一个键。

## 二、原理

### 2.1 四种资源，两种占用方式：先画出来

"资源"这个词太钝了。在运行时里，需要被分配的东西有**四类**，而它们的差别不在重要性，在 **"占用方式"**：

<img class="mermaid-svg" src="/zh/book-assets/diag-0110.svg" alt="&quot;资源&quot;这个词太钝了。在运行时里，需要被分配的东西有四类，而它们的差别不在重要性，在 &quot;占用方式&quot;：" />

> **图 25-1**　四种资源与两种占用方式。**这张图要给出的新结论是：配额的"算法"由占用方式决定，不由资源本身决定。** 占有型（线程、连接、并发槽位）的配额是"池子/槽位数"，可以"先占后还"，所以它的头号故障是**泄漏**；消耗型（请求数、token、钱）的配额是"窗口内的累计值"，**用掉就不存在归还**，所以它的头号故障是**窗口边界**与**估算误差**。把这两类混在一起算，会同时得到错误的配额和错误的告警。

先看工业界是怎么给这三类（而不是四类）资源命名的：

```text
    rate_limit_type: Literal["requests", "tokens", "max_parallel_requests"]
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:516`

**只有三个值，恰好是三类资源**：请求数、token 数、并发数。第四类（钱）不在限流描述符上，而在预算实体上另算。这张类型标注本身就是一份结论：**运行时资源不是一个可以被"总配额"概括的东西，它是几条互不相通的轨道。**

每条轨道上能挂多少个限额，写在另一张结构里：

```text
class RateLimitDescriptorRateLimitObject(TypedDict, total=False):
    requests_per_unit: int | None
    tokens_per_unit: int | None
    max_parallel_requests: int | None
    window_size: int | None
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:488-492`

四个字段：请求数、token 数、并发数、**窗口大小**。前三个是"资源"，第四个是"时间尺度"。这说明配额的最小完整单元其实是 **"资源 × 时间尺度"**——同一个 token 限额，可以是"每分钟"也可以是"每天"：

```text
    tpm_limit: int | None = None
    rpm_limit: int | None = None
    tpd_limit: int | None = None
```

`litellm/litellm/models/team.py:72-74`

`tpm`（每分钟 token）与 `tpd`（每天 token）**是同一资源的两种尺度**。为什么要两个？因为它们的失效模式不同：`tpm` 防的是瞬时打爆上游配额，`tpd` 防的是无人察觉的缓慢超支。**只配一个，就等于只防了一种。**

**而这张图最值钱的结论是：两类资源的实现机制在工业界的同一份文件里是两套。**

消耗型走的是"窗口键 + 计数键"：

```text
-- KEYS layout: pairs of (window_key, counter_key), one pair per descriptor.
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:212`

占有型走的是 gauge（有序集合，成员是每个请求的槽位 id，分数是获得时间）：

```text
-- KEYS: one gauge zset key per descriptor.
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:339`

同一种资源的两套数据结构，是因为两种语义：

- **计数**可以重置（窗口过期就归零），所以它需要两个键（记住窗口起点 + 记住窗口内累计）；
- **槽位**不能重置（在飞的请求必须一直算数），所以它是一个集合，靠 `ZCARD` 数成员。

而槽位这条路立刻带来一个计数路没有的问题——**占了不还**。这段注释把动机写得非常清楚：

```text
-- pruning slots older than the slot TTL, so unlike the windowed RPM/TPM
-- counters the gauge is never reset while requests are in flight, a
-- rejected request never occupies a slot, and a slot leaked by a crashed
-- worker self-heals after the slot TTL even under continuous traffic.
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:334-337`

三句话，三条设计判据：

1. **"in-flight 期间 gauge 永不重置"** —— 与 RPM/TPM 计数器的根本差别；
2. **"被拒绝的请求从不占槽"** —— 顺序必须是"先判定、后占槽"，不许反；
3. **"崩溃泄漏的槽位靠 TTL 自愈"** —— 一个进程崩了不会调用释放回调，所以槽位必须**自己会过期**。

第 3 条决定了占小额的配额必须带一个 TTL：

```text
# How long an acquired slot counts toward the in-flight total before it is
# considered leaked (worker crashed without any release callback firing) and
# pruned. Also the longest request duration the gauge can track: a request
# running longer than this stops occupying its slot.
PARALLEL_REQUEST_SLOT_TTL_SECONDS: Final = 3600
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:466-470`

**这个 TTL 是整段注释里最诚实的一处设计取舍，因为它自己写明了代价。** 前半句说"崩溃泄漏靠它自愈"，后半句紧接着说"**跑得比这个时长的请求会停止占槽**"。也就是说同一个旋钮有两个方向的效果：

- TTL 太短 ⇒ 长请求在跑到一半时**静默退出计数**，配额被低估（实际在飞数超过限额）；
- TTL 太长 ⇒ 崩溃泄漏的槽位会占着配额整整一个 TTL（默认 3600 秒 = 1 小时）。

**这就是"占有型资源"绕不开的一对矛盾**：你不能同时要"泄漏及时回收"和"长请求全程受保护"，只能在两者之间选一个位置，而且要**知道自己选在哪**。默认值给了 3600 秒，这个数本身就是一次选择——它意味着"本系统认为单次请求最长一小时"，而任何超过一小时的任务在这个配额模型下**是不被保护的**。

对照本项目的第四类资源（钱）与"预扣"取向，LiteLLM 还留下了一条可以直接抄的原则：

```text
# the lowest reasonable bitrate means we never under-reserve for higher-
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:458`

`never under-reserve` —— **预扣宁可多扣，不可少扣**。理由很直接：多扣的部分会在结算时退回，少扣的部分就是**超卖**，而超卖一旦发生，你手上没有任何东西能把它追回来。

### 2.2 三种"公平"，代价各不相同

"公平"这个词在运行时里至少有三个意思，而它们的**代价结构和保护力完全不同**。

<img class="mermaid-svg" src="/zh/book-assets/diag-0111.svg" alt="&quot;公平&quot;这个词在运行时里至少有三个意思，而它们的代价结构和保护力完全不同。" />

> **图 25-2**　三种公平与它们各自的代价。**这张图要给出的新结论是：公平不是"要不要做"的选择，而是"愿意付哪种代价"的选择。** 先到先得不要钱，也不提供任何保护（因为它把"公平"定义在顺序上，而不是份额上）；按身份配额真的能拦住坏邻居，代价是容量会被切碎、彼此的闲置不能借用；优先级抢占能把重要租户救出来，代价是要求被抢占方具备"可中断"语义——而 LLM 调用天然不可中断，上游已经计过费了。

**第一种：先到先得。** 工业库的默认值就是它：

```text
    public static final int DEFAULT_MAX_CONCURRENT_CALLS = 25;
    public static final Duration DEFAULT_MAX_WAIT_DURATION = Duration.ofSeconds(0);
    public static final boolean DEFAULT_WRITABLE_STACK_TRACE_ENABLED = true;
    public static final boolean DEFAULT_FAIR_CALL_HANDLING_STRATEGY_ENABLED = true;
```

`resilience4j/resilience4j-bulkhead/src/main/java/io/github/resilience4j/bulkhead/BulkheadConfig.java:33-36`

`DEFAULT_FAIR_CALL_HANDLING_STRATEGY_ENABLED = true` —— **默认就是公平排队**。而第 20 讲已经把这句话的另一半讲透了：**公平只保证"不插队"，不保证"按身份限额"**。一个租户一次发 20 个请求，公平信号量照样发它 20 个许可，因为它"到得早"。

第 20 讲还实测了本项目的一处缺口：`max-inflight-per-tenant: 20` 与 `max-inflight-global: 500` 这两个键**在 Java 侧 0 引用**（本讲复核：`grep -rn "max-inflight" src/main/java/` 命中 **0** 行）。那里留下的不是一个 bug，而是一个**问题**：假设要把它们做成真的，"按租户限额"这件事应该落在哪一层？本讲的第三、四节就是回答它。

**第二种：按身份配额。** 工业界的做法不是给配额对象加字段，而是**把配额挂在一个"描述符"上**：

```text
class RateLimitDescriptor(TypedDict):
    key: str
    value: str
    rate_limit: RateLimitDescriptorRateLimitObject | None
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:495-498`

`key` 是维度名（`team` / `model` / `project` / 自定义 tag），`value` 是维度值（具体那个租户的 id）。**配额不挂在"系统"上，也不挂在"字段"上，它挂在一组"维度名 + 维度值"的键值对上。** 这是一个非常可抄的建模方式，因为它让"给谁多少"变成了一份**数据**，而不是一段代码：加一个维度不用改限流器，只需多一张描述符。

但它带来一个必须处理的连带问题——**一个请求同时受多张描述符约束时，判定必须是原子的。** LiteLLM 用一条 Lua 脚本把它写成了显式语义：

```text
-- Atomic check-and-increment-by-N across one or more descriptors.
-- All-or-nothing: if any descriptor would exceed its limit, no counter is
-- modified.
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:203-205`

**`All-or-nothing` 不是性能优化，是正确性要求。** 如果不做原子，就会出现"requests 计了数、tokens 没计数"的半扣状态：这一次被拒的请求已经把其中一个维度扣掉了，而调用方重试一次，就绕开了另一个维度。**多维配额的半扣状态是一个可以被重试放大的漏洞。**

**第三种：优先级抢占。** 它的代价藏在另一个库里——"取消"是一个**可关的**开关：

```text
    private Duration timeoutDuration = Duration.ofSeconds(1);
    private boolean cancelRunningFuture = true;
```

`resilience4j/resilience4j-timelimiter/src/main/java/io/github/resilience4j/timelimiter/TimeLimiterConfig.java:14-15`

`cancelRunningFuture` 默认 `true`，但它**可以被关掉**——关掉之后，超时就只是"不再等"，线程还在跑。这一条对 LLM 调用尤其要紧：

> **抢占一个已经在烧 token 的请求，省下的只是你自己这一侧的线程，省不下上游的钱。**

于是"抢占"在 Agent 平台上有第三种代价（前两种是"线程要能被打断"和"状态要能回滚"）：**它不能真省钱，反而可能多花钱**——被抢占的请求已经产生了上游用量，重试还要再买一次。**这就是为什么"优先级"在运行时里通常不是靠"杀"，而是靠"排队时排在前面"。**

把三种公平的代价排在一起，会得到一个反直觉的结论：

> **"要不要按租户隔离"这个问题问错了。正确的问法是"分完之后，闲置容量能不能被借用"。**

先到先得的容量利用率最高、保护力为零；按身份配额保护力最强、容量利用率最低。真正的答案在两者之间，那就是下一节和第 2.5 节：**预留一部分、共享一部分、并且让"预留"能临时膨胀。**

### 2.3 舱壁粒度：为什么"按任务分"防不住"按人抢"

第 20 讲已经讲过一个很好的设计：**按任务性质分池**（webhook / review / agent / io）。那是舱壁模式的单进程实现，它解决的问题是"慢的 IO 任务占不满 Agent 池"。

现在把问题换成"按人抢"，同一套舱壁会立刻失效。原因非常简单，用一行代码就能看清：

```text
    public static final int DEFAULT_QUEUE_CAPACITY = 100;
    public static final Duration DEFAULT_KEEP_ALIVE_DURATION = Duration.ofMillis(20);
    public static final int DEFAULT_CORE_THREAD_POOL_SIZE =
        Runtime.getRuntime().availableProcessors() > 1 ? Runtime.getRuntime().availableProcessors()
            - 1 : 1;
    public static final int DEFAULT_MAX_THREAD_POOL_SIZE = Runtime.getRuntime()
        .availableProcessors();
    public static final boolean DEFAULT_WRITABLE_STACK_TRACE_ENABLED = true;
```

`resilience4j/resilience4j-bulkhead/src/main/java/io/github/resilience4j/bulkhead/ThreadPoolBulkheadConfig.java:43-50`

**`DEFAULT_MAX_THREAD_POOL_SIZE` 的默认值不是 25、不是 100，是 `Runtime.getRuntime().availableProcessors()` ——机器核数。**

这条事实的含义比它看上去的重得多：

- 信号量舱壁（上一节那个 `25`）的默认值是**一个与机器无关的业务数**；
- 线程池舱壁的默认值是**机器规格**。

于是"按租户切 N 份舱壁"这个想法，在两种形态下的成本差了一个数量级：

| 按租户切舱壁 | 每份的默认开销 | 150 个租户在一台 32 核实例上 |
|---|---|---|
| 信号量舱壁 | 25 个许可（一个计数） | 3 750 个许可，**0 个额外线程** |
| 线程池舱壁 | max = 核数 = 32 个线程 | **4 800 个线程** |

> **推演**：`150 × 32 = 4 800` 个线程（假设：租户数 150、单实例 32 核；基座值 `DEFAULT_MAX_THREAD_POOL_SIZE = Runtime.getRuntime().availableProcessors()` 见 `ThreadPoolBulkheadConfig.java:48-49`）

> **图 25-3**　三种舱壁粒度，以及切"按租户"时会被什么卡住。**这张图要给出的新结论是：舱壁的粒度不是自由设计项，它被"实现形态"卡死了。** 用信号量，你可以按租户切到几百份（每份只是一个计数）；用线程池，你只能切到十几份，因为**每份默认要吃掉整个机器的核数**。所以正确的顺序是：先问"我要切多少份"，再由这个数字倒过来决定"我能用哪种形态"——而不是反过来。

由此得到本节最有用的一条判据：

> **★ "按租户分池"这句话里，"池"这个字必须先被翻译成"什么形态的池"。** 因为 N 个线程池 ≠ N 个信号量：前者会在租户数增长时线性吃光线程，后者不会。

再回头看本项目。它的四个池都是**全局共享**、**无租户维**的：

```text

            @Value("${review.concurrency.webhook-queue-capacity:2000}") int capacity) {
        return bounded("webhook", threads, capacity);

```

`ProductionExecutorConfig.java:25-30`

四个 `@Bean` 的形状完全一样，参数只有两个：线程数、队列容量。**它们按"任务类型"切了四份，恰恰没有按"身份"切任何一份。** 这不是漏写，这是一个很常见的阶段：先解决"不同类型的任务互相干扰"，再解决"不同的人互相干扰"。但第二件事**不能靠加一个池来做**——按上一节的算法，加池的成本随租户数线性增长。

那么正确的落点在哪？回到本项目的那个死配置。既然 `max-inflight-per-tenant` 想表达的是"每个租户最多同时 20 个在飞"，那它就不是一个池大小，而是一个**准入门**：任务的**准入判定**按 `(teamId)` 计数，通过之后仍然进入同一个共享池。这正是 LiteLLM 的描述符模型在做的事——**池子不必是每租户一份，配额必须是每租户一份。**

### 2.4 队列公平性与队头阻塞

现在看"排队"这件事。本项目的队列语义是写死的一种：

```text

        int n = Math.max(1, threads);
        BlockingQueue<Runnable> queue = new java.util.concurrent.ArrayBlockingQueue<>(Math.max(1, capacity));
```

`ProductionExecutorConfig.java:53-55`

`ArrayBlockingQueue` 是**严格 FIFO**。而它的拒绝策略选的是"直接抛"而不是"静默丢"——工业库恰好相反：

```text
    private RejectedExecutionHandler rejectedExecutionHandler = new ThreadPoolExecutor.AbortPolicy();
```

`resilience4j/resilience4j-bulkhead/src/main/java/io/github/resilience4j/bulkhead/ThreadPoolBulkheadConfig.java:58`

把这两种选择和四种池的参数放在一起，本项目的排队语义就完整了：

| 语义 | 本项目的选择 | resilience4j 的默认 | 差别在哪 |
|---|---|---|---|
| 队列类型 | `ArrayBlockingQueue`（FIFO） | `ArrayBlockingQueue`（FIFO） | 相同 |
| 队列满时 | `DiscardPolicy`（**静默丢新任务**） | `AbortPolicy`（**抛异常给调用方**） | **调用方知不知道** |
| 线程数 | core = max = n（固定） | core = 核数−1、max = 核数（弹性） | 有没有弹性 |
| 等待行为 | 池满即丢，不等 | 队列容量 100，先排队 | 失败发生在什么时刻 |

**这张表里最值得盯的是第二行。** 两种策略都能"保护系统"，但它们的差别不在保护效果，在**信息**：`DiscardPolicy` 让调用方**完全不知道**自己被拒了（它以为提交成功了），`AbortPolicy` 把拒绝变成一个可捕获的异常，调用方可以选择降级、重试或者给用户一个明确的报错。

> **判据**：**"满了"这件事必须至少被两个人知道——系统，和调用方。** 只让系统知道（日志里一行 warn），那是"静默故障"；只让调用方知道（500 报错），那是"用户体验事故"。两个都缺，就是本项目这一处。

再说**队头阻塞**。这个词经常被用错地方，因为在"队列 + N 线程池"的结构里，它其实不会发生——一个长任务只占一个线程，后面的任务还有 N−1 个线程可以用。

它真正会发生的地方是**下游的单点**：

- 一个 12 条连接的 PG 池；
- 一个串行的写库器；
- 一条被限流的上游通道。

在这些地方，**队头阻塞是 100% 的**：第一个拿到连接的长任务不放手，第二个就必须等。本项目那个下游单点就是 `pg-persistence-pool` 的 12 条连接：

```text
    /** 取一个连接（调用方负责关闭）。 */
    public Connection conn() throws SQLException {
        return hikari.getConnection();
    }
```

`PgDb.java:64-67`

`conn()` 是一个**阻塞调用**，而且注释明确把释放责任交给调用方（"调用方负责关闭"）——**这就是"占了不还"在本项目里的具体形态**：一个忘了 close 的调用路径，会永久占掉 12 分之 1 的容量，直到连接被 `maxLifetime = 1_800_000`（30 分钟）回收。

于是第 2.4 节的结论是：

> **★ 你要防的队头阻塞不在自己的线程池里，在共享的下游单点上。** 按租户排队解决不了它；能解决它的只有两件事：**按租户分下游容量**，或者**把长任务和短任务分开走不同的下游路径**。

### 2.5 大租户的专项处理：预留、溢出，以及"自动失效"

每个平台都会遇到"这个租户不一样"的时刻：大促、上线、一次全量扫描。工业界对这件事的处理写在一个字段组合里——**临时提额，而且自带过期时间**：

```text

    temp_budget_expiry: datetime | None = None
```

`litellm/litellm/models/budget.py:34-35`

两个字段配两个方法，一个判"可现在生效多少"，一个算"生效之后的上限是多少"：

```text
    def active_temp_budget_increase(self, now: datetime) -> float:
        if self.temp_budget_increase is None or self.temp_budget_expiry is None:
            return 0.0
        expiry: Final = (
            self.temp_budget_expiry.replace(tzinfo=timezone.utc)
            if self.temp_budget_expiry.tzinfo is None
            else self.temp_budget_expiry
        )
        return 0.0 if expiry <= now else self.temp_budget_increase
```

`litellm/litellm/models/budget.py:39-47`

```text
    def effective_max_budget(self, now: datetime) -> float | None:
        if self.max_budget is None:
            return None
        return self.max_budget + self.active_temp_budget_increase(now)
```

`litellm/litellm/models/budget.py:49-52`

这两段代码里有三条可以直接抄的设计：

1. **"临时"是一个能被计算的判据**：`0.0 if expiry <= now else self.temp_budget_increase`。提额生效与否**只看一个时刻比较**，不需要任何外部调度器去"撤销"它。过期即自动失效，落库不用改一个字。
2. **生效额度只有一处计算**：`max_budget + active_temp_budget_increase(now)`。所有判定（准入、告警、展示、对账）都调用同一个方法 ⇒ **不可能出现"准入认为没超、对账认为超了"**。
3. **提额是加法，不是覆盖**：`+`。这意味着"临时提额"永远不会把基础额度改小，也不会在忘记清理时把一个租户的额度永久改掉——它只会叠加一个**有截止时间的偏移**。

对照运维里最常见的那个失效：

> **"临时提额忘了改回来，一年后它变成了默认额度。"**

`temp_budget_expiry` 把这句话从"人的纪律问题"变成了"代码的判据问题"。这就是为什么"大租户专项处理"的正解不是"给它更多"，而是"**给它更多，并且让'更多'自动过期**"。

第二条要先解决的问题是**谁能改**。配额对象里有一个字段，被刻意从"用户可写面"里摘了出去：

```text

    for user input. Keep server-managed fields (e.g. `budget_reset_at`) on
```

`litellm/litellm/models/budget.py:19-20`

```text

```

`litellm/litellm/models/budget.py:55`

```text

```

`litellm/litellm/models/budget.py:58`

道理很直白：**重置时刻要是用户可写的，租户只要在窗口结束前把它往后推，配额就永远不会有重置的那一天。** 工业界的做法不是"记得校验这个字段"，而是用**类型**把它表达出来——基础类（用户可写面）里根本没有它，它只出现在 `Full` 子类里。**"谁能写哪个字段"这件事，被建模成了类层次结构，而不是一段 if。**

第三条是配额对象里那个不起眼的字段：

```text

```

`litellm/litellm/models/budget.py:25`

**软预算：越线只告警，不拒绝。** 加上硬上限，一个租户的额度就有了两级：

- 过 `soft_budget` ⇒ 告警 + 通知，**服务照常**；
- 过 `max_budget` ⇒ 拒绝。

这两级的存在，是为了让"限制"这个动作**有预警期**。只有一个硬阈值时，租户第一次意识到额度问题，就是被打断的那一刻——而那时候留给他的反应时间已经没有了。

现在把这一节收成两条可复用的结论：

> **★ 大租户的专项处理有两种，成本差一个数量级：预留（把容量切给它，闲置时别人也用不上）与溢出（允许它借用共享容量，峰值会打到别人）。工业界选的是"溢出 + 自动过期"。**
>
> **★ 任何"临时"的放宽，都必须在数据模型里带上过期时间。** 否则它会在某一天变成默认值，而没人知道是哪一天。

### 2.6 怎么知道"是哪个租户在拖累全局"

前面五节都在讲"怎么分"。这一节讲**怎么看见**——因为没有归因的隔离，是不可运维的隔离。

归因需要三样东西，工业界把它们分别落在三个位置上。

**第一样：配额对象上要有累计字段。** 花费不是另建一张表，而是挂在团队对象上：

```text
class LiteLLM_TeamTable(TeamBase):
    team_id: str
    spend: float | None = None
    max_parallel_requests: int | None = None
    budget_duration: str | None = None
    budget_reset_at: datetime | None = None
    model_id: int | None = None
    model_spend: dict | None = {}
    model_max_budget: dict | None = {}
```

`litellm/litellm/models/team.py:86-94`

`spend` 是"这个团队一共花了多少"，`model_spend` 是"按模型分了多少"。**归因维度因此是"租户 × 模型"。** 注意这两件事都长在**同一个对象**上——这就是"归因数据必须和配额同源"的意思：它们共享同一份租户标识，不可能对不上。

**第二样：归因的键必须是"维度名 + 维度值"，不能只是"维度名"。**

```text
    descriptor_key: str
    # Populated by the atomic_check_and_increment_by_n and windowed
    # sliding-window paths. A caller matching a status back to its
    # descriptor must key on (descriptor_key, descriptor_value) when this
    # is present, not descriptor_key alone -- e.g. a batch charging several
    # models' project ITPM/OTPM in one call, or a request carrying multiple
    # rate-limited tags, produces statuses sharing the same descriptor_key.
    descriptor_value: NotRequired[ReadOnly[str]]
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:517-524`

注释给了两个反例：**一次调用给多个模型记账**、**一个请求带多个被限流的 tag**——这两种情况下会产生**多张 `descriptor_key` 相同的状态**。只用维度名当键，你就会把这些状态合并成一条，归因结果直接错。

**第三样：同一个对象上的两张配额，必须用不同的 key。**

```text
# Descriptor "key" values for project-scoped ITPM/OTPM. Distinct from
# "model_per_project" (the combined-TPM descriptor) so both can be enforced
# on the same project+model simultaneously without colliding on cache keys.
PROJECT_ITPM_DESCRIPTOR_KEY: Final = "model_per_project_itpm"
PROJECT_OTPM_DESCRIPTOR_KEY: Final = "model_per_project_otpm"
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:461-465`

这段话点出一个非常容易踩的坑：**"项目级输入 token 配额"和"项目 × 模型联合 TPM 配额"会同时作用在同一个 `(project, model)` 上。** 如果两者的 key 一样，它们的 Redis 缓存键就会撞在一起——**两张配额被算成了同一个计数器，谁先写谁生效**。所以 key 里必须带上"配额的来源"，而不只是"被限制的对象"。

现在回头看本项目。归因能力**不存在**，而且缺在三个地方：

```text

                        log.warn("线程池[{}]任务队列已满({}/{}), 丢弃任务", prefix, e.getQueue().size(), capacity);
```

`ProductionExecutorConfig.java:63-65`

这一行日志能给出的信息是：**哪个池满了、队列多长、容量多大**。它给不出的是：**谁在里面**。

注意一个细节：`rejectedExecution(Runnable r, ThreadPoolExecutor e)` —— **回调是拿得到任务对象的。** 这说明"归因"的改造落点不是日志格式，而是**任务的载体**：

- **做法 A（改载体）**：在提交侧把任务包装成带租户的 `Runnable`（比如 `TenantTask implements Runnable`，字段里带 `teamId`），拒绝时从 `r` 里取。**优点**：语义显式，不依赖执行环境。**代价**：所有提交点都要经过包装这一层。
- **做法 B（改处理器）**：换一个真正的 `RejectedExecutionHandler`，在里面按租户计数（把"一行 warn"升级成"按租户的指标"）。**注意**：`DiscardPolicy` 的动作是"丢"，所以任何"丢了多少"的计数都要自己加；`AbortPolicy` 至少还能靠异常计数。

无论走哪条，验收判据都是同一句：

> **★ "你能说出最近被丢弃的 100 个任务里，哪 3 个租户占了 87 个吗？"** 说不出来，就说明丢弃这件事只是"系统知道了"，还没有"人知道"。

**落地步骤（5 步，每步一个动作）：**

1. **把四类资源列成一张表**，写清每类的"池子/计数器在哪、上限多少、满了怎么反应（拒绝还是等待）、租户维在不在这里"。这张表填不满的地方就是缺口。
2. **对一次账**：把上表里各层的容量并排放，算一遍比值（本项目的答案是 `136 : 12 ≈ 11.3`）。**任何超过 3 倍的比值都是一个必须解释的设计，不是巧合。**
3. **给每个"占有型"资源补一个 TTL，并把它的代价写进注释**（本项目的 `conn()` 是阻塞调用，TTL 就是 `maxLifetime`）。判据：注释里要能回答"跑得比 TTL 长的任务会怎样"。
4. **把配额从"代码里的 if"改成"一份数据"**：至少一张 `(维度名, 维度值) → 限额` 的表，让加一个租户或改一个限额不需要发版。
5. **给"被丢弃 / 被拒绝"这件事补一个按租户的计数**，并把它接到告警上。**验收动作**：人为打满一次队列，然后从数据里指出是哪几个租户被丢了。

> **判据**：**如果一次"一个大租户拖垮全局"的事故里，你只能给出"队列满了"这一个事实，那你的系统不是没有隔离能力，而是没有被设计成可归因的。**

## 三、代码

### 3.1 本项目：四个池 + 一个连接池，五个全局瓶颈

先看清四个池的形状。它们的类注释写着它们要解决什么：

```text
/** 生产级有界线程池，避免使用公共 ForkJoinPool 导致任务无界堆积。 */
```

`ProductionExecutorConfig.java:19`

"避免无界堆积"——这是一个正确的、而且是**必须**的出发点。它解决的问题是"任务无限堆积到 JVM"（`application.yml:114` 的注释原文）。但它不解决"谁在堆积"。

四个池由同一个工厂方法造出来，形状只有一个：

```text
    private ThreadPoolExecutor bounded(String prefix, int threads, int capacity) {
        int n = Math.max(1, threads);
        BlockingQueue<Runnable> queue = new java.util.concurrent.ArrayBlockingQueue<>(Math.max(1, capacity));
        ThreadFactory factory = runnable -> {
            Thread thread = new Thread(runnable, "code-review-" + prefix + "-" + THREAD_ID.incrementAndGet());
            thread.setDaemon(false);
            return thread;
        };
```

`ProductionExecutorConfig.java:53-60`

三个细节值得逐个读：

1. **`core = max = n`，`0L` 存活时间**（`ProductionExecutorConfig.java:61`）⇒ 池**没有弹性**：线程数就是这个数，永远是。多一个就排队，排满就丢。**没有"忙的时候多开几个线程"这条退路。**
2. **`Math.max(1, capacity)` + `Math.max(1, threads)`** —— 参数被夹紧到至少 1，**不会因为配错变成无界队列**。这是一处正确的防御：一个 `capacity = 0` 的误配会让 `ArrayBlockingQueue` 直接抛异常，而它被夹成了 1。
3. **`thread.setDaemon(false)`** —— 线程是**非**守护线程。含义是：优雅停机时 JVM 会等它们跑完（第 16 讲讲过 `server.shutdown: graceful` 与 30 秒上限），**但代价是任何一处忘了关池，进程就退不出去**。四个 `@Bean` 都写了 `destroyMethod = "shutdown"`，正是为了这个。

然后把五层容量并排放在一起（这一讲的核心数字）：

| 层 | 容量 | 出处 | 满了怎么反应 |
|---|---|---|---|
| webhook 池 | 8 线程 + 2 000 队列 | `ProductionExecutorConfig.java:27-28` | 丢新任务（静默）+ 一行 warn |
| review 池 | 32 线程 + 1 000 队列 | `:34-35` | 同上 |
| agent 池 | 64 线程 + 512 队列 | `:41-42` | 同上 |
| io 池 | 32 线程 + 1 000 队列 | `:48-49` | 同上 |
| PG 连接池 | **12 连接 + 2 空闲** | `PgDb.java:54-55` | **等 30 秒再抛**（`PgDb.java:56`） |

**这张表里没有一行是错的，错的是它们之间没有对账。** 前三层用"丢弃"处理过载，最后一层用"等待 30 秒"处理过载——两种策略同一个系统，意味着**同一个过载事件在不同层会产生完全不同的可观测现象**：有人什么都没收到（被丢了），有人 30 秒后收到一个数据库错误。排障的人会去查数据库，而真凶在第一层。

还有一处不对称值得单独说：`PgDb` 的 `conn()` 是阻塞的，而它的注释把释放责任完全交给调用方：

```text
    /** 取一个连接（调用方负责关闭）。 */
    public Connection conn() throws SQLException {
        return hikari.getConnection();
    }
```

`PgDb.java:64-67`

**"调用方负责关闭"是一句正确但危险的注释。** 它正确，因为连接是按请求借出的；它危险，因为**12 这个数字的全部意义都建立在这句话被 100% 遵守上**。任何一个漏掉 `try-with-resources` 的新代码路径，都会永久占掉 12 分之 1 的容量——而且在 `maxLifetime = 1_800_000`（30 分钟）之前，没有任何东西会把连接收回去。

### 3.2 LiteLLM：一个"配额对象"的完整形状

现在把工业界的做法拼成一个完整的对象。它由三种结构组成。

**第一种：描述符（谁能被限制、按几个维度限制）。**

```text
class RateLimitDescriptor(TypedDict):
    key: str
    value: str
    rate_limit: RateLimitDescriptorRateLimitObject | None
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:495-498`

**第二种：状态（一次判定产生了什么）。**

```text
class RateLimitStatus(TypedDict):
    code: str
    current_limit: int
    limit_remaining: int
    rate_limit_type: Literal["requests", "tokens", "max_parallel_requests"]
    descriptor_key: str
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:512-517`

请注意这里**同时带了三个东西**：`code`（结果）、`current_limit` / `limit_remaining`（剩余量）、以及 **`rate_limit_type` + `descriptor_key`（是哪张配额）**。

> **这三样缺一不可。** 只回 `code`，调用方不知道还能不能用；只回"剩余量"，调用方不知道这是哪一维的剩余量；只回"哪张配额"不回数量，调用方无法决定"要不要等一下再试"。**一个可运维的限流返回值，必须自带"我是谁、我还剩多少"。**

**第三种：两套运行时的元数据（两类资源各自的键结构）。**

消耗型的：

```text
class WindowKeyMetadata(TypedDict):
    requests_limit: int | None
    tokens_limit: int | None
    window_size: int
    descriptor_key: str
    descriptor_value: ReadOnly[str]
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:548-553`

占有型的：

```text
class AtomicCounterMeta(TypedDict):
    descriptor_key: str
    descriptor_value: ReadOnly[str]
    current_limit: int
    rate_limit_type: Literal["requests", "tokens"]
    window_key: str
    counter_key: str
    increment: int
    ttl: int
    window_size: int
```

`litellm/litellm/proxy/hooks/parallel_request_limiter_v3.py:556-565`

两边都出现了 `descriptor_key` **和** `descriptor_value`（`ReadOnly[str]`）——这印证了第 2.6 节那条判据：**归因键必须成对**，而且 `ReadOnly` 标注说明"值一旦定下就不许改"，这正是"它要被当键用"的类型级声明。

`AtomicCounterMeta` 比 `WindowKeyMetadata` 多出 `ttl` 与 `increment` 两个字段。这不是随意加的：**计数型资源需要"每次加多少"，而窗口型资源只需要"窗口内总共多少"。** 而 `ttl` 的存在再次说明——**去重、防重放、自动过期这些事，全部靠"给键设寿命"完成，而不是靠定时任务**。

### 3.3 缺口清单：本项目要补的三处

把前面所有实况收起来，本项目在"运行时租户隔离"上有三处缺口。按最小改动排序：

**缺口一：准入门没有实现。** `max-inflight-per-tenant: 20` / `max-inflight-global: 500` 两个键存在，但 Java 侧 0 引用。

```text
    max-inflight-per-tenant: ${REVIEW_MAX_INFLIGHT_PER_TENANT:20}
    max-inflight-global: ${REVIEW_MAX_INFLIGHT_GLOBAL:500}
```

`application.yml:124-125`

**最小改法**（不需要给每个租户建池）：在提交任务前做一次按 `teamId` 的计数准入——准入通过后仍然投进同一个共享池，**用完在 `finally` 里归还**。要照抄 LiteLLM 的两条：① 计数必须**先判定后占用**，被拒的请求不占名额；② **占用必须带超时**，否则一次崩溃永久占掉一个租户的名额。

**缺口二：容量之间没有对账。** 136 线程 vs 12 连接，比值 ≈ 11.3。

这不是"改一个数字"能解决的，因为改哪一边都有代价：调大连接数会打到 PG 的 `max_connections`（第 45 讲展开）；调小线程数会降低并发。**正确的动作是让这个比值变成一个有据可依的设计决定**——问清楚"一次 Agent 任务里有几次 PG 往返"，再决定连接池该多大。

**缺口三：丢弃这件事没有租户维。** 四个 `prefix`、线程名、warn 日志，三处都没有租户。

最小改法见 §2.6。但要先做一件事：**承认 `DiscardPolicy` 选的不是"丢弃"，是"隐藏"。** 如果要把"丢"变成可运维的信号，改成 `CallerRunsPolicy`（第 20 讲提过：最便宜的一种背压）或至少换成一个会计数的处理器，比在日志里加字段更根本——**因为日志是给人看的，计数才是给系统看的。**

## 四、避坑清单

- [ ] **别以为"公平"能防坏邻居。** `DEFAULT_FAIR_CALL_HANDLING_STRATEGY_ENABLED` 默认就是 `true`，但它保证的是"不插队"，不是"按身份限额"。一个租户一次发 20 个请求，公平信号量照样给它 20 个许可。（§2.2）
- [ ] **别给每个租户建线程池舱壁。** 线程池舱壁的 `DEFAULT_MAX_THREAD_POOL_SIZE` 是**机器核数**（`ThreadPoolBulkheadConfig.java:48-49`），按租户切 N 份 = `N × 核数` 个线程。150 个租户在 32 核实例上是 4 800 个线程。要按租户切，用信号量。（§2.3）
- [ ] **别把"配额"和"池大小"当成一回事。** 池子是资源侧，配额是身份侧。**池子不必每租户一份，配额必须每租户一份。**（§2.3）
- [ ] **别在"占用了就归还"这件事上信任调用方。** 本项目 `conn()` 的注释是"调用方负责关闭"（`PgDb.java:64`），而 12 条连接的全部容量都建立在这句话被 100% 遵守上。任何一处漏掉 `try-with-resources` 的路径都会永久占掉 1/12。（§3.1）
- [ ] **占有型资源必须带 TTL，而且要知道 TTL 的副作用。** LiteLLM 的槽位 TTL 是 3 600 秒，注释同时写明"崩溃泄漏靠它自愈"和"跑得更长的请求会停止占槽"（`:466-470`）。**你不能同时要"泄漏及时回收"和"长请求全程受保护"。**（§2.1）
- [ ] **别用同一套计数器实现消耗型和占有型资源。** 消耗型需要"窗口键 + 计数键"两把键（可重置），占有型需要一个有序集合（**在飞期间不可重置**）。LiteLLM 在同一份文件里就是两套 Lua 脚本（`:212` vs `:339`）。（§2.1）
- [ ] **多维度配额的判定必须 All-or-nothing。** 否则会出现"requests 计了数、tokens 没计数"的半扣状态，**而调用方重试一次就绕开了另一个维度**——半扣状态是一个会被重试放大的漏洞。（§2.2）
- [ ] **别用"总配额"概括运行时资源。** 工业界把限流类型明确分成三个（`requests` / `tokens` / `max_parallel_requests`，`:516`），钱在另一条轨道上。**用一个大数字当配额，等于让最先打满的那一类资源自己决定全局上限。**（§2.1）
- [ ] **同一个对象上的两张配额，key 必须不同。** "项目输入 token 配额"和"项目 × 模型联合 TPM"会同时作用在同一个 `(project, model)` 上；key 一样就会在缓存键上撞车，两张配额被算成同一个计数器（`:461-465`）。（§2.6）
- [ ] **归因键必须是（维度名, 维度值）二元组。** 只用维度名，一次"给多个模型记账"或"带多个被限流 tag"的调用就会产生多条同键状态，被合并成一条（`:517-523`）。（§2.6）
- [ ] **别让"临时放宽"没有过期时间。** `temp_budget_increase` + `temp_budget_expiry` 的组合让"临时"成为代码能算的判据（`budget.py:34-35/47`）。没有这个字段，"临时提额忘了改回来"就是必然事件。（§2.5）
- [ ] **生效额度只能有一处计算。** LiteLLM 是 `effective_max_budget() = max_budget + active_temp_budget_increase(now)`（`budget.py:49-52`）。两个地方各算一遍，一定会出现"准入认为没超、对账认为超了"。（§2.5）
- [ ] **别让租户能写自己的"重置时刻"。** `budget_reset_at` 被放进 `LiteLLM_BudgetTableFull` 子类，而不是用户可写的基础类（`budget.py:19-20/55/58`）——**租户把窗口往后推一次，配额就永远没有重置的那一天。**（§2.5）
- [ ] **额度要有软硬两级。** 只有硬上限时，租户第一次知道额度问题就是被打断的那一刻（`soft_budget` 越线只告警，`budget.py:25`）。（§2.5）
- [ ] **预扣宁可多扣，不可少扣。** 多扣的部分会在结算时退回，少扣的部分是超卖——而超卖**追不回来**。（`we never under-reserve`，`:458`）（§2.1）
- [ ] **别以为"池子满了"和"下游满了"是一回事。** 本项目前面四层用"丢弃"处理过载，最后一层（PG 连接池）用"等 30 秒再抛"处理过载（`PgDb.java:56`）。同一个过载在不同层产生完全不同的现象：有人什么都没收到，有人 30 秒后收到数据库错误。**排障的人会去查数据库。**（§3.1）
- [ ] **队头阻塞不在你的线程池里，在共享的下游单点上。** 在 N 线程池里一个长任务只占 1 个线程；在"12 条连接"、"一个串行写库器"这种下游单点上，它是 100% 的。按租户排队解决不了它。（§2.4）
- [ ] **别忽略那句"丢弃时不报错"。** `DiscardPolicy.rejectedExecution` 是空方法（`ProductionExecutorConfig.java:62-66`），被丢的任务连异常都没有。**它选的不是"丢弃"，是"隐藏"。**（§3.3）
- [ ] **排障信息里没有身份，等于没有排障信息。** 本项目的池前缀只有 4 个任务类型（`webhook`/`review`/`agent`/`io`）、线程名只有池前缀 + 自增号（`:57`）、warn 日志只有池名与队列长度（`:65`）——三处都没有租户。（§2.6）
- [ ] **别让各层容量"各自合理、合起来不合理"。** 136 个线程对 12 条连接（`136 / 12 ≈ 11.3`），两边都没有配错，错的是它们之间没有对账。**任何超过 3 倍的比值都是一个必须解释的设计。**（§3.1）
- [ ] **"隔离配置存在"不等于"隔离存在"。** `max-inflight-per-tenant` / `max-inflight-global` 两个键在 yml 里，Java 侧 0 引用。**判据：隔离是否生效，唯一可靠的验证是让它触发一次并观察拒绝**——没有触发、没有拒绝计数，就等于没有这个隔离。（§3.3）
- [ ] **别把"给大租户更多"当成唯一手段。** 预留会把容量切碎（闲置时别人用不上），溢出让峰值打到别人。工业界选的是"溢出 + 自动过期"，而不是"预留一大块"。（§2.5）

## 五、动手任务

**任务一（必做）：把五层容量画成一张对账表。** 用你手上的系统，把"Web 线程池 / 业务线程池 / Agent 线程池 / IO 线程池 / 数据库连接池 / 上游并发配额"各层的**上限**并排列出来，算两两比值。然后在每一行补两列：**"满了怎么反应"**（丢/等/抛/降级）与 **"租户维在不在这里"**。这张表填完之后，你会立刻看到两个东西：哪一层会先满，以及哪一层完全看不见租户。

**任务二（必做）：让你系统的"丢弃"变得可归因。** 选一个池，做两件事：① 把饱和策略从"静默丢"换成会计数的（LiteLLM 的做法是把拒绝写进返回状态；本项目的最小做法是加一个按 `teamId` 的计数器）；② 人为打满一次队列，然后**从数据里指出是哪几个租户被丢了**。第二件事做不成，就说明第一步做得不对。

**任务三（选做）：给一个"占有型"资源补 TTL，并把代价写进注释。** 挑一个"占了才还"的配额（并发槽位、租约、临时 token 池），给它加一个过期时间，然后在注释里回答两个问题：**崩溃泄漏要在多久内自愈？** 以及 **"跑得比 TTL 长的请求会怎样"**？LiteLLM 的答案分别是"一个 TTL 内"和"停止占槽，配额被低估"（`:466-470`）——第二个答案是必须写下来的，因为它是一个**已知的、被接受的**偏差。

## 本讲小结

- **运行时资源有四类，但决定配额算法的是"占用方式"**：线程/连接/并发槽位是**占有型**（用完归还 ⇒ 头号故障是泄漏），请求数/token/钱是**消耗型**（不存在归还 ⇒ 头号故障是窗口边界与估算误差）。两者在工业界是两套实现（`parallel_request_limiter_v3.py:212` vs `:339`）。（§2.1）
- **"公平"有三种，代价各不相同**：先到先得代价为 0、保护力也为 0；按身份配额能防坏邻居、代价是容量碎片化；优先级抢占要求被抢占方可中断——而 LLM 调用**天然不可中断，上游已经计了费**。（§2.2）
- **舱壁的粒度被实现形态卡死。** 信号量舱壁的默认值是"25 个许可"（与机器无关），线程池舱壁的默认值是"核数"（与业务无关）。**要按租户切到几百份，只能用信号量。**（§2.3）
- **池子不必每租户一份，配额必须每租户一份。** 本项目那四个按任务类型切的池、以及那个 0 引用的 `max-inflight-per-tenant`，正好说明：按身份分配是**准入门**的事，不是**池**的事。（§2.3、§3.3）
- **占有型资源必须带 TTL，而 TTL 是一对矛盾的两面。** 短了：长请求静默退出计数、配额被低估；长了：崩溃泄漏要占满整个 TTL。默认值 3 600 秒本身就是一次选择——**它宣称"本系统认为单次请求最长一小时"。**（§2.1）
- **队头阻塞在"队列 + N 线程池"里不会发生，在下游单点上 100% 发生。** 本项目那个单点就是 12 条共享 PG 连接，而 `conn()` 是阻塞调用、释放责任在调用方。（§2.4、§3.1）
- **"临时"必须在数据模型里带过期时间。** `temp_budget_expiry` 让提额过期即自动失效，不需要任何外部调度器；`effective_max_budget()` 让生效额度只有一处计算。**这两条合起来把"临时"从人的纪律问题变成了代码的判据问题。**（§2.5）
- **"谁能写哪个字段"用类型表达，不用 if 表达。** `budget_reset_at` 只在 `LiteLLM_BudgetTableFull` 里——因为一个租户只要能在窗口结束前把重置时刻往后推，配额就永远不会有重置的那一天。（§2.5）
- **归因能力要三样东西齐全**：累计字段长在租户对象上（`spend` / `model_spend`）、归因键是（维度名, 维度值）二元组、同一对象上的两张配额 key 不同。**本项目三样都没有**——池前缀只有任务类型、线程名只有自增号、warn 只有队列长度。（§2.6）
- **隔离做的对不对，只认两个可验证的事实**：租户 A 打满自己额度时租户 B 的 P99 有没有变化；以及如果变了，你能不能从一份数据里指出是哪个租户。**说不出来，就是把"隔离"写进了配置而不是写进了系统。**（§一、§3.3）
