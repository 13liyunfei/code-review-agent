## 一、痛点

上一讲我们把五个 Agent 并行跑起来了。**压力一上来，出现了四类故障。**

**故障一：任务无界堆积，内存慢慢涨。**

代码里写的是：

```java
CompletableFuture.supplyAsync(task);        // ❌ 用默认线程池
```

默认线程池是 `ForkJoinPool.commonPool()`。它的特点是：

- **JVM 全局共享**（所有用默认池的代码抢同一批线程）；
- **队列无界**（任务堆着不会拒绝，直到 OOM）；
- **线程数固定**（约 `CPU 核数 - 1`）。

**结论**：一次 200 个 PR 的批量导入，能把堆内存慢慢吃光。**而这个现象和你自己的代码一点关系都没有** —— 它取决于**整个 JVM 里其他用默认池的地方有多少**。

**故障二：队列满了，任务被丢掉，但报告显示"超时"。**

我配了有界队列，满的时候用 `DiscardPolicy`。**日志里能看到"任务队列已满，丢弃任务"。**

**但报告里写的是"执行超时（300000ms）"。**

**——这是两个完全不同的根因：**

| 真实原因 | 排查方向 |
|---|---|
| **任务太慢**（模型响应慢、prompt 太大） | 优化 prompt、换模型、调大超时 |
| **容量不足**（队列满，任务从未开始跑） | **加线程、加大队列、削峰** |

**报告给了错误的排查方向。** 而这条日志在高峰期会被刷屏，**没有人会去把它和"超时"关联起来。**

**故障三：Webhook 返回了 `accepted`，但那个 PR 永远不会被审查。**

Webhook 控制器：

```java
// GiteaWebhookController.java:139-147
CompletableFuture.runAsync(TraceContext.wrap(() ->
        reviewService.reviewPullRequest(owner, repo, prNum, headSha, teamHeader)
), webhookExecutor);

return ResponseEntity.ok(Map.of(
        "status", "accepted",
        "pr", String.valueOf(prNum),
        "repo", repoFullName
));
```

**如果 `webhookExecutor` 的队列满了，且拒绝策略是"丢弃"，`runAsync` 不会抛异常** —— 它只是把任务丢了。

**而控制器照样返回 `{"status":"accepted"}`。**

**"accepted" 这个词的意思是"我接受了这个请求"。如果任务是丢掉的，那这句话是假的。**

**后果**：某个 PR 永远不会被审查，**Gitea 那边显示成功，开发者以为审查通过了。**

**故障四：调不出"该配多少线程"。**

配置里有四个池、八个数字：

```yaml
review:
  concurrency:
    webhook-threads: 8
    webhook-queue-capacity: 2000
    review-threads: 32
    review-queue-capacity: 1000
    agent-threads: 64
    agent-queue-capacity: 512
    io-threads: 32
    io-queue-capacity: 1000
```

**你一个都说不出"为什么是这个数"。** 而在压力测试里，把 `agent-threads` 从 64 改成 256 之后……**事情变慢了。**

**四个故障，指向同一件事：并行编排不是"开几个线程"，它是"容量规划 + 拒绝策略 + 超时语义"三件事的合成。**

## 二、原理

### 2.1 为什么不能用 `ForkJoinPool.commonPool()`

配置类的类注释只写了一句话：

```java
// config/ProductionExecutorConfig.java:20
/** 生产级有界线程池，避免使用公共 ForkJoinPool 导致任务无界堆积。 */
```

**这句话里的关键词是"无界"。** 展开说，`commonPool()` 有四个问题：

| 问题 | 后果 |
|---|---|
| **Queue 无界** | 任务堆积 → 内存涨（不是拒绝，是慢慢死） |
| **JVM 全局共享** | 你的任务和别人的任务互相影响（**故障表现与你无关**） |
| **线程数固定** | 约 `CPU-1`，与任务性质（IO 密集 or CPU 密集）无关 |
| **业务线程不能控制** | 无法按"webhook / 审查 / Agent / IO"隔离（**没有舱壁**） |

**第三个问题在 LLM 场景里特别致命**：Agent 任务是 **IO 密集**（等模型响应，秒级），而 `commonPool` 是**按 CPU 密集设计的**。

> **一个 IO 密集的任务放在为 CPU 密集设计的池里，等于用少数几个线程去等大量网络响应。** 吞吐量被线程数死死卡住，而 CPU 全程闲着。

### 2.2 四个池 = 四道舱壁

```java
// config/ProductionExecutorConfig.java:25-50（结构）
@Bean(name = "webhookExecutor",  destroyMethod = "shutdown")  // 8  线程 / 2000 队列
@Bean(name = "reviewExecutor",   destroyMethod = "shutdown")  // 32 线程 / 1000 队列
@Bean(name = "agentExecutor",    destroyMethod = "shutdown")  // 64 线程 / 512  队列
@Bean(name = "ioExecutor",       destroyMethod = "shutdown")  // 32 线程 / 1000 队列
```

**按"任务性质"分池，是舱壁模式（Bulkhead）在单进程内的实现：**

| 池 | 任务性质 | 为什么单独一个池 |
|---|---|---|
| `webhookExecutor` | **收件**：解析 payload、快速返回 | **绝不能被审查任务饿死** —— 收不了新请求比审得慢更严重 |
| `reviewExecutor` | **审查编排**（一个 PR 一条链） | 与 Agent 执行分离，避免"编排被 Agent 占满" |
| `agentExecutor` | **Agent 执行**（含 LLM 调用） | 最耗时的一层，单独限流 |
| `ioExecutor` | **IO 操作**（拉代码、Git 平台 API） | 与 LLM 调用分离，避免"等网络"挤掉"等模型" |

**关键的不变式**：

> **`webhookExecutor` 必须比 `agentExecutor` 更容易成功。**
>
> 因为 webhook 是**入口**。入口被堵住，**整条流水线停止接收新工作**；而 Agent 慢，只是**这次审查慢**。
>
> **"入口优先"是一条通用的容量设计原则**：越靠近用户的那一层，越要有独立容量 + 越不能丢。

**但本项目有一个问题**：`reviewExecutor` 和 `ioExecutor` **全项目无人使用**（下一节详述）。**舱壁只建了两道，另外两道是空壳。**

### 2.3 拒绝策略：四种选择，四种后果

Java 的 `ThreadPoolExecutor` 提供四种内置策略：

| 策略 | 行为 | 适合 |
|---|---|---|
| `AbortPolicy`（默认） | **抛 `RejectedExecutionException`** | 调用方能处理失败 —— **最安全** |
| `CallerRunsPolicy` | **调用者线程自己执行** | 能自然削峰（背压）——**但会阻塞调用者** |
| `DiscardPolicy` | **静默丢弃** | ❌ 只有"丢了也无所谓"时才可接受 |
| `DiscardOldestPolicy` | **丢掉最老的，塞进新的** | 只适合"新的比老的重要" |

**本项目的选择：**

```java
// config/ProductionExecutorConfig.java:57-71
private ThreadPoolExecutor bounded(String prefix, int threads, int capacity) {
    int n = Math.max(1, threads);
    BlockingQueue<Runnable> queue = new java.util.concurrent.ArrayBlockingQueue<>(Math.max(1, capacity));
    ThreadFactory factory = runnable -> {
        Thread thread = new Thread(runnable, "code-review-" + prefix + "-" + THREAD_ID.incrementAndGet());
        thread.setDaemon(false);
        return thread;
    };
    return new ThreadPoolExecutor(n, n, 0L, TimeUnit.MILLISECONDS, queue, factory,
            new ThreadPoolExecutor.DiscardPolicy() {
                @Override
                public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
                    log.warn("线程池[{}]任务队列已满({}/{}), 丢弃任务", prefix, e.getQueue().size(), capacity);
                    super.rejectedExecution(r, e);
                }
            });
}
```

**逐行看，有一处必须停下来：**

```java
new ThreadPoolExecutor.DiscardPolicy() {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        log.warn("线程池[{}]任务队列已满({}/{}), 丢弃任务", prefix, e.getQueue().size(), capacity);
        super.rejectedExecution(r, e);        // ← 你以为这里做了什么
    }
});
```

**`DiscardPolicy` 的 `rejectedExecution` 实现是空方法。** 而 `super.rejectedExecution(r, e)` 调用的正是那个空方法。

**所以这个匿名类的实际行为是：打一行日志，然后什么都不做。**

**"只打日志的拒绝策略"，等价于静默丢弃 + 日志。**

**它带来的第一个后果，就是故障一/故障二：**


<img class="mermaid-svg" src="/zh/book-assets/diag-0085.svg" alt="它带来的第一个后果，就是故障一/故障二：" />


> **图 17-1**　一次容量不足，被系统"翻译"成了超时。**报告里写的是「超时」，真实原因是「队列满」**——而这两者的排查方向正好相反。

**报告里写的是"超时"，真实原因是"容量不足"。**

**而它带来的第二个后果是故障三**（webhook 那条）：`runAsync` 静默丢弃，控制器返回 `accepted`。

> **一个判断规则：**
> **凡是"丢弃"类策略，都必须回答一个问题——"被丢掉的那个东西，调用方知不知道？"**
> **如果调用方不知道（返回 200 / 返回 future 不完成），那就是一个静默故障。**

**修法（按代价从低到高）：**

| 方案 | 改动 | 效果 |
|---|---|---|
| **换 `AbortPolicy`** | 一行 | 提交失败会抛异常 → 被现有 catch 捕获并标降级，**归因正确** |
| **换 `CallerRunsPolicy`** | 一行 | 调用者线程执行 → **天然背压**（提交变慢，队列不再堆积） |
| **在拒绝处理器里显式完成 future** | 需要拿到 future 引用 | 最精确，但 `Executor` 接口拿不到 future |
| **用 `CompletableFuture#completeExceptionally` + 自定义 Executor** | 中等 | 最干净 |

**本项目最便宜的正确修法是第二种（`CallerRunsPolicy`）**：它把"排队"变成了"调用者亲自干"，**而调用者就是协调器线程** —— 它正在 `get()` 等结果，于是**等待时间自然变成了执行时间，总量守恒，且没有任务被丢。**

**代价**：协调器线程会被占用。**而这是可接受的，因为协调器线程本来就闲着在等。**

### 2.4 并发度怎么定：从下游反推，不是拍脑袋

**这是本讲最重要的容量推理。**

`agent-threads` 决定了**同一时刻有多少个 LLM 请求在飞**：

```
同时进行的审查数 × 每个审查的 Agent 数 = 并发 LLM 请求数
```

**而"同时进行的审查数"又由 `agent-threads` 反推。**

用 Little's Law（并发 = 到达率 × 服务时长）做一个方向性估算：

```
agent-threads = 64
每个 Agent 平均服务时长 ≈ 20s（量级，含 LLM 往返 + 解析）

Agent 吞吐 = 64 / 20s = 3.2 agents/s
审查吞吐 = 3.2 / 5（每个审查 5 个 Agent）= 0.64 reviews/s ≈ 38 reviews/min
```

**这个数字告诉你两件事：**

1. **调大 `agent-threads` 能提高吞吐吗？** **只有下游还有余量时才行。**
2. **如果下游（LLM 网关 / 供应商）的并发配额是 30，那么 `agent-threads = 64` 就是错的** —— 你会打出 64 个请求，其中 34 个收到 429，然后重试（第 04/07 讲），**重试又会加剧拥塞。**

**故障四"把它改成 256 之后变慢了"，机制就在这里：**

```
线程数 ↑ → 并发请求 ↑ → 触发下游限流 → 429/超时增多 → 重试 ↑
        → 有效吞吐 ↓（而且每次失败都白付了一次 token 的钱）
```

> **结论：线程池大小不是"越大越好"，它是"下游承压能力的映射"。**
> **正确的定法是从最窄的那个瓶颈反推**：
>
> ```
> 供应商并发上限 → 网关限流配置 → agent-threads → 队列容量
> ```
>
> **反着来（先定线程数，再看下游）是故障四的成因。**

**队列容量怎么定？** 它决定"能容忍多长的突发"。

- 队列太小 → 拒绝频繁（丢弃 or 背压）；
- 队列太大 → **等待时间不可控**（下面 2.5 节）。

**一个实用的定法**：`队列容量 ≈ 可接受的排队时长 × 服务速率`。

例如："我可以接受一个请求排队 60 秒"，服务速率 3.2 agents/s → 队列 ≈ 190。而本项目配的是 **512**，也就是**允许排队约 160 秒**（512 / 3.2）。

**而共享的 deadline 是 300 秒（`review.agent.timeout-ms:300000`）** —— **排队 160 秒 + 执行 20 秒 = 180 秒 < 300 秒，还能跑完。**

**但如果队列堆到 512 满，排在最后那个 Agent 要排 160 秒才开始跑** —— 它的"执行耗时"会显示为 180 秒，**其中 160 秒在排队。**

**这就是 2.5 节要讲的事。**

### 2.5 超时的语义：deadline 从哪一刻开始算

这是**故障二之外的第二层归因问题**。

看 deadline 的计算位置：

```java
// CompletableFutureCoordinator.java:477
long deadline = System.currentTimeMillis() + Math.max(1L, timeoutMillis);
```

**这一行在 `futures` 已经创建之后、`get` 循环之前。** 而 `futures` 的创建是**提交**，不是**开始执行**。

**时间线是这样的：**

```
t=0     提交 5 个任务（其中 3 个进入队列排队）
t=0     deadline = t=0 + 300s
t=0     advancedFuture 也提交（也在排队）
t=40s   前 3 个才真正开跑
...
t=300s  deadline 到 → 队列里还没跑的，直接标"执行超时"
```

**所以"执行超时（300000ms）"这句话里，混着三种时间：**

| 组成 | 含义 | 优化方向 |
|---|---|---|
| **排队等待** | 任务在队列里等 | **加容量 / 削峰 / 降并发** |
| **执行时间** | Agent 真的在跑 | **优化 prompt / 换模型 / 缓存** |
| **重试时间** | 失败后重试白等 | **调重试策略 / 修下游** |

**三者混在一个 `reason` 字符串里，你无从优化。**

> **一条通用建议：超时原因里应该包含"排队时长"这个量。**
>
> 例如把 `reason` 写成 `"执行超时（预算 300000ms；其中排队 162000ms，执行 138000ms）"`。
>
> **实现代价很小**（在任务开始的时候记一个时间戳——甚至可以直接用轨迹的 `agent.started` 事件），**但它把"超时"从一个笼统症状变成了两个可归因的子问题。**

**顺带一个已有的可观测资源**：轨迹里其实**已经记了开始和完成**：

```java
// CompletableFutureCoordinator.java:449-455
if (recorder != null) {
    recorder.append(runId, "agent.started", Map.of("agentType", agent.getType().name()));
}
log.info("[Coordinator] 子Agent[{}] 开始审查（并行执行）", agent.getType());
List<Finding> findings = agent.review(diffs, enrichedCtx);
log.info("[Coordinator] 子Agent[{}] 完成：发现 {} 条，耗时 {}ms",
        agent.getType(), findings.size(), System.currentTimeMillis() - a0);
```

**`a0` 是任务体的开始时刻（不是提交时刻）。**

**于是**：`提交时刻` → `agent.started` 的间隔 = **排队时长**；`agent.started` → `完成` = **执行时长**。

**这两个数已经在数据里了 —— 只是从来没有人把它们拼起来看。** 这是一个典型的"可观测性不缺数据、缺关联"的例子。

### 2.6 跨线程的 ThreadLocal：`TraceContext.wrap`

并行的最后一个隐性成本：**所有 ThreadLocal 都不会自动传播。**

本项目的 trace 机制是：

```
TraceContext（ThreadLocal<String> traceId）→ 写入 MDC → 日志里打出 traceId
```

**`CompletableFuture.supplyAsync(...)` 会把任务丢到另一个线程上执行。** 那个线程上：

- `TraceContext.get()` → 拿到的是**那个线程自己的值**（通常是 null 或上一次残留）；
- 于是日志里**五个 Agent 的日志没有 traceId**，**无法按 runId 关联**。

**解法是显式包装：**

```java
// CompletableFutureCoordinator.java:447
.map(agent -> CompletableFuture.supplyAsync(TraceContext.wrap(() -> {
    ...
}), agentExecutor))
```

```java
// GiteaWebhookController.java:139-141
CompletableFuture.runAsync(TraceContext.wrap(() ->
        reviewService.reviewPullRequest(owner, repo, prNum, headSha, teamHeader)
), webhookExecutor);
```

**两处提交点都用了 `wrap`，这一点做得对。**

**但这里有一个必须记住的通用原则：**

> **每一个"提交到另一个线程"的地方，都要问一遍：这个线程上，ThreadLocal 里的东西（traceId / MDC / 用户身份 / 事务 / 请求上下文 / 安全上下文）还成立吗？**
>
> **这类 bug 的特点是"功能全对、可观测性全丢"** —— 业务逻辑一点没错，**只是出了问题时你查不到。**
>
> **而它极难在开发环境暴露**：单人调试时，往往只有一个任务在跑，线程复用地很"顺"，看起来一切正常。

**`wrap` 的正确性还有一个前提**：它必须**恢复现场**而不是清空。

```java
// TraceContext 的契约（第 01/13 讲提过）
// wrap() 结束 restorePrev —— 绝不 MDC.clear()
```

**为什么不能用 `MDC.clear()`？** 因为工作线程是**复用的**（线程池）。如果 `clear()` 清掉了不属于本次任务的上下文，或者清掉了调用方线程 set 进去的东西，**下一个用这条线程的任务会丢上下文。**

> **"恢复"和"清空"的区别，在线程池场景下是本质区别。** 清空假设"线程是干净的"，而线程池里**线程从来不干净**。

### 3.1 ★ 两个定义了但没人用的线程池

**调这四个数字不会有任何变化** —— 而**没有任何日志会告诉你这一点**。

**为什么死代码门禁没抓到？** 第 40 讲会讲 `DeadCodeGuardTest`，它的豁免清单包含 `@Configuration`（因为配置类里的 `@Bean` 方法本来就不被"引用"，只看引用会全部误报）。

> **这就是门禁的盲区：**
> **`@Configuration` 被整体豁免，于是"定义了但没人注入的 Bean"是门禁看不见的死代码。**
>
> **而这类死代码比"没人调用的私有方法"更危险** —— 因为它**对应着一个可配置的开关**，给人一种"这个旋钮有用"的错觉。

**补法有两个：**

| 方向 | 做法 |
|---|---|
| **删掉** | 承认没有这两道舱壁（诚实，且减少误配） |
| **用起来** | 把 IO 类操作（拉代码、Git 平台 API）挪到 `ioExecutor`，把审查编排挪到 `reviewExecutor` |

**第二个方向才是原设计意图**（四个池的分工写在名字里），**但它需要真正去改调用点** —— 而"定义一个 Bean"比"改十个调用点"容易得多。**这就是空壳 Bean 的成因。**

> **一条经验：新增一个线程池 Bean 的正确顺序是"先把调用点改成用它，再加 Bean"** —— 反过来就会留下空壳。
>
> **同理：任何"先建设施、后接使用"的顺序，都有产生空壳的风险。** 看到 `@Configuration` 里的 Bean，**顺手 grep 一下它的名字有没有出现在别处**，是一个很值钱的习惯。

### 3.2 队列等待被算进超时：把两个数拆开

3.1 节讲了 `agent.started` 事件其实已经记了"任务真正开始"的时刻。**把提交时刻和它一起算，就能拆出排队时长。**

**一个最小改动**（不改任何签名，只在 Coordinator 里加一个 Map）：

```java
// 伪代码：在提交前记录提交时刻
Map<AgentType, Long> submittedAt = new HashMap<>();
long submitBase = System.currentTimeMillis();
futures = effectiveAgents.stream()
    .map(agent -> {
        submittedAt.put(agent.getType(), System.currentTimeMillis());
        return CompletableFuture.supplyAsync(TraceContext.wrap(() -> { ... }), agentExecutor);
    })
    .toList();

// 在超时分支里算出排队时长
} catch (TimeoutException te) {
    future.cancel(true);
    Long sub = submittedAt.get(agent.getType());
    long waited = sub == null ? 0 : System.currentTimeMillis() - sub;
    String reason = String.format("执行超时（预算 %dms；提交后已等待 %dms，其中含排队）",
            timeoutMillis, waited);
    ...
}
```

**产出的是这样一个 `reason`：**

```
执行超时（预算 300000ms；提交后已等待 300000ms，其中含排队）
```

**读者立刻能判断**：如果"提交后立即就超时了"（waited ≈ timeoutMillis 且任务体没跑），**大概率是排队**；如果任务体跑了很久（轨迹里有 `agent.started` 但没有 `agent.completed`），**是执行慢**。

**更好的版本：直接记两次时间戳**，用 `agent.started` 的存在与否来区分：

| 轨迹里有 `agent.started` 吗 | 说明 | 归因 |
|---|---|---|
| **有** | 任务开跑了，但没跑完 | **执行慢**（优化 prompt / 换模型 / 加预算） |
| **没有** | 任务从未开始 | **排队 / 被丢弃**（加容量 / 改拒绝策略） |

> **这个判据只用到了系统里已有的数据**（轨迹事件），**不需要新增任何埋点**。
>
> **这是"可观测性"的正确用法：不是加更多日志，而是把已有的信号关联起来。**

### 3.3 提交点的组合清单

**并行系统的正确性，取决于每一个"提交点"都做对了同样几件事。** 本项目有两个提交点，逐个核对：

| 检查项 | `agentExecutor`（Coordinator:447） | `webhookExecutor`（Gitea:139） |
|---|---|---|
| **有界队列** | ✅ 512 | ✅ 2000 |
| **线程命名** | ✅ `code-review-agent-N` | ✅ `code-review-webhook-N` |
| **ThreadLocal 传播** | ✅ `TraceContext.wrap` | ✅ `TraceContext.wrap` |
| **有超时** | ✅ 共享 deadline | ⚠️ **无**（审查链路内部有自己的 deadline，但 webhook 这一跳本身没有） |
| **拒绝可知** | ❌ `DiscardPolicy`（静默） | ❌ `DiscardPolicy`（静默 + 返回 accepted） |
| **有并发上限文档** | ⚠️ 有配数字，无推导依据 | ⚠️ 同上 |

**唯一两个 ❌ 都是同一个原因：`DiscardPolicy`。**

**而唯一的 ⚠️ 是同一个原因：没有"从下游反推"的依据。**

> **这张表是一个可复用的模板。** 你可以在自己的项目里，把所有 `CompletableFuture.supplyAsync/runAsync`、`executor.submit`、`@Async` 的调用点列出来，**逐列打勾** —— 缺哪一项，就是哪一类故障的入口。

## 四、避坑清单

- [ ] **不要用 `ForkJoinPool.commonPool()` 跑 IO 密集任务**：队列无界、JVM 全局共享、线程数按 CPU 定。
- [ ] **按任务性质分池（舱壁）**：收件层必须比执行层更容易成功。
- [ ] **入口层（webhook）的容量要优先于执行层** —— 入口堵住 = 整条流水线停止接收。
- [ ] **`DiscardPolicy` 的 `rejectedExecution` 是空方法** —— 覆盖它只打日志，等于静默丢弃。
- [ ] **凡"丢弃"必须回答：调用方知不知道？** 返回 200 / future 永不完成 = 静默故障。
- [ ] **最便宜的修法是 `CallerRunsPolicy`**（把排队变成调用者亲自执行，总量守恒且零丢弃）。
- [ ] **`agent-threads` 要从下游（LLM 供应商/网关配额）反推**，不要先定线程数。
- [ ] **调大线程数可能降低吞吐**：触发下游限流 → 重试 → 拥塞加剧。
- [ ] **队列容量 ≈ 可接受排队时长 × 服务速率**，并保证"排队 + 执行 < 超时预算"。
- [ ] **"执行超时"要拆成"排队 + 执行 + 重试"三个数**，否则无法归因。
- [ ] **判据**：轨迹里有 `agent.started` → 执行慢；没有 → 排队/被丢弃。
- [ ] **每个跨线程提交点都要检查 ThreadLocal 传播**（traceId / MDC / 身份 / 事务 / 安全上下文）。
- [ ] **`wrap` 要恢复现场，不要 `clear()`** —— 线程池里的线程从来不干净。
- [ ] **新增线程池 Bean 的正确顺序是"先改调用点，再加 Bean"**，否则留下空壳（本项目 `reviewExecutor` / `ioExecutor` 就是空壳）。
- [ ] **`@Configuration` 被死代码门禁豁免**，所以"定义了但没人注入的 Bean"要靠人工 grep 发现。

## 五、动手任务

> **任务一：复现"丢弃伪装成超时"。**
> 1. 写一个 `ThreadPoolExecutor`：1 个线程、队列容量 1、`DiscardPolicy`。
> 2. 提交 5 个任务（每个 `sleep(3s)`），用 `CompletableFuture` 包起来。
> 3. 用共享 deadline（比如 5 秒）逐个 `get(remaining, MS)`。
> **预期结果**：前 2 个正常完成；**后 3 个在 deadline 到时报 `TimeoutException`** —— 尽管它们从未开始执行。
> **然后**：把拒绝策略换成 `CallerRunsPolicy`，重跑。
> **预期结果**：**没有超时**，总耗时约 15s（5 × 3s 串行）—— 因为第 3/4/5 个任务由提交线程亲自执行了。
> **思考题**：这两种行为，哪个对"审查系统"更合适？（提示：审查是异步触发的，**没有"用户线程"可阻塞** → 第 3.3 节的结论是"`AbortPolicy` + 显式标降级"更合适。）
>
> **任务二：从下游配额反推线程数。**
> 1. 定义你的下游约束：LLM 网关的最大并发（比如 30）。
> 2. 用一个"最多 30 个并发"的信号量（`Semaphore`）模拟下游。
> 3. 跑 `agent-threads = 16 / 64 / 256` 三组，**统计成功数、超时数、总耗时**。
> **预期方向**：16 组——慢但都成功；64 组——出现超时（因为 34 个被信号量挡住）；256 组——**超时更多**。
> **验收标准**：你能指着数据说出"为什么 256 反而更差"。
>
> **任务三：验证 traceId 不传播。**
> 1. 在主线程 `TraceContext.set("abc")`。
> 2. 提交一个任务，在任务里打印当前线程名和 `TraceContext.get()`。
> **预期结果**：线程名变了（`code-review-agent-N`），**`traceId` 为 null**。
> 3. 用 `TraceContext.wrap(...)` 包起来再跑。
> **预期结果**：`traceId = "abc"`。
> **附加**：在任务里 `set("xyz")` 后返回，再提交第二个任务，看它看到的是 `abc` 还是 `xyz` —— **这一轮验证的是"恢复现场"而不是"清空"**。
>
> **任务四：找出你项目里所有"空壳 Bean"。**
> 1. 列出所有 `@Configuration` 类里定义的 `@Bean`。
> 2. 对每个 Bean 名，grep 一遍是否被 `@Qualifier` 或按类型注入。
> 3. 把"零使用"的列出来。
> **产出**：一份"可配置但无效"的开关清单 —— **这类开关比没有开关更危险**，因为它会让人以为配置生效了。

## 本讲小结

1. **不用 `commonPool()` 的三个理由**：队列无界、JVM 全局共享、线程数按 CPU 定（而 Agent 是 IO 密集）。
2. **四个池 = 舱壁**，但 **"入口层必须比执行层更容易成功"** 是本项目最该保住的不变式。
3. **`DiscardPolicy` + 只打日志 = 静默丢弃**。两个 ❌ 都来自它：**Agent 提交被丢 → 归因成"超时"；webhook 提交被丢 → 却返回 `accepted`**。
4. **最便宜的修法是 `CallerRunsPolicy`**（排队变亲自执行，零丢弃）；异步入口场景 `AbortPolicy` + 显式降级更合适。
5. **`agent-threads` 要从下游配额反推**，不能拍脑袋 —— **调大线程数可能降低吞吐**（触发限流 → 重试 → 拥塞）。
6. **"执行超时"里混着排队 + 执行 + 重试**，必须拆开才能归因；**判据是轨迹里有没有 `agent.started`**。
7. **每个跨线程提交点都要传播 ThreadLocal**，且 `wrap` 要**恢复**而不是 `clear()`。
8. **`reviewExecutor` / `ioExecutor` 是空壳 Bean** —— 配置项改了没效果，而 `@Configuration` 被死代码门禁豁免，没人会发现。
