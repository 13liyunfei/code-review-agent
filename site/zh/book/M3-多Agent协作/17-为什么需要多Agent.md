# 第 17 讲 · 为什么需要多 Agent

> 🎯 导读问题：**"你为什么用多 Agent？一个 Agent 不够吗？"**（这一问考的是判断力，不是技术）

<img class="mermaid-svg" src="/zh/book-assets/diag-0074.svg" alt="🎯 导读问题：&quot;你为什么用多 Agent？一个 Agent 不够吗？&quot;（这一问考的是判断力，不是技术）" />

> **图 17-0**　本讲地图：多 Agent 不是默认选项，而是一道四级判据：判断标准、失败模式、真实冲突、独立观测。任一不满足就不该拆，通过后还要认下成本翻 N 倍，以及仲裁、编排、聚合三个新问题。

## 一、痛点

第一版代码审查系统只有**一个 Agent**。

提示词大概是这样的：

```
你是一位资深工程师。请从「逻辑、安全、性能、编码规范、架构」五个维度审查以下代码变更。
请以 JSON 数组输出，每条包含 file / line / severity / title / description / suggestion。
```

跑通之后，你会依次遇到三个现象：

**现象一：什么都提到一点，什么都说不深。**

输出是这样的（真实形态）：

```json
[
  {"severity":"MAJOR","title":"存在 SQL 拼接风险","description":"建议使用参数化查询"},
  {"severity":"MINOR","title":"变量命名建议更语义化","description":"userList 可改为 activeUsers"},
  {"severity":"MAJOR","title":"循环内查询数据库可能导致 N+1","description":"建议批量查询"},
  {"severity":"MINOR","title":"缺少注释","description":"建议补充方法注释"}
]
```

每一条都对，但**每一条都像是从清单里抄的**。它没有告诉你这个改动的真正风险在哪。

**现象二：输出配比是"均衡"的，而真实风险不是。**

五个维度的发现数差不多。**但一个真实的 PR 里，五个维度的风险从来不是均等的**——有的改动全是安全问题，有的改动只有性能问题。

模型的"均衡"是它在 prompt 里看到"五个维度"之后的自然反应：**每个维度给 1-2 条，显得都照顾到了。**

**现象三（最致命）：安全发现排在风格发现后面。**

一个 JSON 数组里混着五类问题，模型自己决定排序。而它排序的依据通常是**在代码里出现的顺序**，不是严重程度。

于是一条"SQL 注入"可能被四个"缺少注释"挤到列表末尾——**评审人看到前四条就关掉了 PR 评论。**

**而你想调"安全审得严一点"时，发现自己做不到。** 提示词是一个整体，改动任何一句都可能影响其他四个维度。

## 二、原理

### 2.1 单体的五个天花板

| 天花板 | 机制 | 症状 |
|---|---|---|
| **注意力稀释** | 一个 prompt 里放了 5 个任务，模型把注意力平均分配 | 每个维度都浅（现象一） |
| **输出配比失衡** | 一个数组里 5 类混排，条数配额由模型自己定 | 严重的被淹没（现象二、三） |
| **故障耦合** | 一次调用失败 = 全部维度失败 | 一次超时，整份报告为空 |
| **上下文预算** | 5 个维度各要注入知识与历史，挤在同一个 prompt 里 | 顶爆窗口（第 14 讲） |
| **不可独立调参** | 提示词是一个整体 | 无法"只让安全更严" |

**注意第二个和第五个的关系**：因为配比由一个 prompt 决定，所以调参也只能整体调。**"不可独立调参"不是"不方便"，而是"这个系统无法针对风险分布做优化"。**

### 2.2 判据：什么时候该拆（任务正交性）

拆 Agent 不是"越多越好"。**拆错方向比不拆更糟**——你付出了 N 倍成本，换来的是 N 个各自平庸的输出。

判断标准是**任务正交性**，有三条，必须同时满足：

**判据一：判断标准不共享。**

把本项目五个维度的判据写出来：

| 维度 | 这一维度在问什么 |
|---|---|
| 逻辑 `LOGIC` | 这段代码**会不会算错**？ |
| 安全 `SECURITY` | 这段代码**会不会被利用**？ |
| 性能 `PERFORMANCE` | 这段代码**会不会慢**？ |
| 规范 `STYLE` | 这段代码**符不符合团队的写法**？ |
| 架构 `ARCHITECTURE` | 这段代码**放在这里合不合适**？ |

**五个问题各自独立**：一段代码可以"算得对但会被注入"，也可以"很安全但是 O(n²)"。**没有哪一个维度的结论能推出另一个维度的结论。**

**判据二：失败模式独立。**

安全维度超时了，逻辑维度的结论**仍然有效**。

这一条直接决定了"降级"有没有意义（第 15 讲的 `AgentResult.degraded`）。**如果五个维度绑在一次调用里，那"部分降级"在物理上就不存在**——一次调用要么成功要么失败，你没有任何颗粒度可以保留。

**判据三：存在真实冲突。**

**这是最关键、也最容易被跳过的一条。**

两个维度必须真的会给出**互相矛盾**的建议。在本项目里这是成立的：

```
同一个配置项：
  逻辑 Agent：建议加防御性空值判断（防止 NPE）
  性能 Agent：建议去掉热路径上的分支（减少每次调用的开销）
```

```
同一个方法：
  架构 Agent：这个方法职责过重，建议拆成三个
  性能 Agent：拆成三个会引入额外的对象分配，建议内联
```

**为什么这一条最重要？因为它决定"你要不要做仲裁"（第 21 讲）。**

> **如果没有真实冲突，就不需要仲裁机制。**
> **而如果不需要仲裁机制，那"拆开"只是把一个 prompt 变成了五个 prompt —— 你没有获得任何新信息，只是付了五倍的钱。**

**判据四（工程判据）：拆出来的维度必须能被独立观测。**

如果你无法回答"上个月安全维度漏了多少、性能维度误报了多少"，那么拆开之后你仍然无法优化任何东西。

**这一条在实现上对应的是：每个 Agent 的 `AgentResult` 里必须携带 `agentType`。**

### 2.3 反面：什么情况不该拆

| 情形 | 为什么不该拆 |
|---|---|
| **两个"Agent"的结论永远一致** | 它们是同一个 Agent 的两段提示词 |
| **每个 Agent 的 prompt 里都要写"你也要顺便看看安全"** | 说明安全没被真正拆出去 |
| **拆完后每个 Agent 只处理 3 行代码** | 拆的单位太小了，调度和聚合成本超过收益 |
| **只是为了"看起来架构更高级"** | 这是最坏的理由 |

**第二种情形值得单独说。** 一个很常见的伪拆分是：

```
Agent A 的 prompt：你是逻辑审查专家……【另外，如果发现安全问题也要指出】
Agent B 的 prompt：你是安全审查专家……【另外，如果发现逻辑问题也要指出】
```

**这种"互相兜底"的写法让所有 Agent 的能力集合重新变成同一个。** 结果就是：同一个问题被报 5 遍（聚合阶段去重掉），而每个 Agent 的 prompt 都变长了（注意力再稀释一次）。

### 2.4 拆的代价：诚实的账

**买到了什么：**

| 收益 | 实现方式 |
|---|---|
| 独立调参 | 每个维度一套 prompt + 一套规则（第 13 讲） |
| 独立降级 | 一个维度超时不影响其他（第 15 讲） |
| 独立观测 | 每个 `AgentResult` 带 `agentType` |
| 可扩展 | 业务方加"支付合规审查"不用改内置 5 个（第 19 讲） |
| 可仲裁 | 冲突有明确的"谁说了算"（第 21 讲） |

**付出了什么：**

| 代价 | 具体 |
|---|---|
| **成本 ×N** | N 个 Agent = N 次（或更多）LLM 调用 |
| **新增三个问题** | 谁说了算（仲裁）、怎么并行（编排）、结果怎么合（聚合） |
| **调试复杂度上升** | 一次审查涉及 5 条独立链路 |
| **一致性风险** | 五个 Agent 对"什么算 Major"的理解会漂移 |

**最后一条是最隐蔽的。** 五个 Agent 各自判断严重级别，那么：

- 安全 Agent 觉得"任何注入风险都是 BLOCKER"；
- 性能 Agent 觉得"慢一点只是 MAJOR"；
- 规范 Agent 觉得"缺注释也是 MINOR，不是 INFO"。

**这些口径没有任何地方强制统一**，除非你显式设计它（第 21 讲的仲裁、第 22 讲的校准都在处理这件事）。

**诚实的账翻成数字才扎心。** 用"约 xx 元 / 百万 token"的示意口径（不是精确定价），假设一次审查里每个 Agent 的输入上下文（prompt + diff + 知识注入）稳定在 **3000 token**、输出约 **600 token**；取一个中等模型，输入约 **¥1 / 百万 token**、输出约 **¥3 / 百万 token**：

> **单 Agent 一次调用：**
> 输入 3000 × ¥1/1M = ¥0.0030；输出 600 × ¥3/1M = ¥0.0018
> 合计 ≈ **¥0.0048 / 次**
>
> **拆成 5 个 Agent（输出各自 600）：**
> 5 × (3000 × ¥1/1M + 600 × ¥3/1M) = 5 × ¥0.0048 ≈ **¥0.024 / 次**
>
> **折算到一台每天审 1000 个 PR 的引擎：**
> 单体 ≈ ¥4.8 / 天；5 Agent ≈ ¥24 / 天；按 22 个工作日 ≈ **¥106 / 月 vs ¥528 / 月**——差出四百多块，这就是"拆"的真实价格。

> **注意增量不是"线性"，是"每个 Agent 都要重吃一遍公共上下文"**：5 个 Agent 各自注入同一份 diff、同一份影响面、同一份 base prompt，成本从约 5 倍起跳，还会被"每个维度都要场景化注入知识"再放大（第 23 讲）。**拆之前这笔账不记，拆完就是被动续费。**

**工程判据：** **拆与不拆，先把成本账拍在桌上——拆分后单次审查的 token 预算必须允许约 ×K（K≈Agent 数）的放大；任何纯靠拆换来的"更均衡"，若没有『必须独立降级 / 必须独立观测』两条之一撑腰，就不在预算内，不拆。** 换句话说：**成本 ×N 不是"能接受"的事，而是要用判据一~四逐条换来的、明码标价的投入。**

> **模块三剩下 7 讲，全部在处理拆开之后新增的这三个问题。**
>
> **这一讲真正的价值是：在你拆之前，先确认你真的需要拆。**

### 2.5 前沿深挖：多 Agent 的性价比，业界是拿"实测"拍的板

要不要拆，业界也在用同一本"代价换上限"的账。2025 年 **Anthropic 发布的多 Agent 研究系统**就是一例：在软件工程复杂任务上，**多 Agent 协作把任务通过率从单 Agent 的约 50% 提到 65~70%，代价是约 15 倍的 token 消耗**——注意这不只是 5 倍，因为还要算规划、状态汇总、多轮重试的点数。**我记得的是近似数字，引用前请以原报告为准**，但它给出的量级关系是稳定的：**提升是"十几个点"，成本是"一个数量级"。**

拿这个量级对照本讲的四条判据，决策就清楚了：

- **通过率是跑基线测出来的，不是靠"多 Agent 理应更聪明"推出来的**——第 17 讲"动手任务"让你做的单 Agent vs 多 Agent 对照，正是这套实验的缩小版；
- **只有当任务靠一个 Agent 确实上不去（判据一~四都过）时，那 15 倍才花得值**；否则你只是买了个"看起来更均衡"的心理安慰；
- Anthropic 同期还强调**逐 Agent 单独观测 + 精细路由能显著改善**——这就是判断据四（独立观测）的同义词。

> **结论不变：多 Agent 上限更高但单价更贵；用不用，取决于你能否用单体够到那个上限。**

## 三、代码

### 3.1 七个 Agent 类型，一个枚举

<img class="mermaid-svg" src="/zh/book-assets/diag-0075.svg" alt="### 3.1 七个 Agent 类型，一个枚举" />

> **图 17-1**　`AgentType` 的七值枚举。**五个领域角色**（逻辑/安全/性能/规范/架构）是系统拆出来的专业审查维度，**两个拓扑角色**（CUSTOM / COORDINATOR）是架构层面的。CUSTOM 证明"正交维度"这个抽象是开放的；COORDINATOR 则是个值得警惕的信号——它永远不会出现在任何 `Finding` 里，意味着枚举的值域大于实际使用值域。

**注意这不是 5 个值，是 7 个。** 多出来的两个是：

- **`CUSTOM`** —— 业务方在后管声明的审查维度（第 19 讲详述）。它证明"正交维度"这个抽象是**开放的**：系统没有把维度写死在 5 个里。
- **`COORDINATOR`** —— 协调者。**它不是一个"审查 Agent"**：`Coordinator` 是另一个接口，没有 `ReviewAgent` 实现。

**这里有一个值得学的取舍：把"拓扑角色"和"领域角色"放进了同一个枚举。**

| | 好处 | 代价 |
|---|---|---|
| 同一个枚举 | 报告里统一用 `AgentType` 标识"这条发现是谁出的"；序列化只用一套类型 | **`COORDINATOR` 永远不会出现在任何 `Finding` 里** —— 枚举值域大于实际使用值域 |

**"枚举值域大于实际使用值域"是一类需要警惕的信号**：它意味着在某个 `switch (agentType)` 里，一定有分支是永远不会被走到的。**读代码时可以顺手 grep 一下 `COORDINATOR` 的使用点，判断它是"有意的类型声明"还是"没人清理的遗留"。**

### 3.2 接口的注释把架构决策写出来了

<img class="mermaid-svg" src="/zh/book-assets/diag-0076.svg" alt="### 3.2 接口的注释把架构决策写出来了" />

> **图 17-2**　星型拓扑的两个核心接口。`Coordinator` 是中央调度节点，`ReviewAgent` 是专业审查节点——一个 Coordinator 并行调度 N 个 ReviewAgent。**两处注释措辞一致地说"星型拓扑"**，这不是废话，它是一个已被决策过的架构选择：想改拓扑的人会先看到这段注释，被迫思考"为什么当初这么选"。

同一个决策在三个地方（`AgentType` / `ReviewAgent` / `Coordinator`）措辞一致地出现。

这一点不是废话，它有两个实际价值：

1. **对读者（包括三个月后的你自己）**：这是一个**已被决策过的架构选择**，不是"写到最后自然长成这样"。想改拓扑的人会先看到这段注释，然后被迫思考"为什么当初这么选"。
2. **对面试**：这是一个可以**直接引用**的架构判断依据。

**下一讲专门回答：为什么是星型，而不是流水线。**

### 2.6 多 Agent 的工业界账：成本与收益怎么量化

本讲 §2.4 把"拆的代价"列成了一笔诚实的账（延迟、token、协调成本）。本节把它变成一个**能算的式子**——因为在工业界，"多 Agent 到底贵多少"这个问题是**拿实测拍的板**，不是靠感觉。而算清楚之后，会出现一个和直觉相反的结论。

先把成本拆成三段，它们的量纲不同，所以不能合成一个数：

<img class="mermaid-svg" src="/zh/book-assets/diag-0077.svg" alt="先把成本拆成三段，它们的量纲不同，所以不能合成一个数：" />

> **图 17-3**　拆分的三段成本，与那个最容易被漏掉的第四段。**这张图要给出的新结论是：并行拆分不改变超时预算，它只是把同一份预算分给更多人。** ①②③ 三段在讲拆分"花了多少"；而下面那条从 ② 引出的线在讲拆分"改变了什么"——**共享 deadline 的语义是"整批任务的总预算"，不是"每个任务的预算"**（本项目 `timeoutMillis` 默认 300000ms，`application.yml:128`）。于是 N 越大，单个任务能拿到的有效余量越小，**而这不是调度问题，是预算问题**。

**第一段与第二段的不对称，是本讲最实用的一条账。** 第一段（固定开销）随 N 线性增长，但它是一个**与输入无关的常数**：本项目五个内置提示词模板 973–1069 字节、合计 5185 字节（复算：`find src/main/resources/prompts -type f | wc -l` = 5；对每个文件取 `wc -c`）。这个量级在 128K 上下文里几乎可以忽略。

**真正被乘的是第二段**：同一份 diff 被复制进 N 个提示词。而它的规模不由模板决定，由**截断策略**决定——

```text
  prompt:
    diff-char-budget: ${REVIEW_DIFF_CHAR_BUDGET:-1}
```

`code-review-agent/src/main/resources/application.yml:131-132`

**默认值是 `-1`，即"不截断、全量塞入"**（上一行注释逐字写着 `<0 = 不截断`）。⇒ **默认配置下，一次审查把同一份完整 diff 送进 5 个 Agent 的提示词**。这个默认在基座 A 上是**对的**（团队一天几十个 PR，diff 以代码片段为主，为了省 token 而截断会直接损失检出率）；但它在基座 B 上会立刻失效：

> **推演**：单次任务 fan-out 到 N=5 个子 Agent，每份输入（提示词 + 全量上下文）平均 8,000 token，则单次任务输入侧 = `5 × 8,000 = 40,000` token。若峰值 `20,000` 任务/分钟，输入侧吞吐 = `20,000 × 40,000 = 8×10⁸` token/分钟 ≈ `1.33×10⁷` token/s（假设：N=5、单份输入 8,000 token、峰值 20,000 任务/分钟；N=5 来自本项目内置 Agent 数，基座 A 的并发上限见 `application.yml:120` 的 `agent-threads: 64`）。**同一个"不截断"的默认值，在两个基座上一个是正确取舍、一个是成本事故。**

**而第三段之外还有第四段——共享 deadline。** 它的实现只有两行：

```text
        long deadline = System.currentTimeMillis() + Math.max(1L, timeoutMillis);
```

`code-review-agent/src/main/java/com/codereview/agent/core/coordinator/impl/CompletableFutureCoordinator.java:550`

```text
            long remaining = Math.max(deadline - System.currentTimeMillis(), 1L);
```

`code-review-agent/src/main/java/com/codereview/agent/core/coordinator/impl/CompletableFutureCoordinator.java:555`

`deadline` 是**在 fan-out 之前算好的一个绝对时刻**，而每个 Agent 拿到的等待时长都是 `deadline - now`。关键在于**取结果是串行的**（`for (int i = 0; i < futures.size(); i++)`，`:479`），所以第 i 个 Agent 拿到的余量取决于"前面已经花掉多少"。**注意这里说的是预算而不是调度**：5 个 Future 是同时提交、同时开跑的（`:446-458`）；但如果排在第 1 位的 Agent 跑了 900ms 还没回来，那么轮到第 2 位时，即使它半小时前就完成了，`get(remaining)` 里的 `remaining` 也已经只剩 100ms。

> **这条结论可以机械验证，不必凭推理接受**：把 `timeoutMillis` 调成 1000，让排在第 1 位的 Agent 睡 900ms、其余秒回，然后打印每个 Agent 的 `remaining`——你会看到**只有第一个拿到接近 1000ms，后面的都被前一个吃掉了**。测试可显式调小超时（`setTimeoutMillis`，`:231-233`），所以这个实验是**成本为零**的。

**工业界那一边，本节要看的不是"框架怎么帮你并行"，而是"并行度是谁决定的"。** langchain4j 的 agentic 模块把并行编排做成了一个接口，而这个接口只有一个方法：

```text
    ParallelAgentService<T> executor(Executor executor);
```

`langchain4j/langchain4j-agentic/src/main/java/dev/langchain4j/agentic/workflow/ParallelAgentService.java:8`

**它注进去的是一个 `Executor`，不是一个线程数。** 这句话的信息量在于：**框架没有自带线程池，也没有规定并发度**——"多少人一起跑"完全由使用者的 `Executor` 决定，于是"预算怎么分"自然也由使用者承担。这正好解释了本书为什么在 `ProductionExecutorConfig` 里手工定义四个有界池而不是依赖默认值（第 20 讲会详细算这四个池的尺寸），也解释了为什么 langchain4j 需要你在 `ParallelAgentService` 上显式传一个 `Executor` 进去。

顺带一个可复算的观察：在 `_research/spring-ai` 全树对 `multi-agent|supervisor|agentic` 做 `grep -r`，`.java` 文件命中 **0**（复算：`grep -rE 'multi-agent|multiagent|supervisor|agentic' --include='*.java' _research/spring-ai | wc -l`）。⇒ **"多 Agent 编排"目前在 Java 生态里还不是两个主流框架的共识**，它更像是一组各家自己实现的设计选择。这不是"spring-ai 不行"，而是一个选型事实：**要抄"最佳实践"，你抄到的是某个具体实现，而不是一个标准。**

### 2.7 拆分的验收：什么算"拆对了"

拆是"为了更好"，但拆完怎么知道更好？本项目给出的答案不是"感觉报告更全了"，而是**三个都能从一次审查的运行数据里直接读出来的判据**。

<img class="mermaid-svg" src="/zh/book-assets/diag-0078.svg" alt="拆是&quot;为了更好&quot;，但拆完怎么知道更好？本项目给出的答案不是&quot;感觉报告更全了&quot;，而是三个都能从一次审查的运行数据里直接读出来的判据。" />

> **图 17-4**　三个可观测的拆分判据，与每一个的两侧解释。**这张图的用法是"三判据同时成立才算拆对"**：任一判据单独成立都可能被反向解释（比如 `overridden` 长期为空）。**而三条判据的共同点是：它们都不需要你相信任何人的主观判断，只需要把一次运行的日志读出来。**

**判据①：`supports()` 曾经返回过 false 吗？** 依据是本项目 `ReviewAgent` 接口上那段注释——它逐字写着"本方法只做「内容相关性」准入…返回 false 的 Agent 由 `Coordinator` 在调度前剔除，不会产生「降级」语义，报告维度相应减少"（`ReviewAgent.java:41-43`）。

而这里有一个**可数的事实**：**5 个内置 Agent 里只有 4 个覆写 `supports()`**，

```text
    public boolean supports(List<CodeDiff> diffs, ReviewContext ctx) {
```

`code-review-agent/src/main/java/com/codereview/agent/core/agent/impl/ArchitectureAgent.java:41`

（`LogicAgent.java:41` / `PerformanceAgent.java:41` / `StyleAgent.java:41` 同样各有一处；复算：`grep -rn "boolean supports(" src/main/java/com/codereview/agent/core/agent/ | wc -l` 得 5，其中 1 处是接口上的 `default`）。**而 `SecurityAgent` 不覆写** —— 这不是漏了一处，而是**语义决定**：安全审查对"任意内容都有价值"，所以它不能缺席（讲稿 §2.2 的论点）。⇒ **"从不缺席"这个行为本身就写出了这个 Agent 的定位**；反过来，如果**所有** Agent 都从不返回 false，那"准入"就是一段死代码，而"维度拆分"也就只是个命名。

**判据②：`overridden` 里有东西吗？** 冲突判定需要四个条件同时为真：不同 Agent 类型、同一文件、行区间重叠、建议文本不同（`ArbitrationPolicy.isConflict`，`ArbitrationPolicy.java:54-67`）。**`overridden` 长期为空有两种完全相反的解释**：要么维度真的正交（好），要么**这两个维度审的根本不是同一片代码**（坏——它们本就不该被放进同一份报告一起比较）。**区分二者的办法是看"同一文件是否被多个 Agent 各自报了发现"**：如果多个 Agent 报同一个文件但从不构成冲突，那是正交；如果它们连文件都不重叠，那"冲突判定"这套逻辑就是永远走不到的死路。

**判据③：扇入阶段实际减了几条？** `ReportGenerator.aggregate` 的减条发生在三步，各自独立可测：去重（`:83-102`）、仲裁（`:106-133`）、抑制（`:142-153`）。

> **判据是"减条的原因分布"，不是"减条的总数"。** 如果**去重**减掉的比留下的还多，说明 Agent 的分工没有真的分工——它们在重复报同一件事；如果**抑制**减掉的最多，说明问题不在 Agent 侧而在"误报反馈"侧；如果三步都不减，说明这次 PR 本身就是干净的，**不能拿它当"拆分有效"的证据**。

**这三条判据的共同性质值得单独说一遍**：它们全是**结构性判据，不是质量判据**。"拆对了"在这里的定义是"每个维度都不可替代、且彼此不重叠"——这是一个**可以用集合运算回答的问题**，而**不需要标注数据、不需要人工评分**。这正好对上本讲 §2.5 那条"业界是拿实测拍的板"的说法：实测不一定是人工打分，**很多时候只是把运行数据取出来做一次计数**。

### 2.8 搬到你自己系统：拆分决策树

前面几节把"该不该拆"讲成了一道四级判据（本讲 `图 17-0`），又给成本与验收各加了一层。本节把三层合成一棵**能照着走的决策树**——它的每一个分叉都对应本节某一处可观测的量。

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| 并行度由 `ParallelAgentService.executor(Executor)` 注入（`ParallelAgentService.java:8`） | 你的并发度是谁定的？框架默认、配置、还是调用方？它有没有和下游容量对齐过？ |
| 共享 deadline 是整批预算（`CompletableFutureCoordinator.java:550`） | 你的超时是"每个任务一份"还是"整批一份"？若是整批，排在后面的任务拿什么保证？ |
| 输入默认不截断（`diff-char-budget: -1`，`application.yml:132`） | 你的输入复制了几份？截断策略在两个量级下是同一个默认值吗？ |
| `supports()` 是准入面（`ReviewAgent.java:48`） | 你的每个子 Agent 有没有"不该来的时候"？如果答案是没有，凭什么说它是一个独立维度？ |
| `overridden` 是冲突审计（`ArbitrationPolicy.java:54`） | 你的仲裁记录里有没有冲突？没有的话，是正交还是根本没交集？ |
| 去重 / 仲裁 / 抑制三步各自可测（`ReportGenerator.java:83/106/142`） | 你的扇入阶段减条的原因分布是什么？哪一步减得最多？ |

**搬到你自己系统**，五步：

1. **先把输入的复制次数写下来**：找出"同一份输入被送进几个 Agent"，再乘上单份输入的 token 估算。**这一步通常能直接砍掉一批"看起来很酷但成本不可摊薄"的拆分方案**。
2. **确认你的超时语义**：把"每个任务一份超时"与"整批一份超时"两种写法的行为都推演一遍，选一个然后**把结论写进注释**。**如果选整批，必须同时回答"排在最后的任务怎么活"**（本项目的答案是：所有 Future 同时开跑，所以只有"前面慢"才会挤占后面）。
3. **给每个子 Agent 找出它的"不该来的时候"**，并把判据写成一行代码（本项目是 `supports()`）。**找不到的时候，就说明这个维度还需要再想**——或者它其实是一个"过滤器"而不是一个"Agent"。
4. **把三条验收判据做成一次运行的输出**，而不是等出问题再回头查。判据的形态最好是**计数**（`supports` 为 false 的次数、`overridden` 条数、三步各自减条数），因为计数能进看板、能报警、能做趋势。
5. **在两个量级上各算一遍第二段成本**（输入 × N），如果结论相反，就把这个参数变成**可配置项**而不是常量——本项目的 `diff-char-budget` 正是这个形态（默认 `-1`，需要时开成具体值）。

**判据**：**"该拆就拆"这句话在工程上不成立；成立的版本是"我能说出每个子 Agent 的不该来的时候，且能证明它带来的新增覆盖大于它复制的输入成本"。** 说不出前一半，你拆出来的就不是维度而是**命名**；证不出后一半，你拆出来的就是**更贵的一次调用**。

## 四、避坑清单

- [ ] **拆之前先回答"这两个维度会不会给出互相矛盾的建议"。** 不会冲突 → 不需要拆。
- [ ] **拆出来的维度必须能被独立观测**（能单独回答"上个月这个维度漏了多少"）。
- [ ] **不要用"拆 Agent"解决"prompt 写得不好"** —— 那是第 13 讲的问题。
- [ ] **警惕"每个 Agent 都顺便看看安全"** —— 所有 Agent 的能力集合重新相同，等于没拆。
- [ ] **拆完必须同步建立"一致性约束"**（什么算 BLOCKER / MAJOR），否则五个 Agent 的分级口径会漂移。
- [ ] **枚举里出现"不会产出结果的值"（如 `COORDINATOR`）要留意** —— 条件分支里出现它往往是 bug。
- [ ] **拆的代价要写进成本模型**：N 个 Agent 意味着 N 倍的 token 预算（模块五要算这笔账）。
- [ ] **"部分可用"是拆的收益，前提是每个 Agent 有独立的失败边界**（`AgentResult` 级别的降级）。
- [ ] **别把"并行"理解成"每个 Agent 都有一份自己的超时预算"。** 本项目是在 fan-out **之前**算好一个绝对 `deadline`，每个 Agent 的兜底等待都是 `deadline - now`；取结果又是按顺序 `get(remaining)`。**排在第 1 位的 Agent 慢下来，会把后面所有人的余量一起吃掉**——而 5 个 Future 确实是同时开跑的，所以这个现象在"并发度检查"里永远看不出来。（§2.6）
- [ ] **别用"N 个一起跑所以更快"当拆分理由。** 并行不改变总预算，只是把同一份预算分给更多人；**N 越大，单个任务能拿到的有效余量越小**。真正随 N 变好的是"覆盖率"，不是"时延"。（§2.6）
- [ ] **别忘了量"输入被复制了几份"。** 同一份 diff 进 N 个提示词，而它的规模由截断策略决定——本项目默认 `diff-char-budget: -1`（不截断）。**同一个"不截断"默认值，在中低 QPS 的 B 端是对的取舍，在千万 DAU 上是成本事故。**（§2.6）
- [ ] **别让"准入"（`supports()`）成为死代码。** 如果一个子 Agent 从不返回 false，它就没有"不该来的时候"——那它作为一个**独立维度**的资格是没被证明的。反过来说，"从不缺席"如果是有意为之（安全审查），就该像本项目一样把它写在注释里，而不是让人猜。（§2.7）
- [ ] **别把 `overridden` 长期为空当成"维度正交"的证据。** 空有两种相反的解释：真的正交，或者两个维度审的根本不是同一片代码。**区分办法是看"同一文件是否被多个 Agent 各报过发现"**，而不是看冲突数。（§2.7）
- [ ] **别拿"扇入减了几条"的总数当验收指标。** 要看去重 / 仲裁 / 抑制**三步各自**减了多少：去重减得比留下的多，说明 Agent 在重复报同一件事（分工失败）；三步都不减，说明这次 PR 本身就干净——**那不是"拆分有效"的证据**。（§2.7）

## 五、动手任务

> **任务：用一个真实 PR 做对照实验。**
>
> **步骤**：
> 1. 写一个**单 Agent** prompt：把 5 个维度写进一个 prompt，要求输出 JSON 数组。
> 2. 挑 3 个真实 PR：一个纯文档改动、一个单文件小改动、一个跨 5 文件的中等改动。
> 3. 记录三个数字：**总发现数 / 各维度条数分布 / 你自己判定"这条真的重要"的条数**。
> 4. 换成 5 个 Agent（本项目现成实现），跑同样 3 个 PR，记录同样三个数字。
>
> **预期方向**（刻意不给"预期数字"——数字取决于你的模型和 PR）：
> - 单 Agent 的发现数**更少**；
> - 单 Agent 的维度分布**更均匀**（这正是"配额"现象）；
> - 单 Agent 里"真的重要"的**占比更低**。
>
> **重要**：**不要为了让对照"更好看"而编造数字。** 如果你跑出来差异不明显，那是一个**有价值的结论**——说明你的任务结构不需要拆。
>
> **附加思考题**：把单 Agent 版本的 prompt 改成"只审安全"，再跑一遍。你会发现**单维度 prompt 的效果接近甚至超过多 Agent**。这一轮对照才是"拆"的真正收益所在——**不是"多 Agent 更聪明"，而是"每个 Agent 的 prompt 更专注"。**

## 本讲小结

1. 单体的天花板有五个：**注意力稀释、输出配比失衡、故障耦合、上下文预算、不可独立调参**。
2. 拆的判据是**任务正交性**：判断标准独立 + 失败模式独立 + **存在真实冲突** + 可独立观测。
3. 第三条（存在真实冲突）最容易被跳过，而**它决定了你有没有必要做仲裁机制**。
4. 反面的伪拆分是"每个 Agent 都顺便看看别的维度"——能力集合重新重合，等于没拆。
5. 拆的代价是**成本 ×N**，以及新增三个问题：**仲裁、编排、聚合**——这就是模块三剩下的全部内容。
6. 本项目把正交维度固化成 `AgentType` 枚举，并**把"星型拓扑"显式写进三处注释**。
