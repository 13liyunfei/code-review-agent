> **图 18-0**　本讲地图：聚合是五步流程：降级收集、去重、仲裁、抑制、分级统计，每步减条的理由不同。权重只有序有意义，按后果是否可逆排序；抑制若排在仲裁之后，胜者被抑制、败者被移除＝双输漏报。

## 一、痛点

五个 Agent 并行跑完了，你有五份 `List<Finding>`。**把它们 addAll 到一起，是这一讲的全部反面教材。**

**故障一：同一个问题被报五遍。**

```
[LOGIC]      第 42 行：存在空指针风险
[SECURITY]   第 42 行：存在空指针风险
[PERFORMANCE] 第 42 行：存在空指针风险
```

**因为五个 Agent 互不通信（第 15 讲），它们必然重复。** 而 PR 评论区会出现三条一模一样的建议——**评审人会觉得这个系统很蠢。**

**故障二：两个 Agent 的建议相反，报告里两条并排出现。**

```
[ARCHITECTURE] 第 88 行：这个方法职责过重，建议拆成三个
[PERFORMANCE]  第 88 行：拆成三个会引入额外对象分配，建议内联
```

**报告把两个互相矛盾的结论并列展示，等于把决策成本推给了评审人** —— 而他本来指望这个系统帮他决策。

**故障三：已经确认过的误报，每周都重新出现。**

上周有人点了"这是误报"。这周同样的 `ruleId` 又出现在报告里。**"确认误报"这个动作看起来没有任何效果。**

**故障四（最隐蔽，也最严重）：两条发现同时消失了。**

这是**故障二和故障三叠加**之后的结果：


<img class="mermaid-svg" src="/zh/book-assets/diag-0046.svg" alt="这是故障二和故障三叠加之后的结果：" />

> **图 18-1**　两次"各自正确"的处置，叠加出一次静默漏报。**被抑制的那条本就不该算数，被它挤掉的那条却是有效的**——而四个环节的日志全是正常的。

**两条都没了。** 一条被"仲裁"挤掉，另一条被"抑制"拿掉。

**而报告里读者看到的是**："第 42 行——无问题"。

**它的危险在于：被抑制的那条本来就是"人类说的不算数"，而被它挤掉的那条是有效的。** 于是**系统静默地漏报了一个真实问题**，而且**所有环节的日志都是正常的**（仲裁成功、抑制成功、没有降级、没有异常）。

**四个故障，指向同一件事：聚合不是"合并列表"，它是一套有顺序的、每一步都在做取舍的决策流程。**

## 二、原理

### 2.1 五步流程，以及为什么顺序不能换

```java
// core/report/ReportGenerator.java:63-164（结构）
public ReviewReport aggregate(long prId, String repo, List<AgentResult> results,
                              FeedbackStore feedbackStore, String runId, long durationMs,
                              String teamId, List<AgentDegradation> infraDegradations) {
    // 0. 降级收集
    // 1. 按 (文件 @ 行区间 # 规则) 去重
    // 2. 优先级冲突仲裁
    // 3. 误报抑制
    // 4. 分级统计
}
```

| 步骤 | 做什么 | 为什么在这个位置 |
|---|---|---|
| **0. 降级收集** | 把 `degraded` 的 Agent 与基础设施级降级汇总 | **必须在最前**：它和 findings 无关，**无论有没有发现都要产出** |
| **1. 去重** | 同 `dedupKey` 只留"更严重 或 同级别更高置信度"的 | **必须在仲裁前**：仲裁是 O(n²) 两两比较，**去重后比较次数显著减少** |
| **2. 仲裁** | 冲突的对子里按权重留一个 | 去重解决"同一个问题"，仲裁解决"**不同问题但互相矛盾**" |
| **3. 误报抑制** | 命中人类反馈的移入 `suppressed` | ← **这一步的位置有问题，见 2.5** |
| **4. 分级统计** | 按 `Severity` 统计**未被抑制**的 | **必须在最后**：统计口径 = 最终对外呈现的集合 |

**注意第 4 步的注释：**

```java
// 4. 分级统计（仅保留未被抑制的发现）
Map<Severity, Long> severityCount = new EnumMap<>(Severity.class);
for (Severity s : Severity.values()) {
    severityCount.put(s, kept.stream().filter(f -> f.severity() == s).count());
}
```

**"仅保留未被抑制的发现"** —— 这个口径选择很重要：

> **统计口径必须等于"用户看到的"，而不是"系统算出来的"。**
>
> 反例（很多系统会这么写）：统计**所有**发现的级别分布（包括抑制掉的）。结果报告头写着"BLOCKER 3 条"，而正文里一条都没有 —— **读者会怀疑报告是错的。**
>
> **一个可复用的原则：任何"小计/汇总"的口径，都要和它下面展示的明细严格一致。**

### 2.2 去重键：**故意不含 `agentType`**

```java
// core/model/Finding.java:38-40
/**
 * 生成去重键：同一文件、同一行区间、同一规则视为同一问题。
 *
 * @return 去重键字符串
 */
public String dedupKey() {
    return file + "@" + lineStart + "-" + lineEnd + "#" + ruleId;
}
```

**注意这个键里没有 `agentType`。**

**这是一个刻意的设计**：如果两个 Agent 报了**同一个 `ruleId`、同一个位置**，那它们是**同一个问题**，应该合并。

**这就解释了去重为什么是"跨 Agent"的**：

> **星型拓扑下 Agent 互不通信（第 15 讲），必然重复报同一个问题。**
> **去重就是那个"补偿机制"** —— 它替 Agent 完成了"我不用报，他已经报了"这件事。

**"保留哪个"的规则：**

```java
// core/report/ReportGenerator.java:95-99
boolean replace = f.severity().isMoreSevereThan(existing.severity())
        || (f.severity() == existing.severity() && f.confidence() > existing.confidence());
if (replace) {
    merged.put(key, f);
}
```

**三级优先：严重级别 → 置信度 → 先到者。** 注意最后一级是**隐式**的（`replace` 为 false 时保留先到的），**这意味着"哪个 Agent 先返回"会影响保留哪一条** —— 但因为前两级都是"客观的"，只有在"同级别、同置信度"时才会体现，**影响仅限于展示文案（title/description）的差异。**

### 2.3 冲突判定的三个必要条件

```java
// core/report/ArbitrationPolicy.java:42-67
/**
 * 判断两条发现是否构成"冲突"，需同时满足：
 * <ol>
 *   <li>来自<b>不同</b> Agent 类型；</li>
 *   <li>位于<b>同一文件</b>且行区间<b>重叠</b>；</li>
 *   <li>修复<b>建议文本不同</b>（语义冲突，如"内联" vs "拆函数"）。</li>
 * </ol>
 */
public static boolean isConflict(Finding a, Finding b) {
    if (a == b || a.agentType() == b.agentType()) {
        return false;
    }
    if (!a.file().equals(b.file())) {
        return false;
    }
    if (!linesOverlap(a, b)) {
        return false;
    }
    String sa = normalize(a.suggestion());
    String sb = normalize(b.suggestion());
    return !sa.equals(sb);
}
```

**三个条件，每一个都有具体的理由：**

**① 不同 Agent 类型** —— 同一个 Agent 内部的两条建议不算"冲突"，那是它自己的输出（去重已经处理了同 `ruleId` 的情况）。

**② 同一文件 + 行区间重叠** —— 不同位置的建议不冲突（比如"第 10 行拆函数"和"第 88 行内联"是可以共存的）。

`linesOverlap` 里有一个必须注意的分支：

```java
// core/report/ArbitrationPolicy.java:69-80
/**
 * 行区间重叠判定（lineStart=0 视为"非具体行"，不参与精准重叠，视为不冲突）。
 */
private static boolean linesOverlap(Finding a, Finding b) {
    if (a.lineStart() <= 0 || b.lineStart() <= 0) {
        // 非具体行：仅当两者都在非具体行且同一文件才视为重叠（极少触发）
        return a.lineStart() <= 0 && b.lineStart() <= 0;
    }
    ...
}
```

**`lineStart = 0` 是"文件级发现"（没有具体行）** —— 例如 `SecurityAgent` 产出的"这个文件命中注入信号，已隔离"（`:148-151`，`line(0)`）。

**两条文件级发现会被判为"重叠"**（都在 `lineStart=0`），**于是它们可能被仲裁掉一条。** 注释也承认了这一点（"极少触发"）——**但它不是"极少"，而是"只要同一个文件上有两条不同 Agent 的文件级发现，就必然触发"。**

**③ 建议文本不同** —— 这一条是**最容易反直觉**的。

```java
String sa = normalize(a.suggestion());
String sb = normalize(b.suggestion());
return !sa.equals(sb);
```

**"建议相同 → 不算冲突"。**

**逻辑上说得通**（两个 Agent 建议一样，那就没冲突）。**但它有一个副作用：**

```
第 42 行：
  [SECURITY] ruleId=SEC-001  建议：加非空判断
  [LOGIC]    ruleId=LOG-007  建议：加非空判断      ← 建议文本完全相同

去重：dedupKey 不同（ruleId 不同）→ 不去重
仲裁：isConflict 返回 false（建议相同）→ 不仲裁

结果：报告里出现两条完全相同的建议，来自不同 Agent。
```

**这属于"表现形式不冲突，但内容完全重复"** —— 严格来说这不是 bug（两条发现确实是不同规则命中的），**但它违反了"读者看到的是去重后的结论"这个预期。**

**补法**：把 `dedupKey` 或仲裁判定增加一个"建议归一后相同则合并"的档位。**代价是可能误合并两条真的不同的发现**（比如两条都是"建议加日志"，但针对不同的问题）。

> **这里体现的是一个通用取舍：去重的粒度越粗，报告越干净，越可能误合并；粒度越细，越完整，越可能重复。**
> **本项目选择了"细"** —— 宁可重复，不愿误合并。**因为"漏掉一条真的问题"比"多显示一条重复"严重得多。**
>
> **这个偏向可以推广：在"漏报"和"噪声"之间，审查系统应该偏向前者（宁可多报）。** 这也解释了第 19 讲为什么要有"分级 Profile"来单独处理噪声，而不是靠聚合阶段粗暴合并。

### 2.4 权重：只有"序"是有意义的

```java
// core/report/ArbitrationPolicy.java:20-27
/** 各 Agent 类型的冲突仲裁优先级权重（数值越大越优先）。 */
private static final Map<AgentType, Integer> PRIORITY = Map.of(
        AgentType.SECURITY, 100,
        AgentType.LOGIC, 90,
        AgentType.PERFORMANCE, 70,
        AgentType.ARCHITECTURE, 60,
        AgentType.STYLE, 10
);
```

**100 / 90 / 70 / 60 / 10 —— 这些数字本身没有数学含义。** 换成 5/4/3/2/1 效果完全一样。**重要的是序：**

```
安全 > 逻辑 > 性能 > 架构 > 风格
```

**这个序的依据是什么？"修复的紧迫性"：**

| 维度 | 不修的后果 | 可逆性 |
|---|---|---|
| **安全** | 被利用、数据泄露 | **不可逆**（数据出去了就回不来） |
| **逻辑** | 功能错、算错账 | 部分可逆（可回滚） |
| **性能** | 慢、用户流失 | 可逆（可扩容、可优化） |
| **架构** | 长期维护成本高 | 可逆（可重构） |
| **风格** | 可读性差 | 完全可逆（改个格式） |

**"不可逆的排前面"** —— 这是一个可以直接拿去回答"你的优先级怎么定的"的判据。

**但这里有一个必须指出的缺口：**

```java
public static int priorityOf(AgentType type) {
    return PRIORITY.getOrDefault(type, 0);
}
```

**`getOrDefault(type, 0)`** —— 未在表里的类型权重为 **0**。

**表里没有哪些类型？**

| 类型 | 权重 |
|---|---|
| `SECURITY` / `LOGIC` / `PERFORMANCE` / `ARCHITECTURE` / `STYLE` | 100/90/70/60/10 |
| **`CUSTOM`**（业务方自定义） | **0** |
| **`COORDINATOR`** | **0**（不会产出 Finding，无影响） |

**后果非常具体**：

> **业务方辛辛苦苦在后管配了一个"支付合规审查"自定义 Agent（第 16 讲），但它的意见在任何冲突里权重恒为 0 —— 永远输给任何一个内置 Agent，包括 STYLE（权重 10）。**
>
> **而报告里的 `arbitrationNotes` 只会说"按优先级（安全>逻辑>性能>架构>风格）保留 X"** —— 读者**根本看不出 CUSTOM 的权重是 0**，因为提示文案里压根没提 CUSTOM。

**更麻烦的是它的表现形态**：自定义 Agent 的发现**绝大多数时候是正常出现的**（只有"同一位置 + 有冲突"时才会被挤掉）。**所以它看起来"工作正常"，偶尔"漏几条"** —— 而这正是最难被发现的故障形态。

**补法**（按合理性排序）：

| 方案 | 做法 |
|---|---|
| **给 CUSTOM 一个显式权重** | 加进 `PRIORITY` 表（比如 85，介于安全与逻辑之间） |
| **让权重可配置** | 从 `TeamProperties` 读（业务方自己定优先级） |
| **把"未登记"变成显式错误** | `priorityOf` 遇到未知类型时**抛异常或至少 WARN 一次**，而不是静默返回 0 |

**第三个方案的思路最值得学**：

> **`getOrDefault(key, 0)` 是一个"静默兜底"。** 它让"我漏了配置一种类型"这件事**变成了运行时的默认值**，而不是一个错误。
>
> **凡是"枚举值 + 映射表"的组合，都应该问一句：新增一个枚举值时，这个表会不会自动覆盖它？**
>
> **不会的话（如本例），就要么让它 fail-fast，要么在枚举上挂一个默认权重。** 让"新增枚举值"这件事**必然触发一次编译错误或启动检查**，比让它在运行时静默降级到 0 好得多。

### 2.5 ★ 顺序问题：抑制应该在仲裁之前

**这是这一讲最重要的一处。**

当前顺序是 **先仲裁（步骤 2），后抑制（步骤 3）**：

```java
// 2. 优先级冲突仲裁：同一位置不同 Agent 建议冲突时，高优先级胜出
List<Finding> overridden = new ArrayList<>();
...
removed.add(loser.dedupKey());
overridden.add(loser);

List<Finding> afterArbitration = new ArrayList<>();
for (Finding f : mergedList) {
    if (!removed.contains(f.dedupKey())) {
        afterArbitration.add(f);
    }
}

// 3. 误报抑制：命中开发者已确认误报的发现移入 suppressedFindings
List<ReviewFeedback> falsePositives = feedbackStore == null
        ? List.of() : feedbackStore.falsePositives(teamId);
List<Finding> suppressed = new ArrayList<>();
List<Finding> kept = new ArrayList<>();
for (Finding f : afterArbitration) {
    if (matchesFalsePositive(f, falsePositives)) {
        suppressed.add(f);
    } else {
        kept.add(f);
    }
}
```

**注意 `afterArbitration` 已经完全排除了落败者** —— 落败者在步骤 2 就已经"死"了，**步骤 3 没有机会把它救回来。**

**于是故障四发生了：**

```
步骤 2（仲裁）：SECURITY 胜 → LOGIC 被移出（不可恢复）
步骤 3（抑制）：SECURITY 命中误报 → 被移出
最终：两条都不在 kept 里
```

**为什么这是"漏报"而不是"过度过滤"？**

因为**抑制的对象和仲裁的胜者是同一条**。人类的判断是"**这条 SECURITY 发现是误报**"，而不是"**这一行没有问题**"。

**真正应该发生的是**：SECURITY 这条被抑制掉，**而 LOGIC 那条（从未被判定为误报）应该保留下来。**

**修法：交换步骤 2 和步骤 3。**

```java
// ✅ 正确顺序：先按人类反馈抑制，再在"幸存者"之间仲裁
// 2. 误报抑制（人类判断优先）
// 3. 冲突仲裁（机器规则补位）
```

**依据是一个原则问题：**

> **"人类显式判断"和"机器规则推断"，谁应该先执行？**
>
> **答案是人类判断。** 理由：
> - 人类判断是**关于事实的**（"这条是误报"是外部真理）；
> - 机器规则是**关于取舍的**（"安全优先于逻辑"是内部约定）。
>
> **用一个内部约定去处置一个外部真理，等于让系统去推翻事实。**
>
> **一旦顺序反了，被约定挤掉的那条就永久消失了** —— 而它可能是对的。

**注意 `VetoPolicy` 只救 `BLOCKER`**（下一节），所以**这个顺序问题对 MAJOR / MINOR / INFO 级发现完全生效** —— 而这三个级别恰好是绝大多数发现所在的级别。

### 2.6 强否决：为什么 BLOCKER 必须能"翻案"

前两节的两个步骤都会"移出"发现：仲裁移出落败者，抑制移出误报。**如果一个 BLOCKER 被这两个步骤中任何一个移出，那是一个不可接受的后果。**

**`VetoPolicy` 就是为此存在的，而且它的位置在聚合之后：**

```java
// CompletableFutureCoordinator.java:556-559
// 4.1 权限收敛（P1-⑥）：BLOCKER 级强否决不可被误报抑制 / 仲裁覆盖（父不覆盖子）
if (vetoPolicy != null) {
    report = vetoPolicy.apply(report);
}
```

```java
// core/permission/VetoPolicy.java:11-28
/**
 * 权限收敛策略（对齐 codex {@code intersect_permission_profiles} / {@code retain_constraining_deny_entries}）。
 *
 * <p>多 Agent 审查中，总审查员的宽松结论<b>不得覆盖</b>领域专家的强否决：
 * <ul>
 *   <li>聚合阶段的「误报抑制」与「优先级仲裁」可能把某些发现降级或剔除；</li>
 *   <li>但 <b>{@link Severity#BLOCKER} 级发现是「强否决」</b>——任何 Agent 对安全 / 正确性的阻断级结论
 *       都不可被抑制或覆盖（父不覆盖子），必须保留在最终报告中；</li>
 *   <li>被回收的 BLOCKER 从对应列表移除并回到发现列表，报告内统计随之重算。</li>
 * </ul>
 */
@Component
public class VetoPolicy {

    /** 判定一条发现是否为「不可覆盖的强否决」。当前：阻断级。 */
    public static boolean isVetoable(Finding f) {
        return f != null && f.severity() == Severity.BLOCKER;
    }
```

**"父不覆盖子"** 这个措辞来自权限系统：**父级（更宽的角色）不能覆盖子级（更窄但更严格的角色）的拒绝。**

**放到多 Agent 场景**，它变成：

> **某个 Agent 说"这绝对不能合"（BLOCKER），那么"聚合阶段"这个角色（父）不能以"我把它判成误报了"或"另一个 Agent 优先级更高"为由把它撤掉（覆盖）。**

**但这里有一个必须点出的边界：`VetoPolicy` 只救 `BLOCKER`。**

```java
return f != null && f.severity() == Severity.BLOCKER;
```

**所以：**

| 级别 | 被仲裁/抑制移出后 | 后果 |
|---|---|---|
| `BLOCKER` | **被 `VetoPolicy` 救回** | ✅ 安全 |
| `MAJOR` / `MINOR` / `INFO` | **永久消失** | ⚠️ 依赖 2.5 节的顺序正确性 |

**这意味着 2.5 节的顺序问题不能靠 `VetoPolicy` 兜底** —— 它是另一个层次的保护，**而且只保护一个级别。**

> **一条设计原则：**
> **"强否决"机制只能保护那些"被定义为不可否决"的东西。**
> **把它当成"所有问题的安全网"是错误的** —— 那会让设计者放松对普通路径的审查。
>
> **正确的做法是双管齐下**：普通路径**逻辑正确**（顺序对），特殊路径**有强否决**（BLOCKER 兜底）。

## 三、代码

### 3.1 ★ `overridden` 会重复计数

**先看第 2 步的仲裁循环：**

```java
// core/report/ReportGenerator.java:106-133
List<Finding> overridden = new ArrayList<>();
List<String> arbitrationNotes = new ArrayList<>();
Set<String> removed = new HashSet<>();
for (int i = 0; i < mergedList.size(); i++) {
    Finding a = mergedList.get(i);
    if (removed.contains(a.dedupKey())) {
        continue;
    }
    for (int j = i + 1; j < mergedList.size(); j++) {
        Finding b = mergedList.get(j);
        if (removed.contains(b.dedupKey())) {
            continue;
        }
        if (!ArbitrationPolicy.isConflict(a, b)) {
            continue;
        }
        Finding winner = ArbitrationPolicy.winner(a, b) == a.agentType() ? a : b;
        Finding loser = winner == a ? b : a;
        removed.add(loser.dedupKey());
        overridden.add(loser);                       // ← 没有去重检查
        arbitrationNotes.add(String.format(
                "在 %s:L%d 处，%s 与 %s 意见冲突（落败方建议：%s；胜出方建议：%s），按优先级（安全>逻辑>性能>架构>风格）保留 %s。",
                loser.file(), loser.lineStart(),
                winner.agentType().getDisplayName(), loser.agentType().getDisplayName(),
                loser.suggestion(), winner.suggestion(), winner.agentType().getDisplayName()));
    }
}
```

**`removed` 是 `Set`（去重），但 `overridden` 是 `List`（不去重）。**

**关键在于 `loser` 的判定是"谁输了"，而不是"谁是 `b`"：**

```java
Finding winner = ArbitrationPolicy.winner(a, b) == a.agentType() ? a : b;
Finding loser = winner == a ? b : a;
```

**当内层循环走到 `j=2`、`j=3` 时，`a` 已经输过一次了，但它本身并没有被移出 `mergedList`** —— 它只是在 `removed` 集合里。

**而内层循环只检查 `removed.contains(b.dedupKey())`，不检查 `removed.contains(a.dedupKey())`** —— 所以 **`a` 可以连续输给多个 `b`，每输一次就被 `overridden.add(loser)` 加一遍。**

**具体走一遍。** 同一个位置有三条发现：

```
C (STYLE, 权重 10)     a
B (LOGIC, 权重 90)     b（同时是后面的 a）
A (SECURITY, 权重 100) b
```

```
i=0, a=C:
  j=1, b=B: 冲突 → 胜 B，负 C → removed={C},  overridden=[C],  notes=[#1]
  j=2, b=A: 冲突 → 胜 A，负 C → removed={C},  overridden=[C, C], notes=[#1, #2]   ← C 第二次
i=1, a=B:
  j=2, b=A: 冲突 → 胜 A，负 B → removed={C,B}, overridden=[C, C, B], notes=[#1,#2,#3]
i=2, a=A: 内层空
```

**结果：`overridden` 有 3 条，但只有 2 条是真实存在的发现（C 和 B）。**

**两个后果：**

1. **`CompletableFutureCoordinator.java:583-588` 打出的日志里，`report.getOverriddenFindings().size()` 偏大**：

```java
// CompletableFutureCoordinator.java:583-588（节选）
log.info("[Coordinator] PR#{} 审查完成（runId={}，profile={}）：最终 {} 条，抑制误报 {} 条，仲裁覆盖 {} 条，...",
        pr.getId(), runId, profile, report.getFindings().size(), report.getSuppressedFindings().size(),
        report.getOverriddenFindings().size(), ...);
```

2. **报告 Markdown 里的数字和列表长度对得上**（因为 `msg("report.arbitration.title", overriddenFindings.size())` 用的是同一个 `size()`），**但列表里会出现两条一模一样的说明行**：

```java
// ReviewReport.toMarkdown()
if (overriddenFindings != null && !overriddenFindings.isEmpty()) {
    sb.append("## ⚖️ ").append(msg("report.arbitration.title", overriddenFindings.size())).append("\n\n");
    if (arbitrationNotes != null) {
        arbitrationNotes.forEach(n -> sb.append("- ").append(n).append('\n'));
    }
```

**读者看到的是"仲裁覆盖 3 条"，然后底下两条内容完全相同的说明行。**

**修法（一行）：**

```java
if (removed.add(loser.dedupKey())) {      // 只有在"本次真的新移除"时才记录
    overridden.add(loser);
    arbitrationNotes.add(...);
}
```

**注意 `Set.add` 返回 `boolean`** —— 用它的返回值当"是否新增"的判据，比再写一次 `contains` 更简洁，也更不容易写错。

> **一条通用经验：**
> **"集合去重"和"列表留痕"是两件事，必须各自明确。**
> **本项目里 `removed`（Set，用于判定）做对了，`overridden`（List，用于展示）做错了** —— 而**它们服务于同一个业务语义**。
>
> **写这类代码时，先问"这个东西在结果里有几种身份"**：参与判定（用 Set）？用于展示（要 List，但需去重）？两者都要？**同一个循环里同时维护两者，是最容易漏掉一处的地方。**

### 3.2 ★ 抑制的第三级文件匹配过宽

```java
// core/report/ReportGenerator.java:166-193
private boolean matchesFalsePositive(Finding f, List<ReviewFeedback> fps) {
    for (ReviewFeedback fb : fps) {
        if (!fb.ruleId().equalsIgnoreCase(f.ruleId())) {
            continue;
        }
        if (fb.agentType() != null && !fb.agentType().isBlank()
                && !fb.agentType().equalsIgnoreCase(f.agentType().name())) {
            continue;
        }
        if (fb.file() != null && !fb.file().isBlank()) {
            boolean fileMatch = f.file().equals(fb.file())
                    || f.file().endsWith("/" + fb.file())
                    || f.file().endsWith(fb.file());        // ← 第三级
            if (!fileMatch) {
                continue;
            }
        }
        return true;
    }
    return false;
}
```

**三级文件匹配，从严格到宽松：**

| 级 | 判据 | 例子（`fb.file() = "A.java"`） |
|---|---|---|
| 1 | 完全相同 | `f.file() = "A.java"` ✅ |
| 2 | 以 `"/" + fb.file()` 结尾 | `f.file() = "src/main/java/A.java"` ✅（安全） |
| 3 | **以 `fb.file()` 结尾** | `f.file() = "src/BAA.java"` ✅ ← **误命中** |

**第三级没有斜杠做边界，于是任何"以同样字符结尾"的路径都会命中。**

**验算：**

```java
"src/BAA.java".endsWith("A.java")      // true —— 长度 8，取末 6 位 = "A.java"
"path/DirA.java".endsWith("A.java")    // true
"x/Config2.java".lastIndexOf ...       // 同理
```

**后果**：**对 `A.java` 中某条发现的误报反馈，会把 `BAA.java` 里的同 `ruleId` 发现也一并抑制掉。**

**约束条件是三个字段必须同时匹配**（`ruleId` + `agentType` + `file`），所以**它需要"两个文件同 `ruleId` 同 `agentType`"才会误伤** —— 概率不高，但一旦发生就是**静默漏报**。

**为什么这个缺口值得单独讲？因为它落在"最危险的一类"：**

| 类型 | 表现 | 严重性 |
|---|---|---|
| 误报（false positive） | 报告里多一条 | 烦人，但**可见** |
| **漏报（false negative）** | **报告里少一条，且没有任何信号** | **危险，且不可见** |

**而抑制逻辑的作用方向恰好是"让发现消失"** —— 所以这里的每一处宽松，都在往"漏报"方向偏。

**修法**：把第三级改成"**只比较文件名（basename）**"，而不是路径后缀：

```java
// ✅ 意图明确的写法：要么是同一条路径，要么是同名文件
private boolean sameFile(String findingFile, String feedbackFile) {
    if (findingFile.equals(feedbackFile)) {
        return true;
    }
    String a = findingFile.substring(findingFile.lastIndexOf('/') + 1);
    String b = feedbackFile.substring(feedbackFile.lastIndexOf('/') + 1);
    return a.equals(b);
}
```

**同时把 `endsWith("/" + fb.file())` 也统一进去** —— 它和 basename 相等在"反馈给的是完整路径"时等价，在"反馈给的是文件名"时更严格。

> **一条判据：**
> **凡是"用字符串后缀来匹配路径"的代码，都要问一句：这个后缀有没有可能落在文件名的中间？**
>
> **`endsWith("/" + x)` 是安全的（斜杠保证了它是路径分隔边界）；`endsWith(x)` 不是。**
>
> **这个区别很小，但它是"误报"和"漏报"的分界。**

### 3.3 把五步的价值量化看

用一个具体的例子走完整个流程。**假设五个 Agent 一共报了 12 条：**

```
去重前 12 条
   ├─ 其中 4 条是同一 ruleId 同一位置（跨 Agent 重复）→ 去重后 8 条
   ├─ 其中 2 条在同一位置互相冲突（不同 ruleId，建议相反）→ 仲裁后留 1 条，即 7 条
   ├─ 其中 1 条命中已确认误报 → 抑制后 6 条
   └─ 最后按 Profile 过滤（第 11 讲）→ 对外呈现 N 条
```

**每一步都在减少条数，而每一步减少的"理由"是完全不同的：**

| 步骤 | 减少理由 | 减少了什么性质的东西 |
|---|---|---|
| 去重 | **同一个问题被重复报** | 冗余 |
| 仲裁 | **两个建议互相矛盾** | 矛盾（需要取舍） |
| 抑制 | **人类已判定是误报** | 噪声（人类权威） |
| Profile | **这个场景不需要看这个级别** | 分级噪声（场景相关） |

> **四次"减少"，理由分别是"冗余 / 矛盾 / 噪声 / 场景"** —— **如果你把它们混在一起（比如都叫"过滤"），你就无法回答"为什么这条不见了"。**
>
> **这也是本项目把三个列表分开保存（`findings` / `overriddenFindings` / `suppressedFindings`）的价值所在** —— 它让每一次"消失"都可归因。

**而这正好反过来说明 2.5 节那个顺序问题为什么严重**：

> **当一条发现先被"仲裁"移出、而胜者又被"抑制"移出时，它到底该算在哪一类？**
> **答案是：它谁也不在** —— 它掉进了一个"失败者被抑制、胜利者被抑制"的缝隙里，而报告里没有任何一处记录这件事。

## 四、避坑清单

- [ ] **聚合是有顺序的决策流程，不是 `addAll`。** 每一步减少条数的"理由"不同。
- [ ] **统计口径必须等于"用户看到的集合"**（只统计未被抑制的）。
- [ ] **去重键故意不含 `agentType`** —— 这是对"Agent 互不通信"的补偿。
- [ ] **冲突判定是三个必要条件**：不同 Agent + 位置重叠 + **建议文本不同**。
- [ ] **`lineStart=0`（文件级发现）会互相判为"重叠"** —— 同一文件上两条文件级发现必然触发仲裁。
- [ ] **"建议相同 → 不算冲突"会导致同位置出现两条完全相同的建议** —— 这是"宁可重复不误合并"的取舍，要知 knowingly 接受。
- [ ] **权重数字本身无意义，序才有意义**（依据是"不修的后果是否不可逆"）。
- [ ] **`getOrDefault(type, 0)` 是静默兜底**：新增枚举值不会被映射表覆盖 → **`CUSTOM` 权重恒 0，永远输**。应 fail-fast 或给显式默认。
- [ ] **★ 抑制必须在仲裁之前。** 人类判断是关于事实的，机器规则是关于取舍的；**用取舍去处置事实，会永久消灭一条有效发现**（故障四）。
- [ ] **`VetoPolicy` 只救 `BLOCKER`** —— 普通级别完全依赖顺序正确，不能指望它兜底。
- [ ] **`Set` 用于判定 + `List` 用于留痕时，务必用 `Set.add()` 的返回值控制 List 的写入**，否则出现重复计数。
- [ ] **`endsWith(x)` 匹配路径不安全，`endsWith("/" + x)` 才安全** —— 前者是"漏报"的入口。
- [ ] **把每一次"发现消失"都单独留痕**（去重 / 仲裁 / 抑制 / Profile 各存一个列表），否则无法归因。

## 本讲小结

1. **聚合是五步有序流程**：降级收集 → 去重 → 仲裁 → 抑制 → 分级统计；**每一步减少条数的理由不同**（冗余 / 矛盾 / 噪声 / 场景）。
2. **去重键不含 `agentType` 是刻意的** —— 它补偿了"星型拓扑下 Agent 互不通信"。
3. **冲突判定三条件**：不同 Agent + 位置重叠 + 建议文本不同。第三条会让"同位置同建议"的两条并存（有意选择"宁可重复"）。
4. **权重只有序有意义**：安全 > 逻辑 > 性能 > 架构 > 风格，依据是"不修的后果是否不可逆"。
5. **`getOrDefault(type, 0)` 让 `CUSTOM` 权重恒为 0** —— 业务方自定义 Agent 在冲突里永远输，且报告不提示。
6. **★ 抑制必须在仲裁之前。** 当前顺序会造成"胜利者被抑制 + 失败者已被移除 = 双输"，**这是一条静默漏报**。
7. **`VetoPolicy` 只救 `BLOCKER`**，普通级别完全依赖顺序正确性。
8. **`overridden` 不去重会重复计数**，且计数依赖输入顺序（用 `Set.add()` 的返回值修）。
9. **`endsWith(file)` 匹配路径过宽**，会把 `BAA.java` 当成 `A.java` —— 抑制逻辑里的每一处宽松都在往漏报方向偏。

下一讲处理"打分"：**五个 Agent 的置信度怎么统一？为什么"越用越准"这个功能曾经是空转的？**
