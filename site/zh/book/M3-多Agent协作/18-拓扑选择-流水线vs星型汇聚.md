## 一、痛点

五个 Agent 都写好了，现在面临一个看起来"无所谓"的选择：**它们怎么连起来？**

最直觉的两种写法：

**写法 A（流水线）**：

```java
List<Finding> findings = new ArrayList<>();
findings.addAll(logicAgent.review(diffs, ctx));
findings.addAll(securityAgent.review(diffs, ctx));       // 拿着上面的结果继续
findings.addAll(performanceAgent.review(diffs, ctx));
findings.addAll(styleAgent.review(diffs, ctx));
findings.addAll(architectureAgent.review(diffs, ctx));
```

**写法 B（星型）**：

```java
// 五个 Agent 并行跑，各自拿到同一份原始输入，结果最后汇聚
```

**你随手选了 B，因为它"看起来更快"。** 但半年后你会发现三个问题：

**问题一：延迟账算不清。**

用户投诉"审查太慢"。你想优化，却不知道自己省下的是哪一段——**因为你从来没算过两种拓扑的延迟公式。**

**问题二：为什么"Agent 之间不通信"这件事，在面试里被追问。**

面试官问："你的五个 Agent 会互相看对方的结果吗？"

你答："不会。"

面试官："那其中一个漏了怎么办？"

**你答不上来。** 因为这个问题问的是**拓扑的代价**，而你没有从"拓扑"这个层面思考过。

**问题三：你发现代码里其实有两种拓扑，但你说不清为什么。**

`CompletableFutureCoordinator` 里除了"五个 Agent 并行"这条主路径，还有一条**规划路径**：

```java
// CompletableFutureCoordinator.java:504-509
List<AgentResult> plannedResults = planningSupport == null ? List.of()
        : planningSupport.planAndExecute("审查 PR #" + pr.id() + "：" + pr.title(),
                diffs, enrichedCtx, effectiveAgents, pr.id(), recorder, runId);
```

而 `TaskPlanningSupport` 背后是 `agent-kit` 的 **DAG 执行器**——**那是一套"有依赖关系"的拓扑。**

**同一份代码里存在两套拓扑，如果你说不清"什么时候用哪套"，那这套设计就是没有完成的设计。**

## 二、原理

### 2.1 三种拓扑，一句话说清区别

| 拓扑 | 数据流 | 一句话 |
|---|---|---|
| **流水线（pipeline）** | A → B → C | **B 的输入是 A 的输出** |
| **层级（supervisor）** | 中心决定"下一步叫谁" | **中心是决策者，不是汇总者** |
| **星型汇聚（star / fan-out-fan-in）** | 中心 → N 个 Agent → 中心 | **N 个 Agent 拿到同一份输入，结果回流到中心** |

**关键区别不在"有没有中心"，而在"Agent 之间的数据依赖"。**

- 流水线：**有依赖**（B 需要 A 的结果）
- 层级：**依赖由中心动态决定**（中心可能让 B 重做）
- 星型：**没有依赖**（五个 Agent 各自从原始输入出发）

**四种拓扑一张表看清（多列对齐的选型速查）：**

| 维度 | 流水线 Pipeline | 星型汇聚 Star | DAG | 层级 Supervisor |
|---|---|---|---|---|
| **核心思想** | B 的输入 = A 的输出，串成链 | N 个 Agent 拿同一输入，结果回流中心 | 有依赖才等、无依赖并发 | 中心用模型决定"下一步叫谁" |
| **数据依赖** | 强（B 依赖 A） | 无 | 由 `dependsOn` 显式声明 | 由中心动态决定 |
| **端到端延迟** | Σtᵢ（LLM 场景最差） | max(tᵢ)（池够时） | 关键路径之和，优于 Σ | 多轮、不可预测 |
| **错误传播** | 致命：上游漏报=下游盲区 | 无（各自独立） | 有（沿依赖边传导） | 有（沿决策链） |
| **去重保护** | 少 | 必要（重复默认发生） | 必要（菱形依赖重复提交） | 少 |
| **唯一协作点** | 全程都在协作 | 聚合阶段（集中） | 有向边的传导 | 中心（决策者） |
| **确定性** | 高 | 高 | 高（拓扑排序是算法） | 低（模型调度） |
| **LLM 成本** | 中（可共享一步） | 偏高（N 个重吃公共输入） | 中高 | 高且抖动大 |
| **适用场景** | 强先后依赖的窄任务 | 维度独立的审查/拆解 | 可拆且有子依赖的任务 | 步骤未知的开放式任务 |
| **代表** | `agent-kit` 任务链 | `CompletableFutureCoordinator` | `agent-kit / DagExecutor` | `agent-kit / SupervisorAgent` |

### 2.2 判断依据：任务之间有没有数据依赖

这是本讲唯一需要你记住的判据：

> **如果 Agent B 需要 Agent A 的输出才能开始工作，就用流水线 / DAG。**
> **如果所有 Agent 都能直接从原始输入出发，就用星型。**

**回到代码审查：安全审查需要先知道逻辑审查的结论吗？**

不需要。安全 Agent 要的是那句 `query = "SELECT * FROM users WHERE id = " + userId`，**它自己就能判断这是注入风险**——它不需要先被告知"这段逻辑是正确的"。

**五个维度全部满足"直接可从原始输入出发"。** 所以星型是对的。

### 2.3 流水线的两个硬伤（这是"为什么不用流水线"的正面回答）

**硬伤一：延迟串行累加。**

```
流水线：总延迟 = t₁ + t₂ + t₃ + t₄ + t₅
星型：  总延迟 = max(t₁, t₂, t₃, t₄, t₅)   （并行前提下）
```

**五个 LLM Agent 每个耗时量级相同**（都是"渲染 prompt → 调模型 → 解析"），所以**流水线的延迟约等于星型的 5 倍**。

**注意这是公式，不是实测数字。** 对 LLM 场景，串行 vs 并行的差距恰好最大——因为单次 LLM 调用的耗时是**秒级**（网络 + 推理），而不是微秒级。**5 个串行的 LLM 调用就是分钟级的用户体验差异。**

**配上真实量级，你才信这条公式。** 假设 5 个 Agent，单次 LLM 调用中位数 **t=1.8s、p99=4s**，线程池从 1 调到 5：

> **串行（流水线）：**
> 中位数 ≈ 5 × 1.8 = **9s**；p99 ≈ 5 × 4 = **20s**（尾部延迟也线性叠加，最痛）
> **并行（星型，池 ≥ 5）：**
> 中位数 ≈ max = **1.8s**；p99 ≈ max = **4s**
> **折中：线程池只有 3（`ceil(5/3)=2` 波，每波约一个 p95 量级）：**
> ≈ 2 × 4 = **8s**——跟串行只差 1 秒，回报极低
>
> 三种配置的 p99 端到端：**20s vs 4s vs 8s**——并行对尾部延迟的碾压，比中位数更刺眼。

> **结论是"并行度不是要不要，是够不够"**：池子小于 Agent 数，你用等比列真省不了多少；池子足够，延迟从"Σ 叠成分钟级"降到"max 落在秒级"。这正是第 20 讲"线程池 → 超时预算"要一起设计的同一个数字。

**硬伤二：错误传播（更致命）。**


<img class="mermaid-svg" src="/zh/book-assets/diag-0080.svg" alt="硬伤二：错误传播（更致命）。" />

> **图 18-1**　流水线里的错误传播。**注意每一步都没有报错**——上游只是"少说了一句话"，下游却在不知道这件事的前提下给出了结论。**上游的漏报变成下游的盲区，而下游不知道自己盲了。**

**流水线里，上游的"漏报"会变成下游的"盲区"，而且下游不知道自己盲了。**

> **这是流水线在多 Agent 审查里最不可接受的代价：它把"独立性"这个最大的优点（第 17 讲判据二）换成了"依赖"。**
>
> 而在 LLM 场景里，**漏报是常态而不是异常**——模型本来就不可能保证召回率。用一个"会漏"的输出当前提，等于让错误在链路上累积。

### 2.4 星型的代价：只有一个协作点

星型不是免费的。**"五个 Agent 互不通信"是一个决策，它有明确的代价：**

**代价一：必然重复。** 逻辑 Agent 和规范 Agent 都会看同一行代码，可能对同一个问题各报一条。**所以去重是强制的，不是可选的**（第 21 讲第 1 步）。

**代价二：无法做跨维度推理。**

一个真实场景：

```
代码：String sql = "SELECT * FROM t WHERE id = " + id;
上游：这个方法的所有调用方，id 都来自 request.getParameter("id") 之后的白名单校验
```

一个"看了全貌"的审查者会说：**这里虽然拼接了，但上游有白名单，风险等级降为 MINOR。**

**星型拓扑下，没有任何一个 Agent 能做这个判断**：

- 安全 Agent 只看得到这段 diff（它的输入是 diff，不是调用链）；
- 聚合阶段（`ReportGenerator`）**只做规则计算，不做推理**。

**代价三：聚合阶段成为唯一的"协作点"，它的规则决定了系统上限。**

**而它当前只实现了"规则"，没有实现"推理"。**

看仲裁器的类注释——**它自己承认了这一点**：

```java
// core/report/ArbitrationPolicy.java:8-16
/**
 * 冲突仲裁策略（见文档"冲突解决：按优先级规则或调用高级模型裁决"）。
 *
 * <p>当不同 Agent 在同一代码位置给出<b>相互冲突</b>的建议时，依据固定优先级权重裁决：
 * <pre>
 *   安全(SECURITY)=100 &gt; 逻辑(LOGIC)=90 &gt; 性能(PERFORMANCE)=70
 *      &gt; 架构(ARCHITECTURE)=60 &gt; 风格(STYLE)=10
 * </pre>
 * 高优先级 Agent 的意见胜出，低优先级意见被记录为"已裁决覆盖"。
 */
```

**注意第一行括号里的话**："见文档『冲突解决：按优先级规则**或调用高级模型裁决**』"。

**文档给了两条路，实现只走了第一条。** 全文没有第二处仲裁逻辑，`ArbitrationPolicy` 是一个纯静态类（`private ArbitrationPolicy() {}`，全是 `static` 方法），**没有任何 LLM 调用**。

> **这是一个诚实的设计缺口，也是一个很好的延伸点**："调用高级模型裁决"是一条真实可行的升级路径——把两个冲突的 `Finding` 加代码上下文交给一个"更强/更贵"的模型，让它给出取舍理由。
> **它为什么没有被实现？** 因为**成本**：仲裁发生在每次审查的每个冲突点上，而冲突是有可能很多的。**在"规则够用"的前提下，为一个边缘场景引入不确定的延迟和成本，是不划算的。**
>
> **这个取舍值得记住：不是所有"文档里写了"的能力都该被实现。** 但**不实现的部分应该在文档里显式标注为"设计预留"**，而不是让读者以为它存在。

### 2.5 同一份代码里的两种拓扑：这不是矛盾

回到问题三。项目里确实有两套拓扑：

| 路径 | 拓扑 | 什么时候走 |
|---|---|---|
| **主路径**（默认） | 星型汇聚 | `review.planning.enabled=false`（默认） |
| **规划路径**（可选增强） | **DAG** | `review.planning.enabled=true` |

**为什么会有 DAG 这条路径？因为"审查"和"规划"是两个层次的任务。**

- **审查这一个 PR**：五个维度之间没有依赖 → 星型。
- **"把审查这件事拆成子任务"**：拆出来的子任务之间**可能**有依赖。例如：

```
Task 1: 解析变更的调用链，找出受影响的模块
Task 2: 基于 Task 1 的结果，判断架构影响      ← 依赖 Task 1
Task 3: 审查变更本身的安全问题                 ← 不依赖
```

**当任务之间存在依赖时，星型的"所有 Agent 从同一输入出发"就不成立了** —— 这时需要的是**拓扑排序 + 按依赖执行**，也就是 DAG。

**所以项目的做法是**：

```java
// 1. 先问规划器：这次审查该怎么拆？（LLM 拆解为子任务 DAG）
// 2. 如果规划成功 → 按 DAG 执行（有依赖的执行顺序）
// 3. 如果规划失败/未启用 → 退回固定并行（星型）
```

**"降级到星型"这个设计很关键**：DAG 是**增强**，不是**依赖**。规划失败时系统仍然可用（第 11 讲讲过 `TaskPlanner` 的 `singleStep` 降级）。

> **一句话总结：拓扑不是信仰，是任务结构的映射。**
>
> **"你有依赖吗"决定拓扑**，而不是"多 Agent 系统应该长什么样"。

**工程判据：** **拓扑用两个表达式定，不用感觉——串行 = Σtᵢ、并行 = ceil(K/P)·t（K 个 Agent、线程池 P）、DAG = 关键路径和。只要任务无数据依赖，且『并行收益 Σt − ceil(K/P)·t ≥ 2 × 传播开销（traceId / MDC / 上下文搬运）』，就选星型；任何一项账算不过，就退回更省的结构。** 别凭"多 Agent 当然要并行"的直觉选拓扑，要凭这两个表达式下结论。

### 2.6 第三种拓扑：中心是决策者

`agent-kit` 里还有第三种实现——`SupervisorAgent`（第 10 讲提到过"把 Agent 当成一种工具"）。

**它和星型的区别在一个字：中心是"汇总者"还是"决策者"。**

| | 星型（本项目主路径） | Supervisor |
|---|---|---|
| 中心的职责 | **汇总**：并行下发、收集、聚合 | **决策**：决定下一步叫谁、叫几次 |
| 循环次数 | 一轮（fan-out 一次） | 多轮（中心可能反复调度） |
| 中心用什么做决策 | **代码**（固定并行） | **模型**（一次 LLM 调用决定下一步） |

**Supervisor 的代价是它把"确定性调度"换成了"模型调度"**：更灵活，但**延迟不可预测、成本不可预测、行为不可复现**。

**本项目的选择已经很清楚了**：

- **主路径用星型** —— 审查是一个**结构已知的任务**（5 个固定维度），不需要模型来决定"下一步叫谁"。**用确定性换可预测性**。
- **规划路径用 DAG** —— 需要模型判断"怎么拆"时才引入模型，**且拆完之后的执行又是确定性的**（拓扑排序是纯算法）。

> **这是一个可以复用很多次的设计模式：让模型做"决策"，让代码做"执行"。**
> **模型只回答"拆成什么"，不回答"先跑谁后跑谁"** —— 后者是 `DagExecutor` 用 Kahn 算法算出来的（第 11 讲）。

## 三、代码

### 3.1 星型的 fan-out：一行创建 N 个并行 Future

```java
// CompletableFutureCoordinator.java:518-532
List<CompletableFuture<AgentResult>> futures = List.of();
if (plannedResults.isEmpty()) {
    futures = effectiveAgents.stream()
        .map(agent -> CompletableFuture.supplyAsync(TraceContext.wrap(() -> {
            long a0 = System.currentTimeMillis();
            if (recorder != null) {
                recorder.append(runId, "agent.started", Map.of("agentType", agent.getType().name()));
            }
            log.info("[Coordinator] 子Agent[{}] 开始审查（并行执行）", agent.getType());
            List<Finding> findings = agent.review(diffs, enrichedCtx);
            log.info("[Coordinator] 子Agent[{}] 完成：发现 {} 条，耗时 {}ms",
                    agent.getType(), findings.size(), System.currentTimeMillis() - a0);
            return new AgentResult(pr.id(), agent.getType(), findings);
        }), agentExecutor))
        .toList();
}
```

**四个细节，每一个都是"星型拓扑"的具体含义：**

**① `agent.review(diffs, enrichedCtx)` —— 每个 Agent 拿到的参数完全相同。**

**这就是星型的数据特征**：没有 `findings` 从一个 Agent 流向下一个。`diffs` 是原始输入，`enrichedCtx` 是**在 fan-out 之前就已经准备好**的共享上下文（影响面摘要 + RAG 上下文，见 `:367-369`）。

**② `TraceContext.wrap(...)` —— 跨线程传播 traceId。**

并行带来一个新问题：**每个 Agent 跑在独立线程上，而 `TraceContext` 是 ThreadLocal 的**（第 15 讲）。`wrap` 的作用是把当前线程的 traceId 带到工作线程上，**否则五个 Agent 的日志会丢掉链路 ID**。

**这是"并行"的隐性成本之一**：所有依赖 ThreadLocal 的东西（traceId、MDC、SecurityContext、事务上下文）**都必须显式传播**。

**③ 每个 Agent 的结果独立变成一个 `AgentResult`。**

```java
return new AgentResult(pr.id(), agent.getType(), findings);
```

**`agent.getType()` 是"这条结果来自谁"的唯一标识。** 没有它，聚合阶段就无法做仲裁（第 21 讲需要知道每条 `Finding` 的 `agentType`），也无法做"独立观测"（第 17 讲判据四）。

**④ `futures` 是一个 `List`，顺序与 `effectiveAgents` 一一对应。**

**这个"位置对应"关系在后面的循环里被依赖**：

```java
// CompletableFutureCoordinator.java:552-554
for (int i = 0; i < futures.size(); i++) {
    CompletableFuture<AgentResult> future = futures.get(i);
    ReviewAgent agent = effectiveAgents.get(i);   // ← 靠下标对齐
```

**这是一个隐式契约**：`futures` 和 `effectiveAgents` 必须同序同长。

**它在本项目里是安全的**（两处都是同一个 `stream().map(...)` 产生的），但**它是一个"没有类型保护的约定"** —— 如果将来有人在这里插入一个 `filter`，两个列表就会错位，**而错位的后果是"把 A 的超时算到 B 头上"**，非常难查。

> **更稳的写法**：让 `Future` 自己带上身份。例如 `CompletableFuture<AgentResult>` 的 key 用 `agentType` 装进 `Map<AgentType, CompletableFuture<AgentResult>>`，遍历 `Map.entrySet()` 时 `key` 就是身份，**不依赖下标对齐**。
>
> 这条经验可以推广：**凡是"两个 List 靠下标对齐"的地方，都值得换成一个带 key 的 Map。**

### 3.2 星型的 fan-in：四步聚合

```java
// CompletableFutureCoordinator.java:620-622
// 4. 汇聚、去重、优先级仲裁、误报抑制、定档（降级记录随报告输出告警块）
ReviewReport report = reportGenerator.aggregate(
        pr.id(), pr.repo(), results, feedbackStore, runId, durationMs, teamId, degradations);
```

**注意这里的注释列了五件事**：汇聚、去重、优先级仲裁、误报抑制、定档。

**这是星型拓扑真正的"协作点"。** 第 21 讲会逐条展开这五件事——**它们的顺序不能换**，而原因只有从"拓扑"的角度才能说清：

> **星型拓扑里，Agent 之间不协作，所以"协作"这件事全部压到了聚合阶段。**
> **聚合阶段的每一步，都在替 Agent 之间"本该发生的对话"做补偿：**
>
> - 去重 ← 补偿"我不知道对方也报了这个"
> - 仲裁 ← 补偿"我不知道对方的结论和我冲突"
> - 抑制 ← 补偿"我不知道人类已经否掉了这条"

### 3.3 DAG 路径：有依赖时的拓扑

```java
// agent-kit / planning/DagExecutor.java（形状）
public Map<String, TaskResult> execute(TaskPlan plan, Function<TaskPlan.TaskNode, TaskResult> runner) {
    ...
    Map<String, CompletableFuture<TaskResult>> futures = new LinkedHashMap<>();
    for (TaskPlan.TaskNode n : plan.tasks()) {
        compute(n, byId, futures, runner);       // 递归：依赖就绪则提交，否则等
    }
    CompletableFuture.allOf(futures.values().toArray(new CompletableFuture[0])).join();
    ...
}
```

**和 3.1 的星型 fan-out 对比，差别一目了然：**

| | 星型（`CompletableFutureCoordinator`） | DAG（`DagExecutor`） |
|---|---|---|
| 提交顺序 | 一次全提交 | **按依赖就绪逐级提交** |
| 数据依赖 | 无 | **有**（`TaskPlan.TaskNode` 带 `dependsOn`） |
| 去重保护 | 不需要 | **需要**（菱形依赖会让同一节点被提交两次 —— 第 11 讲的 `futures.containsKey` 缓存） |
| 超时 | **有**（共享 deadline） | **无**（`allOf(...).join()`，第 15 讲已指出的同一形状残留） |

**注意最后一行**。**DAG 路径没有超时** —— 而它正是"可选增强"那条路径。

**这不是巧合，而是一个普遍规律**：

> **"主路径"被反复打磨，"可选路径"永远欠维护。**
>
> 因为主路径每天在跑（问题会被暴露），可选路径只在开了开关的少数环境里跑（问题不会暴露）。
>
> **结论：如果一个功能开关默认关闭，它的代码质量会持续低于主路径 —— 要么定期打开它跑一跑，要么承认它是"未验证功能"并在文档里标注。**

### 3.4 三种拓扑在本项目的完整落点

| 拓扑 | 实现 | 位置 | 状态 |
|---|---|---|---|
| **星型汇聚** | `CompletableFutureCoordinator.review` | 主路径 | ✅ 有超时、有降级、有留痕 |
| **DAG** | `agent-kit / DagExecutor` + `TaskPlanningSupport` | 可选增强 | ⚠️ 无超时（第 15 讲） |
| **层级（Supervisor）** | `agent-kit / SupervisorAgent` | 基座能力 | 主路径未使用 |

**最后一列很重要**：`SupervisorAgent` 作为 `agent-kit` 的能力存在，但**本项目的审查链路没有用它**。

**为什么？** 因为审查任务的维度是固定的（5 个 + 业务方自定义），**不需要一个模型来"决定下一步叫谁"**。用了它，等于把一个确定性的调度换成了一个不确定的调度。

> **"有能力"和"该用它"是两件事。** 一个基座库提供的能力越多，越需要在使用层做"这次不用"的判断 —— **而判断的依据，永远是任务结构。**

### 2.8 拓扑与成本：fan-out 的乘法效应与扇入的收敛成本

本讲 §2.3 / §2.4 分别讲了流水线与星型各自的硬伤，但那是**定性**的。本节把它变成两条曲线，因为**两条曲线的形状不一样**——而形状不一样，就意味着"规模上限"由谁决定是有唯一答案的。

<img class="mermaid-svg" src="/zh/book-assets/diag-0082.svg" alt="本讲 §2.3 / §2.4 分别讲了流水线与星型各自的硬伤，但那是定性的。本节把它变成两条曲线，因为两条曲线的形状不一样——而形状不一样，就意味着&quot;规模上限&quot;由谁决定是有唯一答案的。" />

> **图 18-3**　fan-out 是线性的，扇入是二次的 —— 所以拓扑的规模上限由扇入决定。**这张图要给出的新结论是：拆分的成本有两段，而这两段的增长速度不同，因此"能不能再拆一个"这个问题有唯一答案：看扇入。** 在 N 很小的时候（本项目 N=5）扇入的二次项只有 10 次比较，可以忽略；但**当 N 进入三位数，扇入就会成为唯一的主导项**，而 fan-out 的线性增长反而显得温和。

**先确认扇入确实是二次的。** 本项目的仲裁是一个双重循环：

```text
        for (int i = 0; i < mergedList.size(); i++) {
```

`code-review-agent/src/main/java/com/codereview/agent/core/report/ReportGenerator.java:110`

```text
            for (int j = i + 1; j < mergedList.size(); j++) {
```

`code-review-agent/src/main/java/com/codereview/agent/core/report/ReportGenerator.java:115`

**最坏情况下的比较次数是 `C(N,2) = N(N-1)/2`**：N=5 → 10 次；N=100 → 4950 次。**但这里必须给出一个诚实的补充**：循环体第一步就是 `ArbitrationPolicy.isConflict(a, b)`，而它的第一句是"同类型直接返回 false"（`ArbitrationPolicy.java:55-57`），所以**绝大多数比较是常数级的**——本项目 5 个 Agent 各报各的，绝大多数对儿在第一个 `if` 就返回了。

> **那么问题在哪？** 在 `isConflict` 走到底的那条路径上，最后一步是**字符串归一化**

```text
    private static String normalize(String s) {
        return s == null ? "" : s.trim().replaceAll("\\s+", " ");
    }
```

`code-review-agent/src/main/java/com/codereview/agent/core/report/ArbitrationPolicy.java:98-100`

**用的是正则 `replaceAll`。** ⇒ **"形状是二次"这件事本身不可怕，可怕的是"二次项里的常数不是常数"**：当同类型发现的占比升高（比如团队自定义 Agent 大量产出、或同一个 Agent 在长文件上狂报），比较的代价会从"读一个枚举"跳到"跑一次正则替换"。**这是唯一一个能在压测之前就算出来的规模风险**，因为它是全流程里少数几个纯 CPU、无 I/O、形状确定的环节。

**工业界怎么处理扇入？** langchain4j 的答案是**共享黑板**：所有 Agent 读写同一个 `AgenticScope`，扇入退化成"读一个中心对象"。但共享黑板不是免费的——它的读取方式值得逐字看：

```text
    String contextAsConversation(String... agentNames);
```

`langchain4j/langchain4j-agentic/src/main/java/dev/langchain4j/agentic/scope/AgenticScope.java:147`

**注意返回类型是 `String`，而且可以按 Agent 名过滤。** ⇒ **"读共享上下文"这件事被实现成了"把上下文渲染成一整段字符串"。** 于是：

| 扇入方式 | 形状 | 代价在哪 |
|---|---|---|
| 两两比较（本项目仲裁） | **O(N²)** | 二次项，且常数可能退化成正则 |
| 共享黑板 + 渲染（langchain4j `AgenticScope`） | **O(N)** 次读取，但每次是**全量渲染** | 每次读取都重新拼一遍字符串，**不可增量** |

> **一条可迁移的结论：把扇入从"两两同步"改成"共享黑板"降的是阶（二次 → 一次），但**没有降"每次读取的成本"**。** 如果那段渲染出来的上下文有 8KB，而你在一个 100 步的 loop 里每步都读一次，那么你花掉的不是 `100 × 8KB` 的存储而是 `100 × 8KB` 的**拼接与复制**——这在 Java 里意味着 `100 × 8KB` 的临时对象。**"降阶"和"降常数"是两件事，而工业界通常只解决前者。**

**还有第三个隐藏的旋钮：`AgenticScopeRegistry` 的内存缓存。**

```text
    private final Map<AgenticScopeKey, DefaultAgenticScope> inMemoryAgenticScope = new ConcurrentHashMap<>();
```

`langchain4j/langchain4j-agentic/src/main/java/dev/langchain4j/agentic/scope/AgenticScopeRegistry.java:24`

注释逐字写着这是 "Singleton registry for managing AgenticScope instances"，`update()` 在**有 store 时**额外写一次共享存储（write-through，`:35-39`），`evict()` 显式回收（`:71-82`）。⇒ **`ConcurrentHashMap` 里常驻的 scope 条目数 = 你的并发会话数**，而它是**进程内**的。**这正好是基座 A 与基座 B 的分叉点**：

| 维度 | A：`code-review-agent` | B：千万 DAU 的智能体平台（编排视角） | 由此分叉的设计决策 |
|---|---|---|---|
| 并发会话量级 | 几十到几千个 PR/天 | 峰值数万并发任务 | 黑板**不能常驻单进程内存**，必须外置 + 按 TTL 回收 |
| 扇入候选数 N | 5–7（内置 + 少量自定义） | 单任务可 fan-out 到几十个子 Agent | 扇入的二次项**从可忽略变成主导**，仲裁必须换形态（分桶 / 只比同文件） |
| 上下文策略 | 一个团队一次审查，摘要成本可摊 | 每任务都要付摘要成本 | `SUMMARIZATION` 这类"看得更多"的策略**必须按租户配额开关** |

### 2.9 搬到你自己系统：拓扑选择的判据

本讲从头到尾只回答了一个问题：**你的任务结构长什么样，拓扑就该长什么样。** 下面这张表把三节的机制层结论压成一组可问的问题。

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| `SupervisorContextStrategy` 三值，其中两值要额外做摘要（`:12/16/20`） | 你的中心节点看见多少子节点的中间过程？这个"看见"是免费的吗？ |
| `AgenticSystemTopology` 是枚举（8 值，`:4-11`） | 你的拓扑是代码里的类型，还是配置里的字符串？改一次要发版吗？ |
| 枚举里存在无生产者的值（`STAR`） | 你的类型系统里有没有"声明了但从没被构造过"的值？渲染器会不会替它美化？ |
| 扇入是 `for i / for j = i+1`（`ReportGenerator.java:110/115`） | 你的扇入是几阶？二次项里有正则 / 序列化 / 网络调用吗？ |
| 共享黑板读取是**全量渲染成字符串**（`AgenticScope.java:147`） | 你的共享状态是"增量视图"还是"每次全量渲染"？ |
| scope 注册表是进程内 `ConcurrentHashMap`（`AgenticScopeRegistry.java:24`） | 你的共享状态在进程内还是进程外？并发会话数上限是多少？ |

**搬到你自己系统**，五步：

1. **先写下你的任务结构**（谁依赖谁），再选拓扑。**"多 Agent 就该星型"和"多 Agent 就该图"都不是判据**——判据是"B 需要 A 的输出吗"（本讲 `图 18-0` 的一句话）。
2. **把扇入的数一遍**：列出"扇入阶段要处理多少条候选"，再乘出比较次数。**如果 N 可能到三位数，先改扇入形状，再谈加 Agent。**
3. **检查扇入的二次项里有没有非常数操作**（正则、序列化、网络）。**有的话，先把它挪出比较路径**（比如先把归一化结果算一次缓存起来）。
4. **给"中心看得见多少"定价**：如果你的中心需要跨维度推理，明确它是"读摘要"还是"读全文"，并把摘要那次 LLM 调用算进成本预算。
5. **把"声明了但没实现"的类型值全部审一遍**：枚举、常量、配置项各扫一次，凡是"没有生产者"的就地处理（补实现或删掉）。

**判据**：**拓扑选择的唯一判据是"任务之间有没有数据依赖"，而拓扑的规模上限的唯一判据是"扇入是几阶、二次项里的常数有多大"。** 两个判据都不依赖对"多 Agent 该怎么长"的信仰；**如果你说不出你的扇入是几阶，那就还没到可以加 Agent 的阶段。**

## 四、避坑清单

- [ ] **判据是"有没有数据依赖"**：B 需要 A 的输出吗？需要 → 流水线 / DAG；不需要 → 星型。
- [ ] **LLM 场景下流水线的延迟代价最大**（单次调用是秒级），串行 N 级 ≈ N 倍延迟。
- [ ] **流水线的致命伤是错误传播**：上游漏报 = 下游盲区，且下游不知道自己盲了。
- [ ] **星型的必然代价是重复**：去重是强制的，不是可选的。
- [ ] **星型只有一个协作点**（聚合阶段），它的规则决定系统上限。**不要假装 Agent 之间有"对话"。**
- [ ] **务必区分"文档写了"和"代码实现了"**：本项目仲裁只有规则、没有"调用高级模型裁决"。**没实现的能力要在文档里标注为设计预留。**
- [ ] **并行任务里所有 ThreadLocal（traceId / MDC / 事务 / SecurityContext）都必须显式传播** —— `TraceContext.wrap`。
- [ ] **别用"两个 List 下标对齐"传递身份** —— 换成带 key 的 Map，`filter` 一插就错位。
- [ ] **模型做"决策"，代码做"执行"**：让模型回答"拆成什么"，拓扑排序交给算法。
- [ ] **默认关闭的功能开关会持续腐烂**：要么定期打开跑，要么标注"未验证"。
- [ ] **别把 Supervisor 的参数理解成"叫谁"。** 真正的旋钮是**中心看得见多少**——langchain4j 的三个上下文策略里有两个要在中心与子 Agent 的交互上**另做一次摘要**（一次额外 LLM 调用）。**"跨维度推理"不是免费的，它的价格就写在这三个值里。**（§2.7）
- [ ] **别把拓扑做成字符串配置而不自知代价。** langchain4j 把拓扑做成**枚举**（8 值）：好处是可穷举、可校验，代价是**改结构要改代码**。如果你的拓扑是可热更的字符串，那"拓扑"就没被类型系统管住。（§2.7）
- [ ] **别留着"声明了但没有生产者"的枚举值。** `AgenticSystemTopology.STAR` 在 `langchain4j-agentic` 全树只被 4 处引用：1 处声明 + 3 处 HTML 渲染器配色，**没有任何 planner 产出它**。给一个不存在的值配颜色，比不配更糟——**它让缺失看起来像功能**。要么补生产者，要么删掉。（§2.7）
- [ ] **别只看 fan-out 的线性成本。** 扇入如果是两两比较，形状就是 `N(N-1)/2`；N=5 时是 10 次可以忽略，**N 到三位数时它是唯一的主导项**。**能不能再加一个子 Agent，判据是扇入，不是 fan-out。**（§2.8）
- [ ] **别忽略"二次项里的常数"**：本项目扇入的最后一步是 `s.trim().replaceAll("\\s+", " ")` —— **正则**。形状是二次不可怕，可怕的是**二次项不是常数**：同类型发现一多，比较成本就从"读枚举"跳到"跑正则"。（§2.8）
- [ ] **别以为共享黑板能免费降阶。** 把扇入从"两两同步"改成"读写共享对象"确实把阶从二次降到一次，但 `AgenticScope.contextAsConversation()` 的返回类型是 `String` —— **每次读取都全量渲染一遍上下文**。降阶 ≠ 降常数，而工业界通常只解决前者。（§2.8）
- [ ] **别把"共享状态常驻内存"当默认**。langchain4j 的 scope 注册表是一个进程内 `ConcurrentHashMap` ⇒ **常驻条目数 = 你的并发会话数**。在中低 QPS 上这很省事，在千万 DAU 上它是必须外置并按 TTL 回收的东西。（§2.8）

> **任务一：把延迟公式变成实测。**
> 1. 写一个假的 `ReviewAgent`：`review()` 里 `Thread.sleep(2000)` 后返回空列表。
> 2. 用 5 个这样的 Agent，分别走"串行 for 循环"和"并行 `supplyAsync`"。

> **附加**：把线程池设成 2 个线程，重跑并行版本。**预期总耗时 ≈ 6000ms**（三批）—— **这就是"并行度"和"超时预算"必须一起设计的原因**（第 20 讲）。
>
> **任务二：亲手构造一次"错误传播"。**
> 1. 写两个 Agent：A 只报 `file=X.java` 的问题，B 依赖 A 的结果。
> 2. 让 A 故意返回空（模拟漏报）。
> 3. 观察 B 的输出。
> **预期结果**：B 输出为空，**并且它的日志里没有任何"我拿到了空输入"的痕迹** —— 这就是流水线的盲区。
> **改造**：让 B 在输入为空时显式产出"上游未提供信息，本维度结论不完整"，**这才是把盲区变成可观测故障的做法**（对比第 07/08 讲的"0 条发现不能等于没问题"）。

## 本讲小结

1. 三种拓扑的区别**不在"有没有中心"，而在"Agent 之间有没有数据依赖"**：流水线有、层级由中心动态决定、星型没有。
2. **判据只有一条**：B 需要 A 的输出吗？不需要 → 星型。
3. **流水线的两个硬伤**：延迟串行累加（LLM 场景是 N 倍）、**错误传播**（上游漏报 = 下游盲区）。
4. **星型的代价**：必然重复（去重强制）、**无法做跨维度推理**、唯一协作点（聚合阶段）决定系统上限。
5. 本项目仲裁**只有"规则"没有"模型裁决"**——文档写了、代码没实现，这属于设计预留，应显式标注。
6. **同一份代码里有两套拓扑是对的**：任务结构不同 → 拓扑不同。主路径星型（固定维度）、增强路径 DAG（有依赖）。
7. **模型做决策，代码做执行**：Supervisor 把确定性换成灵活性，代价是延迟/成本/复现性都不可预测——**固定维度的审查任务不需要它**。
