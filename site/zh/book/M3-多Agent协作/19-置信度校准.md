## 一、痛点

**故障一：`confidence` 这个字段，写了但没人真的用它。**

每条 `Finding` 都带一个 `confidence`（0~1）。它在系统里只参与两处判断：

```java
// ReportGenerator.java:95-99（去重时）
boolean replace = f.severity().isMoreSevereThan(existing.severity())
        || (f.severity() == existing.severity() && f.confidence() > existing.confidence());
```

```java
// ArbitrationPolicy.java:91-95（仲裁平局时）
if (a.severity().getPriority() != b.severity().getPriority()) { ... }
return a.confidence() >= b.confidence() ? a.agentType() : b.agentType();
```

**两处都是"平局时的加时赛"。** 而实际上：

- 规则型发现的置信度是**固定值**（`0.95`）；
- LLM 型发现的置信度是**模型自称的**（默认 `0.75`）。

**固定值之间没有区分度**，模型自称的值**没有可信度依据**。

**所以这个字段在绝大多数情况下不产生任何决策差异** —— 它只是被渲染进报告里，看起来"我们考虑了置信度"。

**故障二："越用越准"从来没生效过。**

系统里有一套完整的校准机制：

- `markFalsePositive(ruleId)` → 准确率衰减
- `markTruePositive(ruleId)` → 准确率回升
- `calibrate(ruleId, raw)` → 输出校准后的置信度

**而这三个方法的调用者是谁？**

在修复之前：**没有任何调用者。**

`FeedbackListener` 的注释把这件事写得很直白：

```java
// core/feedback/FeedbackListener.java:6-16
/**
 * 反馈落库监听器：每次有开发者反馈被持久化时触发。
 *
 * <p><b>为什么需要它</b>：反馈存储（{@link FeedbackStore}）是「开发者反馈」的唯一
 * 持久化咽喉（REST API、工作流都汇到这里）。要打通置信度校准闭环——让
 * {@code markFalsePositive / markTruePositive} 真正被调用（此前全仓零调用，校准空转）——
 * 在落库点广播事件，比在每个调用方各自接线更稳：将来新增反馈入口只需存储实现不变。
 *
 * <p>实现方只消费数据，不做任何写回（观测旁路，抛异常不得影响反馈保存本身）。
 */
```

**"此前全仓零调用，校准空转"** —— 八个字概括了一个完整功能的死亡方式。

**而它的症状是什么？**

**没有症状。**

- 报告照样生成；
- `confidence` 照样是个 0~1 的小数；
- 没有人报错；
- 没有任何日志异常；
- 单元测试全绿（因为测试是直接调 `markFalsePositive` 来验校准公式的 —— **测试绕过了"谁来调用它"这个真实问题**）。

**故障三（这是本讲的核心）：校准的失效是"不可见"的。**

设想你去线上验证："校准功能在工作吗？"

你能看到的东西：

```
- **评审人**：安全审查（来源 LLM，置信度 0.75）
- **评审人**：安全审查（来源 RULE，置信度 0.95）
```

**这两个数字，在校准生效时和校准失效时，长得一模一样。**

| | 校准正常 | 校准失效 |
|---|---|---|
| 报告里有没有 `confidence` | 有 | **有** |
| 数字范围合理吗 | 是（0~1） | **是** |
| 有没有报错 | 没有 | **没有** |
| 有没有降级标记 | 没有 | **没有** |

**这是一个"没有失败信号的功能"。**

> **这类功能是最危险的一类** —— 因为：
> **你没有任何理由去怀疑它，而它也永远不会主动告诉你它坏了。**
>
> **对比一下"分散的系统"**：超时会有 `TimeoutException`、降级会有 `AgentDegradation`、模型不可用会抛 `ModelUnavailableException`。**这些都是"会喊的故障"。**
>
> **而"校准不生效"是一个"不会喊的故障"。** 应对它的唯一办法是**主动给它加一个可观测出口**（本讲最后一节）。

## 二、原理

### 2.1 置信度的三个来源，以及为什么需要校准

| 来源 | 值 | 依据 |
|---|---|---|
| **规则命中**（`SKILL` / `RULE`） | `0.95`（固定） | 规则是确定性的，所以给高值 |
| **LLM 输出**（`LLM`） | 模型自称，默认 `0.75` | 模型的自我评估**没有校准过** |
| **校准后** | `raw × accuracy` | **这条规则的历史表现** |

代码里对应的三处：

```java
// AbstractReviewAgent.java:119-124（技能结果 → Finding）
protected Finding toFinding(SkillResult sr) {
    double conf = calibration.calibrate(sr.ruleId(), sr.confidence());
    return new Finding(getType(), sr.file(), sr.lineStart(), sr.lineStart(),
            sr.severity(), category, sr.ruleId(), sr.title(),
            sr.description(), sr.suggestion(), conf, "SKILL");
}
```

```java
// AbstractReviewAgent.java:137-142（便捷构造规则型发现）
protected Finding ruleFinding(String file, int line, String ruleId,
                             String title, String description, String suggestion) {
    double conf = calibration.calibrate(ruleId, 0.95);
    return new Finding(getType(), file, line, line, Severity.MAJOR,
            category, ruleId, title, description, suggestion, conf, "RULE");
}
```

**这两处都调了 `calibration.calibrate(...)`。**

**而 LLM 那条路没有**（第 3 节详述）：

```java
// AbstractReviewAgent.java:325-344（mapFindings，节选）
double confidence = d.confidence() == null ? 0.75 : d.confidence();
out.add(new Finding(getType(), file, line, line, severity, category,
        ..., confidence, "LLM"));        // ← 没有 calibration.calibrate(...)
```

**"校准"到底在校准什么？**

> **它不是在校准"这条发现有多严重"，而是在校准"这条规则有多可信"。**

这就是为什么参数叫 `ruleId` 而不是 `findingId`：

```java
public double calibrate(String ruleId, double rawConfidence) {
    double accuracy = accuracy(ruleId);
    double calibrated = rawConfidence * accuracy;
    return Math.min(1.0, Math.max(0.0, calibrated));
}
```

**`accuracy(ruleId)` 的语义是：这条规则**历史上**的命中准确率。**

| 场景 | `raw` | `accuracy` | `calibrated` |
|---|---|---|---|
| 新规则，从未被反馈 | 0.95 | **1.0（默认）** | 0.95 |
| 被标记过 1 次误报 | 0.95 | 0.8 | 0.76 |
| 被标记过 5 次误报 | 0.95 | 0.52488 | 0.4986 |
| 被打到下限 | 0.95 | 0.5 | 0.475 |

**关键洞察：维度是"规则"，不是"发现"。**

> **为什么按规则而不是按发现？**
>
> 因为**发现的样本量不够**：一个 `Finding` 只会被反馈一次（它只出现在一份报告里）。
> **而规则会被命中很多次** —— 每次命中都是一次"这条规则准不准"的证据。
>
> **"按什么维度学习"是做这类自适应系统时最先要回答的问题。** 答错的典型表现是"学习很慢"或者"学了也没用"（因为每个维度只有 1 个样本）。

### 2.2 两个数字：`0.8` 和 `1.0` 的语义

这两行代码是本讲最容易被读错的地方：

```java
// core/calibration/ConfidenceCalibrationService.java:60-68
public void markFalsePositive(String ruleId) {
    if (ruleId == null || ruleId.isBlank()) {
        return;
    }
    // 首次误报直接落到 0.8，之后每次乘 0.9 衰减，但不再低于 0.5（防一票否决）
    ruleAccuracy.merge(ruleId, 0.8, (old, v) -> Math.max(MIN_ACCURACY, old * 0.9));
    persist();
}
```

```java
// core/calibration/ConfidenceCalibrationService.java:75-82
public void markTruePositive(String ruleId) {
    if (ruleId == null || ruleId.isBlank()) {
        return;
    }
    ruleAccuracy.merge(ruleId, 1.0, (old, v) -> Math.min(1.0, old * 1.05));
    persist();
}
```

**`Map.merge(key, valueIfAbsent, remappingFunction)` 的语义是：**

- **如果 key 不存在** → 放入 `valueIfAbsent`；
- **如果 key 存在** → 用 `remappingFunction.apply(oldValue, newValue)` 的结果替换。

**所以：**

| 操作 | 第 1 次 | 第 2 次 | 第 n 次 |
|---|---|---|---|
| **误报** | `0.8`（**直接落到 0.8**） | `0.8 × 0.9 = 0.72` | `old × 0.9`，不低于 `0.5` |
| **正报** | `1.0`（**直接置 1.0，等于没变**） | `1.0 × 1.05 → 封顶 1.0` | 同上 |

**注意两个初始值的不对称：**

- **误报的初始值是 `0.8`** —— **比默认的 `1.0` 低**，所以**第一次误报就产生了真实的下降**；
- **正报的初始值是 `1.0`** —— **等于默认值**，所以**第一次正报是一个 no-op**（什么都没改变）。

> **数值是 0.8 / 0.9 / 1.05 / 1.0 而不是别的，是工程调参的结果**，没有理论依据。**但"误报首击必降、正报首击不动"这个偏向是有意的** —— 它表达的是"**规则默认是可信的，只有负面证据才需要立刻反映**"。
>
> **这是一个可以迁移的判断：对"默认可信"的实体，正反馈应该是渐进确认，负反馈应该是立即可见。**

### 2.3 衰减与回升的不对称：6 次 vs 15 次

**把常数代入算一下（纯数学，不是实测）：**

**从 1.0 衰减到下限 0.5：**

```
第 1 次误报：0.8
第 2 次：0.8   × 0.9 = 0.72
第 3 次：0.72  × 0.9 = 0.648
第 4 次：0.648 × 0.9 = 0.5832
第 5 次：0.5832 × 0.9 = 0.52488
第 6 次：0.52488 × 0.9 = 0.472392 → Math.max(0.5, …) = 0.5   ← 触底
```

**→ 6 次误报打到底。**

**从 0.5 回升到 1.0（封顶）：**

```
需要 0.5 × 1.05ⁿ ≥ 1.0
→ 1.05ⁿ ≥ 2
→ n ≥ ln2 / ln1.05 ≈ 0.6931 / 0.04879 ≈ 14.2
→ 需要 15 次正报
```

**→ 15 次正报才能回满。**

**6 : 15 —— 破坏比修复快 2.5 倍。**

**这个不对称是有意的**（"防误报"偏向），**但它有一个必须知道的后果：**

> **一条规则一旦被误标了几次（比如有人手滑、或者不同团队对同一条规则看法不同），它需要两倍多的时间才能恢复。**
>
> **而在这段恢复期里，它对所有团队的输出都被压低了**（因为准确率不分团队 —— 下一节）。

**注意这个不对称在"误报"和"漏报"之间选择了"漏报"：**

- 准确率低 → 置信度低 → 在去重/仲裁的平局里**更容易输** → **更不容易被看到**。

**所以这条曲线的实际含义是：宁可漏掉这条规则，也不要让它继续刷屏。**

**这是一个合理的工程偏向**（噪声比漏报更伤害用户信任），**但前提是"置信度真的会影响是否展示"。** 而在本项目里，`confidence` 只影响**平局时的取舍**，**不影响"是否展示"** —— 也就是说：

> **校准的效果被限制在了一个很小的作用面上。**
>
> **它不会让一条低置信度的发现消失** —— 它只会在"同位置、同严重级别、同 Agent"的极罕见平局里决定谁留下。**而"同严重级别同 Agent 同位置"这种情况，去重通常已经处理掉了。**
>
> **这意味着：即使校准正常工作，它也几乎没有可观测的效果。**

**这是"机制正确但作用面太小"的典型。** 补法有两条：

| 方向 | 做法 |
|---|---|
| **让它影响"是否展示"** | 加一条阈值：`calibrated < threshold` 的发现降级为 `INFO` 或移入"低置信度"分区 |
| **让它影响"排序"** | 报告里按 `calibrated` 降序排列（当前是按 `Severity` 分组、组内按原始顺序） |

**这两条都比"只在平局时用"有意义得多。** 而**做这个决定的前提，是你先知道"当前的校准效果有多小"** —— 这又回到了"可观测性"。

**把不对称译成"系统健忘"的时标，你才知道该设多大的恢复窗。** 0.8 / 0.9 / 1.05 这套参数给出两个特征时标：

> **半衰期（误报）**：0.9ⁿ = 0.5 → n = ln0.5/ln0.9 ≈ **6.6 次误报，准确率砍半**（对比上面"6 次触底"的全程）：误报不到 7 条负反馈就把一条规则的可信度腰斩。
> **回升时标（正报）**：从 0.5 回满到 1.0 需 15 次、回到 0.9 需 0.5×1.05ⁿ ≥ 0.9 → n = ln1.8/ln1.05 ≈ **12 次正报**；若一条规则平均每几天才被正反馈一次，那么一记手滑误报，**要让准确率爬回 0.9 大约要 2~3 周的真实数据**。
> 于是：**破坏半衰 ≈ 7 条；恢复大半 ≈ 12 条 → 这就是 2.5 倍不对称在时间轴上的投影。**

**工程判据：** **调"破坏/修复"不对称比前，先定两个可观测信号——① 误报半衰期（衰减到 0.5 需要的负反馈条数）与② 回升时标（从 0.5 回到 0.9 需要的正反馈条数）；要求 ① ≤ ②（破坏快、修复慢，守住"宁可漏报"的偏向），并保证校准的作用面真的影响"是否展示"或"排序"，而不仅是平局。** 一条只用于平局、连半衰期都测不出来的校准，等于没校准——给它加一个作用面，再谈参数。

### 2.4 派生状态：为什么 `ruleAccuracy` 必须落库

```java
// core/calibration/ConfidenceCalibrationService.java:20-32
/**
 * 置信度校准服务（越用越准，降低误报）。
 * ...
 * <p><b>持久化（集群改造）</b>：规则准确率是<b>派生状态</b>——反馈事件本身已落库，
 * 但派生出的 {@code ruleAccuracy} 若只存内存，进程重启或<b>多实例各自为政</b>时
 * 校准学习互相不可见。本服务每次标记后把 {@code ruleAccuracy} 快照写入
 * {@link CalibrationStore}（生产为 PG {@code calibration_accuracy}），构造时自动加载，
 * 重启/换实例不丢失——A 机的反馈学习 B 机同样生效。
 */
```

**"派生状态"这个词是关键。**

**什么是派生状态？**

| 类型 | 例子 | 特点 |
|---|---|---|
| **事实（source of truth）** | 反馈事件（`review_feedback` 表的一行） | **不可推导**，必须存 |
| **派生状态** | 规则准确率（`calibration_accuracy` 表的一行） | **可以从事实重新算出来** |

**"可以算出来"意味着它理论上不需要持久化** —— 重启后把全部反馈重放一遍就能恢复。

**但实践上必须持久化，原因有两个：**

1. **重放成本**：反馈积累到几万条时，启动重放会拖慢启动；
2. **⭐ 多实例一致性**：A 机处理了一次误报 → A 的内存里准确率降到 0.72；**B 机完全不知道** → B 机继续用 1.0 校准。**同一个规则在两台机器上有两个准确率** → 同一个 PR 被哪台机器处理，结果不同。

**第二个原因才是真正的动因。** 类注释里写的"A 机的反馈学习 B 机同样生效"，说的就是这件事。

**而 `persist()` 是"全量快照"：**

```java
// core/calibration/ConfidenceCalibrationService.java:138-148
/** 每次标记后全量写快照（规则量小）。持久化失败不影响校准本身。 */
private void persist() {
    if (store == null) {
        return;
    }
    try {
        store.saveAll(ruleAccuracy);
    } catch (Exception e) {
        log.warn("[Calibration] 写入准确率快照失败（本次学习仅存内存）：{}", e.getMessage());
    }
}
```

**"规则量小"是"全量写"的依据** —— 如果规则有几十万条，全量写就不可接受了。

**这是一个重要的判断习惯**：

> **"全量覆盖写"能不能用，取决于"集合有多大"。**
> **规则数量是几十到几百量级 → 全量写没问题。**
> **如果换成"每个发现"（可能几百万）→ 必须改成增量写。**
>
> **而"规则量小"这个前提，是随系统演化会变的** —— 如果哪一天规则真的涨到几万条，**这里的全量写会变成一个缓慢变严重的性能问题。**

**`saveAll` 的实现用了逐行 UPSERT：**

```java
// core/store/PgCalibrationStore.java:42-67
@Override
public void saveAll(Map<String, Double> ruleAccuracy) {
    if (ruleAccuracy == null) {
        return;
    }
    try (var conn = db.conn()) {
        conn.setAutoCommit(false);
        try (var ps = conn.prepareStatement("""
                INSERT INTO calibration_accuracy (rule_id, accuracy, updated_at)
                VALUES (?, ?, now())
                ON CONFLICT (rule_id) DO UPDATE SET accuracy = EXCLUDED.accuracy, updated_at = now()
                """)) {
            for (var e : ruleAccuracy.entrySet()) {
                ps.setString(1, e.getKey());
                ps.setDouble(2, e.getValue());
                ps.addBatch();
            }
            ps.executeBatch();
            conn.commit();
        } catch (Exception ex) {
            conn.rollback();
            throw ex;
        }
    } catch (Exception e) {
        log.warn("[Calibration] 规则准确率写入失败（本次学习仅存内存）：{}", e.getMessage());
    }
}
```

**三个正确的做法：**

**① 显式 `setAutoCommit(false)` + `commit()`。**

`PgDb` 的连接池可能默认 `autoCommit = true`。**批量 UPSERT 必须在一个事务里** —— 否则要么每条都提交（慢），要么失败时不一致。

**② 内层 `catch` 先 `rollback()` 再 `throw`。**

**这一层不能省**：外层 `catch` 只打日志、不 rollback —— **如果内层不 rollback，连接被归还到池里时事务还开着**，下一个拿到这条连接的操作会看到一个"脏"的事务状态。

**③ `UPSERT` 而不是 `DELETE + INSERT`。**

全量写有一个陷阱：**如果实现成"先清空表再插入"，那么"内存里少了某条规则"就会导致磁盘上那条被删掉。**

**用 `ON CONFLICT DO UPDATE` 就没有这个问题** —— 它只覆盖存在的键，**不会删除内存里没有的键**。

> **这个细节在"load 失败"的场景下很关键**：如果启动时 PG 读不到数据（准确率从空开始），后续 `persist()` 会**只更新自己学到的那几条**，**不会把 PG 里其他规则的记录抹掉。**
>
> **反例（用 `DELETE + INSERT`）**：启动时读失败 → 内存为空 → 第一次反馈触发 persist → **全表清空，只剩那一条** → **几周的校准学习一次性清零。**

### 2.5 落库点广播：比"每个调用方接线"更稳

**修复"校准空转"为什么选择在 `FeedbackStore` 上挂钩子，而不是在 API 控制器里调用？**

`FeedbackListener` 的注释给了答案：

> **"在落库点广播事件，比在每个调用方各自接线更稳：将来新增反馈入口只需存储实现不变。"**

**对比两种接法：**

| | 在 API 控制器里调 | **在落库点广播（当前）** |
|---|---|---|
| 新增一个反馈入口（控制台 / 工作流 / 批处理） | **要去新入口里再调一遍** —— 漏了就是又一处空转 | **自动生效** |
| 反馈入口有几个 | 3 个（REST + 工作流 + …） | 只需 `FeedbackStore` 实现正确 |
| 失败风险 | 与入口数量成正比 | **与入口数量无关** |

**这就是"唯一咽喉"的价值** —— 类注释里那句话是字面意思的：

```java
/**
 * 反馈存储（误报反馈闭环的持久化入口）。
 * ...
 * <p>负责保存开发者对审查发现的反馈，并在聚合阶段提供"已确认的误报"列表，
 * 用于抑制重复误报。...
 */
```

**"唯一持久化咽喉"** —— 所以**在咽喉上装监听器，就是覆盖了所有入口。**

**实际接线在装配层：**

```java
// config/ReviewAgentConfig.java:627-648
/**
 * 反馈落库复合监听器：一条反馈同时驱动两路旁路——
 * ① 置信度校准（规则准确率衰减/回升）；② 经验证据登记（正报升级 ACTIVE / 误报降级 ARCHIVED）。
 * 装配进 {@link FeedbackStore}（StateStoreConfig 提供 PG / 内存实现）。
 *
 * <p>{@code @Primary}：{@code ConfidenceCalibrationService} 也实现 {@link FeedbackListener}，
 * 而反馈存储需要的是「两路都跑」的复合监听器——标注后 ObjectProvider / 类型注入
 * 默认取本复合实现，避免容器内 FeedbackListener 双候选歧义。
 */
@Bean
@Primary
public FeedbackListener feedbackListener(ConfidenceCalibrationService calibration,
                                         ExperienceStore experienceStore) {
    return (teamId, feedback) -> {
        calibration.onFeedback(teamId, feedback);
        if (feedback != null && feedback.ruleId() != null && !feedback.ruleId().isBlank()) {
            try {
                experienceStore.recordFeedback(teamId, feedback.ruleId(), feedback.isFalsePositive());
            ...
```

**三个设计点：**

**① 复合监听器：一次落库，两路旁路。**

- 置信度校准（本讲）；
- 经验证据登记（第 10 讲的 `ExperienceStage` 升级/降级）。

**两路都在同一个反馈事件上触发** —— 因为它们需要的是**同一份事实**（"这条规则被标为误报了"）。

**② `@Primary` 解决"双候选歧义"。**

`ConfidenceCalibrationService` **本身就是** `FeedbackListener` 的实现（`implements FeedbackListener`），而装配层又定义了一个**复合** `FeedbackListener` Bean。

**于是容器里有两个 `FeedbackListener` 候选 → 按类型注入会歧义。**

**注释解释了为什么用 `@Primary` 而不是别的手段**：容器里其他按类型注入的地方应该拿到"两路都跑"的实现。

> **对比一个反面做法**（你在别的项目里可能见过）：**为了消除歧义，把 `ConfidenceCalibrationService` 从 `FeedbackListener` 的实现关系里摘掉。**
>
> 那样做的后果是：**装配层必须显式调用 `calibration.onFeedback(...)`** —— 而一旦有第二个调用点，**"漏接线"的风险又回来了**（正是本讲故障二）。
>
> **当前做法保留了"校准服务天然就是一个监听器"这个事实**（所以它可以被单独注册、被单独测试），**同时用 `@Primary` 告诉容器"注入时优先用复合的"。**
>
> **判断依据**：**`@Primary` 用于"有一个明确的默认选择"；`@Qualifier` 用于"每个注入点自己挑"。** 这里显然是前者。

**③ `calibration.onFeedback(...)` 没有 try/catch，而 `experienceStore.recordFeedback(...)` 有。**

**看起来不一致，但它是安全的**，因为**外层还有一层**：

```java
// core/store/PgFeedbackStore.java:35-45
@Override
public void save(String teamId, ReviewFeedback feedback) {
    try {
        String payload = mapper.writeValueAsString(feedback);
        db.update("INSERT INTO review_feedback (team_id, payload) VALUES (?, ?::jsonb)",
                teamId, payload);
        try {
            listener.onFeedback(teamId, feedback);
        } catch (Exception e) {
            log.warn("[Feedback] 反馈监听器执行失败（不影响落库）：{}", e.getMessage());
        }
    } catch (Exception e) {
        log.warn("[Feedback] 反馈落库失败：team={}, 原因={}", teamId, e.getMessage());
    }
}
```

**注意监听的调用在落库之后、且在独立的 try/catch 里** —— 这实现了 `FeedbackListener` 注释的契约：

> **"实现方只消费数据，不做任何写回（观测旁路，抛异常不得影响反馈保存本身）。"**

**"先落库、后通知"的顺序也很重要**：如果反过来（先通知再落库），那么监听器抛异常就会**导致反馈本身没被保存** —— 用户点了"误报"，系统既没记住，也没学到。

> **这是一个可复用的顺序原则：**
> **"记录事实"必须在"消费事实"之前。**
> **因为事实是唯一的，而消费者可能有很多个、每个都可能失败。**

### 3.1 ★ LLM 路径不做校准：学习了两套，只用了一套

**问题在三处代码的对比里：**

```java
// ① 技能型发现 —— 校准 ✅
protected Finding toFinding(SkillResult sr) {
    double conf = calibration.calibrate(sr.ruleId(), sr.confidence());
    ...
}

// ② 规则型便捷构造 —— 校准 ✅
protected Finding ruleFinding(String file, int line, String ruleId, ...) {
    double conf = calibration.calibrate(ruleId, 0.95);
    ...
}

// ③ LLM 型发现 —— 不校准 ❌
private List<Finding> mapFindings(List<ReviewFindingDto> dtos) {
    ...
    double confidence = d.confidence() == null ? 0.75 : d.confidence();
    out.add(new Finding(getType(), file, line, line, severity, category,
            d.ruleId() == null || d.ruleId().isBlank() ? "LLM-" + getType().name() : d.ruleId(),
            ..., confidence, "LLM"));
    ...
}
```

**而 `markFalsePositive` / `markTruePositive` 是不区分来源的** —— 只要 `ruleId` 非空，就会更新准确率：

```java
@Override
public void onFeedback(String teamId, ReviewFeedback feedback) {
    if (feedback == null || feedback.ruleId() == null || feedback.ruleId().isBlank()) {
        return;
    }
    if (feedback.isFalsePositive()) {
        markFalsePositive(feedback.ruleId());
    } else {
        markTruePositive(feedback.ruleId());
    }
}
```

**于是产生了一个"半死"的功能：**

| 反馈对象 | 学习发生了吗 | 学习被用了吗 |
|---|---|---|
| 规则型发现（`SKILL` / `RULE`） | ✅ | ✅ |
| **LLM 型发现**（`LLM`） | ✅ **（accuracy 真的降了）** | ❌ **从不被读取** |

**所以：对一个 LLM 发现标记误报，你实际上"写了一条永远不会被读的记录"。**

**更细的观察**：LLM 发现的 `ruleId` 兜底值是：

```java
d.ruleId() == null || d.ruleId().isBlank() ? "LLM-" + getType().name() : d.ruleId()
```

**兜底值是 `"LLM-SECURITY"` 这种"按 Agent 类型"的粒度。**

**这意味着**：如果模型没有输出 `ruleId`（很常见——prompt 里要求它给，但它经常忽略），**那么安全 Agent 的所有 LLM 发现共享同一个规则 ID。**

**一旦校准真的被接上**（修好 3.2 节之后），**这个兜底值会带来一个副作用**：**对任意一条安全类 LLM 发现标记误报，会拉低"LLM-SECURITY"这个伪规则的准确率，从而影响该 Agent 的所有 LLM 发现。**

> **这是"兜底值充当身份"的典型风险：**
> **`"LLM-" + getType().name()` 是一个"看起来像 ID、实际上是分类"的值。**
> **它当 ID 用会带来过粗的聚合。**
>
> **修法**：兜底值应该是"**无 ID**"（`null` 或空），让校准显式跳过它 **而不是**造一个假的 ID。
> **"不知道"和"知道它是一个大类"是两回事** —— 用一个看起来合理的默认值把前者伪装成后者，是很多隐性 bug 的来源（对比第 07 讲的"网关静默空串"）。

### 3.2 ★ 加载失败静默从空开始：又一个"没有失败信号"

```java
// core/calibration/ConfidenceCalibrationService.java:130-136
/** 构造时加载已有快照；后端缺失 / 异常时不阻断启动（退化为无学习记录）。 */
private void load() {
    if (store == null) {
        return;
    }
    try {
        Map<String, Double> loaded = store.loadAll();
        ruleAccuracy.putAll(loaded);
        log.info("[Calibration] 已恢复 {} 条规则准确率（共享存储）", loaded.size());
    } catch (Exception e) {
        log.warn("[Calibration] 读取准确率快照失败（本次从空开始）：{}", e.getMessage());
    }
}
```

**而 `PgCalibrationStore.loadAll` 更彻底 —— 它自己把异常吃掉，返回空 Map：**

```java
// core/store/PgCalibrationStore.java:25-39
@Override
public Map<String, Double> loadAll() {
    try (var conn = db.conn();
         var ps = conn.prepareStatement("SELECT rule_id, accuracy FROM calibration_accuracy");
         var rs = ps.executeQuery()) {
        Map<String, Double> out = new HashMap<>();
        while (rs.next()) {
            out.put(rs.getString(1), rs.getDouble(2));
        }
        return out;
    } catch (Exception e) {
        log.warn("[Calibration] 规则准确率读取失败（从空开始）：{}", e.getMessage());
        return Map.of();
    }
}
```

**注意：`loadAll` 把异常转成了 `Map.of()`，所以 `load()` 里的 `catch` 在 PG 实现下永远不会被触发。**

**结果**：PG 短暂不可用 → 校准从 1.0（默认）开始 → **所有规则都被当成"从未被反馈过"** → **校准静默退回"未启用"状态。**

**好消息**：因为 `saveAll` 用的是 UPSERT（2.4 节），**它不会把 PG 里已有的记录删掉** —— 数据还在，只是这个实例暂时"看不见"。

**坏消息**：**"看不见"这件事只有一个 WARN 日志，而它会淹没在启动日志里。**

**两个改进方向：**

| 方向 | 做法 |
|---|---|
| **让"读失败"和"没有记录"可区分** | `loadAll` 改成抛异常（或返回 `Optional`），由 `load()` 决定是"从空开始"还是"降级告警" |
| **给校准一个可观测出口** | 暴露一个只读端点：`GET /admin/calibration` 返回 `ruleAccuracy` 的条数与样本 |

**第二个方向是本讲"核心问题"的正面回答。**

> **对"没有失败信号的功能"，唯一有效的办法是：给它一个能被主动查询的状态。**
>
> 本项目的启发式指标可以是：
>
> ```json
> {
>   "rulesLearned": 37,              // ruleAccuracy 的条数
>   "oldestFeedbackAt": "...",       // 最早一条反馈的时间
>   "lastUpdatedAt": "...",          // 最近一次 persist 的时间
>   "storeAvailable": true
> }
> ```
>
> **`rulesLearned = 0` 就是一个明确的信号**：
> - 要么**从没有人反馈过**（那"校准空转"就不奇怪了）；
> - 要么**反馈落库点没有触发监听器**（校准空转 —— 正是本讲故障二）；
> - 要么**存储读不到**（3.2 节这种情况）。
>
> **三条可能的原因，一个数字就能让你开始排查。** 而当前状态下，这三条原因**在系统里都没有任何出口**。

### 3.3 ★ 准确率不分团队：与"全局基线 + 团队叠加"模型的冲突

**代码注释自己承认了这一点：**

**"当前校准按规则全局生效，不区分团队"** —— 而且 `teamId` **在方法体里完全没有被使用**。

**这与系统其他部分的模型不一致：**

| 数据 | 隔离粒度 |
|---|---|
| 技能启停 / 自定义规则 | **按团队**（`SkillRegistry.getEnabledSkillsForCategory(teamId, category)`） |
| 知识库 | **按团队 + `__global__` 基线**（`PgKnowledgeStore`） |

| 自定义 Agent | **按团队**（`CustomAgentStore.listEnabled(teamId)`） |
| 断点 | **按团队**（`ResumeStore.load(runId, teamId)`） |
| **置信度准确率** | **❌ 全局** |

**后果，用一个具体场景说明：**

```
支付团队：认为 "SEC-007（SQL 注入检测）" 太激进，标了 3 次误报
         → accuracy = 0.8 × 0.9 × 0.9 = 0.648

前端团队：非常需要这条规则，且从未标记过误报
         → 他们理应拿到 accuracy = 1.0

实际：两个团队都拿到 0.648
```

**更糟的是"跨租户干扰"的性质**：

> **A 团队的行为改变了 B 团队看到的报告。**
>
> **这不仅是"不精准"，它还是一条租户隔离的缺口** —— 虽然影响面是"置信度数值"而不是"数据泄露"，**但它意味着"团队隔离"这个承诺在置信度这一维度上是不成立的。**
>
> **而报告里不会有任何提示**：前端团队看到置信度 0.616（= 0.95 × 0.648），**它无从知道这个数字是被别的团队"投票"投下来的。**

**修法的代价不小**（需要把 `ruleAccuracy` 从 `Map<String, Double>` 改成 `Map<TeamKey, Map<String, Double>>`，并把 `calibration_accuracy` 表的主键从 `rule_id` 改成 `(team_id, rule_id)`）—— **所以它当前是有意未做的。**

**但"有意未做"必须被显式记录：**

- ✅ 代码注释里写了（这一点做得对）；
- ❌ 但**没有写进"已知限制"清单**（README / 设计文档），**也没有在报告里体现**；
- ❌ **更没有一条单测锁定这个行为** —— 于是有一天有人"顺手修好了隔离"，**反而会因为改变了行为而惊讶**。

> **一条经验：对"有意未做"的约束，最有力的记录方式是"一条锁定当前行为的测试"。**
>
> ```java
> @Test
> void calibration_isGlobal_notPerTeam_byDesign() {
>     service.markFalsePositive("SEC-007");
>     // 故意不带 teamId —— 当前设计下准确率是全局的
>     assertEquals(0.8, service.accuracy("SEC-007"), 1e-9);
> }
> ```
>
> **测试名里带 `byDesign`** —— 后来的人一看到就知道"这是有意为之，不是漏了"。**这比注释更难被忽略。**

### 3.4 校准在本项目里的完整数据流


<img class="mermaid-svg" src="/zh/book-assets/diag-0073.svg" alt="### 3.4 校准在本项目里的完整数据流" />


> **图 19-1**　一次"误报"点击之后的完整数据流。**`FeedbackStore.save` 是唯一的咽喉**：两条消费路径（校准、经验）都挂在它的广播之后——这也正是"第 3 跳断过"这个故障的根因位置。

**两路旁路的对比很值得看：**

| | 置信度校准 | 经验证据登记 |
|---|---|---|
| 是否用 `teamId` | **❌ 不用（全局）** | **✅ 用（按团队）** |
| 存储 | `calibration_accuracy`（rule_id 主键） | `experience_entry`（team_id + pattern） |
| 作用 | 调低/调高置信度 | 改变经验条目的生命周期状态 |
| 生效位置 | 生成 `Finding` 时（`calibrate`） | 生成 RAG 上下文时（`getRelevantExperiences`） |
| **生效可见性** | **❌ 完全不可见**（只是一个更小的数） | **✅ 可见**（经验条目出现/消失在【历史经验参考】分区里） |

**最后一行是关键差别：**

> **同一个反馈事件驱动两路旁路，其中一路完全不可见。**
>
> **这不是巧合** —— 经验通道的产物是**文本**（会出现在 prompt 里，能被读到），而校准通道的产物是**一个系数**（只会让某个数字小一点）。
>
> **产物形态决定了可观测性。** 当你要判断"这个功能有没有在工作"时，**"能不能直接看到它的产物"比"有没有埋点"更重要。**

## 四、避坑清单

- [ ] **字段存在 ≠ 功能存在。** 有 `confidence` 字段、有 `accuracy` 表、有校准公式 —— **都不代表校准在生效。要检查"谁调用了它"。**
- [ ] **"没有失败信号的功能"要主动给一个查询出口**（如 `GET /admin/calibration` 返回 `rulesLearned`）。
- [ ] **学习维度要选"样本量足够"的那一级**（按规则，而不是按发现）。
- [ ] **`Map.merge` 的三个参数语义要先确认**：初值 / 重映射函数 —— 初值决定了"第一次"的行为。
- [ ] **衰减和回升的不对称要算出来**（本项目 6 次打到底、15 次才回满，**2.5 倍不对称**）。
- [ ] **校准的作用面要能影响"是否展示/排序"**，否则它几乎没有可观测效果（只在平局时用 = 白做）。
- [ ] **派生状态在多实例下必须落共享存储**，否则同一规则在不同机器上有不同准确率。
- [ ] **全量快照写要用 UPSERT，不要 `DELETE + INSERT`** —— 后者在"加载失败"时会把历史学习一次性清零。
- [ ] **批量写要显式 `setAutoCommit(false)`，且内层 catch 必须先 `rollback()` 再 `throw`**。
- [ ] **"记录事实"必须在"消费事实"之前**（先落库、后广播），否则消费者抛异常会导致事实丢失。
- [ ] **在"唯一咽喉"上挂监听器**，而不是在每个调用方接线 —— 新增入口自动生效。
- [ ] **`@Primary` 用于"有明确默认选择"**；保留"服务天然实现某接口"的事实（便于单独测试），而不是为了消歧义把实现关系摘掉。
- [ ] **LLM 路径没接校准 = 学习了一整套但只用了一半**：`accuracy` 真的降了，但从不被读。
- [ ] **兜底值不要伪装成 ID**（`"LLM-" + getType()` 是分类，不是 ID）—— 过粗的聚合会带来意外的影响面。
- [ ] **"有意未做"的隔离缺口要用"名字里带 `byDesign` 的测试"锁定**，光有注释会被忽略。

## 本讲小结

1. `confidence` 存在，但只用在**去重和仲裁的平局**里 —— **它几乎不产生决策差异**。
2. **修复前 `markFalsePositive` / `markTruePositive` 全仓零调用**："越用越准"是一个**从未生效过的完整功能**。
3. **这类故障没有失败信号** —— 报告正常、无异常、无降级；**唯一对策是给它一个可主动查询的状态出口**。
4. 校准的**学习维度是"规则"而不是"发现"**（因为规则才有足够样本）。
5. `Map.merge` 的**初值**决定了第一次的行为：**误报首击落到 0.8（真降），正报首击置 1.0（no-op）**。
6. **衰减 6 次到底，回升 15 次回满 —— 2.5 倍不对称**，偏向"宁可漏掉这条规则"。
7. **校准的作用面太小**（只在平局时影响取舍）→ 即使正常工作也几乎不可观测。
8. **派生状态在多实例下必须落共享存储**，且**全量写必须用 UPSERT**（否则加载失败会清零历史）。
9. **"先落库、后广播"**：事实先记下来，消费者失败不影响事实。
10. **在唯一咽喉上挂监听器**，比在每个调用方接线更稳。
11. **LLM 路径不校准**：`accuracy` 真的降了，但**从不被读取** —— 学习了一整套只用了一半。
12. **准确率不分团队，与全局其他数据的隔离模型不一致** —— 且**只在注释里记了，没有 `byDesign` 测试锁定**。
