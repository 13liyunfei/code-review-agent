# 第 14 讲 · 为什么需要多 Agent

> 🎯 导读问题：**"你为什么用多 Agent？一个 Agent 不够吗？"**（这一问考的是判断力，不是技术）

> **图 14-0**　本讲地图：多 Agent 不是默认选项，而是一道四级判据：判断标准、失败模式、真实冲突、独立观测。任一不满足就不该拆，通过后还要认下成本翻 N 倍，以及仲裁、编排、聚合三个新问题。

## 一、痛点

第一版代码审查系统只有**一个 Agent**。

提示词大概是这样的：

```
你是一位资深工程师。请从「逻辑、安全、性能、编码规范、架构」五个维度审查以下代码变更。
请以 JSON 数组输出，每条包含 file / line / severity / title / description / suggestion。
```

跑通之后，你会依次遇到三个现象：

**现象一：什么都提到一点，什么都说不深。**

输出是这样的（真实形态）：

```json
[
  {"severity":"MAJOR","title":"存在 SQL 拼接风险","description":"建议使用参数化查询"},
  {"severity":"MINOR","title":"变量命名建议更语义化","description":"userList 可改为 activeUsers"},
  {"severity":"MAJOR","title":"循环内查询数据库可能导致 N+1","description":"建议批量查询"},
  {"severity":"MINOR","title":"缺少注释","description":"建议补充方法注释"}
]
```

每一条都对，但**每一条都像是从清单里抄的**。它没有告诉你这个改动的真正风险在哪。

**现象二：输出配比是"均衡"的，而真实风险不是。**

五个维度的发现数差不多。**但一个真实的 PR 里，五个维度的风险从来不是均等的**——有的改动全是安全问题，有的改动只有性能问题。

模型的"均衡"是它在 prompt 里看到"五个维度"之后的自然反应：**每个维度给 1-2 条，显得都照顾到了。**

**现象三（最致命）：安全发现排在风格发现后面。**

一个 JSON 数组里混着五类问题，模型自己决定排序。而它排序的依据通常是**在代码里出现的顺序**，不是严重程度。

于是一条"SQL 注入"可能被四个"缺少注释"挤到列表末尾——**评审人看到前四条就关掉了 PR 评论。**

**而你想调"安全审得严一点"时，发现自己做不到。** 提示词是一个整体，改动任何一句都可能影响其他四个维度。

## 二、原理

### 2.1 单体的五个天花板

| 天花板 | 机制 | 症状 |
|---|---|---|
| **注意力稀释** | 一个 prompt 里放了 5 个任务，模型把注意力平均分配 | 每个维度都浅（现象一） |
| **输出配比失衡** | 一个数组里 5 类混排，条数配额由模型自己定 | 严重的被淹没（现象二、三） |
| **故障耦合** | 一次调用失败 = 全部维度失败 | 一次超时，整份报告为空 |
| **上下文预算** | 5 个维度各要注入知识与历史，挤在同一个 prompt 里 | 顶爆窗口（第 12 讲） |
| **不可独立调参** | 提示词是一个整体 | 无法"只让安全更严" |

**注意第二个和第五个的关系**：因为配比由一个 prompt 决定，所以调参也只能整体调。**"不可独立调参"不是"不方便"，而是"这个系统无法针对风险分布做优化"。**

### 2.2 判据：什么时候该拆（任务正交性）

拆 Agent 不是"越多越好"。**拆错方向比不拆更糟**——你付出了 N 倍成本，换来的是 N 个各自平庸的输出。

判断标准是**任务正交性**，有三条，必须同时满足：

**判据一：判断标准不共享。**

把本项目五个维度的判据写出来：

| 维度 | 这一维度在问什么 |
|---|---|
| 逻辑 `LOGIC` | 这段代码**会不会算错**？ |
| 安全 `SECURITY` | 这段代码**会不会被利用**？ |
| 性能 `PERFORMANCE` | 这段代码**会不会慢**？ |
| 规范 `STYLE` | 这段代码**符不符合团队的写法**？ |
| 架构 `ARCHITECTURE` | 这段代码**放在这里合不合适**？ |

**五个问题各自独立**：一段代码可以"算得对但会被注入"，也可以"很安全但是 O(n²)"。**没有哪一个维度的结论能推出另一个维度的结论。**

**判据二：失败模式独立。**

安全维度超时了，逻辑维度的结论**仍然有效**。

这一条直接决定了"降级"有没有意义（第 13 讲的 `AgentResult.degraded`）。**如果五个维度绑在一次调用里，那"部分降级"在物理上就不存在**——一次调用要么成功要么失败，你没有任何颗粒度可以保留。

**判据三：存在真实冲突。**

**这是最关键、也最容易被跳过的一条。**

两个维度必须真的会给出**互相矛盾**的建议。在本项目里这是成立的：

```
同一个配置项：
  逻辑 Agent：建议加防御性空值判断（防止 NPE）
  性能 Agent：建议去掉热路径上的分支（减少每次调用的开销）
```

```
同一个方法：
  架构 Agent：这个方法职责过重，建议拆成三个
  性能 Agent：拆成三个会引入额外的对象分配，建议内联
```

**为什么这一条最重要？因为它决定"你要不要做仲裁"（第 18 讲）。**

> **如果没有真实冲突，就不需要仲裁机制。**
> **而如果不需要仲裁机制，那"拆开"只是把一个 prompt 变成了五个 prompt —— 你没有获得任何新信息，只是付了五倍的钱。**

**判据四（工程判据）：拆出来的维度必须能被独立观测。**

如果你无法回答"上个月安全维度漏了多少、性能维度误报了多少"，那么拆开之后你仍然无法优化任何东西。

**这一条在实现上对应的是：每个 Agent 的 `AgentResult` 里必须携带 `agentType`。**

### 2.3 反面：什么情况不该拆

| 情形 | 为什么不该拆 |
|---|---|
| **两个"Agent"的结论永远一致** | 它们是同一个 Agent 的两段提示词 |
| **每个 Agent 的 prompt 里都要写"你也要顺便看看安全"** | 说明安全没被真正拆出去 |
| **拆完后每个 Agent 只处理 3 行代码** | 拆的单位太小了，调度和聚合成本超过收益 |
| **只是为了"看起来架构更高级"** | 这是最坏的理由 |

**第二种情形值得单独说。** 一个很常见的伪拆分是：

```
Agent A 的 prompt：你是逻辑审查专家……【另外，如果发现安全问题也要指出】
Agent B 的 prompt：你是安全审查专家……【另外，如果发现逻辑问题也要指出】
```

**这种"互相兜底"的写法让所有 Agent 的能力集合重新变成同一个。** 结果就是：同一个问题被报 5 遍（聚合阶段去重掉），而每个 Agent 的 prompt 都变长了（注意力再稀释一次）。

### 2.4 拆的代价：诚实的账

**买到了什么：**

| 收益 | 实现方式 |
|---|---|
| 独立调参 | 每个维度一套 prompt + 一套规则（第 11 讲） |
| 独立降级 | 一个维度超时不影响其他（第 13 讲） |
| 独立观测 | 每个 `AgentResult` 带 `agentType` |
| 可扩展 | 业务方加"支付合规审查"不用改内置 5 个（第 16 讲） |
| 可仲裁 | 冲突有明确的"谁说了算"（第 18 讲） |

**付出了什么：**

| 代价 | 具体 |
|---|---|
| **成本 ×N** | N 个 Agent = N 次（或更多）LLM 调用 |
| **新增三个问题** | 谁说了算（仲裁）、怎么并行（编排）、结果怎么合（聚合） |
| **调试复杂度上升** | 一次审查涉及 5 条独立链路 |
| **一致性风险** | 五个 Agent 对"什么算 Major"的理解会漂移 |

**最后一条是最隐蔽的。** 五个 Agent 各自判断严重级别，那么：

- 安全 Agent 觉得"任何注入风险都是 BLOCKER"；
- 性能 Agent 觉得"慢一点只是 MAJOR"；
- 规范 Agent 觉得"缺注释也是 MINOR，不是 INFO"。

**这些口径没有任何地方强制统一**，除非你显式设计它（第 18 讲的仲裁、第 19 讲的校准都在处理这件事）。

**诚实的账翻成数字才扎心。** 用"约 xx 元 / 百万 token"的示意口径（不是精确定价），假设一次审查里每个 Agent 的输入上下文（prompt + diff + 知识注入）稳定在 **3000 token**、输出约 **600 token**；取一个中等模型，输入约 **¥1 / 百万 token**、输出约 **¥3 / 百万 token**：

> **单 Agent 一次调用：**
> 输入 3000 × ¥1/1M = ¥0.0030；输出 600 × ¥3/1M = ¥0.0018
> 合计 ≈ **¥0.0048 / 次**
>
> **拆成 5 个 Agent（输出各自 600）：**
> 5 × (3000 × ¥1/1M + 600 × ¥3/1M) = 5 × ¥0.0048 ≈ **¥0.024 / 次**
>
> **折算到一台每天审 1000 个 PR 的引擎：**
> 单体 ≈ ¥4.8 / 天；5 Agent ≈ ¥24 / 天；按 22 个工作日 ≈ **¥106 / 月 vs ¥528 / 月**——差出四百多块，这就是"拆"的真实价格。

> **注意增量不是"线性"，是"每个 Agent 都要重吃一遍公共上下文"**：5 个 Agent 各自注入同一份 diff、同一份影响面、同一份 base prompt，成本从约 5 倍起跳，还会被"每个维度都要场景化注入知识"再放大（第 20 讲）。**拆之前这笔账不记，拆完就是被动续费。**

**工程判据：** **拆与不拆，先把成本账拍在桌上——拆分后单次审查的 token 预算必须允许约 ×K（K≈Agent 数）的放大；任何纯靠拆换来的"更均衡"，若没有『必须独立降级 / 必须独立观测』两条之一撑腰，就不在预算内，不拆。** 换句话说：**成本 ×N 不是"能接受"的事，而是要用判据一~四逐条换来的、明码标价的投入。**

> **模块三剩下 7 讲，全部在处理拆开之后新增的这三个问题。**
>
> **这一讲真正的价值是：在你拆之前，先确认你真的需要拆。**

### 2.5 前沿深挖：多 Agent 的性价比，业界是拿"实测"拍的板

要不要拆，业界也在用同一本"代价换上限"的账。2025 年 **Anthropic 发布的多 Agent 研究系统**就是一例：在软件工程复杂任务上，**多 Agent 协作把任务通过率从单 Agent 的约 50% 提到 65~70%，代价是约 15 倍的 token 消耗**——注意这不只是 5 倍，因为还要算规划、状态汇总、多轮重试的点数。**我记得的是近似数字，引用前请以原报告为准**，但它给出的量级关系是稳定的：**提升是"十几个点"，成本是"一个数量级"。**

拿这个量级对照本讲的四条判据，决策就清楚了：

- **通过率是跑基线测出来的，不是靠"多 Agent 理应更聪明"推出来的**——第 14 讲"动手任务"让你做的单 Agent vs 多 Agent 对照，正是这套实验的缩小版；
- **只有当任务靠一个 Agent 确实上不去（判据一~四都过）时，那 15 倍才花得值**；否则你只是买了个"看起来更均衡"的心理安慰；
- Anthropic 同期还强调**逐 Agent 单独观测 + 精细路由能显著改善**——这就是判断据四（独立观测）的同义词。

> **结论不变：多 Agent 上限更高但单价更贵；用不用，取决于你能否用单体够到那个上限。**

## 三、代码

### 3.1 七个 Agent 类型，一个枚举

<img class="mermaid-svg" src="/zh/book-assets/diag-0070.svg" alt="### 3.1 七个 Agent 类型，一个枚举" />


> **图 14-1**　`AgentType` 的七值枚举。**五个领域角色**（逻辑/安全/性能/规范/架构）是系统拆出来的专业审查维度，**两个拓扑角色**（CUSTOM / COORDINATOR）是架构层面的。CUSTOM 证明"正交维度"这个抽象是开放的；COORDINATOR 则是个值得警惕的信号——它永远不会出现在任何 `Finding` 里，意味着枚举的值域大于实际使用值域。

**注意这不是 5 个值，是 7 个。** 多出来的两个是：

- **`CUSTOM`** —— 业务方在后管声明的审查维度（第 16 讲详述）。它证明"正交维度"这个抽象是**开放的**：系统没有把维度写死在 5 个里。
- **`COORDINATOR`** —— 协调者。**它不是一个"审查 Agent"**：`Coordinator` 是另一个接口，没有 `ReviewAgent` 实现。

**这里有一个值得学的取舍：把"拓扑角色"和"领域角色"放进了同一个枚举。**

| | 好处 | 代价 |
|---|---|---|
| 同一个枚举 | 报告里统一用 `AgentType` 标识"这条发现是谁出的"；序列化只用一套类型 | **`COORDINATOR` 永远不会出现在任何 `Finding` 里** —— 枚举值域大于实际使用值域 |

**"枚举值域大于实际使用值域"是一类需要警惕的信号**：它意味着在某个 `switch (agentType)` 里，一定有分支是永远不会被走到的。**读代码时可以顺手 grep 一下 `COORDINATOR` 的使用点，判断它是"有意的类型声明"还是"没人清理的遗留"。**

### 3.2 接口的注释把架构决策写出来了

<img class="mermaid-svg" src="/zh/book-assets/diag-0071.svg" alt="### 3.2 接口的注释把架构决策写出来了" />


> **图 14-2**　星型拓扑的两个核心接口。`Coordinator` 是中央调度节点，`ReviewAgent` 是专业审查节点——一个 Coordinator 并行调度 N 个 ReviewAgent。**两处注释措辞一致地说"星型拓扑"**，这不是废话，它是一个已被决策过的架构选择：想改拓扑的人会先看到这段注释，被迫思考"为什么当初这么选"。

同一个决策在三个地方（`AgentType` / `ReviewAgent` / `Coordinator`）措辞一致地出现。

这一点不是废话，它有两个实际价值：

1. **对读者（包括三个月后的你自己）**：这是一个**已被决策过的架构选择**，不是"写到最后自然长成这样"。想改拓扑的人会先看到这段注释，然后被迫思考"为什么当初这么选"。
2. **对面试**：这是一个可以**直接引用**的架构判断依据。

## 四、避坑清单

- [ ] **拆之前先回答"这两个维度会不会给出互相矛盾的建议"。** 不会冲突 → 不需要拆。
- [ ] **拆出来的维度必须能被独立观测**（能单独回答"上个月这个维度漏了多少"）。
- [ ] **不要用"拆 Agent"解决"prompt 写得不好"** —— 那是第 11 讲的问题。
- [ ] **警惕"每个 Agent 都顺便看看安全"** —— 所有 Agent 的能力集合重新相同，等于没拆。
- [ ] **拆完必须同步建立"一致性约束"**（什么算 BLOCKER / MAJOR），否则五个 Agent 的分级口径会漂移。
- [ ] **枚举里出现"不会产出结果的值"（如 `COORDINATOR`）要留意** —— 条件分支里出现它往往是 bug。
- [ ] **拆的代价要写进成本模型**：N 个 Agent 意味着 N 倍的 token 预算（模块五要算这笔账）。
- [ ] **"部分可用"是拆的收益，前提是每个 Agent 有独立的失败边界**（`AgentResult` 级别的降级）。

## 五、动手任务

> **任务：用一个真实 PR 做对照实验。**
>
> **步骤**：
> 1. 写一个**单 Agent** prompt：把 5 个维度写进一个 prompt，要求输出 JSON 数组。
> 2. 挑 3 个真实 PR：一个纯文档改动、一个单文件小改动、一个跨 5 文件的中等改动。
> 3. 记录三个数字：**总发现数 / 各维度条数分布 / 你自己判定"这条真的重要"的条数**。
> 4. 换成 5 个 Agent（本项目现成实现），跑同样 3 个 PR，记录同样三个数字。
>
> **预期方向**（刻意不给"预期数字"——数字取决于你的模型和 PR）：
> - 单 Agent 的发现数**更少**；
> - 单 Agent 的维度分布**更均匀**（这正是"配额"现象）；
> - 单 Agent 里"真的重要"的**占比更低**。
>
> **重要**：**不要为了让对照"更好看"而编造数字。** 如果你跑出来差异不明显，那是一个**有价值的结论**——说明你的任务结构不需要拆。
>
> **附加思考题**：把单 Agent 版本的 prompt 改成"只审安全"，再跑一遍。你会发现**单维度 prompt 的效果接近甚至超过多 Agent**。这一轮对照才是"拆"的真正收益所在——**不是"多 Agent 更聪明"，而是"每个 Agent 的 prompt 更专注"。**

## 本讲小结

1. 单体的天花板有五个：**注意力稀释、输出配比失衡、故障耦合、上下文预算、不可独立调参**。
2. 拆的判据是**任务正交性**：判断标准独立 + 失败模式独立 + **存在真实冲突** + 可独立观测。
3. 第三条（存在真实冲突）最容易被跳过，而**它决定了你有没有必要做仲裁机制**。
4. 反面的伪拆分是"每个 Agent 都顺便看看别的维度"——能力集合重新重合，等于没拆。
5. 拆的代价是**成本 ×N**，以及新增三个问题：**仲裁、编排、聚合**——这就是模块三剩下的全部内容。
6. 本项目把正交维度固化成 `AgentType` 枚举，并**把"星型拓扑"显式写进三处注释**。
