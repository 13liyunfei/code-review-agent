# 第 20 讲 · 内容准入：把"噪音"挡在 token 计费之外

> 🎯 导读问题：**"你的 Agent 系统怎么控制成本？"**（答"加缓存"是初级答案；答"先判断该不该跑"才是架构答案）

> **图 20-0**　本讲地图：内容准入是漏斗：PR 先过 supports，纯文档能跳过四个 Agent。但跳过没写进报告，两三条发现会被误读成没问题；加上 PR 级准入配文件级成本，文档吃预算、代码被截断。

## 一、痛点

系统上线一个月，财务发来一张表：

```
2026-08  LLM 调用次数：18,442
         其中「仅含文档/配置变更的 PR」：  6,180 次   ← 33.5%
```

**三分之一的调用，花在了"没有代码可审"的 PR 上。**

这些 PR 是什么？看一眼清单：

```
- docs/ 目录下的 Markdown 批量更新（翻译、术语统一）
- .github/workflows/*.yml（改超时时间、改 runner 版本）
- 前端资源文件的路径调整
- CHANGELOG.md 发布记录
```

**这些 PR 里，没有一个字可以审出"逻辑错误"或"性能问题"。**

**故障一：每个这样的 PR，都触发了五次完整的 LLM 调用。**

五个 Agent 各跑一遍，**各自把 diff 塞进 prompt，各自请模型从"逻辑 / 安全 / 性能 / 规范 / 架构"五个角度审一遍**。模型给出的结果通常是：

```json
[]
```

或者：

```json
[
  {"severity":"INFO","title":"文档建议补充更新日期","description":"..."}
]
```

**"文档建议补充更新日期"** —— 这就是那 33.5% 的产出。

**故障二：更隐蔽的一种浪费——混合 PR。**

一个 PR 里有 **1 个 `.java` + 49 个 `.md`**（改了代码里的一个常量，顺带把文档全刷了一遍）。

**这个 PR 确实有代码可审。** 所以五个 Agent 都会跑。

**但它们拿到的是 50 个文件的 diff** —— 那 49 个 Markdown 文件**照样进了 prompt**。

**于是：**

- 49 个 md 的 diff 文本**吃掉了 prompt 预算**（第 16 讲讲过 `formatDiffs` 的**按文件均摊截断**：50 个文件平分预算，**那个 java 文件只能拿到 1/50 的额度**）；
- **真正的代码可能被截断掉了**；
- **而模型还要花注意力处理那 49 个文档文件**（第 14 讲：注意力稀释）。

**结果**：**成本全额付出，质量反而下降。**

**故障三：你不知道"这次有几个 Agent 没跑"。**

某次审查的日志：

```
[Coordinator] 按内容准入跳过 4 个 Agent（无代码文件可审）：[LOGIC, PERFORMANCE, STYLE, ARCHITECTURE]
```

**这条日志在。但报告里没有任何痕迹。**

**报告里只有：**

```
- 总发现数：2
- 严重级别统计：🔴 BLOCKER 0，🟠 MAJOR 1，🟡 MINOR 1，🔵 INFO 0
```

**读者无法知道"这次只跑了一个安全 Agent"。**

**而这个信息和"降级"一样重要**：

> **"这次审查覆盖了 5 个维度"和"这次审查只覆盖了 1 个维度"，是两份可信度完全不同的报告。**
>
> **报告里没写，读者就会默认"5 个维度都审了，都没问题"。**

**三个故障，指向同一件事：准入（该不该跑）是成本控制的第一道闸门，而它同时也是一个"覆盖度"的承诺。**

## 二、原理

### 2.1 四种"减少"，必须分清

到第 20 讲为止，系统里有**四种让发现变少 / 让调用变少的机制**。**它们的语义完全不同，混淆它们会导致"为了省成本而牺牲正确性"：**

| 机制 | 作用对象 | 何时发生 | 语义 | 留下痕迹吗 |
|---|---|---|---|---|
| **准入 `supports()`** | **Agent** | **调度前** | **"这个维度对这份内容不适用"** | ⚠️ 仅日志/轨迹，报告里没有 |
| **降级 `degraded`** | **Agent** | 执行后 | **"这个维度没看成"** | ✅ 报告告警块 |
| **抑制 `suppressed`** | **发现** | 聚合时 | **"人类已判定这是误报"** | ✅ 报告区块 |
| **仲裁 `overridden`** | **发现** | 聚合时 | **"它与另一个意见冲突，落败"** | ✅ 报告区块 |

**准入和降级的区别是最容易混的，也是最重要的：**

```
准入（supports=false）：这个维度「不需要」跑 —— 这是「设计决定」
降级（degraded=true） ：这个维度「需要」跑，但「没跑成」 —— 这是「故障」
```

**接口注释把这一点写得很清楚：**

```java
// core/agent/ReviewAgent.java:34-47
/**
 * 本 Agent 是否应当参与本次审查（按 diff 内容做细粒度准入）。
 *
 * <p>默认恒 true（行为与历史一致：全集并行）。语义型 Agent 可覆写此方法，
 * 例如当 PR 全部为文档/配置文件（无任何代码文件）时跳过 LLM 语义审查，
 * 只保留对任意内容都有价值的规则型/安全型 Agent——从而把 token 花在真正有对象的地方。
 *
 * <p>注意：本方法只做「内容相关性」准入，不做优先级排序；返回 false 的 Agent
 * 由 {@code Coordinator} 在调度前剔除，不会产生「降级」语义，报告维度相应减少。
 *
 * @param diffs 代码变更列表（与 {@link #review} 同源）
 * @param ctx   审查上下文（单 PR 内共享）
 * @return true=参与审查（默认），false=本次跳过
 */
default boolean supports(List<CodeDiff> diffs, ReviewContext ctx) {
    return true;
}
```

**"只做内容相关性准入，不做优先级排序"** —— 这一句划定了边界。

> **为什么准入不能做"优先级排序"？**
>
> 因为**优先级排序的正确做法是通过"严重级别 + Profile 过滤"**（第 11 讲的 `ReviewProfile`、第 18 讲的仲裁权重）。
>
> **用"准入"去做优先级，会产生一个不可接受的后果**：
>
> **一个 Agent 被跳过了，它的"没发现问题"和"没有问题"就无法区分。**
>
> 而优先级排序是"我跑了，但这个问题优先级低，所以不展示" —— **两种语义在报告里长得完全不同。**

**`default` 方法返回 `true` 也是一个有意的设计**：

> **默认"全都跑"。** 理由是**安全侧优先**：
> **如果一个 Agent 忘了覆写 `supports`，后果是"多花一次 LLM 调用"（成本问题）；**
> **如果默认返回 `false`，后果是"这个维度静默地永远不跑"（正确性问题）。**
>
> **默认值应该偏向"更安全的那一侧"，而不是"更省的那一侧"。**

### 2.2 为什么安全 Agent 不覆写 `supports()`

**四个 Agent 都覆写了：**

```java
// LogicAgent / PerformanceAgent / StyleAgent / ArchitectureAgent 各 57 行，都有同样的覆写
@Override
public boolean supports(List<CodeDiff> diffs, ReviewContext ctx) {
    // 纯文档/配置文件 PR 无代码逻辑可审，跳过以节省 LLM token
    return CodeDiff.containsCodeFile(diffs);
}
```

**而 `SecurityAgent`（152 行）没有覆写** —— 它继承了默认的 `return true`。

**这是有意的，理由很实在：**

**配置文件里藏着最危险的密钥泄露。**

```
.env                     ← 数据库口令、API Key
application.yml          ← 生产环境密钥
docker-compose.yml       ← 暴露的端口、默认口令
.github/workflows/*.yml  ← CI 里的 secrets
k8s/*.yaml               ← Secret 对象
```

**这些文件的扩展名是 `.env` / `.yml` / `.yaml` —— 按 `inferLanguage` 全都落到 `"unknown"`**（2.3 节详述）。

**所以如果安全 Agent 也按 `containsCodeFile` 准入，它会在"只改了 `application.yml`"的 PR 上被跳过** —— **而那恰好是密钥泄露风险最高的场景。**

**更关键的是：安全 Agent 的检测能力不依赖 LLM。**

```java
// core/agent/impl/SecurityAgent.java:80-96（结构）
@Override
public List<Finding> review(List<CodeDiff> diffs, ReviewContext ctx) {
    List<Finding> findings = new ArrayList<>();

    // ===== 1. 输入防护：逐文件分级 =====
    List<DiffInputGuard.Verdict> verdicts = inputGuard.assessAll(diffs);
    ...

    // ===== 2. 技能预扫描（确定性，高置信，无 LLM 风险；全量 diff 照跑） =====
    runSkills(diffs, ctx).forEach(sr -> findings.add(toFinding(sr)));

    // ===== 3. LLM 增强：BLOCK 文件已从输入中隔离，仅剩余文件参与 =====
    if (reviewable > 0) {
        ...
        findings.addAll(llmFindings("security_review", vars));
    }
    ...
}
```

**它的第 2 步是"技能预扫描" —— 纯规则、零 token、零 LLM 风险。** 而安全类规则（硬编码密钥、SQL 注入模式）**对配置文件和 yaml 一样有效**。

> **所以安全 Agent 的取舍是**：
> **"即使这个 PR 只有文档，也值得跑一遍规则扫描"** —— 因为**规则扫描不花钱**，而**漏一个密钥的代价远大于一次白跑。**
>
> **决策依据是"检查的边际成本 vs 漏检的边际损失"。** 当成本接近零（纯规则）时，**任何概率的损失都值得防。**
>
> **而语义型 Agent 的边际成本是"一次 LLM 调用"（真金白银）** —— 所以它们的准入门槛就必须更高。

**这与 2.1 节的"默认值偏向安全侧"是同一个道理：**

> **要不要跑，取决于"跑一次的代价"和"不跑的代价"的对比。**
> **纯规则的代价趋近 0 → 尽量跑；LLM 的代价是钱 → 必须审。**

### 2.3 `inferLanguage`：语言标识是"路由键"，不是展示字段

准入的判据是"有没有代码文件"，而 **"是不是代码"是由 `language` 决定的**：

```java
// core/model/CodeDiff.java:34-56
/**
 * 判断一组 diff 中是否含有「代码文件」（相对文档/纯配置文件而言）。
 *
 * <p>供 {@code ReviewAgent.supports(...)} 做内容相关性准入：纯文档/配置 PR
 * （如 README、CI yaml、资源文件——这些经 {@link #inferLanguage} 落为 "unknown"）
 * 没有代码语义可审，语义型 Agent 可据此跳过，把 token 花在真正有对象的地方。
 *
 * <p>判定口径：language 属已知代码语言（非 unknown）。xml/sql/bash 等因被
 * {@link #inferLanguage} 识别为具体语言，视为代码内容（SQL 注入/慢查询等
 * 语义审查仍有价值）；新增语言支持时同步扩展 {@link #inferLanguage} 即可，
 * 本方法自动生效。
 */
public static boolean containsCodeFile(List<CodeDiff> diffs) {
    if (diffs == null) {
        return false;
    }
    return diffs.stream().anyMatch(d -> d.language() != null
            && !d.language().isBlank()
            && !"unknown".equals(d.language()));
}
```

**口径是"黑名单式"的：只要不是 `unknown`，就算代码。**

**而 `inferLanguage` 的注释点出了一个极重要的性质：**

```java
// core/model/CodeDiff.java:58-72
/**
 * 根据文件扩展名推断语言类型。
 *
 * <p>取值对齐业界通用命名（tree-sitter grammar / GitHub linguist），而非自造缩写。
 * 这一点很关键：语言标识是分析引擎的**路由键**，若写成 {@code py} / {@code js}
 * 这类非标准缩写，注册表里按 {@code python} / {@code javascript} 注册就永远匹配不上，
 * 结果是「支持了该语言却静默不生效」——排查时极难发现。
 *
 * <p>历史上本方法把 {@code .py} 映射为 {@code py}、{@code .ts} 映射为 {@code js}
 * （TypeScript 被当成 JavaScript）。由于既有消费方全部只判断 {@code java}，
 * 修正这些取值不影响任何既有规则。
 */
```

**"语言标识是分析引擎的路由键"** —— 这句话的含金量很高。

**三个静默失效，全都由它引起：**

**① 路由失效（历史坑）**：把 `.py` 写成 `py`，那按 `python` 注册的 tree-sitter analyzer **永远匹配不上** → **"支持了 Python 却静默不生效"。**

**② 语义混淆（历史坑）**：把 `.ts` 写成 `js`（TypeScript 当成 JavaScript）→ **TypeScript 用 JS 的 grammar 解析** → 解析结果错但不报错。

**③ 准入失效（当前坑）**：`containsCodeFile` 用的是**黑名单**（`!= "unknown"`）。**如果哪天有人给 `.md` 加了一个映射**（比如 `case "md" -> "markdown"`），**那么"纯文档 PR"就会突然被认为是"有代码"** → **四个语义 Agent 全部重新开跑** → **成本立刻回到故障一的状态。**

**这个坑的形状值得单独记：**

> **黑名单口径的准入，让"新增一个映射"这个看似无害的改动，变成了一个成本开关。**
>
> **而且它是静默的** —— 没有测试会失败，日志里也不会有异常，**只有下个月的成本报表会告诉你。**
>
> **防御手段**：把"哪些语言算代码"变成一个**显式的白名单**，或者**加一条单测锁定"纯 md PR 的准入结果"**：
>
> ```java
> @Test
> void pureMarkdownPr_shouldSkipSemanticAgents() {
>     List<CodeDiff> diffs = List.of(new CodeDiff("README.md", "..."), new CodeDiff("docs/a.md", "..."));
>     assertFalse(CodeDiff.containsCodeFile(diffs));   // 一旦给 .md 加了映射，这里会红
> }
> ```
>
> **这是"用测试锁定一个口径"的又一个例子**（第 16/19 讲各有一处）。

**本项目当前的具体映射（`inferLanguage`）：**

| 扩展名 | 语言标识 | 算代码？ |
|---|---|---|
| `.java` / `.go` | `java` / `go` | ✅ |
| `.py` | **`python`**（不是 `py`） | ✅ |
| `.js` / `.jsx` / `.mjs` / `.cjs` | **`javascript`**（不是 `js`） | ✅ |
| `.ts` | **`typescript`**（不是 `js`） | ✅ |
| `.tsx` | `tsx` | ✅ |
| `.kt` / `.kts` | `kotlin` | ✅ |
| `.rb` / `.rs` / `.c` / `.h` / `.cpp` / `.cc` / `.cxx` / `.hpp` | `ruby` / `rust` / `c` / `c` / `cpp` / `cpp` / `cpp` / `cpp` | ✅ |
| `.cs` | `c_sharp` | ✅ |
| `.php` / `.scala` | `php` / `scala` | ✅ |
| `.sh` / `.bash` | `bash` | ✅ |
| `.xml` / `.sql` | `xml` / `sql` | ✅ **（有意算代码）** |
| **`.md`** / **`.yml`** / **`.env`** / **`.json`** / **其他** | **`unknown`** | ❌ |

**注意 `.xml` 和 `.sql` 被有意算作代码** —— 注释解释了理由：

> **"SQL 注入/慢查询等语义审查仍有价值"。**

**这是一个很好的判断**：**"是不是代码"不能用"是不是编程语言"来判**，而要用 **"这个文件里有没有可以被审出问题的语义"** 来判。

| 文件 | 是"代码"吗 | 有可审语义吗 |
|---|---|---|
| `.md` 文档 | ❌ | ❌（无） |
| `.yml` CI 配置 | ❌ | **⚠️ 有**（但由规则型/安全型 Agent 覆盖） |
| `.sql` | ⚠️ 严格说不是 | **✅ 有**（注入、慢查询） |
| `.xml`（MyBatis Mapper） | ⚠️ | **✅ 有**（SQL、动态标签） |

> **`containsCodeFile` 这个名字其实有点窄了** —— 它的真实语义是"**这份变更里有没有语义型 Agent 能审的东西**"。**改名成 `hasReviewableContent` 之类的语义会更准确。**
>
> **命名与语义的偏差，在"准入"这种"一个判断决定成本"的地方，代价会被放大。**

### 2.4 成本模型：算清楚"省了什么"

**先说清楚成本由什么构成：**

```
成本 = Σ_Agent (该 Agent 的 LLM 调用次数) × (每次调用的 token)
```

**每个 Agent 的调用次数不是 1：**

```java
// AbstractReviewAgent.llmFindings 的降级链（第 16 讲）
// 1. AiServices 结构化 → 1 次调用
// 2. 失败 → structured.chat(...) → 又是 1 次调用（agent-kit 结构化，内部可能重试）
// 3. 再失败 → askLlm(prompt) → 又是 1 次调用
```

**所以在最坏情况下，一个 Agent 的一次审查可能产生 3 次调用。** `StructuredChatModel.chat(prompt, clazz, 1)` 的第三个参数就是**重试次数**（第 06 讲）。

**再加上 `AdvancedAnalyzer`（高级静态分析）** —— 它也是并行跑的一个环节（`:462-471`）。

**以及可选的自定义 Agent**（业务方加的每一个都会增加调用）。

**所以"跳过 4 个语义 Agent"到底省了多少？**

| 场景 | 语义 Agent 数 | 每 Agent 调用数（含重试的期望值） | 相对成本 |
|---|---|---|---|
| **全跑** | 4 | ~1.2 | 100% |
| **纯文档 PR（跳过 4 个）** | 0 | — | **≈ 25%**（只剩 Security 的规则 + 可能的 LLM） |

**注意：跳过 4 个不等于省 80%** —— 因为 Security 还在跑，**而它仍然会调 LLM**（只要 `reviewable > 0`）。

**而"能省多少"这件事，其实是可以用数据验证的 —— 只要你记录了"哪些 Agent 被跳过"和"每次审查的 token 消耗"。**

> **这正是第 3 节那个缺口的核心：因为"跳过"没有进入报告，你也无法把"省下的 token"归因到具体维度上。**
>
> **成本优化如果不能归因，就只能靠"感觉"。** 而感觉驱动的成本优化，通常会把最贵的那个维度留在最后才动。

**把"该不该准入"译成一个成本不等式，判断就有了抓手。** 用前面那个量级：一次语义 Agent 调用 ≈ ¥0.005、一次纯文档 PR 白跑 5 个 ≈ ¥0.024；而漏跑一个真正含代码文件的比例，会让准入的收益被"漏报"吃掉。于是存在一个临界占比：

> 设纯文档 PR 占比 p，语义 Agent 单次成本 C = ¥0.005、一次漏跑（本应审却没审）的期望损失 L（含密钥/逻辑错漏的低频高损）。
> **每 PR 省下的钱** = p × 4C = 省下的单价。
> **每 PR 的期望漏跑损失** = (1 − p) × ε × L（ε = "真实代码 PR 被误判为纯文档"的比例）。
> 只要 `p × 4C ≥ (1 − p) × ε × L` 就值得准入——否则宁可多跑。
> 代入 **p=1/3、C=¥0.005、ε≈1%（黑名单几乎不误判真实代码）**：省下侧 ≈ **0.0067 元/PR**，漏跑侧 = 0.0067 × L —— 只要 **L ≥ 1 元/漏跑**就成立；**而一个 BLOCKER 级事故的期望损失远超 1 元**，所以准入明显划算，前提是 **ε 必须做进口径**（一旦给 .md 加了映射，ε 陡增，上面的不等式立刻翻转）。

**工程判据：** **准入开关的默认值不是拍脑袋，是拿『纯文档占比 p × 省下的单价』和『漏跑率 ε × 事故期望损失 L』比出来的；任何准入都必须配一个锁定口径的反向用例（纯 md PR 必须不入场），并把『每次跳过几个 Agent』计入报告覆盖度——做到这两条，成本优化才可归因、可验证，而不是靠感觉。** 另外牢记：纯规则型/安全型 Agent 的边际成本趋近 0，它们的准入门槛就该比语义型低一个量级。

## 三、代码

### 3.1 准入的实际执行点

```java
// core/coordinator/impl/CompletableFutureCoordinator.java:405-425
// 内容相关性准入：语义型 Agent 对纯文档/配置 PR（无代码文件）返回 supports()=false，
// 在此剔除（不产生降级语义，仅减少无对象维度的 LLM token 消耗）。Security 恒跑。
List<ReviewAgent> routedAgents = new ArrayList<>(effectiveAgents.size());
List<String> skippedBySupports = new ArrayList<>();
for (ReviewAgent agent : effectiveAgents) {
    if (agent.supports(diffs, enrichedCtx)) {
        routedAgents.add(agent);
    } else {
        skippedBySupports.add(agent.getType().name());
    }
}
if (!skippedBySupports.isEmpty()) {
    effectiveAgents = routedAgents;
    log.info("[Coordinator] 按内容准入跳过 {} 个 Agent（无代码文件可审）：{}",
            skippedBySupports.size(), skippedBySupports);
    if (recorder != null) {
        recorder.append(runId, "agent.skipped-by-supports", Map.of(
                "count", skippedBySupports.size(),
                "types", skippedBySupports));
    }
}
```

**四个正确的做法：**

**① 准入在 `effectiveAgents` 之上执行，且替换了它。**

注意顺序：**先展开自定义 Agent（`:375-403`），再做准入（`:405-425`）。**

**这个顺序是对的**：业务方的自定义 Agent **也会经过准入判断**（`DeclarativeReviewAgent` 没覆写 `supports()`，所以继承 `true` —— **它恒跑**）。

> **等一下，这也有问题**：`DeclarativeReviewAgent` 不覆写 `supports()` → **任何自定义 Agent 都会在所有 PR 上跑**，**包括纯文档 PR。**
>
> **如果业务方配了一个"支付合规审查"，那么每个 `README.md` 的更新都会触发一次它的 LLM 调用。**
>
> **这是"准入默认值偏向安全侧"的代价在自定义 Agent 上的体现。** 它是有意的（宁可多跑），**但它意味着"跳过 4 个语义 Agent"这个优化的效果，会被业务方加的自定义 Agent 部分抵消。**
>
> **补法**：让 `CustomAgentDef` 支持一个"仅代码 PR 才跑"的开关，由业务方自己决定。**这就把"要不要跑"的判断权交回给了最了解这个维度的人。**

**② 传入的是 `enrichedCtx`（已带影响面 + RAG 上下文）。**

**当前实现只用 `diffs`**，但接口留出了按上下文判断的能力（第 16 讲讨论过）。

**③ `effectiveAgents = routedAgents` 是"重新赋值"而不是"原地删除"。**

`effectiveAgents` 原本指向 `pendingAgents` 或 `expanded`。**这里改成指向一个新的 `routedAgents` 列表。**

**这个细节重要，因为后面有靠下标对齐的代码：**

```java
// :479-481
for (int i = 0; i < futures.size(); i++) {
    CompletableFuture<AgentResult> future = futures.get(i);
    ReviewAgent agent = effectiveAgents.get(i);
```

**`futures` 是从 `effectiveAgents` 生成的（`:445-459`）** —— 所以**只要准入发生在生成 futures 之前，下标就对齐**。

**它是安全的，但很脆**：**如果将来有人把准入移到 `futures` 创建之后**（比如"想让它并行判断"），**下标立刻错位** —— 而错位的表现是"把 A 的超时算到 B 头上"（第 15 讲提过）。

> **同一个隐式契约（下标对齐）在这一讲又出现了一次。** **它已经暴露了三处风险（第 15 讲、第 17 讲的 `setDiffCharBudget`、这里），说明"用两个并行 List 传递身份"这个模式本身就不该存在。**
>
> **修法**（第 15 讲给过）：把 `futures` 换成 `Map<AgentType, CompletableFuture<AgentResult>>`，**身份跟着数据走**，顺序无关。

**④ 轨迹里记了 `agent.skipped-by-supports` 事件。**

**这是本节唯一存在的"跳过"留痕** —— 而它只在**开了轨迹记录器**时才有。

### 3.2 ★ 缺口：跳过不进报告

**对比一下"降级"和"跳过"在报告里的待遇：**

```java
// ReviewReport.toMarkdown()（节选）
// 降级告警区块（必须置于发现区块之前：读者先知道「哪些维度没看成」）
if (!degradations.isEmpty()) {
    sb.append("## ⚠️ ").append(msg("report.degraded.title", degradations.size())).append("\n\n");
    sb.append("> ").append(msg("report.degraded.tip")).append("\n\n");
    for (AgentDegradation d : degradations) {
        sb.append("- **").append(stageLabel(d.stage())).append("**：").append(d.reason()).append('\n');
    }
    sb.append("\n");
}
```

**注意注释里那句话："必须置于发现区块之前：读者先知道「哪些维度没看成」"。**

**这个设计意图非常清楚 —— 但 `skippedBySupports` 没有被纳入。**

**于是报告里会出现这样的情况：**

```markdown
# 🤖 代码审查报告
- **总发现数**：2
- **严重级别统计**：🔴 BLOCKER 0，🟠 MAJOR 1，🟡 MINOR 1，🔵 INFO 0
```

**读者看到"2 条发现"，很自然地把这个 PR 判定为"基本没问题"。**

**而真相是：这次只跑了一个安全 Agent，逻辑 / 性能 / 规范 / 架构四个维度根本没跑。**

**这和第 06/07 讲反复强调的原则完全一致：**

> **"0 条发现"绝不能等价于"没有问题"。**
> **而"没跑"是比"降级"更彻底的"没有结论"** —— 降级至少说明"这个维度存在但没看成"，**跳过说明"这个维度连试都没试"。**

**修法（最小改动）：把跳过也当成一种"覆盖度信息"写进报告。**

```java
// 方案一：复用 degradations 通道（不推荐 —— 语义不同，会污染"降级率"这个指标）
// 方案二：新增一个"覆盖度"字段（推荐）

public ReviewReport withCoverage(List<AgentType> ran, List<AgentType> skipped) { ... }
```

**报告里渲染成：**

```markdown
## 🧭 本次审查覆盖度
- 参与审查：安全审查
- **按内容准入跳过**：逻辑审查 / 性能审查 / 规范审查 / 架构审查（本 PR 无代码文件）
```

> **这个信息对读者的价值是决定性的：**
> **它把"2 条发现"的正确解读从"这个 PR 基本没问题"修正为"这个 PR 只审了安全维度"。**
>
> **成本优化必须付出"可解释性"的代价 —— 而代价应该由报告显式承担，而不是让读者自己猜。**

**顺带说一个更小的缺口**：`skippedBySupports` 在 `if (!skippedBySupports.isEmpty())` 里被用来**替换 `effectiveAgents`** —— **但如果所有 Agent 都被跳过（极端情况：四个语义 Agent 都被跳过，Security 也被跳过），那 `effectiveAgents` 会变成空列表** → `futures` 为空 → 循环不执行 → **报告里 0 条发现，且没有任何降级标记。**

**Security 恒跑，所以当前不会出现全空。** 但**如果哪天有人给 Security 也加了 `supports()` 覆写，"全空"就会成为一个静默场景** —— 而它长得和"代码没问题"一模一样。

> **防御手段：在准入之后加一条断言式的检查**：
> ```java
> if (effectiveAgents.isEmpty()) {
>     log.warn("[Coordinator] 内容准入跳过了全部 Agent，本次审查无任何维度参与");
>     // 并显式记入 degradations 或 coverage
> }
> ```
> **用"如果全空就喊一声"来防御"静默的全空"。**

### 3.3 ★ 粒度错配：PR 级准入 + 文件级成本

**这是故障二的根源。**

**准入的粒度是 PR 级：**

```java
return diffs.stream().anyMatch(d -> ...);      // anyMatch —— 只要有一个就算
```

**而成本的粒度是文件级：**

```java
// AbstractReviewAgent.defaultVars → formatDiffs(diffs) 把所有文件拼进 prompt
vars.put("diffs", formatDiffs(diffs));
```

**于是产生错配：**

```
PR 内容：1 个 .java + 49 个 .md
准入判断：anyMatch → true（因为有 1 个 java）→ 4 个语义 Agent 全部开跑
实际成本：50 个文件的 diff 全部进 prompt，其中 49 个是文档
```

**后果有两层：**

**第一层：prompt 预算被文档吃掉。**

第 16 讲的 `formatDiffs` 有"按文件均摊截断"逻辑：

```java
// core/agent/AbstractReviewAgent.java:198
long perFile = Math.max(200L, diffCharBudget / (long) diffs.size());
```

**50 个文件平分预算** → 每个文件拿 `budget / 50`。**那个 java 文件只能拿到 1/50 的额度** —— **真正的代码可能还没被模型看全就被截断了。**

**第二层：注意力被文档分散。**

**模型要在 3 万字的文档 diff 里找代码问题**（第 14 讲：注意力稀释）。

**修法：把"准入"从 PR 级细化到文件级。**

```java
// 思路：过滤掉"语义型 Agent 不需要看的文件"
List<CodeDiff> reviewable = diffs.stream()
        .filter(d -> !"unknown".equals(d.language()))
        .toList();
```

**但这里有一个必须小心的边界**：**这不能由 `supports()` 来做**。

**理由**：

- `supports()` 的返回值是 `boolean`（"我要不要跑"）—— **它无法表达"我要跑，但只看这些文件"**；
- 如果让每个 Agent 自己过滤文件，**那过滤逻辑会被复制 4 遍**（正是第 16 讲讲的"五遍"问题）。

**更好的位置是"在 Coordinator 里做一次文件级预筛，然后把筛过的 diffs 传给语义型 Agent"**：

```java
// 概念示意：把"审查对象"分成两类
// - 语义型 Agent：只看代码文件
// - 规则型/安全型 Agent：看全量
```

**这个改造的代价不小**（要改 `ReviewAgent` 的契约，或者引入"按 Agent 类型分发 diffs"的机制）。

**而它的收益是可以量化的**：

> **对于一个 1+49 的 PR，"语义 Agent 只看代码文件"能把 prompt 从 50 个文件的量级降到 1 个文件的量级 —— 成本降一个数量级，而质量可能上升（因为代码不再被截断）。**
>
> **这是本项目里"性价比最高但未做"的一个优化。** 而它没有被做，原因也很典型：**它需要改接口契约，而"改契约"的短期成本高于"多花点 token"的即时感受。**

**这就是技术债的典型形态：一个可以被量化的长期收益，被一个眼前的改动成本挡住了。** 而**第 20 讲把它写出来，就是让这个取舍从"隐性"变成"显性"。**

**`CodeDiff` 这个文件里有两处提到语言标识，而它们不一致：**

**第一处（record 的字段注释，`:13`）：**

<img class="mermaid-svg" src="/zh/book-assets/diag-0079.svg" alt="第一处（record 的字段注释，`:13`）：" />


**第二处（`inferLanguage` 的方法注释，`:66-68`）：**

```java
 * <p>历史上本方法把 {@code .py} 映射为 {@code py}、{@code .ts} 映射为 {@code js}
 * （TypeScript 被当成 JavaScript）。由于既有消费方全部只判断 {@code java}，

**危害不大**（只是一个举例），**但它是那个反复出现的模式的第四次现身：**

| 讲次 | 不一致的两处 |
|---|---|
| 第 09 讲 | 注释说做"类型校验" vs `props` 从未被使用 |

> **当一次修改改变了"某个值的含义或取值范围"时，最容易漏的不是代码，也不是"主注释"，而是"别处顺手举的例子"。**
>
> **因为举例不承担编译期责任** —— 写错了不会有任何工具报错。
>
> **一条可操作的纪律**：**改一个常量/枚举/取值时，先 grep 它的旧值在整个仓库里的出现位置，包括注释、文档、测试数据。**
>
> 在这个例子里就是 `grep -rn "\bpy\b" --include=*.java`。**成本 5 秒，收益是"举的例子不会骗人"。**

## 四、避坑清单

- [ ] **分清四种减少**：准入（设计决定）/ 降级（故障）/ 抑制（人类判断）/ 仲裁（规则取舍）—— **语义不同，留痕方式也该不同**。
- [ ] **准入只做"内容相关性"，不做"优先级"** —— 用优先级做准入会让"跳过"和"没问题"无法区分。
- [ ] **`default` 准入必须返回 `true`**：忘覆写的后果是"多花钱"，而不是"这个维度永远不跑"。**默认值偏向更安全的一侧。**
- [ ] **规则型检查可以不设准入门槛**（边际成本≈0），**LLM 型必须设**（边际成本是真钱）。
- [ ] **别让安全 Agent 按"是不是代码"准入** —— 最危险的密钥泄露恰恰在 `.env` / `.yml` 里，而它们都是 `unknown`。
- [ ] **"是不是代码"要用"有没有可审语义"判**，不是"是不是编程语言"（`.sql` / `.xml` 要算代码）。
- [ ] **语言标识是路由键，不是展示字段**：写错会"支持了该语言却静默不生效"。
- [ ] **黑名单式准入（`!= unknown`）让"新增一个扩展名映射"变成成本开关** —— 加一条单测锁定"纯 md PR 的准入结果"。
- [ ] **★ 跳过必须进报告**（覆盖度区块），否则"2 条发现"会被误读为"基本没问题"。
- [ ] **加一条"全部被跳过"的显式告警** —— 否则"全空"和"代码没问题"长得一样。
- [ ] **准入是 PR 级、成本是文件级 → 会错配**：1 个 java + 49 个 md 时，文档会吃掉 prompt 预算并挤掉代码的展示额度。
- [ ] **文件级预筛应该做在 Coordinator，而不是让每个 Agent 各写一遍。**
- [ ] **自定义 Agent 若不覆写 `supports()`，会在纯文档 PR 上照样跑** —— 把"要不要跑"的判断权交给配置它的人。
- [ ] **改一个取值的含义时，grep 它的旧值**（含注释与测试数据）—— "顺手举的例子"最容易骗人。
- [ ] **别用"两个并行 List 下标对齐"传递身份**（本讲第三次遇到同一风险）—— 换成 `Map<AgentType, ...>`。

## 本讲小结

1. **四种"减少"语义完全不同**：准入（设计决定）/ 降级（故障）/ 抑制（人类判断）/ 仲裁（规则取舍）—— **前者的痕迹几乎没进报告，后三者都进了。**
2. **准入只做内容相关性，不做优先级**；`default` 返回 `true`，**默认偏向"更安全"而不是"更省"。**
3. **安全 Agent 不设代码准入门槛**：它的规则型技能边际成本≈0，而密钥泄露最常出现在 `.env` / `.yml`（都是 `unknown`）。
4. **语言标识是路由键**：写错 → "支持了该语言却静默不生效"；**黑名单式准入让"新增扩展名"变成成本开关。**
5. **跳过必须写进报告（覆盖度区块）** —— 否则"2 条发现"会被读成"基本没问题"，这违反第 06/07 讲的"0 条 ≠ 没问题"。
6. **粒度错配是本讲最实际的缺口**：准入 PR 级、成本文件级 → 1 + 49 的 PR 里，**文档吃预算、代码被截断**。
7. **文件级预筛应做在 Coordinator**，不能让 4 个 Agent 各写一遍。
8. **"顺手举的例子"最容易骗人**：`@param language（如 java、go、py）` 而 `py` 已是历史值 —— **改取值时先 grep 旧值。**
