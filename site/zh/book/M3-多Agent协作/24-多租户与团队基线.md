# 第 24 讲 · 多租户：一份系统，为什么要有"团队基线"

> 🎯 导读问题：**"多租户系统最容易漏掉哪些隔离？"**（答案不是"表里加个 tenant_id"，而是"派生数据和缓存"）

> **图 24-0**　本讲地图：多租户＝三层基线加叠加：内置、全局基线、团队私有。teamId 进路径与表键，必须净化。最易漏派生数据与缓存；SkillRegistry 加载净化、查询不净化，技能启停会静默失效。

## 一、痛点

系统上线，四个团队开始用：

```
支付团队      自己的自定义规则 12 条、知识库 30 篇、反馈 8 条
前端团队      自己的自定义规则 5 条、知识库 12 篇
数据团队      自己的自定义规则 20 条、知识库 45 篇
基础设施团队   什么都没配（用内置的）
```

**故障一：支付团队把"SEC-007"这条规则关掉了，前端团队发现自己的 `SEC-007` 也不生效了。**

（这个故障是本讲第 3 节要拆的那个 —— 它的表现取决于调用路径，下面详述。）

**故障二：数据团队看到了一条"支付团队才可能关心"的审查意见。**

审查意见里提到了支付团队的内部规范措辞。**数据团队不知道它从哪来的。**

**故障三（最典型的）：某个团队升级了配置，怎么都不生效。**

```
"我们把 review.teams.mapping 里 acme/payments 映射到 team-payments 了，
 但读出来的还是 default 团队的数据。"
```

**你去查，发现配置对了、代码也读了。** 而真正的原因在另一个地方（下面 2.4 节）。

**故障四：一个实习生提交了一个带异常字符的 `X-Team-Id`，然后有两批不相关的数据混到了一起。**

**四个故障指向同一件事：多租户不是"加一个 tenant_id 字段"，它是"给每一份数据明确归属 + 在每一个入口明确校验 + 对每一处派生数据单独决策"。**

**而"团队"这个概念一旦引入，系统里就多出一个贯穿全链路的参数 `teamId`** —— 它出现在：

- 请求头（`X-Team-Id`）
- 配置文件（`review.teams.mapping`）
- **每一个存储的键**（技能配置、知识、反馈、历史、断点、自定义 Agent、画像）
- **文件路径**（`data-dir/<teamId>/...` 的历史实现）
- **每一个 Agent 的上下文**（`ReviewContext.teamId`）

**只要有一处漏了，隔离就不成立。**

## 二、原理

### 2.1 模型：全局基线 + 团队叠加

```java
// tenant/Teams.java:5-24
/**
 * 团队 / 租户相关常量。
 *
 * <p>系统采用「全局基线 + 团队叠加」模型：内置技能与基础编码规范是所有团队共享的基线，
 * 自定义规则 / 知识 / 记忆 / 历史 / 反馈则按团队隔离。保留团队 {@code __global__}
 * 用于承载跨团队共享的基线内容（如编码规范手册向量）。
 */
public final class Teams {

    /** 保留团队：承载跨团队共享的全局基线（如编码规范手册 RAG 向量）。 */
    public static final String GLOBAL = "__global__";

    /** 默认团队：未在任何映射中匹配的仓库回退到此团队。 */
    public static final String DEFAULT = "default";
```

**这个模型有三层，而不是两层：**

```
第 1 层：内置（代码里）
        内置 5 个 Skill、5 个 Agent、内置规则（PatternSkill 等）
        —— 所有团队共享，且团队无法修改

第 2 层：全局基线（__global__）
        编码规范手册向量、跨团队共享知识
        —— 所有团队能"读"到，通过 __global__ 这个保留团队承载

第 3 层：团队私有
        自定义规则、知识、反馈、历史、断点、自定义 Agent
        —— 严格按 teamId 隔离
```

**为什么要分三层而不是两层？**

**因为有一类内容"对所有团队都成立，但需要被管理员维护"。**

举例：**公司的编码规范手册**。

- 如果放进"内置"（代码里）→ **改一次规范要发一次版**；
- 如果做成"每个团队各存一份"→ **四个团队各维护一份，必然会分叉**；
- **所以它需要一个"所有团队共享、但可以热更新"的位置** → 这就是 `__global__`。

**`__global__` 的实现方式很取巧：它是一个"看起来像团队 ID 的保留团队"。**

看知识库的检索是怎么处理全局的：

```java
// core/memory/InMemoryVectorStore.java:54（PG 实现同构）
boolean globalMatch = includeGlobal && Teams.GLOBAL.equals(e.teamId());
```

**检索时同时匹配"当前团队"和 `__global__`（当 `includeGlobal=true` 时）。**

**这个做法的好处是不需要额外的表或字段** —— `__global__` 和其他团队走完全相同的代码路径。

**代价是"全局"变成了一个"约定"而不是"类型"**：

> **"检索时要不要带上 `__global__`"由调用方的一个 boolean 决定**（`includeGlobal`）。
>
> **那么：如果一个调用方忘了传 `includeGlobal=true`，它会静默地看不到全局基线** —— 而不是报错。
>
> **这是"用保留值表达语义"的普遍代价：语义靠约定维持，而约定靠人记住。**

**三层模型的实际覆盖情况（这是本讲最重要的一张表）：**

| 数据 | 层次 | 是否按团队隔离 | 有没有全局基线 |
|---|---|---|---|
| 内置 Skill（5 个） | 第 1 层 | ❌ 共享（代码里） | — |
| 内置编码规范手册 | **第 2 层** | ❌ 共享 | — |
| 知识库（上传的文档） | 第 3 层 | ✅ | **✅ 可叠加 `__global__`** |
| 自定义规则（YAML/正则） | 第 3 层 | ✅ | ❌ 无基线 |
| 技能启停状态 | 第 3 层 | ✅ | ❌ 无基线（缺省全部启用） |
| 自定义 Agent 定义 | 第 3 层 | ✅ | ❌ 无基线 |
| 反馈 | 第 3 层 | ✅ | ❌ 无基线 |
| 审查历史 | 第 3 层 | ✅ | ❌ 无基线 |
| 断点续跑状态 | 第 3 层 | ✅ | ❌ 无基线 |
| **置信度准确率** | **❌ 全局** | **❌** | —（见 3.4） |
| **ChatMemory 短期记忆** | **❌ 跨仓库/跨团队** | **❌** | —（见 3.4） |

**最后两行是本讲的"红旗"。** 前九行都是有意的设计，**后两行是缺口** —— 而且它们有一个共同特征（2.5 节详述）。

### 2.2 `sanitize`：为什么必须净化，以及净化的边界

```java
// tenant/Teams.java:38-56
/**
 * 净化团队标识，防止路径穿越与非法字符（仅允许字母数字、下划线、连字符）。
 *
 * @param teamId 原始团队标识
 * @return 净化后的团队标识；为空或非法时返回 {@link #DEFAULT}
 */
public static String sanitize(String teamId) {
    if (teamId == null || teamId.isBlank()) {
        return DEFAULT;
    }
    String t = teamId.trim();
    if (t.equals(GLOBAL)) {
        return GLOBAL;
    }
    if (!t.matches("[A-Za-z0-9_\\-]{1,64}")) {
        return DEFAULT;
    }
    return t;
}
```

**为什么要净化？因为 `teamId` 会进入"非查询参数"的位置：**

**① 文件路径。**

历史实现把团队配置存在 `data-dir/<teamId>/*.json`。**如果 `teamId` 是 `../../etc`，那文件就写到了别的目录。**

**② 表键 / 分区键。**

现在的 PG 实现里，`teamId` 是 `team_kv`、`review_feedback`、`experience_entry` 的列值。**拼 SQL 时如果不用参数化（本项目用了），就是一个注入面。**

**③ 保留值冲突。**

`__global__` 是一个**功能性的保留值** —— 如果业务方把自己的团队起名叫 `__global__`，**它就能读到全局基线的内容（虽然读本来就允许），并且能往基线里写**。

**关于第 ③ 点，看这段的顺序：**

```java
if (t.equals(GLOBAL)) {
    return GLOBAL;              // ← 先判保留值
}
if (!t.matches("[A-Za-z0-9_\\-]{1,64}")) {
    return DEFAULT;
}
return t;
```

**`__global__` 完全匹配 `[A-Za-z0-9_\-]{1,64}`**（下划线在允许集里）。

**所以第一个 `if` 是"冗余"的** —— 即使删掉它，`__global__` 也会走到最后一行 `return t` 并返回 `__global__`。

**那它为什么在那里？**

**它是一个"意图声明"**：

> **"`__global__` 是保留值，它的通过是**特批**的，不是因为恰好匹配了正则。"**
>
> **这个区别在"有人收紧正则"时会体现出来**：如果哪天把允许集改成 `[a-z0-9\-]`（去掉下划线和大写），**`__global__` 就会因为第一个 `if` 而继续有效** —— **而那个改动原本会静默地把全局基线功能干掉**（所有写到 `__global__` 的知识都会落到 `default`）。

**这是一个很值得学的模式：**

> **"冗余的显式判断"可以是一个安全网。** 它保护的往往不是当前代码，而是**未来的某次修改**。
>
> **判断一个冗余判断"该不该留"的准则**：**删掉它，会不会让一个"看起来无关的改动"变成静默的功能故障？**
> 如果是 → 留着，并且写清楚它为什么在（否则后人"清理冗余"时会删掉它）。

**而 `sanitize` 的兜底行为才是更值得讨论的：**

```java
if (!t.matches(...)) {
    return DEFAULT;        // ← 非法输入 → 落到 default
}
```

**"非法"和"未映射"被归一成了同一个结果。**

| 输入 | 含义 | 结果 |
|---|---|---|
| `null` / 空 / 空白 | 没提供 | `default` |
| `acme/payments` 未在 mapping 里 | 未映射 | `default`（由 `TeamResolver`） |
| **`@@@bad@@@`** | **非法字符** | **`default`** |
| **`../../etc`** | **疑似攻击** | **`default`** |
| `team-acme` | 合法 | `team-acme` |

**两个后果：**

**① 非法输入不会失败，而是"降级到一个共享团队"。**

**如果两个不同的调用方都传了非法值，它们的数据会混在 `default` 里** —— 而**没有任何日志、没有任何异常**。

**② "有人试图穿插路径"这件事不会被观察到。**

**对比第 45 讲要讲的一个决策**：本项目在存储选型上选择了"**连不上 PG 就启动失败**"，理由是"不做自动降级，因为它会制造一整类看起来正常的故障"。

**而 `sanitize` 在这里做的恰好是"自动降级到 default"。**

**这两处的取向是不一致的。**

> **更严的做法**：非法（不匹配正则）→ **抛异常或拒绝请求**；未提供 → `default`。
>
> **理由是**：**"没提供"是正常情况，"提供了但不合法"是异常情况。把异常情况当正常情况处理，就等于放弃了对它的观测。**
>
> **至少也应该区分**：非法时打一条 `WARN`（含原始值），**而不是静默归一**。

### 2.3 解析：`TeamResolver` 的三级匹配

```java
// tenant/TeamResolver.java:36-54
public String resolve(String owner, String repo) {
    String key = owner + "/" + repo;
    String team = mapping.get(key);
    if (team != null) {
        return Teams.sanitize(team);
    }
    team = mapping.get(owner);
    if (team != null) {
        return Teams.sanitize(team);
    }
    if (log.isDebugEnabled()) {
        log.debug("[TeamResolver] 仓库 {}/{} 未命中映射，回退到默认团队 {}", owner, repo, defaultTeam);
    }
    return defaultTeam;
}
```

**匹配优先级：**

```
1. owner/repo      （最具体）
2. owner           （整个组织）
3. defaultTeam     （兜底）
```

**"更具体的优先"是一个通用且正确的原则**（和 CSS 选择器、路由匹配、`.ftl` 优先于同名文件是同构的）。

**配置形态：**

```java
// tenant/TeamProperties.java:20-40
/**
 * 团队（租户）映射配置。
 *
 * <p>通过 {@code review.teams.mapping} 将 Git 仓库的 owner（组织）或 owner/repo
 * 映射到团队标识；未匹配者回退到 {@code review.teams.default}（默认 {@code default}）。
 *
 * <p>示例（application.yml）：
 * <pre>
 * review:
 *   teams:
 *     default: default
 *     mapping:
 *       "acme": team-acme          # 整个组织 acme 归 team-acme
 *       "acme/payments": team-acme-pay   # 更具体的仓库优先
 *       "opensource/tool-x": team-oss
 * </pre>
 */
@ConfigurationProperties(prefix = "review.teams")
public class TeamProperties {
```

**注意 `defaultTeam` 的默认值是 `Teams.DEFAULT`：**

```java
/** 未匹配时的默认团队。 */
private String defaultTeam = Teams.DEFAULT;
```

**而这个字段在 `TeamResolver` 的构造里也被净化了一次：**

```java
// tenant/TeamResolver.java:28-31
public TeamResolver(Map<String, String> mapping, String defaultTeam) {
    this.mapping = mapping == null ? Map.of() : mapping;
    this.defaultTeam = Teams.sanitize(defaultTeam);
}
```

**注意：`mapping` 的 value 没有在构造时净化，而是在每次 `resolve` 时净化（`:44`、`:48`）。**

**两种做法各有代价：**

| | 构造时净化（defaultTeam） | 每次 resolve 时净化（mapping values） |
|---|---|---|
| 成本 | 一次 | 每次调用（正则匹配） |
| 一致性 | 存的就是净化后的值 | **保留原始配置值，便于排障** |

**而 `resolve(...)` 的成本有多高？** 它在**每个 webhook 请求**上调用一次（不是每个 Agent），**所以这点正则成本可以忽略。**

> **结论**：这里的不一致是"无害的不一致"。**但它提醒我们一件事：净化时机是一个需要显式决定的设计点。**
>
> **判断准则**：**如果净化结果会被"存储"**（比如落库、写文件、做键）→ **在入口净化一次，之后一路传净化后的值**；**如果净化结果只在内存里传递** → 可以在使用点净化。

**还有那个"显式覆盖"的重载：**

```java
// tenant/TeamResolver.java:56-68
public String resolve(String owner, String repo, String override) {
    if (override != null && !override.isBlank()) {
        return Teams.sanitize(override);
    }
    return resolve(owner, repo);
}
```

**"显式覆盖优先于自动推导"** —— 这让控制台/API **可以手动指定团队审查一个仓库**（用于测试、或者仓库归属临时调整）。

**而它同样是净化过的**（`:66`）—— 这一点很重要：**如果覆盖值不净化，那"显式覆盖"就成了绕过净化的后门。**

### 2.4 净化的作用域：`SkillRegistry` 里的不一致

**这是本讲最具体、也最有教学价值的一处。**

```java
// core/skill/SkillRegistry.java:68-88
/** 懒加载某团队的持久化配置（启用状态 + 自定义规则）；带短 TTL 惰性刷新以感知他实例变更。 */
private void ensureTeamLoaded(String teamId) {
    String t = Teams.sanitize(teamId);                    // ← 净化
    Long last = loadedTeams.get(t);
    if (last != null && System.currentTimeMillis() - last < REFRESH_MS) {
        return;
    }
    synchronized (loadedTeams) {
        Long again = loadedTeams.get(t);
        if (again != null && System.currentTimeMillis() - again < REFRESH_MS) {
            return;
        }
        try {
            loadEnabled(t);                               // ← 用净化值加载
            loadCustomRules(t);
        } catch (Exception e) {
            log.warn("[SkillRegistry] 加载团队 {} 持久化配置失败，使用默认（全部启用）：{}", t, e.getMessage());
        }
        loadedTeams.put(t, System.currentTimeMillis());
    }
}
```

**而读的地方：**

```java
// core/skill/SkillRegistry.java:174-177
public boolean isEnabled(String teamId, String name) {
    ensureTeamLoaded(teamId);
    return enabledByTeam.getOrDefault(teamId, Map.of()).getOrDefault(name, true);   // ← 用原始值查
}
```

```java
// core/skill/SkillRegistry.java:222-236
public List<Skill> getEnabledSkillsForCategory(String teamId, String category) {
    ensureTeamLoaded(teamId);
    List<Skill> result = new ArrayList<>();
    for (Skill s : builtInSkills) {
        if (category.equals(s.getMetadata().category()) && isEnabled(teamId, s.getMetadata().name())) {
            result.add(s);
        }
    }
    for (Skill s : customSkillsByTeam.getOrDefault(teamId, Map.of()).values()) {   // ← 用原始值查
        ...
    }
    return result;
}
```

**同一个 `teamId`：**

- **写入 map 时用 `Teams.sanitize(teamId)`**（`ensureTeamLoaded` 里的 `t`）；
- **读取 map 时用原始 `teamId`。**

**如果两者不同，会发生什么？**

| 场景 | `teamId` | 净化后 `t` | 写入的键 | 查询的键 | 结果 |
|---|---|---|---|---|---|
| 生产路径（已净化） | `team-acme` | `team-acme` | `team-acme` | `team-acme` | ✅ 命中 |
| 带尾空格 | `"team-acme "` | `team-acme` | `team-acme` | `"team-acme "` | **❌ 未命中** |
| 非法字符 | `"team@acme"` | `default` | `default` | `"team@acme"` | **❌ 未命中** |
| 空值 | `null` | `default` | `default` | `null` | **❌ 未命中** |

**未命中的后果是两个静默行为：**

```java
enabledByTeam.getOrDefault(teamId, Map.of()).getOrDefault(name, true)
//                                        └─ 键不存在 → 空 Map →       └─ 默认 true（全部启用）

customSkillsByTeam.getOrDefault(teamId, Map.of())
//                               └─ 键不存在 → 空 Map → 团队自定义规则「全部消失」
```

**① 团队关掉的技能，会静默地重新启用；**
**② 团队的自定义规则，会静默地不生效。**

**两个都是"静默"，而且方向相反**（一个是"多了不该有的"，一个是"少了该有的"）。

**而它在本项目的生产路径上不会触发** —— 因为：

- `ReviewApiController` 用 `Teams.fromRequest(...)` → 已净化（第 3 节列出全部入口）；
- `GiteaReviewService` / `GitLabReviewService` 用 `TeamResolver.resolve(...)` → 已净化；
- 各 Admin 控制器用 `Teams.fromRequest(...)` → 已净化。

**所以它是"一个被当前调用方纪律掩盖的缺陷"。**

> **而这类缺陷最危险的地方在于：它会在"新增一个入口"时突然暴露。**
>
> 设想：三个月后加一个"从 GitLab 新的事件类型触发审查"的入口。开发者写：
>
> ```java
> String teamId = request.getHeader("X-Team-Id");     // 忘了 Teams.fromRequest
> ```
>
> **结果是**：技能启停和自定义规则静默失效，**而审查照样跑、报告照样出**（默认全部启用 + 无自定义规则）。
>
> **没有任何东西会告诉你出了问题。**
>
> **"靠调用方纪律维持的隔离"不是隔离，是运气。**

**修法（两种，任选但必须选一种）：**

| 方案 | 做法 | 特点 |
|---|---|---|
| **在类内归一** | 每个 public 方法第一行 `teamId = Teams.sanitize(teamId);` | **类自洽**，与调用方纪律解耦 |
| **把归一收进 map 访问** | 封装 `private Map<String,Boolean> enabledOf(String teamId)`，内部净化 | 减少重复，但要记得所有访问点都走它 |

**更彻底的做法是"类型化"**：

<img class="mermaid-svg" src="/zh/book-assets/diag-0104.svg" alt="更彻底的做法是&quot;类型化&quot;：" />

> **图 24-2**　把 `teamId` 从 `String` 升级成 `TeamId` 的思路：构造即净化，让"忘了净化"在类型上不可能发生。**这张图给出的新结论是：隔离的正确性可以被移动到类型系统里，代价是改所有签名。** 而它之所以值得，是因为当前那条兜底方案（"每个调用方都记得净化"）在本讲 §2.6 的表里已经被证明是失效的——11 个存储里有 3 种不同的净化口径。

**这样 `ReviewContext.teamId()` 的类型就是 `TeamId` 而不是 `String`** —— **"忘了净化"在类型上不可能发生。**

**代价**：要改 `PullRequest` / `ReviewContext` / 所有存储的签名。**而收益是"隔离变成一个编译期事实"。**

> **这是本讲的中心论点：**
> **隔离的正确性，不应该依赖"每个调用方都记得净化"，而应该依赖"类型系统不允许未净化的值进入"。**

### 2.5 隔离审计：两个最容易漏的类别

**要把"多租户到底有没有做全"回答清楚，需要一份清单。而这份清单的依据不是"我想到了哪些"，而是"哪些数据类别容易被漏"。**

**经验上，两类最容易被漏：**

**类别一：派生数据（从团队数据算出来的东西）**

**本项目的例子：置信度准确率。**

```java
// core/calibration/ConfidenceCalibrationService.java:101-115
/**
 * 反馈落库回调（{@link FeedbackListener}）：按规则级证据更新准确率。
 * ...
 * @param teamId   团队标识（当前校准按规则全局生效，不区分团队）
 */
@Override
public void onFeedback(String teamId, ReviewFeedback feedback) {
    if (feedback == null || feedback.ruleId() == null || feedback.ruleId().isBlank()) {
        return;
    }
    ...
}
```

**`teamId` 在方法体里完全没有被使用。**

**为什么这类容易漏？** 因为**派生数据"看起来不像数据"** —— 它是一个系数、一个统计量、一个索引。

**而"系数"的作用是"调整展示"**，所以**漏掉隔离的表现不是"数据串了"，而是"行为不一致"** —— 后者更难被注意到。

**类别二：缓存（跨请求存活的中间状态）**

**本项目的例子：`ChatMemory`。**

```java
// core/agent/AbstractReviewAgent.java:319-322

    return getType().name() + "-" + vars.getOrDefault("prId", "shared");

```

**第 19 讲完整分析过：注释承诺"团队隔离"，实现里连仓库都没有。**

**为什么这类容易漏？** 因为**缓存的键通常由"最显然的那个 ID"构成**（这里是 `prId`），而**设计者会默认"ID 是全局唯一的"。**

**而 `prId` 在单仓库语境下唯一，在多仓库多团队语境下不唯一。**

> **一条可复用的审计清单。做多租户系统时，逐项过：**
>
> | 类别 | 问什么 | 本项目 |
> |---|---|---|
> | **主数据** | 每张表有没有 tenant 列？ | ✅ |
> | **派生数据** | 统计量 / 系数 / 索引有没有带 tenant？ | ❌ 置信度准确率 |
> | **缓存** | 缓存键里有没有 tenant？ | ❌ `ChatMemory` 的 memoryId |
> | **异步任务** | 任务提交时有没有丢 tenant 上下文？（ThreadLocal 不会自动传播） | ⚠️ `TraceContext.wrap` 传了 traceId，**但 teamId 是显式参数传递的**（安全） |
> | **共享基线** | 哪些是"有意共享"的？有没有被误当共享？ | ✅ `__global__` 明确 |
> | **保留值** | 保留值（如 `__global__`）能否被用户占用？ | ✅ 净化时特批 |
> | **兜底归属** | 解析不到时落到哪？会不会造成"多租户混入同一兜底桶"？ | ⚠️ `default` |
> | **入口完整性** | 有哪几个入口能指定 teamId？每个都净化了吗？ | ✅（4 个入口全部净化） |

**最后一行"入口完整性"给出一个可验证的结论 —— 它需要 grep。**

### 2.6 隔离的"纵深"：为什么一层不够

**即使每个存储都净化了，也仍然建议在"边界"净化。** 理由是**纵深防御**：

```
第 1 层：HTTP 边界（Teams.fromRequest / TeamResolver）   ← 拒绝非法输入
第 2 层：领域对象（PullRequest / ReviewContext）          ← 应该保证类型正确（当前没有）
第 3 层：存储层（各 Store）                               ← 应该保证键正确（当前不一致）
```

**当前状态：**

| 层 | 状态 |
|---|---|
| HTTP 边界 | ✅ 全部净化 |
| 领域对象 | ❌ `record` 的 `String teamId` **不做任何校验** |
| 存储层 | ⚠️ **部分净化，口径不一** |

**存储层的具体不一致（grep 结果）：**

| 存储 | 是否净化 `teamId` |
|---|---|
| `SkillRegistry` | ⚠️ **部分**（加载时净化、查询时不净化 —— 2.4 节） |
| `PgKnowledgeStore` | ✅ `Teams.sanitize(teamId)` |
| `InMemoryKnowledgeStore` | ✅ `Teams.sanitize(teamId)` |
| `CustomAgentStore` | ✅ `Teams.sanitize(teamId)` |
| `KnowledgeIngestionService` | ✅ `Teams.sanitize(teamId)` |
| `InMemoryFeedbackStore` | ✅ `Teams.sanitize(teamId)` |
| **`PgFeedbackStore`** | **❌ 直接用原始 `teamId`** |
| **`PgExperienceLibrary`** | **❌ 直接用原始 `teamId`** |
| **`PgVectorMemoryStore`** | **⚠️ `teamId == null \|\| isBlank ? GLOBAL : teamId`**（归一但**不净化**） |
| **`InMemoryVectorStore`** | **⚠️ 同上** |
| `RagContextBuilder` | ✅ `Teams.sanitize(teamId)` |

**注意三种不同的处理方式：**

1. **`Teams.sanitize(...)`** —— 完整净化（字母数字+下划线+连字符，非法 → `default`）；
2. **`teamId == null || isBlank ? GLOBAL : teamId`** —— **只处理空值，非法字符原样放行**；
3. **原样使用** —— 什么都不做。

**同一个非法 `teamId`（比如 `"team@acme"`）在不同存储里的归属：**

| 存储 | 落到哪个团队 |
|---|---|
| `PgKnowledgeStore` | `default` |
| `PgVectorMemoryStore` | `team@acme`（原样） |
| `PgFeedbackStore` | `team@acme`（原样） |
| `InMemoryFeedbackStore` | `default` |

**④ 两种"读回来"的差异：**

> **在内存实现里落在 `default`，在 PG 实现里落在 `team@acme`** ——
> **于是本地（内存）测试通过，生产（PG）行为不同。**
>
> **这和第 45 讲要讲的那条原则是同一件事**："**dev 与生产走不同路径 = 本地验过的路径不是线上跑的路径。**"

**而当前能"侥幸安全"的唯一原因是：所有入口都净化了。** 换句话说：

> **存储层的净化不一致，在当前入口纪律下是不可观测的 —— 而它是一颗定时炸弹：任何绕过入口的新调用路径都会引爆它。**

**结论：净化应该"在入口做一次，并保证入口是唯一的"。**

- 如果入口是唯一的 → **存储层不需要净化**（重复净化无害但会掩盖问题）；
- 如果入口不唯一（当前情况：有 8 个 HTTP 入口 + 编程式构造 `PullRequest`）→ **必须在领域层归一（类型化 `TeamId`）**。

**"存储层各自净化"是最差的方案** —— **它给人一种"已经防住了"的错觉，而实际上每处的口径都不一样。**

**把"多处净化"的数量账拍出来，你就知道该不该收敛到一处。** 每次净化都是一条正则匹配（约 ns~µs 级，`[A-Za-z0-9_\-]{1,64}` 极快），真正的成本不是 CPU，是"N 处各自维护一份净化口径"的隐性差：

> 设数据类别 K=11（§2.1 那张表的行数）、`teamId` 会进入的存储/路径点位 P=8、每处净化口径的历史出岔概率 q≈5%（`sanitize`/`原样`/`空值归一`三种写法并存，正是出岔的高发区）。
> **不收敛**：出现"同一非法 teamId 在不同库落在不同团队"的概率 ≈ 1 − (1 − q)^P ≈ **1 − 0.95⁸ ≈ 34%**——三成可能，一个非法输入就在两个库分道扬镳。
> **收敛到入口一处 + 领域层 compact 构造器归一**：P 从 8 降到 1，出岔概率降为 ≈ **q ≈ 5%**。
>
> 关键不是正则快不快，而是 **P（净化点个数）每多 1，跨库不一致的概率就上一档**；而多租户不一致的后果（跨团队数据串味）是隔离级别的安全事件。

**工程判据：** **净化必须在『入口唯一』或『领域层（record 紧凑构造器）』做一次，并保证 P ≤ 2（入口 + 领域兜底）；当『同一输入在不同存储落到不同团队』的可观测信号（如一条非法 teamId 在不同表的归属）一旦出现，先数净化点个数 P 是不是 ≥3——P 每多一处，都是一颗定时炸弹。** 隔离的正确性靠类型/构造器，不靠 N 处各自记得净化。

## 三、代码

### 3.1 请求入口：`Teams.fromRequest`

```java
// tenant/Teams.java:32-40
/**
 * 从 HTTP 请求中提取团队标识：优先 {@code X-Team-Id} 头，其次 {@code team} 参数，最后回退默认团队。
 *
 * @param header X-Team-Id 请求头（可为空）
 * @param param  team 请求参数（可为空）
 * @return 净化后的团队标识
 */
public static String fromRequest(String header, String param) {
    if (header != null && !header.isBlank()) {
        return sanitize(header);
    }
    if (param != null && !param.isBlank()) {
        return sanitize(param);
    }
    return DEFAULT;
}
```

**"头优先于参数"** —— 这个顺序是对的：

| 位置 | 谁写 | 特点 |
|---|---|---|
| **请求头 `X-Team-Id`** | 前端 / 网关 / 调用方 SDK | **更"正式"**，不容易被 URL 手工改写 |
| **查询参数 `team`** | 手工测试 / 临时调试 | **更方便**，但容易被误传播（分享 URL 时带上） |

**"头优先"给了机器调用一个稳定的通道，同时保留了人工调试的便利。**

**注意它返回的是"净化后的值"** —— 所以**调用方拿到的一定是合法值**，不需要自己再净化。

**这也解释了为什么 `PullRequest.teamId()` 在生产路径上总是合法的** —— 因为它在入口就被归一了。

### 3.2 团队的完整传播路径

**`teamId` 从 HTTP 头一路走到存储，中间经过哪些环节？**


<img class="mermaid-svg" src="/zh/book-assets/diag-0105.svg" alt="`teamId` 从 HTTP 头一路走到存储，中间经过哪些环节？" />

> **图 24-1**　`teamId` 从 HTTP 头走到六个消费方。**两个净化入口 + 六个消费方 = 租户隔离的全部接触面**；漏掉其中任何一个，隔离就出现一个缺口。

**注意 `ReviewContext` 是唯一的载体** —— **teamId 没有存在 ThreadLocal 里，而是作为显式参数传递。**

**这是一个正确的选择**，理由：

| | ThreadLocal 传 teamId | **显式参数（当前）** |
|---|---|---|
| 跨线程（`supplyAsync`） | ❌ **必须 `wrap`**，否则丢 | ✅ 天然携带 |
| 可测试性 | ⚠️ 需要 set/clear 配对 | ✅ 直接传 |
| 看到"这个函数依赖 teamId" | ❌ 隐藏依赖 | ✅ 签名即声明 |
| 忘记传 | ❌ 静默落到默认值 | ✅ 编译错误 |

**最后一行是关键：`ThreadLocal` 忘记 set 的后果是"静默用默认值"，而显式参数忘记传是编译错误。**

> **"能用参数传的东西，不要用 ThreadLocal 传"** —— 这条原则在**多租户**场景下尤其重要，因为 ThreadLocal 在异步边界（`supplyAsync`、线程池、`CompletableFuture`）上**不会自动传播**（第 20 讲）。
>
> **本项目里用 ThreadLocal 的是 `traceId`（第 15/20 讲）—— 那是一个"丢了会导致可观测性下降、但不会导致业务错误"的东西。**
>
> **而 `teamId` 丢了会导致隔离错误（业务错误）** —— **所以它用参数传，这是对的取舍。**

### 3.3 一个"最轻量"的改进：把 `teamId` 的校验放进领域对象

**当前 `PullRequest` / `ReviewContext` 是纯 `record`，不做任何校验：**

<img class="mermaid-svg" src="/zh/book-assets/diag-0106.svg" alt="当前 `PullRequest` / `ReviewContext` 是纯 `record`，不做任何校验：" />

> **图 24-3**　`PullRequest.teamId` 从"纯 record 无校验"到"紧凑构造器归一"的改前改后对比。**这张图给出的新结论是：紧凑构造器里的一次 `Teams.sanitize(...)`，可以把存储层的净化整片删掉**——因为值在进入业务层之前就已经合法了。**而它的成本只是一次正则匹配（每 PR 一次，可忽略）**，这也是本讲把这条改动称作"最轻量"的原因。

**收益：**

| | 改前 | 改后 |
|---|---|---|
| 从任何路径构造 PR | 非法 `teamId` 原样进入系统 | **构造即归一** |
| 存储层要不要净化 | 必须（且口径不一） | **可以删掉**（值已保证合法） |
| `SkillRegistry` 的不一致 | 会静默失效 | **不可能发生**（raw == sanitized） |

**代价**：一次正则匹配（每个 PR 一次，可忽略）。

**而它顺带解决了 2.4 节的问题** —— **因为传入的 `teamId` 永远是净化后的，`ensureTeamLoaded` 里的 `t` 和查询用的 `teamId` 必然相等。**

> **这就是"把纪律变成结构"的威力：**
>
> - **纪律**：8 个入口都记得净化（当前靠 code review 维持）；
> - **结构**：值在构造时就合法（靠编译器/构造器维持）。
>
> **成本是一行代码。**
>
> **同样的改法适用于 `ReviewContext`**（它也接收 `teamId`）。
>
> **注意 `ResumeState`（断点状态）也带 `teamId`** —— 它从 `PullRequest` 来，所以只要 `PullRequest` 归一了，它就安全。

**为什么这是一个"轻量"改进而不是"彻底"改进？**

因为它**没有把 `teamId` 变成类型** —— 别人仍然可以写 `context.teamId()` 并把它当普通字符串用：

```java
// 仍然是合法的（虽然经过归一，但类型上无法阻止用错）
String s = ctx.teamId() + "/" + something;      // 拼路径
```

**彻底的改法是 `record TeamId(String value)`（2.4 节末尾）** —— **但它的改动面覆盖全部存储签名，成本高。**

**分层建议：**

| 阶段 | 做法 | 成本 |
|---|---|---|
| **立刻** | 紧凑构造器归一 | **一行** |
| **中期** | 统一所有存储的净化口径（或删掉，因为值已保证合法） | 十几个文件 |
| **长期** | `record TeamId` 类型化 | 全部签名 + 存储层 |

> **这个"三层改进路线"本身就是一个可以拿去做技术方案的模板**：把一个正确性问题分解成"立刻能做的一行"、"中期的一批"、"长期的一次重构"。

### 2.7 租户模型的工业界形态：共享表 + 行级过滤 / 分 schema / 分库

<img class="mermaid-svg" src="/zh/book-assets/diag-0107.svg" alt="本讲 §2.1 给出了三层的&quot;全局基线 + 团队叠加&quot;模型，§2.5 列了 11 类数据的隔离情况。本节把视角换成基础设施侧：这套模型落在数据库上，有几种典型形态，而本项目的选择决定了它的代价出现在哪里。" />

> **图 24-4**　三种租户隔离形态，与它们各自的成本落点。**这张图要给出的新结论是：隔离形态的选择不改变"正确性"，它改变的是"绕过面有多大"。** 共享表把过滤的举证责任交到**每一条新写的查询**手上（绕过面随代码量线性增长）；分库把责任收敛到**连接的选择**上（绕过面固定，但运维成本最高）。**本项目选第一种是对的**（租户数少、数据量小），**但它的代价必须被显式认识：每一条绕过 `WHERE team_id` 的新查询都是一个隔离缺口**——而这正是 §2.6 那张"11 个存储 3 种净化口径"的表所证明的。

### 2.8 行级安全的工程实现：把过滤下沉到数据库

上一节说共享表的绕过面 = 每一条新查询。数据库侧对此有一个直接的答案：**把过滤下沉成策略，让"忘写 WHERE"在物理上不可能**。

<img class="mermaid-svg" src="/zh/book-assets/diag-0108.svg" alt="上一节说共享表的绕过面 = 每一条新查询。数据库侧对此有一个直接的答案：把过滤下沉成策略，让&quot;忘写 WHERE&quot;在物理上不可能。" />

> **图 24-5**　应用层过滤与数据库行级安全，两者的绕过面分别在哪里。**这张图要给出的新结论是：把过滤下沉不等于"零成本"，它只是把绕过面从"N 条查询"换成了"1 个连接状态"。** 后者数量上更小、更容易审计，但它是**有状态**的——而"有状态"在连接池环境下是一个新问题：**连接会被复用，会话变量必须与借还严格配对。**

**PostgreSQL 的行级安全（RLS）是这条路的官方实现**：它允许为表启用行级策略，使查询在返回行之前按策略过滤（对应官方文档 *Row Security Policies*，`postgresql.org/docs/17/ddl-rowsecurity.html`），策略本身用 `CREATE POLICY` 定义（对应 *CREATE POLICY* 语法页，`postgresql.org/docs/17/sql-createpolicy.html`）。这两页都是本讲的 P1 引用（已机检 200 + 探针串命中）。

> **引用形态说明**：上面两句是**对该官方文档内容的转述**（"该文档把 X 定义为 Y"），不是逐字引用——按本书约定，外部资料不参与"逐字引用"，逐字只用于代码仓。

**而这里有一个必须写清楚的工程约束：RLS 的策略通常依赖会话级变量**（如 `current_setting('app.tenant_id')` 这类由应用在查询前设置的变量）。于是：

| 环节 | 需要保证的事 | 本项目现状 |
|---|---|---|
| 连接借出 | 设置会话变量（租户身份） | ❌ 无（当前是应用层 `WHERE`） |
| 查询执行 | 策略按会话变量过滤 | ❌ 无 |
| 连接归还 | **清理或重置会话变量** | ❌ 无 |

**这三步必须配对，而连接池（本项目用 HikariCP，第 45 讲）会复用连接。** ⇒ **如果归还时没有重置，下一个租户会继承上一个租户的身份** —— 这与本讲 §2.6 讨论的"存储层净化口径不一"是**同一类故障**（状态在复用点泄漏），只是层级从应用内存换到了数据库连接。

> **判据：把过滤下沉到数据库，同时也就把"隔离正确性"绑定到了"连接生命周期"上。** 所以采用 RLS 的系统，必须**同时**回答"会话变量在哪里设、在哪里清、连接池是否保证二者成对出现"。**这三个问题的答案要写在配置附近，而不是散在代码里**——因为它们是**跨请求、跨租户**的状态，出问题时最难以复现。

**最后一条诚实的补充：本项目当前没有采用 RLS，而且这不是"欠着的债"。** 8 张表里 7 张带 `team_id`（复算见 §2.9），共享表 + 应用层过滤在**当前租户量级与团队规模下是完全合理的**选择。**风险不在"没用 RLS"，而在"还没把绕过面的数量控制住"**——也就是 §2.6 那张表里的 3 种净化口径。**先把净化收敛到 ≤ 2 处（§2.6 的结论），再考虑要不要下沉**，顺序反了会把两个问题叠在一起。

### 2.9 搬到你自己系统：多租户的六项审计

本讲 §2.5 已经给了一张"**问什么**"的类别表（主数据 / 派生数据 / 缓存 / 异步任务 / 共享基线 / 保留值 / 兜底归属 / 入口完整性）。本节给的是它的**可执行版本**——**六项能用 grep 或一次扫描跑出来的检查动作**。两者的关系是：§2.5 的表告诉你**该问哪些类别**，这六项告诉你**每个类别怎么查**。

| # | 检查动作 | 具体做法 | 本项目结果 |
|---|---|---|---|
| 1 | **列名字典扫描** | 对所有 `CREATE TABLE` 抽 `team_id` 的出现/缺失，把缺的表列出来 | 8 张表 → **1 张缺**（`calibration_accuracy`） |
| 2 | **净化点计数** | 数 `Teams.sanitize(` 的位置，与"会接 `teamId` 的存储类"个数比 | 11 个存储 → **3 种口径** |
| 3 | **入口枚举** | grep `Teams.fromRequest` / `TeamResolver.resolve`，与 `@RestController` 总数比 | **8 个入口，全部净化** |
| 4 | **缓存键审计** | 所有 cache key / map key 的构造表达式里，有没有租户维度 | ❌ `memoryIdFor` 只有 Agent-PR（本讲 §2.5 类别二） |
| 5 | **派生值出口审计** | 从租户数据算出的标量（系数 / 统计 / 索引）有没有租户维度 | ❌ 置信度准确率（本讲 §2.5 类别一） |
| 6 | **跨租户读取路径审计** | 哪些查询允许一次读多个租户（如 `includeGlobal`），**默认值是哪个** | ⚠️ 默认由调用方 boolean 决定（本讲 §2.1） |

**第 1 项的复算方式**（本项目，已实跑）：对 `PgDb.java` 的每个建表区间做两次统计——`grep -c 'CREATE TABLE IF NOT EXISTS'` 得 **8**；对每张表的定义区间 grep `team_id`，命中 **7** 张（`resume_state` :112 / `team_kv` :120 / `experience_entry` :128 / `review_feedback` :145 / `review_history` :153 / `trajectory_store` :162 / `knowledge_meta` :170），**缺的那张是 `calibration_accuracy`（:185）**。

**第 6 项值得单独说一句，因为它是六项里唯一"默认值决定行为"的一项。** `includeGlobal` 这类开关的默认值如果是 `false`，那么**忘传参数的后果不是报错，而是静默地丢掉全局基线**——这和第 20 讲 §2.8 那个"死配置"（配置存在、代码不读）是**同一类问题的两个方向**：

> - 死配置：**有配置，没有代码读它** → 看起来配了但没生效；
> - 默认 false：**有代码，默认关着** → 看起来能用但默认不用。
>
> **两者的共同点：失效是静默的，而且都在"看起来很正常"的状态下发生。**

**搬到你自己系统**，五步：

1. **跑第 1 与第 3 项**（列名字典扫描 + 入口枚举）。这两项成本最低、结论最硬，而且**能立刻告诉你隔离的"表面完整度"**。
2. **跑第 2 项（净化点计数），并要求结果 ≤ 2**。本讲 §2.6 已经算过：净化点从 8 收敛到 1，跨库不一致的概率从约 34% 降到约 5%。**如果结果是 ≥ 3，先别谈下沉到数据库，先把口径收敛。**
3. **跑第 4 与第 5 项**（缓存键、派生值）。这两项**最难靠代码搜索发现**，因为"派生值看起来不像数据"（它是一个系数、一个统计量）。**可行的做法是反过来：把所有"从租户数据算出来的标量"列一遍，逐个问它带不带租户维度。**
4. **检查第 6 项里所有"跨租户读取"开关的默认值**，并把默认值改成"安全的那一侧"。**如果默认必须是 `false`（为了性能），就在启动日志里打印一次当前取值。**
5. **把六项做成一个可复跑的脚本或 checklist**，而不是一次性的审计。**理由是这六项里有两项（入口枚举、列名字典）会随每次新增代码而失效**——它们不是"一次修好就永久正确"的东西。

**判据**：**多租户的审计必须能给出六个数，而不是六句"应该没问题"：表数里有多少张带租户列、净化点有几个、入口有几个且是否全部净化、缓存键里有没有租户维度、派生值有没有租户维度、跨租户开关的默认值是哪一侧。** 六个数里任何一个给不出来，那块隔离就处在"看起来做了、但没人能证明它做了"的状态——**而这种状态在出事之前和"做好了"没有任何区别。**

## 四、避坑清单

- [ ] **三层模型**：内置（代码）/ 全局基线（`__global__`）/ 团队私有 —— **"共享但需热更新"的内容必须有第二层**。
- [ ] **"用保留值表达语义"的代价是语义靠约定维持**（`includeGlobal` 忘了传就静默看不到基线）。
- [ ] **`sanitize` 必须存在**：`teamId` 会进文件路径、表键、保留值判断。
- [ ] **保留值要在净化时"特批"**，而不是"恰好匹配正则" —— 这样"收紧正则"不会静默干掉全局功能。
- [ ] **别把"非法"和"未提供"归一成同一个结果**：前者应拒绝或 WARN，后者回退 `default` 是合理的。
- [ ] **保留值的来源必须净化**（`TeamResolver.resolve(..., override)` 里的 override 也要净化，否则它是绕过净化的后门）。
- [ ] **匹配优先级"更具体优先"**（`owner/repo` > `owner` > default）。
- [ ] **净化作用域必须一致**：**不要"加载时净化、查询时不净化"** —— 键不匹配会静默退回默认行为。
- [ ] **靠调用方纪律维持的隔离不是隔离** —— 用类型或构造器把它变成结构。
- [ ] **隔离审计必须覆盖两类易漏项**：**派生数据**（系数/统计量/索引）和**缓存**（缓存键里有没有 tenant）。
- [ ] **`prId` 不是全局唯一的**（跨仓库、跨团队会重复）—— 任何以它做键的地方都要补上 repo/team。
- [ ] **存储层净化口径不一致 = 定时炸弹**：当前侥幸安全只是因为入口都做了。
- [ ] **`dev` 用内存实现、生产用 PG，若两者净化行为不同 → 本地验过的路径不是线上跑的路径。**
- [ ] **能用参数传的上下文不要用 ThreadLocal**（`teamId` 用参数 ✅，`traceId` 用 ThreadLocal 可接受）。
- [ ] **最小成本的改进：在 `record` 的紧凑构造器里归一** —— **一行代码把"入口纪律"变成"构造期事实"。**
- [ ] **别以为"共享表 + 应用层过滤"的隔离是"一次做好就永久正确"的。** 它的绕过面等于**每一条新写的查询**——绕过面随代码量线性增长，而"我加了 WHERE"这件事没有任何工具替你检查。本项目 11 个存储里出现的 **3 种净化口径**就是这条曲线的一个截面。（§2.7）
- [ ] **别用保留值（`__global__`）表达语义，却不把它的边界写成代码。** 保留值路线的代价是"语义靠约定维持，约定靠人记住"。⇒ **必须有一处代码负责拒绝用户占用它**——本项目的 `sanitize` 把 `__global__` 特批放在正则校验**之前**（`Teams.java:49-51`），这就是那个边界。**只写在文档里的保留值，迟早会被当成普通值用。**（§2.7）
- [ ] **别把"把过滤下沉到数据库"当成零成本方案。** 它只是把绕过面从"N 条查询"换成了"1 个连接状态"——而**有状态的东西在连接池环境下会带来新问题**：会话变量必须在连接借出时设置、归还时清理，**配对失败就会让下一个请求继承上一个租户的身份**。（§2.8）
- [ ] **别把顺序做反：先收敛净化点，再考虑下沉。** 本项目当前没上 RLS 是**合理**的（租户量级与团队规模都还小）；真正的风险不是"没用 RLS"，而是"11 个存储 3 种口径"。**先把净化点收敛到 ≤ 2 处，否则下沉只是把两个问题叠在一起。**（§2.8）
- [ ] **别把多租户审计做成"六句应该没问题"。** 它必须给出**六个数**：表数里有多少张带租户列、净化点有几个、入口有几个且是否全部净化、缓存键里有没有租户维度、派生值有没有租户维度、跨租户开关的默认值是哪一侧。**任何一个数给不出来，那块隔离就处在"看起来做了、但无法证明它做了"的状态**——而这种状态在出事之前和"做好了"没有区别。（§2.9）
- [ ] **派生数据是最容易漏的类别，因为它"看起来不像数据"。** 一个系数、一个统计量、一个索引，漏掉隔离的表现不是"数据串了"，而是 **"行为不一致"**——后者更难被注意到（第 22 讲的置信度准确率就是这一类）。（§2.9）
- [ ] **别只盯着"死配置"，也要盯"默认关着"。** 死配置是"有配置、没有代码读它"；默认 `false` 是"有代码、默认不启用"。**两者的共同点是失效静默、且都发生在"看起来很正常"的状态下**——`includeGlobal` 忘传就是"静默地看不到全局基线"，而不是报错。（§2.9）

## 本讲小结

1. **三层模型**：内置（代码）/ 全局基线（`__global__`）/ 团队私有 —— **第 2 层是为了"共享但需热更新的内容"**，它用保留值实现，代价是语义靠约定维持。
2. **`sanitize` 是必需的**（`teamId` 会进路径与表键）；**保留值的"特批"判断是一个保护未来修改的安全网。**
3. **把"非法"归一成 `default` 是一个可讨论的取舍** —— 它和第 45 讲的"连不上就启动失败"取向不一致。
4. **解析优先级"更具体优先"**（`owner/repo` > `owner` > default）；**override 也必须净化**，否则它是后门。
5. **★ `SkillRegistry` 是本讲最具体的缺陷**：加载时净化、查询时不净化 → **键不匹配 → 技能启停与自定义规则静默失效**。生产路径侥幸安全，**只因为 8 个入口都净化了。**
6. **隔离审计的两个易漏类别是"派生数据"和"缓存"** —— 本项目的置信度准确率（全局）与 `ChatMemory` 的 memoryId（无 repo/team）。
7. **存储层净化口径不一（三种处理方式）= 定时炸弹**，而且**内存实现与 PG 实现的归属不同 → dev 与生产不同路径**。
8. **`teamId` 用参数而不是 ThreadLocal 传递，是正确的取舍**（ThreadLocal 在异步边界丢，而丢了会导致隔离错误）。
9. **最小成本的改进是一行**：在 `record` 的紧凑构造器里归一 —— **把"入口纪律"变成"构造期事实"。**
10. **中心论点**：**隔离的正确性不该依赖"每个调用方都记得净化"，而该依赖"类型系统不允许未净化的值进入"。**

**模块三到此结束。** 你现在有了一个完整的多 Agent 协作系统：**拓扑（星型）、节点（Agent 抽象）、编排（并行 + 超时）、聚合（去重 + 仲裁 + 抑制）、打分（校准）、准入（成本）、边界（多租户）。**

**从第 26 讲开始，我们处理最后一块拼图：知识。** 审查 Agent 现在只能看到 diff 和规则 —— **它凭什么知道"这个团队的规范是什么、历史上踩过哪些坑"？** 那就是 RAG。
