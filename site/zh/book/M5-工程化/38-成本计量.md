# 第 38 讲 · 成本计量：不让钱算错，也不让账单缺口消失

## 一、痛点

网关上线一个月，财务同学拿着我的月度报表来找我，问了一个我答不上来的问题：

> "你这里 3 月总花费 12,847.63 元。我这边采购发票是 13,912.40 元。**差的这 1,064 块去哪了？**"

我把账单翻了三遍，发现三类问题：

**第一类：金额本身有漂移。** 我最初用 `double` 存费用。累加了几十万条记录后，总额和逐条重新加一遍**差了 0.03 元**。0.03 元不多，但它意味着 **"对不上账"**——而一旦对不上账，财务就不会认这张表，这张表就变成了"研发自己看看"的东西。

**第二类：账面上有一些"0 元"的记录。** 有 4,000 多次调用，`cost = 0`。原因是我漏配了某个新供应商的价格规则——**代码返回 0 而不是报错**。

**第三类：有一批调用压根没进账单。** 这一批是"被额度拦截的调用"。

三类的共同点：**它们都不是"算错了"，而是"没算"或"算成了 0"。**

**金额错误分两种：算错（错误可见）和没算（错误不可见）。后者危险得多。** 而绝大多数团队的监控只盯"花费是否异常上涨"，**没有任何一个指标盯"该记的账有没有记"**。

## 二、原理

### 2.1 钱的表示：`long` 微元

<img class="mermaid-svg" src="/zh/book-assets/diag-0168.svg" alt="### 2.1 钱的表示：`long` 微元" />

> **图 38-1**　`Money` 的对象形态。核心就两个字段：`micros`（long 微元）和 `currency`（货币代码）。**为什么不用 `double`**：`0.1 + 0.2 != 0.3`，账单累加会漂移；**为什么不用 `BigDecimal`**：每次运算都分配对象，热路径 GC 压力白送，且精度要人为指定。**"整数最小单位"是唯一同时满足精确和廉价的方案。** 注意 `amount()` 那个警示——它假定 `micros ≥ 0`，将来加退款/冲正时会丢符号。

三个决策：

**① 用 `long` 而不是 `double` / `BigDecimal`。**

为什么不用 `double`：`0.1 + 0.2 != 0.3`。单次误差是 `1e-17` 量级，但**账单是累加出来的**——错误会随记录数线性增长，而"对不上账"只要差一分钱就成立。

为什么不用 `BigDecimal`：它当然正确，但**每次运算都要分配对象**（`BigDecimal` 是不可变的），在"每次 LLM 调用都要算一次钱"的热路径上，GC 压力是白送的。而且 `BigDecimal` 的精度是**需要人为指定的**——`new BigDecimal(0.1)` 和 `new BigDecimal("0.1")` 是两个不同的值，这个坑比 `double` 更隐蔽。

**"整数最小单位"是唯一同时满足"精确"和"廉价"的方案。**

**② 1 元 = 1,000,000 微元。** 为什么是 6 位小数？因为 LLM 单价本身很小——`deepseek-chat` 量级的输入价大约是"每 1000 token 几厘钱"。用"分"（1/100）做单位，**单次调用会被四舍五入成 0**。微元给了足够的分辨率，让单次调用也有意义的整数表示。

**③ 只在展示时换算。**

```java
/** 元（或其他货币主单位）的十进制字符串，保留 6 位小数。 */
public String amount() {
    long major = micros / 1_000_000L;
    long minor = Math.abs(micros % 1_000_000L);
    return major + "." + String.format("%06d", minor);
}
```

**但这里有一个真实的缺陷：负数会丢符号。**

Java 的 `/` 是**向零截断**的：`-500000 / 1000000 = 0`（不是 `-1`）。而 `minor` 用了 `Math.abs`。所以：

| `micros` | 期望输出 | 实际输出 |
|---|---|---|
| `1_500_000` | `1.500000` | `1.500000` ✓ |
| `-1_500_000` | `-1.500000` | `-1.500000` ✓（`major = -1`，能兜住） |
| **`-500_000`** | **`-0.500000`** | **`0.500000`** ✗ |

`micros = -500000` 时，`major = -500000 / 1000000 = 0`，`minor = abs(-500000) = 500000` → 输出 `"0.500000"`。**一个 0.5 元的负数变成了 0.5 元的正数——符号翻转，方向反了。**

现在项目里 `Money` 只有 `plus`，不会产生负数，所以这个缺陷**暂时不可达**。但只要将来加一个 `minus`（退款、冲正、优惠抵扣），它就会立刻生效，而且**错误方向是"把退款变成收入"**。

**这类缺陷的教训是：`amount()` 是一个"展示层"方法，但它的实现对取值域做了隐藏假设（"micros ≥ 0"）。** 这个假设既没写进注释、也没被断言。修法是把假设变成代码：

```java
// 修法示意（不是仓库现状）
public String amount() {
    long abs = Math.abs(micros);
    String sign = micros < 0 ? "-" : "";
    return sign + (abs / 1_000_000L) + "." + String.format("%06d", abs % 1_000_000L);
}
```

**数量级直觉：为什么单位必须是"微元"，而不是"分"。**

"1 元 = 1_000_000 微元"不等于"把小数位拉长"，它对应一个真实的量级判断——**单位分辨率必须盖得住"最小可能的单次费用"**。用 LLM 的典型单价算一遍：

```text
- deepseek-chat 量级：输入价 ≈ 每 1000 token 0.5 元（示意口径），单次平均 300 输入 token
  → 单次费用 = 300/1000 × 0.5 = 0.15 元 —— "分"（1/100）还能表示（15 分）
- 更低价位、更短调用：如每 1000 token 0.01 元、单次 20 token
  → 单次 = 20/1000 × 0.01 = 0.0002 元 = 0.02 分
  → 用"分"：四舍五入成 0 分（这比"记错"更糟——它让你以为"这次没花钱"）
  → 用"微元"：0.0002 元 = 200 微元，单次有精确的整数表示
- 结论：分把"很小但非零"的单次费用压成 0；微元把下限压到"单笔都有意义"
```

> **工程判据：金额单位的分辨率必须刻在最坏情形（单价 × 最短调用）上，使最小可能单次费用仍是非零整数。** 否则微小的调用会系统性变成 0——那正是本讲"宁可少算也不猜价格、但更怕记 0"要避免的"看起来没花钱"。

三种金钱表示的取舍收口成一张表：

| 表示 | 决策 | 代价 | 适用 |
|---|---|---|---|
| `double` 元 | 直接字节数 | 累加漂移、`0.1+0.2≠0.3` | 只要展示不要对账 |
| `BigDecimal` | 精确十进制 | 每次运算分配对象、精度要人为指定 | 需要任意精度、低频 |
| `long` 微元 | 整数最小单位 | 括号整 + 换算只在展示层 | 高频精确累加（本讲选择） |

### 2.2 计价规则：通配 + 特异度

<img class="mermaid-svg" src="/zh/book-assets/diag-0169.svg" alt="### 2.2 计价规则：通配 + 特异度" />

> **图 38-2**　`PriceRule` 的对象形态。一条规则 = "谁的什么模型，输入输出各多少钱"。`specificity()` 用"供应商精确 1000 分 + 模型长度分"的数量级拼接，让"供应商精确 + 模型通配"永远赢过"供应商通配 + 任意长模型"——不需要多级比较器，一个 `int` 就够了。

**特异度用两个数量级分离的分数段拼接**：

- `providerScore`：精确 `1000` / 通配 `0`
- `modelScore`：模式字符串长度（最长也就几十）

所以"供应商精确 + 模型通配"（`1000`）永远赢过"供应商通配 + 任意长模型"（≤ 几十）。**这是"用数字位数制造优先级"的经典技巧**——不需要写多级比较器，一个 `int` 就够了。

`globToRegex` 把 `*` / `?` 翻译成正则，并且**转义了正则元字符**：

```java
private static Pattern globToRegex(String glob) {
    StringBuilder sb = new StringBuilder();
    for (char c : glob.toCharArray()) {
        switch (c) {
            case '*' -> sb.append(".*");
            case '?' -> sb.append('.');
            case '.', '(', ')', '[', ']', '+', '^', '$', '|', '\\' -> sb.append('\\').append(c);
            default -> sb.append(c);
        }
    }
    return Pattern.compile(sb.toString(), Pattern.CASE_INSENSITIVE);
}
```

**这段代码做对了最容易忘的一件事**：把用户输入的 `gpt-4.1` 里的 `.` 转义掉。不转义的话，`.` 是正则的"任意字符"，`gpt-4.1` 会匹配上 `gpt-4x1`。**"用户输入进正则必须转义"是零容错的**，漏一个字符就是一个静默的错误匹配。

### 2.3 `PricingEngine`：宁可少算也不猜价格

```java
/**
 * 计价引擎：把一次调用的 token 用量换算成金额。
 *
 * <p>匹配优先级：供应商精确 &gt; 供应商通配；同级取模型模式更具体的一条。
 * 一条规则都没命中时返回 {@code 0} 并在日志告警——<b>宁可少算也不猜价格</b>，
 * 漏配的计价规则由对账任务发现后补录，猜出来的价格会污染账单。
 */
public final class PricingEngine {

    public Money price(String providerCode, String upstreamModel, TokenUsage usage) {
        if (usage == null || usage.totalTokens() == 0) {
            return Money.zero(currencyOf(providerCode, upstreamModel));
        }
        PriceRule rule = match(providerCode, upstreamModel);
        if (rule == null) {
            return Money.zero("CNY");
        }
        long in = roundDiv(usage.promptTokens() * rule.inputMicrosPer1k(), 1_000L);
        long out = roundDiv(usage.completionTokens() * rule.outputMicrosPer1k(), 1_000L);
        return Money.ofMicros(in + out, rule.currency());
    }

    /** 四舍五入的整数除法，避免浮点误差。 */
    private static long roundDiv(long numerator, long denominator) {
        return (numerator + denominator / 2) / denominator;
    }
}
```

**"宁可少算也不猜价格"是这一讲最重要的一句设计原则。** 它背后的推理是：

> 漏配规则 → 账少了 → 财务发现差额 → **人来补录，错误可修正**。
> 猜一个价格 → 账错了 → **看起来是对的，没人会去核**。

**"看起来对"比"明确错"危险得多。** 一个显式的 0 至少能触发"为什么是 0"的疑问；一个猜出来的 `0.0037` 元会安安静静地进账单，永远不会被质疑。

**但这段注释有一处不诚实：它说"并在日志告警"，而 `PricingEngine` 类里根本没有 Logger。**

```java
public final class PricingEngine {

    private final List<PriceRule> rules;
```

它连 `import org.slf4j.Logger` 都没有。真正打这条日志的是**调用方** `PricingService`：

```java
public Money price(String providerCode, String upstreamModel, TokenUsage usage) {
    PricingEngine current = engine();
    if (current.match(providerCode, upstreamModel) == null) {
        log.warn("缺少计价规则：provider={} model={} —— 本次按 0 计费，请尽快补录",
                providerCode, upstreamModel);
    }
    return current.price(providerCode, upstreamModel, usage);
}
```

有意思的是，**同一个文件里的另一处注释是准确的**：

```java
/** 命中的规则；无匹配返回 {@code null}（调用方据此打「计价规则缺失」告警）。 */
public PriceRule match(String providerCode, String upstreamModel) {
```

`match()` 的注释把责任写给了调用方 ✓，`price()` 的类注释把责任写给了自己 ✗。**一个类里两处注释，一处对一处错。**

这不是"文档瑕疵"，它会**直接影响故障排查**：三个月后有人发现账单有 0 元记录，读到类注释会去 `PricingEngine` 里找日志配置，找不到；而真相是这条日志在 `PricingService` 里，且**只要有人写了另一条调用 `price()` 的路径（绕过 `PricingService`），告警就消失了**。

**顺带一个更隐蔽的性质：并列规则的胜者由加载顺序决定。**

```java
return rules.stream()
        .filter(r -> r.matchesProvider(providerCode))
        .filter(r -> r.matchesModel(upstreamModel))
        .max(Comparator.comparingInt(PriceRule::specificity))
        .orElse(null);
```

`Stream.max` 在**遇到相等值时保留先出现的那个**（它用的是 `reduce` 语义：新值只有在 `compare > 0` 时才替换）。所以当两条规则的 `specificity()` 相同时（比如两条 `provider=*, model=gpt-4*`），**胜者是"先被加载的那条"**——而加载顺序来自 `prices.list()` 的返回顺序，**也就是数据库的返回顺序（没有 `ORDER BY` 时是不确定的）**。

**"并列时取先到的"在这里是一个隐式行为，不是一个显式决策。** 如果要让行为确定，应该补一个决胜条件（比如按 id 排序），或者干脆把"重复规则"当成配置错误在加载时拒绝。

### 2.4 `PricingService`：30 秒 TTL 缓存

计价发生在**每次调用的关键路径**上，而价格表一天都不一定变一次。所以：

```java
private volatile PricingEngine engine = PricingEngine.empty();
private volatile long loadedAtMillis = 0L;

public PricingEngine engine() {
    long now = System.currentTimeMillis();
    if (now - loadedAtMillis > TTL_MILLIS) {
        synchronized (this) {
            if (now - loadedAtMillis > TTL_MILLIS) {
                engine = new PricingEngine(prices.list().stream()
                        .map(r -> r.toCoreRule())
                        .toList());
                loadedAtMillis = now;
            }
        }
    }
    return engine;
}
```

**标准的双检锁**（`TTL_MILLIS = 30_000L`）。但这里有一处值得专门指出的性质：**它是靠"两个 volatile 的写序"才正确的。**

写入顺序是：
```java
engine = new PricingEngine(...);   // 先写 engine
loadedAtMillis = now;              // 后写 loadedAtMillis
```

读取顺序是：
```java
if (now - loadedAtMillis > TTL_MILLIS)   // 先读 loadedAtMillis
return engine;                            // 后读 engine
```

因为 volatile 写有**顺序保证**（前面的写不会被重排到后面），"读到新的 `loadedAtMillis`" 蕴含 "`engine` 已经是新的"。**所以这个双检锁是安全的。**

**但它安全得很脆**：如果哪天有人在两行之间插一句日志、或者把赋值顺序调换、或者把其中一个字段的 `volatile` 去掉（"这个字段只是时间戳啊"）——**双检锁就会静默失效**，表现为"偶发地用到旧价格"，而**旧价格不会报错，只会让账算错**。

这类"靠隐式顺序约束成立的正确性"，正确的处理是**加注释把它钉住**，而现在的代码里没有这行注释。

### 2.5 计量落库：失败也要落，但失败不能拖垮业务

```java
public void record(UsageRecord record) {
    try {
        usage.insert(record);
    } catch (RuntimeException e) {
        // 计量失败不能让业务调用失败，但必须留痕——丢一条用量就等于丢一笔钱
        log.error("用量落库失败（业务调用已成功，需人工补录）：traceId={} provider={} 原因={}",
                record.traceId(), record.providerCode(), e.getMessage(), e);
    }
}
```

**"吞异常 + 留痕"是这里唯一正确的选择**，理由写在注释里：计量是业务的**旁路**，让它失败等于让"记账"拖垮"干活"。但代价是最高的：**这类失败必须被人看见**——而它现在的唯一出口是一行 ERROR 日志（第 42 讲会回到这一点）。

失败记录本身的形态也值得注意：

```java
public static UsageRecord failure(String requestId, String traceId, String tenantCode,
                                  String keyId, String appId, String alias,
                                  String providerCode, String upstreamModel,
                                  long latencyMs, String errorCode) {
    return new UsageRecord(requestId, traceId, tenantCode, keyId, appId, alias,
            providerCode, upstreamModel, 0, 0, 0, 0, "CNY", latencyMs,
            false, errorCode, false, Instant.now());
}
```

**token 记 0、金额记 0，但 `success = false` 和 `errorCode` 都在。** 这样就同时保住了两个信息：

- **"这次调用了"**（请求数 +1）→ 用来算成功率
- **"这次没花钱"**（token/cost = 0）→ 不会污染花费统计

`UsageRecord` 的类注释把这层意思讲得比代码还清楚：

> 失败调用也要落库（token 记 0）：否则「调用量大涨但用量没涨」这类异常永远发现不了。

**"调用量涨了但用量没涨"是 LLM 系统最有价值的异常信号之一**：它同时覆盖了"上游大面积 401"、"模型开始返回空响应"、"计价规则漏配"等多种故障。

### 2.6 而这个信号，恰好漏了最重要的一类

回到 `GatewayService`，看额度校验的位置：

```java
public GatewayResult complete(CallPrincipal principal, ChatRequest request) {
    List<QuotaDecision> decisions = quota.evaluate(principal.tenantCode());
    if (QuotaEvaluator.anyRejected(decisions)) {
        throw new QuotaExceededException(decisions);      // ← 抛在这儿
    }

    long startedAt = System.currentTimeMillis();
    try {                                                 // ← try 从这儿才开始
        ChatResponse response = engine.complete(request);
        Money cost = pricing.price(...);
        metering.record(UsageRecord.success(...));
        ...
    } catch (RuntimeException e) {
        // 失败也要落一条：调用量涨了但用量没涨，是最典型的异常信号
        metering.record(UsageRecord.failure(...));
        throw e;
    }
}
```

**额度拒绝发生在一个 `metering.record` 都到不了的路径上。**

后果是：**被额度拦下的调用，一条记录都不会落库。**

这为什么严重？因为"被拦截"恰恰是**最该被看见的一类流量**：

| 场景 | 落库情况 | 监控看到的现象 |
|---|---|---|
| 上游挂了，全部失败 | ✓ 落 `failure` | 成功率下跌 → 告警 ✓ |
| 计价规则漏配 | ✓ 落 `success`（cost=0） | 花费不涨 → 可查 ✓ |
| **有人狂刷，被额度 REJECT** | **✗ 不落库** | **什么都没发生** ✗ |

第三行是最坏的一种：**你被攻击/被误用的时候，监控是安静的。** 运维在事故复盘时会看到"调用量在某个时间点**下降**了"——因为被拒的请求不计数。**真正的信号（拦截次数）从来没有被记录过。**

注意 `QuotaService.evaluate` 里**确实打了日志**：

```java
for (QuotaDecision d : decisions) {
    if (!d.allowed()) {
        log.warn("额度拦截：tenant={} {}", tenantCode, d.message());
    } else if (d.warn()) {
        log.warn("额度告警：tenant={} {}", tenantCode, d.message());
    }
}
```

所以信息不是完全丢失，而是**降级成了一行日志**：不可聚合、不可画图、不可按租户查询、不能和调用量做比率。**"日志里有"和"指标里有"是两个不同的可用性等级。**

### 2.7 额度判定：注释说对了方向，代码做错了

`QuotaService` 有**两条**取"已用量"的路径。先看查询路径 `snapshot`：

```java
/**
 * 额度现状快照（不计入本次调用，用于查询而非拦截）。
 *
 * <p>按<b>周期分别统计</b>再判定：日额度与月额度的统计起点不同，
 * 若统一取「最早起点」覆盖全部策略，月额度就会被日额度的数据污染。
 */
public List<QuotaDecision> snapshot(String tenantCode) {
    ...
    Map<QuotaPolicy.Period, List<QuotaPolicy>> grouped =
            policies.stream().collect(Collectors.groupingBy(QuotaPolicy::period));
    List<QuotaDecision> out = new ArrayList<>();
    for (Map.Entry<QuotaPolicy.Period, List<QuotaPolicy>> e : grouped.entrySet()) {
        QuotaUsage current = usage.usageSince(tenantCode, periodStart(e.getKey()));   // ← 按周期分别查
        out.addAll(QuotaEvaluator.evaluate(e.getValue(), current, QuotaUsage.ZERO));
    }
    return out;
}
```

**注释明确说："若统一取「最早起点」覆盖全部策略，月额度就会被日额度的数据污染。"** 所以正确做法是**按周期分组、分别统计**——`snapshot` 做对了。

再看**拦截**路径 `evaluate`：

```java
/** 判定一次即将发生的调用（请求数 +1）。 */
public List<QuotaDecision> evaluate(String tenantCode) {
    List<QuotaPolicy> policies = policies(tenantCode);
    if (policies.isEmpty()) {
        return List.of();
    }
    QuotaUsage current = currentUsage(tenantCode, policies);         // ← 统一取最早起点
    List<QuotaDecision> decisions =
            QuotaEvaluator.evaluate(policies, current, QuotaUsage.of(1, 0, 0));
    ...
}

/** 取所有相关周期中最早的那个起点，一次查询覆盖全部策略。 */
private QuotaUsage currentUsage(String tenantCode, List<QuotaPolicy> policies) {
    Instant earliest = policies.stream()
            .map(p -> periodStart(p.period()))
            .min(Instant::compareTo)                                  // ← 取最早的
            .orElseGet(() -> periodStart(QuotaPolicy.Period.DAY));
    return usage.usageSince(tenantCode, earliest);
}
```

**这正是 `snapshot` 注释里被判定为错误的那种做法。**

把两个周期代入算一遍。假设现在**9 月 10 号**，租户同时配了两条策略：

- `REQUESTS / DAY / limit = 10_000`
- `REQUESTS / MONTH / limit = 100_000`

`periodStart(DAY)` = 9 月 10 号 00:00；`periodStart(MONTH)` = 9 月 1 号 00:00。`min()` 取**更早的**，也就是**9 月 1 号**。

于是 `currentUsage` 返回的是"**从月初到现在**的请求数"。而 `QuotaEvaluator` 拿这同一个 `current` 去判定**两条策略**：

```java
for (QuotaPolicy policy : policies) {
    long used = base.valueOf(policy.scope());
    long projected = used + inc.valueOf(policy.scope());
    boolean exceeded = projected > policy.limit();
    ...
}
```

`base` 是同一个 `QuotaUsage`，**它身上没有"周期"这个字段**（`QuotaUsage` 只有 `requests` / `tokens` / `costMicros` 三个值）。所以：

| 策略 | 应该用 | 实际用 | 后果 |
|---|---|---|---|
| `REQUESTS / MONTH` | 9 月 1 日起累计 | 9 月 1 日起累计 ✓ | 正确 |
| `REQUESTS / DAY` | **今天**起累计 | **9 月 1 日起累计** ✗ | **被月累计污染** |

**具体症状**：到了 9 月 10 号，本月累计 9,800 次。今天实际只调了 300 次（日额度 10,000 用掉 3%）——但系统看到的"今日已用"是 9,800，**再加 201 次就会触发日额度拒绝**。

也就是说：**日额度在月初几天会很宽松、在月末会提前打穿**，而且**拦住的理由是错的**（用户看到的提示是"日额度超限"，实际是月累计撞到了日限额）。这个 bug 会让"日额度"这个功能在月初几乎失效、在月末变成"月额度的一个更早触发版本"。

**更值得记的是注释本身的错误：** `snapshot` 的注释说"月额度就会被日额度的数据污染"——**方向说反了**。取"最早起点"（= 月起点）时，**是日额度被月数据污染**（日策略看到了一个更大的数）。注释把因果颠倒了。

**这带来一个非常有代表性的读码教训：注释能告诉你"作者知道这件事"，但不能告诉你"作者做对了"。** `snapshot` 的注释证明了作者**确实意识到**周期混用是错的，但下一个方法就犯了同一个错误——**"知道"和"做到"之间隔着一个方法。**

### 2.10 单位经济：一次审查的毛利怎么算

**成本计量不是财务的事，它是产品定价的输入。** 一次审查的成本由哪些项组成、每一项的敏感度如何，直接决定"砍成本该砍哪里"。

<img class="mermaid-svg" src="/zh/book-assets/diag-0171.svg" alt="成本计量不是财务的事，它是产品定价的输入。 一次审查的成本由哪些项组成、每一项的敏感度如何，直接决定&quot;砍成本该砍哪里&quot;。" />

> **图 38-4**　一次审查的毛利分解：一个收入项、一个两叉的成本项。**这张图要给出的新结论是：毛利的敏感度最高的量不是单价，而是"同一份输入被复制了几份"。** 单价是市场给的、你谈不动的（而且谈价一次只降几个点）；**输入的复制份数由你的架构决定**（第 17 讲那张"三段成本"的图算的就是它），改一次可以变化几倍。

**成本项的形态可以从计价公式逐字读出来**：`PricingEngine.price()` 是两次 `roundDiv` 相加——

```java
        long in = roundDiv(usage.promptTokens() * rule.inputMicrosPer1k(), 1_000L);
        long out = roundDiv(usage.completionTokens() * rule.outputMicrosPer1k(), 1_000L);
```

`token-factory-core/src/main/java/io/tokenfactory/core/metering/PricingEngine.java:41-42`

**两项都是"token 数 × 单价"的乘积，所以成本对这两个因子的敏感度是乘积式的**：token 数翻倍和单价翻倍等价。**但这两件事的可操作度完全不同**——单价的谈判空间是个位数百分比，而"输入被复制几份"是你自己代码里的一个循环边界。

**顺带一个能机械算出来的精度量**：

```java
    private static long roundDiv(long numerator, long denominator) {
        return (numerator + denominator / 2) / denominator;
    }
```

`token-factory-core/src/main/java/io/tokenfactory/core/metering/PricingEngine.java:61-63`

`roundDiv(n, 1000)` 的偏差满足 `|偏差| ≤ 0.5` 微元（因为 `+500` 是"四舍五入"的整数写法：`n = 1000k + 500` 时偏差取到 `+0.5`，其余情况严格小于 0.5）。一次调用触发两次 `roundDiv`，所以**单次调用的舍入偏差 ≤ 1 微元 = 1e-6 元**（复算：`Money.java:38` 的换算系数是 `1_000_000`，1 元 = 1,000,000 微元）。

> **推演**：若平台每天 100 万次调用，则单日累计舍入偏差的**上界** = `1 微元 × 1,000,000 = 1,000,000 微元 = 1` 元（假设：每日 100 万次调用、每次调用各触发一次输入项与输出项 `roundDiv`、偏差取上界 1 微元；基座值 `roundDiv` 的实现见 `token-factory-core/src/main/java/io/tokenfactory/core/metering/PricingEngine.java:61-63`，1 元 = 1,000,000 微元见 `Money.java:38` 的换算系数）。**注意这是上界而不是期望值**——整数方案的价值正在这里：**误差有界且可算**；而 `double` 方案连"上界是多少"都答不出来（本讲 §一 里"几十万条记录漂移 0.03 元"只是一个抽样观测，不是界）。

三个基座放在一起，"单位经济"这件事的重要性差别很大：

| 维度 | A：`code-review-agent`（团队内部工具） | B：千万 DAU 的多租户 SaaS 平台 | 由此分叉的设计决策 |
|---|---|---|---|
| 成本的性质 | 成本中心：花多花少只影响预算 | 毛利的一部分：直接影响单位经济 | A 只需要"账不丢"，B 还需要"账能算毛利" |
| 谁看这张表 | 研发自己 | 定价、销售、财务 | B 的账表要能被非研发的人读懂（口径要写清） |
| 单价的来源 | 谈判结果，写进配置 | 每租户可能有议价档位 | A 一份价目表够用；B 需要"价目表 × 租户"两个维度 |
| 对"按历史价目重算"的要求 | 低（内部不必重算） | 高（客户会质疑账单） | B 必须让价目在时间上可复现（图 38-3 的那个前提） |

### 2.11 搬到你自己系统：成本计量的验收

**"账对不对"可以拆成几个可数的量。** 先数本项目的口径：

| 项 | 值 | 复算方式 |
|---|---|---|
| `Money` 的组件数 | **2** | `Money.java:13` 的 `long micros, String currency` |
| 一次调用的计价公式项数 | **2**（输入项 + 输出项） | `PricingEngine.java:41-42` 两次 `roundDiv` |
| 单次调用的舍入偏差上界 | **1 微元**（= 1e-6 元） | 两次 `roundDiv` 各 ≤ 0.5 微元（`PricingEngine.java:61-63`） |
| 计价规则的 TTL | **30 秒** | `PricingService.java:21` 的 `TTL_MILLIS = 30_000L` |
| 价格的"理论最大重载次数" | **2 880 次/实例/天** | 复算：`86400 / 30 = 2880`（`PricingService.java:21`） |
| 价目表的版本列数 | **0 个可被消费的版本列** | `tf_price_rule` 有 7 列（`V1__init.sql:66-74`），其中 `effective_from` 在 `toCoreRule()` 里被丢弃 |
| LiteLLM 价目表的条目数 | **4 378** | 复算：`json.load(...)` 的顶层键数（`_research/litellm/model_prices_and_context_window.json`） |

**"2 880 次重载"和"价目表一天变不了几次"合起来说明缓存是对的**（讲稿 §2.4 的取舍成立）：2880 次里 2879 次读到的是同一份数据，**代价只是 2880 次带索引的小查询**。真正值得盯的不是这个数，而是 **"价格变更能不能在下一次重载时生效、以及生效之后旧账能不能重算"**——后者是图 38-3 那个缺口。

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| LiteLLM 的价目表跟代码一起走版本（`model_prices_and_context_window.json:889`，4378 条） | 你的价目表版本在哪？是提交 SHA，还是一个没人读的时间列？ |
| LiteLLM 的用量事件用 `float` 存钱（`spend_logs.py:22`） | 你的钱会被累加吗？不累加，`float` 可用；要累加，就必须整数最小单位。 |
| 本项目用 `long` 微元 + 两次 `roundDiv`（`PricingEngine.java:41-42`） | 你的单次计算有没有"四舍五入"？偏差上界算过没有？ |
| 本项目 `effective_from` 无消费方（`V1__init.sql:73`） | 你的表里有"生效时间"列吗？它有没有一个真正读它的人？ |
| 本项目改价走 `insert` + `delete`（`PriceRepository.java:32-42`） | 改价之后，上个月的账还能按上个月的价目重算吗？ |
| 本项目缓存 30 秒（`PricingService.java:21`） | 你的价目缓存 TTL 是多少？它是"及时生效"和"查询压力"之间的哪个点？ |

**搬到你自己系统**，五步：

1. **把"一次调用的计价公式"抄出来**，标出每一项是"token 数 × 单价"还是别的形态。**乘积形态意味着两个因子等价敏感**——然后问"这两个因子我能动哪一个"。
2. **算出单次计算的舍入偏差上界**。`(n + d/2) / d` 这类写法的上界是 `0.5` 个最小单位，乘上"每天调用次数"就是日累计上界。**算不出上界，说明你的金额表示有问题**（`float` 就属于算不出上界的那一类）。
3. **检查你的价目表有没有"只追加不修改"的写入路径**。判据很硬：**能不能按任意历史时刻的价目把当时的用量重算一遍？** 不能，就不要声称"账单可对账"。
4. **把价目表的版本口径写成一行**：是"提交 SHA"还是"生效时间列"。**如果选了生效时间列，就必须有一个读它的地方**——本项目这一列正是没有消费方。
5. **给"计价规则缺失"配一个可聚合的指标**，而不是只留一行 `WARN`（讲稿 §2.3 与 §2.4 已经分别指出这条日志在谁那里、以及它可能被绕过的路径）。

**判据**：**成本计量成熟的标志不是"能算出金额"，而是"能按任意历史时刻的价目重算出当时的金额"，并且"单次计算的舍入偏差有确定的上界"。** 前者要求价目在时间上可复现，后者要求金额用整数最小单位——**两条都是结构性的，都不能靠"事后补对账脚本"补上。**

## 三、避坑清单

- [ ] **钱用整数最小单位（`long` micros），不用 `double`，也不用每次都 `new BigDecimal`。** 只在展示层换算。
- [ ] **展示层方法的取值域假设必须显式化。** `Money.amount()` 假定 `micros ≥ 0`——将来加 `minus()` 时它会静默丢符号。
- [ ] **`glob` / 用户输入进正则必须逐字符转义元字符。** 漏一个 `.` 就是一类静默错配。
- [ ] **"宁可少算也不猜价格"要贯彻到代码里**：缺规则返回 0 + **必须有一条可被监控的告警**（不只是日志）。同时要问："这条日志在谁那里？有没有别的调用路径绕过它？"
- [ ] **注释里说"我做了什么"要能对上代码。** `PricingEngine` 类注释说"并在日志告警"，但它没有 Logger——**这种注释会直接误导故障排查的方向**。
- [ ] **并列匹配必须有显式决胜条件。** 依赖 `Stream.max` 的"保留先到的" + 数据库无序返回 = 行为不确定。
- [ ] **双检锁的字段写序要加注释钉住。** "先写 engine 再写 timestamp"是正确性的前提，不能靠后人自觉。
- [ ] **计量失败可以吞，但必须可被聚合监控。** 只有 ERROR 日志而没有指标 = 丢账靠 grep。
- [ ] **凡"被拒绝的请求"都要能被计数。** 判断标准："如果所有请求都被拒，监控上会显示什么？"如果答案是"调用量下降了"，那你正在把攻击信号读成健康信号。
- [ ] **额度/限流类判定：基线数据必须与策略同维度。** 一条策略带 `period`，基线却不带 `period`，就一定会错。
- [ ] **注释能证明作者"知道"，不能证明作者"做对"。** 读老代码时，注释是线索，代码是事实。
- [ ] **别把"能算出金额"当成成本计量做完了。** 真正的判据是"能不能按任意历史时刻的价目重算出当时的金额"——本项目有 `effective_from` 列，却没有一个读它的地方，改价走"删旧行 + 插新行"，于是上个月的价目永久不可复现。（§2.9）
- [ ] **别在"会不会被累加"这件事上偷懒。** LiteLLM 的用量事件用 `float` 存钱（`spend_logs.py:22`）是可行的，因为它逐条落库不跨记录求和；而一旦你的用途是"把几十万条加起来和发票对"，就必须换成整数最小单位。**判据是"你的钱会不会被累加"，不是"哪个更专业"。**（§2.9）
- [ ] **别让单次计算的舍入偏差成为一个"说不清"的量。** 本项目的 `roundDiv(n, d) = (n + d/2) / d` 给出 `|偏差| ≤ 0.5` 个最小单位、两项合计 ≤ 1 微元——**误差有界且可算**；`float` 方案连上界都答不出来。（§2.10）

> **目标**：亲手复现"日额度被月累计污染"和"零元账单"，并在你的项目里补上"拒绝也要计数"。

**预期结果**：第 11 次开始出现 **429**——**但日额度实际只用了 10 次、月额度只用了 10 次。**

**关键对照**：把第 11 次的响应 message 拿出来读：

```bash

  -H 'Content-Type: application/json' \
  -d '{"model":"default","messages":[{"role":"user","content":"hi"}]}'
```

`QuotaEvaluator.describe()` 生成的 message 形如 `REQUESTS/DAY 已用 N，计入本次为 N+1，上限 10 次：超限已拒绝`。**看那个 N**——如果它等于"本月累计"而不是"今日累计"，你就亲手复现了这个 bug。

再调 `/v1/usage/quota`（走 `snapshot()`，**按周期分组**）对照：

```bash

```

**关键对照**：**同一个租户、同一个时刻，`/v1/usage/quota` 的 `used` 和拒绝消息里的 `used` 不是同一个数**——因为一个是按周期算的（对），一个是按最早起点算的（错）。**这个不一致本身就是最好的证据。**

**步骤 4：给你的项目加"拒绝计数"**

```bash
# 找出所有"提前 return / throw"的拦截点
grep -rn "throw new .*Exception" --include=*.java . | grep -iv "test"
```

**预期结果**：列出所有"请求没走到业务逻辑就结束"的地方。**逐个问一句："这次拦截被计数了吗？"**

对每一处"没有"的，补一条计量（或者在拦截点累加一个计数器）：

```java
// 思路：让"被拦住"成为一个可查询的事实
metrics.counter("gateway.rejected",
```

## 本讲小结

1. **`long` 微元是唯一同时满足"精确"与"廉价"的金额表示。** `double` 会漂移，`BigDecimal` 每次运算都要分配，且精度要人为指定。
2. **"宁可少算也不猜价格"**：漏配规则返回 0 是可修正的错误，猜出来的价格是不可发现且不可修正的错误。
3. **`PricingEngine` 的类注释说"并在日志告警"，但它没有 Logger。** 真话写在了 `match()` 和 `PricingService` 里——同一文件里两处注释一对一错。
4. **`Money.amount()` 会丢负号**（`-500000` → `"0.500000"`）。当前不可达（没有 `minus`），但加退款功能就会生效。
5. **"调用量涨了但用量没涨"是最有价值的异常信号——而额度拒绝恰好不落库。** 被拦的流量在监控里表现为"调用量下降"。
6. **`QuotaService` 的查询路径按周期分组（对）、拦截路径取最早起点（错）**，而注释把因果方向也写反了。`QuotaUsage` 身上没有 `period`，这是不可能对齐的根因。
7. **注释能证明作者"知道这件事"，不能证明作者"做对了"。** `snapshot` 的注释与 `evaluate` 的实现，就是这句话的现场证据。

下一讲我们把账单的另一半补上：**当网关自己挂了、业务方直连上游时，这笔钱怎么回到账上**——以及一个"补报回来了，但金额是 0"的真实缺陷。
