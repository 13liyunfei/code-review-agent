## 二、原理

### 2.1 配置不是一个平面，是三个

先把「配置」这件事拆开。任何一条配置，先要回答**它属于哪一类**——因为分类决定了它什么时候被读、改一次要动多少台机器。

**第二类：运行期配置。** 特征值是**存在数据库里**，每次用的时候读（或读缓存）。本项目的自定义 Agent / 技能 / 知识 / 经验都属这一类。它的代价不是重启，是**并发写**——两个管理员同时改同一个 Agent，谁赢？这一类的问题我们在 2.3 讲。

**第三类：实验开关。** 它和运行期配置的区别不在技术实现，而在**生命周期**：它生来就是为了被删掉的。一个开关从「新建」到「全量」再到「删掉」，是一个完整的生命周期；停在「全量」不删，它就从"开关"退化成"永久分支"——**两版行为都要长期维护**。

**到这里可以得到本讲的第一条判据：**

> **★ 判据：给每一条配置标注它属于哪一类，标注的判据是"改它一次，需要重启多少台机器"。答不出来的配置，就是还没被治理的配置。**

### 2.2 传播才是难点：一个频道、一个版本号、一套兜底

假设我们已经接受了"有些配置必须热更新"。**接下来最容易做错的地方不是"怎么读新值"，而是"怎么让每一台都读到新值"。**

朴素做法是：改完配置，等一个固定的周期（比如 30 秒），所有实例去拉一次。这个做法的问题不是慢，是**它把延迟当成了保证**——你以为 30 秒后一定生效，实际上只要有一次拉取失败、实例正在重启、或者网络抖动，那台机器就**永远停在旧配置上**，而且没有任何机制会再提醒它一次。

工业界的做法在 `litellm` 的配置同步模块里写得很完整。先看四个常量：

```text
CONFIG_SYNC_CHANNEL: Final = "litellm_proxy.config_change"
CONFIG_SYNC_DEBOUNCE_SECONDS: Final = 1.0
CONFIG_SYNC_JITTER_MAX_SECONDS: Final = 5.0
CONFIG_SYNC_MIN_RESYNC_INTERVAL_SECONDS: Final = 10.0
_POLL_TIMEOUT_SECONDS: Final = 1.0
_BACKOFF_INITIAL_SECONDS: Final = 5.0
_BACKOFF_MAX_SECONDS: Final = 60.0
```

`litellm/litellm/proxy/common_utils/config_sync_pubsub.py:30-36`

四个数各解决一个问题，**每一个都不是随手写的**：

- **一个频道**（`CONFIG_SYNC_CHANNEL`）：所有配置变更共用一个广播频道，**不为每张表分别订阅**。这让"有哪些东西会被同步"变成一个**可枚举的清单**，而不是散在各处的订阅关系。
- **去抖 1 秒**（`DEBOUNCE`）：一次批量改配置会连发多个写操作。没有去抖，200 台实例会被触发 20 轮重载；有去抖，收成一轮。
- **抖动 5 秒**（`JITTER`）：光去抖还不够——去抖让**所有实例在同一个时刻**开始重载，正好形成惊群。抖动把这 200 台摊到 5 秒里。
- **最小重同步间隔 10 秒**（`MIN_RESYNC_INTERVAL`）：**这是最关键的一个数**。它承认了一件事——**推（pub/sub）会丢**。订阅者掉线期间发布的消息就永久消失了；只做推的系统里，那台机器会一直停在旧配置上，而**这个差异永远不会自己消失**。

于是架构变成「推 + 拉」两条腿：

<img class="mermaid-svg" src="/zh/book-assets/diag-0196.svg" alt="于是架构变成「推 + 拉」两条腿：" />

> **图 43-2**　本讲地图之三：推 + 拉，缺一不可。推负责快，拉负责对——**因为推会丢，而丢了以后差异不会自己消失**。判定"这台该不该重载"的唯一依据是一个版本号，不是时间戳。

那么，200 台机器怎么知道"我该重载了"？工业界的答案是**一个单调递增的版本号**，而不是时间戳。这份实现把理由写在模块 docstring 里，逐字如下：

```text
Field ownership is split by writer so concurrent writers never overwrite each other:
the schedule endpoints own the ``param_value`` JSON (``interval_hours``), while the
reload job and the manual reload endpoints own the dedicated ``last_run_at`` /
``reload_revision`` columns. ``last_run_at`` lives in the row rather than process memory
so the Admin UI still reports the last execution after a restart and across pods.
``reload_revision`` is a monotonic counter a manual reload increments; each pod records
the revision it last applied and reloads whenever the row's differs, so a request reaches
every pod exactly once without any pod clearing it and without comparing clocks. A booting
pod starts at revision 0 rather than adopting the published one, because it cannot know
whether that request predates the prices it fetched at import. Interval reloads stay
per-pod, driven by when that pod's own copy of the data was loaded.
```

`litellm/litellm/proxy/common_utils/periodic_reload_schedule.py:5-15`

这一段里的每一句都可以单独当一条设计原则。挑四句：

**①「字段所有权按写入方切分」（`Field ownership is split by writer`）。** 三个不同的写入方（调度端点、重载任务、手动重载端点）写**同一行**的不同列，所以它们**永远不会互相覆盖**。这比加一把锁便宜得多，也比"读-改-写"安全得多。**用字段所有权替代并发控制**，这是可以立刻搬走的一招。

**②「每台恰好吃到一次，不依赖任何实例去清标记，也不依赖时钟比较」（`every pod exactly once without any pod clearing it and without comparing clocks`）。** 这句话解决的是分布式里的经典难题。用时间戳当版本的方案必须处理时钟回拨；用"标记已消费"的方案必须处理"谁来清标记、清了别人会不会重复消费"。**换成单调递增版本号 + 每台自己记住已应用版本，两个问题一起消失。**

**③判定逻辑就一行：**

```text

    it has not served. A pod starts at revision 0, so it serves any request published before
    it booted; that costs one redundant fetch per boot and is what keeps a request from being
    marked applied against data fetched before it. Interval reloads compare against this pod's
    own data, and a schedule that has never run anywhere fires immediately rather than one
    interval later
    """
    if schedule.reload_revision != pod_applied_revision:
```

`litellm/litellm/proxy/common_utils/periodic_reload_schedule.py:146-153`

注意它**主动接受一次冗余**：刚启动的实例从 0 开始，会把启动前的版本当成"没应用过"再拉一次。**"启动时多拉一次"换"绝不会把旧数据当成新数据标记为已应用"**——判据句写得很直白：`that costs one redundant fetch per boot`。这是"宁可多做一次也不能漏"的典型取舍。

**④版本号必须由服务端原子自增，不能客户端读-改-写：**

`{"increment": 1}` 是**数据库层**的原子自增。如果改成"读出来 +1 再写回去"，两个并发请求会拿到同一个版本号——**那些中间那台实例就会漏掉一次变更**。

**⑤还有一个反直觉的细节：删配置的时候，行不能删。**

```text
    """Admin-owned write: drops the schedule but keeps the row, because the revision counter
    identifies a request rather than ordering one and so can never reuse a number. Deleting
    the row restarts it, and a reissued revision matches what pods already applied, so their
```

理由逐字：**版本号"标识一次请求"，不是"给请求排序"，所以它永远不能复用。** 一旦把行删掉、版本号从头开始，新发出来的版本号就会**和实例已经应用过的版本号撞上**——于是那次手动重载被**静默跳过**。

**这正是"版本号 vs 时间戳"的分水岭**：时间戳可以删了重来（时间在往前走），单调计数器**不能回退**。

**本项目对照。** 本项目在这个问题上是什么状态？——**没有传播层，因为不需要传播**：配置在进程启动时读一次，不存在"一台用新值、一台用旧值"的两版并存问题。这个选择在中低 QPS、发布频率低的场景下是**合理**的：它用"改配置要重启"这一个代价，换掉了整个传播层的复杂度。

**但这个选择有一个必须承认的代价：滚动发布期间，新旧两版配置并存。** 这正好是本讲的下一节。

### 2.3 灰度：不是"发一半流量"，是"谁看见哪一版"

「灰度」这个词在讨论里经常被简化成"切 1% 流量"。这个理解在**无状态、无配置差异**的服务里勉强成立，但一旦服务带着**启动期配置**，灰度就变成了另一个问题：

> **滚动发布的 30 秒里，集群里同时存在两版配置。谁会被谁服务？**

本项目的优雅停机超时是 30 秒：

```text
# ===== 优雅停机超时（与 server.shutdown=graceful 配合）=====
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

`application.yml:300-303`

**这 30 秒就是"两版并存窗口"的宽度。** 在这个窗口里：

- 老实例还在跑，用的是老配置；
- 新实例已经起来，用的是新配置；
- 负载均衡器**不知道**谁是谁。

所以如果你的配置里有一个**跨实例必须一致**的参数（比如"在飞上限 = 20"——这是一个**集群级**的语义），滚动发布期间真实的在飞上限可能是 `20 + 20 = 40`。**改小一个限流参数，在发布窗口里反而放大了流量。**

这一步不需要引入配置中心就能解决，办法是**给灰度写清维度**。三种维度，各有各的适用面：

| 灰度维度 | 怎么切 | 什么时候必须用它 |
|---|---|---|
| **按租户** | 同一租户的请求恒定落到同一版配置 | 配置里有"租户级语义"（配额、模型白名单、审查强度） |
| **按流量比例** | 随机切 1% 请求 | 纯性能类变更（超时、线程数），且**不能有跨请求聚合语义** |
| **按模型 / 按通道** | 按下游供应商切 | 换模型、换网关、换供应商 key |

**判据是"这条配置的语义是不是跨实例的"**：跨实例的（集群总量、共享配额、共享缓存），只能按租户或按通道切，**不能按流量比例切**——按比例切会让同一份共享资源被两版逻辑各算一遍。

本项目在这一点上其实已经有一个正向例子：**出口模式（egress）是按"外部依赖"切的，不是全局一刀。**

```text
    public static class Endpoint {
        /** 出口模式，默认直连（生产形态）。 */
        private EgressMode mode = EgressMode.DIRECT;
```

`EgressProperties.java:42-44`

`llm` 与 `rerank` 各是一个独立的 `Endpoint`，各配各的 `mode`。**这就是"按通道切"的最小形态**：换某一个供应商的出口方式，不影响另一个。

### 2.4 实验开关的生命周期：它生来就是为了被删掉

实验开关（feature flag）是配置里最容易被低估的一类，因为它的**成本不在创建时，而在忘记清理时**。

> **图 43-3**　本讲地图之四：开关的四个阶段，第三步"全量"之后**必须**走第四步"清理"。停在"全量"的开关不再是开关，它变成了一条永久分支：两条代码路径都要测、都要维护、都不敢删。

**为什么"全量之后不清理"会变成永久分支？** 因为一个全量的开关，在代码里仍然是 `if (flag) { 新逻辑 } else { 旧逻辑 }`。你已经不会再切回旧逻辑了，但**旧逻辑还在那里**——它要过编译、过测试、过静态扫描，还要在每次重构时被人问一句"这段还能删吗"。

**给开关加"过期时间"是能机械执行的一招。** 第 25 讲我们已经见过同一个技巧的另一个用法——LiteLLM 的「临时提额」带了 `temp_budget_expiry`，让"临时"成为代码能判的判据。开关同理：**新建开关时同时写一个清理日期**，日期一到就报警。这不是流程约束，是代码判据。

**本项目在这一类上是空白的。** 本项目的"开关"全部是启动期布尔值，比如：

```text
    public ToolGate(@Value("${review.tools.deferred-enabled:false}") boolean deferredEnabled,
                    @Value("${review.tools.code-mode-enabled:false}") boolean codeModeEnabled) {
```

`ToolGate.java:43-44`

`deferred-enabled` / `code-mode-enabled` 这两个名字读起来很像实验开关，但它们**没有生命周期管理**：没有创建日期、没有清理日期、没有"现在处于哪个阶段"的记录。它们和线程数一样，是一个启动期布尔。

**这不是说本项目做错了**——它在这个阶段不需要实验开关的生命周期管理。但**一旦要引入一个真正的实验开关，就必须同时引入它的生命周期字段**，否则第一个开关就会变成永久分支。

### 2.5 回滚代价：三类变更根本不在一档

前面三节讲的是"怎么让配置生效"。这一节讲反面：**改错了怎么退回来。**

先给结论：**配置变更的回滚代价差三个数量级**，而它们的区别**不在于配置写在哪，而在于"有没有副作用留在系统里"。**

| 变更类型 | 例子（本项目） | 回滚动作 | 回滚代价 |
|---|---|---|---|
| **纯读参数** | `review.profile`、`review.agent.timeout-ms` | 改回去、重启 | 一次发布 |
| **带缓存 / 带连接** | `pgvector.vector-dim`、连接池大小 | 改回去 + **清掉旧结构** | 一次发布 + 一次数据操作 |
| **结构变更** | 加列、重建向量索引、换分词器 | **没有反向操作** | **不可逆** |

前两类的回滚是"再改一次"。第三类不是——本项目里有一个具体的例子：**迁移登记表**。

```text
                CREATE TABLE IF NOT EXISTS rag_schema_migration (
                    name varchar(128) PRIMARY KEY,
                    applied_at timestamptz NOT NULL DEFAULT now()
                )
```

`PgVectorMemoryStore.java:249-254`

它的写入方式是：

```text
                    "INSERT INTO rag_schema_migration (name) VALUES (?) ON CONFLICT DO NOTHING")) {
```

`PgVectorMemoryStore.java:291`

**`ON CONFLICT DO NOTHING` ——这个朴素写法的含义是：迁移只有"做过"和"没做过"两种状态，没有"撤销"。** 一次迁移一旦登记（比如"已按新分词器重建 `search_vector`"），系统就**永远不会再执行它第二次**，也**没有任何代码路径会把它退回去**。全库 8 处 `DELETE FROM` 里，没有任何一处指向这张表（复算：检索所有 `DELETE FROM` 的表名）。

迁移本身还带一个自我保护的上限：

```text
    private static final int MAX_MIGRATE_ROWS = 100_000;
```

`PgVectorMemoryStore.java:65`

超过 10 万行就**放弃迁移并提示手工分批**（`:276-280` 的判据）。这是"迁移不能被一次无界操作拖死"的体现，但它同时也说明：**这类操作是"人工介入才能完成"的重动作，回滚它同样需要人工。**

**所以回滚预案的关键不是"能不能退"，而是"退的时候有没有一个反向脚本"。** 有一条机械可查的判据：

> **★ 判据：任何带 `UPDATE` / `ALTER` / 重建索引的变更，发布单里必须同时写上"反向语句"。写不出反向语句的变更，就不是一个可以回滚的变更——它必须单独走一次评审，并且在这个变更的整个生命周期里保持"可重建"状态（比如：旧数据先不动，新结构并行建）。**

**灰度与回滚的关系**也在这里闭合了：**灰度不是为了"少出事故"，而是为了"出事故时只影响一部分、且能立刻退回"。** 如果一次变更根本不可回滚，那么灰度就失去了大部分意义——你只是把不可逆的操作分成了几批执行而已。

### 2.6 搬到你自己系统：先把配置盘出来，再谈热更新

在讨论"要不要上配置中心"之前，先把**你自己系统里的配置**按类盘一遍。这一步不需要任何基础设施。

| 维度 | A：`code-review-agent` | B：千万 DAU 的多租户 SaaS 平台（推演） | 由此分叉的设计决策 |
|---|---|---|---|
| **配置项规模** | `application.yml` 95 个叶子项，`review.*` 51 个（实测） | **推演**：跨 3 个环境 × 每种部署形态一份，合并后易到 **10³ 量级**（假设：单体拆成 8 个服务，每服务 100–200 项；基座值见 `application.yml`） | A 可以"重启改配置"，B 必须"热更新 + 分环境" |
| **实例数** | 单实例为主 | **推演**：单集群 200 台（假设：按 8 个服务 × 25 副本估；**推演**，无基座值） | 实例数一过百，"推"必然丢，"拉兜底"从可选项变成必需项 |
| **变更频率** | 低（跟版本走） | **推演**：每天数十次（运营活动、限额调整、开关） | A 的发布窗口 = 版本窗口；B 的发布窗口必须与配置变更**解耦** |
| **谁有权限改** | 部署者 | 运营 + 客服 + SRE 多角色 | B 必须把"改配置"做成**带审计的管理端点**，而不是"改文件" |
| **不一致的后果** | 一次发布的事故 | 同一租户在两个副本上被两版逻辑服务 | B 的灰度必须**按租户**切，不能按流量比例切 |

**注意 B 基座的所有数字都是推演值**——它们不是任何真实系统的实测，只是为了让"实例数从 1 变到 200"这条推理链有具体形状。**关键的一列是最后一列：分叉点。**

**落地步骤（4 步，全部可在当前系统上做完）：**

1. **盘配置**：把 `application.yml` 里每一个叶子项写进一张表，字段是「键名 / 当前值 / 属于哪一类（启动期 / 运行期 / 开关）/ 改它要不要重启」。这份表就是配置治理的起点。
2. **标出"迟早要热更新"的那几个**：判据是「运营会不会在事故处理中想改它」。本项目里 `max-inflight-*`、`diff-char-budget`、`min-similarity` 都属于这一类。
3. **给这几条选一条通路**：要么引入配置中心（推 + 拉 + 版本号），要么接受"重启"但**把这件事写进文档并且要求重启能快**（蓝绿 / 滚动窗口足够短）。**两条都是合法选择，唯一不合法的是"注释说能热切换、实现不能"。**
4. **给开关加到期字段**：哪怕不上配置中心，也给实验开关加一个 `expires-at`，让"忘了清理"这件事变成报警而不是习惯问题。

> **★ 判据：改造完成的标志不是"配置能热更新了"，而是"有人问『这个参数属于哪一类』时，答案能在一张表里查到，且查到的答案和实现一致"。**

## 三、避坑清单

- [ ] **注释里的"可热切换"必须能在代码里找到落点**——找不到就删掉这句话。本项目 `ReviewProfile.java:9` 的「可热切换」与 `CompletableFutureCoordinator.java:87` 的 `@Value` 是反例。
- [ ] **枚举"启动期配置"的总量**，并让它是一个可复算的数（本项目 69 处 `@Value` / 5 个 `@ConfigurationProperties` / 0 处 `@RefreshScope`）。
- [ ] **别把"用了 `@ConfigurationProperties`"当成"配置已治理"**——它只解决类型安全，不改变"启动期"这个属性。
- [ ] **非法配置值必须至少打一条 WARN**。静默回退默认值会让"配置生效了但不是你写的那行"这种事故无法从日志里发现。
- [ ] **启动时对配置值做一次启动期校验**（枚举类可以 `Enum.valueOf` 一次就抛），把拼写错误挡在启动阶段。
- [ ] **同一个系统里的两套配置通路（yml / 库）必须有明确的分工说明**，并写进 README。否则新同学会问"改这个参数是改文件还是调端点"，而答案只能靠读代码得到。
- [ ] **集群级语义的配置项（在飞上限、共享配额、共享缓存容量）在滚动发布窗口内会被"放大"**——30 秒的优雅停机窗口里，两版生效值同时存在。改小限流值之前先算这个窗口。
- [ ] **共享语义的配置不能按流量比例灰度**，只能按租户 / 按通道切。
- [ ] **"推"一定会丢**。任何只做推的配置同步，都会出现"某一台永远停在旧值"，且**这个差异不会自己消失**。
- [ ] **必须有独立的"拉"兜底**，且它的周期要独立于推的成功与否（litellm 用 `CONFIG_SYNC_MIN_RESYNC_INTERVAL_SECONDS = 10.0`）。
- [ ] **批量改配置要去抖**。不去抖会让一次批量改动在实例侧放大成 N 轮重载。
- [ ] **去抖之后必须加抖动**。去抖会让所有实例在同一刻重载，正好形成惊群。
- [ ] **投递语义用单调递增版本号，不要用时间戳**——时间戳要处理时钟回拨，"标记已消费"要处理"谁来清标记"。
- [ ] **版本号必须由服务端原子自增**（数据库的 `increment`），不能客户端"读出来 +1 再写回去"。
- [ ] **版本号永远不能复用**：删除配置时保留行。把行删掉、版本号从头开始，会让新版本号和实例已应用过的版本号撞上，那次变更被静默跳过。
- [ ] **不同写入方写同一行的不同列**，用字段所有权替代加锁。这比"读-改-写"安全，也比加锁便宜。
- [ ] **接受"启动时多拉一次"的冗余**，换取"绝不把启动前的旧数据标记为已应用"。冗余是显式的、可数的；错误标记是静默的。
- [ ] **实验开关必须带清理日期**。停在"全量"的开关就是一条永久分支，两条代码路径都要长期维护。
- [ ] **迁移必须有单次操作上限**（本项目 `MAX_MIGRATE_ROWS = 100_000`），超限就停下来要求人工分批——一次无界迁移的回滚同样是人工的。
- [ ] **任何 `UPDATE` / `ALTER` / 重建索引的变更，发布单里必须有反向语句**。写不出反向语句的变更不是可回滚变更。
- [ ] **迁移登记表只增不减是有意设计，不是缺陷**——但要清楚它意味着"这次变更永远退不回去"，所以它必须在发布前单独评审。
- [ ] **回滚演练要真的做一次**。"我们设计上能回滚"和"我们上周真的回滚过一次、耗时 4 分钟"，是两种完全不同的信心。

## 本讲小结

1. **「这条配置能不能热更新」不是一个布尔属性**，而是三件事的组合：它属于哪一类（什么时候被读）、它怎么到达每一台实例（会不会漏）、改错了怎么退（事故能压多久）。
2. **配置分三类，代价完全不同**：启动期（代价 = 重启）、运行期（代价 = 并发写）、实验开关（代价 = 不清理就永远清理不掉）。
3. **分类错了的后果是"静默不生效"**——没有报错，只有"怎么改了没用"。本项目 `ReviewProfile` 的注释与实现正是这个落差。
4. **`@ConfigurationProperties` 不改变"启动期"这个属性**。它把散落的 `@Value` 收成类型安全对象，但仍然是启动时读一次。
5. **非法值静默回退默认档是一种高危写法**。它让"配置生效了但不是你写的那行"变成不可观测的事故。至少打 WARN，最好启动期校验。
6. **传播层的难点不是"读新值"，而是"每台都读到"。** 工业界的答案是：一个频道 + 去抖 + 抖动 + **拉兜底** + 单调递增版本号。
7. **"推"一定会丢，而丢了的差异不会自己消失。** 只做推的系统必然出现"某台永远停在旧配置"，所以拉兜底不是优化，是正确性要求。
8. **投递语义用版本号而不是时间戳**：`每个实例记住自己已应用的版本`，于是"每台恰好一次"既不需要清标记，也不需要比较时钟。
9. **版本号永远不能复用。** 删配置时保留行——行一删、版本号从头开始，新版本号就会和实例已应用过的撞上，那次变更被静默跳过。
10. **回滚代价差三个数量级**：纯读参数（一次发布）、带缓存/连接（一次发布 + 一次数据操作）、结构变更（**不可逆**）。**写不出反向语句的变更，必须单独评审。**
11. **A 基座可以"重启改配置"，B 基座必须"热更新 + 灰度"。** 分叉点不是规模，是**实例数一过百，"推"就必然丢**；一变多角色可改，就必然需要审计。
12. **改造完成的判据不是"能热更新了"，而是"有人问『这个参数属于哪一类』时，答案能在一张表里查到，且与实现一致"。** 注释说一套、实现做另一套，比完全不做配置管理更危险——因为它会让人**以为自己改了**。

下一讲我们换一个方向：**上面这些配置和日志里，有多少内容是"不该留"的**——PII 的三条落点、留存策略、删除权怎么举证。
