## 一、痛点

上线第五天，凌晨 2 点 17 分，网关整机无响应。

**最诡异的地方是：上游没挂。** 三个供应商的健康检查全部正常，供 OpenAI 兼容端点响应时间 200ms 以内。

但网关的 Tomcat 线程池已经满了，健康检查端点 `/actuator/health` 也超时了——**监控上显示的是一个"完全死掉"的服务。**

等它自己恢复（大约 40 分钟后），我去翻日志，看到了一屏这样的东西：

```
LLM 调用失败：alias=default provider=deepseek model=deepseek-chat attempt=1 decision=429 限流，等待 3600000ms（Retry-After）
LLM 调用失败：alias=default provider=deepseek model=deepseek-chat attempt=1 decision=429 限流，等待 3600000ms（Retry-After）
LLM 调用失败：alias=default provider=deepseek model=deepseek-chat attempt=1 decision=429 限流，等待 3600000ms（Retry-After）
...
```

**`3600000ms` 就是一个小时。**

那天上游做了一次限流演练，返回了 `429` 加一个 `Retry-After: 3600`。而我的代码做了最字面的事：

> **上游让我等一个小时，我就等一个小时。**

一个请求等 1 小时，Tomcat 默认 200 个线程——**200 个请求就能把整个网关睡死。** 而且因为线程都在 `sleep`，CPU 是空的、内存是稳的、上游是健康的，**所有传统的"资源告警"都不会响**。

我用一行"尊重上游建议"的代码，给自己造了一个 **DoS 攻击面**：**任何能影响上游响应头的人，都能用 200 个请求打死我的网关。**

这一讲就讲这件事，以及围绕它的四个同类问题。

## 二、原理

### 2.1 先分清三件事：限流、熔断、退避

这三个词经常被混着说，但它们是**三种不同的机制，解决的问题不同**：

| 机制 | 一句话 | 作用方向 | 谁在"保护" |
|---|---|---|---|
| **限流（Rate Limiting）** | 我**自己**最多处理多少 | 主动（前置拦截） | 保护**我自己** |
| **熔断（Circuit Breaking）** | 这个上游已知坏掉，**别再试了** | 被动（故障后短路） | 保护**我的调用方**（快速失败） |
| **退避重试（Backoff Retry）** | 这次抖动，等一下**再试一次** | 被动（失败后重试） | 保护**这次调用**（成功率） |

三者的**时间尺度**也不同：限流是"每秒/每分钟"级的常态控制；熔断是"30 秒到几分钟"的故障短路；退避重试是"几百毫秒到几秒"的单次补偿。

**先诚实交代一件事：`token-factory` 里没有 QPS 限流器。**

```bash
# 用 Grep 工具（不是 shell grep）全仓检索
Grep pattern="RateLimiter|Semaphore|TokenBucket" path=token-factory glob=*.java
# → 只命中 HttpJson.java（超时相关）与 DefaultRetryClassifier.java（注释里提到"限流"）
```

这不是疏忽，而是**优先级判断**：一个公司内部网关，QPS 上限由业务方自己的并发度决定，而"被某个业务方刷爆"在内部环境不是主要风险。**网关真正需要的是"上游抖动时不把自己拖垮"**——那是熔断和退避的活。

所以本讲的"限流"部分，讲的是**业务级配额**（`QuotaEvaluator`，第 32 讲见过它的周期污染缺陷），而 `token-factory` 的韧性主体是**熔断 + 退避重试 + 路由切换**。

**面试时这一点值得如实说**："我们没做应用级 QPS 限流，因为内部网关的容量瓶颈在上游配额而不在自己；我们做的是额度前置拦截 + 熔断 + 退避。**如果要做 QPS 限流，应该加在 AK 维度、用令牌桶，并且拒绝时要返回 429 而不是 503。**"——**知道自己没做什么、以及为什么，比声称什么都做了可信得多。**

### 2.2 熔断：为什么必须有它

`CircuitBreaker` 的类注释把这个因果关系写得很好：

```java
/**
 * 单供应商熔断器：三态机 + 半开探测，线程安全。
 *
 * <p><b>为什么网关必须有它</b>：没有熔断器时，上游整体不可用的每个请求都要等满超时
 * （默认 60s）才失败，线程池瞬间被榨干，健康的供应商也一起陪葬。熔断器让「已知坏掉」
 * 的供应商在冷却期内被零成本跳过——这是故障降级与雪崩防护的分界线。
 *
 * <p><b>与重试的关系</b>：重试解决「单次抖动」，熔断解决「持续不可用」。二者串联：
 * 重试耗尽 → 记一次失败 → 达到阈值 → 打开 → 后续请求直接跳过 → 冷却后放一个探测请求。
 */
```

**"健康的供应商也一起陪葬"是雪崩的核心机制。** 具体过程：

```
上游 A 挂了（每个请求等 60s 超时）
  → 请求线程都卡在 A 上
  → 线程池满
  → 打到健康上游 B 的请求也拿不到线程
  → B 也在用户看来"挂了"
  → 系统整体不可用（而 B 其实一直好好的）
```

**熔断器把"等待"变成"立即失败"**，于是线程周转率恢复，B 的流量不受影响。

### 2.3 三态机与半开探测

```java
public synchronized void acquire() {
    long now = nowMillis.getAsLong();
    if (state == CircuitState.OPEN) {
        long elapsed = now - openedAtMillis;
        if (elapsed < config.openDurationMillis()) {
            throw new CircuitOpenException(providerCode, config.openDurationMillis() - elapsed);
        }
        // 冷却期结束：转半开，放行有限的探测请求
        state = CircuitState.HALF_OPEN;
        halfOpenInFlight = 0;
        halfOpenSuccesses = 0;
    }
    if (state == CircuitState.HALF_OPEN && halfOpenInFlight >= config.halfOpenMaxCalls()) {
        throw new CircuitOpenException(providerCode, 0L);
    }
    if (state == CircuitState.HALF_OPEN) {
        halfOpenInFlight++;
    }
}
```

**注意 `CircuitOpenException` 携带 `remainingMillis`**：

```java
throw new CircuitOpenException(providerCode, config.openDurationMillis() - elapsed);
```

这个数字**不是给用户看的**，是给**告警**看的："熔断还有 12 秒就到期"意味着"快恢复了，别急着叫人"；"熔断刚打开"意味着"要人工介入了"。**没有剩余时间的熔断告警，运维只能靠猜。**

状态迁移规则：

```java
/** 记录一次成功：闭合熔断器并清零计数。 */
public synchronized void recordSuccess() {
    if (state == CircuitState.HALF_OPEN) {
        halfOpenInFlight = Math.max(0, halfOpenInFlight - 1);
        if (++halfOpenSuccesses >= config.halfOpenSuccessToClose()) {
            close();
        }
        return;
    }
    close();
}

/**
 * 记录一次失败：连续失败达到阈值即打开；半开状态下只要失败一次立刻重新打开。
 */
public synchronized void recordFailure() {
    long now = nowMillis.getAsLong();
    lastFailureAtMillis = now;
    if (state == CircuitState.HALF_OPEN) {
        trip(now);
        return;
    }
    if (++consecutiveFailures >= config.failureThreshold()) {
        trip(now);
    }
}
```

**"半开状态下只要失败一次立刻重新打开"是不对称的**：CLOSED 态要连续失败 N 次才打开，HALF_OPEN 态失败 1 次就重新打开。这个不对称是刻意的：

> HALF_OPEN 态放出去的是**探测请求**——我们**本来就不确定上游好了没**。探测失败说明"还没好"，那就继续等冷却，**成本只是再等 30 秒**。而 CLOSED 态下每次误判都要付出"误熔断一个健康上游"的代价，所以要 N 次才动手。

**一个"探测"哲学：不确定的地方，失败了就退回保守状态；确定的地方，要有证据才改变。**

另外注意 **`lastFailureAtMillis` 被记录下来**，并在 `AdminHealthController` 里暴露——它回答的是"这个熔断是刚发生的，还是 10 分钟前的旧状态"。

**还有一个配置项的落差：`halfOpenSuccessToClose` 不可配，被硬编码为 1。**

```java
@Bean
public CircuitBreakerConfig breakerConfig(TokenFactoryProperties properties) {
    TokenFactoryProperties.Breaker b = properties.getBreaker();
    return new CircuitBreakerConfig(b.getFailureThreshold(), b.getOpenDurationMillis(),
            b.getHalfOpenMaxCalls(), 1);
}
```

四个参数里，前三个从配置读，**第四个写死 `1`**。而 `application.yml` 里确实只配了三个：

```yaml
breaker:
  failure-threshold: 5
  open-duration-millis: 30000
  half-open-max-calls: 1
```

**结果**：你可以调"半开时放几个请求进去"，但不能调"这几个请求要成功几个才算恢复"。

这在某些场景下会难受：如果上游是**偶发 500（比如 30% 失败率）**，那么"半开放 3 个、成功 1 个即恢复"和"必须 3 个全成功"是两种完全不同的灵敏度。而现在你只能选后者——**而后者会让一个"基本恢复但偶有抖动"的上游永远卡在熔断循环里**（半开 → 3 个里挂 1 个 → 重新打开 → 30 秒后再试 → 又挂 1 个……）。

**配置项的不对称是一种隐形的设计限制。** 判据："这个参数有没有运维需要调的理由？"有，就该可配；没有，就该在注释里说明为什么写死。

### 2.4 退避：为什么必须抖动

```java
/**
 * 指数退避 + 抖动（jitter）。
 *
 * <p><b>为什么必须加抖动</b>：纯指数退避会让所有客户端在同一时刻重试，形成「重试风暴」，
 * 把刚恢复的上游再打挂一次。抖动把重试时间打散到一个区间内，是分布式系统的基本功。
 *
 * <p>公式：{@code delay = min(maxMillis, baseMillis * multiplier^(attempt-1))}，
 * 再乘以 {@code [1-jitter, 1+jitter]} 区间内的随机系数。
 */
```

**"重试风暴"的具体机制**：

```
t=0      上游抖动，1000 个请求同时失败
t=500ms  1000 个请求同时重试   ← 上游刚恢复，瞬间收到 1000 个请求
t=1500ms 2000 个请求同时重试   ← 还没缓过来，又被压垮
```

**没有抖动的重试，是一台"精确的同步攻击机"。** 加了 ±30% 抖动后，同样的 1000 个请求会散布在 `[350ms, 650ms]` 区间内——上游能逐个处理。

```java
public long nextDelayMillis(int attempt) {
    long raw = rawDelayMillis(attempt);
    if (jitterRatio <= 0.0d) {
        return raw;
    }
    double factor = 1.0d + (ThreadLocalRandom.current().nextDouble(-jitterRatio, jitterRatio));
    return Math.max(1L, Math.min(maxMillis, Math.round(raw * factor)));
}

/** 不含抖动的确定性退避值，便于断言。 */
public long rawDelayMillis(int attempt) {
    if (attempt < 1) {
        throw new IllegalArgumentException("attempt 从 1 开始，收到 " + attempt);
    }
    double raw = baseMillis * Math.pow(multiplier, attempt - 1);
    return Math.max(1L, Math.min(maxMillis, Math.round(raw)));
}
```

**`nextDelayMillis` 和 `rawDelayMillis` 的分工是"可测试性设计"的范例**：随机数让断言不可能，所以把"确定性部分"单独暴露成一个方法。测试断 `rawDelayMillis(1..3)` = `500 / 1000 / 2000`，再单独断 `nextDelayMillis` 落在 `[70%, 130%]` 区间内。**"把随机性和逻辑分开"是所有涉及随机的代码的通用解法。**

默认参数（`BackoffPolicy.exponential()`，也是 `application.yml` 的默认值）：

```java
/** 500ms 起步、2 倍递增、上限 8s、±30% 抖动。 */
public static BackoffPolicy exponential() {
    return new BackoffPolicy(500L, 2.0d, 8_000L, 0.3d);
}
```

**但这里有一个边界行为的细节值得算一遍：饱和区只有向下抖动。**

`rawDelayMillis` **先**把值截断到 `maxMillis`，**然后** `nextDelayMillis` 再乘抖动系数并**第二次**截断到 `maxMillis`：

```java
long raw = rawDelayMillis(attempt);        // 已经 ≤ maxMillis
...
return Math.max(1L, Math.min(maxMillis, Math.round(raw * factor)));   // 又截一次
```

当 `raw == maxMillis`（8 秒，即 attempt ≥ 5）时：

- `factor` 均匀落在 `[0.7, 1.3]`
- `raw × factor` **均匀落在 `[5600, 10400]`**（区间长度 4800）
- 第二次 `min(8000, ...)` 把 `[8000, 10400]`（长度 2400）**全部压到 8000**

于是**实际的取值分布是**：

| `raw × factor` 落在 | 概率 | 最终值 |
|---|---|---|
| `[5600, 8000)` | `2400 / 4800` = **50%** | 落在区间内（均匀） |
| `[8000, 10400]` | `2400 / 4800` = **50%** | **全部变成 8000** |

**这个分布有一处很要紧的性质：一半的重试时间精确地等于上限。**

抖动（jitter）存在的唯一理由是"把重试时间打散"，而在饱和区：

- **50% 的请求被压到同一个值 `8000`**——它们**完全同步**，抖动的目的落空；
- 另外 50% 均匀散在 `[5600, 8000)`。

也就是说，**抖动在饱和区退化成"一半同步、一半散开"**。虽然精确同刻的请求数从 100% 降到 50%（仍然有收益），但"尖峰"并没有被消除——**只是变矮了一半**。

均值方面：`0.5 × (5600+8000)/2 + 0.5 × 8000 = 6800 × 0.5 + 4000 = 7400`，比标称上限低约 **7.5%**。这个偏差不大，**真正值得注意的是那个 50% 的尖峰，而不是均值。**

**根因是运算顺序：注释里的公式是 `min(max, 基值) × factor`，而代码是"先 `min`、再乘、再 `min`"**——多出来的第二次 `min` 把分布的上半截削平了。

**要真正对称，有两种做法**：

```java
// 做法一：允许抖动突破上限一点（上限变"软"）
return Math.max(1L, Math.round(raw * factor));            // 不第二次 min

// 做法二：先抖动、后收口，但收口时按比例重分布（更复杂，收益有限）
```

做法一最简单，代价是"最大等待时间可能到 `1.3 × maxMillis`"。**如果上限是硬的（比如受下游总超时约束），就得保留二次 `min`，并接受饱和区的尖峰**——但这时应该在注释里写清"饱和区抖动会被截断"，而不是只写一个不含截断的公式。

### 2.5 重试分类：哪些错该重试，哪些是浪费

```java
/**
 * 默认重试分类：按 HTTP 语义区分「临时故障」与「永久故障」。
 *
 * <p><b>可重试（临时故障）</b>——同样的问题下一次请求可能就好了：
 * <ul>
 *   <li>无响应 / 超时 / 连接失败（{@code statusCode <= 0}）：网络抖动</li>
 *   <li>408 请求超时、409 冲突</li>
 *   <li>429 限流：尊重上游的 {@code Retry-After}，没给就走退避</li>
 *   <li>5xx：上游自身故障</li>
 * </ul>
 *
 * <p><b>不可重试（永久故障）</b>——重试多少次结果都一样，只会浪费配额和延迟预算：
 * <ul>
 *   <li>400 / 404 / 422：请求本身有问题（参数错、模型不存在）</li>
 *   <li>401 / 403：鉴权失败，重试只会继续失败，而且会加速触发上游风控</li>
 * </ul>
 * 永久故障的正确处置是「立即切下一家供应商并告警人工介入」，而不是原地重试。
 */
```

**这张分类表的判别标准是"重试一次，结果会不会不同"**：

| 类 | 状态码 | 重试有意义吗 | 依据 |
|---|---|---|---|
| 传输层 | `statusCode <= 0` | ✓ | 网络抖动，下次可能通 |
| 超时/冲突 | 408, 409 | ✓ | 瞬时状态 |
| 限流 | 429 | ✓（但要等） | 上游要求你等 |
| 服务端 | 5xx | ✓ | 上游自身故障，可能自愈 |
| **参数错** | 400, 404, 422 | ✗ | 请求本身有问题，重试一模一样 |
| **鉴权错** | 401, 403 | ✗ | **而且会加速触发上游风控** |

**401/403 那一行是最容易做错的。** 直觉上"鉴权失败"像是瞬时问题（密钥刚轮换？），但实际上：

1. 重试 3 次 = **向上游发了 3 次失败鉴权**；
2. 大多数厂商把"连续鉴权失败"当成**攻击特征**，会临时封禁来源 IP；
3. 于是你从"一个供应商不能用"升级成"**整个出口 IP 被这家厂商封了**"——**把局部故障放大成区域性故障**。

**"不可重试"的正确处置不是"放弃"，而是"立刻换一家并告警"。** 分类器只负责回答"要不要在同一条路上再走一遍"，路由层负责"换一条路"——这是两个不同层级的决策。

还有个细节：

```java
if (attempt >= maxAttempts) {
    return RetryDecision.noRetry("已达最大尝试次数 " + maxAttempts);
}
if (!(error instanceof UpstreamException ex)) {
    // 非上游异常（编程错误 / 序列化失败）：重试无意义
    return RetryDecision.noRetry("非上游异常：" + error.getClass().getSimpleName());
}
```

**"非上游异常不重试"** 是很重要的一条：`NullPointerException`、`ClassCastException` 这类编程错误，重试只会得到同样的异常，纯属浪费。

**`RetryDecision` 携带 `reason` 字符串**（"为什么没重试"），这个设计在第 17 讲（`orTimeout` P0）里见过它的价值：**当有人问"为什么这次没重试"，答案在日志里，不需要重新推演代码。**

### 2.6 ★ P0：尊重 `Retry-After` 要有上限

回到开头那个事故。看这两段代码：

```java
case 429 -> RetryDecision.retry(
        ex.retryAfterMillis() > 0 ? ex.retryAfterMillis() : defaultRateLimitBackoffMillis,
        "429 限流，等待 " + (ex.retryAfterMillis() > 0
```

<img class="mermaid-svg" src="/zh/book-assets/diag-0119.svg" alt="RetryDecision 的三个字段（retryable / backoffMillis / reason）：backoffMillis 只夹下界、没有上界，且被直接 sleep() —— 本讲的第三处事故" />


**三个地方，全都只夹下界（`Math.max(0, x)`），没有一个夹上界。**

而最后这个 `backoffMillis` 被直接用来 sleep：

```java
sleeper.sleep(decision.backoffMillis());
```

**所以 `Retry-After: 86400` 就是"睡 24 小时"。**

**这是本讲最严重的一个缺陷，因为它的攻击面在系统之外**：

1. **上游可以决定你的线程占用时长**——上游返回什么，你就睡多久；
2. **它不需要恶意**——上游做限流演练、配置错误、或者一个新上的中间设备塞了一个异常的 `Retry-After`，效果与攻击一致；
3. **它的症状是"静默的"**——CPU 空、内存稳、上游健康，**所有资源监控都不响**，只有"请求超时率 100%"这一个信号；
4. **它的修法只要一行**——但那一行必须在**边界处**。

**修法：外部输入必须在入口被夹紧。**

```java
// 修法示意（不是仓库现状）：尊重上游建议，但要有自己的上限
/** 无论上游建议多久，本网关最多等这么久（保护自己的线程）。 */
private static final long MAX_RETRY_AFTER_MILLIS = 30_000L;

public UpstreamException(...) {
    // 下界 0，上界由网关自己定 —— 上游无权让我们的线程睡多久就睡多久
    this.retryAfterMillis = Math.max(0L, Math.min(MAX_RETRY_AFTER_MILLIS, retryAfterMillis));
}
```

或者更彻底：**在 `DefaultRetryClassifier` 里夹**，因为那里才是"决定等待时长"的地方：

```java
case 429 -> {
    long suggested = ex.retryAfterMillis() > 0 ? ex.retryAfterMillis() : defaultRateLimitBackoffMillis;
    long capped = Math.min(MAX_RETRY_AFTER_MILLIS, Math.max(0L, suggested));
    yield RetryDecision.retry(capped, "429 限流，上游建议 " + suggested + "ms，实际等待 " + capped + "ms"
            + (capped < suggested ? "（已按网关上限截断）" : ""));
}
```

**注意修法里的 `reason` 文案**：它明确告诉运维"上游建议 X，我们只等了 Y"——**"我们拒绝了上游的建议"这件事本身就是一个需要被看见的信号**（它意味着上游正在经历一次大范围限流）。

**这条经验的通用形式：** 凡是"对方给的数字、我照着执行"的地方——`Retry-After`、超时、分页大小、重试次数——**都必须有一层自己的上限**。这与第 31 讲"越权过滤不能依赖一行 filter"、第 32 讲"拒绝也要落库"是同一种思维方式：**边界上的值必须由自己决定。**

### 2.7 ★ 校验：熔断阈值到底是"失败次数"还是"尝试次数"？

看类注释承诺的因果链：

```java
 * <p><b>与重试的关系</b>：重试解决「单次抖动」，熔断解决「持续不可用」。二者串联：
 * 重试耗尽 → 记一次失败 → 达到阈值 → 打开 → 后续请求直接跳过 → 冷却后放一个探测请求。
```

**"重试耗尽 → 记一次失败"**——也就是"一次调用的全部尝试都失败 = 记一次失败"。

再看实现（`RoutingEngine.complete` 的循环）：

```java
for (int attempt = 1; ; attempt++) {
    long startedAt = nowMillis.getAsLong();
    try {
        breaker.acquire();
        allCircuitOpen = false;
        ChatResponse response = upstream.complete(request, target.upstreamModel());
        breaker.recordSuccess();
        ...
        return new ChatResponse(...);
    } catch (CircuitOpenException e) {
        ...
        break;
    } catch (UpstreamException e) {
        allCircuitOpen = false;
        breaker.recordFailure();                      // ← 每次尝试都记一次
        RetryDecision decision = classifier.classify(e, attempt);
        ...
        if (!decision.retryable() || attempt >= HARD_ATTEMPT_CAP) {
            break;
        }
        sleeper.sleep(decision.backoffMillis());
    } catch (RuntimeException e) {
        allCircuitOpen = false;
        breaker.recordFailure();                      // ← 这里也是
        ...
        break;
    }
}
```

**`recordFailure()` 在每个 attempt 的 catch 里被调用——不是"重试耗尽后记一次"。**

后果可以精确算出来。默认配置是：

```yaml
max-attempts: 3              # 单供应商最多尝试 3 次
breaker:
  failure-threshold: 5       # 连续失败 5 次打开
```

**一次完全失败的调用会记 3 次失败**（3 次尝试各记一次）。所以：

| 调用序列 | 累计 failures | 熔断器状态 |
|---|---|---|
| 第 1 次调用：尝试 1 失败 | 1 | CLOSED |
| 第 1 次调用：尝试 2 失败 | 2 | CLOSED |
| 第 1 次调用：尝试 3 失败 | 3 | CLOSED |
| 第 2 次调用：尝试 1 失败 | 4 | CLOSED |
| 第 2 次调用：尝试 2 失败 | **5** | **→ OPEN** |

**两个坏掉的请求就能熔断。**

这好还是不好？**取决于你怎么读 `failure-threshold: 5` 这个配置项。**

- 如果运维认为它是"**5 次失败的调用**"，那实际行为比配置敏感 **3 倍**（因为每次调用记 3 次）；
- 如果运维认为它是"**5 次上游失败响应**"，那它是对的。

**问题的核心不是"3 倍"这个数字，而是"配置项的单位与注释不一致"。**

```java
/**
 * @param failureThreshold     连续失败多少次后打开（默认 5）
 */
```

**"连续失败多少次"——失败的是什么？没有说。** 而类注释说的是"重试耗尽 → 记一次失败"，指向"调用"；实现记的是"尝试"。**配置项文档和类注释给出了两种不同的解释，而实现只对应其中之一。**

**更敏感的熔断本身在多数场景下是好事**（早熔断 = 早保护），但它有代价：

1. **更容易被抖动误伤**——一个上游偶发 5xx，在"记 3 次"的口径下只要 2 个请求就熔断 30 秒；
2. **半开探测更频繁**（每次冷却结束都试），给一个"半死"上游持续加压；
3. **最麻烦的是：无法通过调大 `failure-threshold` 精确控制灵敏度**——你调的是"尝试数"，而你的直觉是"失败调用数"，中间有一个 `max-attempts` 的隐式倍数。

**修法有两种，选哪种取决于你想要哪个语义：**

```java
// 修法一：让实现符合注释 —— 在"本次调用彻底失败"时才记一次
// （需要把 recordFailure 提到 for 循环之外，用一个 boolean 标记本次调用是否成功）
boolean callFailed = false;
for (int attempt = 1; ; attempt++) {
    try { ... return ...; }
    catch (UpstreamException e) {
        callFailed = true;                      // 只标记
        if (!decision.retryable() || attempt >= HARD_ATTEMPT_CAP) break;
        sleeper.sleep(...);
    }
}
if (callFailed) breaker.recordFailure();        // 循环外只记一次

// 修法二：保留实现，把配置项改名或写清单位
// failureThreshold → "连续失败的上游响应数（注意：一次调用最多贡献 maxAttempts 次）"
```

**修法一更符合"配置项应该表达业务意图"的原则**——运维想调的是"多不健康才算坏"，不是"几个 HTTP 响应算坏"。

### 2.8 ★ 两个 `Sleeper` 实现，语义相反

`RoutingEngine` 定义了自己的默认 sleeper：

```java
private static final Sleeper DEFAULT_SLEEPER = millis -> {
    if (millis <= 0) {
        return;
    }
    try {
        Thread.sleep(millis);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("退避等待被中断", e);      // ← 抛异常，中止重试
    }
};
```

而 Spring 装配时注入的是**另一个**：

```java
millis -> {
    if (millis > 0) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();                    // ← 只恢复标志位，继续重试
        }
    }
}
```

**差异在 `InterruptedException` 的处理上：**

| 实现 | 被中断时 | 效果 |
|---|---|---|
| `DEFAULT_SLEEPER`（无框架回退） | 恢复标志位 + **抛 `IllegalStateException`** | 重试**中止** |
| `GatewayConfig` 注入（**生产路径**） | 只恢复标志位 | 重试**继续** |

**生产走的是第二个，也就是"吞掉中断、继续重试"的那个。**

为什么这是个问题？因为 `application.yml` 里开了优雅停机：

```yaml
server:
  shutdown: graceful
```

优雅停机的机制是：**收到 SIGTERM → 给正在处理的请求一个宽限期 → 期间会中断工作线程 → 等待它们结束。** 而如果工作线程在 `sleeper.sleep()` 里被中断，它会：

1. 恢复中断标志位（`Thread.currentThread().interrupt()`）——**这个动作是对的**；
2. **然后继续 `sleep` 之后的逻辑，也就是继续重试。**

这意味着一次"正在退避中的请求"**不会响应停机信号**，它会走完全部重试（最坏情况：3 次尝试 × 8 秒退避 + 3 次上游超时）。**优雅停机的宽限期就这么被吃掉了，最后由强制 kill 收场。**

**同一个抽象的两套实现语义不同，是"默认实现与生产装配不一致"这一类缺陷的典型。** 它比单个 bug 更危险，因为：

- **单元测试跑的是 `DEFAULT_SLEEPER` 的行为**（或者注入自己的假 sleeper，压根不 sleep）；
- **生产跑的是另一个**；
- **两者的差异只在"中断发生时"暴露**——也就是只在停机/取消时暴露。

**判据：如果一个接口有多个实现，而它们的差异只在异常/边界路径上，就必须有测试同时覆盖这几种实现。** 否则你测的是实现 A，跑的是实现 B。

**统一修法**：让两边一致，并且明确选择。"中断即中止重试"是更符合优雅停机语义的选择：

```java
millis -> {
    if (millis <= 0) {
        return;
    }
    try {
        Thread.sleep(millis);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("退避等待被中断，中止重试", e);
    }
}
```

**顺带说清"中断后怎么办"的通用答案**：恢复标志位（必须，否则调用方的取消逻辑失效）+ **向上传递取消**（抛异常或用标志位检查）。**绝不能"恢复标志位然后继续干"**——那等于告诉 JVM"我收到了取消请求，但我不打算理它"。

### 2.9 ★ 重试没有总预算

把一次调用的最坏耗时算出来：

```
单次尝试 = 上游超时（配置值，README 的示例是 60s）
单次退避 = 500ms → 1000ms → 2000ms → 4000ms → 8000ms（上限）

单落点最坏 = 3 次尝试 × 超时 + 2 次退避
          = 3 × 60s + (0.5 + 1)s
          = 181.5s

多落点最坏 = 落点数 × 181.5s
           = 3 × 181.5s
           = 544.5s ≈ 9 分钟
```

**一次业务请求最坏可以在网关里待 9 分钟。**

而客户端的超时通常是多少？30 秒、60 秒。所以真实场景是：

```
t=0     业务方发起请求
t=30s   业务方超时，放弃，向上游返回失败
t=30s   网关还在重试（它不知道业务方已经走了）
t=9min  网关终于失败，落一条 failure 记录，消耗了若干次上游配额
```

**"客户端已经放弃，服务端还在烧钱"**——这是重试类系统最经典的浪费模式。而且它的成本是双倍的：**浪费了 token/配额 + 占用了线程 + 在账单上留下记录**。

第 17 讲（并行编排与超时控制）里，`code-review-agent` 的 `CompletableFutureCoordinator` 用**共享 deadline** 解决了这个问题：

```
共享 deadline + 每次重算 remaining + get(remaining, MS) + cancel(true)
```

**同一个作者的两个系统，一个有总 deadline、一个没有。** 这不是能力差异，是 **"有没有把重试链路当成一个整体来算时间预算"** 的意识差异。

**正确的形态是"重试预算"：**

```java
// 思路：给整条调用链一个 deadline，重试只在"剩余时间还够"时进行
long deadline = now + TOTAL_BUDGET_MILLIS;              // 比如 20 秒
for (int attempt = 1; ; attempt++) {
    long remaining = deadline - now;
    if (remaining <= 0) {
        failures.add("总预算耗尽（" + TOTAL_BUDGET_MILLIS + "ms）");
        break;
    }
    // 上游超时也要用 remaining 截断，而不是用它自己的固定值
    long callTimeout = Math.min(upstreamTimeout, remaining);
    ...
    long delay = decision.backoffMillis();
    if (delay >= deadline - now) {                      // 等完就没时间了，不等了
        failures.add("退避 " + delay + "ms 会超出总预算，放弃重试");
        break;
    }
    sleeper.sleep(delay);
}
```

**两个关键点**：
1. **退避也要算进预算**——"等 8 秒再试"在只剩 5 秒时会直接超支；
2. **上游超时要用 `remaining` 截断**——否则最后一次尝试可能用满 60 秒，把预算冲掉 3 倍。

### 2.10 数量级直觉：几个并发请求就能榨干线程池

"线程池被一个 429 睡死"值得落成数字，因为 V 住线程的数小到反直觉：

```text
Tomcat 默认 max-threads ≈ 200，每个请求最坏占住一个线程 60s（超时）或 1h（睡死）。

- 纯超时：可接受的最大吞吐 = 200 线程 / 60s 占用 ≈ 3.3 req/s（持续）
- 睡满 1 小时：200 线程 / 3600s ≈ 0.056 req/s = 每 18 秒一个请求就能占满池子

反推"打满"所需的并发：
- 只要并发里同时有 ~200 个请求在等/在睡，就满；第 201 个请求立即失败
- 也就是：一只上游只要决定让请求慢下来，它不费什么力气就能让"我的线程池 100% 被它占用"
```

> **结论**：让健康上游"一起陪葬"的不是某个巨大流量，而是**很低的持续到达率就能占满的线性资源**。熔断把"等满超时"变成"立即失败"，就是把这条 `毫无争议的 60s 占用` 从每个请求身上摘掉。这也解释了为什么"线程数/上游超时"这两个数字是网关容量预算的第一张表——**先算"多少并发 = 池满"，再谈保护。**

> **工程判据：为一个阻塞型下游配同步线程池，先把上限当作"池子 = 并发上限"来算——需要多少毫秒的下降就把池打满，答案小于你客户端的超时，就该无等待失败（熔断/快速失败），而不是重试。** 同步模型下，你的抗压上限不是 QPS，是"并发 × 每个请求的最坏等待"。

## 三、避坑清单

- [ ] **任何"对方给的时长"都要夹上界。** `Retry-After` / 上游超时 / 分页大小——照单全收就是让对方决定你的资源占用。
- [ ] **夹紧发生在边界处（异常构造器或决策器），不要散落在各个 `sleep` 调用点。** 边界夹紧了，所有调用点自动安全。
- [ ] **熔断阈值必须说清单位**："失败"是指一次调用还是一次上游响应？如果实现与注释不一致，**要么改实现要么改注释——不能让两者同时存在**。
- [ ] **多个实现共享同一接口时，要在同一条测试里覆盖它们。** 特别是异常/取消路径——那正是它们最容易分叉的地方。
- [ ] **`InterruptedException` 的正确处理是"恢复标志位 + 向上传递取消"。** "恢复标志位 + 继续干活"等于无视停机信号。
- [ ] **重试链路必须有一个总 deadline。** 判据："把最坏情况算出来"——`落点数 × 尝试数 × (超时 + 退避)`。如果结果大于客户端超时，你的重试有一半是白花的。
- [ ] **退避要计入 deadline。** "等 8 秒"是一个需要预算的动作，不是一个免费的动作。
- [ ] **401/403 绝不重试。** 重试会加速触发上游风控，把"一个供应商不可用"升级成"出口 IP 被封"。
- [ ] **抖动要在确定的截断之后做，或者允许超过上限一点。** "先 min 再乘抖动再 min"会让饱和区**一半的重试被压到上限而完全同步**（期望值偏低约 7.5%）——抖动的目的部分落空。
- [ ] **"剩余冷却时间"要进告警内容。** "还剩 12 秒"和"刚打开"需要完全不同的处置。
- [ ] **配置项的不对称（有的可配、有的写死）要在注释里给理由。** 否则运维会以为"调不了是因为没找到配置项"。
- [ ] **没有总 deadline 的重试，等于给自己造了一个"延迟放大器"。**

## 四、动手任务

> **目标**：亲手复现"上游让你睡多久你就睡多久"，算出熔断阈值的真实灵敏度，并给你的调用链加上总预算。

**步骤 1：复现 `Retry-After` 无上限**

写一个最小的桩服务，返回 429 加一个超大 `Retry-After`：

```python
# 桩上游：只做一件事 —— 返回 429 + 巨大的 Retry-After
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        self.send_response(429)
        self.send_header("Retry-After", "86400")     # ← 24 小时
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(b'{"error":{"message":"rate limited"}}')
    def log_message(self, *a): pass

HTTPServer(("127.0.0.1", 9099), H).serve_forever()
```

把它配成一个供应商，然后打一次请求：

```bash
time curl -s -o /dev/null -w "%{http_code}\n" localhost:8090/v1/chat/completions \
  -H "Authorization: Bearer $AK" -H 'Content-Type: application/json' \
  -d '{"model":"default","messages":[{"role":"user","content":"hi"}]}'
```

**预期结果**：请求**长时间挂住不返回**。服务端日志里出现 `429 限流，等待 86400000ms（Retry-After）`。

**关键对照**：把 `time` 的输出（或 `curl` 的 `%{time_total}`）与"上游超时"配置对比——**等待时间应该远远大于上游超时**，因为它压根不是超时问题，是 sleep。

**注意**：验证时把并发压到 1，别把自己环境打挂。这条测试的目的是**证明这种等待是"照单全收"的**，不是压测。

**步骤 2：算出熔断阈值的真实灵敏度**

```bash
# 确认两个配置值
grep -n "max-attempts" token-factory-server/src/main/resources/application.yml
grep -nA4 "breaker:" token-factory-server/src/main/resources/application.yml
```

**预期结果**：`max-attempts: 3`、`failure-threshold: 5`。

现在做算术：

```
一次完全失败的调用贡献的 failure 次数 = max-attempts = 3
熔断所需的最小调用数 = ceil(failure-threshold / max-attempts) = ceil(5 / 3) = 2
```

**关键对照**：去 `RoutingEngine.complete` 里确认 `recordFailure()` 的位置——**在 attempt 循环内的 `catch (UpstreamException e)` 分支里**（`RoutingEngine.java:150`），以及 `catch (RuntimeException e)` 分支里（`:165`）。

**它不在循环外。** 所以"2 次调用即可熔断"成立，而类注释说的"重试耗尽 → 记一次失败"（→ 应该需要 5 次调用）不成立。

**步骤 3：验证两种 `Sleeper` 的行为差异**

```bash
# 两个实现各在哪个文件
grep -rn "InterruptedException" token-factory-core/src/main/java/io/tokenfactory/core/routing/RoutingEngine.java
grep -rn "InterruptedException" token-factory-server/src/main/java/io/tokenfactory/server/config/GatewayConfig.java
```

**预期结果**：
- `RoutingEngine.java` 的 `DEFAULT_SLEEPER`：捕获后 **`throw new IllegalStateException("退避等待被中断", e)`**；
- `GatewayConfig.java` 注入版：捕获后**只调 `Thread.currentThread().interrupt()`，然后继续**（没有 throw）。

**关键对照**：写一个小测试，用 `Future.cancel(true)` 中断一个正在退避的线程，观察它是否停止重试。

```java
// 思路（伪代码）：中断正在退避的线程，断言它是否还继续尝试
// 用 GatewayConfig 的 sleeper → 期望"继续重试"（说明问题存在）
// 用 RoutingEngine.DEFAULT_SLEEPER → 期望"抛异常中止"
```

**两种实现的断言结果不同，本身就证明了"多实现语义分叉"这件事。**

**步骤 4：给你的调用链加总预算**

```bash
# 先算出你当前的最坏情况
grep -rn "timeout\|Timeout" --include=*.yml token-factory-server/src/main/resources/ | head
```

把落点数、尝试数、超时、退避上限四项拿出来，**乘一遍**：

```
最坏耗时 = 落点数 × [尝试数 × 超时 + Σ退避]
```

**关键对照**：把这个数字与你的**客户端超时**并排写下来。

- 如果 `最坏耗时 > 客户端超时` → **你的重试有一部分注定是白费的**，而且它会在你放弃之后继续占用线程和配额。
- 修法是引入 `deadline`：每次循环开头重算 `remaining`，用它截断上游超时；退避时间超过 `remaining` 就直接放弃。

**验收标准**：改完之后，把桩上游设成"永远超时"，打一次请求。**总耗时应该收敛到你设定的预算（比如 20 秒），而不是跑满 9 分钟。**

## 本讲小结

1. **限流、熔断、退避解决三个不同的问题**：限流保护自己、熔断让调用方快速失败、退避保护单次调用的成功率。**`token-factory` 没有 QPS 限流器**——面试时如实说"没做"并给出理由，比含糊其辞强。
2. **熔断的价值是"把等待变成立即失败"**，从而不让健康上游被线程耗尽陪葬。**"剩余冷却时间"要进告警**，因为"还剩 12 秒"和"刚打开"处置完全不同。
3. **半开态的不对称是刻意的**：CLOSED 要 N 次失败才打开，HALF_OPEN 失败 1 次就退回。**不确定的地方失败即退回，确定的地方要有证据才改变。**
4. **★ P0：`Retry-After` 没有上界。** `UpstreamException` 与 `RetryDecision` 都只夹下界，`sleeper.sleep(decision.backoffMillis())` 照单全收 → **上游一行 `Retry-After: 86400` 就能让网关线程睡 24 小时**，200 个请求打满线程池。**"对方给的时长必须由自己夹上界"。**
5. **★ 熔断阈值的单位与注释不一致。** 类是"重试耗尽记一次失败"，实现是"每次尝试都记一次"——默认配置下**两个坏请求就能熔断**，而注释暗示需要 5 次。
6. **★ 两个 `Sleeper` 语义相反**，生产用的是"吞掉中断继续重试"那个，与 `shutdown: graceful` 冲突。**同接口多实现，必须有一条测试覆盖全部实现的中断路径。**
7. **★ 重试链路没有总 deadline。** `落点数 × 尝试数 × (超时 + 退避)` 最坏可达数分钟，远超客户端超时——**客户端放弃后，网关还在烧钱。**（对照第 17 讲：`code-review-agent` 用共享 deadline 解决了这件事。）
8. **抖动在饱和区只向下。** "先 `min` 再乘抖动再 `min`"让期望值比标称上限低约 12%——注释里的公式与代码里的运算顺序不完全一致。
