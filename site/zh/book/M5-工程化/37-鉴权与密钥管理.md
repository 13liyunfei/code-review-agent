## 一、痛点

上线第三天，安全同学来找我，问了一个我当时答得很含糊的问题：

> "你的管理接口，如果 `ADMIN_KEY` 环境变量忘了配，会发生什么？"

我想了一下："那就是空值，比较的时候……应该谁都能过吧。"

他沉默了两秒，说："所以你们的处置方案是——**发布漏配一个环境变量，等于把管理面全网公开**。"

接着他还发现了一个更隐蔽的东西。我们的 AK 校验是这么写的（我当时的版本）：

```java
if (providedKey.equals(record.storedKey())) { ... }   // 字符串比较
```

他说："这个 `equals` 是**逐字节短路**的。攻击者发一个 `aaaa...`，用响应时间就能一个字节一个字节试出正确的密钥——**时间侧信道**。你这个 AK 是 32 位随机串，够长，但如果 AK 更短、或者校验的是别的秘密，这条路是通的。"

两个问题，一个**配置缺失时的默认值**，一个**比较方式**。都不是"功能"，都是"边界"。

**这类问题的共同点：它们在功能测试里永远不会暴露。** 你的测试都会配好密钥、都用正确的 AK——所以 100% 绿。而它们出事的方式是"某次发布漏配了变量"或"某个人耐心地跑了 4 小时定时攻击"。

## 二、原理

### 2.1 AK 为什么用 SHA-256 而不是 BCrypt

先说一个反直觉的结论：**存机器凭证和存用户口令，是两件技术选型相反的事。**

`KeyHasher` 的类注释把这个取舍写得非常清楚：

```java
/**
 * Access Key 的生成与校验。
 *
 * <p><b>为什么用 SHA-256 而不是 BCrypt</b>：AK 是 256 位随机串（不是用户口令），
 * 不存在弱口令问题，无需慢哈希；而网关每次调用都要校验一次，必须足够快。
 * 慢哈希用在这里只会白白消耗 CPU——这是口令存储与机器凭证存储的典型区别。
 */
```

把这段推理拆成两条独立的判据：

| 维度 | 用户口令 | 机器凭证（AK） |
|---|---|---|
| 熵 | 低（人会选 `123456`） | **高**（256 位随机，穷举不可行） |
| 攻击面 | 离线撞库（拖库后爆破） | **在线高频校验**（网关每次调用都要算一次） |
| 需要的哈希 | **慢**（bcrypt/argon2，故意拖慢每次尝试） | **快**（SHA-256，越快越好） |

**慢哈希的价值来自"攻击者只有很少的尝试机会，所以把每次尝试变贵"。** 而 AK 是 256 位随机——攻击者的尝试次数在数学上就不够，把每次校验变贵只是在**惩罚自己的正常流量**。

这就是为什么 `KeyHasher` 里两个方法一快一慢的对比如此干净：

```java
private static final String ALPHABET = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";

/** 生成一个新 Key：{@code tf_<keyId>_<secret>}，明文只在创建时返回一次。 */
public static String generatePlainKey(String keyId) {
    StringBuilder secret = new StringBuilder(32);
    for (int i = 0; i < 32; i++) {
        secret.append(ALPHABET.charAt(RANDOM.nextInt(ALPHABET.length())));
    }
    return "tf_" + keyId + "_" + secret;
}
```

三点值得注意：

**① `SecureRandom` 而不是 `Random`。** `Random` 是线性同余发生器，知道种子就能推出后续全部输出；`SecureRandom` 是密码学安全的。**生成凭证时没有第二个选项。**

**② 字母表 62 个字符 × 32 位** = `62^32` ≈ `2^190`。这个量级的熵下，"爆破"不是"慢"，是"不可能"。

**③ `tf_<keyId>_<secret>` 的三段式。**

```java
/** 生成公开的 keyId（8 位小写十六进制，仅用于日志定位）。 */
public static String generateKeyId() {
    StringBuilder sb = new StringBuilder(8);
    for (int i = 0; i < 8; i++) {
        sb.append(Character.forDigit(RANDOM.nextInt(16), 16));
    }
    return sb.toString();
}
```

`keyId` 是**公开的**（8 位十六进制，约 43 亿种），它的作用只有一个：**日志定位**。这样你的日志可以写 `keyId=a1b2c3d4 的 AK 已被吊销`，而**永远不需要打印密钥本身**。

把"用来定位的标识"和"用来认证的秘密"分开，是所有凭证系统的第一原则。**如果一个系统只能通过打印密钥来定位是哪个调用方，它迟早会把密钥打进日志。**

### 2.2 永远不要 `equals` 比较秘密

```java
/** 定长比较，避免通过响应时间侧信道逐字节猜密钥。 */
public static boolean constantTimeEquals(String a, String b) {
    if (a == null || b == null) {
        return false;
    }
    return MessageDigest.isEqual(a.getBytes(StandardCharsets.UTF_8),
            b.getBytes(StandardCharsets.UTF_8));
}
```

`MessageDigest.isEqual` 是 JDK 提供的**恒定时间比较**：它对两个数组做逐字节 XOR 累积，**不做早期返回**——不管第 1 个字节就不同还是第 32 个字节才不同，都会把全部字节走完。

而 `String.equals` / `Arrays.equals` 都是短路的：第 1 个字节不同就立刻返回 `false`。攻击者测量响应时间，就能判断"我猜对了几位"，把搜索空间从 `62^32` 降到 `62 × 32`。

**这个区别在本地压测里是完全看不出来的**（网络抖动比纳秒级差异大几个数量级），只有在攻击者能精确测量大量样本时才显现。这就是为什么它必须靠**代码规范**而不是测试来防——**你写不出一个稳定失败的测试来证明它对了。**

### 2.3 `AccessKeyInterceptor`：一次调用要做四件事

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    String token = bearerToken(request);
    if (token == null) {
        throw AuthException.unauthorized("缺少 Authorization: Bearer <access-key> 请求头");
    }
    var record = accessKeys.findByHash(KeyHasher.sha256Hex(token))
            .orElseThrow(() -> AuthException.unauthorized("access key 无效或已被吊销"));
    if (!record.isActive()) {
        throw AuthException.forbidden("access key 已停用");
    }

    String traceId = firstNonBlank(request.getHeader("X-TF-Trace-Id"),
            request.getHeader("X-Trace-Id"), UUID.randomUUID().toString());
    String appId = request.getHeader("X-TF-App");
    String requestId = UUID.randomUUID().toString();

    MDC.put("traceId", traceId);
    MDC.put("tenant", record.tenantCode());
    request.setAttribute(CallPrincipal.ATTRIBUTE,
            CallPrincipal.of(record.tenantCode(), record.keyId(), appId, traceId, requestId));
    accessKeys.touchLastUsed(record.id());
    log.debug("调用方身份解析完成：tenant={} keyId={} app={}", record.tenantCode(), record.keyId(), appId);
    return true;
}
```

四个动作，每一个都有明确理由：

**① 按哈希查，不是"取出所有再比较"**

```java
accessKeys.findByHash(KeyHasher.sha256Hex(token))
```

`findByHash` 是**一次带索引的等值查询**（`WHERE key_hash = ?`）。它有两个好处：性能上不随租户数增长；安全上**库里的明文从来不存在**，所以"拖库"拿不到任何可用的 AK。

反模式是：`select * from access_keys` 然后在应用里循环比较——那既慢，又意味着**你手里有一份完整的明文清单**。

**② "无效" 和 "已停用" 是两个状态码**

```java
throw AuthException.unauthorized("access key 无效或已被吊销");     // 401
throw AuthException.forbidden("access key 已停用");                // 403
```

这不是风格问题：**401 的处置是"换一个 AK"，403 的处置是"找管理员开通"。** 把它们混成一个状态码，调用方就只能靠读中文 message 判断该怎么办。

**③ traceId 从请求头继承，而不是新生成**

```java
String traceId = firstNonBlank(request.getHeader("X-TF-Trace-Id"),
        request.getHeader("X-Trace-Id"), UUID.randomUUID().toString());
```

`X-TF-Trace-Id` 优先（网关自定义），`X-Trace-Id` 兜底（业界通用），都没有才生成。**这让"业务系统 A 的一次请求"和"网关里的一次调用"能用同一个 ID 串起来**——这是下一讲（成本计量）能做"全链路溯源"的前提。

`MDC.put("traceId", traceId)` 把它放进日志的 MDC，于是**这一跳的所有日志自动带上 traceId**。`afterCompletion` 里必须 `MDC.remove`——因为 Tomcat 线程是复用的，不清理会让下一个请求的日志带上错误的 traceId。

**④ `touchLastUsed`：为"这把 AK 还在用吗"提供数据**

```java
accessKeys.touchLastUsed(record.id());
```

这个设计解决一个很实际的运维问题：**发出去的 AK，哪些已经没人用了？** 没有这个时间戳，安全审计只能靠"猜"，而"想知道但不敢吊销"的 AK 会越积越多——它们是最危险的闲置凭证。

### 2.4 `AdminKeyInterceptor`：fail-closed

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    String configured = properties.getAdminKey();
    if (configured == null || configured.isBlank()) {
        // fail-closed：没有配置管理密钥就一律拒绝，绝不「默认放行」
        throw AuthException.forbidden(
                "管理接口未配置 token-factory.admin-key，已拒绝访问（fail-closed）");
    }
    String presented = request.getHeader("X-Admin-Key");
    if (!KeyHasher.constantTimeEquals(configured, presented)) {
        throw AuthException.unauthorized("X-Admin-Key 无效");
    }
    return true;
}
```

**`if (configured == null || configured.isBlank())` → 抛异常，而不是 `return true`。**

这就是"痛点"里那个问题的答案。两种写法的差别可以用一句话概括：

> **fail-open**：没配密钥 → 放行（"开发方便"）
> **fail-closed**：没配密钥 → 拒绝（"安全默认"）

**为什么网关类服务必须 fail-closed？** 因为"没配密钥"和"没有攻击者"是两件**不相关**的事。前者的概率不低（发布漏配、配置中心回滚、新环境部署），而后者的概率是 100%（公网扫描是持续的）。两个独立的高概率事件相乘，结论就是：**fail-open 的管理面，迟早会有一个窗口期是裸奔的。**

而且这个窗口期**没有任何症状**：调用方正常、日志正常、监控正常——直到有人在你的管理面里建了一个租户、发了一把 AK。

**反向追问：那开发环境怎么办？** 答案不是"放宽默认值"，而是**显式提供一个不安全的配置**，让"我知道我在干什么"变成一个必须写出来的动作。`token-factory` 的做法是测试里直接注入一个密钥：

```java
/** 便于测试直接判定配置是否就绪。 */
public boolean isConfigured() {
    String configured = properties.getAdminKey();
    return configured != null && !configured.isBlank();
}
```

`isConfigured()` 与 `statusWhenMisconfigured()` 两个方法**专门为测试和运维检查存在**——它们把"当前是 fail-closed 的哪个分支"变成可断言的。

### 2.5 两套鉴权，路径不重叠

```java
registry.addInterceptor(accessKeyInterceptor)
        .addPathPatterns("/v1/**");
registry.addInterceptor(adminKeyInterceptor)
        .addPathPatterns("/api/admin/**");
```

调用面（业务方用 AK）与管理面（运维用 Admin-Key）**挂在不同前缀，认证方式不同、凭证类型不同、暴露对象不同**。

这个"不重叠"是刻意维持的：一旦有一条路径同时匹配两者（比如某个兼容用的 `/v1/admin/...`），你就要回答一串很难回答的问题——"这把 AK 有没有权限调管理接口？"**多一种凭证组合，就多一倍的审查成本。**

### 2.6 租户隔离必须在查询层，而不是在应用层

`UsageController` 的四个查询端点都做了租户过滤。以 `byTrace` 为例：

```java
@GetMapping("/trace/{traceId}")
public List<UsageRow> byTrace(@PathVariable String traceId, HttpServletRequest http) {
    List<UsageRow> rows = usage.findByTraceId(traceId);
    // 只返回调用方自己租户的数据——租户间用量互不可见
    String tenant = ((CallPrincipal) http.getAttribute(CallPrincipal.ATTRIBUTE)).tenantCode();
    return rows.stream().filter(r -> tenant.equals(r.tenantCode())).toList();
}
```

**这段代码是安全的，但它的安全性完全依赖最后一行那个 `filter`。** 先全表查出所有租户的数据、再在内存里过滤掉——多租户隔离变成了**一行代码的责任**。任何一次重构、任何一个新端点忘了写这个 filter，就是跨租户数据泄露。

正确形态是把 `tenant` 下推到 SQL：

```java
// 修法示意（不是仓库现状）：租户条件进 WHERE，越权数据根本不离开数据库
List<UsageRow> rows = usage.findByTraceIdAndTenant(traceId, tenant);
```

**判断标准很简单：如果"删掉这一行"的后果是"越权访问"，那这一行就不该是一个独立的、可被遗忘的步骤。** 它应该是接口签名的一部分——方法名里带 `tenant`，让调用方**没法忘记**。

至于 `recent` 端点，参数夹紧写得很规范，可以照抄：

```java
return usage.listRecent(tenant, Math.min(Math.max(limit, 1), 1000));
```

### 2.7 对照：`code-review-agent` 是 fail-open

同一个作者、同一时期的一个项目，`ApiAuthFilter` 写的是另一种选择：

```java
// 仅对 /api/** 强制鉴权（含管理后台 /api/admin/**）
if (uri.startsWith("/api/")) {
    if (!StringUtils.hasText(authToken)) {
        // 未配置 token：本地/开发便利，放行但持续告警（生产务必配置 REVIEW_API_TOKEN）
        log.warn("[ApiAuth] 未配置 review.api.auth-token，/api 接口当前零鉴权；"
                + "生产环境请通过 REVIEW_API_TOKEN 设置访问令牌");
        chain.doFilter(request, response);
        return;
    }
    ...
}
// 其它路径（如根路径）放行
chain.doFilter(request, response);
```

**这是 fail-open：没配 token → 放行 + WARN 日志。**

它是不是错的？**要看这个服务的部署形态**：

| 服务 | 部署形态 | 默认值该是 |
|---|---|---|
| `token-factory` | 公司级入口，所有业务方都打到它 | **fail-closed** |
| `code-review-agent` | 自部署的单体应用，主要一个人用，PR 通过 webhook 进来 | fail-open + 强告警（可接受，但**必须留痕**） |

**关键差异是"这个端口会不会被别的东西访问到"。** 自部署工具的 `localhost:8080` 和公司网关的 `:8090` 是两个完全不同的暴露面。

但即使是 fail-open，也有一条**不可省略**的要求——**必须留下明确的运行痕迹**：

```java
log.warn("[ApiAuth] 未配置 review.api.auth-token，/api 接口当前零鉴权；"
        + "生产环境请通过 REVIEW_API_TOKEN 设置访问令牌");
```

这行 WARN 是"我知道我在裸奔"的声明。它能不能被看见，取决于你有没有给 WARN 配告警——**而这类"配置缺失"的告警，恰好是所有人都会忽略的一类。**

### 2.8 一个真实的默认放行漏洞

`ApiAuthFilter` 的放行判断：

```java
private boolean isPassThrough(String uri) {
    return uri.startsWith("/webhook/")
            || uri.equals("/health")
            || uri.startsWith("/actuator/health")
            || uri.startsWith("/error")
            || uri.equals("/");
}
```

看起来是"白名单放行"，很稳妥。**但结合这个过滤器的结构读一遍**：

```java
if (isPassThrough(uri)) { 放行; return; }          // ① 白名单命中 → 放行
if (uri.startsWith("/api/")) { ...强制校验... }    // ② /api/** → 鉴权
chain.doFilter(request, response);                 // ③ 其它一切 → 放行
```

**③ 才是默认分支。** 这意味着：

- `/actuator/health` → ① 放行 ✓（有意）
- `/api/xxx` → ② 鉴权 ✓（有意）
- **`/actuator/env`、`/actuator/beans`、`/actuator/heapdump`、`/actuator/loggers` → ③ 放行**（**无意**）

`/actuator/health` 出现在白名单里会给人一个错觉："actuator 被妥善处理了。"但**只有 health 被显式处理**，其余 actuator 端点全靠"默认放行"这条兜底分支溜过去。

**这就是"白名单 + 默认放行"这种结构的危险之处：它看起来像白名单（很安全），实际行为是黑名单（默认全开）。**

对比 `token-factory` 的 `WebConfig`——它没有"默认分支"，只注册了两个拦截器，其余路径**根本不匹配任何 Bean**（也就是**默认不放行任何未声明的东西**，因为那些路径压根没有业务逻辑）。这是"默认拒绝"的结构：

```
token-factory:  只挂 /v1/** 与 /api/admin/**  → 别的路径没有 Controller，404
code-review-agent: 只拦 /api/**               → 别的路径若有 Controller，直接可达
```

**同一个作者的两个项目，一个默认拒绝、一个默认放行。** 差别不在于"谁更懂安全"，在于**有没有意识到"默认分支"也是要设计的东西**。

真正的修法是把默认值反过来：

```java
// 修法示意（不是仓库现状）：把默认分支从"放行"改成"拒绝"
// 只有显式列出的公开路径才放行，其余一律 401
if (isPublic(uri)) { chain.doFilter(request, response); return; }
if (!authenticated(request)) { respond401(response); return; }
chain.doFilter(request, response);
```

这样 `isPublic` 每加一条都要有人签字，而**新端点默认是"受保护"的**。

### 2.9 顺带：`constantTimeEquals` 在这里泄露了长度

`ApiAuthFilter` 自己写了一份常量时间比较：

```java
private boolean constantTimeEquals(String a, String b) {
    if (a == null || b == null) {
        return false;
    }
    byte[] ab = a.getBytes(java.nio.charset.StandardCharsets.UTF_8);
    byte[] bb = b.getBytes(java.nio.charset.StandardCharsets.UTF_8);
    if (ab.length != bb.length) {          // ← 长度不同立即返回
        return false;
    }
    int result = 0;
    for (int i = 0; i < ab.length; i++) {
        result |= ab[i] ^ bb[i];
    }
    return result == 0;
}
```

逐字节 XOR 累积这段是对的（不短路）。**但 `:95-97` 那个长度检查是短路的**——所以攻击者仍然能通过测量响应时间区分"长度猜对了吗"。

它比 `String.equals` 好，但不是"恒定时间"。对比 `KeyHasher` 那一行：

```java
return MessageDigest.isEqual(a.getBytes(StandardCharsets.UTF_8), b.getBytes(StandardCharsets.UTF_8));
```

JDK 的 `MessageDigest.isEqual` **不做长度早退**（它把长度差异也累积进同一个 result 变量，然后仍然遍历完）。**不用自己写，JDK 已经有了。**

而注释写的是"避免计时侧信道泄露 token **长度**/内容"——**注释声称防住了长度泄露，实现恰好泄露了长度**。这是本书反复出现的同一类缺陷：**注释里的承诺 > 代码实现的事实**。只不过这一次，它出现在安全模块里。

### 2.10 数量级直觉：AK 的 256 位熵到底有多硬

"256 位随机，穷举不可行"这句话值得落到数字上，否则它只是口号。给一个最乐观的攻击者账本：

```text
- AK 搜索空间：62 个字符选 32 = 62^32 ≈ 2^190
- 攻击者拿到了你的 secret 前缀部分结构（只差 32 位 secret 全未知）→ 仍旧是 ~2^190
- 攻击速率：一台 PC GPU 的量级，SHA-256 约 10^6 次/s ≈ 2^20/s
- 一天尝试 ≈ 8.6×10^10 ≈ 2^36；一年 ≈ 2^44.7
- 纯暴力需要 ≈ 2^190 / 2^44.7 ≈ 2^145 年
- 宇宙年龄约 10^10 年 ≈ 2^33：2^145 是它的 2^112 倍
```

> **结论**：AK 的难度不是"很难猜"，是"物理上不可行"。这正是它敢用快哈希（SHA-256）而不用慢哈希的结构理由——**攻击者在数学上就没有足够的尝试机会，把每次校验变慢只是惩罚自己的正常流量**（呼应 2.1 的表）。对比之下，8 位十六进制的 `keyId`（`16^8≈2^32`≈43 亿）**可以被撞**，所以它只能当"定位标识"用，绝不能当认证秘密。

**再说为什么"AK 存哈希、密钥走环境变量"是配套的。**

**密钥放哪，决定泄露面有多大。** 环境变量的优势不是"隐蔽"，而是**把泄露时空最小化 + 把轮换成本降到不重新发版**：

| 存放位置 | 可见性 | 轮换成本 | 泄露面 | 适用 |
|---|---|---|---|---|
| 硬编码进代码 | 全仓库长期可见 | 要重发版 | 每个拿到源码/镜像的人 | **杜绝** |
| 写进并提交的配置文件 | 版本历史永久保留 | 要重发版 | 任何人能 `git diff` 出来 | **杜绝** |
| 环境变量 / 启动参数 | 仅运行进程可见 | 改环境 + 重启 | 能访问该主机的人 | 轻量可接受 |
| 配置中心 + KMS 解密 | 仅运行期解密 | 集中轮换、秒级生效 | 控制了 KMS 的人 | 生产推荐 |

**判据核心**：密钥一旦进代码或配置文件，它就**永久**进入了版本历史——**撤回权限 ≠ 撤回泄露**，曾经存在过的明文永远不会被删除。环境变量让"密钥"这一秒不存在于任何文件里，轮换也只是"改一个环境变量再重启"。

> **工程判据：判断密钥能不能进代码，只看一件事——"如果这个密钥明天泄露，我要不要重新发版才能换掉它？"** 要，就不该进代码；环境变量/配置中心把轮换成本从"重发版"降到"改配置 + 重启/热刷新"，所以密钥的默认居所是运行环境，不是仓库。

但也要诚实地划一条线：**环境变量只在"这台机可信"的前提下够用。** 一旦你的部署要共享给外部、要防同一主机的横向渗透，就得退到 KMS——那是把"运行期解密"这一步也收进受控边界。**判据不变量是"最小泄露面 + 最低轮换成本"，实现形态随暴露面升级。**

### 2.11 密钥的轮转与吊销：一个 Key 活多久

本讲讲透了"怎么校验一把 Key"，但没回答一个更基本的问题：**一把 Key 该活多久，以及它怎么死。** 而"怎么死"有两种，方向恰好相反。

<img class="mermaid-svg" src="/zh/book-assets/diag-0165.svg" alt="本讲讲透了&quot;怎么校验一把 Key&quot;，但没回答一个更基本的问题：一把 Key 该活多久，以及它怎么死。 而&quot;怎么死&quot;有两种，方向恰好相反。" />

> **图 37-1**　一个 Key 的两种死法，以及它们对时间窗的相反要求。**这张图要给出的新结论是：轮转与吊销共用"时间"这个维度，但要求的窗口方向相反**——轮转要求旧 Key **再活一会儿**（调用方要时间换），吊销要求旧 Key **一秒都别活**（泄露的凭证要立刻死）。**只要数据模型里只有一个 `status` 字段，这两种死法就没法区分**，于是你只能二选一：要么让事故吊销也等一个窗口（危险），要么让计划轮转也立刻断（大面积 401）。

**"两种死法"在数据模型上的最小要求是三个字段**：一个状态、一个到期时刻、一个吊销时刻。状态告诉你"它现在算不算数"，两个时刻告诉你"它为什么不算数"以及"从哪一刻起不算数"。**缺了吊销时刻，你就答不出"这把 Key 是轮转掉的还是被吊销的"**——而这两个原因对应完全不同的处置：前者是正常运维，后者要去查入侵。

三个基座放在一起，这个模型的必要性差别很大：

| 维度 | A：`code-review-agent`（自部署单体） | B：千万 DAU 的多租户 SaaS 平台 | 由此分叉的设计决策 |
|---|---|---|---|
| 凭证数量 | 一把环境变量里的 token（`ApiAuthFilter` 的 `REVIEW_API_TOKEN`） | 每个租户若干把，随租户数线性增长 | A 不需要凭证表；B 必须有一张 Key 表 |
| 轮转由谁驱动 | 人（改环境变量 + 重启） | 定时任务（不能靠人记得） | A 可以"永不轮转"；B 必须有 `expires` 与轮转流水线 |
| 吊销的后果 | 改一次环境变量，全量失效 | 只失效一把，其余租户不受影响 | A 的吊销是"停机级"操作；B 必须是**逐 Key 的细粒度**操作 |
| 需要审计什么 | 谁在用（有没有人配错了） | 哪把 Key 何时到期、何时被吊销、被谁吊销 | B 需要吊销时刻与操作者，A 不需要 |

> **推演**：轮转在 B 基座上是**一条持续的生产流水线**而不是一次操作。设 1000 个租户、每租户 2 把在用 AK、轮转周期 90 天，则年在用 Key 数 = `1000 × 2 = 2000` 把，年轮转次数 = `2000 × 365 / 90 ≈ 8 111` 次 ≈ `22` 次/天（假设：1000 个租户、每租户 2 把在用 AK、轮转周期 90 天；基座值 `tf_access_key` 的 Key 字段模型与 `rate_limit_rpm` 默认 600 见 `token-factory-server/src/main/resources/db/migration/V1__init.sql:21-32`）。**结论不是"轮转很累"，而是"轮转必须自动化"**：每天 22 次双活切换，只要有一次靠人记得，就会留下一个永久有效的旧 Key。

### 2.12 工业界怎么做：密钥托管与最小可见性

工业界把"一个 Key 活多久"直接建模成**实体上的字段**，而不是流程里的约定。LiteLLM 的虚拟 Key 模型就是这样三行：

```text
    expires: str | datetime | None = None
```

`litellm/litellm/models/verification_token.py:23`

**`expires` 是 Key 自己的属性，不是"某张流程表里的一个日期"。** 这意味着"校验"这一步可以不查任何外部状态就知道该不该放行——这正是第 37 讲 §2.1 那条"网关每次调用都要校验一次"的性能前提被保住的写法。

```text
    auto_rotate: bool | None = False
```

`litellm/litellm/models/verification_token.py:60`

**注意默认值是 `False`。** 这是工业界一条很值得抄的口径：**自动轮转默认关，因为"自动换密钥"是会影响调用方的动作**——默认打开会让所有"没准备好双活期"的集成方在某天集体 401。默认关，把决定权交给使用方。

```text
class LiteLLM_DeletedVerificationToken(LiteLLM_VerificationToken):
```

`litellm/litellm/models/verification_token.py:69`

**吊销是"软删"，用一个继承自 Key 模型的子类留痕，而不是 `DELETE`。** 把这三行连起来读，一个 Key 的生命周期就有了五个状态：

<img class="mermaid-svg" src="/zh/book-assets/diag-0166.svg" alt="吊销是&quot;软删&quot;，用一个继承自 Key 模型的子类留痕，而不是 `DELETE`。 把这三行连起来读，一个 Key 的生命周期就有了五个状态：" />

> **图 37-2**　一个密钥从生成到销毁的五个状态，以及工业界给每个状态配的字段。**这张图的用法是把它当成一张"字段检查表"**：`expires` 管第 ③ 步、`auto_rotate` 管第 ③ 步由谁触发、软删子类管第 ⑤ 步。**五个状态里只有 ② 是"正常"，其余四个都需要一个字段来承载**——这解释了为什么"密钥管理"不是一个函数而是一张表。

**"最小可见性"是这一节的第二个关键词：托管系统自己也不该看见明文。** HashiCorp Vault 的 KV v2 引擎把密钥定义成一个**可版本化、可软删**的实体（该文档给出的核心语义是版本历史与删除标记，不是"加密存储"本身）——见 <https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2>。要和本讲的结论对上：**"能找回的密钥等于没加密"** 这句话（`V1__init.sql:19-20` 的注释逐字如此），在工业界的落地形态就是"版本 + 软删"，而不是"把明文加密后存进另一张表"。

**本项目的边界也要诚实标出来：** `tf_access_key` 的列里有 `status`（默认 `'ACTIVE'`），有 `last_used_at` 与 `created_at`，**但没有 `expires`，也没有 `revoked_at`**（`V1__init.sql:21-32`）；吊销走的是 `update tf_access_key set status = 'REVOKED' where id = ?`（`AccessKeyRepository.java:69-71`）——**在原来的行上把状态改写掉，不留吊销时刻**。所以本项目恰好落在图 37-2 的第 ④ 步"能吊销"，但缺了第 ③ 步与第 ⑤ 步的载体。

### 2.13 数量级直觉与搬到你自己系统：鉴权的验收清单

**"密钥管理"这件事可以数清楚。** 先数本项目的数据模型：

| 项 | 值 | 复算方式 |
|---|---|---|
| `AccessKeyRecord` 的组件数 | **10** | 数 record 头部的参数个数（`AccessKeyRecord.java:11-20`）：`id` / `keyId` / `keyHash` / `tenantId` / `tenantCode` / `name` / `status` / `rateLimitRpm` / `lastUsedAt` / `createdAt` |
| 其中"过期/吊销时刻"类的字段 | **0** | 同上，10 个组件里最接近的是 `lastUsedAt` 与 `createdAt`，**没有** `expiresAt` / `revokedAt` |
| `tf_access_key` 的列定义数 | **9** | 数 `CREATE TABLE tf_access_key (` 到 `);` 之间的列定义行（`V1__init.sql:21-32`） |
| `db/migration/` 下的迁移文件数 | **1** | `git ls-tree -r --name-only HEAD` 过滤 `db/migration/` —— 只有 `V1__init.sql` |

**"只有一个迁移文件"这条比它看起来重要**：它意味着**没有任何一期 schema 变更**。加一个 `expires_at` 就是第一个 `V2__` 迁移——而本书第 43 讲（配置中心与灰度）会说明白：**schema 变更和配置变更是两类不同代价的发布**。

再算一个本项目已经做对的量：

> **推演**：`touchLastUsed` 只在"距上次使用超过 60 秒"时才写那一行（`AccessKeyRepository.java:80-84` 的阈值与 `where ... (last_used_at is null or last_used_at < ?)`）。若某把 Key 稳定打满 `rate_limit_rpm = 600`（`V1__init.sql:28` 的默认值），则一分钟 600 次请求里只有第 1 次会落一次写 ⇒ 写放大 = `1 / 600 ≈ 0.17%`（假设：该 Key 每分钟稳定打满 600 次、每次请求都触发 `touchLastUsed`；基座值 `rate_limit_rpm` 默认 600 见 `token-factory-server/src/main/resources/db/migration/V1__init.sql:28`）。**同一个"记录最后使用时间"的功能，靠一个 60 秒阈值把写压力砍掉了三个数量级**——这就是"高频路径上的审计字段"该有的形态。

| 工业界 / 本项目做法 | 你自己系统里该问的问题 |
|---|---|
| LiteLLM 的 Key 带 `expires`（`verification_token.py:23`） | 你的 Key 有没有"到期"这个字段？没有的话，它靠什么退役？ |
| `auto_rotate` 默认 `False`（`verification_token.py:60`） | 自动轮转是默认开还是默认关？默认关的时候，谁负责轮转？ |
| 软删子类留吊销痕迹（`verification_token.py:69`） | 你的吊销是改状态还是删行？改完之后还剩什么证据？ |
| 本项目 `revoke` 只改 `status`、无时间戳（`AccessKeyRepository.java:69-71`） | "这把 Key 什么时候被吊销的"能不能查出来？查不出来，闲置凭证审计就没有基线。 |
| 本项目 `AccessKeyRecord` 10 个组件里没有过期类字段 | 你的凭证记录有哪些字段？把"到期/吊销时刻"漏掉，等于把生命周期交给流程去记。 |
| 本项目 `touchLastUsed` 带 60 秒阈值（`AccessKeyRepository.java:80-84`） | 你的"最后使用时间"是每请求都写吗？写放大算过没有？ |

**搬到你自己系统**，四步：

1. **给 Key 状态机补两个字段**：`expires_at` 与 `revoked_at`。**不要只加 `status`**——状态说不清"为什么不算数"。
2. **把双活期长度写成一条判据**，并同时写下两个失败模式："窗口太短"是调用方来不及换（大面积 401），"窗口太长"是旧 Key 一直能认证（等于没轮转）。
3. **把轮转做成定时任务**，并照 §2.11 的算式算出你的年轮转次数。**只要这个数 > 每年 12 次，就必须自动化**（人一年记 12 件事已经到极限了）。
4. **给"最后使用时间"这类高频审计字段加热阈值**，并把写放大算出来留档。**没有算过的写放大，迟早会以"这一行在排队等锁"的形式出现。**

**判据**：**鉴权的成熟度不看"校验得多严"，只看两件事——没配密钥时默认是拒绝，并且每把 Key 都能回答"它什么时候到期、什么时候被吊销"。** 第 37 讲前半段给的是第一件事的做法，后半段（本节）给的是第二件事的字段。

## 三、避坑清单

- [ ] **AK/Token 类凭证只在创建时返回一次明文，库里只存哈希。** 并且设计上要接受"无法找回，只能重新签发"。
- [ ] **机器凭证用快哈希（SHA-256），用户口令用慢哈希（bcrypt/argon2）。** 判据是"攻击者有没有足够的尝试机会"。
- [ ] **凭证生成必须用 `SecureRandom`。** `Random` 的种子可推。
- [ ] **比较秘密用 `MessageDigest.isEqual`，不要 `String.equals`，也不要自己手写（容易留下长度早退）。**
- [ ] **把"定位标识"（keyId）与"认证秘密"分离。** 日志只打前者。
- [ ] **未配置密钥时的默认行为必须是拒绝（fail-closed）**——除非你能论证这个端口不会被第三方访问到，并且必须留 WARN 痕迹。
- [ ] **区分 401（换凭证）与 403（找管理员）。** 状态码是调用方的处置说明。
- [ ] **拦截器的路径挂载要显式列举，默认分支必须是"拒绝"。** 特别是——**当你想放行 `/actuator/health` 时，先确认你项目里 actuator 到底暴露了哪些端点**（`management.endpoints.web.exposure.include`）。只放行 health 而默认放行 `/actuator/**` 是常见的组合漏洞。
- [ ] **越权过滤要下推到查询层。** 判据："删掉这行 filter 会导致越权吗？"会，就说明它不该是可遗忘的独立步骤。
- [ ] **记录 `lastUsedAt`。** 没有它，你无法安全地吊销闲置凭证。
- [ ] **别把"计划轮转"和"事故吊销"做成同一条路径。** 轮转要求旧 Key 再活一段双活期（调用方要时间换），吊销要求它立刻死；只在行上改一个 `status` 就没法区分这两种死法。**最小要求是三个字段：状态、到期时刻、吊销时刻。**（§2.11）
- [ ] **别把双活期当成一个"取中间值"的拍脑袋参数。** 窗口太短 = 调用方来不及换（大面积 401），窗口太长 = 旧 Key 一直能认证（等于没轮转）。**两个失败模式必须同时写下来，否则你只是在猜。**（§2.11）
- [ ] **别让凭证记录答不出"它什么时候到期、什么时候被吊销"。** 本项目的 `AccessKeyRecord` 有 10 个组件，最接近的两个是 `lastUsedAt` 与 `createdAt`——**没有 `expiresAt`，也没有 `revokedAt`**，而 `revoke` 只把 `status` 改成 `'REVOKED'`、不留时刻。**没有这两个字段，闲置凭证审计就没有基线。**（§2.13）

## 本讲小结

1. **机器凭证用快哈希，用户口令用慢哈希。** 判据是"攻击者有没有足够的尝试机会"——AK 是 256 位随机，慢哈希只会拖慢自己的每次调用。
2. **`tf_<keyId>_<secret>` 三段式把"定位"与"认证"分开。** 日志只打 `keyId`，永远不打密钥；`lastUsedAt` 让闲置凭证可被安全吊销。
3. **比较秘密必须恒定时间。** 用 `MessageDigest.isEqual`——它不做长度早退；自己手写极易留下 `if (a.length != b.length) return false;` 这个漏洞。
4. **fail-closed 的理由是"两个独立高概率事件相乘"**：漏配密钥的概率不低，公网扫描的概率是 100%。
5. **fail-open 不是绝对错误，但它依赖"端口不会被第三方访问"这个前提**，并且**必须留下可被监控查询的痕迹**——而不是一行会被淹没的 WARN。
6. **"白名单 + 默认放行"的结构看起来安全、实际是黑名单。** `ApiAuthFilter` 只显式处理了 `/actuator/health`，其余 actuator 端点全从默认分支溜过。
7. **越权过滤要成为接口契约的一部分。** 判据是"删掉它会不会导致越权"——会，它就不该是一行可遗忘的 `filter`。
