## 二、原理

### 2.1 PII 的三条落点：日志、存储、出网

先把"数据落在哪"这件事画清楚。**任何一份内容进入系统，它只有三条出口**：

<img class="mermaid-svg" src="/zh/book-assets/diag-0199.svg" alt="先把&quot;数据落在哪&quot;这件事画清楚。任何一份内容进入系统，它只有三条出口：" />

> **图 44-1**　本讲地图之二：PII 的三条落点与各自的"可见面"。三条里最难处理的是第三条——**前两条你删了就是删了，第三条删了也不代表对方删了**。而最容易漏的是第一条：日志有独立的保留策略、独立的访问权限、独立的副本数。

**落点一：日志。** 它的特殊性在于**它不是"存储系统"**，所以不参与任何数据盘点。它的三个特点是：

1. **可见面宽**：数据库要连库、要账号；日志要的只是一个能读 stdout 的权限。
2. **副本多**：本地的文件 + 采集 agent + 中心日志服务（往往还有索引热层 + 归档冷层），**一份内容在这里可能变成四份**。
3. **留存期不由你决定**：它由日志平台的保留策略决定，而那个策略通常是"全公司统一 30 天"，跟你这个服务的合规要求**没有任何关系**。

**落点二：存储。** 这一条看起来最好管——你有 `DELETE` 语句。但它有一个**极其容易漏的变体**：**系统自己产生的副本**。本项目就有一处：

```text
            String bak = "memory_store_bak_" + Instant.now().getEpochSecond();
            stmt.execute("CREATE TABLE " + bak + " AS SELECT * FROM memory_store");
```

`PgVectorMemoryStore.java:379-380`

**换嵌入模型时，维度对不上，代码会先 `CREATE TABLE memory_store_bak_<时间戳> AS SELECT * FROM memory_store`，把整张表复制一份再重建向量列。** 而 `memory_store` 里有一列 `content TEXT NOT NULL`——**原文**。

于是这个系统里存在一类**表名带时间戳的、不在建表清单里的、不在任何删除路径上的、也没有留存期的**表，每换一次模型就多一张。**"删干净了"这个证明，第一关就卡在"你根本不知道有几份副本"。**

有意思的是这段代码在正常路径上"没有什么错"——它甚至写了 WARN 日志说明备份位置（`:381-382`）。它的问题是**它没有被纳入数据治理的视野**：备份建了，没人删。

> **★ 判据：凡是代码里出现 `CREATE TABLE … AS SELECT`、`pg_dump`、`COPY TO`、导出到对象存储这类"制造副本"的动作，都必须同时回答一个问题——这份副本谁来删？答不出来，这个动作就是一个合规暗坑。**

**落点三：出网。** 这一条的特殊性在于**删不回来**。数据一旦发给了第三方模型供应商，你能控制的只剩"以后不再发"和"要求对方不留"，而后者是**合同问题不是代码问题**。

而这个项目在出网这件事上的默认值是**直连**：

```text
 *   <li>{@link #DIRECT}：强制直连（忽略系统代理）。<b>生产默认</b>——服务器在合规网络内直接出网，
```

`EgressMode.java:11`

注释把理由说得很清楚：本服务**不接管、不中继**，由上游的 AI Gateway（Envoy AI Gateway / LiteLLM Proxy）统一持有供应商 key、做限流/重试/计费/审计。这个设计在工程上是对的（第 37 讲讲过），但它有一个直接后果：

> **本服务不知道自己把数据发给了谁，因此也无法在服务内实现"某类数据不许出网"这条规则。它把合规边界外包给了网关，而代码里没有任何地方记录这个外包关系。**

更要紧的是，**出网路径不止一条**。除了走 `Egress` 抽象的两条（大模型、重排），还有第三条**自己实现代理**的：

```text

```

`application.yml:316`

这是 SCA 漏洞扫描访问 OSV（Google 托管的开源漏洞库）用的。它**没有走 `EgressMode` 抽象**，而是自己在 `OsvVulnSource` 里 `proxy(...)`（`OsvVulnSource.java:73-74`）。

> **★ 判据：合规面必须能"一处枚举"。任何一条绕开统一出站抽象的出网路径，都会让"我们只往哪几个地址发数据"这句话变成无法验证的断言。本项目三条出网路径里有一条是绕开的——这不是说它写错了，而是说你要么把它并进抽象，要么在文档里显式登记它。**

### 2.2 脱敏的三种时机：早、中、晚，代价差一个数量级

知道落在哪之后，下一个问题是**在哪一步把它变干净**。这里有一个必须记住的排序：**脱敏越晚，代价越大，而且可选项越少。**

**时机一：采集之前（不采集）。** 这是 OpenTelemetry 在 GenAI 语义约定里的默认取向。规范对输入输出消息属性的态度是明确的：

> OpenTelemetry 的 GenAI 语义约定把 `gen_ai.input.messages` / `gen_ai.output.messages` / `gen_ai.system_instructions` 三个属性**显式标注为"很可能含敏感信息"**，并在 span 文档里写明这些内容**默认不采集**，只有打开 opt-in 开关才采。

三个属性分别见语义约定注册表里的 `gen_ai.input.messages`、`gen_ai.output.messages`、`gen_ai.system_instructions` 三条。

那个 opt-in 开关是**有名字的、可审计的**——规范里给出的环境变量是 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`。**这一点值得单独记住**：把"要不要采"做成一个"有名字的配置项"，而不是"代码里某个 if"，意味着**这件事可以被审计**——你可以查这个环境变量在哪些环境里被打开了。

**时机二：序列化之前（结构还在，字段能被真正删掉）。** 规范给出的第三种模式是内容外置：

> 规范原文：`Store content externally and record references on the spans.`

也就是**span 上只留引用（一个 ID），内容放到受控的存储里**。这样脱敏/删除发生在那个受控存储上，而 trace 数据本身是干净的。**这是三条里唯一能同时满足"可观测"与"可删除"的做法**——也是生产推荐的做法。

时机为什么这么关键？规范里有一句：

> 脱敏钩子应当在内容**被序列化成 JSON 字符串之前**运行——此时结构还在，字段可以被真正删掉。

**这句话是本节的判据**：

> **★ 判据：按字符截断是"看起来脱敏了"，按字段删除才是脱敏。** 一条 JSON 被 `substring(0, 800)` 之后，你既不知道切掉了什么，也不知道剩下的半截里有没有身份证号——**它从"一段可能含 PII 的文本"变成了"一段可能含 PII 的、不完整的、无法解析的文本"，风险没降，可读性还变差了。**

本项目的实现正好踩在这一条的反面：

```text
    private static String truncate(String s, int max) {
        if (s == null) {
            return "null";
        }
        if (s.length() <= max) {
            return s;
        }
        return s.substring(0, max) + "...(已截断, 共" + s.length() + "字符, 完整内容请开 DEBUG)";
    }
```

`LoggingChatModelListener.java:220-228`

**按字符切。** 切完还在提示"完整内容请开 DEBUG"——**这句话本身就在告诉运维怎么拿到那 800 字符之外的东西**。

**时机三：查询之后（在应用层过滤）。** 这是最晚的一步，代价也最大：数据已经全文落库，你只是在读出来之后做一次替换。它有三个问题：① **原始数据还在**，删除权仍然无法满足；② **过滤规则和写入规则是两份代码**，必然漂移；③ 一旦有新读取方（报表、导出、对接），过滤就会被绕过。

三者对比如下：

| 时机 | 什么时候做 | 原始数据还在吗 | 新增读取方会自动受保护吗 |
|---|---|---|---|
| **采集前（不采集）** | 写入之前 | 不在 | 不适用（压根没写） |
| **序列化前（按字段删）** | 写入之前 | 不在 | 不适用 |
| 内容外置 + 引用 | 写入之前 | 在（受控存储里） | ✅ 拿到的只有引用 |
| **查询后（应用层过滤）** | 读出之后 | **在** | ❌ 每个读取方都要自己记得过滤 |

**规律很清楚：脱敏的位置越靠前，后面的所有读取方就自动安全；越靠后，每一层都要重新证明一次自己没漏。** 而"每一层都要重新证明"这件事，在系统规模上来之后**一定会有某一片漏掉**。

### 2.3 留存与删除：TTL、软删、级联删

#### 先说一个反直觉的事实：删除权的最难点不是 `DELETE`

把内容"删掉"在 SQL 里只需要一行。难的是 **"删掉"这个词在你的存储栈里根本不是一个单一动作**。一份数据从可见到彻底不存在，要经过至少五层：

<img class="mermaid-svg" src="/zh/book-assets/diag-0200.svg" alt="把内容&quot;删掉&quot;在 SQL 里只需要一行。难的是 &quot;删掉&quot;这个词在你的存储栈里根本不是一个单一动作。一份数据从可见到彻底不存在，要经过至少五层：" />

> **图 44-2**　本讲地图之三：`DELETE` 执行完只走完了第一层。后面四层里，**第二、三层由数据库自己收敛（靠 VACUUM）**，**第四、五层只能靠流程收敛**（备份的保留期、副本的同步延迟）。所以"删干净了"从来不是一个数据库问题，而是一个**跨系统的期限问题**。

这个阶梯直接决定了"删除权"的正确提法：**它不是"立刻不存在"，而是"在承诺的期限内不再可访问，并可举证"。** 承诺了什么期限、由谁触发、怎么证明——这才是要设计的东西。

#### 三类留存策略，代价完全不同

| 策略 | 做法 | 代价 | 适合谁 |
|---|---|---|---|
| **TTL 自动过期** | 存储层自带过期（Redis TTL / 分区表 drop / 定时任务） | 最低：不用写删除逻辑 | 有明确"过期即无用"语义的数据 |
| **软删 + 延迟物理删** | 先标记 `archived` 退出业务面，过一段再物理删 | 中：多一个状态，多一条清理线 | **会被引用/复用**的数据 |
| **手动删（接口触发）** | 有人调接口才删 | 高：依赖人记得 | 低频、有明确操作人的数据 |

本项目的经验数据（10 张表）：

- **走"软删 + 延迟物理删"的只有 1 张**：`experience_entry`（`candidate/active/archived/purged` 四态，180 天归档、再 90 天物理删）。选它的理由是**经验条目会被检索复用**——直接删会让"今天检索得到、明天检索不到"变成不可解释的行为。
- **走 TTL 直接过期的 1 张**：`resume_state`（24 小时）。
- **只有条数上限、没有时间维度的 1 张**：`review_history` 同一 `hkey` 只留最近 **30** 条（`PgReviewHistoryStore.java:26`）。

```text
    /** 同一存储键（repo#pr）最多保留的历史条数。 */
    static final int MAX_PER_KEY = 30;
```

`PgReviewHistoryStore.java:25-26`

**这条特别值得看**：它看起来"有治理"（不会无限增长），但它约束的是**条数**不是**时间**。一个半年没人动的 PR，它的 30 条历史**会一直留着**；而一个高频 PR 的 30 条可能只覆盖三天。**"有上限"和"有留存期"是两件事**——前者防的是容量爆炸，后者防的是合规超期。**把前者当成后者，是数据治理里最常见的自欺。**

#### 级联删：向量库的删除为什么贵

RAG 系统有一条别的系统没有的删除难点：**一份文档在向量库里是 N 条**（切块后每块一条向量）。所以删一份文档不是删一行，而是"按某个属性删一组"。

本项目对这件事的处理是**唯一做对的一处**，值得完整看一遍：

```text
    /**
     * 删除某团队的知识：清理元数据与已入库的 RAG 向量。
     */
    public void delete(String teamId, String id) throws Exception {
        String t = Teams.sanitize(teamId);
        metaStore.delete(t, id);
        knowledgeStore.deleteByMetadata(t, "kbId", id);
        log.info("[KB] 已删除团队 {} 的知识 {}（含 RAG 向量）", t, id);
    }
```

`KnowledgeIngestionService.java:81-89`

**两条删除，顺序是"先元数据、后向量"。** 这个顺序是刻意的：先删元数据，这份知识立刻从列表里消失、不再被检索到；再删向量（这是慢操作）。**如果反了，就会出现"列表里没有、但检索还能命中"的窗口** —— 一个用户以为删掉了、系统还能吐出来的状态，是合规上最不能接受的状态。

再看向量侧的实现：

```text
        String sql = "DELETE FROM memory_store WHERE team_id = ? AND metadata->>? = ?";
```

`PgVectorMemoryStore.java:542`

一行 SQL，但它有三个必须知道的代价：

**① 走不了索引。** `memory_store` 上一共建了四个索引：`idx_memory_agent(agent_type)`、`idx_memory_team(team_id)`、`idx_memory_tsv(search_vector)`、`idx_memory_embedding(vector)`。**没有任何一个建在 `metadata` 上**。所以 `metadata->>? = ?` 这个条件只能在取出的行上逐行求值——**删除是"按租户扫一遍再过滤"**，而 `team_id` 索引只能帮你缩小到"这个租户的全部向量"。

**② `->>` 是文本比较。** `jsonb ->> text` 返回的是 `text`。如果当初写进去的是数字（`"kbId": 123`），用字符串 `"123"` 去比**不匹配**——**删除静默地少删了**。而这段代码的日志会照常打印"已按团队 … 删除元数据 kbId=xxx 的向量 N 条"，**N 是 0 也不会报错**。

**③ 删除不释放空间。** PostgreSQL 的 MVCC 决定了 `DELETE` 只是**标记**，真正回收空间要等 `VACUUM`。所以"我执行了删除"和"空间不再占用"之间隔着一个不确定的时间窗——**如果你的合规报告里写的是"已删除"，而审计员查的是磁盘占用，这两件事会打架**。

> **★ 判据：向量库的删除必须能回答"删了几条、期望几条"。** 本项目打印的是"删除 N 条向量"，但没有打印"这份知识原本有几条"。**没有期望值的计数，等于没有校验** —— N=0 和 N=370 在日志里长得一样漂亮。

### 2.4 删除权：怎么证明"删干净了"

到现在为止我们说的都是"怎么删"。但删除权真正难的是**举证**——有人问你"那份数据删了吗"，你得拿出一份能经得起看的东西。

**一份可用的删除清单（deletion manifest）至少有五列：**

| 列 | 为什么必须有 |
|---|---|
| **落点** | 数据在哪一层（表 / 日志 / 备份 / 出网）——少一列就等于漏一层 |
| **定位谓词** | "删哪些行"的判据（`team_id = ? AND metadata->>kbId = ?`）。**这一列是删干净与删漏的分界线** |
| **期望条数** | 执行前先算一遍"应该删几条"。**没有这一列，删除就是盲删** |
| **实际条数** | 执行后回读。**`期望 == 实际` 才叫删干净** |
| **不可删的部分 + 理由** | 审计轨迹、备份快照这类**删不掉或不能删**的，必须显式登记并写明期限 |

**第五列是本项目最需要的一列。** 因为按 2.1 的盘点，这个系统有 **5 张表没有任何删除路径**，其中 `trajectory_store` 里装的正是"模型看见过的全部内容"。它删不掉不是 bug，而是**被审计不变量有意锁住的**（见 2.5）。

对这类"删不掉"的数据，合规上只有三种合法出路：

1. **不写进去**（采集前脱敏）——最干净，但会牺牲可观测性；
2. **写进去但作为"不可识别"内容**（假名化：把主体标识换成不可逆的 ID，原文另存并单独管理生命周期）；
3. **写进去、按时限允许被引用**，并在协议/隐私声明里**明确写出来**（"为审计目的保留 N 天"）。

**三种都成立，唯一不成立的是第四种：既不脱敏、又不设期限、也不写进声明——然后假装它能删。**

还有一件很容易忘的事：**备份与只读副本**。你删了主库的行，但——

- 昨晚的全量备份里还有这份数据（**保留期 = 备份保留策略**）；
- WAL 归档里还有那条 `INSERT`（**保留期 = WAL 保留策略**）；
- 只读副本上，如果复制延迟或复制中断，那份数据可能**还在**。

所以删除权在工程上的正确形态是一个**期限矩阵**：

| 层 | 承诺期限 | 由谁实现 |
|---|---|---|
| 主库 | 立即（下一次查询不可见） | `DELETE` |
| 主库物理空间 | 由 `VACUUM`/自动清理收敛 | 数据库 |
| 只读副本 | 复制延迟量级（秒～分钟） | 复制机制 |
| 备份快照 | **备份保留期**（常见 7～30 天） | 备份策略 |
| 日志 | **日志平台保留期**（常见 7～30 天） | 日志平台 |
| 第三方（已出网） | **合同约定期限** | 采购/法务 |

> **★ 判据：删除权的交付物不是一段 `DELETE` 代码，而是一张"层 / 期限 / 责任人"的表。** 只要有一层答不出期限，那个期限就是"永远"。

**本项目在这张表里的实况是**：主库有两层（立即 + VACUUM）都能答；只读副本取决于部署形态（未验证）；备份与日志层**代码里没有任何约定**——它们完全在本服务的视野之外。

### 2.5 审计与删除权的正面冲突，以及唯一的解法

这是本讲最需要想清楚的一节。

审计要的是**完整性**：审查结论必须能追溯到"模型当时看见了什么"，否则一条误报无法复盘、一条漏报无法归因。本系统把这条要求写成了不变量：

```text
 *   <li><b>任何写入审查 LLM 的内容必须先登记事件</b>——"Model-visible means logged"；</li>
```

`ReviewEventLog.java:16`

而要让它真的可信，日志本身必须是**不可变的**：

```text
        // 防御性拷贝 + 包装为不可修改列表，保证 deepFreeze 语义
        this.events = Collections.unmodifiableList(new ArrayList<>(events));
```

`ReviewEventLog.java:27-28`

再加上接口层**没有 delete**（`TrajectoryStore.java:12-19`），三者合起来构成了一个**结构性的互斥**：

<img class="mermaid-svg" src="/zh/book-assets/diag-0201.svg" alt="再加上接口层没有 delete（`TrajectoryStore.java:12-19`），三者合起来构成了一个结构性的互斥：" />

> **图 44-3**　本讲地图之四：审计与删除权指向同一份数据、要求相反。**这不是"设计没做好"，而是一对真实的约束冲突**——你能选的只有"用哪种方式让它们共存"，不能选"让它们都完全满足"。而三条共存方案全部作用在**写入之前**。

**为什么三条出路全在写入之前？** 因为一旦写进了 append-only 的日志，"抹掉"这个动作在结构上就不存在了。于是只剩：

**出路一：写入前脱敏（最常用的那条）。** 轨迹里存的不是原文，而是**脱敏后的文本或引用**。它的代价是可观测性下降——第 42 讲的"漏斗日志"要的是真实内容，脱敏之后"为什么这条没被召回"就看不清了。**所以这条路必须配合一个"可回读的引用"**（内容外置，span/事件上只留 ID），也就是 2.2 里那个 `Store content externally and record references` 模式。

**出路二：假名化（pseudonymization）。** 主体的直接标识（邮箱、手机号、工号）在写入前被替换成**不可逆的稳定 ID**。轨迹里仍然是"某个人"，但那个 ID 无法反查到自然人。**注意"不可逆"必须是真的**——用一个固定 salt 的哈希、且 salt 也在你的库里的做法，只是把明文换了个写法。

**出路三：显式声明保留期与用途。** 承认"为了审计我保留 N 天"，并把它写进对外文档。这条路合法性取决于你所在法域和数据的性质，但**它至少是诚实的**——而"我们有一套删除流程"这句不能证伪的话，在出事时一分钱都不值。

> **★ 判据：区分"可被遗忘的数据"与"必须被记住的事实"。** 同一次审查里，**"某个人的代码内容"是可被遗忘的**（脱敏或外置），**"这次审查发生过、结论是什么、耗时多少"是必须被记住的**（审计）。把这两类**在同一张表、同一个 JSONB 里混着存**，就是本系统现在这个矛盾的结构性来源。**解法不是加一个删除接口，而是在写入时就把两类分开。**

**本项目现在的取舍**：审计优先，删除权在轨迹这一层**不成立**。这个取舍在"只服务内部团队"的阶段可以接受，但**它必须被显式写下来**——因为它是一条**已知的、有意的合规缺口**，而不是一个尚未发现的细节。

### 2.6 出网合规：zero-retention 与数据驻留

第三条落点（出网）有两个专有名词值得记住，因为它们是和供应商谈的前提条件。

**Zero data retention（零数据留存）。** 主流供应商都提供了这个选项：企业客户可以要求请求内容**不被用于训练**、并且**在短时间内（或不）留存**。OpenAI 的《Data usage》文档与 Anthropic 的留存说明页都给出了各自的留存期与"不出网/不留存"选项——这两份文档是你在评审会上唯一能引的一手依据，**不要用二手转述**（转述会把"默认 30 天"和"可以申请 0 天"讲混）。

**数据驻留（data residency）。** 数据存在哪个法域。它的工程含义很具体：**同一个请求，走不同 region 的网关，数据就落在不同法域**。而这个项目里，"走哪个网关"是由一个**配置项**决定的：

```text
      mode: ${EGRESS_LLM_MODE:direct}
```

`application.yml:256`

于是出现一个很典型的错位：**数据驻留是一个合规属性，而它的开关是一个运维参数。** 改这个参数的人（运维）看到的是"出口模式"，看不到"这次改动让数据从 A 法域挪到了 B 法域"。

> **★ 判据：凡是会改变数据法域或数据留存期的配置项，它的注释里必须写明"这一项影响合规属性"。** 本项目 `egress` 段的注释（`application.yml:244-253`）解释了三种模式的网络语义，**一个字都没提合规**。这不是错，但它让"合规边界"这件事在配置层是不可见的。

### 2.7 搬到你自己系统：从一张表开始

先看 A/B 两个基座的差异。**B 基座的所有数字都是推演值**——它们不是任何真实系统的实测，只是为了让"规模变大之后哪一条先崩"这条推理链有具体形状。

| 维度 | A：`code-review-agent` | B：千万 DAU 的 C 端产品（推演） | 由此分叉的设计决策 |
|---|---|---|---|
| **数据主体** | 开发者（内部） | **终端消费者** | A 可以接受"轨迹不删"，B 不行——**主体权利的性质不同** |
| **PII 密度** | 代码（可能含硬编码的凭据、测试数据） | 姓名/手机/地址/对话内容 | B 必须做**写入前**脱敏，A 可以靠"不落库"缓解 |
| **日志量** | 单实例，人工可读 | **推演**：10³ QPS × 2 KB/条 ≈ 2 MB/s（假设：每请求 1 条含内容日志；基座值见 `LoggingChatModelRenderer` 的 800 字符截断） | B 的日志内容**不能默认落全文**，只能落引用 |
| **表数量** | 10 张（实测） | **推演**：单体拆 8 服务后 80～200 张 | B 必须有**机器可读的数据资产目录**，人工盘点必然漏 |
| **删除触发方** | 团队内部（口头） | **用户自助 + 法务工单** | B 必须把删除做成**带审计的端点**，且要能异步执行（删不是瞬时的） |
| **备份保留** | 代码里无约定 | **推演**：7～30 天（多数团队默认值） | B 的删除承诺必须先和备份保留期对齐，否则承诺即违约 |
| **第三方** | 1 个模型供应商（经网关） | 模型 + 短信 + 推送 + 埋点 + 客服系统 | B 的"出网清单"本身就是一个必须维护的资产 |

**注意最后一行**：B 基座的难点不是"更难删"，而是 **"有几处在存你都不知道"**。所以落地顺序必须是"先盘点、再治理"，而不是反过来。

**落地步骤（4 步，全部可以在当前系统上做完）：**

1. **盘三张清单。** ① **落点清单**：所有会存内容的地方（表 / 日志 / 备份 / 出网 / 系统自建副本）；② **留存清单**：每一处的 TTL 与它的来源（配置项 / 平台策略 / 合同）；③ **删除清单**：每一处"删得掉吗、用什么删、删完怎么验"。**这三张清单就是合规的起点，不需要任何新基础设施。**
2. **给每一处补一个"期望条数"。** 把 `DELETE` 调用改成"先 `COUNT` 再 `DELETE` 再比对"，不匹配就 WARN。这一步不改任何业务行为，只让**删漏变得可见**。
3. **把"不该写进去的"挡在写入之前。** 优先处理日志：给 `LoggingChatModelListener` 的 INFO 分支改成**只打结构与长度**（消息数、字符数、角色序列），全文只在显式的 opt-in 开关下打。**这一处改动就能消掉本系统最大的一条 PII 落点。**
4. **把"删不掉"的那部分写成声明。** 在 README 里加一节：哪些数据、为什么保留、保留多久、依据是什么。**"有意保留"和"忘了删"在出事时的性质完全不同**——前者是决策，后者是失职。

> **★ 判据：合规改造完成的标志不是"加了一个删除接口"，而是"有人问『这份数据在哪几处』时，答案能在一张表里查到，且表里的每一行都能指出它的期限与责任人"。**

## 三、避坑清单

- [ ] **盘点数据资产时，先问"除了数据库还有哪些地方存内容"**。日志、备份、缓存、消息队列、导出文件、**代码自建的副本表**——本项目就有 `memory_store_bak_<epoch>` 这一类（`PgVectorMemoryStore.java:380`）。
- [ ] **表名与内容不一致的表要单独标出来**。`knowledge_meta.content` 是原文，`memory_store.content` 是原文——按表名分类必然把它们归错。
- [ ] **凡是 `CREATE TABLE … AS SELECT` / `pg_dump` / `COPY TO` 的动作，必须同时回答"这份副本谁来删"**。答不出来就是合规暗坑。
- [ ] **内容日志不能默认打在 INFO**。本项目 `LoggingChatModelListener.java:75` 用 INFO 打 800 字符 prompt——**这一处是全网最大的 PII 落点**。
- [ ] **截断不是脱敏**。`substring(0, 800)` 切出的是"不完整的原文"，不是"合规的内容"；而且它把 PII 从"可解析"变成"不可解析"，反而更难治理。
- [ ] **"完整内容请开 DEBUG"这类提示语要审一遍**。它等于在教运维怎么拿到全量数据。
- [ ] **脱敏要做在"序列化之前"**（OTel GenAI 语义约定的取向），这样结构还在、字段能被真正删掉；采集开关要**有名字、可审计**（如 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`）。
- [ ] **优先选"内容外置 + span 上只留引用"**（规范原文：`Store content externally and record references on the spans`）。它是可观测与可删除之间唯一的交集。
- [ ] **"有上限"不等于"有留存期"**。本项目 `review_history` 有 `MAX_PER_KEY = 30`（按 key 保留条数），但它防的是容量爆炸，不防合规超期——低频 key 的历史会无限期留着。
- [ ] **删除顺序：先删元数据、后删向量**。反了会出现"列表里没有、检索还能命中"的窗口——一个用户以为删了、系统还能吐出来的状态。
- [ ] **向量删除必须给"期望条数"**。本项目打印"删除 N 条"却不打印"原本几条"⇒ **N=0 和 N=370 长得一样**。
- [ ] **`metadata->>?` 是文本比较，且走不了索引**。类型不一致会静默少删；没有表达式索引就会按租户扫一遍。两件事都要在删除脚本里显式处理。
- [ ] **`DELETE` 不释放磁盘空间**。承诺"已删除"时要分清是"应用不可见"还是"空间已回收"——后者要等 `VACUUM`。
- [ ] **删除权要覆盖只读副本与备份**，否则承诺期限就是假的。备份保留期（常见 7～30 天）必须和对外承诺的删除期限对齐。
- [ ] **"层 / 期限 / 责任人"三列缺一不可**。只要有一层答不出期限，那个期限就是"永远"。
- [ ] **不要把"可被遗忘的"和"必须被记住的"混在同一个 JSONB 里**。本项目的 `trajectory_store.events` 同时装了"个人内容"与"审计事实"——**这是审计与删除权冲突的结构性来源**。
- [ ] **审计的 append-only 是有意设计，不要试图给它加 delete**。正确做法是写入前分层（脱敏 / 假名化 / 声明保留期），不是事后抹除。
- [ ] **"有意保留"必须显式写进文档**。忘删是失职，有理由地保留是决策——**两者的性质完全不同，但在代码里长得一模一样**。
- [ ] **合规面要能"一处枚举"**。本项目三条出网路径里，OSV 那条绕开了 `EgressMode` 抽象（`application.yml:316` 自己的 `proxy-host`）——绕开的路径会让"我们只往哪发数据"变成无法验证的断言。
- [ ] **会改变数据法域或留存期的配置项，注释里必须写明"这一项影响合规属性"**。`egress` 段现在只解释了网络语义。
- [ ] **"零留存"这类承诺要和供应商的书面条款对齐**，引用只用一手文档（供应商的 data-usage / privacy 页），不用二手转述。
- [ ] **删除权的交付物是一张表，不是一段代码**。给不出那张表，就不叫"支持删除权"。

## 四、动手任务

1. **盘出你自己的"三张清单"**。用一段脚本把系统里所有会落库的内容点找出来（本项目可用 `grep -rn "CREATE TABLE IF NOT EXISTS" src/main/java`，实测命中 10 张表），然后手工补三列：**每张表哪一列存原文 / 这列留多久 / 怎么删**。

   ```bash
   # 思路：先穷举建表语句拿到表名，再逐表检索是否存在 DELETE FROM <表名>
   # 期望产出：10 行，其中 5 行"怎么删"一栏是空的
   ```

   **那 5 行就是你的合规缺口清单**——它比任何合规检查表都准，因为它是从代码里数出来的。

2. **让"删漏"变得可见**。挑本项目那唯一做对的级联删（`KnowledgeIngestionService.delete`）做一次加固：在 `deleteByMetadata` 前后各加一次计数，日志里同时打出**期望条数与实际条数**，不一致就 WARN。跑一次单测：造一份知识 + 3 个向量块，调用删除，确认日志里出现 `期望 3 / 实际 3`；再把 `metadata` 里的 `kbId` 改成数字类型重跑，**观察它变成"期望 3 / 实际 0"** —— 这一步会亲手复现 2.3 里那个"静默少删"。

3. **给日志脱敏，并量出前后差异**。把 `LoggingChatModelListener` 的 INFO 分支从"打前 800 字符"改成"只打结构"（消息数 + 各消息角色 + 各消息字符数），跑一次真实审查，把前后两次日志的**字符数**记下来。**这个差值就是这次改动消掉的 PII 面积**——把它写进 README，这样下一个人问"日志里有没有敏感内容"时，答案是一个数字而不是一句"应该没有吧"。

## 本讲小结

1. **合规的四个问题**：它落在哪几处、每处留多久、要删的时候删得掉吗、删完之后凭什么证明。四个都要能答，缺一个就只是"看起来做了"。
2. **PII 的三条落点里，日志最容易漏**——它不在"数据库"这个心智模型里，所以不参与数据盘点；但它副本最多、权限最宽、留存期还由别人定。
3. **最容易漏的第二类是"系统自建的副本"**。本项目换嵌入模型时会 `CREATE TABLE memory_store_bak_<epoch> AS SELECT * FROM memory_store`（`PgVectorMemoryStore.java:380`）——**带原文、带时间戳、不在建表清单、不在任何删除路径上**。
4. **表名与内容会不一致**。`knowledge_meta` 里有原文 `content TEXT`（`PgDb.java:180`），`memory_store` 里也有（`PgVectorMemoryStore.java:360`）。**按表名做分类，必然漏。**
5. **脱敏越早越好，三条时机差一个数量级**：采集前（不采集）> 序列化前（按字段删）> 内容外置（只留引用）> 查询后（应用层过滤，每个读取方都要自己记得）。**按字符截断不是脱敏**——它把 PII 从"可解析"变成"不可解析"，风险没降。
6. **`DELETE` 只是五层里的第一层**：后面还有页上旧版本（等 VACUUM）、索引项、备份快照、只读副本。所以"删干净了"从来不是数据库问题，而是**跨系统的期限问题**。
7. **"有上限"≠"有留存期"**。本项目的 `review_history` 有"每 key 30 条"的上限，但低频 key 的历史会无限期留着——**前者防容量爆炸，后者防合规超期**。
8. **级联删的顺序是"先元数据、后向量"**。反了会留下"列表里没有、检索还能命中"的窗口，而这正是合规上最不能接受的状态。
9. **向量删除有两个静默风险**：`metadata->>?` 是文本比较（类型不符就少删）、`metadata` 上没有任何索引（删除是扫一遍）。而代码打印的是"删除 N 条"——**没有期望值的计数等于没有校验**。
10. **删除权的交付物是一张"层 / 期限 / 责任人"的表**，不是一段代码。本项目主库两层能答，备份与日志层**代码里没有任何约定**。
11. **审计与删除权在结构上互斥**：`Model-visible means logged`（`ReviewEventLog.java:16`）+ append-only + `TrajectoryStore` 无 delete，三者合起来让"抹除"这个动作在轨迹层不存在。**出路全部在写入之前**（脱敏 / 假名化 / 声明保留期），不在事后抹除。
12. **本项目的取舍是"审计优先，轨迹层不成立删除权"**。这个取舍可以接受，但**必须被显式写下来**——因为它是一条**有意的合规缺口**，而不是一个尚未发现的细节。
13. **合规面必须能"一处枚举"**。三条出网路径里有一条绕开了统一抽象（`application.yml:316`），绕开的那条会让"我们只往哪几个地址发数据"变成无法验证的断言。
14. **落地的第一步不是加接口，是盘三张清单**（落点 / 留存 / 删除）。这三张清单不需要任何新基础设施，而它们能立刻告诉你：**哪几行是空的**——那几行就是你现在真实存在的缺口。
