## 一、痛点

网关上线第二个月的一个下午，`token-factory` 所在的机器磁盘满了。数据库写不进去，网关**整体不可用**。

我的第一反应是好事：**降级生效了。** `code-review-agent` 里的 `ModelGateway` 检测到工厂不可用，自动切到直连上游——**审查服务一点没停。**

一个小时后工厂恢复。我去看账单，愣住了：

> 那一个小时的调用量，是 **0**。

不是"少"，是 **0**。因为所有调用都走了直连，**网关压根不知道发生过这些调用**。

我当时的处置是"手动补一下"：翻日志、数条数、估算 token。折腾了两个小时，最后在账单上补了一个**估出来的**数——然后我在心里把它标成了"不可信"。

**这笔账从此永远是脏的。** 后来财务再问"这两个月花了多少"，我给出的答案里总有一块是"大约"。

这次事故之后我做了一件事，**这件事成为了 `token-factory` 的一条硬约束**：

> **降级可以有，但账不能丢。**

## 二、原理

### 2.1 降级天然会绕过一个计费点

先把机制讲清楚。正常情况下，钱是这样被记下来的：


<img class="mermaid-svg" src="/zh/book-assets/diag-0121.svg" alt="先把机制讲清楚。正常情况下，钱是这样被记下来的：" />


> **图 33-1**　正常路径。**钱是在中间层被记下来的**——这决定了中间层一旦被绕过，账就一定有缺口。

网关挂了之后，调用变成：


<img class="mermaid-svg" src="/zh/book-assets/diag-0122.svg" alt="网关挂了之后，调用变成：" />


> **图 33-2**　降级路径绕过的**不是"一个服务"，而是"一个计量点"**。这是所有"计费放在中间层"的架构的固有代价——只要中间层可以被绕过，账就一定有缺口。所以补报不是锦上添花，**它必须是降级方案的组成部分**。

**降级路径绕过的不是"一个服务"，而是"一个计量点"。** 这是所有"计费在中间层"的架构的固有代价——只要中间层可以被绕过，账就一定有缺口。

所以补报不是一个"锦上添花的功能"，它**必须是降级方案的组成部分**。README 里把它写成了三条设计约束：

> 1. 补报是**一等公民接口**（`POST /v1/usage/report`），不是运维手动修数据的后门；
> 2. 补报失败**不影响业务**——工厂已经不可用了，再让补报打断业务就是把「一个服务挂了」放大成「两个服务都挂了」；
> 3. 上游没返回 `usage` 时按字符数估算并打 `estimated=true`——宁可要一个带标记的估算值，也不要账上记 0（0 会被当成「没花钱」）。

三条各针对一种失败模式：

| 约束 | 防的是 |
|---|---|
| **① 一等公民接口** | 防止补报变成"只有 DBA 会用的 SQL 脚本"——那种修补**不可审计、不可重复、没人知道数据是否完整** |
| **② 补报失败不影响业务** | 防止**故障传染**：网关已经挂了，补报再挂一次就变成了两个故障 |
| **③ 估算 + 标记** | 防止**静默的 0**：0 会被读成"没花钱"，而标记过的估算值至少能被识别出来 |

**第 ③ 条是这一讲的核心思想，请记住它——因为代码在三个地方违反了它。**

### 2.2 补报用装饰器实现，且只包"直连"这一条路

```java
/**
 * 用量补报装饰器：包在「直连上游」的供应商外面，调用成功后把用量补报回 Token 工厂。
 *
 * <p><b>只装饰直连供应商，不装饰工厂供应商</b>：走工厂的调用工厂自己会计量，
 * 再补报一次就是重复计费。装配层负责区分。
 */
public class UsageReportingProvider implements ModelProvider {

    private final UsageAwareModelProvider delegate;
    private final UsageReporter reporter;
    private final String alias;
    private final String upstreamModel;

    @Override
    public String chat(String prompt) throws Exception {
        long t0 = System.currentTimeMillis();
        try {
            UsageAwareModelProvider.ChatOutcome outcome = delegate.chatWithUsage(prompt);
            long latency = System.currentTimeMillis() - t0;
            if (outcome.hasUsage()) {
                reporter.reportSuccess(TokenFactoryChatProvider.currentTraceId(), alias, name(),
                        upstreamModel, outcome.promptTokensOrZero(), outcome.completionTokensOrZero(),
                        latency, false);
            } else {
                int estimatedIn = estimate(prompt);
                int estimatedOut = estimate(outcome.text());
                reporter.reportSuccess(TokenFactoryChatProvider.currentTraceId(), alias, name(),
                        upstreamModel, estimatedIn, estimatedOut, latency, true);
            }
            return outcome.text();
        } catch (Exception e) {
            reporter.reportFailure(TokenFactoryChatProvider.currentTraceId(), alias, name(),
                    upstreamModel, System.currentTimeMillis() - t0, errorCodeOf(e));
            throw e;
        }
    }
```

**装饰器是这里唯一正确的选择。** 如果改成"在业务代码里手动调 reporter"，你会得到 N 个调用点，其中总有几处忘记——**而"忘了补报"不会有任何症状**。

用装饰器的效果是：**只要这条链路被走，就必然补报**，业务方不需要知道补报存在。

三个实现细节值得学：

**① `hasUsage()` 分支：有真实 usage 用真实值，没有则估算并打标记。**

```java
static int estimate(String text) {
    if (text == null || text.isEmpty()) {
        return 0;
    }
    return Math.max(1, (int) Math.ceil(text.length() / CHARS_PER_TOKEN));
}
```

**② 失败也要报。**

```java
} catch (Exception e) {
    reporter.reportFailure(TokenFactoryChatProvider.currentTraceId(), alias, name(),
            upstreamModel, System.currentTimeMillis() - t0, errorCodeOf(e));
    throw e;
}
```

注意 `throw e` —— **补报之后原样抛出。** 装饰器不能把异常吞掉（否则降级路径上的失败会被静默），也不能包装成别的异常类型（否则上层按类型做的分支判断会失效）。**"记录了，然后原样继续"是装饰器的正确姿态。**

**③ 错误码取异常类简名。**

```java
/** 错误码取异常类简名：够短、够区分，且不会把可能含敏感信息的 message 发到工厂。 */
private static String errorCodeOf(Throwable e) {
    return e == null ? "UNKNOWN" : e.getClass().getSimpleName();
}
```

这行注释值得单独看：**"不会把可能含敏感信息的 message 发到工厂"**。异常 message 里可能带请求体片段、可能带 API Key（有些 SDK 的报错会把整个请求 URL 打进去）。**跨系统上报时，只发"分类"，不发"细节"。**

### 2.3 `NO_OP` 而不是 `null`

<img class="mermaid-svg" src="/zh/book-assets/diag-0123.svg" alt="### 2.3 `NO_OP` 而不是 `null`" />


> **图 33-3**　`UsageReporter` 接口形态。两个方法（成功/失败补报）+ 一个 `NO_OP` 空实现常量。**`NO_OP` 是这个接口最值得学的设计**：当"工厂未启用"或"关了补报"时，返回一个空实现而不是 `null`——调用方不需要判空，也就永远不会因为"忘了判空"而把审查主流程打断。

`TokenFactoryClientHolder.reporter()` 的注释解释了为什么：

```java
/**
 * 用量补报出口。工厂未启用、或显式关闭补报时返回 {@link UsageReporter#NO_OP}——
 * 调用方无需判空，避免出现「补报失败」的空指针打断审查主流程。
 */
public UsageReporter reporter() {
    if (!properties.usable() || !properties.isReportDirectUsage()) {
        return UsageReporter.NO_OP;
    }
    return new TokenFactoryUsageReporter(client(), properties.getAlias());
}
```

**"区分两种关闭"这个设计很重要**：`!usable()` 是"工厂压根没接"，`!isReportDirectUsage()` 是"接了但关掉了补报"。两者都返回 `NO_OP`，但对运维的含义不同——**前者是架构选择，后者是配置决定。**

而用 `NO_OP` 而不是 `null` 的价值，注释也说了：**避免空指针打断主流程。**

这条经验可以推广成一句判据：

> **如果"这个依赖不存在"是合法状态，就应该返回一个空实现，而不是 `null`。** 因为 `null` 会把"没配"变成一个必须在 N 个调用点处理的**运行时风险**，而 `NO_OP` 把它变成一个**设计上的合法分支**。

反例是很常见的：`if (reporter != null) reporter.report(...)` —— 这个写法在代码里出现几次，就有几处忘记判空的机会。

### 2.4 补报失败必须吞掉——但"降噪"藏了一个 bug

```java
/**
 * <p><b>补报失败绝不能影响业务</b>：这里所有异常都被吞掉并降级成日志。
 * 工厂已经不可用了（否则也不会走直连），此时再让补报失败把审查链路打断，
 * 等于把「一个服务挂了」放大成「两个服务都挂了」——典型的故障传染。
 *
 * <p><b>日志降噪</b>：连续失败超过阈值后从 WARN 降到 DEBUG。
 * 工厂长时间不可用时，逐条 WARN 会把真正有用的错误淹掉。
 */
public class TokenFactoryUsageReporter implements UsageReporter {

    /** 连续失败超过这个次数后，日志降级为 DEBUG。 */
    private static final int NOISY_AFTER = 10;

    private final AtomicLong consecutiveFailures = new AtomicLong();

    @Override
    public void reportSuccess(...) {
        try {
            ...
            client.reportUsage(request);
            consecutiveFailures.set(0);
        } catch (Exception e) {
            fail("补报用量失败", traceId, e);
        }
    }

    private void fail(String what, String traceId, Exception e) {
        long failures = consecutiveFailures.incrementAndGet();
        if (failures <= NOISY_AFTER) {
            log.warn("{}（traceId={}，连续第 {} 次）：{}", what, traceId, failures, e.getMessage());
        } else {
            log.debug("{}（traceId={}，连续第 {} 次）：{}", what, traceId, failures, e.getMessage());
        }
    }
}
```

**故障传染的推理链条完整且正确**：工厂挂 → 业务直连 → 直连成功但补报失败（因为工厂还挂着）→ 如果补报抛异常，审查就失败了 → **用户看到的是"审查服务挂了"，而真相是"一个我们本来就在绕过的服务挂了"。**

**"连续失败 10 次后降噪"也是个好想法**——工厂长时间不可用时，每个请求都打一条 WARN，日志会被刷爆，真正有用的错误被淹没。

**但这个降噪逻辑有一个真实的缺陷：成功即清零。**

```java
consecutiveFailures.set(0);   // 成功时重置为 0
```

考虑"工厂半死"的场景——**大约一半的补报成功、一半失败**（这是最典型的部分故障形态：超时、连接池耗尽、偶发 502）。那么失败计数的演化是：

```
失败 → failures=1  → WARN
成功 → failures=0
失败 → failures=1  → WARN
成功 → failures=0
失败 → failures=1  → WARN
...
```

**计数永远到不了 10，降噪永远不生效。** 结果是：**在最需要降噪的场景（故障持续但非全量）下，日志逐条 WARN 刷屏；而降噪只在"100% 全挂"时生效——那恰好是"日志量最大但持续时间最短"的场景。**

用一句话概括这个模式：

> **"连续失败计数 + 成功即清零"是一个只对"全挂"有效的降噪策略，对"半挂"完全失效。** 而生产环境里，"半挂"远比"全挂"常见——因为全挂会被熔断/摘流量快速处理掉，而半挂能持续几小时。

正确的形态应该是**两个计数**：一个是"连续失败"（用于判断是否已经恢复，可用于恢复日志），另一个是"滑动窗口内的失败率"（用于决定日志级别）：

```java
// 思路：降噪应该看失败率，而不是"严格连续"
// 比如：最近 60 秒内失败率 > 50% → 降为 DEBUG；否则 WARN
```

或者更简单：**按时间节流**（"每 60 秒最多打一条 WARN"）。它不需要任何状态机，且对全挂、半挂、抖动三种形态都有效。

### 2.5 估算系数：注释里的"折中"不是折中

回到约束 ③。当上游没返回 `usage` 时（有些兼容端点、有些代理会吞掉 usage 字段），就要估算：

```java
/** 估算系数：英文约 4 字符/token，中文约 1.5 字符/token，取折中值。 */
private static final double CHARS_PER_TOKEN = 3.0d;
```

**注释说"英文约 4、中文约 1.5，取折中值"。但 3.0 不是 4 和 1.5 的任何一种标准折中：**

| 折中方式 | 结果 |
|---|---|
| 算术平均 `(4 + 1.5) / 2` | **2.75** |
| 调和平均 `2 × 4 × 1.5 / (4 + 1.5)` | **2.18** |
| 几何平均 `√(4 × 1.5)` | **2.45** |
| 代码里的值 | **3.0** |

3.0 比任何一种折中都**更接近英文的 4**。这意味着：**对中文内容，估算值会系统性偏低。**

把数字算一遍。假设一次调用：

- **输入**：一段 300 字的中文 prompt
- **真实** token 数 ≈ `300 / 1.5` = **200 token**
- **估算** token 数 = `ceil(300 / 3.0)` = **100 token**

**少算了 50%。**

- **输出**：一段 600 字的中文回应
- **真实** ≈ **400 token**；**估算** = `ceil(600 / 3.0)` = **200 token**
- 同样**少算 50%**

而 `code-review-agent` 恰好是一个**中文占绝对多数**的系统（中文 prompt、中文审阅意见、中文规范库）。所以在这条链路上：

> **所有走"估算"分支的补报数据，token 数大约是真实值的一半，金额也随之减半。**

**这就把约束 ③ 的目标反转了。** 约束 ③ 的原文是"宁可要一个带标记的估算值，也不要账上记 0（0 会被当成「没花钱」）"——目的是**避免严重低估**。而实现的结果是：**在一个确定会低估 50% 的场景里，选择了一个偏向"另一种语言"的系数。**

这不是"实现错误"，而是 **"注释里的推理"和"代码里的常量"没有对齐**：如果真的按注释做算术折中，应该是 2.75；如果考虑到这个系统中文为主，应该**小于 2**（因为中文是 1.5）。

**更根本的问题是"折中"这个思路本身。** 用一个全局常量去拟合两种差异巨大的语言，注定只能对一半场景准确。可选的更好做法：

1. **按内容自动判定**：数一下非 ASCII 字符占比，占比高就用中文系数，低就用英文系数。实现只要几行。
2. **要求上游补 usage**：`usage` 字段是 OpenAI 协议的一部分，缺失本身就是异常——可以把它当成降级信号记录下来。
3. **接受估算、但保留标记**：这正是 `estimated=true` 的用途。**关键是这个标记必须真的被使用**——对账时要能"把 estimated 的记录单独拉出来，标记为不可用于结算"。现在标记是打上了，但没有任何下游在消费它。

**数量级直觉：单笔微元误差，在百万次调用下怎么滚雪球。**

第 32 讲的账本单位是"微元"（1 元 = 1_000_000 微元），所以单笔有误差时，数字小到账户页面上根本看不出。但放大到月度量级，性质就变了：

```text
- 中英系数混用导致的系统性低估 ≈ 每百万输入 token 少记 0.5 元
- 月调用量：输入 token 5 亿 = 500 × 10^6
- 单月缺口 = (5×10^8 / 10^6) × 0.5 = 500 × 0.5 = 250 元
- 一年 = 3000 元 = 3×10^9 微元 的账面缺口
```

> **更致命的是它不互相抵消。** 随机误差在 N 次调用里按 √N 式摊平；而这里的低估是**系统性偏差**——每一次都往同一个方向偏，于是**线性累加**。一句话判别法：**把 N 次调用翻成 10N，缺口翻 10 倍就是系统性，只翻 √10 ≈ 3 倍就是随机。**

> **工程判据：一个"每笔都很小"的误差值不值得修，不要看单笔，看"单笔误差 × 年调用量"。** 算出来如果是年 3×10⁹ 微元（3000 元）级别，它就不是"可忽略误差"，而是**一条结构性缺陷**——这正好是约束③"宁可要带标记的估算值，也不要记 0"的反面：0 和系统性低估，都会让"没花钱"变成一整月的账面事实。

### 2.6 补报接口的信任边界

看服务端：

```java
/** 补报一条用量（业务方直连上游时）。可通过配置关闭。 */
@PostMapping("/report")
public Map<String, Object> report(@RequestBody(required = false) UsageReportRequest body,
                                  HttpServletRequest http) {
    if (!properties.isUsageReportEnabled()) {
        throw new ResponseStatusException(HttpStatus.FORBIDDEN,
                "服务端已关闭用量补报（token-factory.usage-report-enabled=false）");
    }
    ...
    UsageRecord record = new UsageRecord(
            principal.requestId(),
            body.traceId(),
            principal.tenantCode(),
            principal.keyId(),
            principal.appId(),
            body.alias(),
            body.providerCode(),
            body.upstreamModel(),
            body.promptTokens(),
            body.completionTokens(),
            body.promptTokens() + body.completionTokens(),
            0L, "CNY",
            body.latencyMs(), body.success(), body.errorCode(),
            body.estimationMode(),
            Instant.now());
    gateway.recordReported(principal, record);
    return Map.of("accepted", true, "traceId", body.traceId());
}
```

**这里有三层值得注意的设计，以及一个严重的缺陷。**

**先说做对的三层：**

**① 身份没有被伪造的可能。** `tenantCode` / `keyId` / `appId` 全部取自 `principal`（AK 解析出来的），**而不是请求体**。所以租户 A 无法把用量记到租户 B 头上。这是补报接口最关键的一条——**如果 tenantCode 从请求体取，整个多租户计量就废了。**

**② 可关闭。** `usage-report-enabled` 配置项。"补报"本身是一个高风险能力（下面会讲），能关掉它意味着出问题时有一个止血开关。

**③ 返回 `accepted` 而不是 `recorded`。**

```java
return Map.of("accepted", true, "traceId", body.traceId());
```

这个措辞很讲究：**`accepted` 是"我收到了"，不是"我记账了"。** 补报方不应该认为"返回 200 就等于账已入账"——因为落库是异步的语义（`MeteringService` 吞异常），而且补报方**事后很难验证**。

**然后说那个严重的缺陷：金额是 0。**

```java
            0L, "CNY",       // ← costMicros 硬编码为 0
```

**这个 0 不是估算值，是字面量。** 顺着链路往上查，会发现这个 0 是**必然**的，因为**没有任何一个地方能提供金额**：

| 环节 | 是否有金额字段 |
|---|---|
| 客户端 DTO `io.tokenfactory.client.dto.UsageReportRequest` | ✗ 没有（字段：traceId/alias/providerCode/upstreamModel/promptTokens/completionTokens/latencyMs/success/errorCode/estimationMode） |
| 服务端 DTO `io.tokenfactory.server.api.dto.UsageReportRequest` | ✗ 没有（同上 10 个字段） |
| `UsageController.report` 构造 `UsageRecord` | 硬编码 `0L, "CNY"` |
| `GatewayService.recordReported` | 直接落 `record.costMicros()`，**不重算** |

再看 `GatewayService.recordReported`：

```java
/** 补报一条用量（业务方直连上游的降级场景）。 */
public void recordReported(CallPrincipal principal, UsageRecord record) {
    metering.record(new UsageRecord(
            principal.requestId(), record.traceId(), principal.tenantCode(),
            principal.keyId(), principal.appId(), record.alias(),
            record.providerCode(), record.upstreamModel(),
            record.promptTokens(), record.completionTokens(),
            record.promptTokens() + record.completionTokens(),
            record.costMicros(), record.currency(), record.latencyMs(),
            record.success(), record.errorCode(), record.estimationMode(),
            record.occurredAt()));
}
```

**它只是把入参里的 `costMicros` 原样落库，没有任何"补算"逻辑。**

所以最终结果是：

> **补报回来的记录，有 `providerCode`、有 `upstreamModel`、有 token 数——但金额是 0。** 而 `providerCode` + `upstreamModel` + `token` **恰好是计价所需的全部输入**（第 32 讲的 `PricingEngine.price(providerCode, upstreamModel, usage)` 三个参数）。

**这意味着：补报接口具备了算出金额的全部信息，却没有算。**

而 `UsageController` 的构造器里**没有 `PricingService`**：

```java
public UsageController(GatewayService gateway, QuotaService quota, UsageRepository usage,
                       TokenFactoryProperties properties) {
```

**"少注入一个依赖" -> "金额恒为 0"。** 这是"接口设计缺一个参数"导致业务结果错误的最小案例。

**这个缺陷的严重性，直接冲击了本讲的核心目标。** 约束 ③ 说"宁可要一个带标记的估算值，也不要账上记 0（0 会被当成「没花钱」）"——而补报这条路的金额**就是 0**。于是：

| 维度 | 正常调用 | 补报调用 | 后果 |
|---|---|---|---|
| 请求数 | ✓ 记 | ✓ 记 | 调用量对了 |
| token | ✓ 真实/估算 | ✓ 真实/估算 | token 大致对了 |
| **金额** | ✓ 计价 | **✗ 恒为 0** | **账单缺口 == 补报的那些调用** |

**降级时"账不能丢"这个目标，只实现了一半：token 账保住了，金额账没保住。** 而财务看的正是金额。

修法有两种，取决于信任模型：

```java
// 修法一（推荐）：服务端按规则重算 —— 补报方只需提供"事实"，不需要提供"价格"
Money cost = pricing.price(body.providerCode(), body.upstreamModel(),
        new TokenUsage(body.promptTokens(), body.completionTokens()));
// 然后用 cost.micros() / cost.currency() 构造 UsageRecord

// 修法二：接受补报方传来的金额，但必须有交叉校验与审计
// —— 只有在"补报方持有价格权威"时才考虑，且要能事后发现异常金额
```

**修法一是明显更优的：价格是平台方的知识（第 2.3 节的 `PricingEngine`），不该由调用方提供。** 让调用方传金额，等于把"钱算得对不对"这个责任交给了一堆不受控的客户端。

### 2.7 补报数据是"自报"的——所以只能对账，不能结算

顺着上面的思路再往前推一步：**补报接口对整个请求体是无条件信任的。**

```java
body.promptTokens(), body.completionTokens(),        // 直接用
body.success(), body.errorCode(),                    // 直接用
body.estimationMode(),                               // 直接用
```

服务端没有任何校验：

- `promptTokens = 999_999_999` 会被原样接受并落库
- `success = true` 且 `errorCode = null` 是一条"成功记录"，没有任何交叉印证
- `estimationMode = false` 意味着"这是真实值"——而这**仅仅是补报方的声明**
- `occurredAt` 是 `Instant.now()`（服务端时间），**不是补报方声明的发生时间**

**所以补报接口的正确使用定位是"对账参考"，不是"计费结算依据"。**

这个定位必须显式化，否则会有人拿它去算钱。三种落地方式：

1. **在表里打一个来源标记**（`source = 'REPORTED'`），结算时排除或单独列示；
2. **对账任务交叉验证**：补报量的绝对值、补报失败率、与直连监控的吻合度——**补报量远大于直连监控量，就是有人在刷**；
3. **对超大 token 数设上限**（`Math.min(body.promptTokens(), MAX_PLAUSIBLE)`），至少把荒谬值挡在外面。

## 三、避坑清单

- [ ] **降级路径必须跟着一个补报点。** 判断标准："这次降级有没有绕过一个计费/统计点？"绕过了，就必须补。
- [ ] **补报要用装饰器包在降级链路上，而不是在业务代码里手动调。** 手动调必然有漏点，而漏点无症状。
- [ ] **补报失败必须吞掉，且原样抛出自异常（`throw e`）。** 不吞 → 故障传染；吞掉原异常 → 上层分支失效。
- [ ] **跨系统上报只发分类（异常类简名），不发 message。** message 可能含密钥、请求体片段。
- [ ] **"依赖不存在"是合法状态时，返回 `NO_OP` 而不是 `null`。** 避免 N 个调用点的判空。
- [ ] **降噪不要用"连续计数 + 成功即清零"。** 它对"半挂"完全失效——而半挂比全挂常见。用失败率窗口或时间节流。
- [ ] **估算系数必须与内容语言分布对齐，并且要算一遍误差方向。** 一个"折中"常量在单一语言为主的系统里必然系统性偏高或偏低。**算出来是 +50% 还是 -50%，决定这个功能是"有用"还是"有害"。**
- [ ] **补报的 tenant/key/app 必须取自认证身份，不能取自请求体。** 这是补报接口唯一不能妥协的一条。
- [ ] **补报要么服务端重算金额，要么显式声明"本记录不计入结算"。** 保留一个"金额字段但永远填 0"的中间态是最糟的——**它对账时看起来像"这些调用没花钱"。**
- [ ] **补报数据是自报的，要能区分来源。** 表里加 `source`，对账时能单独拉出来；对超大值设上限。
- [ ] **接口响应措辞要诚实：`accepted`（收到了）不是 `recorded`（已入账）。**

## 四、动手任务

> **目标**：亲手把"降级 → 直连 → 补报"这条链路跑通，并量化估算系数的误差。

**步骤 1：建立"账本基线"**

```bash
# 记录当前总额
curl -s "localhost:8090/v1/usage/summary" -H "Authorization: Bearer $AK"
```

记下 `totalCost` 与 `totalTokens`。

**步骤 2：切断工厂，制造一次"直连 + 补报"**

让 `code-review-agent` 指向一个**不存在的**工厂地址，触发直连降级：

```bash
export TOKEN_FACTORY_BASE_URL=http://127.0.0.1:9999   # 一个没有服务的端口
# 然后跑一次审查，观察日志里是否出现"直连"与"补报失败"
```

此时工厂挂掉，补报应当失败（这正是设计预期——**不能因为补报失败而中断审查**）。

**预期结果**：审查**正常完成**，日志出现 `补报用量失败（traceId=...，连续第 1 次）`。

**关键对照**：审查的结果与工厂正常时**应当无差别**。这就是"故障不传染"的验收标准。

**步骤 3：恢复工厂，量出估算误差**

现在通过**手工补报**接口，把第 2 步那次的用量补回来，并对照真实值：

```bash
# 用一段已知长度的中文 prompt 直接调上游（拿到真实 usage），再用补报接口报同一段内容
curl -X POST localhost:8090/v1/usage/report \
  -H "Authorization: Bearer $AK" -H 'Content-Type: application/json' \
  -d '{"traceId":"manual-test-1","alias":"default","providerCode":"deepseek",
       "upstreamModel":"deepseek-chat","promptTokens":200,"completionTokens":400,
       "latencyMs":1200,"success":true,"estimationMode":true}'
```

然后**按 `estimate()` 的公式手算一遍**同一段文本的估算值：

```
估算 token = ceil(字符数 / 3.0)
```

**预期结果**：对一段 300 字的**中文**文本：

| 量 | 值 |
|---|---|
| 真实 token（`使用上游返回的 usage`） | ≈ 200 |
| `estimate()` 结果 | `ceil(300 / 3.0)` = **100** |
| **误差** | **-50%** |

**关键对照**：换成一段 300 字符的**英文**文本再算一次（真实 ≈ 75 token，估算 `ceil(300/3.0)` = 100）→ **误差 +33%**。

**同一个常量，对中文低估 50%、对英文高估 33%。** 这就是"用全局折中值拟合两种语言"的真实代价。

**步骤 4：验证"补报金额恒为 0"**

```bash
# 补报之后，查这笔记录的金额
curl -s "localhost:8090/v1/usage/trace/manual-test-1" -H "Authorization: Bearer $AK"
```

**预期结果**：记录存在，`promptTokens` / `completionTokens` 都有值，但 **`costMicros = 0`**。

**关键对照**：把 `providerCode` 与 `upstreamModel` 拿去查价格规则：

```bash
curl -s "localhost:8090/api/admin/prices" -H "X-Admin-Key: $TF_ADMIN_KEY"
```

**如果这个 `providerCode + upstreamModel` 组合**有**价格规则，那这笔金额本可以算出来——它只是没被算。信息是齐的，计算没发生。**

**步骤 5：给补报补上服务端重算**

```bash
# 确认 UsageController 是否有 PricingService
grep -n "PricingService\|pricing" token-factory-server/src/main/java/io/tokenfactory/server/api/UsageController.java
```

**预期结果**：**无匹配。** 这就是根因。

修法：给 `UsageController` 注入 `PricingService`，把 `0L, "CNY"` 换成按规则算出的金额（注意：**如果规则也没配，仍然按第 32 讲的原则记 0**——但这一次是"有理由的 0"，而不是"结构性的 0"）。

## 本讲小结

1. **降级绕过的是"一个计量点"而不是"一个服务"。** 所以补报不是锦上添花，它是降级方案的组成部分。
2. **补报要用装饰器实现**——"只要这条链路被走就必然补报"，业务方不需要知道它存在。装饰器还要保证 `throw e`（记录后原样继续）。
3. **`NO_OP` 优于 `null`。** 当"依赖不存在"是合法状态时，让它成为一个设计分支，而不是 N 个判空的运行时风险。
4. **"连续失败计数 + 成功即清零"的降噪只对全挂有效，对半挂完全失效**——而半挂更常见。
5. **估算系数 3.0 在中文为主的系统里系统性低估约 50%。** 注释说是"折中"，但 3.0 连算术平均（2.75）都不是，它偏向英文的 4。**"折中常量 + 单一语言为主的系统" = 系统性偏差。**
6. **补报链路的金额恒为 0**：两端 DTO 都没有金额字段，`UsageController` 硬编码 `0L, "CNY"`，且没有注入 `PricingService` 去重算——**而 `providerCode + upstreamModel + token` 恰好是计价所需的全部输入。** "降级时账不能丢"只实现了 token 那一半。
7. **补报数据是"自报"的，只能用于对账，不能用于结算。** 必须在数据里保留来源标记，并对荒谬值设上限。

下一讲我们处理网关的"韧性三件套"：**限流、熔断、退避重试**——包括一个能让上游用一行响应头把你的线程睡满 24 小时的缺陷。
