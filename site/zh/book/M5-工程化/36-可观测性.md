## 一、痛点

有一次，一个业务方来找我：

> "为什么我从上周开始，审查意见里就没有'性能'类的问题了？"

我的第一反应是**看日志**。日志里一切正常：5 个 Agent 都在跑，`PerformanceAgent` 也执行了，返回 200。我再去看它的输出——**"0 条发现"**。

于是问题变成了："`PerformanceAgent` 是**没发现问题**，还是**没在运行**？"

我花了**三个小时**才回答完这个问题。因为：

- 日志里"Agent 执行成功"不代表"Agent 真的调了模型"（第 16 讲：`DeclarativeReviewAgent` 自己吞异常 → 报告里变"0 条发现"）；
- `TokenUsageRecorder` 里有 token 用量记录，但**没有一个端点能按 Agent 类型查**；
- 那个能按操作细分的聚合器（`AggregateTracer`）**确实在内存里累计了数据，但没有任何端点可以读它**。

最后我是**重启服务、加了临时日志**才定位到的。

**真相是：`PerformanceAgent` 的 token 用量从上周开始变成了 0——它的模型调用在某个环节被跳过了。而"性能意见消失"只是这个事实的下游症状。**

**这类问题的本质是：系统的"事实"存在，但没有"出口"。**

我这里说的"事实"包括：`AggregateTracer` 里的聚合计数、`TokenUsageRecorder` 里的用量缓冲、`CircuitBreaker` 里的连续失败数。**它们全都在内存里，全都在被写，但没有任何人能查到它们。**

**"被写进去"和"能被查到"之间，隔着一个端点。** 而那个端点往往是最容易被漏掉的一步——因为**埋点写在业务代码里（能感受到），端点写在 admin 层（容易忘）**。

## 二、原理

### 2.1 可观测性是三段链，缺一段就等于零

先把这件事拆开。一个"可观测"的能力，必须完整走完三段：

```
① 埋点（Instrumentation）     —— 在业务路径上记录事实
        ↓
② 出口（Exposure）            —— 把事实变成一个可查询的形态
        ↓
③ 消费（Consumption）         —— 有东西在读它：人、看板、告警规则
```

**三段是"与"的关系，不是"或"的关系。**

| 缺哪一段 | 现象 | 会被发现吗 |
|---|---|---|
| 缺 ① | 有端点但返回空 | 会被发现（"为什么是空的"） |
| **缺 ②** | **数据在内存里，但没人能查** | **不会被发现**（没有任何异常） |
| 缺 ③ | 端点能查，但没人看 | 不会被发现（直到出事） |

**第②段是最危险的缺口**，因为它**没有任何症状**：埋点代码执行了、内存里有数据、日志正常、端点返回 200——**只是没那个端点。**

而 `LlmHealthController` 的注释里，恰好留下了这个缺口的**真实历史记录**：

```java
/**
 * LLM 调用聚合指标（agent-kit {@link AggregateTracer}）：总次数/错误/输入输出 token/
 * 平均耗时/估算成本 + 按操作（agent 类型）细分。喂数方为 {@code LoggingChatModelListener}。
 *
 * <p>2026-09-08 落地：此前该聚合器只在内存累计、无任何端点可读（文档 8 节标注的
 * 「指标是死的」），现经本端点暴露，可对接 Prometheus exporter / 告警。
 */
@GetMapping("/trace")
public Map<String, Object> trace() {
    if (llmTracer == null) {
        return Map.of("status", "unavailable", "reason", "AggregateTracer 未装配");
    }
    return Map.of(
            "status", "UP",
            "total", llmTracer.snapshot(),
            "byOperation", llmTracer.byOperation());
}
```

**"此前该聚合器只在内存累计、无任何端点可读"** —— 这句注释是**这个项目里最诚实的一句话**。它承认了一件事：

> **埋点写了、数据有了、但"指标是死的"。**

而这个状态**持续了多久？** 注释里的日期是 `2026-09-08`，而 `AggregateTracer` 是 agent-kit 里的组件——**从"接上监听器"到"加上端点"，中间隔了相当一段时间。**

**这段时间里，"有没有 LLM 调用"这个最基本的问题，只能靠日志回答。** 而日志只能回答"有过"和"没有过"，不能回答"多少次"、"平均多久"、"哪个 Agent 最多"。

**"指标是死的"这个说法很精准——它不是说"没有数据"，而是说"数据活着（在内存里）但不产生任何可用的结论"。**

### 2.2 `@Autowired(required = false)` + `unavailable`：诚实报告

上面 `trace()` 端点里有一个值得单独学的设计：

```java
private final AggregateTracer llmTracer;

public LlmHealthController(ModelGateway gateway, TokenUsageRecorder usageRecorder,
                           @Autowired(required = false) AggregateTracer llmTracer) {
    this.gateway = gateway;
    this.usageRecorder = usageRecorder;
    this.llmTracer = llmTracer;
}

@GetMapping("/trace")
public Map<String, Object> trace() {
    if (llmTracer == null) {
        return Map.of("status", "unavailable", "reason", "AggregateTracer 未装配");
    }
    ...
}
```

```java
/** LLM 调用聚合器（监听器喂 span）；可能未装配（为 null 时 /trace 返回空指标）。 */
private final AggregateTracer llmTracer;
```

**三个动作，共同构成了"可选依赖"的正确姿势：**

1. **`@Autowired(required = false)`** —— 依赖缺失是**合法的启动状态**，不阻止应用起来；
2. **字段注释明确写了"可能未装配"** —— 后来者不会以为它是必选的；
3. **端点返回 `status: unavailable` + `reason`** —— **不是返回空对象，而是明确说"我没装"。**

**第 3 点是最关键的，也是最容易被做错的。** 对比两种写法：

```java
// 坏：返回空数据 —— 调用方无法区分"没数据"和"没装配"
return Map.of("total", Map.of(), "byOperation", Map.of());

// 好：明确说明原因
return Map.of("status", "unavailable", "reason", "AggregateTracer 未装配");
```

**"没数据"和"没装"是两个完全不同的事实，必须能区分。** 如果返回空对象，运维看到"total 是空的"会去查"为什么没有调用"；而真相是"这个功能压根没开"。

**"不可用"必须是一个显式状态，而不是"空值的语义推断"。** 这一条与第 29 讲（`RagEvaluator` 的 `NaN`）是同一种思想：**空值/NaN 会被误读，必须显式标记。**

### 2.3 健康端点的语义：`degraded` 的判据

```java
/** 全链路快照（供 k8s readinessProbe / Prometheus exporter 消费）。 */
@GetMapping("/health")
public Map<String, Object> health() {
    LlmGatewaySnapshot snap = gateway.snapshot();
    long totalProviders = snap.providers().size();
    long healthy = snap.providers().stream()
            .filter(p -> p.state() == com.codereview.agent.core.llm.CircuitBreakerState.CLOSED)
            .count();
    long open = snap.providers().stream()
            .filter(p -> p.state() == com.codereview.agent.core.llm.CircuitBreakerState.OPEN)
            .count();
    boolean degraded = totalProviders == 0 || healthy == 0;
    return Map.of(
            "status", degraded ? "DEGRADED" : "UP",
            "totalProviders", totalProviders,
            "healthy", healthy,
            "open", open,
            "totalFailures", snap.totalFailures(),
            "providers", snap.providers());
}
```

**`degraded = totalProviders == 0 || healthy == 0`** —— 注意这个判据：

| 场景 | `healthy` | `totalProviders` | `degraded` | 合理吗 |
|---|---|---|---|---|
| 全部健康 | = total | > 0 | false | ✓ |
| **3 个里 1 个 OPEN** | 2 | 3 | **false** | ✓ **还有冗余，不该报 DOWN** |
| 全部 OPEN | 0 | 3 | **true** | ✓ |
| **一个都没配** | 0 | **0** | **true** | ✓ **配错也是故障** |

**"部分 OPEN 仍然是 UP"是一个刻意的选择**：readinessProbe 的语义是"**这个实例还能不能提供服务**"。3 个供应商挂了 1 个，实例仍然能服务（第 07 讲的 failover 会切到健康的那个）——**这时候把实例踢出负载均衡，等于自己把可用容量砍掉三分之一。**

**"`totalProviders == 0` 也算 degraded"** 这一条也很重要：它覆盖的是"**配置完全没生效**"这种情况——比如配置文件没挂上、Provider 表是空的。**如果没有这个条件，一个"什么都没配"的实例会报 `UP`**（因为它"没有不健康的供应商"）。

**"空集合的 `allMatch` 恒为 true"是所有健康检查里最常见的陷阱**：

```java
// 坏：没有任何供应商时，这两个条件都是"满足"的
boolean healthy = providers.stream().allMatch(p -> p.isHealthy());   // 空集合 → true
boolean noOpen  = providers.stream().noneMatch(p -> p.isOpen());     // 空集合 → true
```

**空集合会让"全部合格"的检查通过。** 所以任何"全部 X"的判定都必须补一条"非空"：

```java
boolean degraded = totalProviders == 0 || healthy == 0;   // ← 前半句就是那条补丁
```

### 2.4 运维视图：把"配了但没生效"变成可见

`AdminHealthController` 的类注释说明了它存在的理由：

```java
/**
 * 运维视图：把「这家供应商现在是活的还是熔断了」暴露成一个能 curl 的端点。
 *
 * <p>SLA 可观测的最小闭环：上游挂了要能在秒级被发现，而不是等业务方来报。
 * 熔断状态是内存态，重启即丢失——所以这里同时给出「供应商配置状态」，
 * 便于区分「从没通过」还是「刚被打挂」。
 */
```

这段注释最后一句是**这一讲最实用的一条经验**：

> **熔断状态是内存态，重启即丢失——所以同时给出"配置状态"，便于区分「从没通过」还是「刚被打挂」。**

**两个状态在监控上看起来是一样的**（都是 `circuit = CLOSED`），但含义完全不同：

| 现象 | 含义 | 处置 |
|---|---|---|
| `circuit = CLOSED` + 有调用记录 | 从来没出过问题 | 什么都不用做 |
| `circuit = CLOSED` + **零调用记录** | **这台供应商从来没被路由到过** | **去查路由配置！** |

**"没有失败"和"没有使用"是两件完全不同的事，而它们的最直观表现都是"没有异常"。** 一个"从来没被路由到"的供应商，在监控上和一个"运行良好"的供应商完全一样——**这就是为什么必须同时暴露"配置状态"。**

而 `view()` 方法里有一个专门的字段：

```java
private Map<String, Object> view(ProviderRecord p) {
    CircuitBreaker breaker = null;
    for (CircuitBreaker b : breakers.all()) {
        if (b.providerCode().equals(p.code())) {
            breaker = b;
            break;
        }
    }
    boolean keyPresent = upstreams.get(p.code()) != null;
    return Map.of(
            "code", p.code(),
            "name", p.name(),
            "protocol", p.protocol(),
            "enabled", p.isEnabled(),
            "status", p.status(),
            "timeoutMs", p.timeoutMs(),
            "circuit", breaker == null ? "CLOSED" : breaker.state(),
            "consecutiveFailures", breaker == null ? 0 : breaker.consecutiveFailures(),
            "remainingOpenMillis", breaker == null ? 0L : breaker.remainingOpenMillis(),
            // 缺密钥的供应商会被路由跳过，这里显式暴露，避免「配了但没生效」的困惑
            "usable", p.isEnabled() && keyPresent);
}
```

**`usable = p.isEnabled() && keyPresent`** —— 这个字段就是"配了但没生效"的可见化。

类注释说明的场景是："配置里写了这个供应商，`enabled = true`，但对应的**上游密钥环境变量没配**（`apiKeyEnv` 指的那个变量不存在）"。这时候：

- `enabled = true`（配置看起来没问题）
- `circuit = CLOSED`（没有失败，因为**压根没被调用**）
- **`usable = false`（真相）**

**如果没有 `usable` 这个字段，这个故障只能通过"这个供应商从来没有调用记录"来推断**——而那需要你**先知道要找它**。

**"把判断条件算成字段暴露出来"是一个通用技巧**：不要暴露 `enabled` 和 `keyPresent` 让运维自己组合，直接把 `usable` 给他。**因为运维在凌晨 3 点不想做布尔代数。**

### 2.5 `remainingOpenMillis`：告警需要"剩余时间"

```java
"remainingOpenMillis", breaker == null ? 0L : breaker.remainingOpenMillis(),
```

**"熔断了"这个事实不足以让人做决策。** 需要的是：

- **剩余冷却还剩多久**（`remainingOpenMillis`）→ "快好了，先看看别的"
- **连续失败了几次**（`consecutiveFailures`）→ "刚触发，可能要人工介入"
- **最后一次失败是什么时候**（`lastFailureAtMillis`，`CircuitBreaker` 有这个字段）

**"状态 + 剩余时间 + 计数"三件套**才构成一个可决策的告警。只有状态的话，运维每次都要去翻日志算时间。

**这一条与第 34 讲的 `CircuitOpenException.remainingMillis()` 是同一个设计思想的两次落地**：异常里带剩余时间（给日志和调用方）、端点上带剩余时间（给监控）。

### 2.6 ★ 有现成 API 不用：手写的线性查找

`view()` 里这段代码值得单独看：

```java
CircuitBreaker breaker = null;
for (CircuitBreaker b : breakers.all()) {
    if (b.providerCode().equals(p.code())) {
        breaker = b;
        break;
    }
}
```

**这是 O(供应商数) 的线性查找，而对每个供应商都要做一次——所以整个 `providers()` 是 O(n²) 的。**

但真正的问题不是性能，而是：**`CircuitBreakerRegistry` 里明明有现成的方法。**

```java
public CircuitState stateOf(String providerCode) {
    CircuitBreaker breaker = breakers.get(providerCode);
    return breaker == null ? CircuitState.CLOSED : breaker.state();
}
```

`stateOf(code)` 是 `Map.get` —— **O(1)，而且它返回的默认值（`CLOSED`）恰好与手写循环里的 `breaker == null ? "CLOSED" : ...` 一致。**

**"有 API 不用，手写一遍等价逻辑"是一种典型的重复实现问题**，而它的真实代价不是性能，是**一致性风险**：

- 手写版本用 `Map` 的 `values()` 遍历 → 每个供应商都走一遍全部 breaker
- **如果哪天 `stateOf` 的默认值策略改了**（比如改成返回 `UNKNOWN`），手写这份**不会跟着变**

更值得说的是这段代码的存在本身就有一个信号意义：**作者写它的时候，可能不知道 `CircuitBreakerRegistry` 提供了 `stateOf`。** 而 `stateOf` 的存在恰好是为了"给健康检查用"（`RoutingEngine` 也用它：`strategy.order(candidates, breakers::stateOf)`）。

**这提示了一条实践**：一个"给外部查询用"的方法（`stateOf`），如果**没有在它该被用的地方被用**，说明它的命名或位置没有提示出用途。**方法名里带上使用场景**（比如 `stateForHealthCheck`）或者**在方法注释里写明调用方**，能显著降低这类重复实现的概率。

### 2.7 ★ `Map.of` 正好 10 个键

```java
return Map.of(
        "code", p.code(),
        "name", p.name(),
        "protocol", p.protocol(),
        "enabled", p.isEnabled(),
        "status", p.status(),
        "timeoutMs", p.timeoutMs(),
        "circuit", breaker == null ? "CLOSED" : breaker.state(),
        "consecutiveFailures", breaker == null ? 0 : breaker.consecutiveFailures(),
        "remainingOpenMillis", breaker == null ? 0L : breaker.remainingOpenMillis(),
        "usable", p.isEnabled() && keyPresent);
```

**数一下：`code` / `name` / `protocol` / `enabled` / `status` / `timeoutMs` / `circuit` / `consecutiveFailures` / `remainingOpenMillis` / `usable` —— 正好 10 个键。**

**`Map.of` 的固定重载最多只到 10 对键值。** 所以这段代码**卡在上限上**：再加任何一个字段（比如 `lastFailureAtMillis`），就**编译不过**，必须改成 `Map.ofEntries(...)`。

**这是"隐性天花板"的一个好例子**：

- **好消息**：它**编译期就失败**，不会静默降级（对比 `Map.of` 用 `Map.ofEntries` 之外的规避方式，或者用 `HashMap` 手动 put 就不会有这个保护）；
- **值得注意的**：一个"运维视图返回几个字段"的决定，**受到了 JDK API 签名数量的限制**。这在代码 review 时是看不出来的，只有当你想加第 11 个字段时，编译器会告诉你。

**如果这个视图预期会持续加字段（运维视图通常会），正确做法是主动换成一个 record：**

<img class="mermaid-svg" src="/zh/book-assets/diag-0113.svg" alt="如果这个视图预期会持续加字段（运维视图通常会），正确做法是主动换成一个 record：" />


**"用 `Map` 拼响应"在字段少、临时视图场景下很方便，但它有两个代价**：① `Map.of` 的 10 键上限；② **字段名没有编译期检查**（拼错 `"remainingOpenMillis"` 不会报错，只会让监控查不到）。**运维端点是"给机器消费"的，更适合强类型。**

### 2.8 ★ 三类"看不见的失败"

前面讲的都是"数据在但没有出口"。现在讲另一半：**根本没有被记录下来的失败。**

把三讲里的发现汇总一下，这个系统里有**三类失败不会产生任何可查询的记录**：

**第一类：额度拒绝不落库**（第 32 讲）。

```java
public GatewayResult complete(CallPrincipal principal, ChatRequest request) {
    List<QuotaDecision> decisions = quota.evaluate(principal.tenantCode());
    if (QuotaEvaluator.anyRejected(decisions)) {
        throw new QuotaExceededException(decisions);      // ← 在 try 之外，不落库
    }
    long startedAt = System.currentTimeMillis();
    try {
        ...
    } catch (RuntimeException e) {
        metering.record(UsageRecord.failure(...));
        throw e;
    }
}
```

**症状**：被拦的流量在监控上表现为"调用量下降"——**把攻击信号读成了健康信号。**

**第二类：计量落库失败只有一行 ERROR 日志**（第 32 讲）。

```java
public void record(UsageRecord record) {
    try {
        usage.insert(record);
    } catch (RuntimeException e) {
        // 计量失败不能让业务调用失败，但必须留痕——丢一条用量就等于丢一笔钱
        log.error("用量落库失败（业务调用已成功，需人工补录）：traceId={} provider={} 原因={}",
                record.traceId(), record.providerCode(), e.getMessage(), e);
    }
}
```

**"丢一条用量就等于丢一笔钱"，而它的唯一出口是一行日志。** 要发现它，你得：
1. 先想到要去 grep `用量落库失败`；
2. 并且在一个可能几百 MB 的日志文件里捞；
3. 并且**每天都要捞一次**（因为它不会累积成一个"计数"）。

**注释里那句"需人工补录"是关键——它明确承认了"这件事需要人来做"，但没有给出任何人能做的工具。** 一个 `metering_failed_total` 计数器只需要三行代码，而它能让"今天丢了几笔账"变成一个可以直接看的数字。

**第三类：`AggregateTracer` 的"指标是死的"时期**（本讲 2.1）。

**三类的共同结构**：

| 类 | 数据有吗 | 有出口吗 | 能被发现吗 |
|---|---|---|---|
| 额度拒绝 | ✗ **没有** | ✗ | ✗✗ **完全不可见** |
| 计量失败 | 部分（日志里） | ✗（日志不是指标） | △ 需要主动 grep |
| 死指标 | ✓（内存） | ✗（当时） | ✗ **无症状** |

**修法的通用形态是同一个：让"失败/拒绝/不可用"成为一个可聚合的计数。**

```java
// 思路：三类都应该变成"能被查询的数字"，而不是"能被 grep 的字符串"
metrics.counter("gateway.rejected", "reason", "QUOTA_EXCEEDED", "tenant", tenant).increment();
metrics.counter("metering.failed", "provider", providerCode).increment();
metrics.counter("llm.trace.unavailable").increment();     // 或者用 gauge 暴露装配状态
```

### 2.9 该开的没开、该关的全开：actuator 的两面

`token-factory` 的 actuator 配置：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      show-details: always
```

**只有两个端点被暴露**（`health`、`info`）—— 这个"最少暴露原则"是对的。但结合第 31 讲发现的"`/actuator/**` 没有挂任何鉴权拦截器"，就得到一个奇特的状态：

| 配置项 | 值 | 从可观测性角度 | 从安全角度 |
|---|---|---|---|
| `exposure.include: health,info` | 只开 2 个 | ✓ 够用（health 用于探针） | ✓ 暴露面小 |
| **`show-details: always`** | **详情全开** | ✓ 排查方便 | ✗ **健康详情匿名可见** |

**`show-details: always` 会暴露**：数据库连接信息（URL 的 host/port、连接池状态）、磁盘空间、各组件的健康明细。这些信息在**一个没有鉴权的端点上**是可读的。

**所以正确组合是两条一起改**：

```yaml
# 思路：要么给 actuator 加鉴权，要么把详情收起来（或两者都做）
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      show-details: when-authorized     # 而不是 always
```

**"该开的没开、该关的全开"** —— 这个说法在这里是字面成立的：

- **该开的**：`token-factory` **自己有一份很好的运维视图**（`AdminHealthController`，含熔断状态、`usable`、剩余冷却时间），它在 `/api/admin/health` 下，**有鉴权** ✓
- **该关的**：actuator 的 `health` 详情**没有鉴权**，而它还开了 `always`

**所以这个项目的运维视图分裂成了两份**：一份安全但"不在标准位置"（`/api/admin/health`），一份在标准位置（`/actuator/health`）但不安全。

**这不是"多写了一份代码"，而是"两个服务于不同目的的东西被打散了"**：

| 端点 | 目的 | 消费者 | 该有的保护 |
|---|---|---|---|
| `/actuator/health` | **存活/就绪判定** | k8s、负载均衡 | **可以匿名**（但详情要收） |
| `/api/admin/health` | **运维排查** | 人、监控系统 | **必须鉴权** |

**"探针端点"和"排查端点"是两个不同的东西，它们的访问策略天然不同。** 把两者混成一个端点（既给 k8s 探针用、又给人排查用），就必然要在这两个需求之间做妥协——**而最常见的妥协结果就是"为了探针能用，把鉴权去掉"。**

**正确做法是拆成两个端点**（各自明确的访问策略），而不是"一个端点两边凑合"。

## 三、避坑清单

- [ ] **可观测性三段链：埋点 → 出口 → 消费，缺一段等于零。** 其中"缺出口"最危险——它**没有任何症状**。
- [ ] **加了埋点，就要在同一次提交里加端点。** 否则你会得到一个"指标是死的"的系统，而且你不知道它死了多久。判据："这个数据写在哪个字段里？谁能读到它？"
- [ ] **可选依赖缺失时，端点要返回 `unavailable` + `reason`，不要返回空对象。** "没数据"和"没装"必须能区分。
- [ ] **"全部合格"类的判定必须补"非空"条件。** 空集合会让 `allMatch` 恒为 true——一个"什么都没配"的实例会报 `UP`。
- [ ] **健康检查的判据要按"实例还能不能服务"来定，而不是"有没有组件不健康"。** 有冗余时，部分组件 OPEN 仍然是 UP。
- [ ] **同时暴露"运行状态"和"配置状态"。** "没有失败"和"没有使用"在监控上长得一模一样，而处置完全相反。
- [ ] **把判断条件算成字段（`usable`），不要让运维做布尔代数。**
- [ ] **告警要带"剩余时间"和"计数"，不只是"状态"。** "熔断了"不足以做决策，"还剩 12 秒"和"刚触发"才够。
- [ ] **有现成的查询 API 就别手写等价逻辑。** 手写版本不会跟着 API 的默认值策略一起演进。
- [ ] **字段会持续增长的响应别用 `Map.of` 拼。** 它有 10 键上限（编译期挡住），而且字符串键名没有编译期检查——运维端点是给机器消费的，用 record。
- [ ] **"吞异常 + 打日志"的失败路径必须配一个计数器。** 日志不是指标：不可聚合、不可画图、不可告警。判断标准："这个失败今天发生了几次？"如果答案是"得去 grep 日志"，就补计数器。
- [ ] **"被拒绝的请求"必须计数。** 否则"拒绝率 100%"在监控上表现为"调用量下降"——**把攻击读成健康。**
- [ ] **探针端点和排查端点分开。** 前者的访问策略可以宽松，后者必须严格；混在一起的结果通常是"为了探针能用把鉴权去掉"。
- [ ] **`show-details: always` 要配合鉴权一起考虑。** 健康详情会暴露连接串、连接池、磁盘状态。

## 四、动手任务

> **目标**：找出你项目里"数据有、出口没有"的地方，并给两类"看不见的失败"补上计数。

**步骤 1：盘点三个端点的实际输出**

对 `token-factory`（或你自己的服务）逐个探测：

```bash
# 1) 标准探针端点（无鉴权）
curl -s localhost:8090/actuator/health | head -c 800; echo

# 2) 项目自建的运维视图（有鉴权）
curl -s localhost:8090/api/admin/health -H "X-Admin-Key: $TF_ADMIN_KEY"; echo

# 3) 供应商级明细（含熔断状态）
curl -s localhost:8090/api/admin/health/providers -H "X-Admin-Key: $TF_ADMIN_KEY"; echo
```

**预期结果**：对比三者的**信息粒度差异**，并回答：

- `/actuator/health` 暴露了哪些"不该匿名可见"的细节？（`show-details: always` 的效果）
- `/api/admin/health/providers` 里，`usable = false` 的供应商有几个？（如果有，那就是"配了但没生效"）
- 有多少个供应商 `circuit = CLOSED` **且**没有任何调用记录？（**"没有失败"与"没有使用"的区分**）

**关键对照**：如果第 3 个问题的答案不是"0 个"，你就找到了一个"在监控上看起来健康、实际从未被使用"的供应商——**这正是 `usable` 与"配置状态"字段存在的意义。**

**步骤 2：找出"数据有、出口没有"的组件**

```bash
# 找内存里累计、但没有端点暴露的组件
grep -rn "class TokenUsageRecorder\|class AggregateTracer\|snapshot()\|byOperation()" \
  code-review-agent/src/main/java
# 再查这些方法被谁调用
grep -rn "\.snapshot()\|\.byOperation()" code-review-agent/src/main/java
```

**预期结果**：列出每个"累计器"和它的读取方。

**关键对照**：对每一个累计器问："**除了这个端点，还有别的地方读它吗？**"

- **有** → 如果那个地方是业务逻辑（比如用它做决策），它就不是"可观测性数据"而是"业务状态"（那这条就不用改）；
- **没有** → 它**只**为可观测性存在。那么"有没有端点"就是它有没有价值的唯一判据。

**这一步的价值在于建立一个习惯：每次加埋点时，顺手 grep 一次"谁在读它"。**

**步骤 3：给"计量失败"补一个计数器**

这是本讲最实际的一个改动。现在 `MeteringService` 的失败路径只有一行日志：

```java
log.error("用量落库失败（业务调用已成功，需人工补录）：traceId={} provider={} 原因={}",
        record.traceId(), record.providerCode(), e.getMessage(), e);
```

**改法**：加一个计数器，并让它出现在健康端点里。

```java
// 思路：让"今天丢了几笔账"变成一个可查询的数字
private final AtomicLong failedRecords = new AtomicLong();

public void record(UsageRecord record) {
    try {
        usage.insert(record);
    } catch (RuntimeException e) {
        long total = failedRecords.incrementAndGet();
        log.error("用量落库失败（业务调用已成功，需人工补录）第 {} 笔：traceId={} provider={} 原因={}",
                total, record.traceId(), record.providerCode(), e.getMessage(), e);
    }
}

/** 供运维视图暴露：丢了多少钱（笔数）。 */
public long failedRecords() {
    return failedRecords.get();
}
```

**然后在 `AdminHealthController.overview()` 里加一个字段**：

```java
"meteringFailed", metering.failedRecords(),
```

**关键对照**：改完之后，**故意制造一次落库失败**（比如把用量表临时改名，或者注入一个必然失败的 SQL），然后：

1. `curl /api/admin/health` → **应当看到 `meteringFailed: 1`**；
2. **不需要 grep 任何日志**就能知道"丢了一笔账"。

**验收标准**：**这个数字能被直接读到，且不依赖日志轮转**。这一步做完，你就把"需人工补录"从一句注释变成了一个可监控的事实。

**步骤 4：给"额度拒绝"补计数**

```bash
# 找到拦截点
grep -rn "QuotaExceededException\|anyRejected" token-factory-server/src/main/java
```

**预期结果**：`GatewayService.complete` 里的两行（`quota.evaluate` + `throw`），**位于 `try` 之外**。

**改法**：在抛出前记一条（或者累加一个按租户的计数器）。

**关键对照**：改完后做一个对照实验——

1. 先把某个租户的额度设成 1（必然超限）；
2. 打 100 次请求；
3. **看 `/v1/usage/summary` 的调用量**与**你新加的拒绝计数**分别是多少。

**预期结果**：`summary` 里的调用量**不会涨到 100**（因为被拦的不落库），而你的新计数器**应该正好是 100**。

**如果两者相差 100，你就亲手量化出了"看不见的那部分流量"有多大。**

## 本讲小结

1. **可观测性 = 埋点 + 出口 + 消费，三段是"与"的关系。** 最危险的是"缺出口"——它没有任何症状，只表现为"数据活着但不产生结论"。
2. **这个项目留下了一条极诚实的历史注释**："此前该聚合器只在内存累计、无任何端点可读（文档 8 节标注的「指标是死的」）"——**"指标是死的"不是说没数据，是说数据不产生可用结论。**
3. **可选依赖的正确姿势**：`@Autowired(required = false)` + 字段注释写明"可能未装配" + **端点返回 `unavailable` 并带 `reason`**。"没数据"和"没装"必须能区分。
4. **健康判据要按"实例还能不能服务"来定**：`degraded = totalProviders == 0 || healthy == 0`——**"部分 OPEN 仍是 UP"**（有冗余）；**"一个都没配也算故障"**（防空集合让 `allMatch` 恒为 true）。
5. **运行状态与配置状态要一起暴露。** "`circuit = CLOSED` + 零调用" = 从未被路由到（去查配置），而它在监控上与"运行良好"完全一样。
6. **`usable = enabled && keyPresent` 是把判断条件算成字段的范例。** 运维在凌晨 3 点不想做布尔代数。
7. **告警需要"状态 + 剩余时间 + 计数"三件套。** 只有"熔断了"不足以决策。
8. **★ 有现成 API 不用**：`AdminHealthController` 手写 O(n) 线性查找 breaker，而 `CircuitBreakerRegistry.stateOf()` 就是 O(1) 的现成方法，且默认值策略一致。
9. **★ `Map.of` 正好 10 键**——它卡在重载上限。再加一个字段就编译失败，必须换 `ofEntries`。**字段会持续增长的运维响应应该用 record**（还能避免字符串键名的拼写错误）。
10. **★ 三类"看不见的失败"**：额度拒绝**不落库**（完全不可见）、计量失败**只有日志**（需主动 grep）、死指标**无症状**。**三者的修法是同一个：让失败成为一个可聚合的计数。**
11. **探针端点与排查端点必须分开。** `token-factory` 的运维视图分裂成 `/actuator/health`（标准位置但不安全、`show-details: always`）与 `/api/admin/health`（安全但不在标准位置）——**"为了探针能用而把鉴权去掉"是这种混用最常见的代价。**

**模块五到此结束。** 你现在有了一个"平台方视角"的完整能力：**分层（能被人引进去）、门锁（fail-closed）、账本（成本计量）、缺口补录（用量上报）、韧性（熔断退避）、防线（注入检测）、眼睛（可观测性）。**

从第 37 讲开始进入模块六——**把它真正交付出去**：存储选型的取舍、事件接入与平台回写、一键自托管部署、效果评测与误报治理，最后是**从项目到面试的话术地图**。
