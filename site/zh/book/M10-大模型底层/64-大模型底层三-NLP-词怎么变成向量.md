## 一、痛点

你在 M4 已经踩过一堆 RAG 的坑：相似度铁律、混合检索、中文分词。但可能没问过最底下的那个问题：**"凭什么向量能表示语义？凭什么两个词相近可以用一个数字（余弦）算出来？"**

这带来两个隐性痛点：

**痛点一："检索比字符串就行，为什么要向量？"** 你可能会觉得"关键词匹配便宜又快"，大不了做分词。→ 但字符串匹配对**同义不同形**（"汽车"vs"车"、"成本"vs"开销"）完全无能为力，这正是第 25 讲"稀疏路漏同义不同词"要补盲区的根本原因。

**痛点二："向量是个黑盒子，我用就完了，不用懂。"** 于是你不理解为什么第 27 讲"余弦和排名分必须分开放"、为什么第 24 讲"维度对不上就毁数据"——**这些"坑"的根，都在"向量"这两个字上**。

本讲要破除"检索匹配够用"和"向量是黑盒"两个错觉。真相是：

> **语言进模型的第一站是『变成向量』——一个让词的『意义』可以被数学表达的数字点。** 同义词因为"经常在相似上下文里出现"，被训练成在向量空间里靠近。你的 RAG 用向量近似去算"谁和谁语义接近"，正是借用了模型内部对语言的这种表示。**它不是黑盒，是一条可理解、可比较的『语义数值化』。**

## 二、原理

### 2.1 从"符号"到"向量"：语义被搬进数字

人眼里的"汽车"和"车"是同一个东西；但对一台只认字符串的机器，它们是两个完全不同的字符串。要让机器理解"相近"，就必须给每个词一个**数字表示**，而且这个数字表示要**反映词义**。

于是有了**词向量（word embedding）**。实现上，它就是一张**巨大的查找表（lookup table）**：

```
E ∈ R^{|V| × d}      |V| = 词表大小（几万到十几万），d = 向量维度（几百到几千）
```

每个词在词表里占一行、对应一个 d 维向量。"把一个词编码成向量"这个动作，本质就是**用词的 ID 去这张表里取一行**。所以严格说，模型一开始并不知道"汽车"和"车"有关系——**它们各自是表里互不相干的两行**。

"有关系"这件事，是第 63 讲那套训练**压出来的**：通过训练，让**语义相近的词在向量空间里靠得近**：

```
   汽车 的向量 ≈ 车 的向量        （同义，靠得近）
   汽车 / 车 与 香蕉 的向量差很远   （异义，离得远）
```

**这一招是 NLP 从"规则"迈入"学习"的分水岭**——从此机器不再靠穷举规则，而是靠"语义在数字空间的度量"来理解语言的相近性。

### 2.2 向量凭什么"学会"语义：分布假设 + 对比训练

有算法背景的你自然要追问：**训练时靠什么信号，让"汽车"和"车"挤到一起的？** 答案是语言学里一条经典判断——**分布假设（distributional hypothesis）**：

> **"语义相近的词，出现在相似的上下文里。"** "汽车"和"车"几乎可以在同一句话里互换（"我开___上班"、"___停在路边"），而"香蕉"不行。把这些"共现模式"喂给模型，它就学到了词义。

经典算法 **Word2Vec** 把这个假设变成两个可训练的目标：

- **CBOW（连续词袋）**：用**周围词**预测**中心词**。
- **Skip-gram**：反过来，用**中心词**预测**周围词**——实践中更常用，对低频词更友好。

而真正让它算得动的，是两个工程技巧：

1. **负采样（negative sampling）**：满词表算一遍 softmax 太贵，于是每次训练不更新全部 |V| 行，只更新"正样本（真实共现的那对）"加随机抽几个"负样本（乱配的对）"。**把"软归一化"变成了"二分类对比"**——让正样本的向量靠拢、负样本的向量推开。这正是现在所有"对比学习 + 负样本"思路的鼻祖（第 67 讲 CLIP 也是同一招）。

2. **这个"靠拢/推开"的几何度量，就是向量夹角**。它引出了你在 RAG 里天天用的 **cosine 相似度**：

```
cos(u, v) = u·v / (‖u‖·‖v‖)  ∈ [−1, 1]
```

**为什么用余弦而不是欧氏距离**：余弦只关心"方向"、不关心"长度"。两个向量方向越一致，cos 越接近 1；正交则 0；反向则 −1。**在 RAG 里"语义接近"通常更看方向而非绝对距离**，所以 pgvector 的相似度默认按余弦/内积，这就是数学根源（第 24/27 讲的维度契约、相似度语义都挂在这条式子上）。

### 2.3 词表从哪来：BPE 子词分词，让"没见过的词"也能有向量

前面说"每个词占一行",但自然语言有无穷多的词（新词、拼写变体、中文人名）。**不能真按"词"建表，否则词表爆炸、且遇到生词就废。** 现代大模型的解法是 **BPE（Byte-Pair Encoding，字节对编码）**：

```
从"字符级"开始，反复把语料里"出现频次最高的相邻字符对"合并成一个新子词，
直到词表达到目标大小（几万到十几万）。
```

- "unhappiness" 可能被切成 `un` + `happiness`（或更细 `un` + `happi` + `ness`）；
- 于是**任何词都能由一小组子词拼出来**——生词也不再是"查不到"，而是"拆成见过的子词"。

**这一层和你的工程直接相关**：第 62 讲的"token"、第 32 讲的"token 计费"、为什么中文 token 比英文"贵",全在分词这层被决定。**同一个模型，切得越碎 → token 越多 → 越贵、越占上下文**；中英混排、代码、数字的切分规则，直接决定你一次调用花多少钱。**你买的"token",其实是"这个模型分词的产物"**——这是 NLP 给你扣费账单的第一课。

**BPE 合并算法手算：三步看懂词表怎么长大。** 用一个极简语料走一遍 BPE 的前 3 次合并，你就彻底懂了：

> **初始词表**（字符级）：a, b, c, d, e, f, g, h, i, ...（字母表 + 特殊标记）
> **语料**（词频）：`low`×5, `lower`×2, `newest`×6, `widest`×3
> （实际 BPE 是在字符序列上操作，这里简化为词级演示）
>
> **第 1 步**：统计所有相邻字符对的频次。`es` 在 `newest`(6) + `widest`(3) = 9 次，是最高频对。**把 `es` 合并成一个新 token**，加入词表。
> - `newest` → `n e w es t`，`widest` → `w i d es t`
>
> **第 2 步**：重新统计。`est`（`es` + `t`）在两个词里共出现 9 次，最高频。**合并 `est`**，加入词表。
> - `newest` → `n e w est`，`widest` → `w i d est`
>
> **第 3 步**：重新统计。`lo` 在 `low`(5) + `lower`(2) = 7 次，最高频。**合并 `lo`**。
> - `low` → `lo w`，`lower` → `lo w e r`
>
> **……继续合并几万次，词表从几百个字符长到几万/十几万个子词。**

**从这个手算里你能读出三件事**：**① BPE 是纯统计的、确定性的**——给同样的语料和目标大小，任何人跑出的词表一样（这也是为什么模型发布时必须同时发布 tokenizer 权重的原因）；**② 合并顺序决定了切分粒度**——越早合并的对越"黏"，越晚合并的越容易被拆开；**③ 低频词一定会被拆碎**——这既是 BPE 的优点（生词也能表示），也是它的代价（低频词切成很多碎片，token 数暴增）。

### 2.4 词表设计决策树：大小、算法、语言覆盖怎么选

词表设计不是"拍一个数字"，它是一连串工程权衡。一棵决策树帮你理解每个模型为什么这样选：

```
词表多大？
├─ <50K     → 英文单语模型（早期 GPT-2/3 的水平）
│              优点：embedding 矩阵小，训练信号集中
│              缺点：多语言碎得厉害，中文/代码尤其贵
├─ 100K 左右 → 多语言通用（Llama 3: 128,256）
│              优点：兼顾中英文，生态最成熟
│              缺点：中文仍然偏碎（约 1.5–2× 英文 token 数）
└─ 150K+    → 多语言+多模态强化（Qwen2: 151,643；DeepSeek-V3: 129K+）
               优点：中文/代码/特殊符号覆盖好，fertility 低
               缺点：embedding 矩阵大（参数量增加约 20%），稀疏 token 训练信号弱

用什么算法？
├─ BPE      → GPT/Qwen/Llama 系主流
│              优点：确定性、实现简单、推理快
│              缺点：合并是贪心的，未必全局最优
└─ Unigram  → T5/Gemma/部分多语言模型
               优点：可以输出多种分词候选（更适合 beam search 解码）
               缺点：训练复杂，推理略慢

中文怎么处理？
├─ 纯 BPE 字节级 → Llama 系列
│   （中文按字节切，一个字拆 2–3 个 token）
│   → 成本高，但英文/代码表现稳
└─ 中文字符级 BPE → Qwen/DeepSeek 系
    （中文字符整体保留，再按子词合并）
    → 中文 token 数少 30–50%，更便宜更高效
```

**工程判据**：**选型模型时，别只看参数量和 benchmark 分数，先拿你业务的真实语料跑一次 tokenizer，算 fertility（平均每个汉字/每个单词多少 token）**——这个数字直接乘进你的账单和延迟，比跑分榜上的零点几分差距重要得多。

### 2.5 词向量在模型里 vs 在检索里：同一条线两端

**在模型里**（面向生成）：模型输入不是"文字本身"，而是每个 token 的向量（第 2.3 节 BPE 切完 → 第 2.1 节查表取向量）。模型在这些向量上做第 65 讲的注意力运算，理解整句话的"意思"，然后预测下一个 token。

**在你的 RAG 里**（面向检索）：你同样把文档和查询变成向量，用 **cosine / 内积**算"谁和谁语义接近"，召回"语义相关"的文档——这是第 22–29 讲整套 RAG 的根基。

**关键洞察**：模型与你的 RAG **用的是同一个『语义=向量近疏』的假设**，只是方向不同——模型向前用来生成，你的检索向后用来召回。**读懂这一层，你就明白为什么 RAG 需要嵌入模型、为什么向量维度是三方的契约（第 24 讲）、为什么相似度只有序有意义（第 27 讲）。**

### 2.6 中文的特殊关卡：没有空格

向量这条路，英文很顺（BPE 也是按字符/子词去并，天然无空格障碍）。但**中文的坑在"分词"和"向量"的接缝处**：

> 中文没有空格，一个字串怎么切成"词"直接决定语义。你的 `TextTokenizer` 用 **bigram（二元组）** 切中文、用**子词**切标识符——这就是"先分词、再向量"在中文场景的工程落地。

这里有个容易被忽略的深层问题：**如果分词切错了，"汽车"和"车"根本连不成相近的向量，语义检索必然失准**。第 26 讲"中文不能当英文处理"、bigram 方案的由来，以及"写入与检索两侧必须同用 TextTokenizer"的铁律，**根都在本讲的"词→向量"**：两边分词口径不一致，等于在对比两个不同向量空间里的东西，相似度自然乱掉。

**判据句**：**凡是要"比语义"的地方，都要先把符号变成有语义的向量，并且先解决"怎么切词/建模词表"**——这是 NLP 给 RAG 的第一定律，也是第 26 讲所有中文之坑的源头。

### 2.7 前沿深挖：词表设计是大模型的"隐藏架构决策"，中文用户要为它付费

词表大小和分词算法是模型发布时最少被讨论、但影响最直接的决策之一：

**① 词表大小是一笔三方交易。** 词表大 → 序列变短（省算力、省 KV cache）→ 但 embedding 矩阵变大（参数多）且每个 token 的训练信号变稀疏。2024 年后主流模型的选择明显分化：**Llama 3 词表 128,256**，而 **Qwen2 词表 151,643**（官方文档明确承诺"无 unknown token，任意多语言文本可完整编码"）。Qwen 多出来的两万多个 token 相当一部分是给中文/多语言的高频片段——**这就是"同一段中文，Qwen 切的 token 数通常比 Llama 少 20–40%"的结构性原因**。选型时这不是小事：token 数直接乘进你的账单和延迟。

**② 分词算法有客观的评测框架了。** BPE（GPT/Qwen 系）、Unigram（T5/Gemma 系）、SentencePiece（工具链而非算法）长期靠信仰争论。2024 年的 Qtok（[arXiv:2410.12989](https://arxiv.org/abs/2410.12989)）把三者放进统一框架，按**语言覆盖、压缩率（fertility，每词平均 token 数）、多语言公平性**量化比较。对你的实操意义：**接入一个新模型前，先拿你业务的真实语料测 fertility**——十行代码的事，却能提前暴露"中文成本比英文贵 2 倍"这类账期惊喜。

**③ 分词器一致性是线上事故的隐形炸弹。** 训练用一套分词、推理用另一套（比如训练 tiktoken、推理 HuggingFace tokenizers），某些边界样本会切出不同 token 序列，模型行为随之漂移且极难排查。**判据：训练侧与推理侧的分词器实现、版本、特殊 token 表必须逐项对齐并锁版本**——这与第 26 讲"写入/检索两侧必须同用 TextTokenizer"是同一个铁律在两个层面的投影：检索层如此，模型层亦如此。

## 三、避坑清单

- [ ] **别想用纯字符串匹配做语义检索**——它对同义不同形无能为力，这是第 25 讲稀疏路盲区的根。
- [ ] **别把向量当黑盒**——它表达"语义近疏",理解它你才懂相似度、维度、一致性那些坑。
- [ ] **分词是向量化的前置**——中文不先切好词，向量一定不靠谱（第 26 讲）。
- [ ] **全系统字词统一分词口径**——写入检索两侧同用 `TextTokenizer`，否则语义不统一（第 26 讲）。
- [ ] **把"语义=向量近疏"作为判断设计成不成立的工具**——比如"这条路要不要向量",先问"有没有语义近似需求"。

- [ ] **验证分词一致性的快速方法**——取 10 条真实查询，分别用写入侧和检索侧的 tokenizer 切词，结果必须完全一致；不一致的地方就是语义对不齐的源头。
## 四、动手任务

> **目标**：用 "词→向量" 的眼光，验证并解释你 RAG 的一个设计。

**步骤 1：解释你的一个检索选择**

挑你系统里一个**用向量近似**的地方（如查询召回），用本讲的因果链讲清：**为什么这样能召回"语义相近"的内容？** 讲不清，说明你还没真懂向量这条线。

**步骤 2：验证分词口径**

确认你的检索在**写入与查询两侧用了同一个 `TextTokenizer`**（第 26 讲），并找一个"同义不同形"的正例，验证它能被召回。

**步骤 3：给"要不要向量"立判据**

给你系统里下一个"要不要引语义检索"的决策点，用"有没有同义/语义近似需求"判断，而不是看热不热闹。

## 本讲小结

1. **NLP 的基石是"把符号变成有语义的向量"**——同义词在向量空间里靠近。
2. **模型用向量向前生成，你的 RAG 用向量向后召回**——是同一条线的两端。
3. **中文没有空格，要先分词**——这就是第 26 讲所有坑的源头。
4. **"语义=向量近疏"是 RAG 的第一性**——帮你判断一个设计该不该用向量、以及那些相似度的"坑"为什么存在。
5. **分词要全系统同一口径**，否则语义不一致。
