# 人机协作工作流

审查输出只有在**可以被执行和被纠正**时才有价值。状态机拥有每个审查项的完整生命周期，人在关键决策点介入。

## 状态与转移

工作流引擎定义了 11 个状态 × 19 条转移 × 4 类角色（作者、审查者、管理者、QA）：

```
SUBMITTED ──► IN_REVIEW ──► APPROVED ──►（完成）
    │              │
    ▼              ▼
REJECTED ◄──（返工闭环）◄── 再次 SUBMITTED
    │
    ▼
ASSIGNED ──►（修复）──► SUBMITTED
```

关键转移：

- 人工驳回 `SUBMITTED` / `IN_REVIEW` → `REJECTED` → 回到 `ASSIGNED`（返工）
- 已通过项抽检不合格 → `ASSIGNED` 并带抽检标记
- 任意在途项可走 `EXCEPTION` → `ASSIGNED` 人工恢复

转移矩阵穷举测试——440 种组合，覆盖 11 个测试类。

## 误报反馈闭环

审查者把发现判为误报时，信号回灌规则库：

- 记录该发现的规则 id 与驳回原因
- 同一规则反复被驳回会降低严重级别
- 知识库存入驳回作为负例

长期下来，规则集会收敛到你的团队真正在意的内容。

## 抽检

QA 可以抽取已通过的审查做抽检。不合格的抽检把项翻回 `ASSIGNED` 并带 `SPOT_FAIL` 标记，审计轨迹完整保留。

## 可追溯

每次转移都记录进带 traceId 的轨迹日志——"谁因何驳回"端到端可回放。
